## Findings

### [BLOCKING] container_path off by one `.parent` — affects Cards 3, 9, 12, 16, 18, `_build_tokens`
**Location:** Batches 01–04, every site that computes `container_path`
**Issue:** In the new layout the main worktree lives at `<container>/wts/<repo>`. Therefore `resolve_main_worktree_root(git_root).parent = <container>/wts` — the *worktrees dir*, not the container. The plan calls this value `container_path` and then uses it in expressions that require `<container>` (e.g. `container_path / "wts" / slug` → `<container>/wts/wts/<slug>`; `container_path / "portals" / slug` → `<container>/wts/portals/<slug>`; `discover_active_worktrees(container_path / "wts")` → `<container>/wts/wts`). Concretely affected sites:
- Card 3: `resolve_active_worktree(container_path, slug)` returning `container_path / "wts" / slug` requires `container_path = <container>`, but the derivation gives `<container>/wts`.
- Card 9: portal created at `container_path / "portals" / slug` lands under `wts/portals/` instead of `portals/`.
- Card 12: `_review_common.resolve_path` derives `container_path` the same way, then calls `resolve_active_worktree` with the wrong value.
- Card 16: `discover_active_worktrees(container_path / "wts")` walks `<container>/wts/wts`, an empty phantom directory.
- Card 8 / `_build_tokens`: `"CONTAINER_PATH": str(git_root.parent)` = `<container>/wts` after migration; junction targets referencing `<CONTAINER_PATH>/portals/…` point at the wrong tree.
**Fix:** Replace all `resolve_main_worktree_root(git_root).parent` with `resolve_main_worktree_root(git_root).parent.parent` at every site where `container_path` is intended to be the top-level container directory (parent of `wts/`). Equally, update `_build_tokens` to `git_root.parent.parent` for `CONTAINER_PATH` in the new layout. The Card 3 function body and Card 16 call site become correct once the derivation is fixed.

### [NIT] Card 5: `render_block` "overload" lacks a Python implementation strategy
**Location:** Batch 01, Card 5, `_gitignore.py`
**Issue:** Python has no overloading. Keeping `render_block(hardlink_entries)` (one arg) while adding `render_block(glob_entries, anchored_entries)` (two args) results in the second definition silently replacing the first, breaking the preserved legacy call sites.
**Fix:** Specify the implementation pattern — the simplest approach is `render_block(entries_or_glob, anchored_entries=None)` with the `anchored_entries is None` branch replicating the old single-list behaviour; both `upsert` and `upsert_split` call the same function with different arities.
