## Findings

### [BLOCKING] Card 4 setUp provides no reference to subprocess mock for Test 4 inspection
**Location:** Batch 02, Card 4, Test 4
**Issue:** The setUp spec describes patching `millpy_implement.subprocess` via `patch.object(...).start()` with `addCleanup(p.stop)`, but never saves the returned mock object. Test 4 requires inspecting `subprocess.run.call_args_list` to assert the review file was staged — that assertion is impossible without a stored reference (`self.mock_subprocess = p.start()`).
**Fix:** In the setUp patch-list description, specify that the return value of `.start()` is saved as an instance attribute (e.g., `self.mock_subprocess`) for each patch that any test method must inspect.

### [NIT] Card 3 silent about module-level `uuid`/`subprocess` imports
**Location:** Batch 01, Card 3
**Issue:** Card 3 says "imports inside main" following `millpy-review-code.py`'s pattern, but Card 4 patches `millpy_implement.uuid.uuid4` and `millpy_implement.subprocess.run` — both require module-level bindings. If an implementer puts `import uuid` inside `main()`, the Card 4 mock silently no-ops and tests pass for the wrong reasons.
**Fix:** Card 3's requirements should explicitly state that `uuid` and `subprocess` are imported at module level alongside `json`, `sys`, `argparse`, and `Path`.

### [NIT] Card 4 subprocess mock qualifier implies conditional side_effect
**Location:** Batch 02, Card 4, setUp
**Issue:** The mock description says "whenever the first argv element is `'git'`", which reads as a conditional `side_effect`. All subprocess calls in the CLI are git commands, so a plain `return_value` is correct. The conditional qualifier is misleading and could lead the implementer to write an unnecessary `side_effect` function.
**Fix:** Replace the qualifier with "all subprocess.run calls in the CLI are git commands; use `return_value`".

### [NIT] Card 1 fix template leaves session_id retrieval ambiguous on resume
**Location:** Batch 01, Card 1
**Issue:** `implementer-brief.md` instructs the implementer to read session_id from `--session-id` argv. On a `--resume` invocation, `--session-id` is absent. Card 1 says to instruct "(5) report the same JSON shape as before" but doesn't clarify that the implementer should recall the UUID from session context rather than re-reading argv.
**Fix:** The fix template should include an explicit note: session_id is the UUID from the original spawn, already in session context — do not attempt to re-read `--session-id` from argv.
