## Findings

### [BLOCKING] Two-worktree test fires real subprocess via unguarded `find_open_vscode_paths`
**Location:** Batch 2 / Card 4
**Issue:** Card 4 prohibits modifying the existing two-worktree test, but the new default flow calls `_filter_open_worktrees` → `_vscode_processes.find_open_vscode_paths()` before showing the unified prompt. The two-worktree test does not mock this symbol, so a real `powershell`/`ps` subprocess fires on every unit-test run, violating the hermetic subprocess-mocked pattern every other test in the file follows. The test will likely pass (temp paths won't match any running VS Code process), but it makes the suite non-hermetic, slow on Windows with cold PowerShell starts, and theoretically flaky if CI opens paths under the system temp dir.
**Fix:** Add `patch("mill_vscode._vscode_processes.find_open_vscode_paths", return_value=set())` to the two-worktree test's `with (...)` patch chain. Narrow the Card 4 prohibition to "do not modify assertion logic, fixture setup, or expected paths" — not "do not touch the patch chain", since the patch chain must grow whenever the code under test acquires a new external call.

### [NIT] `_path_matches_cmdline` loop initialization left implicit in requirements
**Location:** Batch 1 / Card 1
**Issue:** Requirements say "scan the haystack with `hay.find(needle, idx)` in a loop" without showing that `idx` is initialised as `hay.find(needle)` (not 0) before the `while` loop. The discussion.md pseudocode is unambiguous, but batch-level requirements are meant to be self-contained; an implementer reading only the batch file must infer the initialization.
**Fix:** Add the explicit assignment `idx = hay.find(needle)` immediately before `while idx != -1:` in the requirements prose, matching the pseudocode in `discussion.md`.
