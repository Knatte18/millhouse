## Findings

### [NIT] Card 1 -- resolve_task_path shim: cfg_relative_path argument contract is implicit
**Location:** `task/plan/01-resolve-task-path-shim.md`, Card 1 (`_paths.py` shim definition)

**Issue:** The plan names the parameter `cfg_relative_path` but does not show what callers actually pass. After Card 8 changes `wiki/config.yaml` to `discussion_file: _mill/discussion.md`, a caller that passes the raw config value to the shim and the shim then prepends `task/` would produce `task/_mill/discussion.md` -- wrong. The shim must either (a) receive the stem only (`discussion.md`) with callers pre-stripping the prefix, or (b) path-swap `_mill/` -> `task/` in the received string rather than prepend.

**Fix:** Card 1 should include the exact shim body and one worked call-site example. The Card 2 diff for `_review_common.py` should show what string is passed so reviewers can verify the contract holds across Card 8's config rename.

---

### [NIT] Batch 4 -- portal removal timing gap for normally-cleaned-up tasks
**Location:** `task/plan/04-cleanup-orphan-scan.md`

**Issue:** Batch 4 adds `orphan_portals` to `CleanupPlan` and removes dangling portals during `apply_plan`. But if `apply_plan`'s existing done/abandoned worktree-removal path does not also remove `portals/<slug>`, that portal becomes a dangling junction between the worktree removal and the next mill-cleanup run that triggers the orphan scan. Batch 3 is the first time portals are written by mill-spawn/claim, so there is no pre-existing removal path to rely on.

**Fix:** Confirm that at least one batch 3 or batch 4 card adds `portals/<slug>` removal inside the normal worktree-removal block of `apply_plan`, not only inside the orphan-removal block. If missing, add a sub-card.

---

### [NIT] Card 20 -- pre-existing wiki/active/ directories: no operator guidance
**Location:** `task/plan/03-portals-junctions-hardlinks.md`, Card 20 (remove `wiki_active_dir` from `SlugRecord`)

**Issue:** Dropping `wiki_active_dir` tracking means `wiki/active/<slug>/` directories created by tasks that ran before this merge are never collected. The plan acknowledges this is a one-time artifact, but no updated SKILL.md or note tells operators how to reclaim the space.

**Fix:** Add one bullet to the Batch 6 mill-cleanup SKILL.md update noting that operators on pre-33 hubs may find stale `wiki/active/` subdirectories and can delete them manually with `rmdir /s /q` (after confirming no junction points into them).
