### [BLOCKING] Batch 5 leaves existing ERROR-path tests contradicting the new code behavior

**Location:** Batch 5 / Cards 9, 10, 11 (test-review-code-flow.py Tests 9, 10, 11; test-review-plan-flow.py Test 16)
**Issue:** Card 9 changes `_review_code.run` so all-ERROR `reviews[]` → top-level `verdict == "ERROR"`. Card 10 aligns `_review_plan.run` the same way. But Tests 9, 10, and 11 in `test-review-code-flow.py` each assert `r.verdict == "REQUEST_CHANGES"` on the LLMError path — which is exactly the all-ERROR scenario. Test 16 in `test-review-plan-flow.py` does the same. Card 11 then adds *new* tests that correctly assert `verdict == "ERROR"` for the same scenario, creating a direct contradiction. The verify command for Batch 5 (`test-review-code-flow.py && test-review-plan-flow.py`) will fail because the new behavior contradicts the old assertions.
**Fix:** Card 11 must also update Tests 9, 10, 11 (`test-review-code-flow.py`) to assert `verdict == "ERROR"` (not `"REQUEST_CHANGES"`) and update Test 16 (`test-review-plan-flow.py`) identically. Test 4 in plan-flow (mixed APPROVE+ERROR, not all-ERROR) is unaffected.

### [NIT] Batch 1 / Card 1 — `.gitignore` placement risks wrong block

**Location:** Batch 1 / Card 1
**Issue:** The card says to place `.claude/scheduled_tasks.lock` "inside the existing `# === mill-managed ===` block (or directly before that block)". The `mill-managed` block's heading comment says it is "regenerated by mill-setup"; `.claude/scheduled_tasks.lock` is a Claude Code harness file, not mill-managed. Placing it inside that block misrepresents ownership and could mislead future maintainers who read the comment.
**Fix:** Reorder the options: "directly before the `# === mill-managed ===` block" should be primary, with the inside-the-block option dropped.

### [NIT] Batch 3 / Card 5 — `_warn_if_prose_diverges` regex ignores the `severity` parameter

**Location:** Batch 3 / Card 5
**Issue:** The function is defined as `_warn_if_prose_diverges(raw_output, severity, heading_count)` and uses `severity` in the warning message, but the detection regex is hardcoded to `(blocking|BLOCKING)`. For GAP severity (discussion reviews), the function will never fire — prose like "Three gaps remain" won't match. The `severity` parameter appears in the emission but not in the detection, creating a misleading signature.
**Fix:** Either (a) use `re.escape(severity.lower())` in the regex so it adapts to BLOCKING/GAP/NIT, or (b) rename the function to `_warn_if_blocking_prose_diverges` and restrict its callers to BLOCKING-severity paths only, making the limitation explicit.

### [NIT] Batch 7 / Card 14 — described fix may already be present

**Location:** Batch 7 / Card 14
**Issue:** The card describes changing `_wiki.read_hardlinks` to `cfg.get("hardlinks", {}) or {}`, but the current code already returns `dict(_HARDLINK_DEFAULTS)` (an empty dict) when `cfg.get("hardlinks")` is falsy — covering both the absent-key and `hardlinks: null` cases. Similarly, `_setup.create_hub_links` iterates `hardlinks_cfg.items()` over whatever `read_hardlinks` returns, so an empty dict already means the loop body doesn't execute. The card includes a conditional ("If `_setup` already handles this case, no edit needed") but does not note that the current code likely satisfies it.
**Fix:** The docstring update and the regression test (Card 15) remain valuable. Make the card's verification step explicit: "run `read_hardlinks` against a config with no `hardlinks:` key and confirm it returns `{}`; if so, skip the code edit and proceed directly to the docstring addition."
