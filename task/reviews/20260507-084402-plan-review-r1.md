## Findings

### [BLOCKING] test_9_missing_mode raises SystemExit, not returns 2
**Location:** Batch 3 / Card 6
**Issue:** `main([])` with `--mode required=True` causes argparse to call `sys.exit(2)`, raising `SystemExit(2)`. The test as specified asserts `rc == 2` from a return value, but the function never returns — it throws. Unittest marks the test ERROR, `run-all.py` exits 1, and the Batch 3 `verify:` gate fails.
**Fix:** Replace the bare call with `with self.assertRaises(SystemExit) as cm: main([])` followed by `self.assertEqual(cm.exception.code, 2)`.

### [NIT] `_render.render` mock missing from test_1_conflicts_success spec
**Location:** Batch 3 / Card 6
**Issue:** The assertion "Assert `_render.render` was called with tokens containing `CONFLICTING_FILES`…" requires a mock, but the test spec never says to patch `_render.render`. An implementer following the spec literally has no mock to call `assert_called_with` on.
**Fix:** Explicitly state to patch `_render.render` (e.g. `unittest.mock.patch("millpy_merge_in_subagent._render.render", return_value="rendered")`) and assert on the captured `call_args`.

### [NIT] No error handling for git rev-parse failure in verify success path
**Location:** Batch 1 / Card 1 — `_run_verify_fix`
**Issue:** When `verify_cmd` returns 0, the spec says to call `git rev-parse HEAD` and print the success JSON, but specifies no fallback if that subprocess fails — unlike `_forward_output`, which preserves the original sha on git failure.
**Fix:** Add a fallback: if `rev-parse` returns non-zero, still print `{"status":"success"}` without `commit_sha` (or with `commit_sha: null`). One-liner guard is sufficient.
