## Findings

### [NIT] `_forward_output` inference path missing try/except around `compute_new_dirt`
**Location:** Batch 4 / Card 11
**Issue:** `_cleanliness.compute_new_dirt` calls `_subprocess_util.run` with `check=True`; a git failure raises `CalledProcessError` which propagates out of `_forward_output` unhandled. Current code always emits JSON (even on failure). New code silently breaks that contract for the small fraction of callers that pass the new kwargs, leaving mill-go with no stdout JSON to parse.
**Fix:** Wrap the `compute_new_dirt` call (and the HEAD rev-parse below it) in `except Exception: pass` with a `continue`/fall-through to the stuck sentinel so the "always emit JSON" invariant is unconditional.

### [NIT] Redundant `read_batches` call in fix-cycle resume path
**Location:** Batch 4 / Card 12
**Issue:** The plan instructs calling `_status.read_batches(status_path)` a second time to obtain `batch_state_for_forward`, even though `batch_state` (computed a few lines earlier from `existing = _status.read_batches(status_path)`) already holds the same data.
**Fix:** Use `start_sha_for_forward = batch_state.get("start_sha") if batch_state else None` directly; no second `read_batches` needed. The `_for_forward` suffix is still available for the variable name if shadowing is the concern.

### [NIT] Card 9 instructions contradict their own code template on arrow representation
**Location:** Batch 3 / Card 9
**Issue:** The text says `test-no-unicode-arrow.py` "MUST itself contain `→` as the escape sequence (not the literal character) so it does not self-fail," but the code template immediately below uses the literal U+2192 in `if "→" in text:`. The SELF guard makes both forms safe; the stated constraint is misleading and will confuse the implementer.
**Fix:** Clarify that the SELF guard is the primary protection and the escape sequence is optional. Either rewrite the code template to use `\u2192` (matching the stated rule) or drop the "escape sequence" requirement and trust the guard.
