## Findings

### [BLOCKING:design] Demotion rewrite has no path for YAML-block findings
**Location:** batch 1, card 4 (`apply_blocking_ceiling`/`rewrite_demoted_headings`).
**Issue:** Card 2's `extract_findings` scans both the markdown-heading mechanism and the fenced `findings:` YAML mechanism per the `dual-mechanism-scan-preserved` Decision, but card 4's `rewrite_demoted_headings` only locates and rewrites `### [BLOCKING:<cls>]` heading lines. A finding demoted after being extracted from the YAML mechanism has no such heading to find, so the written review file keeps `severity: BLOCKING` in its YAML block while the envelope reports it as `NIT` — the exact file/envelope divergence the `demotion-rewritten-into-review-file` Decision exists to prevent.
**Fix:** Extend the rewrite step to also demote a finding's `severity:` field inside its source fenced `findings:` block when it originated there, and add a card-8 test covering a YAML-only demoted finding.

### [BLOCKING:design] Plan-review carryforward entries break findings/count consistency
**Location:** batch 3, cards 14–16 (`_scan_approved_batches` / `run` aggregation).
**Issue:** `_scan_approved_batches` builds carryforward review-entry dicts with `blocking_count`/`nit_count` parsed straight from disk, but card 14 explicitly forbids adding a `findings` key there (only a comment). Card 15's `aggregate_findings = [f for r in reviews for f in r.get("findings", [])]` silently drops these entries' findings, so any round with an already-approved carried-forward batch whose file has `nit_count > 0` yields a top-level `ReviewResult` where `nit_count`/`blocking_count` exceed `len(findings)` — violating the `structured-findings-in-envelope` Decision's own statement that the scalars are "derived values consistent with `findings`." No card-16 test exercises carryforward + aggregation together.
**Fix:** Have `_scan_approved_batches` call `extract_findings` on the already-demoted file text (no ceiling reapplication needed) and include the result in its returned entries, or explicitly test/document the accepted mismatch.

### [BLOCKING:scope] bench-reviewers.py still hardcodes retired GAP/NOTE severities
**Location:** `plugins/mill/integration_tests/bench-reviewers.py:177-186` — not referenced by any batch.
**Issue:** This live-dispatch benchmark harness counts discussion-type findings via `parse_blocking_count(text, severity="GAP")` + `severity="NOTE"`. Discussion.md's Scope states "Retire GAP, NOTE, and GAPS_FOUND from every template, SKILL, **script**, and test," and this file is exactly such a script, yet it is absent from every batch and from the overview's `## All Files Touched` list. Once the discussion template stops emitting `[GAP]`/`[NOTE]` (batch 5, card 20), this script's discussion-type `findings` count silently and permanently becomes 0.
**Fix:** Add a card (e.g. folded into batch 2) updating the discussion-type branch to use `severity="BLOCKING"`/`"NIT"` like the plan/code branches already do.

### [NIT:consistency] Batch 3 scope prose miscounts finalize_scope call sites
**Location:** `03-plan-backend.md`, Batch Scope paragraph.
**Issue:** States "four `finalize_scope` call sites," but `_review_plan.py` has five (lines 291, 602, 998, 1015, 1031). Cards 13+14 do correctly cover all five (1 + 1 + "three remaining"), so this is prose-only drift, not a coverage gap.
**Fix:** Correct "four" to "five."

### [NIT:consistency] Card 17's blanket findings:[] clause matches no extra site
**Location:** batch 4, card 17 (`_review_code.py`).
**Issue:** "Add `findings: []` to every other hand-built review-entry dict ... that currently sets `blocking_count=0`" — in `_review_code.py` only the outer `ReviewResult(blocking_count=0, ...)` calls set that, never a nested `reviews[]` entry dict; the clause matches nothing beyond the one `ReviewError`-path dict already named.
**Fix:** Drop the blanket clause, or note that `ReviewResult`'s default `findings=[]` already covers those constructions with no explicit argument needed.
