## Findings

### [NIT] batch-oversized context estimate includes Deletes tokens
**Location:** 03-plan-review-cli-and-validator / Card 7
**Issue:** The requirement says "collect Context: + Edits: + Creates: tokens" but instructs the implementer to "reuse `parse_batch_refs`", which also returns `Deletes:` tokens. Deleted files on disk would inflate the byte estimate, potentially triggering spurious `batch-oversized` halts for batches that delete large files.
**Fix:** After calling `parse_batch_refs`, subtract `_parse_deletes_only(batch_path)` from the token set before resolving paths — or explicitly document that Deletes are included intentionally as an acceptable over-count in the rough estimate.

### [NIT] NIT-fix commit timing is ambiguous in mill-go prose
**Location:** 05-mill-go-skill / Card 10
**Issue:** "that commit now also captures the NIT-fix changes" implies the approve commit stages fixer source-file edits. But `millpy-fix.py` commits its own source-file changes atomically; the subsequent approve commit only stages `status_path` and `review_file_path`, which is unchanged behavior.
**Fix:** Replace with: "The NIT-fix session commits its own source-file changes; the approve commit then stages `status_path` and `review_file_path` as before."

### [NIT] Cases B/F update options underspecified
**Location:** 01-review-guard-overstep / Card 2
**Issue:** "Update both to assert NO raise… or remove them" leaves implementers a choice that could produce inconsistent results across self-fix rounds: one pass might update, another might remove, causing the batch `verify:` to oscillate between passing/failing.
**Fix:** Prescribe one option: "Update Case B to assert NO raise and add a stderr-capture assertion for the fast-forward warning; apply the same update to Case F. Do not remove — the new fast-forward-removal test does not duplicate the commit-inside-expected_paths scenario."

APPROVE
