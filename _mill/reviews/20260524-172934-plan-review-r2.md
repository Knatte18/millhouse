## Findings

### [BLOCKING] CAS mechanism never raises WikiConflictError
**Location:** Batch 1, cards 5 and 6
**Issue:** Card 6 says mutating methods retry up to `CAS_RETRIES=5` on `WikiConflictError`, but card 5's new handlers (`_handle_upsert_task`, `_handle_set_phase`, etc.) never raise `ERR_CONFLICT`. The old `_handle_write` raised it via `base_hash` checking; new handlers omit `base_hash` entirely. The "no-advisory-lock" shared decision claims "CAS handles cross-host conflicts via WikiConflictError" but the CAS mechanism is removed without replacement. Cross-host races silently lose data via the existing rebase retry in `commit_push`.
**Fix:** Either specify in card 5 how WikiConflictError is raised (e.g., daemon detects origin advanced post-pull and re-reads tasks.json before re-upserting), or remove WikiConflictError retry logic from card 6 and update the shared decision to accept push-level rebase semantics.

### [BLOCKING] Batch 1 verify gate omits integration tests modified by cards 11/12
**Location:** Batch 1 (`00-overview.md` yaml; `01-wiki-module-refactor.md` Batch Tests)
**Issue:** Batch 1's `verify:` field runs `unit_tests/run-all.py` only, but cards 11 and 12 modify integration tests (`test-wiki-e2e.py`, `test-wiki-daemon.py`, `test-wiki-daemon-tinydb.py`, `test-wiki-noop-commit.py`, `test-wiki-sync.py`, `test-wiki-concurrency.py`). The prose says "plus the integration tests touched in cards 11 and 12" but the YAML doesn't reflect this. Regressions in ported integration tests will not be caught by the DAG-driven verify gate.
**Fix:** Either add a wrapper script to `verify:` that runs both run-all.py and the touched integration tests, or split card 11 and 12 work into a separate verify-gated step. Card 14's pattern (`test-wiki-migrate.py` as verify) shows integration tests can be verify gates.

### [BLOCKING] Card 13 backup commit step not idempotent on re-run
**Location:** Batch 2, card 13, step 5b
**Issue:** Step 5b is `git -C <wiki_path> add Home.md.pre-v3.bak && git -C <wiki_path> commit -m "wiki: backup pre-V3 Home.md"`. On re-run when `Home.md` is unchanged from the prior migration, the backup file content is identical and `git commit` returns non-zero with "nothing to commit". The `&&` chain breaks and the script exits with error before reaching step 5c-e. Card 14's idempotency test (`re-run idempotency`) will not reach the daemon's upsert call and the assertion `git log head SHA unchanged` will not be exercised — the test will fail at script exit.
**Fix:** Step 5b must tolerate the no-change case. Either run `git diff --cached --quiet` after `git add` and skip the commit when it returns 0, or use `git commit --allow-empty`, or add explicit returncode-tolerant handling. Update card 14 to assert script exits 0 on second run.

### [NIT] Card 36 scope risks reviewer/implementer fatigue
**Location:** Batch 3, card 36
**Issue:** Card 36 edits 28 test files in one card with 8 distinct rewrite rules. Card itself acknowledges "this is the largest card in the plan". Single-commit atomicity will be hard to review and risks a giant noisy diff.
**Fix:** Split into 3-4 cards grouped by rewrite rule family (e.g., one card for import deletions + `_tasks_md` direct calls; one for `mock.patch` retargeting; one for `_sidebar.regenerate` removal + assertion conversion).

### [NIT] Card 22 line-reference to discussion bug fix is dangling
**Location:** Batch 3, card 22 (line `:68` requirement)
**Issue:** Card text says "pass the hub root as `repo_root`, not the wiki path — see linked bug in the discussion's Constraints if a fix lands". The discussion is not part of the plan artefact; implementer reading the plan in isolation cannot resolve the reference.
**Fix:** Inline the constraint rather than referencing discussion: state "pass `repo_root=git_root` (hub root), not `wiki_path`" with the rationale.
