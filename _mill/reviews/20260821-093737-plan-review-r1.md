## Findings

### [BLOCKING:design] Card 7's stub-misuse warning contradicts Card 9's own new use case
**Location:** batch 4 (`config-caller-alignment`), Card 7 vs Cards 8–10
**Issue:** Card 7 adds a stderr warning in `_config.load_config` whenever `worktree_root != hub_root` and the `worktree_root/.millhouse/config.local.yaml` stub carries any key besides `hub_relative_path`, framed as "in a nested-hub layout this file is meant to be a pointer stub." But Card 9's whole purpose is to make `millpy-review-plan.py` pass `git_root` as `_review_common.load_config`'s `worktree_root` precisely so a `git_root`-level `.millhouse/config.local.yaml` carrying real override keys (not just `hub_relative_path`) is honored in a nested-hub layout (`hub_root != git_root`). Card 10's own Test 3 (`test_review_common_load_config_git_root_param`) constructs exactly this scenario — a `git_root/.millhouse/config.local.yaml` with a `roles:` block and no `hub_relative_path` — which will now also trip Card 7's "unexpected top-level key(s)" warning on every legitimate invocation of the feature Card 9 just enabled. The `worktree_root != hub_root` gate is also the routine condition for the existing container/wts pattern already used by `mill-merge`'s and `git-commit`'s own `_config.load_config(hub_root, git_root)` calls, so this is not a narrow edge case.
**Fix:** Either narrow Card 7's gate to only fire when `hub_subpath == "."` in a genuinely-nested (sub-project hub overlay) call, or exempt call sites that pass `git_root` explicitly as an override layer; reconcile the "pointer-only stub" premise with Card 9's "stub carries real overrides" premise before implementation.

### [BLOCKING:scope] Cards 3 and 4 assert external-file facts absent from their own Context:
**Location:** batch 2, Card 3 (`Context: none`) and Card 4 (`Context: plugins/codeguide/settings.json`, `git-commit/SKILL.md` only)
**Issue:** Card 3's Requirements quotes `_implementer_common._run_verify_gate`'s docstring ("When None, falls back to project_root") and asserts its cwd-resolution behavior as the load-bearing justification for flipping the `cwd is None` default — but `_implementer_common.py` is not in Card 3's Context (which is `none`). Card 4's Requirements similarly asserts `codeguide/scripts/resolve.py`'s walk algorithm and `codeguide-update/SKILL.md`'s Step 1/Step 2 argument shape, but neither file is in Card 4's Context (only `settings.json` and `git-commit/SKILL.md` are listed). I independently verified both claims are accurate against source, but per this stage's Context-completeness rule the implementer has no sanctioned way to do the same verification before applying a behavior-changing edit.
**Fix:** Add `plugins/mill/scripts/_implementer_common.py` to Card 3's Context, and `plugins/codeguide/scripts/resolve.py` + `plugins/codeguide/skills/codeguide-update/SKILL.md` to Card 4's Context.
