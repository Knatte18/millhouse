## Findings

### [BLOCKING] DETACHED_PROCESS contradicts _subprocess_util.py documented decision
**Location:** Batch 5 (Wiki client), Card 6; Shared Decision `windows-compatible-subprocess`
**Issue:** `_spawn_server` specifies `DETACHED_PROCESS | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`, but `_subprocess_util.py` explicitly documents "DETACHED_PROCESS is intentionally omitted — causing a console flash when combined with CREATE_NO_WINDOW." The project already solved daemon survival via the `cmd.exe` shim + `CREATE_BREAKAWAY_FROM_JOB` in `popen_detached`; the plan bakes in the known-bad flag into a new file.
**Fix:** Update the shared decision and Card 6 requirements to use `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB` (no `DETACHED_PROCESS`), and replicate the `cmd.exe` shim pattern (`["cmd", "/c", "start", "", "/B", "/MIN"] + cmd`) from `popen_detached` — mill imports are disallowed so the pattern must be inlined.

### [BLOCKING] DaemonBase._is_stale referenced in Card 6 requirements, _daemon.py not in Context
**Location:** Batch 5 (Wiki client), Card 6 — `_is_stale` requirements
**Issue:** Requirements say "Same pattern as `DaemonBase._is_stale`" naming the class and method from `_daemon.py`, but `_daemon.py` is absent from Card 6's `Context:` list. Context completeness criterion: BLOCKING when `Requirements:` names a function/class from a file outside `Context:`/`Edits:`.
**Fix:** Add `plugins/mill/scripts/_daemon.py` to Card 6's `Context:`.

### [NIT] run-all.py not updated for new wiki unit tests
**Location:** Batch 6 (Unit tests), Cards 7–10
**Issue:** CLAUDE.md states unit tests run via `run-all.py`, but no card updates it. The four new `test-wiki-*.py` files are only reachable via the explicit batch verify command.
**Fix:** Add a step to update `run-all.py`, or add a batch-local decision explaining the intentional exclusion (e.g., `test-wiki-sync.py` uses real git and violates the in-memory constraint documented for that runner).

### [NIT] Pull failure in _handle_read leaves _last_pull un-updated
**Location:** Batch 4 (Wiki server), Card 5 — `_handle_read`
**Issue:** If `pull()` raises `WikiPushError`, `self._last_pull = time.monotonic()` is never reached. Every subsequent read immediately re-attempts pull, hammering a transiently unavailable remote at request rate.
**Fix:** Set `self._last_pull = time.monotonic()` before calling `pull()` (or in a `try/finally`), so the refresh interval is always honoured regardless of pull outcome.

## Verdict

Two blocking issues: `DETACHED_PROCESS` flag contradicts documented codebase decision; `_daemon.py` missing from Card 6 Context.
