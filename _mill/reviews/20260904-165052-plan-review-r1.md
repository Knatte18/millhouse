## Findings

### [BLOCKING:design] Out-of-repo exemption's `is_relative_to` test is lexical, defeats its own required test case
**Location:** Batch 1 / Card 2 (second half of the out-of-repo exemption), exposed by Batch 2 / Card 10's "escapes the fixture roots through parent-directory segments" clean case.
**Issue:** Card 2's second half tests `existing_files` (returned unresolved by `resolve_existing_paths`, which never calls `.resolve()`) against `project_root`/`git_root`/`wiki_root` via `Path.is_relative_to`. `is_relative_to` is a pure string-prefix comparison and does not collapse `..` segments — a token like `../../outside/foo.py` joined onto `project_root` still has `project_root`'s parts as a literal prefix, so `is_relative_to(project_root)` returns `True` even though the path escapes the root on disk. Card 10's clean case (zero findings expected for exactly this parent-traversal escape) will therefore fail against an implementation that follows Card 2's Requirements literally.
**Fix:** Resolve the candidate and each root via `.resolve()` before the `is_relative_to` comparison, mirroring the codebase's own established idiom for this exact problem in `_check_out_of_worktree_target` (`project_root.resolve()` + `wt not in resolved.parents`); update Card 2's Requirements to say so explicitly.
**Note:** the same unresolved-candidate value is reused by Card 3's gitignored exemption to pick a `source_root` via the identical `is_relative_to` test — the mandatory try/except there fails safe (no crash), but a bad root pick could still suppress the wrong finding or silently no-op the `git check-ignore` call.

### [NIT:scope] "Absolute-looking" shape in Card 2's first half misses UNC/backslash-rooted literals
**Location:** Batch 1 / Card 2, first half.
**Issue:** The absolute-look test covers `/`, `~`, and single-letter-drive (`C:\`) prefixes, but not a UNC path (`\\server\share\...`), which is also unambiguously out-of-repo on Windows.
**Fix:** Either note this as an accepted gap (low likelihood in Requirements prose) or extend the regex to also match a leading `\\`.
