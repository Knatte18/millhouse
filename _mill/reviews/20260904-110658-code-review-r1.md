## Findings

### [BLOCKING:design] mill-merge-in's dead-parent resolution never propagates back to mill-merge
**Location:** `plugins/mill/skills/mill-merge-in/SKILL.md:29-31` (override branch, `status_path.exists()` False sub-case), consumed by `plugins/mill/skills/mill-merge/SKILL.md:249-254` (Step 2) and `:313-345` (Step 5, all `<parent_branch>`/`<parent-path>` references)
**Issue:** When `mill-merge` hits its own `status_path`-absent fallback (Entry Step 4, `parent_branch = cfg.git.base_branch`, deliberately un-liveness-checked there per line 135) and passes that value to `mill-merge-in` as the positional override, Card 2's reordering now runs `mill-merge-in`'s own liveness check against it unconditionally. If it's dead, `mill-merge-in` resolves a successor and — since `status_path` is absent — explicitly uses that successor "for the remainder of this run" (its own run only) without any rebind write. `mill-merge`'s own `parent_branch`/`<parent-path>` (already used to acquire the lock at Step 1, and reused verbatim through Step 5's fetch/merge/push/rollback) is never updated to the successor, so Step 5 goes on to `git -C <parent-path> fetch origin "<parent_branch>"` against the branch `mill-merge-in` just proved dead.
**Fix:** Have `mill-merge-in` surface the substituted branch name back to the caller (e.g. in its failure/success report), and have `mill-merge`'s Step 2 re-bind its own `parent_branch`/`<parent-path>` from that report before continuing to Step 3 onward.

### [NIT:design] cwd-rejection callout borrows the "dead" branch's action but not its detection mechanism
**Location:** `plugins/mill/skills/mill-merge-in/SKILL.md:114` (Step 3.5 callout)
**Issue:** The true `"dead"` outcome is discovered by polling `_bg.check_bg_status` on an already-created `<log-path>`. When `millpy-bg.py` itself rejects cwd (see `plugins/mill/scripts/millpy-bg.py:156-167`), it exits 1 synchronously and never prints `pid=<N> log=<abs-path>` — no log file exists to poll. The callout says to "treat this specific call exactly like the existing `dead` branch," which reads as invoking the same polling mechanism, but there is nothing to poll in this path.
**Fix:** Clarify that the cwd-rejection reason comes from the launcher's own stderr (captured directly from the failed Bash call), not from a `check_bg_status` poll, before instructing to log-and-continue.
