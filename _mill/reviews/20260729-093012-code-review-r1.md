## Findings

### [BLOCKING] Diagnostic print of raw git stderr is not ASCII-sanitized
**Location:** `plugins/mill/scripts/_treeguard.py:124-128`
**Issue:** The still-missing diagnostic interpolates `result.stderr` (decoded via `_subprocess_util.run`'s `encoding="utf-8", errors="replace"`, which can legitimately contain non-ASCII replacement/content characters) directly into a `print(..., file=sys.stderr)` call with no ASCII sanitization. This violates Card 1's own explicit requirement ("Any diagnostic print()/log output this module emits must be ASCII-only … per project convention") and CLAUDE.md's `print()`/`_log()` ASCII-only rule (Windows cp1252 console crash risk). The established codebase idiom for exactly this situation — `_pygit2_util.py`'s `error_msg = str(e).encode("ascii", errors="replace").decode("ascii")`, applied consistently before every error string it prints/raises — is not used here.
**Fix:** Sanitize `result.stderr` (and the path list, for symmetry) through the same `.encode("ascii", errors="replace").decode("ascii")` idiom before interpolating it into the stderr print.

### [NIT] Duplicate `read` entry in test-status.py's import block
**Location:** `plugins/mill/unit_tests/test-status.py:17` and `:24`
**Issue:** The `from _status import (...)` block imports `read` twice (line 17, out of alphabetical order before `append_phase`, and again at line 24 in its correct alphabetical slot). **Fix:** Drop the stray `read,` at line 17.
