## Findings

### [BLOCKING:design] Speculative baseline launch writes to the shared worktree while mill-plan may still be committing
**Location:** Batch 3 (`03-entry-gate-parallel-baseline.md`), Card 5, Edit A
**Issue:** Edit A fires its `_status.set_baseline_preflight_log` write + `git commit` (and the backgrounded job later does a plain `_status.set_module_verify_baseline` write) during the Entry-gate wait — i.e. before `phase: planned`, precisely the window the file's own text (SKILL.md lines 164-167) says an upstream mill-plan session may still be "actively progressing... in a separate concurrent thread" in the *same* task worktree. Today's wait is read-only for exactly this reason (mill-go's own first write, Prepare's `init_batches`, is deliberately deferred until after the wait so it never races mill-plan's writes/commits to the same local branch/`.git`). The builder lock acquired at step 4 only guards re-entrant mill-go runs ("one task per worktree" / "do not attempt to relax it" — line 962-963); it is not shown to be held by mill-plan, so it provides no mutual exclusion between the two skills. Card 5's own "Restart/orphan reconciliation" text only covers a *sequential* restart losing track of the launch — it never addresses two *simultaneously live* sessions both writing/committing status.md in the same worktree.
**Fix:** Either gate Edit A's write+commit on some session-mutual-exclusion signal proving mill-plan is no longer actively writing (not just `approved: true`, which can be set while mill-plan is still finishing its own commit/push), or scope the speculative write to something that cannot race a concurrent commit (e.g. write to a file outside the git-tracked worktree, or defer the commit until after the wait resolves).
