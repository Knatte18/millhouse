## Findings

### [BLOCKING] millpy-wikipush leaves orphaned `try:` block
**Location:** batch 4 / card 6 (millpy-wikipush.py edits)
**Issue:** Card instructs deletion of `with _wiki.wiki_lock(...):` (line 111) and `except _wiki.LockBusy as e:` clause (line 113) but never says to remove the surrounding `try:` (line 110). An exact-instruction-following implementer produces `try: return _push_inner(...)` with no except/finally — `SyntaxError`.
**Fix:** Add explicit instruction: "Line 110: delete the bare `try:` line as well; the body becomes a single top-level `return _push_inner(...)` call at function scope." Then re-state the post-edit shape so the implementer can verify.

### [NIT] Card 11 fixture-helper scope ambiguity
**Location:** batch 6 / card 11
**Issue:** Card says "Add a bare-clone 'origin' remote to the test's wiki fixture" but all three tests in `test-wiki-noop-commit.py` build the fixture via private per-test `_setup_wiki(wiki)` calls. Per-test patching is duplicative; modifying `_setup_wiki` itself fixes all three with one edit.
**Fix:** Prefer "Modify the `_setup_wiki(wiki_path)` helper at the top of the file to also init a bare repo and `git remote add origin`/`push -u origin HEAD`. The two no-op tests still pass (early-return path skips push); the third test now reaches push successfully."

### [NIT] Card 8 patching scope leaks to other importers
**Location:** batch 5 / card 8 (failure-path patching)
**Issue:** Patching `mill_fold.wiki.upsert_task` actually mutates `wiki._client.upsert_task` globally (Python's `from X import Y as Z` binds Z to the same object). Other tests in the same process run that share `wiki._client` would see the failing version unless the patch is restored cleanly. The plan's `try/finally` restoration handles this but should be called out.
**Fix:** Add one sentence: "Because `mill_fold.wiki` IS `wiki._client`, the patch is process-global; ensure the `try/finally` restoration runs even on assertion failure (use `unittest.mock.patch` context manager if simpler than manual try/finally)."

### [NIT] Card 9 retains redundant slug-matching-s test
**Location:** batch 5 / card 9
**Issue:** Plan keeps `test_pick_task_single_slug_matching_s` (line 197) on the grounds that it tests `--slug` mode. Under V3, `[s]` parses to `status=None`, so this test becomes functionally identical to `test_pick_task_single_slug_matching_unmarked` — same code path, same fixture meaning.
**Fix:** Either delete `test_pick_task_single_slug_matching_s` along with the other `[s]`-dead tests, or rename it to clarify it exercises slug-matching on a task originally marked `[s]` (now parsed to None) and note in the docstring that V3 collapses `[s]` to unmarked.

### [NIT] Card 4 proposal-file rendering claim is unverified
**Location:** batch 2 / card 4 (multi_select_groom_then_claim rewrite)
**Issue:** Card asserts "the V3 daemon writes `proposal-<slug>.md` automatically from the `body` key" but the source for `wiki._render.render` is not included in the manifest. The `Store.list_tasks_brief` derivation of `has_proposal` from `bool(body)` is consistent with this, but the rendering itself is not file-grounded.
**Fix:** Either include `wiki/_render.py` in card 4's `Context:` so the implementer can verify directly, or add a verify-time sanity check: "After implementing, confirm `proposal-merged-proposal.md` exists in the wiki clone after running `multi_select_groom_then_claim` with `body=<text>` via a minimal repro."
