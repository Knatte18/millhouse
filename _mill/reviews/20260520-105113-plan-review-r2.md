## Findings

### [BLOCKING] repo-named-"worktrees" false positive in resolve_common_dir_parent and list_worktrees
**Location:** Batch 1, Card 2 (`_pygit2_util.py` spec)
**Issue:** Both `resolve_common_dir_parent` and `list_worktrees` use `git_dir.parent.name == "worktrees"` as the sole discriminator between main and linked worktrees. A main worktree whose directory is literally named `"worktrees"` (e.g. `/projects/worktrees/`) would produce `git_dir = /projects/worktrees/.git`, triggering the linked-worktree branch and returning the wrong ancestor (three levels up instead of one).
**Fix:** Add `and git_dir.parent.parent.name == ".git"` to the condition — a linked worktree's git dir always sits at `<main>/.git/worktrees/<name>`, so the grandparent is always `.git`; a coincidentally-named main repo would not satisfy this.

### [BLOCKING] Batch 4/5 verify test files not analyzed for stale-mock risk
**Location:** Batches 4 and 5 verify commands; analogous to Card 7 rationale
**Issue:** `test-worktree.py`, `test-cleanliness.py`, and `test-review-common-guard.py` are referenced in verify steps but absent from "All Files Touched" with no analysis of whether they mock `_subprocess_util.run` for the functions being migrated (`list_worktrees`, `capture_snapshot`/`compute_new_dirt`, `_capture_head_sha`/`_capture_porcelain`). Card 7's existence proves this class of problem was considered for `test-paths.py`; the same analysis is missing for these three files. If they use subprocess mocks for those specific calls, they would fail loudly after migration (pygit2 call reaches a non-repo path and raises), making the verify steps fail.
**Fix:** Confirm each file uses real git repos for those functions, or add update cards for them parallel to Card 7.

### [NIT] Windows path format divergence in list_worktrees output
**Location:** Batch 1, Card 2; Batch 4, Card 9
**Issue:** The existing `_worktree.list_worktrees` returns raw git-CLI path strings (git for Windows outputs forward-slash paths, e.g. `C:/Code/…`); the new `_pygit2_util.list_worktrees` returns `str(Path(…).resolve())` which on Windows produces backslash paths (`C:\Code\…`). Callers doing string equality on `entry["path"]` against expected values would silently mismatch on Windows.
**Fix:** Either normalise the returned path strings with `.as_posix()` to match the existing forward-slash format, or document the format change and verify callers use `Path(entry["path"])` for comparisons.
