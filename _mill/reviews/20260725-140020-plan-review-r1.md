## Findings

### [BLOCKING] fail-fast guard breaks the bulk of test-millpy-implement.py
**Location:** Batch 1 (fail-fast-guard) / Card 1-2
**Issue:** `_agent_dispatch.resolve_dispatch_mode` defaults to `"agent"` when `llm.claude.dispatch` is unset (confirmed in `_agent_dispatch.py`). `setUp`'s shared `mock_load_config.return_value` in `test-millpy-implement.py` has no `llm.claude.dispatch` key, so it resolves to `"agent"`. Card 1's guard (`args.stage == "full" and resolve_dispatch_mode(cfg) == "agent"`) will therefore fire for every existing bare `self._run_main(["test-batch"])` test that relies on that default cfg (e.g. `test_1_initial_dispatch_success`, `test_2/_3/_7/_9/_10`, `test_commits_made_*`, `test_skip_start_commit_on_refire`, `test_card_ids_extraction_non_contiguous_headings`, and more) — all of which expect `rc == 0` and a dispatch into `_implementer_claude.run`. These will now fail with `rc == 1` before the guard's insertion point. Card 2 only adds 4 new tests and never instructs updating the shared default cfg or the dozen+ pre-existing tests; batch 1's own `verify:` runs this exact file.
**Fix:** Add `"llm": {"claude": {"dispatch": "subprocess"}, ...}` to the shared `setUp` default cfg (or an equivalent non-agent default), and audit every pre-existing bare/full-stage test in this file for the new guard's effect before landing Card 1.

### [BLOCKING] find_active_slug reorder can silently return a stale slug
**Location:** Batch 2 (on-disk-first-resolution) / Card 3
**Issue:** Today, `_marker.slug_from_branch` (which validates the branch against Home.md) always runs first; the `_mill/*.active` glob is only consulted as a fallback when it fails. Card 3 reverses this: a single on-disk `.active` match now returns immediately, **never calling `slug_from_branch` at all**. If a task is cleanly on a different, valid branch (e.g. a leftover/stale marker from a prior in-place claim not cleaned up — `millpy-cleanup.py`'s own comments acknowledge `.active` markers can go stale), the reordered code silently returns the stale marker's slug instead of the branch-validated one that today's code would have returned correctly. This contradicts the batch's own Shared Decision ("preserving today's correctness envelope exactly... no fast path is allowed to change the observable outcome except skipping the slow branch"). No test in Card 5 exercises single-marker + valid-but-different-branch.
**Fix:** Only take the glob-first fast path when the on-disk match also agrees with a cheap branch-derived slug check (mirroring `paths-skip-slug-validation`'s prefix-strip approach), or add a comment/test proving the stale-marker case cannot occur in practice; otherwise keep branch-first precedence.

### [BLOCKING] Card 12/15 misstate millpy-review-code.py's current briefs_dir binding
**Location:** Batch 5 (project-root-rebinding-review-side) / Card 12, Card 15
**Issue:** Card 12 claims "`briefs_dir = _paths.resolve_task_path(git_root, "_mill/briefs/")` already reads `git_root`... needs no change." The actual current line (verified in `millpy-review-code.py`) is `briefs_dir = _paths.resolve_task_path(project_root, "_mill/briefs/")` — it reads `project_root`, not `git_root`. Card 15 repeats the same false premise ("already correctly git_root-based, unchanged by Card 12"). The rebind happening to fix this line as a side effect doesn't excuse a plan quoting source that doesn't exist — an implementer/reviewer told to "verify... and leave untouched if so" has no instruction for the case (this one) where the premise is false.
**Fix:** Correct Card 12/15 to state `briefs_dir` uses `project_root` and IS fixed by the rebind (like the other two review-CLI files), and adjust Card 15's "unaffected" regression test accordingly.

### [NIT] Module docstrings not updated for new keyword-only params

### [NIT] find_active_slug module-summary line goes stale
