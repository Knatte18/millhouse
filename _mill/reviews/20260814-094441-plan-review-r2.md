### [BLOCKING:design] "Inline comments" section left byte-identically duplicated across golang and csharp
**Location:** Batch 1, cards 2 and 4 **Issue:** Card 1's shared file already states the why-not-what inline-comment rule ("Inline comments explain **why** something is done, never **what** is being done; the code already shows that."), but cards 2/4's Requirements never touch the existing `## Inline comments` section, so `golang-comments/SKILL.md` and `csharp-comments/SKILL.md` both keep the byte-identical block ("Use inline comments only to explain **why**, never **what**. If the code needs a "what" comment, the code itself is unclear — refactor instead.") verbatim. **Fix:** Extract this rule (including the "refactor instead" tail, which is new information not yet in the shared file) into `code-comments/SKILL.md` and trim/drop the per-language `## Inline comments` sections in cards 2 and 4, per the `no-redundancy-extraction` decision, which explicitly applies to all batches.

### [NIT:consistency] Python's sub-function-decomposition bullet overlaps the shared "many comments needed" corollary
**Location:** Batch 1, card 3 **Issue:** The replacement bullet for the dropped "How it works" requirement ("When a function's steps genuinely need explaining, decompose it into named sub-functions that each get their own docstring...") restates the substance of card 1's new shared corollary ("An implementation that seems to need many comments... is a signal to decompose it into well-named sub-functions with their own docstrings"), only adding a fallback clause about a single inline comment. **Fix:** Either fold the fallback clause into the shared corollary and drop the python restatement, or shorten python's bullet to reference the shared corollary and state only the fallback delta.
