## Findings

### [BLOCKING:consistency] `phase: blocked` row's `--approve`/`--revise` text is dead prose
**Location:** `plugins/mill/skills/mill-plan/SKILL.md:78` vs `:117-138` ("### Entry: resuming after a max-rounds block")
**Issue:** Card 2 edited the table's `phase: blocked` row to tell the operator to run `--revise` or (for a max-rounds-exhausted block) `--approve`. But this row is only reached on a bare `/mill-plan` (no flags), and the very next section states unconditionally "Whenever the phase-table lookup above lands on the `phase: blocked` row, run this procedure **instead of** jumping straight to its listed action." For a `max-rounds exhausted` reason, that procedure auto-resumes silently (computing `local_max_review_rounds`, no halt); for any other reason it prints its own generic "surface `blocked_reason`... and halt" text. Neither branch ever reproduces the row's own text, so the `--approve` mention Card 2 added can never actually be shown to an operator.
**Fix:** Either fold the `--revise`/`--approve` guidance into item 5's own halt branch (the only reachable path for a non-max-rounds block), or explicitly state in the row and/or item 5 that the row's action is superseded for `phase: blocked` and describe the real (auto-resume) behavior instead.

### [BLOCKING:design] Live round-cap override not wired at any concrete dispatch site
**Location:** `plugins/mill/skills/mill-plan/SKILL.md:316` vs dispatch sites `:417-421`, `:457-475` (esp. `:461`), `:494-495`, `:501-514` (esp. `:505`)
**Issue:** The new "Live operator-raised round-cap override" paragraph (Card 5) states `operator_max_review_rounds` "must additionally pass `--max-rounds <operator_max_review_rounds>`... at every dispatch site in this phase including the Step 3.5 ERROR-only retry." None of the four concrete dispatch blocks (step 2 Agent-mode/subprocess, step 3.5 Agent-mode/subprocess) actually reference `operator_max_review_rounds` — grep across the file shows the token appears only in the two documentation paragraphs (lines 316, 336), never at a call site. Contrast this with the blocked-resume mechanism, which repeats an explicit inline `>` reminder ("append ` --max-rounds <local_max_review_rounds>`...") directly above each of the two subprocess bash blocks (lines 461, 505) — the established in-repo convention for this exact class of override. A rule stated once in a paragraph far above the literal command-construction points is easy for the orchestrating agent to miss when actually executing dispatch.
**Fix:** Add the same inline reminder pattern used for `local_max_review_rounds` at each of the four dispatch sites (both Agent-mode branches' `<args>` construction and both subprocess bash blocks), not just the general prose paragraph.
