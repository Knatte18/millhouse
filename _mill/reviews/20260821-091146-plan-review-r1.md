## Findings

### [NIT:consistency] Card 1's "(every attempt)" contradicts Card 3's narrowed forking
**Demoted-from:** BLOCKING
**Location:** Batch 1 / Card 1 vs Card 3 **Issue:** Card 1 sets the catalog `description` to "Forks the implementer (every attempt) and the first fixer dispatch per scope/round"; Card 3 then narrows the implementer's forked set to "these attempts only: initial dispatch and step 3(a)'s transient re-dispatch," explicitly moving the stuck-escalation self-resolve re-fire to cold dispatch — so after the batch runs, "(every attempt)" is false, defeating the #851 catalog-accuracy goal these very cards are meant to fix. **Fix:** In Card 1, replace "(every attempt)" with wording that matches Card 3's narrowed set (e.g. "initial dispatch and transient re-dispatch") or drop the parenthetical qualifier entirely.

### [BLOCKING:scope] Card 2 Requirements cite mill-go-base/SKILL.md content not in its Context
**Location:** Batch 1 / Card 2 **Issue:** Card 2's Requirements justify "no other wiring is needed" by quoting `mill-go-base/SKILL.md`'s Entry section ("Override point B" / "treat your variant's `## Driver preamble` text as if written here") and the Batch Tests section separately invokes mill-go-base's "Override point A" contract — but `mill-go-base/SKILL.md` is listed in neither Card 2's `Context:` (only `workflow/SKILL.md` is) nor this review's file manifest, so the single-file-scope Shared Decision's premise (that Card 2 alone, with no mill-go-base edit, achieves a working once-per-session preload) is unverified. **Fix:** Add `plugins/mill/skills/mill-go-base/SKILL.md` to Card 2's `Context:` and confirm the quoted "Override point B" mechanism actually behaves as claimed before relying on it.

### [NIT:design] Ambiguous double-logging when both cold-fallback triggers occur in one batch
**Location:** Batch 1 / Card 3 **Issue:** The rewritten "Cold fallback, once per batch" bullet folds two distinct triggers (already-retried-transient re-fire, and verify/logic self-resolve re-fire) into one fallback routine that always runs the notify/status/commit sequence "before either," but doesn't say whether a second trigger firing later in the same batch (after the dispatch is already cold from the first) should log again or is a no-op. **Fix:** State explicitly whether the fallback logging is idempotent/gated once the implementer is already dispatching cold.
