## Findings

### [NIT] Push error handling in _archive_tag tests is implicit
**Location:** Batch 1, Cards 1 and 2
**Issue:** `create_or_resolve` always calls `git push` internally, but test tmp repos have no remote. The plan says "skip the push assertion" but never states how the helper handles push failure. The only interpretation consistent with the TDD flow (tests must pass after Card 2) is that push return codes are silently ignored — but this is not stated. An implementer who adds explicit push error-checking will find all "created" and "force_update" test cases fail at the push step.
**Fix:** Add one sentence to Card 2 Requirements: "Do not check the push return code — push failure is a non-fatal warning; the function returns the result dict regardless of push outcome."

### [NIT] Card 13 overstates commit sites in millpy-implement.py
**Location:** Batch 4, Card 13
**Issue:** Card 13 states "the script has multiple commit points (batch-start, batch-resume, and potentially others)." The actual `millpy-implement.py` has exactly one `git commit` call (`mill-go: start batch {batch_name}`). There is no "batch-resume" commit. The instruction to "read the file in full" will surface the discrepancy, but the language may cause unnecessary searching.
**Fix:** Remove "batch-resume, and potentially others" — replace with "the script has one commit point (batch-start)."

## Verdict

APPROVE
Two NITs; neither blocks implementation — the push-handling intent is derivable from the TDD flow, and Card 13's single commit site is discovered on first read.
