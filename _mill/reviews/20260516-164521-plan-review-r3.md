## Findings

### [BLOCKING] `_wiki.read_junctions` not updated — post-migration cleanup is junction-unsafe
**Location:** Batches 2 and 4; `_wiki.py` absent from every `Edits:` list in the plan
**Issue:** After migration deletes `wiki/config.yaml`, `_wiki.read_junctions(wiki_path)` returns only `_JUNCTION_DEFAULTS = {".wiki": "<WIKI_PATH>"}`, silently omitting `.portals: <CONTAINER_PATH>/portals/` and `.active: <CONTAINER_PATH>/portals/<SLUG>/`. `millpy-cleanup.py` passes this incomplete map as `junctions_cfg` to `_worktree.remove_safe`. Per CLAUDE.md §issue #100, calling the long-path fallback (`rmdir /s /q`) with an incomplete junction set follows unstipped `.portals` and `.active` junctions directly into the real portals directory and sibling worktrees, wiping them.
**Fix:** Either (a) add `_wiki.py` to Batch 4 edits and update `read_junctions` to fall back to the hub's `mill-config.yaml` when `wiki/config.yaml` is absent, or (b) replace the `junctions_cfg = _wiki.read_junctions(wiki_path)` call in Card 12's `millpy-cleanup.py` edits with `cfg.get("junctions", {})` — `cfg` is already loaded via the refactored `_config.load_config` which reads from `mill-config.yaml`.

### [BLOCKING] `_wiki.health_check` always raises post-migration — permanently breaks mill-go
**Location:** Batches 2 and 4; `_wiki.py` absent from every `Edits:` list
**Issue:** `_wiki.health_check(wiki_path)` raises `WikiHealthError(wiki_path, "wiki/config.yaml missing …")` when `wiki/config.yaml` is absent. The function's own module docstring declares it "is intended to be called at the start of each mill-go batch iteration and each holistic review round." Migration permanently removes `wiki/config.yaml` from every hub; therefore all mill-go batch dispatches fail with `WikiHealthError` on every task after migration runs. `health_check` is listed in `_wiki.py`'s Public API and is unguarded in the plan.
**Fix:** Add `_wiki.py` to Batch 4 edits; update `health_check` to verify that at least one valid config source exists — either `wiki/config.yaml` (pre-migration) or `mill-config.yaml` at the resolved hub root (post-migration). The hub root is resolvable via `_paths.resolve_git_root()` or by accepting an optional `hub_root` argument from call sites that already hold it.

### [NIT] Card 10 leaves `resolve_wiki_path` failure mode unspecified
**Location:** Batch 2, Card 10 (`_config.load_config` rewrite), Requirements §step 2
**Issue:** "Resolve `wiki_cfg_path = _paths.resolve_wiki_path(repo_root) / 'config.yaml'` if the wiki resolves, else None" does not name the exception to catch. `_paths.resolve_wiki_path` raises `SystemExit`, which a bare `except Exception` misses; the lenient loader would crash instead of falling back. Card 11 (`_review_common.load_config`) is explicit: "if wiki resolution raises, treat wiki_cfg_path as None."
**Fix:** Add to Card 10's Requirements: "wrap `_paths.resolve_wiki_path(repo_root)` in `try: … except (Exception, SystemExit): wiki_cfg_path = None`", matching Card 11's wording verbatim.

## Verdict

REQUEST_CHANGES
Two post-migration safety holes in `_wiki.py` — junction-unsafe worktree cleanup and a permanently-failing health check — are unaddressed by the plan.
