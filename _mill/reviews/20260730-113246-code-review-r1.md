## Findings

### [BLOCKING] Nested-heading test never actually exercises `in_fence` tracking
**Location:** `plugins/mill/unit_tests/test-plan-validate.py:2353-2399` (fixture built with `_plan_validate.py:1651-1695`'s `_requirements_fence_aware_body`)
**Issue:** The fixture applies the SAME 2-space drift indent to the fence delimiters (`"  ```\n"`) and to the nested `### `/`- **SomeField:**` lines. Since `in_fence` only toggles on `line.startswith("```")` (no leading-whitespace tolerance) and `any_field_header_re` requires literal `^-` at column 0, none of these indented lines ever reach either check — the assertion (`exactly one error`) would pass identically with `in_fence` tracking deleted entirely. The test's own docstring even states the nested lines "carry the same drift indent," confirming it sidesteps the exact scenario (flush-left fence containing a flush-left `- **Field:**`/`### ` line) that the `fence-aware-boundary-detection` Decision — itself born from a prior discussion-review GAP — was meant to guard against.
**Fix:** Rebuild this fixture with a flush-left (non-indented) fence whose body legitimately contains a flush-left `### `/`- **Field:**`-shaped line (no drift needed on that specific test, since boundary-truncation risk is orthogonal to the strip-search), and assert the full fence body is retained (e.g. via a second card/no-truncation check) so the test can actually fail if `in_fence` tracking is removed.

### [NIT] CRLF test doesn't isolate the explicit normalization step
**Location:** `plugins/mill/scripts/_plan_validate.py:1783` and `plugins/mill/unit_tests/test-plan-validate.py:2311-2350`
**Issue:** `Path.read_text()` already performs universal-newline translation (CRLF→LF) by default, so the explicit `.replace("\r\n", "\n")` on the resolved file's content is redundant for on-disk reads, and the test would pass identically even if that `.replace(...)` call were deleted — it doesn't isolate "normalization present" from "normalization absent."
**Fix:** No functional change needed (harmless/defensive), but the test docstring's claim "proving the `\r\n`-to-`\n` normalization step runs" is not actually demonstrated; consider noting this is exercising `read_text`'s own universal-newlines behavior rather than the explicit code path, or construct disk I/O that bypasses universal-newline translation (e.g. `open(..., newline="")`-based read stand-in) if the explicit step truly needs isolated coverage.
