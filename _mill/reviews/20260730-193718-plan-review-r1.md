## Findings

### [BLOCKING] `build_wait_command`'s grep anchors break on CRLF status.md
**Location:** Batch 1, Card 1 (`_phase_wait.build_wait_command`)
**Issue:** The returned script uses `grep -q "^phase: <ready_phase>$"` with a trailing `$` anchor. `_status.py` (`update_field`/`append_phase`/`set_blocked`) writes via `Path.write_text` with no `newline=` override, so on Windows the platform-default newline translation produces CRLF-terminated lines; GNU/POSIX `grep`'s `$` anchor does not match before a trailing `\r`, so the poll loop never detects `READY`/`blocked` on Windows and always runs to `TIMEOUT`.
**Fix:** Either write status.md with an explicit `newline="\n"` override, or have `build_wait_command` strip `\r` before matching (e.g. `grep -q "^phase: <ready_phase>\$"` on a `tr -d '\r' <"<status_path>"` pipe), and add a CRLF-input case to card 2's unit test.

### [BLOCKING] Monitor tool's `persistent`/`task_id`/notification contract is unverified
**Location:** Batch 2 Card 4, Batch 3 Card 5 ("Entry-gate wait" subsections)
**Issue:** Cards 4/5 assume the harness `Monitor` tool accepts `persistent: true`, returns a `task_id`, and later delivers a `<task-notification>` whose single stdout line the orchestrator branches on — mirroring the Agent tool's `agentId`/notification contract. The only in-repo confirmation of `Monitor` (`plugins/mill/skills/cli/SKILL.md`) says only "Monitor runs bash, not PowerShell" — it does not document a `persistent` parameter, a `task_id` return value, or that Monitor emits `<task-notification>`s at all. No file in this task's manifest or repo confirms this contract.
**Fix:** Before batches 2/3 are approved for execution, confirm Monitor's actual parameter/return/notification shape against real platform docs or a spike run; if the shape differs, this task's whole wait mechanism needs re-specifying.

### [NIT] Replacement phase-table rows use 5-space indent, contradicting the "preserve 3-space" instruction
**Location:** Batch 2 Card 4 step 1 (line ~49 of `02-mill-go-entry-wait.md`); Batch 3 Card 5 step 1 (lines ~52-53 of `03-mill-plan-entry-wait.md`)
**Issue:** Both cards correctly quote the existing row with its true 3-space indent, then immediately say "preserve the row's original 3-space indentation" — but the replacement row's own illustrative fenced block is indented 5 spaces in both batch files, not 3. Markdown tables tolerate this cosmetically, but it is a self-contradiction in the requirement text.
**Fix:** Re-indent both replacement-row fences to exactly 3 leading spaces to match the surrounding table and the card's own explicit instruction.

### [NIT] Card 3's wiki-config-mutation bootstrap claim may not match the Phase: Plan self-validate call
**Location:** Batch 1, Card 3 ("Bootstrap justification" paragraph)
**Issue:** Card 3 states "the plan-review self-validation step re-runs the validator with `skip_checks=frozenset({"wiki-config-mutation"})`... per that row's documented resolution." `mill-plan/SKILL.md`'s Phase: Plan self-validate call (before the plan's first commit) is documented as always passing `skip_checks=frozenset()` ("this self-run has no CLI args to source a skip-list from") — there is no stated override for that specific call site, only for the later CLI-based Step 1.5 gate (`--skip-check` flag). If accurate, this plan's own mill-config.yaml edit could halt at Phase: Plan's self-validate before ever reaching the mechanism Card 3 relies on.
**Fix:** Confirm against `_plan_validate.py`/`millpy-review-plan.py` whether the Phase: Plan self-validate call site actually has a way to bypass `wiki-config-mutation`; if not, note it explicitly as a known one-time manual step rather than asserting it "re-runs...per that row's documented resolution."
