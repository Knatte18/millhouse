## Findings

### [BLOCKING] Card 24 appends fold note to wrong field
**Location:** Batch 3, Card 24 (millpy-fold.py port at line `:135`)
**Issue:** The card writes `body=((task["body"] or "") + "\n" + fold_line)`. In V3, the renderer (Card 2) emits `body` to `proposal-{slug}.md` and emits `brief` as the inline text under the Home.md slug line. V2's `_tasks_md.append_to_body` appended below the slug line — i.e., into what is now the `brief` field. Using `body=` will (a) make fold notes disappear from Home.md, (b) create a new `proposal-{slug}.md` file for any folded task that previously had no proposal, silently flipping the task into proposal form.
**Fix:** Change to `brief=((task["brief"] or "") + "\n" + fold_line)`. The `parse_batch_refs` / `get_task` shape per Card 1 includes `brief` in `list_tasks_brief`, but Card 24 reads via `get_task` (full dict) which includes both fields, so the field swap is the only change.

### [BLOCKING] Card 14 commit-count assertion ignores daemon gitignore commit
**Location:** Batch 2, Card 14 (test-wiki-migrate.py, assertion #5)
**Issue:** Step 5d's first call to `upsert_tasks_batch` spawns the daemon, whose `on_start` runs `_ensure_gitignore` (see seeded `wiki/_server.py`). On a freshly-V3 wiki the daemon adds `.wiki-daemon.json` / `.wiki-daemon.log` to `.gitignore` and commits with message `chore(wiki): gitignore daemon artifacts` BEFORE the migration commit. The fixture has no pre-existing daemon-artifact lines so this commit always fires. Assertion (5) ("exactly two new commits exist") will fail with 3 commits: backup + gitignore + migrate.
**Fix:** Either pre-seed the gitignore entries in the fixture before pushing initial state, or relax the assertion to require both expected commit messages present anywhere in `git log` (drop the "exactly two" count).

### [NIT] mill-fold loses concurrency protection
**Location:** Batch 3, Card 24 + Shared Decision `no-advisory-lock`
**Issue:** The `get_task` → compute → `upsert_task` sequence is a client-side read-modify-write window the daemon cannot serialize. Two concurrent folds on the same slug will lose one fold's appended line. V2's `wiki_lock` protected this. The shared decision's claim that structured ops "have no read-modify-write window" holds for single ops but not for client-composed multi-step append patterns.
**Fix:** Document this regression in the decision, or add an atomic `OP_APPEND_BRIEF` / `OP_APPEND_BODY` op in Card 5 plus a `wiki.append_brief` client method consumed by Card 24.

### [NIT] mill-add silently overwrites instead of rejecting duplicate slugs
**Location:** Batch 3, Card 21 (millpy-add.py port)
**Issue:** Current `millpy-add.py` has explicit `_slug_already_present(home_text, args.slug)` and `raise SystemExit(f"Slug {args.slug!r} already present in Home.md.")`. Per Card 1, `wiki.upsert_task` keyed by slug updates and preserves id when slug exists — silent replacement. Card 21 removes the V2 read-and-check flow without preserving the duplicate-rejection behaviour.
**Fix:** Either keep the duplicate check by calling `wiki.get_task(wiki_path, slug)` first and exiting if present, or explicitly call out in Card 21 that mill-add becomes idempotent / upsert-style.

## Verdict

REQUEST_CHANGES — two concrete bugs (field name swap, commit count) plus two behaviour regressions to address.
