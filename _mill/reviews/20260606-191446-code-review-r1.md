## Findings

### [BLOCKING] Step 2 script corrupts wiki-tasks.json with non-JSON prefix

**Location:** `plugins/mill/skills/mill-ghissues-to-tasks/SKILL.md:39-46`
**Issue:** The Step 2 bash snippet redirects all stdout to `.scratch/wiki-tasks.json`, but prints both `_paths.resolve_git_root()` (a plain filesystem path string) and `json.dumps(tasks, ...)` to stdout. The resulting file starts with the path string, making it unparseable as JSON; any subsequent `json.load` of that file will raise `JSONDecodeError`.
**Fix:** Remove the `print(_paths.resolve_git_root())` line from the redirected script -- the git root is already used in Step 1 via `_gh_issues.detect_repo(git_root=_paths.resolve_git_root())` and can be resolved again in Step 5 independently; there is no reason to persist it to `wiki-tasks.json`.

### [NIT] Step 3 calls get_task for locked-phase check on already-loaded data

**Location:** `plugins/mill/skills/mill-ghissues-to-tasks/SKILL.md:60`
**Issue:** Step 3 instructs the assistant to call `_client.get_task(wiki_path, target_slug)` for every fold candidate to read `task["status"]`, but Step 2 already loaded every task's `status` via `list_tasks_brief` into `.scratch/wiki-tasks.json`. This makes an unnecessary live daemon call per fold candidate during analysis.
**Fix:** In Step 3, read `status` from the already-loaded `list_tasks_brief` data; reserve the `get_task` call for Step 5 (the apply path), where a re-check against an operator-edited proposal is the intended use case.
