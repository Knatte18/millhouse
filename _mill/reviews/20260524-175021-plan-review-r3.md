## Findings

### [BLOCKING] TinyDB refresh after pull undefined
**Location:** Batch 1, Cards 1 + 5
**Issue:** Card 1 deletes `Store.set`/`Store.get`; Card 5 deletes the explicit "Repopulate TinyDB from disk after pull" step that today's `_handle_read`/`_handle_write` perform via `self._store.set("Home.md", disk_content)`. The no-CAS design (Card 5 rationale) hinges on "each handler reads the current DB state and re-renders from it" — but if TinyDB's JSONStorage caches in memory (which it does when wrapped in CachingMiddleware, and behavior varies between versions otherwise), cross-host changes that arrive via `pull --rebase` won't be visible to the in-memory Store. This causes lost updates: host A writes `{slug-x: active}`, host B independently sets `{slug-x: done}`, rebase succeeds on push, but next read on either host still sees pre-rebase state.
**Fix:** Card 5 must add an explicit reload step (e.g. `_store.reload()` or recreate `self._store = Store(...)` after `pull` succeeds) and Card 1 must add a `Store.reload()` method. Alternatively, document TinyDB's actual storage semantics (no-cache default) and pin the dependency version that guarantees this behavior.

### [BLOCKING] Multi-step ops lose atomicity without replacement
**Location:** Batch 3, Card 26 (`groom_and_claim_merge`)
**Issue:** Card 26 ports `groom_and_claim_merge` from one wiki_lock-wrapped block to three sequential daemon calls (`remove_task` × N, `upsert_task`, `set_phase`). Each is now its own commit+push. Crash between calls leaves wiki in inconsistent state: source slugs removed but merged slug missing, or merged slug present but not `[active]`. The "no-advisory-lock" decision rationale only covers single-op writes, not multi-op logical transactions.
**Fix:** Either (a) add a single batched daemon op like `OP_GROOM_AND_CLAIM_MERGE` that performs remove+upsert+set_phase as one TinyDB transaction + one render + one commit, or (b) explicitly document the eventual-consistency tradeoff in `## Shared Decisions` and add Card 26 wording that the operator is expected to manually recover from partial-state crashes.

### [NIT] CAS_RETRIES kept declared just to be imported by test
**Location:** Batch 1, Cards 6 + 11
**Issue:** Card 6 keeps `CAS_RETRIES` declared "to make the `test-wiki-e2e.py` migration trivial" and "leave a single place to revisit"; Card 11 imports it solely to "pin the value against drift". This is circular — the constant has no production use after the CAS removal in Card 5.
**Fix:** Delete `CAS_RETRIES` from `_client.py` entirely. Card 11's test should hardcode whatever interleaving expectation it actually needs.

### [NIT] `[s]` fast-path becomes dead code after parser change
**Location:** Batch 1 Card 3 + Batch 3 Card 26
**Issue:** Card 3 parses `[s]` as `status = None`. After migration no task ever has `phase == "s"`. The `[s]` fast-path in `_spawn_core.pick_task_single` and `pick_task_single_or_multi` becomes unreachable dead code. Card 26 doesn't mention removing it.
**Fix:** Add to Card 26's line-by-line: "Remove the `fast = next((t for t in tasks if t.phase == 's'), None)` fast-path; `[s]` is no longer a parseable status."

### [NIT] `test-wiki-noop-commit.py` disposition unclear
**Location:** Batch 1 Card 12 (lists it in Edits) + Batch 3 Card 35 (does not list it for deletion)
**Issue:** This test exercises V2 `_wiki.write_commit_push`'s no-op-commit detection. After batch 3 deletes `_wiki.py`, the test is broken. Card 12 says "port to structured ops" but the test's semantic is about git-layer noop detection, not protocol surface; Card 35 doesn't delete it.
**Fix:** Either add `test-wiki-noop-commit.py` to Card 35's deletion list (with note that V3 `_sync.commit_push` already has equivalent test coverage in `test-wiki-sync.py`), or rewrite Card 12's treatment to port it to test `wiki._sync.commit_push` directly.

### [NIT] millpy-wiki-migrate.py claims mill-config.yaml is required but doesn't enforce it
**Location:** Batch 2 Card 13 (preamble + step 1)
**Issue:** Card 13's help-text states "`mill-config.yaml` must exist at the hub repo root" and asserts `_paths.resolve_wiki_path` raises if it's missing. But `_paths.resolve_wiki_path` only needs `paths.wiki` from `.millhouse/config.local.yaml` and otherwise uses sibling discovery — it does NOT check for `mill-config.yaml`. The script's resolver call cannot enforce what the docstring promises.
**Fix:** Either add an explicit check in step 1 (`if not (_paths.resolve_hub_path() / "mill-config.yaml").exists(): raise`), or weaken the preamble to "wiki path must be resolvable via sibling discovery or `paths.wiki` override".
