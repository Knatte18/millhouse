## Findings

### [BLOCKING:design] New unit-test fixtures break on Windows via `Path.resolve()` drive semantics
**Location:** Batch 1, Card 2 — tests 1, 3, 4, 5 (`..._basic`, `..._not_at_index_one`, `..._trailing_slash`, `..._first_match_wins`).
**Issue:** The fixtures use POSIX-style literal strings (e.g. `'/home/x/.claude/plugins/cache/millhouse/mill/2.0.0/scripts'`) and assert equality against a bare, un-resolved `Path('/home/x/.../2.0.0')`. Card 1's implementation calls `.resolve().parent` on the matched entry; on Windows, `Path('/home/x/...').resolve()` fills in the current working directory's drive letter (e.g. `C:\home\x\...`), which will never equal the drive-less expected `Path(...)`. All four comparison-based tests will fail on any Windows dev/CI run.
**Fix:** Build fixtures with OS-native/tempfile-derived paths (as the file's existing `resolve_plugin_template_path` tests already do) or resolve both sides identically, instead of hardcoding POSIX literals as plan-mandated test bodies.

### [NIT:consistency] "`--only`-scoped" language misapplied in Batch Tests rationale
**Location:** Batch 1, `## Batch Tests`, first paragraph.
**Issue:** States verify runs the full file "not `--only`-scoped to the five new test functions," but `test-config.py` has no `--only`/argparse mechanism at all (only `run-all.py --only <file>...` exists, and it scopes by file, not function). The wording implies a function-level scoping option that doesn't exist anywhere in this codebase.
**Fix:** Rephrase to state the choice is simply "run the whole file" vs. a hypothetical narrower alternative, without invoking the (unrelated, file-level) `--only` flag name.
