## Findings

### [BLOCKING] Card 17: wiki_root → hub_dir rename breaks wiki-path ops in review backends
**Location:** Batch 2 / Card 17
**Issue:** Card 17 renames the `wiki_root` parameter to `hub_dir` in `_review_code.py`'s `run()`, `_review_discussion.py`'s `run()`, and `_review_plan.py`'s `run()`, and changes callers to pass `hub_dir` (= cwd = `project_root`). But these backend functions use the same parameter for `_reviewers.load(wiki_root)` AND for `resolve_ref_paths(..., wiki_root=wiki_root)`, `resolve_existing_paths(..., wiki_root=wiki_root)`, and `load_task_title(project_root, wiki_root, cfg, slug)`. After the rename, all four uses receive `hub_dir` (worktree root), which breaks wiki-prefixed ref resolution (`wiki/active/…` paths resolve against cwd instead of the wiki clone) and task-title lookup.
**Fix:** Do not rename `wiki_root` in the backend signatures or change its callers. Instead, add `hub_dir = project_root` locally inside each backend function and use it only for the `_reviewers.load` call; leave every other use of `wiki_root` unchanged.

### [BLOCKING] Card 20: Phase 3.1 runs before Phase 3.2b — user config overwritten by template
**Location:** Batch 3 / Card 20
**Issue:** Card 20 places Phase 3.2b (migration script) immediately after Phase 3.2, which is after Phase 3.1. For any existing hub being migrated, Phase 3.1 (case 1: dest missing) copies `mill-config.yaml` from the plugin template before Phase 3.2b runs. When the migration script then executes, it finds both `mill-config.yaml` (just seeded from template) and `wiki/config.yaml` exist, prints "already exists — skipping copy", and **still deletes `wiki/config.yaml`**. The user's custom hub config is permanently replaced by template defaults. The integration test `test_config_migration_plain_copy` does not catch this because it tests the migration script in isolation (no prior Phase 3.1 run).
**Fix:** Place Phase 3.2b **before** Phase 3.1 in the SKILL.md. With that ordering: the migration script copies `wiki/config.yaml` → `mill-config.yaml` (user config preserved), then Phase 3.1 case 2 (dest present) runs the block-level upsert for any blocks missing from the user's config.

### [NIT] Card 12/13: strict-check bodies in local wrappers not specified after rename
**Location:** Batch 2 / Cards 12, 13
**Issue:** Several scripts (e.g. `millpy-claim.py`, `millpy-spawn.py`) have a local `_load_config(wiki_path, ...)` wrapper that performs a strict existence check (`wiki_path / "config.yaml"`) before calling the lenient loader. Cards 12 and 13 say "rename first parameter to `repo_root` and update every reference inside the wrapper body accordingly" but do not specify what the strict check becomes. The `wiki_path / "config.yaml"` expression would reference a nonexistent variable after the rename, and the semantically correct replacement (check for `repo_root / "mill-config.yaml"` or just drop the strict check and let the lenient loader return `{}`) is left to implementer judgment.
**Fix:** Explicitly state the disposition of the strict check for each wrapper: either convert it to `if not (repo_root / "mill-config.yaml").exists() and not _paths.resolve_wiki_path(repo_root) ...` (preserve strict semantics) or document that the wrapper becomes a pass-through and the caller handles the empty-dict case.

### [NIT] Card 20: integration test does not cover Phase 3.1→3.2b interaction
**Location:** Batch 3 / Cards 20–21
**Issue:** `test-migration.py` tests the migration script in isolation. No test exercises the full mill-setup Phase 3.1 → Phase 3.2b sequence, which is where the config-overwrite bug (BLOCKING 2) lives. Even after the phase-ordering fix, future regressions to the mill-setup phase sequence would not be caught.
**Fix:** Add a test case `test_setup_phase_ordering_preserves_wiki_config` to the integration test (or note that mill-setup SKILL.md interpretation is out of scope for automation and document the expected behavior in the SKILL.md text explicitly: "Phase 3.2b must execute before Phase 3.1 so that `wiki/config.yaml` content is not discarded").
