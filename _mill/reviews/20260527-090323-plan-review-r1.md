## Findings

### [BLOCKING] Card 11: `_subprocess_util.py` missing from Context despite Requirements reference
**Location:** Batch 4, Card 11
**Issue:** Requirements says "immediately before each of the two `_subprocess_util.run(...)` call sites ... pass `env=child_env` as a new kwarg to the `run()` call" — `_subprocess_util.run` is a function from `_subprocess_util.py`, which is absent from Card 11's `Context:` and `Edits:`. Per the Context completeness criterion this is BLOCKING. Card 10 (same batch) does list `_subprocess_util.py`, so the implementer will have seen it, but each card's declaration must be self-sufficient.
**Fix:** Add `plugins/mill/scripts/_subprocess_util.py` to Card 11's `Context:` list.

### [NIT] Cards 9, 11, 14 have `Context: none` — violates non-empty rule
**Location:** Batch 4, Cards 9, 11, 14
**Issue:** The plan criteria require "Context field — non-empty per card". All three cards declare `Context: none`. For Cards 9 and 14 the Edits file implicitly provides sufficient context; Card 11 is covered by the BLOCKING finding above.
**Fix:** Card 9: set `Context:` to `plugins/mill/scripts/_subprocess_util.py`. Card 14: set `Context:` to the three template files being edited (or at minimum one of them as an anchor). Card 11 fix is covered above.

### [NIT] Card 7 guard block: wiki daemon exceptions not caught
**Location:** Batch 3, Card 7
**Issue:** The inserted guard calls `_client.get_task(wiki_path, slug)`, which raises `WikiStartupError` or `WikiProtocolError` when the daemon is unavailable. Neither exception is caught, so a daemon failure produces a raw traceback rather than the operator-readable halt message the batch is designed to provide.
**Fix:** Wrap the `_client.get_task` call in a `try/except (WikiStartupError, WikiProtocolError) as e` block and halt with `f"_mill/status.md absent and wiki daemon unavailable: {e} -- inspect manually."` This keeps the guard consistent with its own design goal of eliminating unhelpful crashes.
