## Findings

### [BLOCKING] Card 2 invalidates existing is_bg_worker_alive mocks

**Location:** Batch 1 / Card 2, cross-cutting with Card 4 and existing tests

**Issue:** Card 2 rewrites `check_bg_status` to call `_probe_liveness` directly instead of `is_bg_worker_alive`. The existing `TestCheckBgStatus` tests (`test_check_bg_status_running`, `test_check_bg_status_dead_no_exit`, `test_check_bg_status_race_guard_exit_appears`) all patch `_bg.is_bg_worker_alive`. After Card 2 those patches target a function that `check_bg_status` no longer calls, so the tests pass the wrong path silently -- `check_bg_status` will call the real `_probe_liveness` and produce unexpected results against the tempfile logs in those tests.

**Fix:** Card 4 Requirements must explicitly direct the implementer to update the three existing `TestCheckBgStatus` mocks from `patch.object(_bg, "is_bg_worker_alive", ...)` to `patch.object(_bg.os, "kill", ...)` (or equivalent `_probe_liveness`-compatible mocking) to restore their intended stimulus. The plan currently says only "if the Card 1 refactor renames internals, update only the references" -- that is not sufficient because the mock target itself becomes structurally inert, not merely renamed.

### [BLOCKING] Card 4 Context missing _bg.py

**Location:** Batch 1 / Card 4

**Issue:** Card 4 Requirements reference `_bg._STALE_LOG_SECONDS`, `_bg.check_bg_status`, and `_bg.os.kill` but `_bg.py` is not listed in `Context:` or `Edits:`. Per the plan criteria an implementer may only read files in `Context:` -- a cold-start session will not know the module's internal constants or the exact mock target without reading the source.

**Fix:** Add `plugins/mill/scripts/_bg.py` to `Context:` in Card 4.

### [BLOCKING] Card 5 Context missing _bg.py

**Location:** Batch 1 / Card 5

**Issue:** Card 5 Requirements reference `_bg._has_valid_json_result` (the consumer-acceptance assertion) but `_bg.py` is absent from `Context:` (Card 5 has no `Edits:` entry). The implementer cannot inspect the function's signature or its `{`-line detection semantics without the file.

**Fix:** Add `plugins/mill/scripts/_bg.py` to `Context:` in Card 5.

### [NIT] _probe_liveness exit-code extraction is ambiguous

**Location:** Batch 1 / Card 2 Requirements

**Issue:** `_probe_liveness` is specified to return `"exit"` when the EXIT sentinel is present, but the return type is `tuple[str, int|None]` and `check_bg_status` step 2 must ultimately yield `("exit", code)`. The Requirements do not state whether `_probe_liveness` carries the parsed exit code or just the sentinel flag, leaving the implementer to guess how the code flows from `_EXIT_CODE_RE` into the 6-step resolver.

**Fix:** Add one sentence to Card 2 Requirements clarifying that `_probe_liveness` may return `pid` (not `code`) even in the `"exit"` case, and that `check_bg_status` extracts the numeric code via `_EXIT_CODE_RE` from the already-read text before returning `("exit", code)`.

## Verdict

REQUEST_CHANGES
Two context-completeness blockers and one mock-invalidation blocker must be resolved before implementation.
