## Problem

Five reliability gaps in mill-go's dispatch/nit-enforcement machinery, each discovered during live task runs (issues #619, #612, #609, #610, #616 — all folded into this task and closed on the tracker as "captured"). Four are real functional defects; the fifth (#616) turns out to be half-already-fixed on inspection and needs a narrower follow-up than originally filed. All five live in `plugins/mill/skills/mill-go/SKILL.md` and its supporting scripts/templates — the shared orchestration path every mill-go task run goes through, so each gap reproduces on every task that hits the relevant condition (any batch/holistic APPROVE with nits, any implementer dispatch that gets killed, any task run with the affected model tier).

## Scope

**In:**
- Root-cause fix for the `nits-fixed-<scope>` marker never being written under Agent-mode dispatch (#619), plus documenting the marker for manual recovery in the Handoff section (#612).
- Reword the NIT-fix-pass dispatch instruction in both the per-batch and holistic APPROVE branches of `mill-go/SKILL.md` so it can't be misread as permission to skip *dispatching* the pass (#609).
- Extend the existing `TaskOutput(agentId, block:false)` liveness probe (already used for reviewer/fixer per #587/#595) to implementer dispatches, scoped to the stopped/interrupted-notification path only (#610).
- Harden `implementer-brief.md`'s final-report contract so the implementer's free-text summary states an honest card-count rather than an unqualified completion claim, independent of model tier (#616, second half).
- Add a regression test locking `roles.implementer.model` in the config template away from `haiku` (#616, guards against the default flip-flopping back — it has already changed direction twice in git history).

**Out:**
- Do NOT re-litigate or lower `roles.implementer.model`'s default — verified it already resolves to `sonnethigh` in this repo's `mill-config.yaml` template (commit `410f8053`, 2026-06-23), so the "raise the default" half of #616 is already done. No config value changes.
- Do NOT touch reviewer/fixer's existing liveness-probe logic (step 4(c)) — it already works correctly; #610 only extends the pattern to implementer dispatch, it doesn't change reviewer/fixer.
- Do NOT change `_nit_gate.compute_unfixed_nits`'s marker-based semantics (e.g. inferring "fixed" from commit evidence instead of a marker) — rejected in Q1 as unnecessarily large blast radius for what is a dispatch-layer bug, not a gate-design flaw.
- Do NOT remove the implementer's free-text summary or make output JSON-only — rejected in Q4 as a bigger behavior change than the defect warrants.
- Do NOT touch subprocess/psmux dispatch mode's fix/implementer flow — the marker-drop bug (#619) and the liveness-probe gap (#610) are both specific to Agent-mode dispatch's split prepare/finalize processes; subprocess/psmux's `--stage full` runs prepare+dispatch+finalize in one process invocation, so `args.nits_only` and liveness are not subject to the same cross-process argument-loss failure mode.

## Decisions

### nits-only-envelope-threading (#619 root cause)

- Decision: Thread `nits_only` through the prepare-stage JSON envelope emitted by `emit_prepare` (in `_implementer_common.py`), mirroring the existing optional-field pattern used for `start_sha` (only added to the dict when not `None`/falsy). `millpy-fix.py`'s prepare-stage call passes `nits_only=args.nits_only` through to `emit_prepare`. Update mill-go/SKILL.md's "## Agent-mode dispatch" step 6 generic finalize-argument-threading rule: for `millpy-fix.py` finalize calls specifically, additionally re-pass `--nits-only` when the prepare envelope's `nits_only` field is `true` (alongside the already-documented `--scope`, `--batch-name`, `--review-file` re-pass and the `--session-id`/`--start-sha` envelope-threaded flags).
- Rationale: `_forward_output` in `_implementer_common.py` only writes the `nits-fixed-<scope>` marker (and skips the no-content-commit gate) when `nits_only=True` is passed at `--stage finalize` (confirmed at `millpy-fix.py:319`, `_implementer_common.py:1093-1097`). Because Agent-mode dispatch splits prepare and finalize into two separate CLI process invocations, `argparse` state does not persist between them — each stage only knows what flags it was literally given. SKILL.md's step 6 (line 152, as of task start) lists the flags to re-pass at finalize and does not include `--nits-only`, so under Agent-mode dispatch (the config default: `llm.claude.dispatch: agent`) every NIT-fix pass's finalize call silently runs with `nits_only=False`. This is the exact, previously-undiagnosed root cause of #619's reproduction (`unfixed_nits: ["holistic"]` after a documented, successfully-completed NIT-fix pass) — it was not a "SKILL.md forgot to call `_status.append_phase`" gap as the issue speculated; the marker-writing code already exists and already runs, it just never receives the flag it's gated on. Threading the field through the envelope (rather than just adding it to the flag-list prose) matches the established pattern already used for `session_id`/`start_sha`/`round`, and is unit-testable at the script layer, unlike a second hand-maintained prose flag list that could drift again the same way the first one did.
- Rejected: (a) docs-only fix (just add `--nits-only` to the existing flag list) — same fragility class as the bug being fixed, no test coverage possible; (b) redesigning `_nit_gate.compute_unfixed_nits` to infer "fixed" from commit evidence instead of requiring a marker — treats a dispatch-argument bug as a gate-design problem, unnecessarily large blast radius, and breaks the marker-based manual-recovery workflow #612 depends on.

### nits-fixed-marker-recovery-docs (#612)

- Decision: Add a short paragraph to mill-go/SKILL.md's Handoff section (near the existing "Nit-enforcement gate" prose) documenting that the gate requires a `nits-fixed-<scope>` row in status.md's timeline, and that when an operator manually completes/verifies a NIT-fix pass outside the documented flow (e.g. recovering from an orphaned/crashed fixer session), they must append it themselves: `_status.append_phase(status_path, f"nits-fixed-{scope}", _timestamp.now_utc_iso())`, where `scope` is the batch name or `"holistic"`.
- Rationale: Independent of the #619 root-cause fix above (which corrects the automatic path), an operator can still end up needing manual recovery for other reasons — a crashed fixer session, a subprocess/psmux worker that died mid-run, or any future edge case. Today the marker's existence is discoverable only by reading `_nit_gate.py` / `_implementer_common.py` source, which is exactly the friction #612 reports.
- Rejected: none — this is uncontroversial documentation, not a design fork.

### nit-dispatch-wording-split (#609)

- Decision: In both the per-batch (SKILL.md line ~378) and holistic (line ~680) APPROVE branches, split the single ambiguous sentence into two: a Builder-facing mandate ("dispatch the NIT-fix pass whenever `nit_count > 0` — there is no exception to this for the Builder") and a fixer-facing latitude clause ("the fixer may leave a nit unfixed only when the reviewer explicitly marked it 'no action required'"), matching the issue's own suggested rewrite verbatim.
- Rationale: The current single sentence — "NEVER skip the NIT-fix pass... Only nits a reviewer explicitly marks 'no action required' may be left." — puts the fixer-scoped exception clause immediately after a Builder-scoped imperative, so it reads as modifying the Builder's dispatch decision instead of the fixer's per-finding judgment. This caused a live misread (#609's reproduction) where the sole nit being "no action required" was taken as permission to skip dispatching the pass entirely, which then tripped the nit-enforcement gate anyway (no `nits-fixed-<scope>` marker was ever produced, since the fix pass never ran).
- Rejected: (a) keep one sentence, reorder clauses — still one sentence to misparse, doesn't remove the ambiguity, just relocates it; (b) replace with a condition→action table — bigger structural change to the surrounding prose than the fix warrants, and this SKILL.md section is otherwise in imperative-prose style throughout.

### implementer-liveness-probe (#610)

- Decision: Extend the existing step 4(c) liveness probe pattern to implementer dispatches, but scoped specifically to the "stopped/interrupted notification" branch of step 4(b) — not to clean-turn-exhaustion. When an implementer's `<task-notification>` indicates the background agent was stopped/interrupted (as opposed to a clean non-error, non-JSON turn-exhaustion message), call `TaskOutput(task_id: <agentId>, block: false)` using the retained `agentId` (same mechanism as step 4(c)) *before* invoking `--stage finalize`. Branch: if the probe reports the agent is still running, take no action this turn (no finalize call, no escalation) — wait for the agent's own next `<task-notification>` for the same `agentId`. If the probe reports the agent is no longer running, or the probe call itself errors, proceed to invoke `--stage finalize` exactly as documented today; its existing success/incomplete/transient/logic classification is unchanged and remains the second-layer disambiguation for any commit-count evidence that does exist.
- Rationale: Step 4(b)'s existing carve-out reasoning ("finalize's own completeness recount already disambiguates partial-vs-dead") only holds when there is commit evidence to recount against. The #610 incident is exactly the case where it doesn't: a stopped/interrupted notification arrived with zero commits made, finalize correctly found no JSON and emitted the synthetic `stuck_type: logic, reason: "no structured report"` (confirmed reachable at `_implementer_common.py:1466`), and this routed straight to ask-user (SKILL.md line 283) — with no opportunity to catch that the underlying agent was, per the incident report, still alive and later delivered a genuine completion notification for the same `agentId`. That is structurally identical to the `#587`/`#595` staleness problem the reviewer/fixer probe already solves; reusing the same mechanism at the same decision point (before treating the notification as terminal) closes the gap with no new pattern to design or test independently.
- Rejected: (a) docs-only — just name "logic/no structured report" as a documented 4th outcome, no behavior change — doesn't actually prevent the false escalation the incident describes; (b) bounded sleep before finalize instead of a point-in-time probe — reintroduces exactly the fixed-timeout guessing game the #587/#595 probe was built to avoid, and the harness already tells us definitively whether the agent is alive.

### implementer-brief-completeness-self-check (#616, second half)

- Decision: Add an explicit instruction to `implementer-brief.md`'s final-report section, alongside the existing "Pre-report self-check (mandatory before emitting success JSON)" dirty-tree check: before writing the free-text turn summary, count committed cards (`git -C <PROJECT_ROOT> log <batch-start-ref>..HEAD --oneline`, matched against the batch file's `## Cards` entries — the same matching approach already described in the brief's "Resume-after-incomplete" section) and require the prose summary presented to the Builder/operator to state the real count (e.g. "4 of 9 cards committed, batch not yet complete") rather than an unqualified "all complete" claim.
- Rationale: Verified the config-template half of #616 is already fixed — `mill-config.yaml`'s `roles.implementer.model` already resolves to `sonnethigh`, not `haiku` (confirmed via `_config.load_config` and via `git log` on the template, commit `410f8053`, 2026-06-23, well before #616 was filed against a downstream consumer repo's own hub config). The remaining, still-open half of #616 is the issue's second suggestion: even with the code-side completeness gate working correctly (as it did in the incident — it demoted the false "all 9 complete" self-report to `stuck_type: incomplete` and recovery proceeded correctly), the implementer's own free-text chat summary can still mislead an operator who isn't aware they need to cross-check the finalize JSON. This is independent of model tier — a task can still be configured to use a weaker model via `.millhouse/config.local.yaml` (as the incident's own workaround shows is a supported, sanctioned override), so the brief-level self-check must hold regardless of which model tier ends up running it.
- Rejected: (a) no brief change, rely solely on the finalize gate — leaves the actual reported defect (a misleading chat summary) unaddressed even though the underlying safety net already works; (b) JSON-only output, no free-text summary — removes operator visibility into what happened, a bigger behavior change than the narrow defect warrants.

### implementer-model-default-regression-test (#616 hardening)

- Decision: Add a unit test to `test-config.py` asserting that the plugin template's `roles.implementer.model` value is not `haiku` (or, more precisely, is present in an explicit allowed-tier set that excludes `haiku`).
- Rationale: `git log -p --follow` on `plugins/mill/templates/mill-config.yaml` shows this exact value has already flipped `sonnethigh` -> `haiku` -> `sonnethigh` across the file's history — i.e. it has already regressed once and been fixed once, independent of this task. A cheap, explicit test is warranted given a demonstrated recurrence risk, not a hypothetical one.
- Rejected: (a) no test, rely on manual review — review already failed to prevent the last regression; (b) runtime warning instead of a hard test — doesn't block a bad template value from shipping, only surfaces after the fact at runtime.
