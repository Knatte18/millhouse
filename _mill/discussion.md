## Problem

Four independent infrastructure/tooling bugs were reported against the mill plugin and consolidated into this one task (GitHub confirms: "Consolidated into wiki task: mill-infra-and-tooling-fixes" on all four issues). They share no code paths but are small enough to bundle:

1. **#594** — `wiki._client.health_check()` can report the daemon healthy immediately before the very next dispatch call (e.g. `set_phase()`) fails with a raw `ConnectionRefusedError` surfaced as `WikiBusyError`. Observed during a real mill-go Handoff run; not reliably reproducible (daemon restart/GC-pause race).
2. **#591** — mill-finalize's Step 5 instructs invoking `/git-pr <parent_branch>` with an env-var prefix (`MILL_FINALIZE_PR_CLEANUP=1 /git-pr <parent_branch>`) so git-pr's task-branch guard skips itself. `/git-pr` is invoked via the Skill tool, not as a literal Bash subprocess — the env-var prefix syntax never reaches git-pr's own Bash tool calls. On the "restore" path (stacked branches, `base_tracks_task_dir` true) this would incorrectly halt PR creation even though mill-finalize's cleanup already ran.
3. **#589** — `millpy-skills-index.py`'s frontmatter parser (`_extract_frontmatter()`) catches `yaml.YAMLError` and returns `None` on any parse failure, indistinguishable downstream from "no frontmatter block at all". A `description:` value with a bare unquoted `: ` substring silently drops the whole skill from `SKILLS.md` with only a generic "missing frontmatter" stderr line — no indication a parse actually failed, and the real YAML error is discarded.
4. **#588** — `mill-start`'s Phase: Select gate printed task body/brief with a plain `print()`, crashing with `UnicodeEncodeError` on Windows cp1252 consoles when the body contains non-cp1252 characters (e.g. `→`).

**Why now:** all four were found incidentally while doing other mill-go/mill-start work and filed as they were hit; grouping them into one task avoids four separate single-issue task cycles for unrelated one-file fixes.

## Scope

**In:**
- `wiki/_client.py`: make `_dispatch()`'s retry loop respawn/re-verify the daemon on `ConnectionRefusedError` instead of only resolving host/port once before the retry loop starts.
- `git-pr` SKILL.md + `mill-finalize` SKILL.md: replace the `MILL_FINALIZE_PR_CLEANUP` env-var handoff with an explicit flag argument in the `/git-pr` invocation string; update git-pr's Step 2 base-branch resolution to strip/ignore the new flag token.
- `millpy-skills-index.py`: distinguish "no frontmatter" from "frontmatter present but failed to parse" and print the actual `yaml.YAMLError` message naming the offending file when parsing fails.
- `millpy-wiki-migrate.py`: apply the same utf-8-safe-stdout treatment to `_print_task_brief()` that mill-start's Phase: Select/Explore snippets already use, closing the same bug class at the one other unguarded print site found during exploration.

**Out:**
- `mill-start` SKILL.md itself needs **no change** for #588 — both call sites (Phase: Select line ~74, Phase: Explore Step 1 prose) already carry `PYTHONIOENCODING=utf-8`. Verified via `grep -rn PYTHONIOENCODING plugins/mill/skills/` — this is the only committed evidence needed; the fix predates this task.
- `mill-ghissues-to-tasks/SKILL.md`'s frontmatter is already properly quoted (verified: `description: "Drain the GitHub issue queue..."`) — the specific file named in #589's repro no longer reproduces the bug. No content fix needed there, only the scanner's silent-failure behavior.
- No change to `_dispatch()`'s connect/read timeouts or backoff schedule (`_CONNECT_TIMEOUT_SECONDS`, `_READ_TIMEOUT_SECONDS`, `[2, 4, 8]`) — the fix targets respawn-on-retry, not budget size.
- No auto-tolerant YAML parsing (e.g. pre-quoting scalars) for #589 — rejected, see Decisions.
- No change to git-pr's non-cleanup-related guard behavior, or to any other mill-finalize step.
- No broader audit of every `print()` site in the codebase for cp1252 safety beyond the one migrate-script site found during exploration.

## Decisions

### daemon-respawn-on-retry (#594)

- Decision: In `_dispatch()`, when a `ConnectionRefusedError` is caught inside the retry loop, re-invoke `_ensure_daemon(wiki_path)` (or an equivalent liveness+respawn check) before the next attempt, instead of only resolving `(host, port, token)` once at the top of the function. Re-bind `host`/`port`/`token`/`req[FIELD_TOKEN]` from the fresh `_ensure_daemon()` result before retrying. `TimeoutError` and `ConnectionResetError` retries are unaffected (a live-but-slow/reset daemon doesn't need respawning — only "connection refused" implies the target process isn't listening).
- Rationale: confirmed via code inspection that `_ensure_daemon(wiki_path)` runs exactly once at the top of `_dispatch()`, before the `for attempt in range(4)` loop. If the daemon process dies between `health_check()`'s successful round-trip and a subsequent `set_phase()` call, the retry loop just re-attempts a connection to a dead socket on the same stale `(host, port)` for the full backoff budget (~14s) and then raises `WikiBusyError` — it never re-checks whether the daemon is alive or attempts to respawn it. Fixing this at the retry-loop level closes the race for every op via `_dispatch()`, including `health_check()` itself, `set_phase()`, and future ops — no caller-side changes needed (mill-go's existing `health_check()`-then-later-write pattern keeps working as-is).
- Rejected: (a) making `health_check()` a stronger predictor by holding open a connection for the next op — breaks the stateless one-shot dispatch model, and two different ops (health-check now, set_phase later) can be separated by arbitrary caller-side work, so no held connection would span that gap anyway. (b) Widening the retry backoff budget alone — treats the symptom; if the daemon process is genuinely dead (not just slow), no amount of waiting fixes it without a respawn.

### git-pr-explicit-flag (#591)

- Decision: Add a `--skip-task-branch-guard` flag to `/git-pr`'s accepted arguments (parsed the same way mill-start already parses `--auto` from `<command-args>`/`ARGUMENTS`). mill-finalize's Step 5 changes from `MILL_FINALIZE_PR_CLEANUP=1 /git-pr <parent_branch>` to `/git-pr <parent_branch> --skip-task-branch-guard`. git-pr's Step 1.5 guard checks for the flag in its own parsed arguments instead of `$MILL_FINALIZE_PR_CLEANUP`. git-pr's Step 2 (base-branch resolution, which currently treats "the argument the user provided" as the base branch) must also be updated to strip/ignore the `--skip-task-branch-guard` token before resolving the base branch, so the two-token invocation `/git-pr <parent_branch> --skip-task-branch-guard` never has the flag mistaken for a second positional argument.
- Rationale: `/git-pr` is invoked via the Skill tool, not literally executed as a shell command — an env-var shell prefix on the invocation text has no delivery mechanism into the Bash tool calls the skill's own instructions later run (each Bash tool call is a fresh subprocess; nothing threads an outer env var into it). Flag-style arguments on skill invocations are an established, working pattern in this codebase (mill-start's own `--auto` flag, received via `<command-args>` in this very session). Reusing that mechanism requires no new machinery.
- Rejected: having mill-finalize instruct the orchestrating assistant to skip git-pr's guard bash block entirely by prose judgment call — fragile (relies on the assistant correctly recognizing "I already ran mill-finalize Step 3" and selectively skipping part of another skill's documented procedure rather than following it verbatim), and not auditable/testable the way an explicit flag is.

### skills-index-fail-loud (#589)

- Decision: Change `_extract_frontmatter()` to distinguish three outcomes instead of two: no `---`-delimited block found → `None` (current "missing frontmatter" message is correct here); block found but `yaml.safe_load` raises `yaml.YAMLError` → propagate the error (e.g. raise a typed exception or return a sentinel distinct from `None`) so `_scan()` can print a specific message: `[skills-index] {path}: frontmatter YAML parse error: {exc}` instead of the generic "missing frontmatter". The skill is still dropped from the index either way (a scanner can't safely guess intent from malformed YAML) — the fix is diagnosability, not tolerance.
- Rationale: matches the issue's own stated expectation ("fail loudly... instead of silently omitting the row"). The previously-known offending file (`mill-ghissues-to-tasks/SKILL.md`) is already fixed (description value is properly quoted) — this decision is purely about preventing the *next* occurrence from being silent, not about repairing a specific file.
- Rejected: auto-tolerating unquoted colons via preprocessing (e.g. best-effort quoting of scalar values before parsing) — YAML ambiguity here is inherent (a colon could legitimately start a new mapping key in some contexts and not others); a heuristic fix risks silently accepting genuinely malformed frontmatter in a different, harder-to-diagnose way. Failing loudly and requiring the author to quote the value is simpler and matches how the one known instance was actually fixed (by quoting).

### encoding-crash-scope (#588)

- Decision: No change needed in `mill-start`'s SKILL.md — verified both call sites already carry `PYTHONIOENCODING=utf-8`. Extend the same treatment to `millpy-wiki-migrate.py`'s `_print_task_brief()` (lines ~39-59), which prints raw `title`/`brief` strings via plain `print(f"...")` with no encoding guard — the same crash class, just currently untriggered/unreported. The fix is `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` added at the top of the script itself — not an env-var-in-invocation-docs approach.
- Rationale: cheap, directly related, closes the same bug class before it resurfaces as a separate issue. This is explicitly a one-shot migration tool (per its own docstring), so risk of touching it is low. The in-script `sys.stdout.reconfigure()` approach is chosen specifically over documenting a `PYTHONIOENCODING=utf-8` invocation prefix because `millpy-wiki-migrate.py` has no SKILL.md or wrapper invocation site — it is run manually and, separately, from one integration test — so there is no reliable place to attach an invocation-prefix convention; a human running it ad hoc would have no reason to remember the prefix, and the crash would still occur. An in-script fix is unconditional and requires no operator discipline.
- Rejected: leaving `millpy-wiki-migrate.py` untouched as "unreported, out of strict scope" — rejected because the fix is trivial and the whole point of bundling infra fixes into one task is to close a bug *class*, not just the one reported call site. Also rejected: documenting a `PYTHONIOENCODING=utf-8` invocation-prefix convention instead of an in-script fix — see rationale above, this path is unenforceable for a script with no fixed invocation site.

### combined-plan-structure

- Decision: One plan for all four fixes, structured as four independent cards in a single parallel layer (Layer A) — `wiki/_client.py`, `git-pr`+`mill-finalize` SKILL.md, `millpy-skills-index.py`, and `mill-start`-adjacent (`millpy-wiki-migrate.py`) touch disjoint files with zero overlap, so there is no DAG ordering constraint between them.
- Rationale: the four issues were explicitly consolidated into this one wiki task already (each issue's GitHub thread was closed with "Consolidated into wiki task: mill-infra-and-tooling-fixes") — splitting back into four separate mill tasks would undo that consolidation and cost four separate mill-start/mill-plan/mill-go cycles for changes this small.
- Rejected: four separate mill tasks — cleaner isolation in the abstract, but contradicts the already-made consolidation decision and adds process overhead disproportionate to the fix size.

## Technical context

- **`wiki/_client.py`** (`plugins/mill/scripts/wiki/_client.py`):
  - `_dispatch(wiki_path, op, payload)` (~line 130) is the single chokepoint for all daemon ops (`health_check`, `set_phase`, `upsert_task`, `merge_tasks`, etc.). It calls `_ensure_daemon(wiki_path)` once (line ~154) to get `(host, port, token)`, then loops `for attempt in range(4)` calling `_connect_send_recv`, catching `(TimeoutError, ConnectionResetError, ConnectionRefusedError)`, with backoff `[2, 4, 8]` seconds, raising `WikiBusyError` after the 4th failed attempt.
  - `_ensure_daemon(wiki_path)` (~line 592) reads `.wiki-daemon.json` state file, checks protocol version, does its own inline liveness probe (`socket.create_connection(..., timeout=0.5)` + an `OP_HEALTH` request with `timeout=1.0`, no retry), and if stale/dead calls `_spawn_server()` then polls `wait_for_socket_reachable()` up to `SPAWN_TIMEOUT`. This function is idempotent and safe to call repeatedly — it already returns fast (cached state file read + one quick liveness probe) when the daemon is alive, so re-invoking it inside the retry loop is not expensive.
  - `health_check(wiki_path)` (~line 570) is just `_dispatch(wiki_path, OP_HEALTH, {})` wrapped in try/except returning bool — it goes through the identical retry path as every other op, so the fix in `_dispatch()` benefits `health_check()` itself too.
  - Test harness note: `_dispatch()` short-circuits to an in-process server when `WIKI_DAEMON_INPROCESS=1` or a registered in-process server exists (`_inprocess_server(wiki_path)`) — the retry/respawn path only matters for the real-daemon TCP branch. Unit tests will need to exercise that branch specifically (likely by monkeypatching `_ensure_daemon` and `_connect_send_recv` rather than using the in-process server shortcut).

- **git-pr / mill-finalize** (`plugins/mill/skills/git-pr/SKILL.md`, `plugins/mill/skills/mill-finalize/SKILL.md`):
  - git-pr's Step 1.5 (~line 34-81) currently branches on `[ -n "$MILL_FINALIZE_PR_CLEANUP" ]` first, then falls back to checking `_paths.resolve_task_path(...)` / `_mill/status.md` existence to decide whether to halt with "This is a mill task branch...".
  - mill-finalize's Step 5 (~line 94-108) currently documents the env-var-prefixed invocation and explains why (`base_tracks_task_dir` restore-vs-remove cleanup already ran in Step 3).
  - Both files are prose+bash instructions read and executed by the orchestrating assistant — there is no separate "argument parser" module; "parsing `--auto`" in mill-start's case means the assistant reads `<command-args>`/`ARGUMENTS` and follows the documented branching logic textually. The same pattern applies here: git-pr's SKILL.md needs a documented rule for recognizing `--skip-task-branch-guard` in its own invocation arguments.

- **`millpy-skills-index.py`** (`plugins/mill/scripts/millpy-skills-index.py`):
  - `_extract_frontmatter(text)` (~line 35-51): finds the `---`-delimited block, calls `yaml.safe_load`, catches `yaml.YAMLError` → returns `None`.
  - `_scan()` (~line 70-87): for each `SKILL.md`, calls `_extract_frontmatter`; if result is `None` or missing `name`/`description` keys, prints `[skills-index] skip {path}: missing frontmatter` to stderr and continues.
  - No test currently distinguishes "no frontmatter" from "malformed frontmatter" — a new unit test fixture with a `SKILL.md` containing an unquoted colon in `description` is the direct regression test.

- **Encoding safety** (`plugins/mill/skills/mill-start/SKILL.md`, `plugins/mill/scripts/millpy-wiki-migrate.py`):
  - Confirmed via `grep -rn PYTHONIOENCODING plugins/mill/skills/`: only mill-start's two Phase: Select / Phase: Explore snippets reference it — this is the complete set of previously-vulnerable mill-start call sites, both already fixed.
  - `millpy-wiki-migrate.py`'s `_print_task_brief()` (~line 39-59) prints raw `title`/`brief` via plain `print(f"...")` (it does not print `body` — that field only emits a " BODY" marker line) — this is a **pass-through of externally-authored content** (wiki task text a user wrote, which can legitimately contain non-ASCII), which is a distinct concern from CLAUDE.md's "print()/_log() output: ASCII only" convention (that convention governs mill's own *authored* log strings, e.g. not typing an em-dash into a print statement — it cannot help with content mill code didn't compose). The fix for pass-through content is forcing the interpreter's stdout encoding, not rewriting strings.
  - `millpy-review-discussion.py` and `millpy-bg.py` were checked and are **not** at risk: all stdout output goes through `json.dumps(...)` with the default `ensure_ascii=True`, which escapes non-ASCII to `\uXXXX` before it reaches the console.
  - No central `_log.py`/logging helper exists in the codebase — `print()` is called ad hoc throughout `plugins/mill/scripts/`.

## Testing

- **`_dispatch()` respawn-on-retry**: unit test in `plugins/mill/unit_tests/` monkeypatching `_ensure_daemon` to return a stale `(host, port, token)` on first call and a fresh one on a second call, and `_connect_send_recv` to raise `ConnectionRefusedError` for the stale target and succeed for the fresh one — assert `_dispatch()` calls `_ensure_daemon` more than once across retries and ultimately succeeds instead of raising `WikiBusyError`. Also assert `TimeoutError`/`ConnectionResetError` paths do NOT trigger an extra `_ensure_daemon` call (only `ConnectionRefusedError` should re-check daemon liveness), to keep the two retry semantics distinct.
- **git-pr `--skip-task-branch-guard`**: no unit test possible (SKILL.md prose, not executable Python) — verify via existing git-pr/mill-finalize integration test if one exists in `plugins/mill/integration_tests/`, otherwise document a manual verification step (run mill-finalize's PR step on a stacked-branch fixture and confirm no halt).
- **`millpy-skills-index.py` fail-loud**: unit test fixture — a temp `SKILL.md` with an unquoted colon in `description:`; assert `_scan()`'s stderr output names the file and includes "parse error" (or similar), distinct from the "missing frontmatter" message used for files with no `---` block at all. Existing `plugins/mill/unit_tests/` likely already has a `test-skills-index.py` or similar to extend — check before adding a new file.
- **`millpy-wiki-migrate.py` encoding**: manual verification (one-shot script) — construct a task with a non-ASCII body/brief and run the script's print path in a cp1252-simulated environment (`PYTHONIOENCODING` unset), confirm no crash after the fix. A lightweight unit test around `_print_task_brief()` capturing stdout is a reasonable TDD candidate if the function is easily importable and testable in isolation.
- **`mill-start` encoding**: no test needed — already fixed and covered by the `PYTHONIOENCODING=utf-8` prefix in the documented bash snippets themselves; no separate regression test exists or is being added since the fix is a shell-invocation prefix, not Python logic.
