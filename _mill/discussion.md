### revise-blocked-resume (#852)

- Decision: widen `--revise`'s existing pre-check (Entry step 4 of `mill-plan/SKILL.md`) to also accept `phase == "blocked"`, in addition to the existing `phase == "planned" and approved == true` condition. On the `blocked` branch:
  1. Do **not** touch the overview's `approved:` field (it's already `false`).
  2. `_status.append_phase(status_path, "planning", <timestamp>)`.
  3. Commit on the task branch: `git -C <worktree> add <plan_dir> <status_path> && git -C <worktree> commit -m "mill-plan: --revise resume from blocked for {slug}"`; push.
  4. Bind a new local variable `blocked_resume_round = _review_common.discover_round(reviews_dir, "plan", "holistic")` (the next round number that will actually run).
  5. Fall through into the existing `phase: planning`/`plan-review-r{N}`/`plan-fix-r{N}` re-entry row (Phase: Plan Review; do NOT rewrite plan files) — same fallthrough target the existing `planned+approved` `--revise` branch already uses.
  - In Phase: Plan Review step 2's dispatch (both the Agent-mode branch's `<args>` and the subprocess/psmux branch's `millpy-review-plan.py` invocation via `millpy-bg`): when `blocked_resume_round` is bound **and** the current loop `round == blocked_resume_round`, thread `--max-rounds <blocked_resume_round>` into that round's dispatch only; omit it on every other round (mirrors the exact `--reviews-subdir revise-{N+1}` threading pattern already documented for the `planned+approved` `--revise` case, and mirrors mill-start's `--auto` extension-round mechanism, which threads `--max-rounds <max_review_rounds + 1>` the same way).
  - Do **not** reuse or extend the `revise-{N+1}` reviews-subdir namespacing (Phase: Plan Review's existing `revise_requested` override at lines ~266-270). That namespacing exists specifically for re-reviewing an *already-approved* plan without colliding with its original review files. A blocked-resume is a continuation of the *same never-approved* round sequence — reviews continue writing into the plain `reviews_dir`, picking up at `blocked_resume_round` via the normal `discover_round` mechanism.
  - Update the pre-check's existing "condition not met" halt message (today: names the current `phase:` and says revising an in-flight or unapproved plan is unsupported) to also cover this widened condition — i.e. it now fires only when `phase` is neither `planned+approved==true` nor `blocked`.
  - Add an explicit `blocked` row to the Entry step 4 phase table (mirrors `mill-go-base/SKILL.md`'s existing `| blocked | surface blocked_reason from status.md and halt |` row) for the **no-`--revise`** case: `phase: blocked` with no `--revise` flag surfaces `blocked_reason` and tells the operator to re-run `/mill-plan --revise` to resume plan review (or resolve manually), then halts. This is reached only when the `--revise` pre-check (which runs before the table) didn't intercept — i.e., plain `/mill-plan` with no flag.
  - No new state needs to persist across rounds (no `extension_used`-equivalent flag) — but the "one extra round, self-terminating" property below holds for only 2 of the 4 `BLOCKED:`-halt sites, not uniformly across all four. **This splits into two genuinely different cases, which must be documented separately, not asserted as one uniform behavior** (correction from discussion-review r3, BLOCKING, confirmed accurate — the first drafted version of this bullet wrongly generalized the round-exhaustion reasoning below to all four sites):
    - **Category A — the one genuinely round-cap-gated site (step 6 max-rounds escape only).** Step 6 explicitly fires "only when round counter exhausts without APPROVE" — it is the sole site actually gated on `round >= max_review_rounds`. So on `--revise` resume from a step-6 block, `blocked_resume_round > max_review_rounds` always holds, and the loop's own existing convergence-gate / step-6 logic (keyed off `round >= max_review_rounds`, the *original*, unbumped config value) treats the resumed round as already terminal regardless of its outcome: an `APPROVE` verdict hits the existing "implicit-approve-at-cap" branch in 4a/4b/4c; a `REQUEST_CHANGES` verdict with blocking findings re-triggers step 6 on that same round. The loop genuinely never attempts a further round within the same `--revise` invocation for this site — a real single-round, self-terminating grant. A second block requires the operator to explicitly re-run `--revise` again, which recomputes `blocked_resume_round` fresh.
    - **Category B — round-count-independent halts (step 1.5 validator gate, step 4.5 non-reviewable-round retry, and step 5 non-progress).** **Correction (discussion-review r4, BLOCKING, confirmed accurate): step 5 was originally placed in Category A on the false claim that it "only fires once `round >= max_review_rounds`" — re-checked against SKILL.md's actual step 5 text ("after writing each fixer report from round 2 onward... both rounds have a non-empty Pushed Back AND the title set is identical"): it has no dependency on `max_review_rounds` at all, exactly like step 1.5/4.5, and is moved here.** All three of these sites can fire at *any* point in the loop (step 1.5/4.5 from round 1, step 5 from round 2 onward), well below `max_review_rounds` in the common case. Here `blocked_resume_round <= max_review_rounds` is the common case, so the `--max-rounds <blocked_resume_round>` override is not actually granting anything extra — the CLI's own round guard was never the obstacle for these three sites (only the missing `_status.set_blocked` call was, for step 1.5/4.5; step 5 already calls it). A `--revise` resume from a Category B halt does **not** terminate after one round: it clears the sticky block and lets the loop continue with its full, ordinary *remaining* budget up to the original `max_review_rounds`, exactly as an uninterrupted run would have — a `REQUEST_CHANGES`-with-blockings outcome on the resumed round falls through to ordinary step 4d (or, for a fresh non-progress recurrence, step 5 again) and the loop keeps going; it does not re-trigger step 6. This is not a bug: threading the `--max-rounds` override is still harmless here (it's always `<= max_review_rounds` by construction, so it never grants more than the CLI's default already allows), it simply isn't doing the same *job* as it does for Category A — for Category B it exists only to satisfy the CLI's guard in the rare edge case where `blocked_resume_round` did happen to exceed the cap, not to grant a bonus round.
  - No round-budget-tracking mechanism is added to unify these cases — the natural behavior of each (self-terminating for Category A, full-remaining-budget for Category B) is accepted and documented rather than forced into a single "always exactly one extra round" story, since Category B's looser behavior is already gated by the same requirement as Category A: an explicit, operator-invoked `--revise`.
  - **Distinguishing a blocked-resume `--revise` from a planned+approved `--revise` at Phase: Plan Review.** Both branches of the widened Entry step 4 pre-check set the same `revise_requested` flag and fall through to the identical `phase: planning`/`plan-review-*`/`plan-fix-*` re-entry row — but Phase: Plan Review's existing `revise-{N+1}` reviews-subdir namespacing override (SKILL.md ~lines 266-270) is gated purely on `revise_requested`, and per the bullet above, blocked-resume must NOT trigger that namespacing (it's a continuation of the same never-approved round sequence, not a fresh revision pass over an approved plan). A bare `revise_requested` flag cannot distinguish the two sources at that later point. **Fix (correction from discussion-review r4, BLOCKING, confirmed accurate — the original text asserted the "do not reuse the namespacing" requirement with no mechanism to actually implement it):** the Entry step 4 pre-check binds a second, distinct local boolean, `revise_from_blocked` — `True` only when the pre-check's `blocked` branch fires, `False`/unbound on the `planned+approved` branch — and threads it (alongside `revise_requested`) into Phase: Plan Review. Phase: Plan Review's Path Setup then gates the `revise-{N+1}` namespacing override on `revise_requested and not revise_from_blocked` (instead of `revise_requested` alone), and gates the `blocked_resume_round`/`--max-rounds` threading (described above) on `revise_from_blocked` specifically, not on `revise_requested`. This is a strict narrowing of the existing namespacing condition and a new, separately-gated condition for the round-cap-override behavior — no other existing `revise_requested`-gated behavior in Phase: Plan Review changes.
  - **All four `BLOCKED:`-halt sites, not just step 5/step 6, must set `phase: blocked`.** `mill-plan/SKILL.md` currently has *four* places that halt with a `BLOCKED:`-prefixed message, but only two of them (step 5 non-progress, step 6 max-rounds escape) actually call `_status.set_blocked` — confirmed by re-reading the current text: step 1.5's two-pass cap ("halts with `BLOCKED: plan-validate non-progress`", ~line 300) and step 4.5's two-pass cap ("halt: ... report `BLOCKED: plan review no-JSON round {N}` ... / `BLOCKED: review ERROR-only round {N}`", ~lines 478-479) both halt without ever mutating `status.md`. This is a real, pre-existing gap, not a hypothetical: since Phase: Plan already appended `phase: planning` before Phase: Plan Review starts, and neither of these two halts advances phase any further, the halt is **not sticky** — a plain (no `--revise`) re-run of `/mill-plan` lands back on Entry step 4's existing `phase: planning`/`plan-review-*`/`plan-fix-*` re-entry row and silently resumes straight back into the same failing two-pass cycle, which defeats the entire point of a two-pass cap (forcing a human to look at the unresolved errors before another attempt). This is in scope for #852 (not scope creep): it's the same control structure (Phase: Plan Review + step 1.5), the same underlying issue (a `BLOCKED:` halt with no working resume/re-entry contract), and leaving it unfixed means the widened `--revise` mechanism above only actually works for 2 of the 4 halt sites — a user hitting the other two still has no resume path, which is exactly the symptom #852 reports.
    - **Step 1.5 fix:** immediately before the existing halt, add `_status.set_blocked(status_path, "plan-validate non-progress", timestamp=<now_utc_iso()>)`; commit `git -C <worktree> add <status_path> && git -C <worktree> commit -m "mill-plan: blocked (plan-validate non-progress) for {slug}"`; push. Then halt with the existing `BLOCKED: plan-validate non-progress` message and the unresolved errors, unchanged.
    - **Step 4.5 fix:** immediately before the existing halt, add `_status.set_blocked(status_path, f"plan review no-JSON round {N}", timestamp=<now_utc_iso()>)` (absent-JSON branch) or `_status.set_blocked(status_path, f"review ERROR-only round {N}", timestamp=<now_utc_iso()>)` (ERROR-only branch); commit `git -C <worktree> add <status_path> && git -C <worktree> commit -m "mill-plan: blocked (<same reason string>) for {slug}"`; push. Then halt with the existing message, unchanged.
    - Both additions mirror step 5/step 6's existing `set_blocked` → commit → push → halt shape exactly — no new pattern is introduced.
  - **Stale cross-reference to fix during implementation.** `mill-plan/SKILL.md`'s "Entry-gate wait for upstream mill-start" section (~line 98) currently states "mill-plan's phase table has no pre-existing `blocked` row to reuse the exact message shape from (unlike mill-go's side)" — this becomes false once the new Entry-table `blocked` row lands. The plan must update this sentence to either point at the new row or drop the "no pre-existing row" caveat (keep the rest of that branch's behavior — an unrelated `BLOCKED: <reason>` halt for a *different* condition, the upstream mill-start wait timing out or reporting blocked — unchanged; only the stale cross-reference sentence needs editing).
- Rationale: reuses existing, already-battle-tested machinery — `millpy-review-plan.py`'s own `--max-rounds` CLI override (already implemented, used nowhere in `mill-plan/SKILL.md` today) and mill-start's proven round-cap-extension shape — rather than inventing new mechanics. Bounded by construction: every resume grants exactly one additional round, with no risk of an unbounded auto-retry loop, since each resume requires an explicit operator-invoked `--revise`.
- Rejected:
  - A separate `--unblock` flag: unnecessary fragmentation — `--revise`'s existing meaning ("re-open this plan for another review pass") already covers "give the review loop another shot," whether the plan was previously approved or blocked.
  - A message-only Entry-table `blocked` row with no widened `--revise` (mirroring mill-go's existing row verbatim and stopping there): does not satisfy the issue's core ask (an actual resume path) — mill-go's `blocked` row was confirmed, while investigating this, to have exactly the same "surface and halt" dead end mill-plan has today, so it's not a working precedent to copy as the *complete* fix, only as the message-shape precedent for the no-`--revise` case.

### go-tags-chained-invocation (#853)

- Decision: in the Step 1.5 fix table's `verify-excludes-edited-tagged-test` row (`mill-plan/SKILL.md` ~line 326), replace the remedy text. Current text:
  > If a `-tags` flag already exists, append `,<tag>` to its value; otherwise append `" -tags <tag>"` to the command.

  New text (only the "already exists" branch changes; the "otherwise" branch is correct as-is per the issue's own note and is kept verbatim):
  > If a `-tags` flag already exists on the command: do not comma-join `<tag>` into its value. Note this is a defense-in-depth choice, not a correction of broken Go semantics — Go's `-tags` set is satisfied by ANY-membership (each file's own `//go:build` line is checked independently against the full enabled-tag set, so a plain single-tag `//go:build scout` file is compiled/run whenever `scout` is enabled, regardless of what else is also enabled; `-tags integration,scout` does NOT exclude it). The real risk is project-specific: some repos deliberately give tagged suites mutually exclusive semantics (a suite's own constraint combines its tag with a negation of a sibling suite's tag, e.g. to keep suites isolated for cost/reporting reasons) — comma-joining silently breaks that convention if it's in use, and this check cannot tell whether a given project relies on it. Instead, append a new ` && `-chained invocation of the same base command (same verb and package pattern as the existing invocation) carrying its own `-tags <tag>` flag — strictly safer, since it never assumes either way. Otherwise (no `-tags` flag anywhere in the command yet): append `" -tags <tag>"` to the command in place, unchanged.
- Rationale: verified against the actual check implementation (`_plan_validate.py`'s `_verify_command_has_any_tag`, ~line 2115) that this remedy round-trips cleanly: it scans the *entire* command string via `_RE_VERIFY_TAGS_FLAG.finditer(command)`, not just the first `-tags` occurrence, so a `&&`-chained second invocation's own `-tags <tag>` is correctly detected on re-validation — this fix will not trigger the two-pass validator-fix cap. The "no `-tags` yet" branch is left untouched because there is no existing tag to conflict with in that case — a single in-place `-tags <tag>` append is already correct, exactly as the issue states.
  **Correction (discussion-review r1, BLOCKING, confirmed accurate):** the first drafted version of this row claimed Go's `-tags` list is a conjunction (AND) that "satisfies neither" suite when comma-joined. That is factually wrong — this repo's own `_verify_command_has_any_tag` uses ANY-membership matching, which only makes sense because Go's `-tags` semantics are themselves ANY/union, not AND. The row text above was rewritten to ground the remedy in the real, narrower risk (project-specific mutual-exclusion conventions this check cannot detect) instead of a false universal semantics claim. The remedy (chain a new invocation) is unchanged — it remains strictly safer regardless of which theory justifies it — only the stated *reason* changed.
- Rejected: rewriting both branches to always chain a new invocation (even when no `-tags` exists yet) — unnecessary; the issue explicitly confirms the untagged case is already correct, and always chaining would produce a redundant untagged-plus-tagged invocation pair where one is unneeded.

## Technical context
