## Problem

`_plan_validate.py`'s `context-completeness` check has a symbol branch: when a plan card's `Requirements:` backtick-quotes a bare or dotted identifier (`SaveState`, `reedengine.New`), the check resolves it to a declaring file via `_resolve_symbol_files` and flags the card if that file isn't in its own `Context:`/`Edits:`/`Creates:`/`Deletes:`/`Moves:`-source set. `_resolve_symbol_files` resolves by walking every source file under a candidate root and doing `word_re.search(content)` — a raw case-sensitive whole-word regex against the entire file text, with no check that the match is an actual declaration of that symbol, and no scoping beyond a build-artifact denylist (`.git`, `node_modules`, `vendor`, `__pycache__`, `dist`, `build`, `.venv`).

Six closed GitHub issues (#1008, #1015, #1023, #1030, #1033, #1037), filed across three different source repos over two weeks of real `/mill-plan` sessions, all trace to this one function:

- **#1037** — a package-qualified reference (`loomengine.ConfigTemplate()`) is unambiguous as written, but `_symbol_candidate_shape` discards the qualifier and searches only the bare trailing segment (`ConfigTemplate`); when that bare name is declared in 10 packages, the caller's `len(matches) != 1` ambiguity guard silently drops a reference a human already disambiguated. False negative — the check goes clean, missing a real Requirements:/Context: gap.
- **#1033** — a JSON envelope key (`` `status_file` ``, in a Go struct tag string) and a Claude Code hook event name (`` `SessionStart` ``, likely a string literal) each resolve to a file that merely contains the text, not a declaration of a symbol by that name. False positive with an actively-wrong suggested remedy.
- **#1030** — a bare property name (`Outlet`) the card is declaring on its own new type coincidentally matches a real property declaration inside a deprecated, out-of-solution C# tree (`NORCE.Models.Deprecated`). False positive: the match is a genuine declaration, just in a tree that was never in scope.
- **#1023** — a token (`Known`) matches only as the first word of a `//` line comment, not any declaration. False positive from the purest form of the naive-search bug.
- **#1015** — several tokens (`plan.Language`, `Unit`, `glyph.Self`, `CGO_ENABLED`) resolve to files where the identifier is used (test-fixture code, an unrelated struct-field selector, an external-module identifier with no in-repo declaration) rather than declared. False positives from usage-site matches.
- **#1008** — a card introducing new types with fields `Path`/`Disposition` gets flagged because those common names happen to also appear (most likely as usages, not declarations) in unrelated files elsewhere in the repo.

Commit `ae07b506` (already landed) fixed a batch of false positives in the check's **path** branch (gitignored/quoted/negated/citation/cross-reference prose). It did not touch `_resolve_symbol_files` or `_symbol_candidate_shape` — confirmed by reading the current source (`plugins/mill/scripts/_plan_validate.py:1973-2037` for `_resolve_symbol_files`, `:1926-1970` for `_symbol_candidate_shape`) and by `git log --oneline -- plugins/mill/scripts/_plan_validate.py`, which shows `ae07b506`'s own commit message scoped to path-token exemptions only. The symbol branch's core resolution logic is unchanged since it was introduced in `e040f4e5`.

## Scope

**In:**
- `_resolve_symbol_files`, `_symbol_candidate_shape`, and their caller `_check_context_completeness` in `plugins/mill/scripts/_plan_validate.py`.
- Declaration-form matching per source extension (`.py`, `.go`, `.cs`, `.ts`) replacing the current naive `word_re.search(content)` whole-file text search.
- Qualifier-aware disambiguation: when a dotted token's bare trailing-segment search yields more than one match, narrow using the qualifier segment (currently discarded) instead of unconditionally treating >1 matches as unresolvable.
- Solution-scope directory pruning: extend the existing walk-pruning mechanism (`_SYMBOL_SEARCH_DENYLIST_DIRS`) to also skip conventionally out-of-solution trees, so a real declaration living only in a deprecated/legacy tree doesn't produce a match.
- New unit tests in `plugins/mill/unit_tests/test-plan-validate.py` covering the underlying mechanisms (declaration-vs-usage, qualifier disambiguation, scope pruning) plus a minimal characterization test per source issue (#1008, #1015, #1023, #1030, #1033, #1037).
- Docstring updates on `_resolve_symbol_files` and `_check_context_completeness` describing the new matching semantics.

**Out:**
- The path branch of `_check_context_completeness` — unchanged, already covered by `ae07b506` and earlier commits.
- Any new citation/escape-hatch marker syntax for "this names a symbol I'm creating" — the existing citation-marker/prohibition/negation/contrast/quoted-material exemptions (which already apply to both branches per the check's own docstring) are the accepted residual escape hatch; see Decision `fix-scope` below.
- Config-driven customization of the scope-pruning directory list — hardcoded, matching the existing `_SYMBOL_SEARCH_DENYLIST_DIRS` precedent; see Decision `solution-scope-pruning`.
- Full AST/tokenizer-based parsing for any of the four languages — regex-based declaration-form matching only, consistent with this check's existing heuristic nature ("heuristically detects", "unresolvable-with-confidence... never flagged" already in its docstring).
- Re-triaging or re-commenting on the six source GitHub issues — all six are already closed; this task lands the fix, not issue bookkeeping.
- The emitted finding `message` wording — stays byte-for-byte unchanged (a downstream fixer-doc check parses it to distinguish the symbol case from the path case; see `_check_context_completeness`'s own docstring warning at `plugins/mill/scripts/_plan_validate.py:2214-2217`).

## Decisions

### fix-scope

- Decision: Fix the resolution engine only (declaration-form parsing + qualifier disambiguation + solution-scope pruning). No new escape-hatch marker.
- Rationale: All six issues are precision/recall bugs in how `_resolve_symbol_files` decides "does this file declare this symbol", not gaps in the exemption system around it. The existing citation-marker escape hatch (`signature inlined`, `no file read needed`) already covers any residual case a human plan-author needs to force through. Adding a second escape-hatch mechanism for the same underlying problem would be scope creep the three-pronged engine fix makes unnecessary.
- Rejected: A new "this names a symbol I'm creating" marker — redundant with the existing citation marker, and adds a second phrase for plan-authors to remember for what is fundamentally the same "don't read this file" signal.

### declaration-form-regex

- Decision: Per-extension regexes recognizing genuine declaration syntax, not bare word occurrence:
  - **Go (`.go`)**: top-level `func [(<recv>)] SYMBOL(` / `func [(<recv>)] SYMBOL[`, `type SYMBOL`, `const SYMBOL`, `var SYMBOL` — including a `SYMBOL`-leading member line inside a grouped `const ( … )` / `var ( … )` block, tracked as a single bounded open/unclosed-group boolean carried while scanning the file (increment on an unmatched `const (`/`var (`, decrement on the closing `)`). This is a single-level state counter, not the general enclosing-scope tracking the Python bullet below declines to add for the class-body-attribute case — it answers only "am I currently inside one specific still-open paren group", never "which class or function currently encloses this line", so it doesn't reopen the mini-parser the `declaration-form-regex` decision rejects.
  - **C# (`.cs`)**: type-level `(class|struct|interface|enum|record) SYMBOL`; member-level a line carrying an access modifier (`public|private|protected|internal`) followed by `SYMBOL` followed by `(`, `{`, `;`, or `=` (covers methods, properties, fields).
  - **Python (`.py`)**: `(def|class) SYMBOL`, plus a module-level (column-0, unindented) assignment or annotation form — `^SYMBOL\s*(:\s*\S.*)?=` — to cover a module constant (`MAX_SIZE = 100`, `MAX_SIZE: int = 100`). A same-shape line indented one level (a class-body attribute, e.g. `    SYMBOL: str`) is a deliberately accepted residual gap: Python has no access-modifier keyword to anchor on the way C#'s member regex does, so distinguishing a class attribute from a same-indentation local variable inside a top-level function would need enclosing-scope tracking — the mini-parser the `declaration-form-regex` decision already rejects. A symbol declared only as a class-body attribute in Python falls back to today's zero-match, not-flagged behavior, not a crash or a wrong resolution.
  - **TypeScript (`.ts`)**: `(function|class|interface|type|enum) SYMBOL`, or `(export )?(const|let|var) SYMBOL`.
  - A match must be anchored to one of these declaration shapes; a token that only appears inside a string/template literal, a struct tag, a comment, or as a usage/field-access site does not match, because none of those shapes are declaration syntax. No separate comment-stripping pass is needed — anchoring to the keyword shape already excludes ordinary comment text (a comment would need to independently start with `func`/`type`/`class`/`def` etc. to false-positive, which is not the failure mode any of the six issues exhibit).
  - Also capture, per matched file: the Go `package <name>` line (if any) and the C#/TS `namespace <name>` line (if any) — needed by qualifier disambiguation below.
- Rationale: This is the single change that fixes #1033 (JSON key / hook-event-name string literal, never a declaration) and #1023 (comment-only occurrence) outright, and substantially reduces #1015's and #1008's false-positive rate by rejecting usage-site matches (field access, local assignment, string literals) that a bare `word_re` cannot distinguish from a declaration. It does not by itself fix #1030 (a genuine declaration in an out-of-scope tree) or fully eliminate #1008's residual risk (a common name can still be legitimately declared elsewhere in-scope) — those are handled by the other two decisions below and an accepted residual limit, respectively.
- Rejected: Restrict to Go only, since most repro reports are Go — rejected because `_SYMBOL_SEARCH_EXTENSIONS` already spans all four languages today, #1030 is a C# repro, and narrowing coverage would reintroduce the bug for three of the four already-supported languages.

### qualifier-disambiguation

- Decision: `_symbol_candidate_shape` keeps returning the trailing segment as the search key (unchanged — it's still what gets searched for), but now also returns the qualifier segment (`None` for a bare token) alongside it. `_resolve_symbol_files` itself stays cached and keyed by `search_key` **alone**, exactly as today, and returns the **full, unfiltered** declaration-form match list for that search key — it does not accept or apply the qualifier at all. Qualifier filtering is a separate step the caller (`_check_context_completeness`) applies to whatever match list it gets back, whether from a fresh `_resolve_symbol_files` call or a cache hit: when that list has more than one entry and the token was dotted, filter to matches whose file satisfies the qualifier — first by an exact match against that file's captured `package`/`namespace` name; if no `package`/`namespace` statement narrows it to exactly one file (e.g. non-Go/C#/TS languages, or a file with no such statement), fall back to matching the qualifier against the immediate containing directory's basename (case-insensitive). If this narrows the match set to exactly one file, resolve to it (previously silently discarded by the `len(matches) != 1` guard). If it narrows to zero, or stays above one, keep today's behavior: unresolvable-with-confidence, not flagged. A bare (non-dotted) token skips this step entirely and keeps today's `len(matches) != 1` check verbatim.
- Rationale: Directly fixes #1037 — `loomengine.ConfigTemplate()` now resolves because the ambiguous bare-name match set narrows to the one file whose `package loomengine` line matches the qualifier. Keeping `_resolve_symbol_files`'s cache keyed by `search_key` alone and applying qualifier-filtering downstream of every lookup (hit or miss) means two dotted tokens sharing a trailing segment but different qualifiers (`reedengine.New` then `otherpkg.New`) each get filtered against their own qualifier every time, instead of the second one silently inheriting the first call's already-filtered result from the cache — the cache only ever holds the qualifier-independent raw match list, so it can't go stale across different qualifiers for the same trailing segment. The fallback to directory-basename matching keeps the mechanism useful for C#/TS callers where a `namespace` statement may be absent or the qualifier is a local alias rather than the full namespace.
- Rejected: Go-only, `package`-statement-only disambiguation (no directory-basename fallback) — rejected because it silently does nothing for C#/TS/Python qualified references, which are equally valid dotted tokens under `_RE_SYMBOL_SHAPE`. Also rejected: threading the qualifier into `_resolve_symbol_files` and caching under a composite `(search_key, qualifier)` key — this would multiply cache entries per distinct qualifier sharing a trailing segment and adds a second cache-key shape to reason about, for no benefit over filtering the same cached raw list downstream.

### solution-scope-pruning

- Decision: Extend the directory-pruning set the walk already applies (today `_SYMBOL_SEARCH_DENYLIST_DIRS`, checked against `dirnames` during `os.walk`) with a second, case-insensitive check against a small fixed list of conventional out-of-solution directory-name markers: `deprecated`, `legacy`, `obsolete`, `archive`. Any directory whose basename matches one of these (case-insensitive) is pruned exactly like `node_modules`/`vendor` — never descended into, so no file below it is ever a candidate declaration site, for either the plain bare-name path or the qualifier-disambiguation path above.
- Rationale: Fixes #1030 directly — `NORCE.Models.Deprecated` is pruned, so `Outlet`'s only match (a real property declaration inside that tree) never enters the candidate set, leaving zero matches for the card's own new property (correctly unresolvable-with-confidence, not flagged). This mirrors the existing denylist's own mechanism and cost profile exactly (a `dirnames` basename check per directory visited), so it adds no new walk pass and no new candidate-root concept.
- Rejected: Making the pruned-name list configurable via `mill-config.yaml` — rejected as unneeded weight for a heuristic gate; the existing `_SYMBOL_SEARCH_DENYLIST_DIRS` is itself hardcoded, and these four markers are conventional enough (already proven by one real-world repro) to not need per-project tuning. A project with a legitimately-named `legacy/` directory that IS in scope can still name the file directly in `Context:`/`Edits:` — this check is advisory, not a hard gate.

## Technical context

Current implementation (`plugins/mill/scripts/_plan_validate.py`):

- `_resolve_symbol_files` (line 1973): builds `candidate_roots` in the documented first-match-wins precedence (`git_root/root`, then `project_root/root` or bare `project_root`, then bare `git_root`), walks each with `os.walk`, prunes `_SYMBOL_SEARCH_DENYLIST_DIRS` (line 1828: `.git`, `node_modules`, `vendor`, `__pycache__`, `dist`, `build`, `.venv`), and for every file whose suffix is in `_SYMBOL_SEARCH_EXTENSIONS` (line 1823: `.py`, `.go`, `.cs`, `.ts`) does `word_re.search(content)` where `word_re = re.compile(r"\b" + re.escape(search_key) + r"\b")` (line 2012). Memoized per `run()` call via the `cache`/`search_cache` dict, keyed by `search_key` only — per Decision `qualifier-disambiguation`, this stays exactly as-is: the cache holds the raw, qualifier-independent match list, and qualifier filtering happens downstream of every lookup (hit or miss), never inside `_resolve_symbol_files` or the cache key.
- `_symbol_candidate_shape` (line 1926): strips a trailing `:line-range` suffix and trailing call/generic groups, requires the remainder to match `_RE_SYMBOL_SHAPE` (bare or one-dot-segment identifier), then — for a dotted token — returns **only** `segments[-1]` (the trailing segment) when it "qualifies" (not all-lowercase, or contains `_`); the qualifier segment (`segments[0]`) is read only to note in the docstring that it doesn't matter, and is otherwise discarded today. This is the discard point Decision `qualifier-disambiguation` needs to stop doing.
- Caller `_check_context_completeness` (symbol branch at lines 2468-2500): checks `search_cache` first, else calls `_resolve_symbol_files`; `if len(matches) != 1: continue` (line 2478) is the ambiguity guard Decision `qualifier-disambiguation` needs to feed a narrowed match set into, not bypass. `canonical = matches[0].relative_to(producing_root).as_posix()` (line 2481) canonicalizes the sole surviving match; `_covered_by_own_refs(canonical, own_refs, moves_sources)` (existing, unchanged) checks it against the card's own `Context:`/`Edits:`/`Creates:`/`Deletes:` tokens and plan-wide `Moves:` sources before emitting a finding.
- Every existing exemption (quoted-material at lines 2317-2327, then prohibition-marker, non-dependency-negation, citation-marker, contrast-citation at lines 2340-2359) already runs before the branch split on `is_path_shaped`, so all of them already apply to the symbol branch unchanged; this task adds no new exemption logic there.
- The emitted finding's `message` field format (`"card {card_num}'s Requirements: references symbol '{token}', which resolves to '{canonical}' -- not in this card's Context:/Edits:/Creates:/Deletes:/Moves:-source"`, lines 2494-2497) must not change wording — a downstream fixer-doc check parses it (see the check's own docstring, lines 2214-2217).
- Existing unit test fixtures in `plugins/mill/unit_tests/test-plan-validate.py` (functions `test_check_context_completeness_symbol_*`, starting line 3047) already use genuine declaration-form Go source in their fixtures (e.g. `"package internal\n\nfunc SaveState() {}\n"`) — confirmed by reading every symbol-branch test in that file. None of them rely on a non-declaration-form match, so none should need assertion changes from the declaration-form-regex decision alone; `test_check_context_completeness_symbol_dotted_trailing_segment_only` and `test_check_context_completeness_symbol_dotted_ambiguous_trailing_segment` already have exactly one matching `package <qualifier>` file (former) or zero matching-qualifier files among the ambiguous set (latter — both fixture files declare `package internal`, not `package batch`), so their expected outcomes are unchanged by qualifier disambiguation either; verify this expectation holds rather than assuming it while implementing, since the exact regex shape could shift it.
- `_check_context_completeness`'s own docstring (lines 2202-2217) documents the symbol branch's current semantics and needs updating to describe declaration-form matching, qualifier disambiguation, and solution-scope pruning — same content, this task changes what the paragraph says the branch does.

## Testing

TDD candidates, all in `plugins/mill/unit_tests/test-plan-validate.py` alongside the existing `test_check_context_completeness_symbol_*` suite:

- **Declaration-form matching**: a token that occurs only inside a `//`/`#` comment does not resolve (characterizes #1023); a token that occurs only inside a string/struct-tag literal does not resolve (characterizes #1033's `status_file` case); a token that occurs only as a usage/field-access site (not a declaration) in an unrelated file does not resolve (characterizes #1015 and #1008's residual usage-site false positives); a token at a genuine top-level declaration still resolves exactly as before (regression, covers the existing suite's fixtures) — cover **all four** supported extensions (`.py`, `.go`, `.cs`, `.ts`) for each of these, not just a Go/C# subset, since each language's declaration regex is a distinct piece of matching logic that can independently regress. Additionally, for Python specifically: one test confirming the module-level assignment/annotation form resolves (`MAX_SIZE = 100` at column 0), and one confirming a class-body attribute at one indent level does NOT resolve — the accepted residual gap from Decision `declaration-form-regex`, characterized rather than left implicit.
- **Qualifier disambiguation**: a dotted token whose bare trailing segment matches two files, exactly one of which declares the matching `package`/`namespace`, resolves to that one file (characterizes #1037); the same but disambiguating via containing-directory basename when no `package`/`namespace` line narrows it; a dotted token whose qualifier matches zero or more than one candidate stays unresolvable (regression of current ambiguous-skip behavior).
- **Solution-scope pruning**: a symbol declared only inside a directory named `Deprecated` (or `legacy`/`obsolete`/`archive`) under a candidate root yields zero matches even though the declaration is real (characterizes #1030); a symbol declared both inside and outside such a directory still resolves to the outside declaration.
- **Full characterization pass**: one minimal fixture per source issue (#1008, #1015, #1023, #1030, #1033, #1037) reproducing that issue's reported scenario closely enough to serve as a regression guard, asserting the previously-reported bad outcome no longer occurs.
- Run existing suite unchanged and confirm every current `test_check_context_completeness_symbol_*` test still passes without assertion edits (per the Technical context note above) — a failure there means the declaration-form/qualifier changes have a narrower or wider match surface than intended and needs investigation before proceeding, not a fixture rewrite.
- Verify command per this repo's own convention: must start with `PYTHONPATH=` (literal, empty, single space) so the test subprocess doesn't load the plugin-cache copy of `_plan_validate.py` instead of this worktree's.
