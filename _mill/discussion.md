## Problem

mill-go's batch-verify, finalize, and baseline machinery has accumulated seven independent reliability bugs/gaps, each caught live during real mill-go runs across three different downstream repos (loomyard, millhouse itself, and NORCE.Models). None of them are hypothetical — every one has a filed GitHub issue with a concrete reproduction from an actual run. They cluster into five subsystems:

1. **mill-plan's verify-command authoring** misses failure modes it should catch and folds in failure modes it shouldn't: batches that add `//go:build` tags to previously-untagged files don't get an untagged compile check, so a Tier-1 build break introduced by re-tiering can go undetected for several batches (#642); and batches' `--only` verify lists can accidentally include test files unrelated to the batch's own cards, causing a pre-existing `main`-level failure to falsely block a fully-correct batch (#638).
2. **mill-go's finalize completeness recount** is a bare "commits since start_sha vs. cards in batch" comparison with no way to know when a batch brief legitimately sanctioned combining multiple cards into one commit — it misclassifies a genuinely complete batch as `stuck_type: incomplete`, and because `--resume-incomplete`'s re-dispatch makes no new commit (there's nothing left to do), the same misclassification repeats forever (#660).
3. **`pipeline.done_gate`** has no pre-implementation baseline pre-flight, so a self-capturing regression/snapshot test suite used as the done_gate silently captures its "baseline" from the task's own just-finished implementation at Handoff — reporting success while providing zero actual regression protection (#650).
4. **mill-go SKILL.md's extended-timeout guidance** (600000ms/10min for Bash-tool calls that replay a batch's `verify:` command) is scoped only to `millpy-fix.py --stage finalize`, but `millpy-implement.py --stage finalize` runs the exact same regression-guard verify replay and hits the same default 2-minute Bash-tool timeout (#639, #624) — a pure documentation gap.
5. **`_verify_baseline.compute_baseline`'s transient-worktree checkout** can hit a Windows `WinError 3` (path not found / MAX_PATH) on repos with deeply-nested test fixtures, because `.scratch/verify-baseline-<uuid4().hex>/` adds ~50+ characters of path prefix on top of an already-long fixture path (#629). This is a real gap, but investigation during discussion turned up a wrinkle: a prior fix (commit `698b5a10`, landed 2026-07-09) already added `core.longpaths=true` to the `git worktree add` call, two days *before* #629 was filed — yet the failure still occurred. It is not established from static analysis alone whether the WinError 3 originates in git's checkout itself (longpaths insufficient at this nesting depth) or in the verify command's own test-fixture writes during execution inside the deep transient path. No Windows machine is available in this dev environment to confirm either way (see Decisions → `windows-long-path-mitigation`).

**Why now:** all seven were auto-filed by `/mill-self-report` (or manually) during real task work over 2026-07-09 through 2026-07-15 — this is accumulated operational debt in the pipeline's own reliability, not a feature request. Left unfixed, several of these actively cause wasted implementer/reviewer cycles (false `stuck_type: verify`/`incomplete` escalations) or silent loss of regression protection (`done_gate` capturing from the wrong commit).

## Scope

**In:**
- mill-go / `_implementer_common.py`: a new finalize-time gate diffs each batch's commits for Go build-tag additions and removals that change a file's default-build membership (excludes same-membership tag-value edits) and runs the corresponding compile check over the affected package(s) before accepting success (#642).
- mill-plan / `_plan_validate.py`: a new deterministic validator (`_check_verify_unrelated_test_files`) drops candidate verify test files from a batch's `verify:` command when they're both untouched by the batch's cards and byte-identical to the task's resolved parent branch (#638).
- mill-go / `_implementer_common.py`: the implementer's success envelope gains a self-reported `cards_done` field (integer card numbers, extracted batch-file card IDs as the comparison set — not a bare count); the finalize completeness gate compares against it instead of raw commit count; `--resume-incomplete` re-dispatch gets an idempotent-confirmation short-circuit as a backstop (#660).
- mill-go / new `_done_gate.py`: an opt-in Prepare-phase `done_gate` baseline pre-flight (`run_preflight`), config-gated, non-blocking, mirroring the existing "0.5 Baseline pre-flight" module-wide-verify pattern's timing and the Handoff-time "Pre-done gate" block's invocation shape (#650).
- mill-go SKILL.md: generalize the existing extended-timeout note (Agent-mode dispatch step 6) to cover any finalize-stage CLI call that replays a `verify:` command, not just `millpy-fix.py` (#639, #624). Documentation-only.
- `_verify_baseline.py`: shorten the transient-worktree directory name (`verify-baseline-<uuid4().hex>` → a shorter collision-resistant form) to reclaim Windows path budget (#629).

**Out:**
- Generalizing the #642 build-tag-retiering detection beyond Go (no pytest-marker / C#-trait equivalent) — explicitly deferred until a concrete non-Go instance is observed.
- Extending the module-wide verify-baseline (clean/pre-existing-failures) machinery down to per-batch verify commands (the heavier alternative fix considered for #638) — the lighter plan-time list-validation fix was chosen instead; this is documented as a rejected alternative, not built.
- Any `\\?\`-extended-length-path-prefix change to the `git worktree add` invocation for #629 — cannot be validated without a Windows machine; explicitly rejected as too risky to land unverified. The existing non-blocking degrade (baseline computation fails → `result: "error"` → task proceeds with strict per-batch gating) remains the terminal safety net and is not being changed.
- Heuristic auto-detection of "self-capturing" done_gate commands for #650 — the fix is an explicit opt-in config flag, not automatic detection.
- Any change to `pipeline.done_gate`'s existing Handoff-time invocation itself (step 0, "Pre-done gate" in mill-go SKILL.md) — it still runs at Handoff exactly as today; the new pre-flight is an *additional*, earlier, opt-in step.

## Decisions

### go-build-tag-retiering-check (#642)

- Decision: **not** authored by mill-plan at plan-write time — at plan-write time no diff exists yet, only card prose, so there is nothing mechanical to detect. Instead, this is a new automatic **finalize-time gate**, parallel to the existing verify/module-wide-verify/completeness/dirty gates in `_implementer_common.py`'s success-path pipeline (see Technical context). On a batch's explicit-success path, after the existing verify gate passes, finalize diffs `start_sha..HEAD` for `.go` files whose **default-build-membership transitions** — i.e., a `//go:build` line was added (file exits the untagged/default build) or removed (file enters the untagged/default build) — not merely any line in the build-constraint region changing. A pure tag-*value* edit (e.g. `//go:build integration` → `//go:build e2e`) does NOT trigger the gate: the file's default-build membership is unchanged either way (excluded before, excluded after), so the compile-break risk this gate targets does not apply. **Package resolution:** "the affected package(s)" is the immediate directory containing each transitioned file — Go's one-package-per-directory convention makes this a direct file→directory mapping, no import-graph resolution needed. Multiple transitioned files landing in the same directory within one batch are deduplicated to a single compile check per unique directory (not one check per file). For an **added** tag (file exits default build): finalize runs a plain untagged compile check (`go build ./<dir>/... ` or `go vet ./<dir>/...`, `<dir>` being the transitioned file's containing directory) — the original #642 direction, verifying nothing left in the default build still depends on what just left it. For a **removed** tag (file enters default build): `//go:build` constraints are boolean expressions (`a && b`, `a || b`, `!a`, GOOS/GOARCH terms like `linux`), not always a single custom tag — an unspecified translation to `-tags` risks compiling with the wrong tags and producing exactly the false-positive class this whole task exists to eliminate. The removed-tag direction therefore only fires the compile check when the removed constraint parses as a **single, non-negated, non-GOOS/GOARCH custom identifier** (e.g. `//go:build integration` — the literal shape of the original #642 repro); it runs `go build -tags <removed-tag> ./<pkg>/...` over the affected package(s) in that case, verifying nothing in the build variant the file just exited still depends on it being there. For any compound (`&&`/`||`), negated (`!`), or GOOS/GOARCH-only removed constraint, the gate does NOT attempt a translation — it logs a skip (naming the file and the unparsed constraint) and does not run a compile check for that removal. The added-tag direction is unaffected by this restriction: it only ever runs the plain untagged build, and never needs to interpret the added constraint's value, however complex. Either a fired check's failure demotes the result to `stuck_type: verify` with a reason naming the retiered package(s) and direction — identical in shape to the existing verify-gate failure path, so it flows through the same `_reclassify_verify_failure` partial-batch logic already in place.
- Rationale: the batch that introduces the re-tiering is the one whose diff is available to inspect — by construction, this gate can only run after the commits exist, so finalize-time is not a compromise, it's the only point in the pipeline where "which files gained a build tag" is actually knowable. Catching the compile break in the introducing batch's own finalize call (rather than incidentally, several batches later) avoids a discovered-scope fix commit downstream. This mirrors the resolution chosen for #638's implementation locus (see `batch-verify-list-validation` below): prefer a deterministic, unit-testable gate over mill-plan skill-authoring judgment wherever a mechanical check is possible. Framing the trigger as "default-build-membership transition" rather than "any build-tag line changed" is deliberately more precise than either the original added-only design or the naively broadened any-change design: it symmetrically covers both directions of the actual risk (a file entering or leaving the default build) while correctly excluding a same-membership tag-value swap, which carries none of #642's compile-break risk.
- Rejected: (a) mill-plan authoring the check at plan-write time — physically unsatisfiable; no diff exists before implementation. (b) a task-level module-wide verify entry that always runs both tagged and untagged builds on every batch — broader than needed; only batches that actually retier files need the extra check, and the finalize-time diff scopes it precisely. (c) doc-only reviewer guidance — relies on manual vigilance for a mechanically detectable pattern. (d) triggering on "added tag only" (the original round-1 design) — asymmetric; missed the removed-tag direction, which carries the mirror-image compile-break risk against whichever tagged build the file exited. (e) triggering on "any build-tag line changed" (the naive broadening) — over-broad; would also fire on a pure tag-value swap that doesn't change default-build membership at all, running an unnecessary compile check with no corresponding risk. (f) attempting a general boolean-expression-to-`-tags` translation for the removed-tag direction (handling `&&`/`||`/`!`/GOOS terms) — a `-tags` value is a flat OR-of-ANDs set, not a full boolean-expression evaluator; a naive translation of an arbitrary constraint risks compiling under the wrong tag combination, which would produce a false pass/fail indistinguishable from the exact problem #642 reports. Restricting to the single-custom-tag case is a deliberate scope boundary, not an oversight, and is logged rather than silently skipped so the restriction is visible.
- Scope note: Go-only for now. `//go:build` is a Go-specific mechanism; no other language's equivalent (pytest markers, C# `[Trait]` categories) has produced a concrete failure yet. Generalizing now would be designing for a hypothetical. The finalize-time diff check (newly-added build-tag lines → untagged compile check over affected packages) is documented as a pattern a future language-specific extension can follow, implemented as its own gate rather than generalized prematurely.

### batch-verify-list-validation (#638)

- Decision: at plan-write time, mill-plan's existing self-review loop (`mill-review-plan`) runs a **new deterministic validator function** — `_check_verify_unrelated_test_files` — added to `plugins/mill/scripts/_plan_validate.py` alongside its existing `_check_verify_*` family (`_check_verify_not_isolated`, `_check_verify_full_suite`, `_check_verify_malformed_cwd`, `_check_verify_mixed_cwd`; see `_plan_validate.py:1218` onward). For each candidate test file in a batch's `verify:` command: if it is NOT in the batch's own "Files Touched" list AND its content is byte-identical to **the task's resolved parent branch** (`git diff <parent_branch> -- <file>` is empty — resolved via `_parent_branch.resolve`, the same helper `compute_baseline` and the rest of this codebase's baseline/verify machinery already use, NOT a hardcoded literal `"main"`; this task's own parent branch is `hanf/linux-port-more`, not `main`, which is exactly the case this distinction has to get right), the validator flags it; mill-plan drops the flagged files from the batch's verify command before the plan is committed.
- Rationale: directly targets the root cause described in the issue's reproduction hint (an unrelated file that is byte-identical to the parent branch and not touched by the batch's own cards has no business gating that batch). Naming the concrete module resolves the code-vs-skill ambiguity: `_plan_validate.py` already runs deterministic, unit-testable checks against batch files as part of the same self-review loop this decision hooks into (see CLAUDE.md's `_plan_validate.py` verify-not-isolated convention), so this is an additive check in an established pattern, not a new mechanism. Lower implementation cost than extending the module-wide baseline machinery to per-batch granularity, and doesn't risk under-including legitimately-related tests the way a strict exact-match-only heuristic would. Resolving against the batch's actual parent branch (rather than a hardcoded `"main"`) also keeps this check correct for the common mill-go case of a task branching off another task branch rather than off `main` directly — exactly this task's own situation (parent `hanf/linux-port-more`).
- **Accepted coverage trade-off:** byte-identity to the parent branch proves a candidate file is *unchanged*, not that it's *unrelated* to the batch — a test file could be untouched by the batch's own cards yet still legitimately exercise the touched code (e.g. an integration test that imports a touched module without needing its own edit), in which case dropping it removes real regression coverage for that batch. This is an accepted, bounded risk rather than a defect to eliminate: a precise fix would require parsing each candidate file's imports/references against the batch's touched modules, which is language-specific (Go/Python/C# all differ) and disproportionate to what is meant to be a narrow, conservative drop heuristic. Mitigation instead of elimination: the validator logs every dropped file (batch name, file path, "dropped: unchanged vs. parent branch and not in Files Touched") to the plan-review's own review file, so a human or the holistic plan reviewer can catch a bad drop before the plan is approved, rather than the drop happening silently.
- Rejected: (a) exact-match-only verify lists (verify = Files Touched, no keyword/path matching at all) — simpler, but would under-include a test file that legitimately exercises a touched module without being named after it. (b) Extending the existing module-wide verify-baseline (clean/pre-existing-failures) machinery down to per-batch verify commands — more robust in principle (catches ANY pre-existing failure regardless of how it entered the list, not just ones the plan-time heuristic already knew to check), but a materially bigger mechanism change (baseline computation is currently task-scoped and module-wide only); deferred as a heavier follow-up if plan-time validation proves insufficient in practice. (c) leaving the implementation locus as "mill-review-plan, the natural place" skill-prose only — makes the check impossible to unit test, which the Testing section below requires. (d) import/reference-graph analysis to tighten the drop condition — disproportionate, language-specific complexity for a narrow safety heuristic; logging the drop for auditability is the chosen proportionate mitigation instead. (e) hardcoding the literal branch name `"main"` as the comparison reference — wrong whenever a task's parent isn't `main` (this task's own parent is `hanf/linux-port-more`); would either drop files that legitimately differ from the batch's real base or fail to drop genuinely pre-existing-failing ones. Use `_parent_branch.resolve`, matching `compute_baseline` and the rest of the codebase's convention.

### completeness-recount-cards-done (#660)

- Decision: two complementary changes. (a) The implementer's success JSON envelope gains a self-reported `cards_done` field: a list of integer card numbers the implementer addressed in this commit set. The **declared card-ID set** the gate compares against is extracted from the batch file itself, reusing the same heading regex `millpy-implement.py` already uses to compute `card_count` (`r"(?m)^###\s+Card\s+\d+\s*:"`, line 368) — extended to capture the numeric group (`^###\s+Card\s+(\d+)\s*:`) so the result is the literal `set[int]` of card numbers actually declared in the batch file, not an assumed contiguous `1..card_count` range. This distinction matters: the #660 repro's own batch had cards numbered "Card 7" and "Card 8" (task-global numbering, not batch-local 1-indexing), so a range assumption would have been wrong. This `card_ids: set[int]` is threaded into `_batch_completeness_stuck` alongside `card_count` (both derived from the same batch-file parse; `card_count` can become `len(card_ids)` rather than a separately-computed value). **The gate's new rule, with an explicit absent-vs-empty distinction:** if the `cards_done` key is entirely absent from the envelope (`parsed.get("cards_done")` is `None`, not an empty list — covers implementer sessions predating this field, or a non-compliant model that omits it), the gate falls back to today's existing behavior unchanged: `stuck iff content < len(card_ids)` (the raw commit-count comparison). If `cards_done` IS present (including as an explicit empty list, which is a genuine self-report of "zero cards done"), the gate uses the new rule: stuck iff `card_ids - set(cards_done)` is non-empty — after coercing every entry to `int` (a model may legally emit JSON strings, e.g. `["7","8"]`; `set[int]` `card_ids` would never match uncoerced string entries, silently defeating the whole fix). A `cards_done` entry that fails `int()` coercion makes the field untrusted for that call — treated identically to the absent-field case below (falls back to the old count heuristic) rather than raising or partially applying a malformed list. This fail-open design means old/non-compliant sessions regress to exactly today's heuristic (no worse than the pre-#660-fix baseline), while sessions that populate the field get the precise fix; it also closes the specific hazard where an entirely-absent `cards_done` would otherwise be treated as an empty set and make `card_ids - {}` always non-empty, permanently stuck with no path to resolution (the resume backstop below is itself gated on `cards_done`, so it could never fire either). (b) As a backstop, `--resume-incomplete`'s re-dispatch short-circuits directly to `status: success` when the fresh implementer session makes zero new content commits AND its envelope explicitly confirms (e.g. an `already_complete: true` field, itself populated by the same `cards_done` self-report matching all declared `card_ids`) that every card's requirements are already satisfied by the existing commit(s). When the resumed session's envelope also omits `cards_done` (same absent-field case), the backstop simply doesn't fire — falls through to whatever the primary gate's fallback branch above determines, unchanged from today's resume behavior.
- **`_reclassify_verify_failure` is updated in lockstep.** This sibling function (`_implementer_common.py:102`, called immediately before each `_batch_completeness_stuck` call site at lines 1021/1208/1304/1396) has its own independent `0 < content < card_count → incomplete` check, fired specifically when a batch's verify command genuinely fails mid-batch. It carries the exact same #660 bug class — a legitimately-combined-commit batch whose verify command fails for an unrelated reason would still be misclassified as `incomplete` by this check, since it compares against `card_count` too. In scope: replace its `0 < content < card_count` partiality check with the same `card_ids - set(cards_done)` non-empty test used by `_batch_completeness_stuck`. Its `content == 0` branch (reclassify to `stuck_type: logic`, "no content commit") is unchanged — that case is orthogonal to `cards_done` (zero commits means nothing was self-reported either way).
- **Verify-present short-circuit is preserved unchanged.** `_batch_completeness_stuck` today returns `None` (gate disabled) whenever `verify_cmd is not None and not ignore_verify` (line 215) — "a passing verify command is conclusive evidence of completeness." This decision does NOT touch that short-circuit: `cards_done` only supplements the heuristic on the paths where it already runs today (`verify_cmd is None`, or the no-JSON-inference fallback paths where `ignore_verify=True`). This is why #660's own repro batch hit the heuristic at all — it had no `verify:` command configured, so the short-circuit never applied. A batch with a passing verify command still short-circuits past the completeness check entirely, `cards_done` or not; nothing in the #660 repro or issue motivates changing that established behavior.
- Rationale: the raw commit-count heuristic was always a proxy for "did the implementer finish all the cards" — it has no way to represent the batch brief's own explicit permission to combine cards into one commit. Self-reporting `cards_done` replaces the proxy with the actual signal the gate wants, consistently across both call sites that currently share the buggy count comparison. The resume backstop closes the specific infinite-loop failure mode from the issue (identical verdict repeats forever because no new commit is possible) as defense-in-depth, in case `cards_done` self-reporting has its own edge cases (e.g. a batch resumed after a mill-go version upgrade where the original session predates the new field).
- Rejected: (a) loosening the heuristic to "at least one content commit exists" — simplest, but weakens the gate's ability to catch a genuinely partial batch (implementer does card 1 of 2, stops — one content commit would now pass even though card 2 is unaddressed). (b) resume-backstop only, without `cards_done` — fixes the infinite loop but leaves the *initial* misfire on every legitimately-combined-commit batch unfixed; every such batch would always burn one wasted resume round-trip before the backstop rescues it. (c) leaving `_reclassify_verify_failure`'s own count check unfixed — would just relocate the same bug class to the verify-failure trigger path instead of eliminating it. (d) also removing/loosening the verify-present short-circuit — no evidence in scope motivates it; a passing verify command remains conclusive. (e) treating an absent `cards_done` the same as an empty list (i.e., always requiring the field) — rejected because it turns a forgetful/pre-upgrade implementer session into a permanently-stuck batch with no backstop able to rescue it, a strictly worse outcome than today's count-only heuristic.
- Note for mill-plan / implementer-brief template: this decision requires a template change to `implementer-brief.md` (or wherever the success-envelope schema is documented) so implementers know to populate `cards_done`. mill-plan itself is not otherwise involved in this fix — it's implementer-brief + `_implementer_common.py`.

### done-gate-baseline-preflight (#650)

- Decision: add a new, explicitly opt-in Prepare-phase step to mill-go — a `done_gate` baseline pre-flight, gated by a new config key (e.g. `pipeline.done_gate_baseline_preflight: true`, default `false`/absent). **Implementation locus:** a new small module `plugins/mill/scripts/_done_gate.py` exposing `run_preflight(gate_cmd: str, git_root: Path) -> dict`, which runs `gate_cmd` once via `subprocess.run(gate_cmd, cwd=git_root, shell=True, capture_output=True, text=True)` — the exact same invocation shape already used inline in mill-go SKILL.md's existing Handoff-time "0. Pre-done gate" block (lines 780-798) — and returns one of `{"result": "skipped", "reason": "no done_gate configured"}`, `{"result": "skipped", "reason": "preflight not enabled"}`, `{"result": "ok"}`, or `{"result": "blocked", "reason": <captured stdout+stderr tail>}`. SKILL.md gets a new inline-Python block in the Prepare flow — positioned immediately after "0. Wiki health-check" and before "0.5 Baseline pre-flight," i.e. strictly before batch 1's implementer is ever dispatched — that imports and calls `_done_gate.run_preflight`, mirroring the Pre-done gate block's own `$MILL_PYTHON -c "..."` inline-Python style but delegating the actual subprocess work to the new testable function instead of hand-rolling it a second time. This runs **directly in the task's real worktree (not a transient one)**, from `git_root` — identical cwd to the Handoff-time invocation. Because this point in the flow is, by construction, before any batch has made a commit, the working tree is already at the pre-implementation state — no detached-HEAD checkout or throwaway worktree is needed (unlike `compute_baseline`'s transient-worktree pattern for `module_wide_verify_cmd`, which exists specifically to test the *parent* branch's state without touching the task's own tree; done_gate's self-capturing baseline needs the opposite — it must write into the real tree so the identical Handoff-time invocation finds it there later). mill does not parse, move, or persist whatever snapshot/baseline artifacts the project's own test framework writes as a side effect — they're left exactly where that framework put them; the framework's own "does a baseline already exist" internal logic is what makes the Handoff-time run compare instead of re-capture.
- **Exit-code / failure contract:** non-blocking and fail-safe, mirroring `_run_baseline_stage`'s existing contract exactly (see Technical context) — `run_preflight` never raises to its caller. A non-zero `gate_cmd` exit is reported as `{"result": "blocked", ...}` in the returned dict, but the orchestrator only **logs** this (ASCII-only, ≤2000 chars of captured output, same truncation the existing Pre-done gate block already applies) and proceeds to batch 1 regardless — it does NOT halt the task. This differs deliberately from the Handoff-time gate's own behavior (which DOES halt on `status: blocked`, SKILL.md:796): at Prepare, a failing done_gate on the *parent* branch's own pre-implementation state is diagnostic information about the parent branch, not something this task's batches can fix, and blocking Prepare on a pre-existing parent-branch failure would make the task undispatchable through no fault of its own implementation. The Handoff-time gate remains the actual enforcement point; the Prepare-time pre-flight's only job is to get a self-capturing suite's baseline captured from the right commit, and it fulfills that job even when the gate command itself reports `blocked` (a captured "blocked" baseline is still a valid, correctly-timed baseline for the Handoff-time comparison).
- Rationale: mirrors an established, already-working pattern in the same file (mill-go SKILL.md's "0.5 Baseline pre-flight") for *when* to run, and mirrors the Handoff-time "0. Pre-done gate" block for *how* to invoke the command, while diverging deliberately on *where* to run relative to `compute_baseline` (real tree, not transient) and *whether to block* relative to the Handoff-time gate (never blocks, since it's diagnostic-only at this point in the flow). Extracting `run_preflight` into a real function (rather than a second inline SKILL.md snippet) is what makes this decision's own Testing entry (a mocked-subprocess unit test) satisfiable, and is consistent with this discussion's broader theme of preferring deterministic, unit-testable code over duplicated orchestrator prose (see `go-build-tag-retiering-check` and `batch-verify-list-validation`).
- Persistence confirmed safe without new mill-side plumbing, provided the captured artifacts land in a gitignored path (true for the motivating repro: NORCE.Models' regression suite already wrote to `.scratch/regression-baseline/`, gitignored per this repo's own CLAUDE.md "Numerical Regression Testing" convention). Verified against `_cleanliness.py`: `compute_new_dirt`/`revert_out_of_scope_drift` (the per-batch cleanliness gate) call `_pygit2_util.status_porcelain(..., include_untracked=False)` — tracked-file diffs only — and `compute_scope_violations` (the Handoff terminal scope-violations gate) reads `git status --porcelain` output, which never includes gitignored paths by default. A gitignored baseline directory is therefore invisible to both gates through every intervening batch; no new persistence location or restore step is required. Caveat carried forward for implementation: if a project's self-capturing done_gate writes baseline artifacts to a *tracked* (non-gitignored) location, those files would surface as new tracked-file dirt in a later batch's cleanliness gate and could false-positive block it — this decision assumes/requires the artifacts are gitignored, and the implementer should verify that precondition for the specific `done_gate` command being configured, not assume it universally.
- Rejected: (a) doc-only guidance — doesn't actually prevent the original failure (silent capture from the wrong commit); the issue's own recovery required manual detached-HEAD surgery, which is exactly the kind of error-prone manual step automation should remove. (b) heuristic auto-detection of "self-capturing" done_gate commands (e.g. "did new files appear after a first run") — no reliable signal exists; a heuristic here is more likely to misfire (false positive on an unrelated gate that happens to write a log file) than to help. (c) running the preflight in a transient worktree mirroring `compute_baseline` exactly — would require the same self-capturing baseline files to somehow be copied back into the real tree afterward, an extra mechanism the real-worktree approach makes unnecessary. (d) inline SKILL.md-only prose with no backing function (mirroring the Handoff-time gate's own current implementation exactly) — rejected specifically because it would make the Testing section's unit test unsatisfiable; a small extracted function costs little and closes that gap. (e) blocking Prepare on a `blocked` pre-flight result, matching Handoff's behavior — rejected because a failing pre-implementation parent-branch state isn't this task's batches' fault to fix, and would make otherwise-startable tasks undispatchable.
- **Timeout guidance:** the new Prepare-phase inline-Python block that calls `_done_gate.run_preflight` runs a full done_gate command via a Bash-tool `$MILL_PYTHON -c` invocation — for a self-capturing regression suite (the motivating #650 repro used a dotnet regression-test project), this is exactly the same slow-command-under-the-default-2-minute-Bash-timeout risk class that `finalize-timeout-guidance-generalization` (#639/#624) already fixes for finalize-stage calls elsewhere in this task. Folding in the two done_gate call sites keeps this task internally consistent — `done-gate-baseline-preflight` explicitly relies on this decision for its own timeout guidance rather than duplicating a separate note. Leaving the two `done_gate` call sites as a separate, unfixed gap — rejected because it was cheap to close in the same text edit and left an obvious loose end for `done-gate-baseline-preflight`'s own Testing section to trip over.

### windows-long-path-mitigation (#629)

- Decision: shorten the transient-worktree directory name in `_verify_baseline.compute_baseline` from `verify-baseline-<uuid4().hex>` (32 hex chars) to a shorter collision-resistant form (e.g. 12 hex chars — still ~2^48 combinations, effectively collision-free for a short-lived per-invocation scratch directory) to reclaim path budget. Do not modify the `git worktree add` invocation to use a `\\?\`-extended-length-prefixed target path.
- Rationale: reclaiming ~20 characters of path budget is a pure string-length change, verifiable via existing unit tests on any platform (assert the directory-name pattern/length), and carries no platform-specific behavioral risk. It may or may not be sufficient to resolve #629's specific fixture path on its own — that's unknown without a Windows repro — but it strictly reduces the chance of hitting the limit and has zero downside. A `\\?\`-prefix change to the `git worktree add` target is a genuine git-invocation behavior change that cannot be validated in this dev environment (no Windows machine); landing it unverified risks a worse regression (broken worktree creation for every Windows user) than the narrow issue it targets.
- Rejected: (a) the `\\?\`-prefix approach — real regression risk, unverifiable here. (b) doc-only ("avoid self-capturing test frameworks with deeply-nested fixtures on Windows") — doesn't reduce the actual chance of hitting the limit for repos that already have such fixtures and can't restructure them. (c) splitting #629 out of this task's scope entirely — the shortened-directory-name mitigation is low-risk and low-cost enough to include; full scope-out is unnecessarily conservative given a safe partial fix exists.
- Open uncertainty carried into implementation: it remains unconfirmed whether the WinError 3 in #629 originates in `git worktree add`'s own checkout (where `core.longpaths=true`, already present since commit `698b5a10`, evidently wasn't sufficient) or in the verify command's own test-fixture writes during execution inside the transient worktree (i.e., the self-capturing-snapshot pattern from #650, but tripping a path-length limit rather than a wrong-baseline problem). The implementer should note this ambiguity in the batch's PR/commit message rather than asserting the mitigation "fixes" #629 — it reduces the odds, it does not guarantee resolution. The existing non-blocking degrade (baseline computation fails → `result: "error"` printed → task proceeds with strict per-batch gating, per `_run_baseline_stage`'s docstring contract) is unchanged and remains the terminal safety net regardless.

## Q&A log

- **Q:** How should mill-go catch Tier-1 compile breaks when a batch adds Go build tags to previously-untagged files (#642)? **A:** [auto-pick] Add an untagged build/vet check over the affected package(s), run automatically at the introducing batch's own finalize stage (not authored by mill-plan at plan-write time, since no diff exists then — see Decisions → `go-build-tag-retiering-check`, resolved during discussion review round 1 after this design gap was flagged). **Why:** the introducing batch's finalize call is the first point where the compile-break-causing diff actually exists; catching it there avoids a downstream discovered-scope fix commit.
- **Q:** Should the #642 fix generalize beyond Go build tags to other languages' re-tiering mechanisms? **A:** [auto-pick] Go-only for now; document the pattern for future extension. **Why:** no concrete non-Go instance has been observed — generalizing now would be designing for a hypothetical (YAGNI).
- **Q:** How should mill-plan avoid folding unrelated pre-existing-failing tests into a batch's verify list (#638)? **A:** [auto-pick] Validate candidate verify test files against the task's resolved parent branch at plan-write time (via `_parent_branch.resolve`, not a hardcoded `main` — corrected during discussion review round 4 after this exact discrepancy was flagged against this task's own non-`main` parent); drop files that are both untouched by the batch's cards and byte-identical to that parent ref. **Why:** directly targets the issue's own reproduction hint at lower implementation cost than extending the module-wide baseline machinery to batch-level granularity, and stays correct for tasks (like this one) whose parent isn't `main`.
- **Q:** How should finalize's completeness gate account for brief-sanctioned combined commits without looping forever on resume (#660)? **A:** [auto-pick] Self-reported `cards_done` in the implementer's success envelope as the primary completeness signal, plus an idempotent-confirmation short-circuit on `--resume-incomplete` as a backstop. **Why:** replaces a heuristic proxy (commit count) with the actual signal the gate wants, while still closing the specific infinite-loop failure mode as defense-in-depth.
- **Q:** How should `done_gate` get a pre-implementation baseline for self-capturing snapshot suites (#650)? **A:** [auto-pick] New opt-in Prepare-phase pre-flight step, config-gated, mirroring the existing module-wide-verify baseline pre-flight. **Why:** reuses an established working pattern; explicit opt-in avoids forcing an extra done_gate run on tasks whose done_gate isn't self-capturing.
- **Q:** Should the extended-timeout SKILL.md guidance (#639, #624) be generalized or just extended to name `millpy-implement.py` specifically? **A:** [auto-pick] Generalize the rule to any finalize-stage CLI that replays a verify command, while still naming the current concrete instances. **Why:** same edit cost as the narrow fix, but prevents the identical doc gap recurring for a future finalize-stage CLI.
- **Q:** How should the Windows long-path WinError 3 in baseline computation be mitigated (#629), given it can't be reproduced or validated from this Linux dev environment? **A:** [auto-pick] Shorten the transient-worktree directory name only; explicitly reject an unverifiable `\\?\`-extended-length-prefix change to the git invocation. **Why:** a pure string-length change is verifiable cross-platform and has zero regression risk, unlike a git-invocation behavior change that can't be tested here; the existing non-blocking degrade remains the safety net either way.
