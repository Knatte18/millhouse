## Problem

`plugins/mill/scripts/_plan_validate.py` is the static plan pre-validator run before every plan-review round.
Four independent, previously-filed bugs in it currently degrade mill-plan's own orchestrator experience:

1. **#1040** — the git-ignore probe used by `context-completeness` prints two `[subprocess]` trace lines to stderr for every candidate path that is confirmed *not* git-ignored (the common case), flooding the orchestrator's output with dozens of noise lines per validation run and burying the actual JSON result.
2. **#1000** — `batch-oversized`'s context-size sub-check sums the whole-file byte size of every `Context:`/`Edits:`/`Creates:`/Move-source token across an *entire batch* and checks the sum once. A genuinely TDD-shaped batch (one card editing a large source module together with its equally-large test file) can legitimately exceed the cap even though no single card is oversized, forcing source and tests into separate batches and defeating TDD.
3. **#999** — `verify-unrelated-test-file` exempts a `--only` test-file token only when that token's own basename is directly touched (Edited/Created/Moved) by the same batch. It does not recognize a token that is the *natural, convention-named test file* for a source module the batch touches — so a source-only batch verifying with its own subject-under-test's test file gets a false positive.
4. **#992** — the card/field parser's fence-tracking (`_parse_cards`, `_requirements_fence_aware_body`, and the `context-completeness` Requirements: scanner) only recognizes a fenced-code-block delimiter when the ` ``` ` line starts at column 0. A real `Requirements:` fence is written as an indented list sub-bullet (e.g. `` `  ```markdown` ``), while the sibling `requirements-quote-indent-drift` check can force the fence's *content* (not its delimiters) to column 0 so it byte-matches the quoted source file. That mismatch defeats the fence toggle, so a column-0 heading line inside the fence is wrongly read as a real section/card boundary, truncating the card and producing spurious `card-missing-field` findings for fields that come after the fence (e.g. `Commit:`).

All four were filed as separate GitHub issues (#1040, #1000, #999, #992) and are grouped into this one task because each is small in isolation.

## Scope

**In:**
- `_subprocess_util.run()`: add an opt-in flag to suppress the spawn/exit breadcrumb on an *expected* non-zero exit, and use it from the git-check-ignore call site in `_plan_validate.py`.
- `_check_batch_oversized`'s context-token-estimate sub-check: move from batch-aggregate to per-card evaluation.
- `_check_verify_unrelated_test_files`: add a naming-convention basename exemption alongside the existing direct-touch exemption.
- `_parse_cards`, `_requirements_fence_aware_body`, and the context-completeness Requirements: fence scan: tolerate a leading-whitespace-indented fence delimiter.
- Unit test coverage for all four fixes in `plugins/mill/unit_tests/test-plan-validate.py` and `test-subprocess-util.py`.

**Out:**
- `batch-oversized`'s card-*count* sub-check (check 1) — untouched, stays batch-level; it isn't a token-budget concern.
- Batching `git check-ignore` into a single `--stdin` call — rejected in favor of the smaller breadcrumb-suppression fix (see Decision below).
- Any change to `requirements-quote-indent-drift` itself — it is the check that *forces* column-0 fence content; that behavior is correct and out of scope here. This task only fixes the parser's fence-boundary detection so it tolerates the indentation mismatch that check's own correctness requires.
- Go-side line-range/partial-file discounting for `batch-oversized` — not needed once the check evaluates per card (see Decision below); the concrete blocking scenario in #1000 is fully resolved by per-card evaluation without a partial-file discount.
- Any mill-plan/mill-go SKILL.md prose changes — this task is a validator bugfix, not a docs update.

## Decisions

### subprocess-trace-suppression (#1040)

- Decision: add a keyword-only `quiet_nonzero: bool = False` parameter to `_subprocess_util.run()`. When `True`, the existing "`if proc.returncode != 0: print(...)`" breadcrumb block (both the spawn and exit lines) is skipped for a plain non-zero exit. Timeout and `Popen`-raise breadcrumbs are untouched (those remain genuine failures, never expected). Update the single git-check-ignore call site in `_is_confirmed_git_ignored` (`_plan_validate.py`, calling `_subprocess_util.run(["git", "-C", ..., "check-ignore", "-q", ...])`) to pass `quiet_nonzero=True`.
- Rationale: root-caused by reading `_subprocess_util.py` directly (not just the issue text) — the breadcrumb fires on *any* non-zero `proc.returncode`, not on an error path specifically. `git check-ignore` returns 1 for "not ignored", which is the overwhelmingly common, entirely expected outcome for the paths `context-completeness` probes — that's the actual source of the ~90-line flood on a 51-file plan, not excessive subprocess spawning (calls are already memoized per resolved candidate path via `ignore_memo`, confirmed at the call site). A `quiet_nonzero` flag is a minimal, backward-compatible addition (154 existing call sites keep default `False` behavior unchanged) that fixes exactly this call site's known-expected-nonzero semantics without touching `_subprocess_util`'s general contract.
- Rejected: batching into a single `git check-ignore --stdin` call (the issue's alternative suggestion) — bigger surface change (would require restructuring `_is_confirmed_git_ignored` from a per-candidate memoized lookup into a batch-collect-then-resolve pass across the whole `context-completeness` check), and does not by itself remove the breadcrumb noise from other still-per-path git subprocess use elsewhere in the file if any existed. The `quiet_nonzero` flag directly targets the actual root cause (expected-nonzero-exit noise) and generalizes to any future caller with the same shape.

### batch-oversized-per-card (#1000)

- Decision: change `_check_batch_oversized`'s context-size sub-check (check 2) to compute and compare the token-estimate cap **per card** instead of once for the whole batch's unioned token set. Card-count sub-check (check 1) is unchanged (stays batch-level). Add card-scoped token-extraction helpers mirroring the existing `_card_edits_tokens`/`_card_creates_tokens` pattern: `_card_context_tokens(card_text) -> list[str]`, `_card_deletes_tokens(card_text) -> list[str]`, and a card-scoped Moves: pair walk (reusing the module-level `_RE_MOVES_HEADER`/`_RE_MOVE_PAIR` patterns already used by `parse_moves`). For each card: build its own token set (`Context: ∪ Edits: ∪ Creates:`, minus `Deletes:` and Move-targets, plus Move-sources — the same set algebra the current whole-batch computation uses), resolve existing paths, sum bytes, divide by 4, and compare against `max_context_tokens`. On violation, emit one `batch-oversized` error with `"card": <card_num>` set (the error dict schema already has a `card` field; previously always `None` for this sub-check).
- Rationale: the aggregate whole-batch sum measures something no single implementer turn ever needs simultaneously — an implementer works one card at a time, so the relevant budget is what one card's own references cost, not the sum across every card in the batch. Per-card evaluation directly resolves the reported blocking case (a TDD batch with a test-writing card and an implementation card, each individually well under the cap, but summed over it) while leaving single-card batches — which are what all the existing `test_batch_oversized_context_tokens_*` unit tests use — byte-for-byte unaffected, since for a one-card batch, per-card and per-batch evaluation are the same computation. Confirmed by reading `_make_batch_file` in the unit test file: it always emits exactly one card.
- Rejected: doc-only fix ("acknowledge TDD is unavailable above this threshold") — the issue names this as the *minimum* bar, not the preferred fix, and this task is scoped as a bugfix, not a docs task. Discounting a file the batch only reads a named line-range of — doesn't address the concrete reported scenario, where both the full source module and full test file are genuinely edited in their entirety (no `:N-M` line-range citation applies to either), so a partial-file discount would not by itself unblock the TDD case that motivated the issue.

### verify-unrelated-test-file-naming-convention (#999)

- Decision: in `_check_verify_unrelated_test_files`, alongside the existing exemption (`Path(token).name in touched_basenames`), add a second exemption: a candidate `--only` token is also exempt when its basename matches the *derived* test-file name of any of the batch's own touched (Edits:/Creates:/Moves-target) source files, under this repo's established naming conventions:
  - Python: `<stem>.py` → `test-` + `stem.lstrip("_").replace("_", "-")` + `.py` (verified against this repo's own layout: `_plan_validate.py` → `test-plan-validate.py`, `_review_common.py` → `test-review-common.py`).
  - Go: `<stem>.go` → `<stem>_test.go` (standard Go convention, mirrors this file's own existing Go-specific handling in `_check_verify_excludes_edited_tagged_test`).
  A touched file that is *itself* already a test file is skipped when deriving (no derived name computed from a test file), since the derivation is source→test only.
- Rationale: this is exactly the issue's own suggested fix. The existing basename check only catches the case where the batch edits the test file directly; the reported false positive is precisely the opposite (batch edits only the source, verifies with that source's own natural test file, split into separate batches purely because of the #1000 cap). Deriving the expected test name from the touched source files and exempting a match is a narrow, convention-scoped addition that doesn't weaken the check's actual purpose (catching a genuinely *unrelated* pre-existing test file slipped into `--only`).
- Rejected: matching by directory/prefix heuristics broader than the two named conventions — higher false-negative risk (would exempt genuinely unrelated files sharing a directory), and neither source issue nor this codebase's own test-naming convention needs it.

### fence-delimiter-indentation-tolerance (#992)

- Decision: change the fence-delimiter detection in all three affected call sites from `line.startswith("```")` to a leading-whitespace-tolerant match (`line.lstrip().startswith("```")`, or an equivalent `^\s*```` regex) so an indented fence delimiter still toggles `in_fence` correctly:
  1. `_parse_cards` (line ~174) — card-boundary detection.
  2. `_requirements_fence_aware_body` (line ~2619) — Requirements: field body extraction (feeds `context-completeness` and `requirements-quote-indent-drift`).
  3. The context-completeness Requirements: token scan's own local fence toggle (line ~2324).
- Rationale: root-caused directly against current code, not from the issue text alone — issue #992 was filed nearly a month after #776's fence-awareness fix (commit `101a4897`, 2026-08-08) already landed, so the already-merged fix does NOT explain the reported repro; something else was still broken. Reproduced live against the current worktree source: a card whose `Requirements:` fence is written with an *indented* opening delimiter (`"  ```markdown\n"`, the natural shape for a fenced block nested under a `- **Requirements:**` list sub-bullet) but *column-0* fence content (forced there by `requirements-quote-indent-drift`'s byte-exact-substring matching against the quoted source file's own indentation) defeats the existing `in_fence` toggle — the indented delimiter line never matches `line.startswith("```")`, so `in_fence` never goes `True`, and the column-0 `### heading` line inside the fence is then read as a real card-boundary, truncating the card before its `Commit:` field. This reproduces the issue's exact symptom ("a later field on the same card... will be misreported as missing, even when it is present"). The existing `#776` regression test (`test_check_card_missing_field_fence_guard_real_boundary_still_detected`) happens to use a delimiter *and* an embedded heading that are *both* indented, so it never exercised this column-0-content/indented-delimiter mismatch — which is why it passed and shipped without catching this case.
  All three call sites share the identical `line.startswith("```")` pattern (confirmed via grep), so fixing only `_parse_cards` (the literal function issue #992 names) would leave `_requirements_fence_aware_body` and the context-completeness scan equally exploitable by the same indentation mismatch, silently reintroducing an equivalent false-positive/false-negative surface in `requirements-quote-indent-drift` and `context-completeness` instead of `card-missing-field`. Fixing all three consistently is the only way this root cause is actually closed.
- Rejected: fixing `_parse_cards` alone (narrowly matching only the issue's literal repro) — leaves the two sibling call sites with the identical latent bug, which the CLAUDE.md source-verification rule (verify against actual current code, not just the issue text) surfaced during exploration.

## Technical context

All four fixes are in `plugins/mill/scripts/_plan_validate.py` (3832 lines) plus one shared-utility change:

- `_subprocess_util.py` (`plugins/mill/scripts/_subprocess_util.py`): `run()` at line 76. The breadcrumb block is at lines 204-209 (`if proc.returncode != 0: print(spawn); print(exit)`). No other behavior in this function needs to change.
- `_is_confirmed_git_ignored` (line 2056) — the sole call site of the check-ignore subprocess, at line 2107 (inside a `try/except` at lines 2105-2113). Memoized via `ignore_memo` (created once per `_check_context_completeness` call), keyed by resolved candidate path.
- `_check_batch_oversized` (line 3613) — check 1 (card count, lines 3629-3637) stays as-is. Check 2 (context tokens, lines 3639-3678) is the part to restructure to per-card. Existing whole-batch helpers it currently calls: `parse_batch_refs` (from `_review_common.py`, line 697), `_parse_deletes_only` (line 261, this file), `parse_moves` (from `_review_common.py`, line 753) — these all take a `batch_path: Path` and re-read/re-scan the whole file; they are NOT reused for the per-card version. Instead, mirror the already-existing card-scoped pattern: `_card_edits_tokens` (line 2548) and `_card_creates_tokens` (line 2119) both take `card_text: str` and walk `_RE_REFS_HEADER`/`_RE_REFS_SUB` restricted to one field. New `_card_context_tokens`/`_card_deletes_tokens` follow the identical shape restricted to `Context`/`Deletes`. A card-scoped Moves: walk needs the same treatment using `_RE_MOVES_HEADER` (line 101) and `_RE_MOVE_PAIR` (line 106) directly against `card_lines`/`card_text` (no existing card-scoped Moves helper to reuse — write a small one, e.g. `_card_moves_tokens(card_text) -> list[tuple[str, str]]`, following `parse_moves`'s inline/sub-bullet walk but scoped to a card).
  `_check_batch_oversized` already calls `_parse_cards(text)` once per batch (line 3626) to get `card_count`; reuse that same `cards` list (`list[tuple[int, list[str]]]`) for the per-card loop instead of re-parsing.
- `_check_verify_unrelated_test_files` (line 3448) — the existing exemption is at lines 3528-3532 (`touched_basenames` set built from `_parse_edits_only` (line 183) ∪ `_parse_creates_only` (line 222) ∪ Move-target basenames, then `if Path(token).name in touched_basenames: continue`). Add the naming-convention derivation immediately alongside this, building a second set of *derived* test-basenames from the same `touched` set before the per-token loop, and checking membership in that set too.
- `_parse_cards` (line 146), `_requirements_fence_aware_body` (line 2583), and the context-completeness fence toggle inside `_check_context_completeness`'s Requirements: scan loop (starts ~line 2297, the specific toggle is at line 2324) — all three currently do `if line.startswith("```"): in_fence = not in_fence`. Change to a leading-whitespace-tolerant form consistently in all three.
- `_RE_FENCE_BODY` (line 119, used by `requirements-quote-indent-drift`) is unaffected — it's a `re.DOTALL` substring search with no `^`-anchor, so it already finds a mid-line/indented ` ``` ` fence marker inside the (now-correctly-extracted) `requirements_text`; only the three `startswith`-based line-scanners need the fix.

## Q&A log

- **Q:** How should the git-check-ignore subprocess-trace noise (#1040) be silenced — (1) add an opt-in `quiet_nonzero` flag to `_subprocess_util.run()` used at the one check-ignore call site, or (2) restructure the check-ignore probe into a single batched `git check-ignore --stdin` call? **A:** [auto-pick] Option 1 (add `quiet_nonzero` flag). **Why:** smaller, backward-compatible surface change that directly targets the actual root cause (breadcrumb fires on any non-zero exit, and exit 1 is `check-ignore`'s routine "not ignored" result) confirmed by reading `_subprocess_util.py`'s current code; batching would require a larger restructure of `_is_confirmed_git_ignored`'s per-candidate memoized-lookup shape for no added benefit toward the actual complaint.
- **Q:** Should `batch-oversized`'s context-token cap (#1000) be evaluated (1) per card instead of per batch, (2) via a doc-only acknowledgment that TDD is unavailable above the threshold, or (3) by discounting line-range-cited partial reads? **A:** [auto-pick] Option 1 (per-card evaluation). **Why:** the issue's own concrete blocking scenario involves full-file edits of both source and test with no line-range citations (ruling out option 3), this task is scoped as a code bugfix not a docs task (ruling out option 2 as the sole fix), and per-card evaluation both resolves the reported case and leaves every existing single-card-batch unit test's behavior unchanged.
- **Q:** Should `verify-unrelated-test-file`'s (#999) fix scope cover (1) a naming-convention basename derivation exactly as the issue proposes, or (2) a broader directory/prefix-based heuristic? **A:** [auto-pick] Option 1 (naming-convention derivation). **Why:** matches the issue's own suggested fix, keeps the check's false-negative surface tight (a broader heuristic risks exempting genuinely unrelated files), and this repo's own test-naming convention (`test-<stem>.py` for `_<stem>.py`) is concretely verifiable against the actual `unit_tests/` directory listing.
- **Q:** For the fence-indentation bug (#992), should the fix be scoped to (1) `_parse_cards` alone (the function the issue names), or (2) all three call sites sharing the identical `line.startswith("```")` pattern? **A:** [auto-pick] Option 2 (all three call sites). **Why:** per this repo's CLAUDE.md instruction to verify against actual current code rather than the issue text alone, direct reproduction against the current worktree source showed the already-merged #776 fix does not cover this scenario (indented delimiter, column-0 content), and grepping confirmed `_requirements_fence_aware_body` and the context-completeness fence scan share the exact same brittle pattern — fixing only `_parse_cards` would leave two sibling checks (`requirements-quote-indent-drift`, `context-completeness`) equally exploitable by the same root cause.
