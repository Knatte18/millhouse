# Discussion: mill-go's one-shot pre-batch-1 baseline can't cover a task's own later per-batch-baseline capability

```yaml
task: mill-go's one-shot pre-batch-1 baseline can't cover a task's own later per-batch-baseline capability
slug: mill-go-per-batch-baseline-preflight-gap
status: discussing
parent: main
```

## Problem

mill-go's "0.5. Baseline pre-flight" step (`plugins/mill/skills/mill-go/SKILL.md`) invokes `${CLAUDE_PLUGIN_ROOT}/scripts/millpy-implement.py --stage baseline` exactly once, before batch 1, against whatever baseline-computation code exists **in the installed plugin cache** at that moment. `${CLAUDE_PLUGIN_ROOT}` is the plugin cache entry, never the task's own dev tree (see root `CLAUDE.md` "Hard constraints"), and nothing re-syncs it mid-run.

For a self-hosting millhouse task (mill developing mill) whose own plan introduces or modifies the baseline-computation machinery itself (`plugins/mill/scripts/_verify_baseline.py`, and the `_run_baseline_stage`/`_enumerate_batch_verify_triples` orchestration in `plugins/mill/scripts/millpy-implement.py`) in an early-to-middle batch, the one-shot pre-flight structurally cannot benefit from that batch's own new code — it already ran, using the frozen cache copy, before batch 1. This was observed live on `mill-validate-verify-diagnostics-gaps` batch 6: that batch's own verify command (`test-millpy-implement.py`) hit 8 pre-existing failures + 1 error unrelated to any of the batch's own cards (a `_is_valid_commit_sha` test/prod skew from an earlier #744 postmortem fix). No per-batch baseline existed to classify these as pre-existing and waivable, because the cache copy of `millpy-implement.py` invoked by the pre-flight predated the per-batch substage entirely. The batch blocked with `verify/logic: unresolved after retry` and required a manual out-of-plan fix, even though the underlying feature being built could — in principle — have classified the failure as waivable if a baseline had existed.

**Why now:** the per-batch baseline/waiver mechanism (`_run_baseline_stage`'s `per_batch` substage, `verify_baseline_failures` in status.md) has since landed and is exercised on every mill-go run. The chicken-and-egg gap is structural to how the pre-flight is wired, not to the maturity of the feature itself, so it will recur on any future self-hosting task whose plan touches this same machinery again.

## Scope

**In:**
- A new per-batch retry hook in mill-go's batch loop, inserted at the last point before that batch's own baseline gets read and used for verify gating — this point differs by dispatch mode (see Decision: hook placement below): before step 6's `--stage finalize` call in Agent-mode; before the backgrounded `millpy-implement.py <batch_name>` (bare, defaulting to `--stage full`) dispatch in subprocess/psmux, since that mode has no separate finalize call point. At that point, check whether that batch's `verify_baseline_failures` is still unset in status.md **and** that batch has a non-`None` resolved verify command (see Decision: retry trigger condition below).
- When both hold, and only when this is a self-hosting task (the task worktree itself contains `plugins/mill/scripts/millpy-implement.py` at the expected relative path), attempt one recapture by invoking `--stage baseline` against the **task worktree's own copy** of `millpy-implement.py` (via `PYTHONPATH="<git_root>/plugins/mill/scripts"`), not the cache. `_run_baseline_stage` already enumerates and computes baselines for *every* not-yet-cached batch from the plan in one shared checkout, so a single successful retry backfills the triggering batch plus any later not-yet-finalized batches for free.
- A new `_paths.is_self_hosting_task(git_root: Path) -> bool` helper (existence check on `git_root / "plugins" / "mill" / "scripts" / "millpy-implement.py"`), unit-tested.
- Non-blocking failure handling: any failure of the retry call itself (non-zero exit, timeout, malformed JSON, `--stage baseline` not yet supported by the in-development worktree code) is logged and falls through to that batch's normal strict-mode finalize — exactly as if no retry had been attempted.
- The retry fires **at most once per task run** (lazily, the first time a batch's own finalize would otherwise hit a missing baseline).

**Out:**
- No new config key. The mechanism is self-gating: a no-op for every non-self-hosting target repo (existence check fails), and for self-hosting tasks it only fires when a baseline is actually missing at finalize time.
- No file-diff-based detection of "did this batch touch baseline-computation code" — the trigger condition is purely "is this batch's own baseline still unset," regardless of cause.
- No change to the existing batch-1 "0.5. Baseline pre-flight" step itself — it keeps using cache form unconditionally, as today. This task only adds the later, per-batch retry hook.
- No retry beyond the first successful-or-failed attempt within a task run (a second batch further refining baseline-computation code later in the same plan will not get an additional automatic backfill attempt).
- No fix for the subprocess/psmux dispatch-mode timing asymmetry (see Decision: hook placement's "Accepted limitation") — under subprocess/psmux, a batch's own retry attempt cannot see that same batch's own in-flight commits, only prior batches'. Closing this would require moving the retry logic into `millpy-implement.py` itself and persisting the "attempted" flag to status.md — deferred to a future task.
- No change to the "0.55. Done-gate baseline pre-flight" step (unrelated `done_gate` mechanism).

## Decisions

### cache-vs-worktree execution path for the retry

- Decision: the retry invokes the task worktree's own copy of `millpy-implement.py` (`PYTHONPATH="<git_root>/plugins/mill/scripts" "$MILL_PYTHON" "<git_root>/plugins/mill/scripts/millpy-implement.py" --stage baseline`), not `${CLAUDE_PLUGIN_ROOT}`.
- Rationale: `${CLAUDE_PLUGIN_ROOT}` is frozen for the whole mill-go run and never reflects a self-hosting task's own in-progress commits (root `CLAUDE.md` "Hard constraints"). Re-invoking the cache copy later in the run is provably a no-op — same code, same result as the original pre-flight call. This is a deliberate, narrow exception to the "cache form for all operational calls" convention, in the same spirit as the existing "task-worktree path for source verification" exception already carved out in `CLAUDE.md` — the whole point of this call is to observe the task's *own* commits, which the cache structurally cannot do.
- Rejected: keeping the retry on cache form (defeats the purpose — see above).

### self-hosting gate

- Decision: gate the retry entirely on `_paths.is_self_hosting_task(git_root)`, a new helper checking `(git_root / "plugins" / "mill" / "scripts" / "millpy-implement.py").exists()`. No config key.
- Rationale: for any non-millhouse target repo, `plugins/mill/scripts/` is never part of that repo's own tree (mill is a plugin layered on top), so the worktree-path invocation would simply fail to find the script — the existence check turns that into a clean, silent skip instead of a failed subprocess call every batch. Recent history in this repo (see `0467ba27 pipeline.autonomous_mode warns as unknown config key on every mill invocation`) shows added config keys carry real maintenance/warning-hygiene cost; this feature is inherently self-scoping and doesn't need one.
- Rejected: a `pipeline.per_batch_baseline_recapture` opt-out config key (dead weight for ~100% of tasks; unnecessary since the retry is already non-blocking on failure).

### retry trigger condition (no file-diff detection)

- Decision: the retry fires when, at the batch's dispatch-mode-specific hook point (see Decision: hook placement), that batch's `verify_baseline_failures` is still unset in status.md **and** that batch's own `verify:` frontmatter resolves to a non-`None` command — regardless of *why* the baseline is unset (errored, never enumerated because the substage didn't exist in cache yet, etc.).
- Rationale: `_run_baseline_stage` is already fully idempotent per-batch (`entry.get("verify_baseline_failures") is not None` skip check), so the "still unset" half of the condition is free to check (finalize already reads this field) and directly matches the actual failure mode: "this batch is about to finalize without a baseline it could have had." The non-`None`-verify half is required because `_enumerate_batch_verify_triples` (`millpy-implement.py`, `_enumerate_batch_verify_triples`) *permanently* skips any batch whose `verify:` resolves to `None` (docs-only/no-verify batches) — such a batch's `verify_baseline_failures` stays unset forever no matter how many times baseline stage runs, so without this half of the condition a no-verify batch reaching its hook point before a genuinely-recapturable batch would consume the single once-per-run retry attempt (see Decision: retry cadence) on a batch that could never benefit. A curated file list (watching `_verify_baseline.py` / `millpy-implement.py`) goes stale on refactors and either over-triggers (large files with unrelated changes) or under-triggers (logic moved to a new file). A plan-authored opt-in flag adds authoring burden mill-plan has no way to anticipate.
- Rejected: git-diff against a curated file list; a new batch frontmatter flag (`recaptures_baseline: true`); triggering on "unset" alone without the non-`None`-verify guard (wastes the single retry on structurally-ineligible batches).

### retry cadence — once per task run

- Decision: the retry attempts at most once per task run, lazily triggered the first time a batch hits its hook point with a still-missing, structurally-eligible baseline. Whether that one attempt succeeds or fails, no further automatic retry fires later in the same run. The "already attempted" flag is a **local Builder variable scoped to the current mill-go invocation** — no status.md field, matching the existing precedent of the Agent-mode `agent_id` handle (see `mill-go/SKILL.md` "## Agent-mode dispatch" step 3), which is likewise an in-memory-only value never persisted to disk.
- Rationale: the retry does a full parent-branch checkout + dependency-junction linking (`_verify_baseline._checkout_parent_branch` / `_link_dependency_dirs`), which is not free. A persistent failure (e.g. the in-development baseline code is still broken mid-plan) shouldn't pay that cost again on every subsequent batch's finalize. Because the flag is in-memory only, the bound it actually achieves is **"once per mill-go session," not "once per task lifetime"**: if mill-go is restarted mid-task (crash recovery, operator-initiated resume), the flag resets and the retry can fire again on the next session. This is an accepted, explicitly-stated limitation, not a gap — a restart is already a rare, human-visible event, and a second attempt in that case is harmless (idempotent no-op if the batch already has a baseline; a fresh useful attempt otherwise).
- Rejected: retrying on every batch until it succeeds (unbounded repeated checkout cost on a persistent failure); persisting the "attempted" flag to status.md (unnecessary schema addition for a cost-bounding mechanism that's already acceptable on a per-session basis). Accepted trade-off: a second batch further refining baseline-computation code later in the same plan won't get an additional automatic backfill within the same session — the existing fail-safe (strict verify gate) still applies to whatever it misses, just without the optimization.

### failure handling

- Decision: any failure from the retry invocation itself — non-zero exit, timeout, malformed/missing JSON output, or `--stage baseline` not yet existing in the worktree's mid-development code — is logged (ASCII-only, per `CLAUDE.md`) and the batch loop proceeds to that batch's normal strict-mode finalize exactly as if the retry had never been attempted. It never blocks or marks the task `stuck`.
- Rationale: matches `_run_baseline_stage`'s own documented "never raises, never blocks the task" contract. The baseline mechanism exists purely as a soft optimization (skip known-pre-existing failures); the retry that tries to opportunistically populate it must inherit the same non-blocking guarantee, especially since the worktree code it's invoking is by definition mid-development and may be transiently broken partway through the batch.
- Rejected: escalating a retry failure to `stuck`/blocking the task.

### hook placement

- Decision: one new sub-step in `mill-go/SKILL.md`, but its insertion point is **dispatch-mode-specific**, not a single shared call point:
  - **Agent-mode:** step 6 ("Run finalize stage") of the shared "## Agent-mode dispatch" pattern is reused verbatim at every dispatch call site in `mill-go/SKILL.md` (`### 1. Implement`, `### 3. Code Review loop`, the fix loop, Holistic Review, etc. — for `millpy-implement.py`, `millpy-review-code.py`, and `millpy-fix.py` alike), but only the implementer CLI's own finalize actually reads `verify_baseline_failures` (`millpy-implement.py`, line ~730). The hook is therefore inserted **locally within `### 1. Implement`'s own Agent-mode dispatch instance only** (the one with `<cli> = millpy-implement.py`), immediately before that instance's step-6 `--stage finalize` invocation — never into the shared step-6 definition itself, which would incorrectly also fire the check before every review/fix finalize call. This matches the file's existing precedent of locally-scoped, per-call-site insertions rather than edits to the shared pattern (e.g. the tree-guard checkpoints repeated at each call site rather than folded into the shared step).
  - **subprocess/psmux:** immediately before the backgrounded dispatch of `millpy-implement.py <batch_name>` (bare form, which defaults to `--stage full`) via `millpy-bg`. This mode has **no separate `--stage finalize` call to insert before** — `--stage full` runs the implementer and forwards straight into the same finalize logic (`_forward_output`, which reads `batch_verify_baseline` — `millpy-implement.py`, `main()`'s "Stage: full" branch) inside one synchronous process. The hook must therefore run and complete *before* that single backgrounded call is launched, so the baseline is already in status.md by the time the in-process finalize logic reads it.
- Rationale: the original premise — "finalize is a shared, dispatch-mode-agnostic call point" — is false for subprocess/psmux, which has no standalone finalize invocation at all; `--stage finalize` as a literal CLI call only exists on the Agent-mode path. The two insertion points share the same underlying check (status.md read + worktree-path invoke + JSON-parse), just wired at different points in each dispatch branch's existing structure.
- **Accepted limitation — dispatch-mode timing asymmetry:** the two insertion points are NOT functionally equivalent. Agent-mode's hook runs *after* the Agent tool call has already committed that batch's own cards, so the retry can see and benefit from the *current* batch's own fix to baseline-computation code. subprocess/psmux's hook necessarily runs *before* that batch's implementer has committed anything (`--stage full` runs implement-then-finalize inside one synchronous process with no external call boundary between them to hook into) — so under subprocess/psmux, the retry can only ever see *prior* batches' commits, never the current batch's own in-flight changes. A batch that itself introduces or fixes baseline-computation code, dispatched under subprocess/psmux, will not get its own fix reflected in its own recapture attempt — only a later batch would benefit, once that fix has landed. The original motivating incident (`mill-validate-verify-diagnostics-gaps` batch 6) is agnostic to this asymmetry only by coincidence (whichever dispatch mode it ran under, the fix — once landed — would have been visible to every *later* batch's retry regardless). This is accepted rather than fixed here: closing it would require moving the retry logic out of SKILL.md-level orchestration and into `millpy-implement.py` itself (invoked from inside the `--stage full` handler, after the implementer call returns but before `_forward_output`), which would also force the "once per task run" cadence (Decision: retry cadence) to become a persisted status.md field instead of an in-memory Builder variable — a substantially larger redesign than this task's scope, deferred to a future task if the asymmetry proves costly in practice.
- Rejected: describing this as one shared, functionally-equivalent insertion point (inaccurate for subprocess/psmux — see accepted limitation above); duplicating the check as two independently-varying implementations rather than one shared helper/block invoked from two different SKILL.md locations; moving the retry logic into `millpy-implement.py` itself to close the timing asymmetry (deferred — out of scope, see above).

## Technical context

- `plugins/mill/skills/mill-go/SKILL.md` "### 0.5. Baseline pre-flight (first batch of the task only)" (~line 396) is the existing one-shot pre-flight; this task adds a new, separate per-batch step, not a modification of this one (see Scope: Out).
- `plugins/mill/scripts/millpy-implement.py`:
  - `_run_baseline_stage(project_root, git_root, status_path, module_wide_verify_cmd, module_wide_cwd_override, plan_base)` (line ~220) — already idempotent per-batch and per-module-wide; computing it again with the worktree's own (possibly newer) code is exactly what's needed, no changes required to this function itself.
  - `_enumerate_batch_verify_triples(plan_base, project_root, git_root)` (line ~179) — reads every batch's own verify command straight from batch frontmatter; this is why one retry call can backfill multiple batches at once.
  - `main()`'s `--stage baseline` dispatch (line ~663) takes no `batch_name` — task-scoped, matching how the retry should invoke it (recompute everything outstanding, not just the current batch).
  - Batch's own finalize path (Agent-mode) reads `batch_verify_baseline = batch_status.get("verify_baseline_failures")` (line ~730) immediately before calling `finalize_from_output` — this read is the exact point the new hook must run before, for Agent-mode.
  - The **subprocess/psmux** path is `main()`'s "Stage: full" branch (line ~966 onward): it runs the implementer synchronously, then re-reads batches from status.md and looks up `batch_verify_baseline` (line ~1014, `_full_stage_batch_entry.get("verify_baseline_failures")`) before calling `_forward_output` — there is no separate finalize invocation for this dispatch mode; SKILL.md's hook must run before the CLI process is even launched (i.e., before the `millpy-bg`-backgrounded `millpy-implement.py <batch_name>` dispatch), not "before finalize" in the Agent-mode sense.
- `plugins/mill/scripts/_verify_baseline.py` — holds the actual computation logic (`compute_baseline`, `compute_batch_baselines`, `_checkout_parent_branch`, `_link_dependency_dirs`, `_run_module_wide_verify_algorithm`); `millpy-implement.py`'s baseline-stage functions are orchestration/wiring around this.
- `plugins/mill/scripts/_status.py`: `read_batches(status_path)` and `set_batch_field(status_path, name, "verify_baseline_failures", failures)` are the existing status.md accessors for this field — no schema changes needed.
- `plugins/mill/scripts/_paths.py` is the existing home for path/layout predicates (`resolve_git_root`, `resolve_wiki_path`, `resolve_hub_path`, etc.) — the new `is_self_hosting_task` helper belongs here, alongside `plugins/mill/unit_tests/test-paths.py` which already covers this module.
- Root `CLAUDE.md` "Script invocation" section documents the existing cache-form convention this task deliberately, narrowly departs from for the retry call only; "Path invariants" documents the analogous existing "task-worktree path for source verification" exception this design mirrors.

## Q&A log

- **Q:** How does mill-go decide a per-batch baseline retry is worth attempting? **A:** [auto-pick] Unconditional check — no file-diff detection; retry when `verify_baseline_failures` is still unset immediately before that batch's own finalize. **Why:** a curated file list drifts on refactors; a plan-authored opt-in flag adds burden mill-plan can't anticipate. The "still unset" condition already matches the actual failure mode and costs nothing extra to check.
- **Q:** Execution path for the retry call? **A:** [auto-pick] Worktree path (`PYTHONPATH="<git_root>/plugins/mill/scripts"`), gated by a self-hosting existence check; no-op for non-millhouse target repos. **Why:** the cache copy is frozen for the whole run — re-invoking it is provably a no-op.
- **Q:** Retry cadence? **A:** [auto-pick] Once per task run, lazily triggered on the first batch whose baseline is still missing. **Why:** the retry does a full parent-branch checkout; a persistent failure shouldn't repeat that cost on every subsequent batch.
- **Q:** Failure handling for the retry call itself? **A:** [auto-pick] Non-blocking — log and fall through to strict finalize, never escalate to stuck/blocked. **Why:** matches `_run_baseline_stage`'s own "never raises, never blocks" contract; the whole mechanism is a soft optimization.
- **Q:** New config key to enable/disable this? **A:** [auto-pick] No new config key — self-gating via the existence check is sufficient. **Why:** recent history in this repo (`0467ba27`) shows added config keys carry real maintenance cost; this feature is inherently self-scoping and already non-blocking on failure.
- **Q:** Where does the hook live, and does it apply to both dispatch modes? **A:** [auto-pick] One new sub-step immediately before each batch's `--stage finalize` call, shared across Agent-mode and subprocess/psmux dispatch. **Why:** finalize is the single, dispatch-mode-agnostic call point both branches already funnel through — avoids duplicating logic that would need to stay in sync.
- **Q:** Self-hosting gate + retry-worthiness check: extracted testable Python helper, or inline Bash? **A:** [auto-pick] Extract `_paths.is_self_hosting_task(git_root) -> bool`, unit-tested; keep the "still-unset baseline + non-`None` resolved verify command" check inline (trivial, already-tested `_status.read_batches` / `_plan_dag.parse_verify_field` reads — see the round-1 GAP fix entry below for the full two-part condition). **Why:** matches this repo's existing pattern of `_paths.py` owning layout predicates; a one-line existence check is essentially free to unit-test.
- **Q:** Should the existing batch-1 pre-flight (0.5) also prefer worktree-path when self-hosting is detected? **A:** [auto-pick] Out of scope — pre-flight keeps using cache form unconditionally; only the new later, per-batch retry hook uses worktree form. **Why:** at batch-1 time no task commits exist yet, so cache-vs-worktree there is a different, unrelated question (installed cache lagging the parent branch) that doesn't need solving to close this gap.
- **Q (round-1 review GAP):** Is "immediately before `--stage finalize`, shared across both dispatch modes" an accurate hook-placement description? **A:** No — subprocess/psmux has no separate `--stage finalize` call; `--stage full` runs implementer + finalize logic in one synchronous process (`millpy-implement.py` "Stage: full" branch, reading `batch_verify_baseline` at the same point `_forward_output` is called). Fixed: the trigger condition now also requires the batch's own `verify:` to resolve to a non-`None` command.
