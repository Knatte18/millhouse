## Problem

`plugins/mill/skills/mill-plan/SKILL.md` is meant to be a **self-contained** doc: a fresh Opus session with zero conversation history reads it and autonomously turns `discussion.md` into an approved implementation plan, with no operator interaction except at designed halt points. Seven GitHub issues (#839, #832, #831, #827, #826, #821, #815), filed against real mill-plan runs across three different repos (millhouse, loomyard), each found a place where the doc's literal instructions are unsatisfiable, misleading, or silently wrong — forcing the executing agent to guess, fail once, or (in #815's case) miss a real regression entirely. All seven are fixed in this task; none require behavior changes to shared scripts (`_paths.py`, `_status.py`, `_phase_wait.py`, `_plan_validate.py`) — every fix is text/logic inside `mill-plan/SKILL.md` itself, using helpers that already exist and already do the right thing.

**Why now:** these are all recently-filed (2026-08-11/12), real-usage-triggered bugs, not speculative — each has a concrete repro from an actual run.

## Scope

**In:**
- `plugins/mill/skills/mill-plan/SKILL.md` — Entry section (hub_root binding), Entry-gate wait section, Phase: Plan (new authoring guardrail), Phase: Plan Review (Step 1.5 fix table, Agent-mode dispatch `--agent-output` documentation, Step 6 halt message, new Entry `blocked` row).
- No script changes. `_paths.resolve_main_worktree_root`, `_status.append_phase`'s `blocked_reason` auto-clear, and `_phase_wait.matches_wait_trigger`'s regex parameter all already exist and already behave correctly — the bugs are exclusively in how (or whether) `mill-plan/SKILL.md` calls them.

**Out:**

Its one-line docstring wording ("Return the hub directory (the main worktree, where mill-config.yaml lives)") carries the same "main worktree" mislabel mill-plan's own comment does, and is folded into this task's scope as a zero-ripple, docstring-text-only correction (see Decisions) — but the function's signature and behavior are unchanged, and no call site elsewhere in the codebase is touched.
- `--recompute-baseline` / `mill-merge-in` — the wiki task body mentioned "`--revise` implies `--recompute-baseline`" but the actual GitHub issue #832 body never mentions this; `--recompute-baseline` exists only in the unrelated `mill-merge-in` skill. Treated as a stale wiki transcription, not pursued.
- A new mechanical `_plan_validate.py` check for #815's existing-test-impact guardrail — rejected in favor of a planner-authoring principle (see Decisions), since "this card intentionally changes an exported symbol's contract" is a judgment call, not a greppable pattern.
- Strengthening the plan-review reviewer's own prompt/template (`plugins/mill/templates/`) for #815 — the issue shows the reviewer template already *can* catch this (it flagged the omission as a NIT, just too late in the pipeline); mill-plan's own authoring guardrail is the primary fix, and reviewer-template changes are a separate concern outside this task's named scope.
- mill-start/SKILL.md's own copy of the identical Entry step-2 `<hub_root>` ordering issue (same pattern, same bug shape) — out of scope; this task is named for mill-plan only. Worth a follow-up issue but not fixed here.

## Decisions

### Entry: bind `hub_root` explicitly (#839, #826)

- Decision: Entry step 1 binds **both** `hub_root = _paths.resolve_main_worktree_root(git_root)` **and** `worktree_root = _paths.resolve_hub_path()` explicitly, alongside `git_root`/`wiki_path`, named exactly like steps 1/3 already name their resolvers (`resolve_git_root`, `resolve_wiki_path`, `slug_from_branch`). Step 2's `load_config` call is updated to reference both now-bound arguments (`_config.load_config(hub_root, worktree_root)` per `_config.py:221`'s actual signature). **`worktree_root` moves too, not just `hub_root` (added after discussion-review round 5 caught this):** the original plan fixed `hub_root`'s forward-reference but left `worktree_root` bound only in the later, unnumbered "**Path Setup.**" section — positioned after step 3, i.e. still after step 2's `load_config` call needs it — reproducing the identical "referenced before bound" defect class on the sibling argument. "**Path Setup.**" keeps deriving `status_path` (which depends on the now-already-bound `worktree_root`), but no longer derives `worktree_root` itself. Path Setup's remaining `worktree_root`-derivation comment drops the "(the hub root; ...)" phrase — replaced with wording that says what it actually is: the task worktree root, used to anchor `_mill/` paths (unchanged behavior, comment-only fix). Additionally, `_paths.py`'s `resolve_hub_path` docstring (currently "Return the hub directory (the main worktree, where mill-config.yaml lives)") gets the same wording correction — a one-line docstring text edit, no signature/behavior change, no other call site affected.
- Rationale: both issues independently converge on `_paths.resolve_main_worktree_root(git_root) -> Path` as the correct, already-existing, already-tested helper (`_paths.py:233`, uses `pygit2` to resolve the git common dir and correctly collapses to the main worktree root from any child worktree). No script change needed. Fixing the stray "hub root" label on `resolve_hub_path()`'s result prevents the exact naming collision issue #839 warned about ("note the naming collision that makes this easy to get wrong: `resolve_hub_path()` returns the worktree, not the hub") from being reintroduced now that a *second*, correctly-named `hub_root` exists in the same file. Moving `worktree_root` to step 1 alongside `hub_root` closes the identical ordering gap on `load_config`'s second argument — fixing only one of the two arguments a single call needs would have left the call just as unsatisfiable-as-written as before, only on the other parameter.
- Rejected: renaming/fixing `_paths.py`'s `resolve_hub_path` itself (unrequested by either issue, ripples into every skill that calls it — mill-start, mill-go — well beyond this task's scope); leaving the ordering issue as doc-only prose clarification without actually reordering (doesn't fix the unsatisfiable-as-written problem #839 reports); fixing only `hub_root`'s binding and leaving `worktree_root`'s identical forward-reference in place (the bug discussion-review round 5 caught — `load_config` needs both arguments bound before step 2, not just one).

### Max-rounds block: add a `blocked` re-entry row (#832)

- Decision: Entry step 4's phase table gets a new `blocked` row. On re-entry, read `blocked_reason` via `_status.read_full`. If it starts with `"max-rounds exhausted"`: first inline-derive `reviews_dir = _paths.resolve_task_path(worktree_root, cfg['paths']['reviews_dir'])` (the same expression Phase: Plan Review's own "**Path Setup (Plan Review).**" section uses at SKILL.md:263 — `worktree_root` and `cfg` are already bound by this point in Entry step 4, so this is a one-line addition, not a restructure; `reviews_dir` is otherwise explicitly punted to Phase: Plan Review per SKILL.md:51, which does not run until *after* this `blocked` row's own logic needs it). Then derive the next round number as `N = _review_common.discover_round(reviews_dir, "plan", "holistic")` (the file's own established round-discovery helper — scans `reviews_dir` for existing review files and returns `max(found) + 1`, or `1` if none exist; deliberately not regex-parsed out of the `blocked_reason` string, which is prose meant for a human, not a machine-parseable field, and contains more than one number). **Round-budget interaction (added after discussion-review round 2 caught this as a live dead-end-reproducing bug):** because `set_blocked`'s `"max-rounds exhausted"` reason is only ever written when `round == max_review_rounds` (step 6's own firing condition), `N` from `discover_round` will typically equal `max_review_rounds + 1` — meaning every one of the loop's existing `round >= max_review_rounds` checks (4a/4b/4c/6) would already be satisfied on the very first resumed iteration, immediately re-triggering an implicit-approve-at-cap or a fresh max-rounds halt without ever running a real review round. To prevent this, the resumed session computes `local_max_review_rounds = N + max_review_rounds - 1` (a fresh, full `max_review_rounds`-sized budget starting at round `N`) and uses `local_max_review_rounds` in place of the config-derived `max_review_rounds` for every round-cap check and every CLI dispatch (`--max-rounds <local_max_review_rounds>`, mirroring the exact per-invocation-override pattern mill-start's own `--auto` non-progress-extension already uses) for the remainder of this resumed Plan Review loop only — the config value itself is never mutated, and a subsequent fresh `/mill-plan` invocation (no `blocked` re-entry involved) uses the unmodified config value as always. Call `_status.append_phase(status_path, f"plan-review-r{N}", ts)` (this auto-clears `blocked_reason` per `_status.append_phase`'s existing transition-away-from-blocked behavior), commit+push, and fall through into the Plan Review loop starting at round `N` with the `local_max_review_rounds` cap in effect. **`--revise` interaction (added after discussion-review round 6 caught this):** a max-rounds block can occur while a `--revise` session is active, in which case the review files that were actually written live under a namespaced `reviews_dir / f"revise-{N}"` subdirectory (per SKILL.md:266-270), not the plain `reviews_dir` — and `revise_requested` itself is derived only from `$ARGUMENTS` per invocation, never persisted to `status.md`, so the `blocked` row cannot simply "remember" that a revise session was active. Detect this before deriving `N`: list any `reviews_dir/revise-*` subdirectories; if the most-recently-modified review file across all of them is newer than the most-recently-modified review file directly in the plain `reviews_dir` (or the plain directory has no review files at all), the block occurred mid-`--revise`. Treat this combination as an explicit, distinct hard stop — surface a message stating the block occurred during a `--revise` session and that resuming it is unsupported (the ordinary `--revise` pre-check cannot be re-supplied to recover the namespace, since it requires `phase == "planned"`, which is false once `phase: blocked`) — rather than silently deriving a wrong round number from the un-namespaced directory. Otherwise (newest file lives directly in the plain `reviews_dir`, or no `revise-*` subdirectories exist), proceed with the ordinary re-entry exactly as decided above.
  Any other `blocked_reason` value stays a hard stop exactly as today — surface the reason, require manual `status.md` intervention. The only other `_status.set_blocked` call sites in mill-plan/SKILL.md today are step 5's `"non-progress round {N}"` and step 4.5's `"plan review usage error: <message>"` (corrected illustrative list — `"plan-validate non-progress"` was a wrong example: Step 1.5's two-pass-cap halt, and step 4.5's own ERROR-only/no-JSON two-pass-cap halt, are both ephemeral `BLOCKED: ...`-prefixed messages surfaced directly to the operator, never routed through `_status.set_blocked`, so they never reach `status.md` and structurally cannot land on this `blocked` row at all). Separately, reword step 6's user-facing halt message from `"...{M} BLOCKINGs remain."` to `"...the last round's {M} BLOCKING finding(s) were addressed but not yet re-reviewed."`, since step 4d's fixer pass runs on those exact findings *before* the round-cap check fires. `_status.set_blocked`'s `blocked_reason` argument keeps its existing, unreworded text (`"max-rounds exhausted after {N} rounds, {M} BLOCKINGs remain"`) — this is intentional, not an oversight: `blocked_reason` is a machine field consumed only via the `.startswith("max-rounds exhausted")` prefix check in the new `blocked` re-entry row above, never read verbatim by a human at that point (the operator sees the accurate, reworded halt text at the moment of the original halt); reserving the wording fix for the message an operator actually reads avoids touching `_status.set_blocked`'s call site for no functional benefit.
- Rationale: matches the issue's own suggested fix ("add a `blocked` row to Entry step 4 routing back into Phase: Plan Review"). Distinguishing max-rounds (resource exhaustion — safe to retry once an operator explicitly re-invokes `/mill-plan`) from non-progress (stuck disagreement — genuinely needs a human, per mill-plan's existing Principles: "non-progress... user intervention is required") preserves the existing halt semantics for the case that's supposed to stay hard-stopped, while actually fixing the case that was reported as a pure dead end. The message reword directly addresses the issue's repro: an operator saw "3 BLOCKINGs remain" when all three had, in fact, just been fixed and committed. The `local_max_review_rounds` extension directly mirrors an already-shipped precedent in mill-start's own `--auto` non-progress-extension machinery (`mill-start/SKILL.md`'s "Phase: Discussion Review — `--auto` changes" section: `--max-rounds <max_review_rounds + 1>`, scoped to the extension round's invocations only, config never mutated) — same shape of problem (a round-cap re-entry needs a fresh, bounded extra budget without touching shared config), same solved-once-already mechanism.
- Rejected: requiring manual `_status.append_phase` surgery for every `blocked` case (documents around the bug instead of fixing it — status quo the issue is complaining about, which the file's own Board Discipline section separately says is banned: "Hand-editing the status.md yaml block is banned"); routing re-entry through `--revise` instead (conflates two different verbs — `--revise` is specifically for reopening an *already-approved* plan, not resuming a stalled, never-approved review round); resuming with the unmodified `max_review_rounds` value (the bug discussion-review round 2 caught — reproduces the exact dead end #832 reports, since the cap is already exceeded the instant `N` is computed); calling `discover_round` against an unbound `reviews_dir` (the bug discussion-review round 5 caught — `reviews_dir` is otherwise not derived until Phase: Plan Review, after the `blocked` row's own logic needs it); fully replicating the `--revise` subdir-probe-and-increment logic inside the `blocked` row to transparently resume a mid-revise block (the bug discussion-review round 6 caught the missing interaction, but full continuity restoration adds real complexity — scanning, re-arming `--reviews-subdir` on the resumed dispatch — for a narrow double-edge-case; an explicit, detected hard stop is simpler and still correctly distinguishes the two situations rather than silently deriving a wrong round).

### Step 1.5 fix table: add missing rows, resolve `verify-full-suite` contradiction (#827)

- Decision: add four rows to the Step 1.5 fix table:
  - `verify-malformed-cwd` — re-fix the `{cwd, command}` mapping per the validator error (bad `cwd` value or missing `command`).
  - `verify-mixed-cwd` — make every batch's `verify:` mapping resolve to the same `cwd` (all `hub` or all `git_root`) within one plan.
  - `depends-on-batch-mismatch` — sync a per-batch file's `depends-on:` with the overview's Batch Index entry for that batch.
  - `verify-full-suite` — if the batch's own `## Batch Tests` section already documents the cross-cutting-helper justification (see escape hatch below), re-run with `--skip-check verify-full-suite`; otherwise scope the command via `-k <pattern>` or `--only <every affected test file>`.
  Keep the "Verify command scope" section's existing carve-out ("A batch that legitimately touches a cross-cutting helper... MAY use the unbounded `run-all.py`"), but formalize it as a `verify-full-suite` skip-check escape hatch, added as a new paragraph directly modeled on the existing `wiki-config-mutation` skip-check override paragraph (SKILL.md:225-230): if a batch's `## Batch Tests` section documents that it genuinely touches a cross-cutting helper imported by many/all tests and cannot be meaningfully scoped via `-k`/`--only`, set `skip_checks = skip_checks | frozenset({"verify-full-suite"})` and record the justification in the validator-fix commit message, then re-run with `--skip-check verify-full-suite`. If the justification is absent or unconvincing, the check fires and halts on the two-pass cap exactly like any other unaddressed validator error.
- Rationale: grounded via direct grep of `_plan_validate.py` for every check-name literal it emits, cross-referenced against the ~20 rows already in the SKILL.md table — these 4 are confirmed emitted (`~1071`, `~2237`, `~2306`, `~2369`, matching Technical Context's citations below) and confirmed absent from the table. **Revised after discussion-review round 1 found the original plan's premise false:** `--skip-check` is a generic, repeatable argparse flag already wired into both `--stage prepare` (`millpy-review-plan.py:220`) and `--stage full` (`:327`) — it requires no new plumbing. `_check_wiki_config_mutation` itself has no code-level allowlist either; `wiki-config-mutation`'s entire "escape hatch" is SKILL.md-prose (the two-condition justification test), not extra script machinery. Since the mechanism already exists and is this cheap, formalizing the same pattern for `verify-full-suite` preserves the original prose's intent (a genuinely justified cross-cutting-helper batch shouldn't be forced into a fictional per-file scoping list) at effectively zero implementation cost, rather than silently dropping a previously-permitted case.
- Rejected: removing the "cross-cutting helper" carve-out entirely and requiring `--only` in all cases (the originally-drafted plan) — was based on the false premise that no skip-check mechanism exists for this validator check; once the mechanism is confirmed as cheap and precedented, dropping a legitimately useful escape hatch is worse than formalizing it.

### Widen the entry-gate wait trigger (#821)

- Decision: change `matches_wait_trigger(phase, {"discussing"}, [])` to `matches_wait_trigger(phase, {"discussing"}, [r"^discussion-fix-r\d+$"])`. Rewrite the justification paragraph (current SKILL.md lines 79-81) to drop the now-disproven claim that `discussion-fix-r{N}` "is never itself pushed as a standalone, externally observable phase."
- Rationale: issue #821 has a concrete repro — commit `ab1786d6` pushed `phase: discussion-fix-r1` standalone while mill-start was mid-loop. This is explained by mill-start's own convergence-gate logic (`mill-start/SKILL.md` Phase: Discussion Review step 4b, not-converged branch): when `round < max_review_rounds` and the convergence gate hasn't fired, mill-start appends+commits+pushes `discussion-fix-r{N}` and continues to the next round *without* the `discussed` phase following in the same commit — directly contradicting mill-plan's stated assumption. `_phase_wait.matches_wait_trigger`'s third parameter already supports fully-anchored regex patterns, and mill-go's own copy of this exact wait pattern already uses it for mill-plan's phases (`mill-go-base/SKILL.md:172`: `{"discussed", "discussing", "planning"}, [r"^plan-review-r\d+$", r"^plan-fix-r\d+$"]`) — direct precedent, same mechanism, same file family.
- Rejected: widening the trigger without correcting the justification paragraph — leaves a demonstrably false claim in a doc that's supposed to be authoritative for a cold-start agent, risking reintroduction of the narrow matcher by a future editor who trusts the (wrong) prose over the (fixed) code.

### New authoring guardrail: existing-test-impact check for contract changes (#815)

- Decision: add a new principle to mill-plan/SKILL.md's `## Principles` section, next to the existing "Card `Context:` is an allowlist" / "`Requirements:` must use stable identifiers" principles (~line 551-560): when a card's `Requirements:` states that it changes an exported function's, method's, or class's existing behavior/contract (not just adding new code), the planner must grep the codebase for existing callers and tests of that symbol before finalizing the plan, and add any found to that card's `Context:` (read-only) or `Edits:` (if the test itself needs updating to match the new contract).
- Rationale: issue #815's repro is a genuine miss across the *entire* existing pipeline — 5 discussion-review rounds, 5 plan-review rounds, and a holistic code review all failed to catch that hardening `Fabric.ResetHard` against dirty checkouts would break an existing, unlisted integration test, because no card's `Edits:` or the overview's `All Files Touched` ever named the test file. The holistic reviewer *did* eventually flag the omission — but only as a post-hoc NIT, after the plan was already through review. "Intentionally changes an exported symbol's contract" is a judgment call about the card's own stated design intent — something only the planning agent (Opus, already reading the full `Requirements:` prose) can reliably make; a mechanical validator check can't distinguish an intentional contract change from an incidental edit to the same function.
- Rejected: a new `_plan_validate.py` mechanical check (can't judge intent, only greppable patterns — would need a fragile heuristic like "any Requirements: line containing a negation+behavior-change keyword," prone to false positives/negatives the same way the existing `context-completeness` prohibition-detection already is); relying on the reviewer template/prompt instead (issue shows this path already exists and already failed once — too late in the pipeline to prevent the wasted implementer round the issue describes); doing nothing (leaves the exact gap #815 reports).

## Testing

These are `mill-plan/SKILL.md` prose/logic changes (an instruction doc read by an LLM orchestrator, not directly executable code), but there IS a relevant existing unit-test surface: `plugins/mill/unit_tests/test-skill-helper-drift.py` scans every `SKILLS.rglob("SKILL.md")` file (including mill-plan's) and asserts that every `_<module>.<fn>(`-shaped prose reference resolves to a real, currently-shipped function signature. This task's edits add/touch several such references (`_paths.resolve_main_worktree_root(...)`, `_status.append_phase(...)`, `_review_common.discover_round(...)`, `_phase_wait.matches_wait_trigger(...)`), so the implementer must run this test against the edited SKILL.md before committing (`PYTHONPATH= uv run --project plugins/mill python plugins/mill/unit_tests/test-skill-helper-drift.py`) — it would catch a typo'd or renamed helper reference, or a reference to a module/function that no longer exists. **It does not check argument count or order** (verified: `_run_drift_guard`, `test-skill-helper-drift.py:135-150`, resolves `(module_stem, fn)` to *some* function of that name and stops there — no `arity`/`signature`/`inspect.signature` logic anywhere in the file), so it will NOT catch a call written with the right function name but the wrong argument order or count — e.g. `_config.load_config(hub_root, worktree_root)`'s exact 2-argument order (the precise class of bug #839/#826 are about) still needs manual verification against `_config.py:221`'s actual signature.
Beyond that: (a) re-read the rendered SKILL.md end-to-end for internal consistency after edits (no dangling references to the old narrow wait trigger, no stale "hub root" double-labeling, no orphaned mention of a removed carve-out); (b) grep-based self-checks the implementer should run before committing — e.g. `grep -n "agent-output" mill-plan/SKILL.md` should show 2 hits, `grep -n "hub_root" mill-plan/SKILL.md` should show the new Entry-step-1 binding preceding step 2's use of it.
