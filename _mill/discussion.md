## Problem

Nine GitHub issues (#968, #967, #957, #931, #952, #951, #962, #958, #975), filed independently across four different consuming repos over roughly a week, all land on the same family of files: `plugins/mill/skills/mill-go-base/handoff.md`, `SKILL.md`, `mill-pause/SKILL.md`, and `plugins/mill/scripts/_cleanliness.py`. Each is a real incident, not a hypothetical: an operator hit a documented gap in a halt/recovery path, had to infer or hand-roll the fix live, and filed the issue afterward. They cluster into two root causes:

1. **Handoff's "0. Pre-done gate" halt path is under-built relative to every other halt path in this file family.** It's missing the builder-lock release step every sibling halt path has (#968), has no dispatch path to the `mill-done-gate-fixer` agent that already exists specifically to resolve this exact failure in downstream repos (#967, #931), and its raw inline Python subprocess snippet gets blocked outright by the Claude Code auto-mode permission classifier with no documented fallback (#957).
2. **The two mill-go cleanliness gates (`SKILL.md` step 2b, `handoff.md`'s terminal gate) have no recovery when a task's recorded parent branch has been squash-merged and deleted** — a routine outcome of a sibling/parent task's own `mill-merge` run. `mill-merge-in` already solved this exact problem (`_parent_branch.check_liveness` / `resolve_dead_parent`); mill-go's two gates just never got the same treatment (#952, #951).

Three more issues in the same brief round out unrelated but adjacent gaps in the same file family: `mill-pause` has no documented disposition for an in-flight Agent-mode dispatch and wrongly `TaskStop`s a running reviewer (#962); `SKILL.md` step 5.5's warm-resume path lacks the liveness probe step 3(b)/(c) already has, risking a two-writers collision (#958); and `_cleanliness.clean_ephemeral_scope_violations`'s fixed allowlist has no entry for Python's `__pycache__`/`.pyc` artifacts, so the one sanctioned Python test directory in at least one consuming repo hits a manual-classification gate on every run (#975).

**Why now:** these are all live-incident reports from real task runs (loomyard, quarry, NORCE-Models repos) across the past ~2 weeks — each one cost an operator manual intervention that the documented skill should have handled.

## Scope

**In:**
- `handoff.md` "0. Pre-done gate": add builder-lock release on halt; add conditional `mill-done-gate-fixer` dispatch (self-resolve once) before halting; replace the raw inline `subprocess.run(shell=True, ...)` snippet with a call to a new `_done_gate.run_gate()` helper.
- `handoff.md`'s other three halt paths (unfixed-nits gate, terminal-dirt gate, scope-violations gate): add the same builder-lock release step for consistency with every other BLOCKED path in this file family.
- `SKILL.md` step 2b (per-batch cleanliness gate) and `handoff.md`'s terminal cleanliness gate: wire in `_parent_branch.check_liveness` / `resolve_dead_parent` dead-parent recovery, mirroring `mill-merge-in`'s existing Entry Step 2 pattern but adapted for mill-go's non-interactive/self-resolve-once posture.
- `plugins/mill/skills/mill-pause/SKILL.md`: add a third documented case — in-flight Agent-mode dispatch — with an explicit disposition (wait, finalize, stop; never `TaskStop`).
- `SKILL.md` step 5.5 (`incomplete` recovery, warm-`SendMessage` branch): apply the existing `TaskOutput(block: false)` liveness probe (already used in step 3(b)/(c)) before treating a stale-looking "completed without JSON" warm-resume result as terminal.
- `plugins/mill/scripts/_cleanliness.py`'s `clean_ephemeral_scope_violations`: extend the fixed allowlist to recognize `.pyc` files and `__pycache__` path components.
- `plugins/mill/scripts/_done_gate.py`: add `run_gate(gate_cmd, git_root) -> dict`, mirroring `run_preflight`'s shape/never-raise contract, additionally performing the existing Windows dotnet-build-server-shutdown cleanup on success.

**Out:**
- Not touching `mill-merge`/`mill-merge-in`'s own dead-parent-branch handling — already correct, only reused here.
- Not shipping a generic `mill-done-gate-fixer` agent template in millhouse itself — the agent's fix strategy is inherently project-specific; millhouse only adds the conditional dispatch step that uses it *if* a project has registered one.
- Not touching `holistic-review.md`'s existing halt paths — they already release the builder lock correctly; nothing to fix there.
- Not generalizing `_cleanliness.py`'s allowlist beyond Python — no other language gap has been reported.
- Not changing `pipeline.done_gate_baseline_preflight`'s (0.55) behavior or its existing `_done_gate.run_preflight` — it stays as-is; `run_gate` is a new sibling function, not a replacement.
- Not adding a bounded retry/backoff policy to the new `TaskOutput` probe in step 5.5 — it follows the exact same "no bounded re-check loop, unbounded wait for the next notification" contract step 3(b)/(c) already documents.

## Decisions

### builder-lock-release-all-handoff-halts

- Decision: Add the builder-lock release step (`millpy-builder-lock.py release`) to all four `handoff.md` halt points — pre-done-gate (#968's literal ask), unfixed-nits gate, terminal-dirt gate (both of its two halt messages), and scope-violations gate — immediately before each `BLOCKED:` halt message, in the same position/order every other halt path in `SKILL.md`/`holistic-review.md` already uses it (see the shared `### Blocked` section in `SKILL.md` for the canonical shape).
- Rationale: #968's own justification ("unlike every other BLOCKED path in SKILL.md and holistic-review.md") is equally true of handoff.md's other three gates — none of them release the lock either. Fixing only the literally-filed one leaves the same bug live and likely to be re-filed against a sibling gate.
- Rejected: Fixing pre-done-gate alone (matches the filed issue exactly, but leaves a known-identical gap in the same file).

### done-gate-fixer-conditional-dispatch

- Decision: In `handoff.md`'s "0. Pre-done gate", on a `blocked` result from the gate command: check whether `<git_root>/.claude/agents/mill-done-gate-fixer.md` exists. If it does, dispatch it once via a plain `Agent(subagent_type: "mill-done-gate-fixer")` call — not through the CLI prepare/finalize family used for implementer/reviewer/fixer — with a brief containing the plan overview (`00-overview.md`), the configured `done_gate` command, and the captured failure output (same `reason` text the halt message would otherwise carry). After the fixer's dispatch completes, re-run the done-gate command once. If it now passes, proceed to step 1 (`phase: done`) as normal. If it still fails, release the builder lock and halt with the existing `BLOCKED: done gate failed — <reason>` message, now including a note that the fixer was already attempted.
  If `.claude/agents/mill-done-gate-fixer.md` does **not** exist in the project, skip the dispatch entirely and halt immediately as today (with the lock-release fix from the decision above).
- Rationale: #967/#931 both point at the same disconnect — the agent exists and is purpose-built for exactly this failure, but nothing in the shipped skill text knows to use it. #931's own suggested fix is the conditional-existence-check approach, which also avoids millhouse having to ship or maintain a generic fixer template that would necessarily be wrong for most individual projects' `done_gate` commands.
- Rejected: Unconditional dispatch assuming the agent always exists (breaks on any project without it — the common case, since millhouse itself doesn't ship one); building a full CLI/prepare-finalize contract for this dispatch (over-engineered for a single self-resolve-once step that isn't part of the implement/review/fix family).

### done-gate-classifier-safe-invocation

- Decision: Add `run_gate(gate_cmd: str, git_root: Path) -> dict` to `plugins/mill/scripts/_done_gate.py`, running the identical `subprocess.run(gate_cmd, cwd=git_root, shell=True, capture_output=True, text=True)` shape `run_preflight` already uses (same stdout+stderr concatenation, same 2000-char tail truncation, same never-raise contract), and additionally performing the existing Windows-only `dotnet build-server shutdown` cleanup on a successful (`returncode == 0`) run when `'dotnet' in gate_cmd.lower()`. Return shape: `{"result": "ok"}` or `{"result": "blocked", "reason": <truncated output>}` (no `"skipped"` case needed here — Handoff already checks `gate_cmd is None` before calling). `handoff.md`'s "0. Pre-done gate" block is rewritten to call this function (`import _done_gate; result = _done_gate.run_gate(gate_cmd, git_root); print(json.dumps(result))`) instead of inlining the raw `subprocess.run(...)` call directly in the Bash-tool Python snippet.
- Rationale: #957 hit the Claude Code auto-mode classifier blocking the literal inline `subprocess.run(shell=True, ...)` text with no recourse. The 0.55 done-gate-baseline-preflight step already runs the *same underlying command* via `_done_gate.run_preflight` — a named module-level function call rather than an inline literal `subprocess.run(shell=True,...)` — and there is no report of the classifier blocking that call site. `_done_gate.py`'s own docstring already claims `run_preflight` "mirrors the exact subprocess-invocation shape already used inline in mill-go SKILL.md's Handoff-time 0. Pre-done gate block" — the two were meant to share logic and never actually were wired together. Moving the Handoff invocation onto the same pattern is a straightforward DRY fix that also resolves the classifier issue as a side effect, rather than a classifier-specific workaround.
- Rejected: Documenting a manual fallback path for when the classifier blocks the call (doesn't fix the underlying duplication, and leaves autonomous/`--auto` runs with no path forward when it's blocked); trying to guess and special-case exactly what the classifier flags (fragile, unfalsifiable without access to the classifier's rules — the DRY fix sidesteps the question entirely).

### cleanliness-gate-dead-parent-recovery

- Decision: At both mill-go cleanliness call sites — `SKILL.md` step 2b's `_parent_branch.resolve(status_path, interactive=False)` and `handoff.md`'s terminal cleanliness gate's identical call — wrap the resolved `parent_branch` with a liveness check before computing dirt:
  1. `_parent_branch.check_liveness(parent_branch, git_root)`.
  2. If alive: proceed exactly as today, no behavior change.
  3. If dead: call `_parent_branch.resolve_dead_parent(parent_branch, git_root, cfg)`.
     - `outcome: "resolved"` (chain walk found a live successor): **auto-rebind non-interactively** — `_status.update_field(status_path, "parent", resolved_branch)`, commit (`git -C <worktree> add <status_path> && git -C <worktree> commit -m "<VARIANT_LABEL>: rebind dead parent branch for <batch_name/terminal>"`), no push required (matches this file's existing no-push-mid-batch convention), then retry the dirt computation once against the new `parent_branch`. Proceed normally if the retry succeeds.
     - `outcome: "fallback"` (only a base-branch guess, no confirmed chain): halt — `blocked_reason: "parent branch <dead_branch> no longer exists; no archive-tag chain resolved a successor (<reason>); would fall back to <base_branch> but needs operator confirmation"` — release the builder lock, same halt shape as the existing "parent diff unresolvable" message.
     - `outcome: "cycle"`: always halt — `blocked_reason: "parent branch archive-tag chain walk hit its hop cap without resolving a live parent"` — release the builder lock.
  4. If the retry after a `resolved` rebind still yields `in_scope_dirt is None` (or the batch-2b equivalent), halt with the existing "parent diff unresolvable" message as today — do not loop further.
- Rationale: `resolved` is a high-confidence outcome (an actual, verified archive-tag chain to a currently-live branch) — mill-go already self-resolves comparably-confident situations elsewhere in this same file without operator confirmation (terminal dirt, scope violations), so treating this the same way is consistent with the existing autonomy posture. `fallback` is a bare guess at the configured base branch with no actual verification it's correct for this task — that's exactly the kind of ambiguous case mill-go's existing gates already choose to halt on rather than guess. `mill-merge`/`mill-merge-in` always require confirmation for both outcomes because they're typically operator-invoked directly; mill-go runs unattended mid-task and needs a bar that doesn't stall every batch on an operator being present.
- Rejected: Always halting for operator confirmation, mirroring mill-merge/mill-merge-in exactly (safer but defeats mill-go's autonomous-execution design — every squash-merged parent would stall the whole task on a human); auto-rebinding on `fallback` too (guessing the base branch could silently point a scope-drift check at the wrong branch, corrupting what counts as "in scope").

### mill-pause-in-flight-agent-dispatch

- Decision: Add a third bullet to `mill-pause/SKILL.md`'s "When invoked" section: **if an Agent-mode dispatch (implementer/reviewer/fixer) is in flight** — wait for its `<task-notification>` to arrive, run the CLI's `--stage finalize` call so the round is correctly recorded in status.md/reviews, then stop cleanly without dispatching the next round or batch. Explicitly state that calling `TaskStop` on a running Agent-mode dispatch is forbidden — the round is not resumable from a kill, and `discover_round` would just re-run it from scratch on the next `/mill-go`, silently discarding the in-flight work.
- Rationale: #962 is a direct account of the current two-case document (`millpy-bg` poll in progress / no poll in progress) having no match for the now-default Agent-mode dispatch, causing the orchestrator to `TaskStop` a running reviewer and lose a full review round. The correction is exactly what the operator said live: wait, don't kill.
- Rejected: Extending the existing "no poll in progress" case to implicitly cover this (too easy for a future reader to miss — this needs its own explicit, named case per [[feedback_inline_mode_guard_at_override_site]]-style guidance already established for this codebase: override/exception behavior needs its own inline statement at the site it applies, not an inference from a nearby rule).

### step-5-5-warm-resume-liveness-probe

- Decision: In `SKILL.md` step 5.5's warm-`SendMessage` resume branch (item 1), after sending the resume message and before treating the resulting `<task-notification>` as terminal: if that notification is non-clean-terminal in the same sense step 3(b)/(c) already define (status present and not `completed`, or `completed` but with no valid JSON report), call `TaskOutput(task_id: <agentId>, block: false)` — the same `agentId` retained from the original dispatch — before falling through to the `--resume-incomplete` cold-dispatch fallback. If the probe reports the agent still running, take no action this turn and wait for its next notification (unbounded, matching step 3's existing contract). If it reports the agent no longer running (or the probe errors), proceed to `--resume-incomplete` as already documented.
- Rationale: #958 is a direct incident: the warm-resumed agent's "completed" notification was stale (still genuinely running, mid-commit) with no probe to catch it, and only a manual `TaskOutput` check by the operator prevented a two-writers collision from a redundant cold `--resume-incomplete` dispatch onto the same worktree. Step 3(b)/(c) already solved this identical staleness problem for the original dispatch; step 5.5 is the one remaining call site with the same risk shape and no probe.
- Rejected: Leaving step 5.5 unprobed and relying on operators to manually check (works until it doesn't — this is precisely the incident that got filed); building a distinct bespoke probe mechanism for this one call site instead of reusing the existing one (no reason for the two to differ — same risk, same fix).

### pycache-ephemeral-allowlist

- Decision: Extend `_cleanliness.clean_ephemeral_scope_violations`'s fixed-allowlist rule (rule 3, the extension-bearing branch) to also allowlist any violation whose basename ends with `.pyc`, or whose path contains a `__pycache__` path component (checked the same way the function already splits `basename = violation.split("/")[-1]`, but here also checking `"__pycache__" in violation.split("/")`). Both cases are removed from disk the same way every other allowlisted entry already is (`os.remove`, `FileNotFoundError` swallowed).
- Rationale: #975 is a direct incident — 13 individual `.pyc` files landed in `blocking_paths` (pygit2's `status()` reports untracked files individually rather than collapsing an untracked directory the way plain `git status --porcelain` does, so each `.pyc` shows up as its own violation line, not a single `__pycache__/` directory entry) and required manual Builder classification against the plan's `All Files Touched` list every single run. This is the exact same ephemeral-build-artifact category the Go allowlist rules already exist to auto-clean, just missing the Python case.
- Rejected: Fixing this via a per-repo `.gitignore` entry instead (doesn't help any other consuming repo hitting the same gap, and the existing allowlist mechanism is explicitly designed to generalize this way across languages already — see the Go rules).

## Technical context

It currently reads `pipeline.done_gate` from deep-merged config, runs it inline via `subprocess.run(shell=True, ...)`, and on a `blocked` JSON result halts with no lock release and no fixer dispatch.
- **`handoff.md`'s other three halt paths** (unfixed-nits gate ~line 33, terminal-dirt gate ~lines 53/59/61, scope-violations gate ~line 84) all currently halt with a `BLOCKED:` message and explicitly say "Do NOT set `phase: done`" — none of them release the builder lock today. All four share the file's general shape: self-resolve once, re-check, halt if still failing.
- **The shared `### Blocked` section in `SKILL.md`** (~line 859) is the canonical builder-lock-release shape to match: `_notify.notify(...)`, then `millpy-builder-lock.py release`, then tell the user and stop — do not proceed to Handoff. `holistic-review.md`'s several halt paths (usage-error, ERROR-only, fallback-also-failed, rate-limited-no-fallback — ~lines 114-146) already follow this same shape and are the direct precedent to mirror.
- **`plugins/mill/scripts/_done_gate.py`** already exists (added for #650, the baseline-preflight self-capturing-suite problem) and exposes `run_preflight(gate_cmd, git_root) -> dict`, whose docstring explicitly (and currently inaccurately) claims to mirror Handoff's inline logic. `SKILL.md`'s "0.55. Done-gate baseline pre-flight" (~line 498) is the existing, working call site to pattern-match for the new `run_gate` — same `-c "import ... _done_gate; ...; print(json.dumps(result))"` shape, same 10-minute Bash-tool timeout recommendation (arbitrary, potentially slow project command).
- **`.claude/agents/mill-done-gate-fixer.md` does not exist anywhere in this millhouse repo** (confirmed via `find` and `grep -rl "done-gate-fixer"` across `plugins/mill/` — zero hits). It is a project-local convention in at least loomyard, quarry, and other individual repo checkouts, per the filed issues' own descriptions of its `subagent_type` and description text. The existence check for the conditional-dispatch decision above is a plain `Path(git_root, ".claude/agents/mill-done-gate-fixer.md").exists()` check, no millhouse-side registry needed.
- **`plugins/mill/scripts/_parent_branch.py`** already implements everything the dead-parent-recovery decision needs: `check_liveness(branch, git_root) -> bool` and `resolve_dead_parent(dead_branch, git_root, cfg, *, max_hops=10) -> dict` (three outcome shapes: `resolved`/`fallback`/`cycle`, each documented in the function's own docstring). Both were added for `mill-merge`/`mill-merge-in`'s own dead-parent handling (#817) and need no changes — only new call sites.
- **`mill-merge/SKILL.md` Entry Step 4** (~lines 76-133) and **`mill-merge-in/SKILL.md`** (~lines 21-27) are the existing reference implementations of the liveness-check-then-resolve-then-confirm-then-rebind flow. The two new mill-go call sites (`SKILL.md` step 2b ~line 658-673, `handoff.md`'s terminal gate ~lines 45-53) follow the same `check_liveness` → `resolve_dead_parent` → branch-on-outcome shape but skip the operator-confirmation step for the `resolved` outcome per the Decision above (mill-go is non-interactive; mill-merge/mill-merge-in are typically operator-invoked).
- **`SKILL.md` step 3(b)/(c)** (~lines 297-341) is the existing `TaskOutput(task_id: <agentId>, block: false)` liveness-probe pattern to reuse verbatim for step 5.5 (~lines 379-403). The `agentId` is already retained per step 2's existing documentation ("Record the `agentId` the Agent tool returns in that launch message and retain it for the duration of this batch") — no new plumbing needed to make it available at step 5.5's call site.
- **`plugins/mill/skills/mill-pause/SKILL.md`** is an 26-line file with exactly two documented cases today (millpy-bg poll in progress / not in progress). The new third case slots in alongside them at the same "When invoked" heading.
- **`plugins/mill/scripts/_cleanliness.py`'s `clean_ephemeral_scope_violations`** (~lines 253-331) and its three ordered allowlist rules are the edit site for the pycache fix — rule 3 (~lines 306-313) is a plain boolean OR-chain over `basename` checks, the natural place to add the two new conditions.
- **`_pygit2_util.status_porcelain`** (~line 202) uses `pygit2`'s `repo.status()`, which reports untracked files individually rather than collapsing an untracked directory into one `?? dir/` line the way plain `git status --porcelain` (CLI) does — this is *why* #975 saw 13 individual `.pyc` violations rather than one `__pycache__/` directory violation, and confirms the fix must match on file basename/path-component, not assume a directory-level violation string.

- **Q:** Should the builder-lock release fix apply only to the literally-filed pre-done-gate halt path, or to all four halt paths in handoff.md? **A:** [auto-pick] Fix all four, for consistency with every other BLOCKED path in this file family. **Why:** #968's own comparison rationale applies equally to handoff.md's three sibling gates, which have the identical gap.

- **Q:** Should the mill-done-gate-fixer dispatch go through the full CLI prepare/finalize contract used for implementer/reviewer/fixer, or a plain one-shot Agent() call? **A:** [auto-pick] Plain one-shot Agent() call. **Why:** this agent isn't part of the implement/review/fix CLI family; building a full contract for a single self-resolve-once step is over-engineering.
- **Q:** Should the classifier-blocked subprocess snippet be fixed by documenting a manual fallback, or by moving the logic into a `_done_gate` module function (as 0.55's `run_preflight` already does successfully)? **A:** [auto-pick] Move it into a new `_done_gate.run_gate()` function. **Why:** `_done_gate.py`'s own docstring already (inaccurately) claims to mirror Handoff's logic — wiring them together is a DRY fix that also happens to sidestep the classifier issue, rather than a classifier-specific workaround.
- **Q:** On a `resolved` dead-parent-branch outcome, should mill-go's cleanliness gates auto-rebind non-interactively, or always halt for operator confirmation like mill-merge/mill-merge-in? **A:** [auto-pick] Auto-rebind non-interactively on `resolved` (high-confidence, verified chain); still halt on `fallback` (a guess) and always halt on `cycle`. **Why:** mill-go runs unattended mid-task; mill-merge/mill-merge-in are typically operator-invoked directly, so their always-confirm posture doesn't transfer without stalling every batch on an operator being present.
- **Q:** After an auto-rebind, should the gate retry once with the new parent branch, or rebind then halt anyway for a manual re-run? **A:** [auto-pick] Retry once immediately; halt only if the retry itself still fails. **Why:** matches this file's existing self-resolve-once-then-halt shape used by every other gate in Handoff.

- **Q:** Should step 5.5's warm-resume path get the same `TaskOutput(block: false)` liveness probe as step 3(b)/(c), or a new bespoke mechanism? **A:** [auto-pick] Reuse the existing step 3(b)/(c) probe verbatim. **Why:** identical risk shape (stale "completed" notification for a still-running agent) to what step 3 already solved; no reason for the two to diverge.
- **Q:** Should `__pycache__`/`.pyc` cleanup be fixed in millhouse's `_cleanliness.py` allowlist, or pushed to per-repo `.gitignore`? **A:** [auto-pick] Fix in `_cleanliness.py`'s allowlist. **Why:** the allowlist mechanism already exists specifically to generalize this kind of ephemeral-artifact cleanup across languages (see the existing Go rules); a per-repo `.gitignore` fix wouldn't help any other repo hitting the same gap.
