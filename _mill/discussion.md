# Discussion: Fix nested-hub-layout path resolution bugs across scope violations and review CLIs

## Problem

Five GitHub issues (#603, #608, #601, #607, #604) all share one root cause: code paths in `plugins/mill/scripts/` that assume the mill project root (`hub_root`, resolved via `_paths.resolve_hub_path()`) is identical to the git repository root (`git_root`). That assumption holds for most repos but breaks for "nested hub layout" repos where the mill hub lives in a subdirectory of the git root (e.g. `src/csharp/NORCE.Models`). In those repos, scope-violation checks false-positive and block every Handoff, review CLIs write briefs to the wrong `_mill/` directory, and the finalize verify step can run from the wrong cwd and fail with MSB1009-style errors. This surfaced on a real nested-layout repo; the fix needs to make all five sites nested-aware without regressing the (more common) flat-layout case where `hub_root == git_root`.

## Scope

**In:**
- `_cleanliness.compute_scope_violations` and `_cleanliness.clean_ephemeral_scope_violations` — fix false-positive scope violations in nested layouts (#603, #608; one underlying bug, two signatures to update).
- The `clean_ephemeral_scope_violations` call site at `plugins/mill/skills/mill-go/SKILL.md:749` — updated to pass both `hub_root` and `git_root` (both already resolvable locals at that point in the SKILL).
- `millpy-review-plan.py` and `millpy-review-code.py` — fix `brief_path` to resolve under the hub root, not git_root (#601, #607).
- Verify-command cwd policy across `_implementer_common.py`, `millpy-implement.py`, `millpy-fix.py`, `_plan_dag.py` (`iter_batch_verifies`), `_verify_baseline.py` (`compute_baseline`), `plugins/mill/skills/mill-merge-in/SKILL.md` step 4 (Verify replay), plan schema, and `_plan_validate.py` — add an explicit `cwd` field to plan verify steps (both per-batch and module-wide/overview) so nested-layout plans can opt into hub-relative execution without regressing the git-root-relative convention pinned for #554 (#604).
- New nested-layout test fixture(s), reused across the affected test files, including the 9 existing `test-cleanliness.py` CESV cases (updated to pass both roots).
- Updating the mill-plan skill/template so newly authored plans on nested-layout tasks set `cwd: hub` and write hub-relative verify commands.

**Out:**
- Any migration/cleanup of already-existing orphaned `_mill/briefs/` directories left at git_root by the #601/#607 bug — left to `mill-cleanup`'s general sweep, not this task.
- Changing `_pygit2_util.status_porcelain`'s low-level path semantics (it stays git-root-relative; callers rebase).
- Retroactively rewriting existing plans' verify commands — the `cwd` field defaults to `git_root` so existing plans are unaffected.
- Any redesign of the junction system itself (`.active`/`.wiki`/`.portals` continue to live at `hub_root`, unchanged).

## Decisions

### compute_scope_violations rebasing

- Decision: Change `compute_scope_violations(worktree: Path)` to `compute_scope_violations(hub_root: Path, git_root: Path)`. Internally, keep calling `_pygit2_util.status_porcelain(hub_root, include_untracked=True)` (unchanged — pygit2 discovers the repo and reports git-root-relative paths regardless of which path is passed), then compute the hub-relative prefix (`hub_root` relative to `git_root`, POSIX-normalized) and, for each reported path: if it does not start with that prefix, **drop it entirely** (not a violation — it's outside this task's hub subtree, e.g. a sibling module's untracked file, and has nothing to do with this task's scope); otherwise strip the prefix and apply the existing `_mill/`-prefix check and junction first-segment (`_JUNCTION_SKIP_SET`) check to the remainder. When `hub_root == git_root` the prefix is `""`, every path starts with it trivially, and stripping is a no-op — flat-layout behavior is byte-identical to today.
- Rationale: `_pygit2_util.status_porcelain` always returns git-root-relative paths no matter what path is passed to it — the four call sites in `_implementer_common.py` already pass `project_root` (the correct hub root) as `worktree`, but that alone doesn't fix anything because the string paths returned are still git-root-relative. The double failure mode (both the `_mill/` check and the junction check misfire) needs the git_root→hub_root prefix, not just a differently-named single path argument. Merely stripping the prefix without dropping non-matching paths would reintroduce the exact false-positive-block failure this task exists to remove, just relocated to files outside the hub subtree instead of inside it — scope violations are about catching untracked drift within *this task's* project directory, not anywhere in the whole git repo.
- Rejected: Changing `status_porcelain` itself to accept a root override (touches a shared low-level helper used elsewhere, higher blast radius); shelling out to `git -C <hub_root> status --porcelain` instead of pygit2 (introduces a second status-reading code path with potentially different quoting/edge-case behavior); treating out-of-hub paths as violations unchanged (the bug this task fixes, just moved).

### compute_scope_violations caller signature

- Decision: All four call sites in `_implementer_common.py` (lines ~1077, ~1175, ~1264, ~1408) pass both `project_root` and `git_root` explicitly. `git_root` is already threaded as a parameter through the enclosing functions in this file (used for `_run_verify_gate`'s `git_root=` kwarg), so no new path resolution needs to be added at these call sites — just pass the existing local `git_root` through. `clean_ephemeral_scope_violations` (`_cleanliness.py:210`) also changes its signature from `(worktree: Path)` to `(hub_root: Path, git_root: Path)`, forwarding both straight into `compute_scope_violations`. Every reference to the renamed `worktree` parameter inside the function body — the file-removal join at line 268 (`worktree / violation` → `hub_root / violation`) and the `_is_go_main_artifact(worktree, violation)` call at line 256 (`_is_go_main_artifact(hub_root, violation)`) — is renamed identically, with no behavior change: `compute_scope_violations` now returns hub-relative paths and `hub_root` was already the value this parameter held at every real call site, and `_is_go_main_artifact` only matches on basename so the rename is purely cosmetic there. The one external caller, `plugins/mill/skills/mill-go/SKILL.md:749` (`_cleanliness.clean_ephemeral_scope_violations(worktree_root)`), is updated to `clean_ephemeral_scope_violations(worktree_root, git_root)` — both `worktree_root` (itself resolved via `_paths.resolve_active_hub(..., git_root=git_root)` at SKILL.md:42, i.e. already the hub root) and `git_root` are already local variables in scope at that point in the SKILL, so no new resolution call is needed there either. The 9 existing CESV test cases in `test-cleanliness.py` (lines ~556-778, `clean_ephemeral_scope_violations(tmp_path)`) are updated to pass `(tmp_path, tmp_path)` — same value for both roots, since those fixtures are flat-layout — preserving their existing assertions unchanged.
- Rationale: Matches CLAUDE.md's path invariant — "helpers with path args must not consult cwd for config" — and keeps `compute_scope_violations` unit-testable with synthetic paths, no real `.millhouse/config.local.yaml` needed. Propagating the signature change to `clean_ephemeral_scope_violations` and its one real caller closes the gap where the rebase would otherwise happen inside `compute_scope_violations` but silently break the caller that joins violation paths back to a filesystem location for deletion.
- Rejected: Having `compute_scope_violations` call `_paths.resolve_hub_path()` / `_paths.resolve_git_root()` internally — couples a low-level cleanliness helper to config/cwd resolution and makes it untestable in isolation. Leaving `clean_ephemeral_scope_violations`'s signature at one arg and re-deriving `git_root` inside it — same coupling problem, one level up.

The fix is copying the already-correct pattern.

### Verify-cwd explicit field (#604)

- Decision: Add an explicit `cwd` field to plan verify steps — both per-batch (batch file frontmatter `verify:`) and module-wide (overview file frontmatter `verify:`) — accepted values `hub` or `git_root`, defaulting to `git_root` when absent (preserves every existing plan's behavior and the #554-pinned unit test in `test-implementer-common.py` unchanged). The `verify:` frontmatter value becomes either a plain string (implicit `cwd: git_root`, today's format, unchanged) or a `{cwd: ..., command: ...}` mapping.
  - `millpy-implement.py` is the actual read site: `batch_frontmatter.get("verify")` (lines ~371, ~591) and `overview_frontmatter.get("verify")` (line ~311) both currently assume a bare string. A shared helper (e.g. `_plan_dag.parse_verify_field(frontmatter, hub_root, git_root) -> tuple[str | None, Path | None]`) normalizes both forms, returning the command string and a resolved `cwd` Path (`None` for the string form, meaning "use the existing default"; `hub_root` or `git_root` resolved from the mapping form otherwise). When `verify` is absent, `None`, or an empty/whitespace-only string, `parse_verify_field` returns `(None, None)` — matching `_plan_dag.py:320`'s existing `isinstance(verify, str) and verify.strip()` guard in `iter_batch_verifies`, so pure-docs batches keep being skipped unambiguously. All three call sites use this helper before passing `verify_cmd` onward. Malformed input fails loud: an unrecognized `cwd` value (anything other than `hub`/`git_root`) or a mapping missing the `command` key raises `ValueError` from `parse_verify_field` itself, with no silent default — `millpy-implement.py`'s call sites let this propagate as an uncaught exception (surfacing as a `stuck_type: logic`-shaped failure via the same top-level error handling that already wraps the finalize/full stage entry points), since a malformed plan file is an authoring bug that should be visible immediately, not silently coerced to some fallback.
  - `_plan_validate.py`'s `_check_verify_not_isolated` / `_check_verify_full_suite` currently iterate `batch_files` only, so an overview-level `verify` (module-wide) is never validated for the `PYTHONPATH=` prefix or the `run-all.py` filter rule — pre-existing for the string form, but the new mapping form widens the surface (a malformed overview mapping would previously have just been ignored; now it's actually executed). Both validators are extended to also check the overview frontmatter's extracted `command` alongside the existing per-batch loop, using the same `parse_verify_field` extraction (with validation errors surfacing as their own `_plan_validate` finding, not a raised exception, matching how the rest of `_plan_validate.py` reports problems as findings rather than raising).
  - `millpy-fix.py` has two more read sites that also need `parse_verify_field`: batch-scope fixes read `batch_frontmatter.get("verify")` directly (lines ~239, ~284); holistic-scope fixes call `_plan_dag.iter_batch_verifies(plan_base)` and join every batch's verify string with `" && ".join(...)` (line ~244) before passing the result through `finalize_from_output` -> `_run_verify_gate` with `git_root=` but no cwd control today. `iter_batch_verifies` itself is updated to yield the extracted `(name, command, cwd)` per batch (via `parse_verify_field`) instead of a bare string, and holistic-scope joining requires **all contributing batches to resolve to the same cwd** — mixed `cwd` values across batches joined into one shell command cannot be satisfied by a single subprocess cwd, so this is a plan-authoring error rather than a runtime coercion. `_plan_validate.py` gains a new check (alongside the existing per-batch checks) that flags a plan where `iter_batch_verifies` would resolve to mixed cwd values, so the conflict is caught at plan-review time, not fixer runtime. Both batch-scope and holistic-scope call sites thread the resolved cwd through as `cwd_override`, same as `millpy-implement.py`.
  - `_verify_baseline.compute_baseline(project_root, git_root, ...)` runs the module-wide verify command inside a **separate temporary git worktree** (`tmp_path`, created via `git -C <git_root> worktree add <tmp_path> <parent_sha>`) rather than the real `project_root`/`git_root`, via `_run_verify_in(module_wide_verify_cmd, tmp_path)`. Because `tmp_path` is a fresh checkout rooted at the equivalent of `git_root`, a nested-layout hub-relative command must run at `tmp_path / <hub-relative-prefix>` in this context — **not** `hub_root` itself, which belongs to the real worktree, not the temp one. `compute_baseline` gains a `cwd_override_relative: Path | None` parameter (the hub-relative prefix, when the module-wide verify resolved to `cwd: hub`; `None` for the `git_root` default) and `_run_verify_in` is called with `tmp_path / cwd_override_relative` when set, `tmp_path` otherwise — preserving today's behavior when the field is absent. `parse_verify_field` itself returns a resolved absolute `cwd` Path (`hub_root` or `git_root`), not a relative prefix; the baseline call site is the one that derives `cwd_override_relative` by computing `hub_root.relative_to(git_root)` when the resolved `cwd` is `hub_root` (empty/`.` when they're equal, i.e. flat layout), and passing `None` when the resolved `cwd` is `git_root`. `parse_verify_field` is not re-resolved or called a second time for this — the baseline caller does the absolute-to-relative conversion itself from the one resolution.
  - `plugins/mill/skills/mill-merge-in/SKILL.md` step 4 ("Verify", lines ~75-87) is a third replay site: it calls `_plan_dag.iter_batch_verifies(plan_dir)` (line ~77, currently documented as yielding `(batch_name, verify_cmd)` pairs) and, for each `(name, cmd)`, "run[s] the command from the worktree root" (line ~84) with no per-batch cwd distinction — reproducing #604 in the merge-in verify-replay path for any batch whose verify resolves to `cwd: hub`. This step is updated to unpack the new `(name, command, cwd)` 3-tuple and run each command at its resolved `cwd` (`hub_root` or `git_root`, both already resolvable in this SKILL's scope) instead of a single fixed "worktree root"; the existing `${PLUGIN_ROOT}` substitution and `skip_list` allowlist pre-check (lines ~81-83) are unaffected since they operate on the extracted `cmd` string either way.
  - `_run_verify_gate` in `_implementer_common.py` gains a `cwd_override: Path | None = None` kwarg (in addition to its existing `git_root` kwarg). When `cwd_override` is not None, it takes precedence over the existing `git_root if git_root is not None else project_root` fallback. `millpy-implement.py` passes the resolved cwd from the helper above as `cwd_override` for both the per-batch and module-wide verify gate calls.
  - `_plan_validate.py`'s `_check_verify_not_isolated` / `_check_verify_full_suite` are updated to accept `verify` as either a plain string or the `{cwd, command}` mapping, extracting `command` either way before applying their existing string checks (PYTHONPATH-prefix check, run-all.py filter check).
  - The mill-plan skill/template is updated so that when authoring a plan for a task where `_paths.resolve_hub_path() != _paths.resolve_git_root()` (nested layout), it sets `cwd: hub` (per-batch and module-wide, as applicable) and writes the verify command hub-relative. CLAUDE.md's PYTHONPATH auto-prepend rule (mill-plan auto-prepends `PYTHONPATH=` on `verify-not-isolated` validator failure) operates on the extracted `command` string, not the raw frontmatter value, so it works unchanged against either form.
- Rationale: #554 and #604 are mirror-image bugs from two different nested-layout repos with opposite verify-command authoring conventions (git-root-relative vs hub-relative) — there is no single default cwd that satisfies both. A heuristic ("nested layout → always cwd=hub_root") would silently reintroduce #554 for any nested-layout plan that intentionally wants git-root-relative commands. An explicit per-plan field is the only option that fixes #604 without regressing #554's pinned test. Extending the field to module-wide verify too (not just per-batch) avoids leaving a partial fix that still reproduces #604 for any repo whose *overview*-level verify command is hub-relative. Fixing all verify-command read sites (`millpy-implement.py`, `millpy-fix.py`, `_verify_baseline.py`) rather than just the implementer path avoids leaving #604 half-fixed for the fixer and baseline flows, which share the same plan schema and would otherwise silently misbehave (a dict reaching a subprocess call, or a baseline check running at the wrong path and mis-caching "clean").
- Rejected: Heuristic auto-detect based solely on `hub_root != git_root` (reintroduces #554's failure mode for nested-layout plans authored git-root-relative); leaving `cwd=git_root` permanent and treating #604 as a plan-authoring error only (leaves the filed bug unresolved with no code fix); scoping the field to per-batch verify only (leaves module-wide verify exposed to the same bug class); scoping the fix to `millpy-implement.py` only (leaves `millpy-fix.py`, baseline computation, and `mill-merge-in`'s verify replay exposed to the same class of bug, including a hard crash on the fixer's holistic-join path once `verify` can be a dict, and a silent #604 reproduction on every merge-in that replays a hub-relative verify).
