## Problem

Two unrelated diagnosability gaps surfaced during real mill runs, filed as GitHub issues #772 and #770, both closed and folded into this task.

**Gap 1 (#772):** `_plan_validate.py`'s `_check_context_completeness` flags a card's `Requirements:` prose when it backtick-references a file absent from that card's own `Context:`/`Edits:`/`Creates:`/`Deletes:`/`Moves:`. The scan works per-line via `backtick_re.findall(line)` (`_plan_validate.py:1536-1537`), with no state carried across lines — a true multi-line-split backtick pair (an opening backtick with no closing backtick on the same line) simply yields zero matches on each of the two lines involved; it cannot mis-pair across a line boundary. The actual false-positive mechanism is narrower and entirely single-line: a `Requirements:` line containing an ODD number of backtick characters (e.g. from an unrelated adjacent backtick reference, or a stray backtick left behind by a multi-line quote that was only partially closed on that one line) makes `findall`'s greedy left-to-right pairing on that single line group the wrong backtick characters together, incidentally capturing text between backticks that were never intended to delimit a path reference — observed producing a bare `/` flagged as an unresolved reference. The emitted error dict (`{check, batch, card, path, message}`) names the batch and card but not the source line, so tracing a false positive back to the actual malformed line required an ad-hoc one-off script re-running the same regex.

**Gap 2 (#770):** `millpy-implement.py --stage finalize`'s verify-replay runs a batch's own `verify:` command and unconditionally classifies ANY non-zero exit as the batch's own regression (`stuck_type: verify`, then `logic` on retry). Observed case: a batch's two cards were both implemented and committed correctly, but its `verify:` command's test file had 5 pre-existing, unrelated failures (confirmed against a clean `main` checkout) — a sloppy-fixture bug unrelated to the batch's diff. mill-go's one-shot self-resolve-then-block path blocked a fully-correct batch, requiring an out-of-band operator override. The existing `module_verify_baseline` mechanism already solves exactly this class of problem for the overview's single, task-wide module-wide verify command; it has no equivalent for each batch's own (per-batch, differently-scoped) `verify:` command.

Both are diagnosability/false-positive-avoidance fixes to mill's own validation/execution tooling, not user-facing product changes.

## Scope

**In:**
- Add a `line` field (the offending raw `Requirements:` line, `.strip()`ped, verbatim) to every error dict `_check_context_completeness` emits.
- Update `mill-plan/SKILL.md`'s context-completeness fixer-remedy table row to mention the new `line` field.
- Extend the existing baseline mechanism (`_verify_baseline.py`, `_status.py`'s `module_verify_baseline` machinery, `millpy-implement.py --stage baseline`) so that, before batch 1 starts, each batch's own `verify:` command is also snapshotted against the parent branch — not just the overview's module-wide command.
- Store each batch's baseline failure-signature set on its `## Batches` entry in `status.md`.
- At `--stage finalize`, when a batch's `verify:` command fails, diff its failure signatures against that batch's stored baseline; only signatures NOT present in the baseline count toward `stuck_type: verify`/`logic`. A failure set that's a subset of baseline is treated as passing (module-wide gate semantics are unchanged).
- Extract the existing FAIL-marker-prefix line scan (`"--- FAIL:", "FAIL\t", "FAILED ", "--- FAIL ", "FAIL -- "`, currently inline in `_implementer_common.py`'s truncation path) into a shared helper reused by both the truncation logic and the new baseline-diff logic.

**Out:**
- No change to the overview's `module_wide_verify_cmd` baseline semantics or its `"clean"`/`"pre-existing-failures"` binary contract — that mechanism is reused/extended, not replaced.
- No absolute file-line-number computation for gap 1 (raw line text only — see Decisions).
- No changes to `_check_ref_not_backtick_path` or `_check_requirements_quote_indent_drift` — neither scans free-text `Requirements:` prose per-line the way `_check_context_completeness` does, so neither is vulnerable to the malformed-backtick false-positive class this task fixes.
- No new parsing of language-specific test-runner output formats beyond the existing fixed marker-prefix list (no pytest/go-test/dotnet-specific structured parsers).
- No change to the flakiness-guard retry/corroboration behavior of the module-wide baseline path in `_verify_baseline.compute_baseline` (unchanged for `module_wide_verify_cmd`); the new per-batch baseline computation gets its own, simpler corroboration (see Decisions).

## Decisions

### gap1-line-field-not-line-number

- Decision: Add a `line` field carrying the raw offending `Requirements:` line (stripped of leading/trailing whitespace, otherwise verbatim, no length cap) to `_check_context_completeness`'s error dicts. Do not compute an absolute file line number.
- Rationale: The issue explicitly accepts "a line number OR the offending raw line text." The raw line is available for free inside the existing `for line in requirements_lines:` loop (`_plan_validate.py:1536`). Computing an absolute file line number would require `_parse_cards` (`_plan_validate.py:129`) to also track each card's starting line offset — that function's return shape (`list[tuple[int, list[str]]]`) is consumed by 6 other call sites (`_plan_validate.py:758, 850, 884, 1526, 1753, 2585`), so changing it is a much larger, riskier change for no added diagnostic value here (the raw line text already answers "which line").
- Rejected: Absolute line number via `_parse_cards` signature change — too invasive for the value gained.

### gap1-scope-single-check

- Decision: Only `_check_context_completeness` gets the new `line` field.
- Rationale: It is the only check that scans free-form `Requirements:` prose per-line with `backtick_re.findall(line)`, which is the exact mechanism vulnerable to the described malformed-backtick false positive. `_check_ref_not_backtick_path` (`_plan_validate.py:1166`) scans structured `Context:`/`Edits:`/`Creates:` header values, not prose. `_check_requirements_quote_indent_drift` (`_plan_validate.py:1699`) scans fenced code blocks within `Requirements:`, a different extraction path entirely.
- Rejected: Adding `line` to all checks sharing the `{check, batch, card, path, message}` shape — unnecessary; those checks aren't exposed to this false-positive class.

### gap1-no-existing-test-breakage

- Decision: Adding `line` is purely additive to the error dict; no existing test or consumer needs updating.
- Rationale: Confirmed unit tests in `plugins/mill/unit_tests/test-plan-validate.py` (e.g. `test_check_context_completeness_dirty_missing`) assert on individual keys (`e["check"]`, `e["card"]`, `e["path"]`), never full-dict equality. `mill-plan/SKILL.md`'s fixer-remedy table (line 267) references `message`/token content, not the dict's exact key set.
- Rejected: N/A — no rejected alternative; this is a confirmed-safe observation, not a choice.

### gap2-per-batch-baseline-storage

- Decision: Store each batch's baseline failure-signature set as a new field on that batch's entry in `status.md`'s `## Batches` section (e.g. `verify_baseline_failures: [<signature>, ...]`), added to `_status.py`'s `_BATCH_ALLOWED_KEYS` AND to `_serialise_batches`'s hardcoded `order` list (`_status.py:608-617`) — `_serialise_batches` is a hand-rolled writer (NOT `yaml.safe_dump`) that iterates only the keys named in that fixed `order` list, silently omitting any key an entry dict holds that isn't in it; a field added to `_BATCH_ALLOWED_KEYS` alone would round-trip in memory for one call but be silently dropped on every actual write to `status.md`. `_serialise_batches`'s per-key value branch (currently: quoted string, or raw `str(value)` for everything else) also needs a THIRD branch for list values, serialized via `yaml.safe_dump(value, default_flow_style=True).strip()` (reusing the already-imported `yaml` module for correct per-element YAML quoting, e.g. a signature line containing a colon or quote character) rather than Python's `str()`/repr form. An empty list means "clean baseline" (no pre-existing failures for that batch's verify command); a missing/unset field (pre-existing status.md predating this feature, or a batch whose baseline computation failed/was skipped) means "not yet computed" and finalize falls back to today's strict behavior (any failure blocks) — the same fail-safe direction as `module_verify_baseline`'s `None` default.
- Rationale: `## Batches` is a structured, list-of-dicts section (`read_batches` parses it via `yaml.safe_load`) rather than the top block's fragile `task_description:` literal-scalar-adjacent re-serialization risk, but its WRITE path (`_serialise_batches`) is a hand-rolled fixed-key-order emitter, not a generic `yaml.safe_dump` round-trip — the new field must be added to that fixed list explicitly, or it is silently lost. Batch name already 1:1-maps to a single `verify:` command per the plan format, so keying by batch name (not by command string) needs no extra indirection.
- Rejected: A new top-level scalar block keyed by verify-command string, mirroring `module_verify_baseline` — avoided due to the top block's re-serialization fragility and the unneeded command-string-keying indirection. Leaving `_serialise_batches`'s new list value to fall through to the existing raw `str(value)` branch — produces a Python-repr-shaped string (e.g. `['a', 'b']`) that is fragile YAML rather than a properly quoted flow sequence.

### gap2-compute-eagerly-before-batch-1

- Decision: Compute every batch's verify-command baseline eagerly, once, inside the existing `millpy-implement.py --stage baseline` call (already invoked unconditionally by mill-go before batch 1, idempotent, non-blocking on failure) — not lazily on each batch's own first finalize.
- Rationale: Matches the issue's explicit ask ("snapshot each batch's verify-command failure set before batch 1 starts"). `_status.init_batches` (mill-go's `## Prepare` step) already runs before `--stage baseline` is ever invoked, so every batch's `## Batches` entry exists to write the new field onto.
- Rejected: Lazy per-batch computation on first finalize — would run each batch's verify command twice (once as an ad-hoc "is this pre-existing" check, once as the real verify-replay) and doesn't match the issue's stated timing.

### gap2-enumerate-batches-directly-not-via-iter-batch-verifies

- Decision: Enumerate batches for baseline purposes by reading every batch file's OWN `verify:` frontmatter field directly (via `_plan_dag._read_batch_frontmatter` + `_plan_dag.parse_verify_field` over `plan_dir.glob("??-*.md")`, excluding `00-overview.md`), not via `_plan_dag.iter_batch_verifies`.
- Rationale: `iter_batch_verifies` (`_plan_dag.py:499`) deliberately drops a batch from its returned list when a strictly-later batch's `Deletes:`/`Moves:` bullets reference a path that batch's own `verify:` command names ("reason 2") — correct for its actual callers (`mill-merge-in`, `millpy-fix.py`'s holistic verify-replay), which replay the DAG-wide surviving-verify set. But a single batch's own `--stage finalize` call is unconditional: it runs THAT batch's `verify:` command regardless of what any later batch will eventually delete, since the deletion hasn't happened yet at that batch's own finalize time. Reusing `iter_batch_verifies` for baseline enumeration would silently skip baseline computation for exactly those batches, permanently falling back to today's strict any-failure-blocks behavior for them — the opposite of what this task is fixing. Reading each batch's own frontmatter directly sidesteps the cross-batch suppression entirely, matching what finalize itself actually does.
- Rejected: `_plan_dag.iter_batch_verifies` — correct for DAG-wide verify replay, wrong scope for per-batch baseline coverage.

### gap2-per-batch-baseline-idempotency

- Decision: On each `--stage baseline` invocation, compute a baseline only for batches whose `## Batches` entry does not yet have a `verify_baseline_failures` field set; batches that already have the field (from a prior run of this same stage, e.g. a resumed/restarted mill-go run) are skipped, mirroring the existing single-scalar `module_verify_baseline` cache-hit check but applied per batch instead of once for the whole task. Per `gap2-baseline-stage-independent-of-module-wide-early-returns` below, this per-batch check is the ONLY gate on per-batch computation — it is never additionally gated by the module-wide command's own presence or cache state.
- Rationale: The existing mechanism's cache check (`millpy-implement.py:126-129`, `get_module_verify_baseline`) is a single "already cached -> skip" gate for one scalar. Extending to N per-batch values needs the same idempotency guarantee at per-batch granularity: a `--stage baseline` re-invocation (e.g. after a crash mid-computation) must not needlessly recompute batches that already succeeded, but must still fill in any that hadn't been reached yet.
- Rejected: Recompute-all on every invocation — defeats the purpose of the idempotent/safe-to-invoke-unconditionally contract this stage already has, and would re-run every batch's (potentially slow) verify command on every resumed run.

### gap2-baseline-stage-independent-of-module-wide-early-returns

- Decision: `_run_baseline_stage` (`millpy-implement.py:78`) restructures into two independent sub-steps that both run on every invocation, in either order: (1) the EXISTING module-wide baseline computation, completely unchanged, including its own two early returns (`module_wide_verify_cmd is None` at line 114, and `get_module_verify_baseline(status_path) is not None` at line 126); and (2) the NEW per-batch baseline computation, gated ONLY by the per-batch `verify_baseline_failures`-already-set idempotency check (`gap2-per-batch-baseline-idempotency`) — never by whether a module-wide verify is configured, and never by whether the module-wide baseline is already cached. The function's single JSON-line-per-call output contract changes to report both sub-steps (e.g. `{"stage": "baseline", "module_wide": {...}, "per_batch": {...}}` or two separate printed JSON lines) rather than one flat dict, since the two sub-steps can now independently reach different outcomes (e.g. module-wide skipped/no-op while per-batch successfully computes three baselines).
- Rationale: `_run_baseline_stage`'s two existing early returns (`millpy-implement.py:114-124` for "no module-wide verify configured," `126-129` for "already cached") both `return 0` before any batch-related work — a naive "extend this function" that appends new per-batch logic AFTER that existing logic, as the word "extend" superficially implies, would mean per-batch baselines are NEVER computed for the (very common — module-wide `verify:` is optional per `plan-overview.md`) case where a task has no module-wide verify configured at all, and would never backfill per-batch baselines on a resumed run where a prior invocation's module-wide computation already succeeded/cached but per-batch computation crashed partway through. Both failure modes directly contradict `gap2-per-batch-baseline-idempotency`'s own stated guarantee that a re-invocation "must still fill in any [batches] that hadn't been reached yet."
- Rejected: Appending per-batch logic strictly after the existing function body unchanged (the naive "extend" reading) — silently disables per-batch baselines for any task without a module-wide verify command, and breaks the stated idempotency guarantee on partial-failure resume.

### gap2-shared-transient-checkout

- Decision: Extend the baseline computation to run the module-wide command AND every distinct batch verify command inside a single shared transient parent-branch worktree checkout (one `git worktree add`/dependency-junction-setup/teardown for the whole `--stage baseline` invocation), rather than one checkout per command.
- Rationale: `_verify_baseline.compute_baseline`'s checkout + junction setup is the expensive part of the mechanism, and `--stage baseline` fires unconditionally on every mill-go run (even resumed ones, where it no-ops on a cache hit, but a fresh task still pays this cost once). Batching every batch's verify command plus the module-wide command into one checkout materially reduces wall-clock cost without changing the semantics of any individual command's result.
- Rejected: One `compute_baseline`-shaped call per distinct verify command (N+1 separate checkouts) — correct but needlessly slow.

### gap2-failure-signature-extraction

- Decision: Extract `_implementer_common.py`'s existing FAIL-marker-prefix line scan (`"--- FAIL:", "FAIL\t", "FAILED ", "--- FAIL ", "FAIL -- "`, `_implementer_common.py:795`, currently used only to build the truncation marker's earlier-failures excerpt) into a shared helper (e.g. `_extract_failure_signatures(output: str) -> list[str]`), applied to the FULL command output (not just the >2000-char truncation path) both at baseline-computation time and at finalize-diff time. The extracted lines ARE the failure signature set (order-independent set comparison). The shared helper itself is UNCAPPED — it returns every matching line in the output, no `[:20]` limit. The existing `[:20]` cap (`_implementer_common.py:797`) is display-only budgeting for the truncation excerpt shown in a stuck reason; that call site keeps applying its own local `[:20]` slice to the helper's full return value for that purpose, but the baseline/finalize signature sets always use the helper's uncapped output — a failure past the 20th FAIL-marker line must still be detectable as a new regression.
- Rationale: This exact marker list already encodes cross-ecosystem failure-line conventions the codebase has already validated (Go's `--- FAIL:`/`FAIL\t`, pytest's `FAILED `, presumably dotnet's `--- FAIL `/`FAIL -- `) — reusing it avoids inventing new per-language parsers and keeps the truncation excerpt and the baseline diff using one consistent notion of "a failure." Capping the shared helper itself (rather than only the truncation call site's local slice) would silently make baseline/finalize signature sets miss failures past line 20, defeating the point of a correctness-critical diff.
- Rejected: Raw full-output byte-diff — too strict; a pre-existing failure whose incidental output (timing, absolute paths) changes between runs would spuriously read as "new." Continuing to use only the binary `"clean"`/`"pre-existing-failures"` verdict for batch-level commands — doesn't give finalize enough information to distinguish "still the same pre-existing failure" from "a new one," which is the whole point of this fix.

### gap2-signature-normalization-strips-duration

- Decision: Before using an extracted FAIL-marker line as a signature for baseline storage or finalize-diff comparison, apply a normalization step that strips a trailing volatile-duration suffix: Go's per-test form `--- FAIL: TestFoo (0.00s)` has its trailing `(<digits>[.<digits>]s)` parenthetical removed, and Go's package-summary form `FAIL\tgithub.com/pkg\t0.123s` has its trailing tab-separated `<digits>[.<digits>]s` field removed (the seconds-only `s` unit is what `_is_benign_windows_cleanup`'s own comments actually attest at `_implementer_common.py:542-546`, e.g. `"(0.00s)"`/`"0.1s"`; also match the `ms` variant defensively even though it isn't attested in that citation, since Go's `testing` package can legitimately emit sub-second durations in either unit). The RAW (unnormalized) line is still what `_extract_failure_signatures` returns and what the truncation excerpt displays to a human (see `gap2-failure-signature-extraction`); normalization is a second, separate step (`_normalize_failure_signature(line: str) -> str`) applied only when building or comparing the baseline/finalize signature SETS, never applied to the human-facing truncation excerpt.
- Rationale: Go's failure-line formats embed a per-run elapsed-time value directly in the line text. Comparing raw lines by exact string equality means a genuinely pre-existing, unchanged Go test failure would almost never produce an identical string between the baseline run and finalize's replay run (different elapsed time each run), causing the subset-diff to spuriously treat it as "new" on every finalize call — defeating the entire point of this fix for any Go-verified batch. pytest's `FAILED ` lines (test node IDs, no embedded timing) and dotnet's `--- FAIL `/`FAIL -- ` lines are unaffected by this specific issue but pass through the same normalization step harmlessly (no matching trailing-duration pattern, so no change).
- Rejected: Comparing raw unnormalized lines — provably broken for Go per the volatile-timing issue above. Stripping ALL trailing whitespace-separated tokens unconditionally (not just duration-shaped ones) — too aggressive, could strip meaningful trailing content from a non-Go marker format.

### gap2-subset-diff-semantics

- Decision: At finalize, a batch's verify-replay failure is waived (does not raise `stuck_type: verify`/`logic`) only when the replay's extracted failure-signature list is NON-EMPTY AND every signature in it is already present in that batch's stored baseline signature set (non-vacuous subset check). Any signature not in the baseline still blocks, even if the baseline set is non-empty. An EMPTY or ABSENT replay `signatures` value is NEVER eligible for waiver and always blocks (propagates `batch_result` unchanged), regardless of what the baseline contains — this covers two distinct real cases that would otherwise both collapse to the same vacuously-true `set().issubset(...)` result: (a) a non-zero exit whose output contains no recognized FAIL-marker line at all (a build/compile error, a crash, a linter failure, or any failure shape the fixed marker list doesn't recognize), and (b) `_run_verify_gate`'s exception-path stuck dict (missing binary, `FileNotFoundError`, etc. — see `gap2-signatures-field-on-stuck-dict`), which has no subprocess output to extract signatures from in the first place.
- Rationale: Issue #770's suggested fix says "a failure that also failed on the pre-task baseline should not, **by itself**, classify the batch as `stuck_type: verify`/`logic`" — the "by itself" wording means other, non-baseline failures in the same run must still block. A binary "skip the whole gate if baseline is non-empty" (mirroring `module_verify_baseline`'s existing behavior) would silently permit a genuine new regression to slip through any batch whose verify command happens to already have one unrelated pre-existing failure. Separately, an empty extracted-signature set is mathematically a subset of ANY set including an empty baseline — without the explicit non-vacuous carve-out, an unrecognized-format failure (or an infrastructure error with no output at all) would be silently waived as "passed" purely because the fixed marker list didn't happen to match its output, which is the opposite of the fail-safe direction this whole feature is meant to establish.
- Rejected: Binary skip-whole-gate-on-non-empty-baseline — too permissive, defeats the purpose of a regression gate. Treating an empty signature list as vacuously waivable — silently masks any failure shape outside the fixed marker list's coverage, including genuine new regressions.

### gap2-signatures-field-on-stuck-dict

- Decision: `_run_verify_gate` (`_implementer_common.py:690`) gains a new `signatures: list[str]` field on the stuck dict it returns from its non-zero-exit-code path (the branch starting at `_implementer_common.py:778`, `stuck_type == "verify"`), populated by the shared `_extract_failure_signatures` helper applied to the FULL (untruncated) `output = result.stdout + result.stderr` before `reason` is computed/truncated. These are the RAW (unnormalized) extracted lines — `reason`'s human-facing truncation excerpt keeps using raw lines unchanged. The SEPARATE `except Exception` path (`_implementer_common.py:810-817` — missing binary, `FileNotFoundError`, etc.) has no subprocess `output` to extract from and does NOT gain a `signatures` field at all; its stuck dict is `{status, stuck_type, reason}` exactly as today, with `signatures` absent. `_run_verify_gates` (`_implementer_common.py:822`), which already receives the batch's stored baseline signature list as a new parameter (parallel to the existing `module_verify_baseline` parameter), performs the subset-diff there: it treats a missing or empty `batch_result.get("signatures")` (covering both the exception path and a non-zero exit whose output matched no FAIL-marker line) as NEVER eligible for waiver per `gap2-subset-diff-semantics`'s non-vacuous rule — only when `signatures` is present and non-empty does it apply `_normalize_failure_signature` (see `gap2-signature-normalization-strips-duration`) to it and compare against the stored (already-normalized) baseline list. If the normalized replay set is a non-empty subset of the baseline set, treat the batch-level gate as passed (return `None` from that stage) instead of propagating `batch_result`; otherwise return `batch_result` unchanged (with its original, unnormalized `signatures` field when present, since that field is also read for the human-facing reason) for whatever surfaces it upstream.
- Rationale: `_run_verify_gate` is the only place with access to the raw subprocess output; `_run_verify_gates` is the only place with access to the cached baseline value (mirroring how it already receives and uses `module_verify_baseline`). Splitting responsibilities this way — extraction in the gate, diffing in the gates-plural sequencer — keeps `_run_verify_gate`'s existing single-command contract intact and reuses the exact seam the module-wide baseline already established. The exception path getting no `signatures` field (rather than a defaulted `[]`) makes its ineligibility structurally explicit rather than relying on the same code path that also handles "ran fine, no recognized failure markers" — both still resolve to "never waived" via the same missing/empty check in `_run_verify_gates`, but the exception path's stuck dict shape itself documents that no output was ever available to scan.
- Rejected: Doing the diff inside `_run_verify_gate` itself — that function has no access to per-batch baseline state today (it's a generic single-command runner reused for both batch-level and module-wide commands with different baseline semantics), and threading batch identity into it would conflate two different baseline mechanisms in one function. Defaulting the exception path's `signatures` to `[]` — works under the non-vacuous rule but muddies the exception path's stuck dict shape with a field that never had a real value.

### gap2-baseline-corroboration

- Decision: Per-batch baseline computation runs each distinct verify command in the shared transient checkout, and on any failure, runs it once more (same flakiness-guard shape as the module-wide path) — the STORED baseline signature set is the UNION of both runs' extracted failure signatures (not a single run's set, and not a binary "clean"/"dirty" verdict).
- Rationale: A flaky pre-existing failure that only reproduces on one of two runs still needs to be in the baseline (so it doesn't spuriously block a later batch), but unlike the module-wide path's binary verdict, there's no need for a third "control run in the task worktree" step — finalize's own verify-replay run against the real (in-progress) worktree IS the natural downstream corroboration point: if a signature was flagged as baseline via a fluke, a subsequent finalize run simply won't reproduce it and the batch passes cleanly anyway (the diff only excludes signatures that keep recurring in the baseline set, never PENALIZES an extra one).
- Rejected: Reusing the module-wide path's exact three-run (retry + task-worktree control) sequence per batch command — unnecessary extra subprocess cost per distinct command when the union-of-two-runs approach already prevents a single flaky baseline run from being trusted alone, and finalize's own run is a free additional corroboration point the module-wide binary verdict doesn't have.

## Technical context

**Gap 1:**
- `_plan_validate.py:1471` `_check_context_completeness` — the function to change. The per-line loop is at `_plan_validate.py:1536` (`for line in requirements_lines:`); `line` is already in scope when the error dict is built at `_plan_validate.py:1579`.
- `_plan_validate.py:129` `_parse_cards` — NOT to be changed (see Decisions).
- `plugins/mill/unit_tests/test-plan-validate.py` — existing `test_check_context_completeness_*` tests (17 of them) assert on individual dict keys; add a new assertion on `line` to the relevant dirty-case test(s) (e.g. `test_check_context_completeness_dirty_missing`) rather than rewriting them.
- `plugins/mill/skills/mill-plan/SKILL.md:267` — the context-completeness row in the validator-fixer-remedy table; mention the new `line` field so the autonomous fixer can locate the offending Requirements: line without re-deriving it.

**Gap 2:**
- `plugins/mill/scripts/_verify_baseline.py` — today's module-wide-only baseline computation (`compute_baseline`, single command in, `"clean"|"pre-existing-failures"` out).
