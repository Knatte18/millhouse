## Problem

Five independent, previously-filed-and-consolidated bugs (GitHub issues #734, #727, #724, #733, #731 — all closed with "Consolidated into wiki task: mill-plan-review-validation-gaps") degrade the mill-plan/mill-go review-and-validation pipeline in ways that either produce false-positive validator errors, hard-fail an entire review over informational-only content, silently skip compiling test assertions a batch itself added, or hide a failure from the operator making a stuck-escalation decision. None share a root cause; they are fixed independently in this task. Each was caught in real usage of mill (self-hosted development of the millhouse repo, plus two external projects — loomyard, Models), so each has a concrete reproduction already on file in its source issue.

## Scope

**In:**
- Fix 1 — `plugins/mill/templates/plan-batch.md`: move the `## Cards` field-legend prose inside the template's existing "strip before writing" HTML comment (issue #734).
- Fix 2 — `plugins/mill/skills/mill-plan/SKILL.md`: reword the `non-existent-path` mechanical-fix-table row to state the Creates:-target resolution rule explicitly, and add a "self-run `_plan_validate`" instruction alongside the existing self-validate-DAG instruction (issue #727).
- Fix 3 — `plugins/mill/scripts/_plan_validate.py`: add a new Go-specific validator check, `verify-excludes-edited-tagged-test`, plus its mechanical-fix-table row in `mill-plan/SKILL.md` (issue #724).
- Fix 4 — `plugins/mill/scripts/_review_common.py` (`resolve_ref_paths`) and `plugins/mill/scripts/_review_code.py` (its `prepare()` call site): degrade a missing `Context:`-only reference to a soft warning when the resolved path is git-ignored, instead of hard-failing the whole review (issue #733).
- Fix 5 — `plugins/mill/scripts/_implementer_common.py` (`_run_verify_gate`): enrich the truncated verify-failure `reason` with an omitted-content marker and extracted failure-summary lines (issue #731).
- Unit tests for each fix, added to the existing test files covering the touched modules (no new test files).

**Out:**
- Any change to `_review_common.py`'s `parse_batch_refs`/`parse_moves`/`compute_creates_union`/`compute_deletes_union`/`compute_moves_union` whole-file-scanning behavior. Fix 1 is resolved entirely in the template; scoping these shared scanners to card-blocks-only was considered (see Decisions) and explicitly deferred — it is not needed once the template no longer emits legend prose outside a card block.
- Applying Fix 4's gitignore-soft-fail behavior to `_review_plan.py`'s three `resolve_ref_paths` call sites. The reported bug is specific to `millpy-review-code.py`'s holistic prepare stage; `_review_plan.py` runs pre-implementation when `.scratch/` probe files are much less likely to be referenced yet. The new `resolve_ref_paths` parameter is opt-in and defaults to the old hard-fail behavior everywhere else, so `_review_plan.py` can adopt it later with a one-line change if the same failure mode is ever reported there.
- Legacy Go `// +build integration` build-tag syntax detection in Fix 3 — deprecated since Go 1.17; only the `//go:build` form the issue reports is handled.
- Any change to the 2000-character truncation window size in Fix 5 — the fix adds content ahead of the existing tail, it does not change the tail's size.
- `Edits:`/`Creates:`/`Deletes:` reference resolution in Fix 4 — only `Context:`-only references get the soft-fail path; a missing `Edits:`/`Creates:`/`Deletes:` target remains a hard `ReviewError` (those must exist for the review's diff to be meaningful).

## Decisions

### Fix 1 — template fix over parser-scoping

- Decision: Move `plan-batch.md`'s `## Cards` field-legend bullets (the `- **Context:** ...` / `- **Edits:** ...` / `- **Creates:** ...` / `- **Deletes:** ...` / `- **Moves:** ...` lines, the "Context/Edits/Creates/Deletes/Moves fields contain ONLY backtick-wrapped paths..." paragraph, and the "Note for reviewers: ..." paragraph — currently `plan-batch.md` lines 61-72) inside the template's HTML comment block that currently closes at line 22 (`Strip this HTML comment before writing.\n-->`). The intro sentence at lines 57-60 ("_One `### Card N` per card. ... Fields per card:_") stays with it since it is already italicized planner-guidance prose referring to the legend. The literal `### Card N: <short title>` example block (lines 74-86) stays where it is — it is the one part of `## Cards` a planner is expected to see rendered as a concrete example while authoring, distinct from the field-semantics legend.
- Rationale: The template's own comment already carries structurally identical guidance — the `verify:` command notes at lines 16-20 (non-null prefix requirement, scope guidance, `{cwd, command}` mapping form) are exactly this same category of "planner needs to know this, but it must not land in the rendered file" content, and they are correctly placed inside the comment. The field legend was simply misplaced relative to that existing convention. This is a zero-risk, single-file, moved-lines-only change: it does not touch `_plan_validate.py`'s or `_review_common.py`'s parsing functions, so every existing validator/review behavior for real card content is unaffected. It also transitively helps Fix 4's concern (fewer bogus non-path "references" reaching `resolve_ref_paths` from future plans) without any code change.
- Rejected: Scoping `_plan_validate.py`'s `_parse_edits_only`/`_parse_creates_only`/`_parse_deletes_only`/`_parse_context_only`/`_check_ref_not_backtick_path`/`_check_move_format` AND `_review_common.py`'s `parse_batch_refs`/`parse_moves` (which `_check_non_existent_path`, `compute_creates_union`, `compute_deletes_union`, and `compute_moves_union` all depend on, and which are also shared by `_review_plan.py`/`_review_code.py`'s bulking) to only read inside `### Card N:` blocks. This is the more "root-cause" fix in the abstract (it would guard against ANY future stray prose using the `- **Field:**` syntax outside a card, not just this one known case) and was seriously considered, since `_review_common.py` currently has no card-scoping helper at all (`_plan_validate.py`'s local `_parse_cards` is not shared). It was rejected for this task because: (a) it requires touching parsing primitives shared by three scripts (`_plan_validate.py`, `_review_plan.py`, `_review_code.py`) with no card-scoping precedent in `_review_common.py` to build on, meaningfully raising the risk of an unrelated regression in review bulking; (b) the template fix alone fully resolves the only known trigger; (c) YAGNI — there is no second reported instance of this failure class to justify the larger investment right now.

### Fix 3 — Go integration-tag validator check

- Decision: Add a new check function `_check_verify_excludes_edited_tagged_test` to `plugins/mill/scripts/_plan_validate.py`, registered in `run()` alongside the other checks, using check key `verify-excludes-edited-tagged-test` (the exact name suggested in issue #724). Detection logic, mirroring `_check_verify_not_isolated`'s Python-project-conditional pattern:
  1. One-time Go-project detection: `(project_root / "go.mod").exists()`. Only apply this check when true (fail-open: non-Go projects are never checked, exactly like `verify-not-isolated`'s `is_python_project` gate).
  2. For each batch: collect the batch's `Edits:` ∪ `Creates:` tokens (via the existing `_parse_edits_only`/`_parse_creates_only` helpers) that end in `_test.go`.
  3. For each such test-file token that resolves to an existing file on disk (via `resolve_existing_paths`), read the file and find its first non-blank line. If that line matches `^//go:build` and the constraint expression contains the word `integration`, the file is "integration-tagged."
  4. If the batch has at least one integration-tagged test file among its `Edits:`/`Creates:` targets, parse the batch's `verify:` command (via `_plan_dag.parse_verify_field`, same pattern as `_check_verify_not_isolated`) and check whether it contains a `-tags` flag whose value includes `integration` (e.g. `-tags integration`, `-tags=integration`, or `-tags "integration,other"` — split the flag's value on `,`/whitespace and check for the literal token `integration`).
  5. If the batch has an integration-tagged edited/created test file but the verify command's `-tags` value does not include `integration` (or there is no `-tags` flag at all), emit one `verify-excludes-edited-tagged-test` error naming the batch, the tagged test file, and the missing flag.
  - Add the corresponding mechanical-fix-table row to `mill-plan/SKILL.md`'s step 1.5 table: `verify-excludes-edited-tagged-test | Open the offending batch's verify: command (payload's batch/path fields name the batch and the tagged test file). If a -tags flag already exists, append ,integration to its value; otherwise append " -tags integration" to the command.`
- Rationale: Mechanically checkable with both inputs already on disk at validate time, exactly as the issue states. Reuses the exact conditional-check architecture (`is_python_project` → language-scoped check, silently skipped for other languages) already established by `verify-not-isolated`, so no new architectural pattern is introduced. Registering a fix-table row is required — mill-plan's step 1.5 loop mechanically fixes every validator finding per that table or halts; a check with no row would make the validator gate un-actionable for this finding.
- Rejected: Detecting the legacy `// +build integration` syntax too (see Scope — Out). Rejected as unverified scope creep; the issue's own mechanism description and repro only reference `//go:build`.

### Fix 4 — soft-fail gitignored Context: refs via git check-ignore

- Decision: Add an opt-in keyword parameter to `_review_common.py`'s `resolve_ref_paths`, e.g. `soft_fail_gitignored: bool = False`. When `True` and a candidate path is not found on disk and not in `creates_union`/`deletes_union` (the current hard-fail trigger), before raising `ReviewError`, run `git -C <git_root or project_root> check-ignore -q <candidate>` via `_subprocess_util.run` (same subprocess pattern already used by `_check_verify_unrelated_test_files` in `_plan_validate.py`). If the process exits 0 (path is git-ignored), skip the path (print a one-line warning to stderr, matching the existing `[_review_code] warning: ...` convention already used in `_review_code.py`) instead of raising. On any subprocess error, non-zero/other exit code, or when `git_root`/`project_root` cannot be resolved to a real repo, fall through to the existing hard-fail — the new leniency only activates on a confirmed git-ignore hit; every other outcome preserves current strictness (fail-safe, matching the "never raise from a new gate/check function" convention, applied here as "never silently expand the leniency surface").
  In `_review_code.py`'s `prepare()` (currently lines 271-287), split the single merged `all_raw_refs` (currently built from `parse_batch_refs(bp)` with the default `fields=("Context", "Edits", "Creates", "Deletes")`, across all batch files) into two separate unions: `context_only_refs` (via `parse_batch_refs(bp, fields=("Context",))`) and `other_refs` (via `parse_batch_refs(bp, fields=("Edits", "Creates", "Deletes"))`). Call `resolve_ref_paths` twice — once for `other_refs` with `soft_fail_gitignored` omitted/`False` (unchanged hard-fail behavior, since `Edits:`/`Creates:`/`Deletes:` targets must exist for the review's diff to be meaningful), and once for `context_only_refs` with `soft_fail_gitignored=True`. Merge the two resolved-path lists (dedup, preserving existing order semantics) before building `source_files` as today.
- Rationale: Directly fixes the reported failure mode — a `.scratch/`-rooted `Context:` reference that didn't survive a cross-machine transfer no longer hard-fails the entire holistic review — while using the actual `.gitignore` rules (via `git check-ignore`) rather than a hardcoded directory list, so it generalizes to any conventionally-ignored path (`.scratch/`, `.wiki/`, or a future addition to `.gitignore`) without needing a code change when the ignore rules change. Scoping the leniency to `Context:`-only refs (never `Edits:`/`Creates:`/`Deletes:`) preserves the existing strictness where it actually matters — those fields describe the review's own diff surface and must resolve.
- Rejected: A hardcoded prefix allowlist (`.scratch/`, `.wiki/`). Rejected because it silently drifts from the actual `.gitignore` (CLAUDE.md documents `**/.scratch/` as the real rule, and the wiki has its own separate ignore conventions) and would need a matching code update every time a new gitignored working-state directory is introduced. Also rejected: applying the same soft-fail to `_review_plan.py`'s call sites in this task (see Scope — Out) — kept the change scoped to the reported call site, with the new parameter designed so `_review_plan.py` can opt in later with a one-line change.

### Fix 5 — enrich truncated verify-failure reason

- Decision: In `_implementer_common.py::_run_verify_gate`, replace the current unconditional `output_stripped[-2000:]` truncation with: when `len(output_stripped) > 2000`, take `tail = output_stripped[-2000:]` and `omitted = output_stripped[:-2000]`. Scan `omitted.splitlines()` for lines starting with `--- FAIL:`, `FAIL\t`, or `FAILED ` (Go subtest / Go package-level / pytest failure markers respectively — the three ecosystems this function's existing Windows/dotnet-aware logic already has to reason about in this codebase's usage). Cap the extracted list at a small fixed count (e.g. 20 lines) to bound pathological blowup. Build `reason` as a marker line — `f"[... {len(omitted)} earlier chars omitted"` extended with `f"; earlier failures:\n" + "\n".join(fail_lines)` when `fail_lines` is non-empty, closed with `" ...]\n"` — followed by `tail`. When `len(output_stripped) <= 2000`, `reason` is unchanged (`output_stripped` verbatim, no marker).
- Rationale: Satisfies the issue's "better" bar, not just its "at minimum" bar — the reported repro (an early `internal/reedengine` failure silently dropped behind a later `internal/webstercli` failure) is exactly recovered by the `FAIL\t<package>` line extraction, giving the operator both failing packages' identities even though only one fits in the raw tail. The three patterns chosen are the failure-summary markers a `go test`/`pytest` verify command actually emits — matching what this task's own scope already touches (Fix 3 is Go-specific) and what `_run_verify_gate`'s existing dotnet/Windows-specific branches already treat as ecosystem-aware territory, without requiring a full per-ecosystem plugin architecture.
- Rejected: Marker-only enrichment with no pattern extraction (issue's stated minimum). Rejected because it tells the operator "something is missing" without telling them what — for the stuck_type:verify escalation decision the issue describes, knowing "N chars omitted" alone does not materially help a retry/edit-plan/block decision the way knowing "internal/reedengine also failed" does.

## Technical context

- `_plan_validate.py`'s `run()` (lines 2001-2120) is the single registration point for all validator checks — a new check function is written, then one `errors.extend(_check_...(...))` line is added in `run()`. Every check function follows the same `{check, batch, card, path, message}` error-dict shape (see docstring at the top of the file, lines 13-46, which enumerates every check key — the new `verify-excludes-edited-tagged-test` key must be added there too).
- `_check_verify_not_isolated` (lines 1430-1510) is the closest existing precedent for Fix 3: same project-marker-detection-once pattern, same `_plan_dag.parse_verify_field` frontmatter parsing, same "malformed mapping is `_check_verify_malformed_cwd`'s job, silently skip here" convention on `ValueError`.
- `_plan_dag.parse_verify_field(frontmatter, project_root, project_root)` returns `(command, cwd)` and is the canonical way to extract a batch's actual verify command string from either the plain-string or `{cwd, command}` mapping form — reuse it rather than reading the frontmatter YAML directly.
- `mill-plan/SKILL.md`'s step 1.5 fix table (lines 128-144+) is read by the mill-plan orchestrator to mechanically resolve every validator finding without LLM judgment where possible; every new check key needs a corresponding row or the orchestrator has no defined action for it.
- `resolve_ref_paths` (in `_review_common.py`, lines 820-923) is called from three places: `_review_code.py:283` (the Fix 4 target) and `_review_plan.py:172,383,479,833` (out of scope — see Scope). All four calls currently pass no `soft_fail_gitignored` argument, so adding it as a keyword-only parameter defaulting to `False` is fully backward compatible with the three untouched call sites.
- `_review_code.py`'s `prepare()` function (the whole surrounding block is lines ~200-330) already prints warnings to stderr in the same style Fix 4's new warning should match: `print(f"[_review_code] warning: ...", file=sys.stderr)` (see the existing `start_sha` and `no source files resolved` warnings in the same function).
- `_subprocess_util.run(argv, *, cwd=None, ...)` (in `_subprocess_util.py`, line 79) is the shared subprocess wrapper already used for `git` calls elsewhere in this pipeline (`_check_verify_unrelated_test_files` in `_plan_validate.py` calls `git -C <git_root> diff ...` through it) — Fix 4's `git check-ignore` call should go through the same wrapper for consistency (UTF-8 I/O, spawn/exit breadcrumbs).
- `_run_verify_gate` (in `_implementer_common.py`, lines 682-792) is called from `_run_verify_gates` (lines 795+), which is itself called from multiple places in the implementer flow (grep shows call sites around lines 1478, 1697, 1809, 1920) — the fix is entirely internal to `_run_verify_gate`'s truncation logic and does not change its return-dict shape (`{"status": "stuck", "stuck_type": "verify", "reason": <str>}`), so none of those call sites need to change.
- Unit test files already covering the touched modules, to extend (not create new files): `plugins/mill/unit_tests/test-plan-validate.py` (Fixes 1's regression + Fix 3's new check — the file's own docstring lists check coverage by check-key, follow that convention when adding the new entries), `plugins/mill/unit_tests/test-review-code-flow.py` and/or `test-review-common.py` (Fix 4), `plugins/mill/unit_tests/test-implementer-common.py` (Fix 5). All three follow the repo's tempfile/in-memory fixture convention — no real git, no real LLM (per each file's own docstring and `mill:testing`).
