## Problem

Four independent review/verify quality gaps surfaced during real mill-go runs (loomyard `weft-engine` and `prune-board-tests` tasks) and were filed as GitHub issues #515, #517, #518, #523. Each one cost wasted review rounds or manual cleanup because a rule that mill *describes* in prose is not *enforced* structurally:

1. **#515 — nit-fix pass is skippable.** mill-go's "always fix nits" rule is realized only as a conditional prose branch (`if nit_count > 0` in the per-batch and holistic APPROVE branches). Nothing prevents an orchestrator from skipping the cold-start NIT-only fix pass and still reaching `phase: done`. This happened on weft-engine: a deferred NIT was re-judged BLOCKING a round later, wasting ~3 rounds. Deferred nits are not free — they re-surface as BLOCKING, so fixing them each round is the time-saving move.
2. **#517 — Windows verify false-positive.** `_run_verify_gate` keys purely on the verify subprocess exit code. On Windows, `go test` can exit non-zero from a post-test temp-file cleanup race (`go: unlinkat …\\weft.test.exe: Access is denied`) *even when every package printed `ok`*. The gate misclassifies this as `stuck_type: verify`, which escalates to an operator prompt. The race recurred several times in one task.
3. **#518 — reviewer oscillation + blind fixer compliance.** Holistic reviewers are explicitly forbidden from reading prior reviews ("evaluate fresh each round"), so a settled NIT can be independently re-escalated to BLOCKING with no new information. On weft-engine this drove the fixer to write an in-process test of a detached-spawn path (`spawnPush` launches `os.Executable()`, which under `go test` is the test binary, not `lyx`) — a test physically impossible to pass — and the fixer reported success instead of flagging the contradiction. ~2-3 wasted rounds plus a manual revert.
4. **#523 — stray `coverage.out` / unhandled `scope_violations`.** A `-cover` verify run writes `coverage.out` to the repo root (untracked, outside `_mill/` scope). `millpy-fix` surfaces this in its finalize JSON as `scope_violations`, but no SKILL.md documents any handling, and the Handoff terminal gate uses `--untracked-files=no` so it never catches the artifact. The file required manual removal before merge.

**Why now:** these are accumulated, reproduced lessons from recent autonomous runs; each has a closed source issue with a concrete reproduction. All four fixes live in the mill tooling (`plugins/mill/`), independent of any managed project.

## Decisions

### #517 — Windows verify-success detection (narrow, win32-only)

- **Decision:** In `_run_verify_gate` (`_implementer_common.py`), when the verify subprocess exits non-zero on `win32`, treat it as **success** *only when both* hold: (a) the combined stdout+stderr contains **no test-failure marker** (`FAIL`, `--- FAIL`, `panic:`, `build failed`, `FAILED`), **and** (b) the residual error matches a Windows cleanup-race signature (`unlinkat`, `Access is denied`, or WinError 5/32 on a build/temp path). Factor the signature match into a shared helper `_is_benign_windows_cleanup(output: str) -> bool`. The existing `_is_windows_lock_error(e: Exception)` (`millpy-fix.py:43`) takes an **Exception**, not a string, so unification is not a drop-in substitution: keep `_is_windows_lock_error(e)` as a thin wrapper that stringifies/inspects the exception (`str(e)` plus the `__cause__.winerror` check it does today) and delegates the textual signature match to the shared `_is_benign_windows_cleanup(output)`. Both call the one string-signature matcher; the wrapper retains the structured `winerror` inspection that has no string equivalent. Non-win32 behaviour is unchanged.
- **Rationale:** The cleanup race leaves the *real* test result (`ok`/`PASS`) intact in output; the only failure is go's post-test temp unlink. Requiring "no failure marker" guarantees we can never mask an actually-failing test. Keeping it win32-only avoids changing Linux/CI semantics.
- **Rejected:** Generic cross-platform "all packages ok / no FAIL" parsing — go-test-specific, risks masking failures in pytest/dotnet runners whose output shapes differ. Literal-`unlinkat`-string-only match — too narrow; misses the WinError-32 unlink sibling and `Access is denied` variants.

### #515 — structural nit-fix enforcement (script gate + script-written marker)

- **Decision:** Add `--nits-only` to `millpy-fix.py`. On a successful nit-only pass it (1) appends a `nits-fixed-<scope>` row to `status.md` atomically with its own source commit (scope = `<batch_name>` or `holistic`), and (2) emits `nits_applied: true` in its finalize JSON. Add a new inline helper `_nit_gate.py` exposing a function (e.g. `compute_unfixed_nits(worktree, reviews_dir, status_path) -> list[str]`) that, for each approved scope, reads the **final** review file for that scope, counts `### [NIT]` headings via the existing `_review_common.parse_blocking_count`, and returns scopes whose final review had `nit_count > 0` but lack a matching `nits-fixed-<scope>` row. Note: `parse_blocking_count(raw_text, *, severity)` takes `severity` **keyword-only** (`_review_common.py:1288`), so the gate must call `parse_blocking_count(text, severity="NIT")` — a positional call would `TypeError`. mill-go's Handoff calls this gate via `python -c` (mirroring how `compute_terminal_dirt` is invoked) **before** `phase: done`; a non-empty result **blocks** Handoff with a clear message naming the unfixed scopes. Also strengthen both APPROVE-with-nits branches with a non-skip clause carrying its own rationale ("'non-blocking' does NOT mean optional; deferred nits re-surface as BLOCKING and cost more rounds; only nits a reviewer explicitly marks 'no action required' may be left").
- **Rationale:** The marker is written by the *script* that does the work, not by orchestrator memory — which is exactly what failed in #515. The gate recomputes truth from on-disk artifacts (review files + status timeline), so an orchestrator cannot reach `done` by skipping the pass. Keying on the final review per scope correctly handles REQUEST_CHANGES → … → APPROVE chains (only the APPROVE's nits matter).
- **Rejected:** mill-go writing the marker via `append_phase` after the pass — relies on the orchestrator remembering, the original failure mode. Prose-only strengthening — doesn't make skipping impossible. A standalone `millpy-handoff-gate.py` CLI — heavier than needed; the inline-helper pattern matches the existing terminal-cleanliness gate.

### #518a — reviewer anti-oscillation (curated prior-non-blocking digest)

- **Decision:** mill-go extracts, from the previous round's review file for the **same scope**, each `### [NIT]`/non-blocking finding's heading title + a one-line reason, writes them to a digest file, and passes it to `millpy-review-code.py` via a new `--prior-notes <file>` arg. The backend injects it as a `<PRIOR_NONBLOCKING>` token into the code-review templates. The templates instruct: "These items were judged non-blocking in a prior round. Do NOT escalate any of them to BLOCKING unless NEW information justifies it — a new diff, a real reproducible failure, or a concrete in-repo convention. If you escalate, you MUST state the new information explicitly." Add in-repo-analog anchoring language ("prefer the convention already used by analogous code in the provided files"). The "Do NOT read `reviews/`" ban **stays** — the reviewer sees only the curated digest, never the raw review directory. Round 1 (no prior round) passes an empty digest and the token renders to a neutral "(none)". **`prepare()` MUST set `prompt_kwargs["prior_nonblocking"]` unconditionally** (defaulting to `"(none)"` when `--prior-notes` is absent), because `render_prompt` raises `KeyError` on any unresolved `<TOKEN>` once the templates carry `<PRIOR_NONBLOCKING>` — a missing default would crash round 1.
- **Rationale:** Directly targets the failure: the reviewer had zero memory of round 1's settled judgment. A curated digest gives it just enough anchoring to avoid re-litigating settled non-issues, while the "new information required" clause preserves the ability to legitimately escalate when the code actually changed. Keeping the read-ban prevents prompt bloat and rubber-stamping from full prior-review exposure.
- **Rejected:** Lifting the read-ban for the preceding round — risks the reviewer over-anchoring to the whole prior review (including its blocking calls) and rubber-stamping. Persisting findings into status.md — pollutes the status timeline with review detail and couples two subsystems. Prose-only calibration with no digest — the reviewer still can't see what was settled.

### #518b — fixer must flag unsatisfiable demands (stuck path + structural holistic verify gate)

- **Decision:** Two complementary mechanisms.
  - **Judgement path (brief):** Update `fixer-batch-brief.md` and `fixer-holistic-brief.md` so that if a BLOCKING finding requires a change the fixer can demonstrate **cannot pass** (e.g. an in-process test of a detached-spawn / `os.Executable()` path, or a demand that contradicts an in-repo analog the codebase deliberately follows), the fixer must NOT comply silently — it returns `stuck_type: logic` with the contradiction described, citing the in-repo analog, so a human/orchestrator adjudicates. Strengthen `mill-receiving-review/SKILL.md`'s PUSH BACK/HARM CHECK language to name the "physically unsatisfiable / contradicts in-repo convention" case explicitly.
  - **Structural catch (script):** `millpy-fix.py`'s holistic finalize derives a **concatenated `verify_cmd`** from every batch's `verify:` frontmatter and passes it to the existing `_run_verify_gate` in `_forward_output`. **Join contract:** filter out null/empty `verify:` values *first*, then join the survivors with `&&`; if no batch has a verify command, the derived value is `None` (no gate, matching today). This avoids a dangling `&&` or empty leading segment when a `verify: null` batch sits beside a non-null sibling. Each survivor keeps its own `PYTHONPATH=` prefix (the per-project verify-shape constraint), so the joined form is `PYTHONPATH= <cmd1> && PYTHONPATH= <cmd2>` — each prefix scopes only its own command. A fixer-written failing or timing-out test then demotes a self-reported `success` to `stuck_type: verify` **automatically** — no reliance on the LLM honouring the brief. This reverses the earlier "no holistic `verify_cmd`" stance: holistic now gets the same script-side gate the per-batch path already has.
- **Rationale:** #518's exact failure was a knowingly-failing test reported as success on the holistic path, where `verify_cmd=None` meant no automated catch. A derived gate closes that hole structurally — the same lesson #515 encodes for nits ("enforce with a gate, not prose"). The brief judgement path still helps the fixer bail out *before* writing a doomed test (and cites the in-repo analog), but it is now backstopped by the gate rather than being the sole defence. Concatenating batch verify commands is safe because the holistic brief already instructs the agent to run each batch's verify from the project root; the script merely re-runs them as the authoritative check.
- **Rejected:** A full regression-diff *baseline* harness (capture pre-fix pass/fail, re-run post-fix, diff which specific test newly failed) — heavier plumbing for marginal benefit; the derived single-pass gate already catches a self-induced failure. If a batch has `verify: null`, that batch contributes nothing to the concatenation (no gate for it), matching today's per-batch behaviour.

### #523 — scope_violations handling (surface + allowlist auto-clean + extended terminal gate)

- **Decision:** Extend the Handoff terminal cleanliness gate so it *also* runs `_cleanliness.compute_scope_violations(worktree)`. Known-ephemeral build artifacts on a conservative allowlist — `coverage.out`, `*.test`, `*.test.exe`, `*.prof`, `*.cover` — are **auto-removed**; any out-of-scope untracked file **not** on the allowlist **blocks** Handoff with a message listing the offenders. Document in mill-go's per-batch and holistic fix paths that a `scope_violations` field in the fixer envelope is read and surfaced. Prevention: add a one-line, **non-enforced** note in `mill-plan` guidance suggesting `-cover` verify commands write to `-coverprofile=.scratch/coverage.out`.
- **Rationale:** The allowlist removes the exact recurring artifact (`coverage.out`) with zero manual work while refusing to delete anything that could be legitimate untracked WIP — the safe middle between "always manual" and "delete everything". Extending the *terminal* gate catches the artifact regardless of which path (implement/per-batch-fix/holistic-fix) produced it.
- **Rejected:** Auto-cleaning *all* out-of-scope untracked files — risks deleting real work. Surface-and-block only — still forces manual cleanup of a known-ephemeral file. Enforced verify-command rewriting in the plan validator — too invasive for a guideline.

## Constraints

No `CONSTRAINTS.md` at the hub root. Constraints carried from `CLAUDE.md` and mill conventions relevant to this task:

- **ASCII-only stdout** in all `print()`/`_log()` output — replace `—`/`->` with ` -- `/` -> ` (Windows cp1252 crashes on non-ASCII). New gate/marker messages must obey this.
- **Verify-command shape:** plan `verify:` commands for this Python project MUST start with `PYTHONPATH=` (literal empty value) so test subprocesses load worktree code, not the cache. Enforced by `_plan_validate.py`'s `verify-not-isolated`.
- **Script invocation** uses the cache form: `PYTHONPATH="${CLAUDE_PLUGIN_ROOT}/scripts" "$MILL_PYTHON" "${CLAUDE_PLUGIN_ROOT}/scripts/millpy-X.py"`. Tests use `uv run --project plugins/mill`.
- **Generated markdown** (status rows, review files) uses fenced ` ```yaml ` metadata, never `---` frontmatter.
- **All path resolution through `_paths.py`**; never pass junctions (`.wiki`, `.active`, `.portals`) to a helper. The new `_nit_gate.py` and the terminal-gate extension resolve real paths only.
- Win32-only behaviour must be gated on `sys.platform == "win32"` (or `os.name == "nt"`) so Linux/CI verify semantics are unchanged.
- Reviewer read-ban on `reviews/` is preserved; new context reaches the reviewer only through the curated `<PRIOR_NONBLOCKING>` digest.
