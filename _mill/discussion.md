## Problem

Twelve independent reliability/correctness bugs were filed against mill's own `mill-go`/`mill-merge-in` orchestration machinery while running real tasks against other repos (loomyard, NORCE-DrillingAndWells/Models). None share a root cause; they are grouped only because they were discovered incidentally during other work and are individually small. Each is closed on GitHub and folded into this backlog task (source issues: #1104, #1091, #1090, #1089, #1069, #1068, #1065, #1061, #1060, #1059, #1057, #1047). This discussion covers all twelve; each gets its own Decision below.

This task explicitly depends on `mill-infra-reliability-misc-r2`'s resolution of its own #1102 item (the eager per-batch baseline pre-flight), since that shapes this task's #1089 (slow rebuild) and #1060 (go-vet baseline gap). `mill-infra-reliability-misc-r2` has already merged to `main` (commits `18d3eebb`..`3e600c24`). Its landed `discussion.md` (`git show 3e600c24:_mill/discussion.md` on `main`) resolved #1102 as **lazy, on-demand** per-batch baseline computation, not the issue's "halt on red parent" primary proposal: the eager "0.5 Baseline pre-flight"/"0.6 Per-batch baseline recapture" steps are gone; a `baseline_parent_sha` is pinned once at task start; a batch's own `verify_baseline_failures` is computed on demand, via `_verify_baseline.compute_batch_baseline_on_demand`, only the first time that batch's own verify gate actually fails with no cached baseline yet, from inside `_implementer_common._run_verify_gates`. This is already live in the current worktree's code (confirmed by reading `_verify_baseline.py` and `_implementer_common._run_verify_gates` directly) — it is not something this task needs to build, only to build on.

## Decisions

### fixer-incomplete-recovery-ancestor-check (#1104)

- Decision: do not extend the `incomplete` classification (issue's option (a)) to the fixer role — that classification is card-based (`_batch_completeness_stuck`/`_reclassify_verify_failure`, gated on `card_ids`), and the fixer has no cards. Instead implement option (b): when `_forward_output` (in `_implementer_common.py`) parses a well-formed self-reported `{"status":"stuck","stuck_type":"logic",...}` JSON, and `card_ids` is `None` (the fixer/merge-in signature — confirmed both callers never pass `card_ids`) and `start_sha` is set, run the same ancestor/clean-tree inference the "no structured report" fallback paths already run for a different trigger (lines ~2165–2385 of `_implementer_common.py`: `_content_commit_count(project_root, start_sha) > 0` plus a clean `git status --porcelain`, then `_run_verify_gates`) before accepting the self-report verbatim. If that inference says "already complete and verify passes," override to `{"status": "success", "commit_sha": <head>, "inferred": true}` instead of emitting the self-reported `logic` stuck.
- Rationale: this is exactly the manual check the Builder performed by hand in the observed incident (`git merge-base --is-ancestor`, `git status --porcelain`) after a crashed-then-retried fixer dispatch; mechanizing it removes the manual step without inventing a new classification. Scoping the guard to `card_ids is None` naturally limits the new check to fixer/merge-in dispatches and leaves the implementer's own self-report handling (which already has richer card-based gates) untouched.
- Rejected: option (a) (full `incomplete` classification for fixer) — bigger surface (a new warm-`SendMessage`/`--resume-incomplete`-equivalent path for a role with no card concept to resume against), and the issue's own incident shows option (b) is sufficient for the observed failure mode.

### merge-in-skip-attribution-topo-order-dict-mismatch (#1091)

- Decision: `mill-merge-in/SKILL.md` step 4's skip-attribution paragraph must mirror the exact pattern `_plan_dag.iter_batch_verifies` already uses internally (`_plan_dag.py` lines 618–631): call `batches = extract_batch_index(overview_text)`, `order = topo_order(batches)` (a `list[str]` of names), build `file_by_name = {entry["name"]: entry.get("file") for entry in batches}`, then for each `name` in `order`, resolve `batch_path = plan_dir / file_by_name[name]` and call `_read_batch_frontmatter(batch_path)` — never index a `topo_order()` element as a dict.
- Rationale: `topo_order()`'s own docstring and return-type annotation (`-> list[str]`) confirm it returns batch-name strings, not dicts; the existing `iter_batch_verifies` function is the working reference implementation of the exact recompute this SKILL step is trying to describe, so the fix is citing that pattern precisely rather than inventing new plumbing.
- Rejected: none — this is a documentation-accuracy fix with one clearly correct answer, confirmed by reading both functions' actual signatures.

### taskoutput-unavailable-fallback (#1090)

- Decision: in `mill-go-base/SKILL.md`, both the implementer's step 3(b) probe and the reviewer/fixer step 3(c) probe already document "if the probe call itself errors: proceed to [the terminal/no-longer-running] branch exactly as documented" as an existing fallback. Add one sentence to both sites making explicit that "the probe call itself errors" includes the case where `TaskOutput` is not a callable tool in this host at all (confirmed via `ToolSearch("select:TaskOutput")` returning no match, or an immediate "unknown tool" failure) — that case routes identically to a runtime probe error, i.e. straight to "no longer running."
- Rationale: this session's own environment is a live confirmation of the gap — `TaskOutput` is absent from this session's deferred-tool listing exactly as the issue describes. Treating "tool doesn't exist" the same as "tool call failed" is the safe direction already established by every other fail-toward-strict convention in this codebase: the branch it falls through to (finalize's real git-state inspection) is what actually adjudicates success/failure, so skipping an unavailable liveness optimization never fabricates a false success.
- Rejected: inventing a replacement liveness-check mechanism — no such capability exists in a Claude Code session, and the existing "no longer running" branch is already safe to take when the probe can't run.

### baseline-preflight-lazy-already-landed (#1089)

- Decision: no orchestration change needed for the 25-minute-upfront-cost complaint — it is architecturally eliminated by `mill-infra-reliability-misc-r2`'s already-landed lazy on-demand baseline (see Problem section). Add one incremental improvement in scope here: in `_implementer_common._run_verify_gates`'s on-demand-compute prelude (around line 1171, guarded by `not batch_verify_baseline and replay_signatures and status_path is not None and verify_cmd is not None`), print one ASCII progress line to stdout (e.g. `[baseline] computing on-demand baseline for {batch_name}...`) immediately before calling `_verify_baseline.compute_batch_baseline_on_demand`, so the rare case where this on-demand computation actually fires and takes a while is attributable in the `[mill-bg]` log rather than reading as a generic `HEARTBEAT`.
- Rationale: the issue's first suggestion (reuse a warm build/restore across batches) is exactly what "make it lazy" already achieves for the common case (most batches never fail, so most tasks now pay zero per-batch baseline cost instead of paying it for every batch up front). The issue's second suggestion (a progress line) still has a narrow, real target: the on-demand path can still take as long as a full verify run when it does fire, and currently emits no attributable log line of its own.
- Rejected: building a per-batch progress-tracking mechanism (e.g. "batch 3/8") — that made sense for the old eager pre-flight, which iterated every batch up front; the lazy path only ever computes one batch's baseline at a time, on demand, so there is no "N of M" to report.

### build-tag-tier-coverage-check (#1069)

- Decision: add a new `_plan_validate.py` check, `_check_verify_untested_tag_in_touched_package`, registered alongside the existing Go-specific checks (same `validate()` call site as `_check_verify_excludes_edited_tagged_test`, `_plan_validate.py` line ~4533). Gated the same way (`(project_root / "go.mod").exists()`, fail-open otherwise). For each package directory touched by any batch's `Edits:`/`Creates:` tokens, scan every `_test.go` file in that directory (not just ones a batch's `Edits:`/`Creates:` names — the gap is specifically an *untouched* co-located test file) via the existing `_go_file_custom_tags`, and check whether the union of every batch's `verify:` command's `-tags` flags (via the existing `_verify_command_has_any_tag`, evaluated per-package across every batch's normalized `verify:` command, not just the touching batch's own) ever includes that file's tag when run against that package. Report one finding per (package, untested tag) pair.
- Rationale: the existing `_check_verify_excludes_edited_tagged_test` (confirmed by reading it) only fires when a batch itself *edits* a custom-tagged test file — it does not, and by its own docstring's design was never meant to, cover an untouched sibling test file in a package some batch's non-test changes touch. #1069's incident (`internal/reedcli`'s untouched `cli_integration_test.go`) is exactly this gap. Reusing the sibling check's own primitives (`_go_file_custom_tags`, `_verify_command_has_any_tag`, the `go.mod` gate) keeps the new check consistent with established plan-validate conventions rather than inventing a parallel mechanism.
- Rejected: a runtime (execute every tag combination) check — the issue's own suggestion, and this decision, are both static/diff-based (comparing declared tags against declared verify commands), matching every sibling check in this file; a runtime sweep would reintroduce exactly the "full rebuild per check" cost #1089 just eliminated elsewhere.

### verify-subprocess-terminal-geometry (#1068)

- Decision: `millpy-merge-in-subagent.py`'s `verify-fix` mode subprocess invocations (both call sites, `_run_verify_fix` and the `--stage finalize --mode verify-fix` early-exit branch) currently call `subprocess.run(...)` with no explicit `env=`, inheriting whatever environment the orchestrating Python process has. Pass an explicit environment that starts from `os.environ` and sets `COLUMNS`/`LINES` to a generous fixed value (e.g. `"220"`/`"50"`) only when either is absent or smaller than that floor, so a tmux server started inside this subprocess tree gets a deterministic, adequately-sized default session regardless of whether the orchestrating process itself has a controlling terminal.
- Rationale: the reporter's own investigation ruled out a tty-vs-pipe difference (the "direct shell" control run still passed 4/4 with stdin from `/dev/null` and stdout piped through `cat`) but left terminal-geometry (the "no space for new pane" symptom, `COLUMNS`/`LINES`, tmux's `default-size`) explicitly as the one unconfirmed but plausible theory, and could not root-cause further without live tracing access this discussion doesn't have either. Setting a generous explicit size is a safe, no-op-when-irrelevant mitigation for exactly that theory's symptom, costs nothing for verify commands that don't touch tmux, and requires no invasive change to `_run_verify_gate`'s shared code path (scoped to merge-in's own subprocess calls, not the implementer/fixer per-batch verify gate, since the flake was only observed through merge-in's replay).
- Rejected: leaving it unfixed on the grounds that root cause is unconfirmed — per this task's brief, a genuinely open design decision gets the most defensible call, not a deferral, when a safe, targeted mitigation for the reporter's own leading theory exists.

### conflict-brief-rename-chain-intent (#1065)

- Decision: two changes to `millpy-merge-in-subagent.py`'s `_collect_task_intent` and `plugins/mill/templates/merge-in-conflict-brief.md`: (1) widen the plan-file bullet-extraction regex from `^-\s*\*\*(Edits|Creates|Deletes):\*\*` to `^-\s*\*\*(Edits|Creates|Deletes|Moves):\*\*` (`millpy-merge-in-subagent.py` line ~93) so a batch's `Moves:` (rename) declarations reach `<TASK_INTENT>` exactly like `Deletes:` already does. (2) Add a new instruction step to `merge-in-conflict-brief.md`, adjacent to the existing step 6 (`Deletes:` special-case), telling the resolver: when Task intent lists a file under a batch's `Moves:` (old path → new path), and a conflict lands on the OLD path, check whether the parent's incoming change to the old path is actually a feature addition that belongs on the NEW path instead (the old path's identity moved) before accepting a resolution that discards it — when uncertain, keep the parent's addition and report it via `discarded` rather than silently dropping it.
- Rationale: reading `_collect_task_intent`'s regex directly confirms `Moves:` is never extracted today (only `Edits|Creates|Deletes`) — the resolver in the observed incident had no way to know about the `run.go`→`start.go`, `drive.go`→`run.go` rename chain at all. The step-6-adjacent brief addition targets the specific "conflicted file's current identity has diverged from its git history" pattern #1065 names, without requiring the resolver to reconstruct a rename graph from raw git history itself.
- Rejected: fully automating rename-chain detection in `millpy-merge-in-subagent.py` (walking git history to trace a file's pre-rename identity programmatically) — a much larger change for a judgment call (does incoming content belong on the renamed sibling) that a sufficiently capable model, now given the `Moves:` declaration, is positioned to make directly; see also the tier-bump decision below, which independently raises the bar on that judgment.

### self-resolve-finalize-full-history-fallback (#1061)

- Decision: extend `_content_commit_count`'s consumers, specifically the completeness recount finalize performs after a self-resolve re-fire, with a full-batch-history fallback: when the SHA-range recount (commits between the current recorded `start_sha` and `HEAD`) finds zero content commits for a batch whose self-resolve just fired, before classifying as `stuck_type: logic` ("no content commit"), check whether every one of the batch's own declared cards' `Commit:` field text (parsed from the batch file, as already done elsewhere for `commit_none_card_ids`) already appears somewhere in `git log` for the full branch history (not scoped to any `start_sha` window). If every card's commit message is found, treat the batch as already complete (`status: success`) instead of `stuck_type: logic`.
- Rationale: confirmed by reading `millpy-implement.py`'s `_prepare_reuse_entry` logic (added 2026-09-04, already self-resolve-aware) that the first re-fire after a `self-resolved-verify-logic` marker is *deliberately* fresh-minted (a new `start_sha`) exactly once, by design, to distinguish a self-resolve re-fire from a stale reused session — this is not a bug to reverse. The residual gap #1061 hit is narrower: when the batch's cards were ALL already committed before that fresh mint, the fresh `start_sha` postdates every real content commit, so the SHA-range recount alone can never find them. A full-history fallback closes exactly that gap without touching the deliberate one-remint bookkeeping in `millpy-implement.py`, which the code's own dense commentary (referencing #625/#635/#643/#574) marks as fragile and already correctly scoped to a different problem.
- Rejected: option (a) verbatim (skip the `start_sha` reset entirely on self-resolve re-fire) — this is what `_prepare_reuse_entry` deliberately does NOT do on the first re-fire, and its own comments explain why (cannot yet distinguish a self-resolve re-fire from a stale transient-retry reuse without the one-remint bound); reversing that risks reintroducing whatever bug the one-remint design was added to fix.

### baseline-signature-extraction-non-test-failure (#1060)

- Decision: extend `_implementer_common._extract_failure_signatures` (or its caller) so that when a verify command's overall exit code is non-zero but the output contains zero lines matching `_FAILURE_MARKER_PREFIXES`, the function synthesizes one opaque signature line representing the whole-command failure (e.g. a fixed-prefix line embedding the command's exit code and the first non-empty line of output), instead of returning `[]`. This applies uniformly everywhere `_extract_failure_signatures` is called: the on-demand batch baseline computation (`_verify_baseline._signatures_for_pair`) and the live batch verify replay (`_run_verify_gate`) both call it, so both sides of the subset-diff comparison in `_run_verify_gates` gain a comparable, non-empty signature for a `go vet`-shaped failure (or any other non-zero exit with no recognized FAIL-format lines).
- Rationale: confirmed by reading `_FAILURE_MARKER_PREFIXES` (`"--- FAIL:", "FAIL\t", "FAILED ", "--- FAIL ", "FAIL -- "`) that none of these match `go vet`'s diagnostic output shape (`# package\n./file.go:N:M: message`), so a `verify:` command chaining `go vet ... && go test ...` produces `replay_signatures == []` whenever `go vet` itself fails before any test ever runs. Tracing `_run_verify_gates`'s on-demand-compute guard (`not batch_verify_baseline and replay_signatures and ...`) confirms this empty-signatures case never even triggers on-demand computation, and the later `if batch_verify_baseline and replay_signatures:` waiver block is likewise never entered — so today, a `go vet`-shaped failure can never be waived as pre-existing at any point in this pipeline, always blocking regardless of whether the parent branch was already broken the same way. A synthetic signature (deterministic for a given file:line:message, since `go vet` output carries no volatile timestamp) lets the existing subset-diff waiver machinery work for this failure shape exactly as it already does for test-format failures.
- Rejected: adding `go vet`-specific parsing (matching its `file:line:col: message` shape directly) as a fourth recognized format alongside the four test-runner shapes — a generic "no recognized format but non-zero exit" fallback covers `go vet` and any other non-test command failure (lint tools, `go build` itself) with one change instead of an open-ended list of per-tool parsers.

### merge-conflicts-tier-bump-and-roadmap-dedup-check (#1059 / #1047)

- Decision: (1) raise `plugins/mill/templates/mill-config.yaml`'s `merge.model` default from `haiku` to a stronger tier (`sonnet`) for `conflicts` mode specifically — since `millpy-merge-in-subagent.py` currently uses the same `cfg.get("merge", {}).get("model")` value for both `conflicts` and `verify-fix` modes, split them: keep `verify-fix`'s default at `haiku` (a mechanical pass/fail check against a test command needs no semantic judgment) and introduce `merge.conflicts_model` (falling back to `merge.model` when absent, for config backward-compatibility) read only by `_run_conflicts`. (2) Add one sentence to `merge-in-conflict-brief.md`'s existing step 3/4 combine-guidance: before accepting a roadmap-shaped Planned/Done (or similarly staged/shipped) split as correct, explicitly check whether the item is ALREADY represented under the other status further down the SAME resolved file — not just within the immediate conflict hunk — since the losing side's move may already be reflected outside the hunk boundary.
- Rationale: three separate incidents in this backlog — #1059 (missed a genuinely unmatched marker, though only reachable when the subagent's own report parses as success, which #1104's ancestor-check doesn't touch), #1065 (silently discarded a parent-side feature addition across a rename chain, asserting nothing was lost), #1047 (created a self-contradictory Planned+Done duplicate, explicitly self-assessed as correct) — all trace to the same haiku-tier default for `conflicts` mode, confirmed by reading `millpy-merge-in-subagent.py`'s single shared `model_name` read. The issue's own control experiment (#1059: an identical brief re-dispatched at `opus` tier resolved both files correctly on the first attempt) is direct evidence the tier, not the brief text, was the primary lever for at least that incident. Splitting the config key rather than blindly raising `merge.model` wholesale keeps `verify-fix`'s already-adequate haiku default untouched, honoring this task's #1102-precedent of preferring the smallest change that resolves the issue.
- Rejected: raising `merge.model` unconditionally for both modes — `verify-fix` has no incidents in this backlog and no semantic-judgment component (it is a straight command-pass/fail loop), so bumping its tier would only add cost with no evidence of a corresponding reliability gain.

### self-resolve-card-insertion-auto-renumber (#1057)

- Decision: when `compute_next_card_number` raises `PlanDAGError` for a simple contiguous-range collision (the candidate number is already used by exactly one other, later batch — confirmed by inspecting the exception's own message shape, which names the colliding batch), teach the mill-go-base self-resolve path to auto-renumber instead of escalating immediately: shift every card number `>= candidate` in every batch file positioned after the target batch in `topo_order` up by one (rewriting each `### Card N:` heading in descending numeric order so no intermediate state collides), then retry `compute_next_card_number` (now guaranteed to succeed) and proceed with the existing card-insertion flow unchanged. Only fall back to the existing immediate-`blocked` escalation when the collision is NOT a simple one-batch, contiguous-range shift (e.g. the exception indicates something else, or the retry after renumbering still fails).
- Rationale: confirmed by reading `compute_next_card_number` and `mill-go-base/SKILL.md`'s existing `PlanDAGError` handling (line 909) that today's behavior is exactly what #1057 describes: any collision escalates straight to `blocked`, and since mill-plan's batches are always flush/contiguous/disjoint ranges, this makes self-resolve's card-insertion mechanism structurally unable to ever succeed for a non-final batch. Card numbers carry no cross-reference beyond their own `### Card N:` heading and each card's own `Commit:` message (confirmed: no "depends on card N" syntax exists anywhere in this codebase — batch-to-batch dependencies are declared via `depends-on:` in the Batch Index, never at card granularity), and mill-go executes batches strictly sequentially per `topo_order`, so a downstream batch being renumbered has, by construction, not yet been dispatched and has no commits referencing its old card numbers yet — renumbering it is safe.
- Rejected: option 1 (reserve numbering gaps at plan-authoring time) — this changes mill-plan's batch/card numbering convention itself (affecting every plan going forward, plus any tooling that assumes contiguity), a much larger and more invasive change than teaching the rare self-resolve collision path to renumber on demand.
