## Problem

This task is a narrowed remainder of a 4-issue cluster (GitHub #798-#801 originally); 2 of the 4 were already fixed directly and are out of scope here. Two confirmed gaps remain in mill-go/mill-plan's quality gates:

1. **NIT-fix passes can silently revert a just-fixed BLOCKING defect (#801).** Both the per-batch and holistic NIT-only fix passes in `mill-go/SKILL.md` are dispatched with "Do NOT re-review — the NIT fix is trusted", and the fixer brief (`fixer-batch-brief.md` / `fixer-holistic-brief.md`) gives the fixer only the current round's review file — no visibility into *why* prior rounds' BLOCKING findings were fixed the way they were. Reported incident: round 1's BLOCKING fix reworded a sentence to remove a banned bare-word reference; round 2's reviewer flagged the resulting phrasing as a NIT ("confusing sentence"); the NIT fixer reworded it back to the exact form containing the banned reference, reintroducing the BLOCKING defect. Nothing downstream (batch/holistic review, terminal cleanliness gates, the `done` gate's test run) caught it, because the regression was prose-only — no test exercises it.
2. **Lint findings slip past every gate to PR-time (#800).** Batch `verify:` commands don't run the project's lint tool by default, and code-review's class taxonomy (`_review_common.RECOGNIZED_CLASSES` = `design`, `scope`, `decision`, `consistency`) has no lint/static-analysis class. Reported incident: a `golangci-lint` (ineffassign) finding in a newly-created Go file survived the batch's own `verify:`, holistic code review (including its own NIT pass), and the pre-`done` gate (`go test ./... && go test -tags integration ./...`) — it only surfaced when the orchestrator manually ran `golangci-lint run ./...` during `git-pr`'s ad-hoc Verify step, after the task was already marked `done`.
   **Deeper root cause found during discussion review round 2:** the repo already has a per-commit lint gate (`git-commit/SKILL.md` step 1, "Detect the project language ... and run the lint/format step ... on changed files only") — but `workflow/SKILL.md`'s Language Detection table (lines 67-77) only has rows for Python (`pyproject.toml` etc.) and C# (`.csproj`/`.sln`); there is **no Go/`go.mod` row**. So git-commit's "skip if no language detected" branch silently no-ops lint on every Go commit repo-wide, not just in mill-go's pipeline — this is the more likely actual root cause of the reported incident. See the `defer-go-language-detection-gap` Decision for why this task closes the incident via `done_gate` rather than also fixing the Language Detection table.

**Why now:** both are real regressions observed in production mill-go runs (`loomyard` repo, tasks `builder-retire` and `fabric-warp-binding-in-weft`), not hypothetical. Both slipped through every existing gate in the pipeline.

## Decisions

### prior-blocking-digest-for-nit-fixer

- Decision: Build a "prior-BLOCKING digest" analogous to the existing prior-NIT digest (`mill-go/SKILL.md` ~line 697-703 for batch, ~line 1045-1050 for holistic), but sourced from `### [BLOCKING...]` headings instead of `### [NIT...]` headings, and pass it to the NIT-only fixer via a new `--prior-blocking <path>` flag on `millpy-fix.py`, rendered into the fixer brief as a new `<PRIOR_BLOCKING>` token.
- Rationale: The fixer currently has zero context on why prior BLOCKING-fixed prose/code reads the way it does, so a plausible-looking NIT fix can trivially undo it. Giving the fixer the prior findings' titles + issue context (not full review files — the `reviews/` read-ban stays intact, mirroring the existing NIT digest's curated-summary approach) closes this without adding a review round.
- Rejected: re-review after NIT fix (cost); terminal acceptance-sweep re-run (too narrow — only covers tasks with an explicit zero-hit grep convention).

### prior-blocking-digest-is-cumulative-and-cross-scope

- Decision: The digest source set is **asymmetric by dispatch scope**, both cumulative (all rounds so far, not just N-1) and cross-scope (never siloed to only-batch or only-holistic), but NOT cross-batch for the batch-scope dispatch:
  - **Holistic-scope NIT-fix digest:** every code-review file for this task, from ANY batch (`*-code-review-{batch_name}-r{N}.md`, any batch name) plus every prior holistic round (`*-code-review-r{H}.md`, no batch-name segment), from the start of the task through the round immediately preceding the current holistic dispatch.
  - **Batch-scope NIT-fix digest (for batch B):** only batch B's own review files (`*-code-review-B-r{N}.md`) plus every prior holistic round's review files — explicitly NOT other batches' (`A`, `C`, ...) review files.
- Rationale: Holistic review is, by definition, over the whole task's diff — a holistic NIT-fix pass could plausibly revert ANY batch's BLOCKING fix, which is exactly discussion-review round 1's BLOCKING finding ("Holistic digest is blind to batch-scope BLOCKING history"), so the holistic digest must include every batch. A per-batch NIT-fix pass, by contrast, is scoped to its own batch's `Edits:`/`Creates:`/`Context:` files per the plan DAG — there is no established rationale (and none surfaced in either reported incident) for why batch B's fixer would need to know about batch A's unrelated BLOCKING history, and pulling it in would only bloat the digest with irrelevant noise (discussion-review round 2's BLOCKING finding: "Cross-batch digest scan not justified by the stated rationale"). Both file-naming patterns already coexist in `_mill/reviews/` and are each individually globbable (see the existing crash-recovery glob patterns `mill-go/SKILL.md` already uses to distinguish them), so scanning either set is cheap text extraction (no LLM calls) — the cost argument for "cumulative" still holds identically for both.
- Rejected: narrow N-1-only, same-scope-only digest (leaves both a same-scope delayed-reintroduction gap and a cross-scope blind spot — round 1's BLOCKING finding); unrestricted cross-batch scan for the batch-scope digest too (round 2's BLOCKING finding — no rationale supports it, and it would need its own test fixture and justification neither incident provides).

### symmetric-batch-and-holistic-application

- Decision: Apply the prior-blocking digest mechanism to all THREE `--nits-only` NIT-fix dispatch sites in `mill-go/SKILL.md`, identified by heading/step name (not line number, which drifts as the file is edited — see Testing note below): the per-batch in-flow dispatch (`## Execute` step 4's `APPROVE` branch), the holistic in-flow dispatch (`## Holistic code review` step 4), and the Handoff **"Nit-enforcement gate"** self-resolve dispatch (under `## Handoff`) — all three carry the identical "Do NOT re-review — the NIT fix is trusted" / "trusted" framing and the identical blind-fixer gap, and the Handoff site explicitly reuses the in-flow sites' exact CLI/args shape (per-batch or holistic, whichever scope has unfixed nits), so wiring `--prior-blocking` through it is the same mechanism, not new machinery. Per `prior-blocking-digest-is-cumulative-and-cross-scope` above, each dispatch's digest scan is determined by which scope it's dispatching for (batch B -> batch B's own files + holistic; holistic -> every batch + holistic), regardless of which of the three call sites triggered the dispatch.
- Rationale: Per-hub config can enable batch-scope code review (`roles.code-review.batch.reviewer`, `null` by default) — the mechanism must exist at every dispatch site, and each site's scan must cover the scope-appropriate history, so hubs that do enable batch review get genuinely equivalent protection everywhere rather than protection that silently stops at a scope boundary or is only wired into the two most obvious call sites. Discussion-review round 3 confirmed the Handoff site is a real, distinct dispatch point, not a re-description of the in-flow ones — omitting it would leave exactly the reintroduction risk this task exists to close, just reached via the self-resolve path instead of the normal round flow.
- Rejected: holistic-only (leaves batch-scope reviewers exposed to the identical failure mode when enabled); same-scope-only scanning at each site (leaves the cross-scope hole identified in review round 1); wiring only the two in-flow sites and leaving the Handoff self-resolve dispatch unprotected (round 3's BLOCKING finding — no rationale supports excluding it, and including it is near-free since it reuses the in-flow call shape exactly).

### done-gate-defaults-to-lint

- Decision: `mill-plan/SKILL.md`'s `done_gate` authoring guidance changes from "consider setting `done_gate` to a cheap repo-wide test command" to: when the language build skill defines a lint command, default `done_gate` to include it, decoupled from whether a repo-wide *test* command is also included. A plan whose repo-wide test would be too slow may still set `done_gate: golangci-lint run` (lint-only) rather than leaving it `null`.
- Rationale: `done_gate` is the existing, already-wired mechanism (`_done_gate.py`, `mill-go/SKILL.md`'s pre-done gate step) for "cheap repo-wide check before marking done" — reusing it needs no new config key or script plumbing, just an authoring-guidance change. The reported incident had `done_gate` already set (`go test ./... && go test -tags integration ./...`) but lint-free — this decision directly closes that exact gap. Linters are typically fast (unlike full regression suites), so decoupling lint from the "too slow" carve-out is safe.
- Rejected: adding lint to every batch `verify:` (expensive — runs on every implementer/fixer round, whole-project, per `golang-build`'s "whole-project lint stays whole-project" convention); adding a reviewer-side lint class (doesn't address the actual failure mode — the reviewer already missed the same bug in its own NIT pass).

### no-new-reviewer-class

- Decision: Do not add a `lint`/static-analysis entry to `_review_common.RECOGNIZED_CLASSES` or any `blocking_classes` list.
- Rationale: YAGNI — the reported incident's own LLM reviewer NIT pass already missed the lint finding, so LLM-side classification is not the reliable layer for this; the deterministic `done_gate` fix (see above) is what actually catches it.
- Rejected: adding the class as a "second line of defense" — no evidence it would catch anything the deterministic gate doesn't already catch, and it's unused machinery per this project's stated YAGNI principle.

### defer-go-language-detection-gap

- Decision: This task does NOT add a Go/`go.mod` row to `workflow/SKILL.md`'s Language Detection table, and does NOT fix the resulting no-op per-commit lint gate for Go (`git-commit/SKILL.md` step 1 silently skips lint on every Go commit today, repo-wide). `done_gate-defaults-to-lint` (above) remains this task's sole mechanism for closing #800.
- Rationale: The Language Detection gap is real (confirmed: `workflow/SKILL.md` lines 67-77 list only Python and C# marker rows) and is the more likely actual root cause of the reported incident, but it is a repo-wide gap affecting every Go commit across every task, not something scoped to mill-go's quality-gate pipeline — fixing it properly also requires resolving a file-scoping conflict (`git-commit`'s "changed files only" lint step vs. `golang-build`'s documented "whole-project lint stays whole-project" convention; `golangci-lint` doesn't cleanly accept an arbitrary changed-file subset the way `goimports -w <changed-files>` does), which is its own design problem with its own blast radius. Taking it on here would balloon this task well past "quality-gate coverage gaps in mill-go/mill-plan." `done_gate` closes the reported symptom (PR-time slip) deterministically regardless of whether per-commit lint ever gets fixed for Go — it is not contingent on that fix landing.
- Rejected: fixing the Language Detection table as part of this task (correct long-term, but a separate, larger, repo-wide-blast-radius task — should be filed as its own follow-up, e.g. via `mill-self-report` or a direct GitHub issue, referencing this Decision for context).

## Technical context

- `mill-go/SKILL.md`'s existing prior-notes digest (batch: ~line 696-703; holistic: ~line 1044-1050) is the direct template to mirror: same extraction pattern (`### [NIT...] <title>` heading regex, next non-empty line for Location/Issue context, ASCII-only digest text written to `<briefs_dir>/prior-nonblocking-<batch_name>-r<N>.txt`), same "round 1 passes nothing, digest defaults to `(none)`" convention. The new mechanism swaps the heading marker to `### [BLOCKING...]` and the output path prefix to `prior-blocking-`, and — per `prior-blocking-digest-is-cumulative-and-cross-scope` — widens the file-scan set per dispatch scope: the holistic-scope digest covers every batch's files plus every prior holistic round; the batch-scope digest for batch B covers only batch B's own files plus every prior holistic round (never another batch's).
- **File classification MUST use `_review_common.RE_SIMPLE`/`RE_BATCH` (checked in that order — RE_SIMPLE first, matches excluded from RE_BATCH), never an unpinned `*-code-review-r*.md`-style wildcard.** `mill-go/SKILL.md`'s existing Handoff nit-gate logic documents exactly why: a batch named e.g. `retry-fix` produces a filename `...-code-review-retry-fix-r1.md`, which an unanchored holistic-style glob wrongly matches as a holistic file. Because the new digest must scan an *unbounded range* of prior rounds (not a single pinned round number the way the existing crash-recovery glob patterns do), this collision risk is live, not theoretical — discussion-review round 4 caught it. List every file in `_mill/reviews/`, classify each with RE_SIMPLE first (type `code`, holistic when no batch group) then RE_BATCH (type `code`, batch name from the matched group), and bucket accordingly — never string-match `*-code-review-r*` directly.
- Class-suffixed headings matter: `### [BLOCKING:design] <title>` must match exactly like a bare `### [BLOCKING] <title>` (same rule already documented for the NIT scan).
- A `**Demoted-from:** BLOCKING` marker line means the finding was demoted to NIT by the stage's `blocking_classes` ceiling (`_review_common.apply_blocking_ceiling`) and is rendered as `### [NIT...]`, not `### [BLOCKING...]` — so scanning for the literal `### [BLOCKING` heading text naturally excludes demoted findings without extra filtering. This is correct: a demoted finding was never presented to (or fixed by) anyone as BLOCKING, so it has nothing to protect against reintroduction.
- `millpy-fix.py`'s `main()` (scripts/millpy-fix.py:214-313) currently accepts `--scope`, `--batch-name`, `--review-file`, `--round`, `--stage`, `--agent-output`, `--start-sha`, `--session-id`, `--nits-only` — `--prior-blocking` is a new, independent optional flag, parsed the same way, defaulting to `None`/omitted.
- The render-token wiring for `--nits-only` (scripts/millpy-fix.py:449-454, `NITS_ONLY_CARVEOUT` computed once and passed into both the batch and holistic brief render calls at lines ~537 and ~601) is the pattern to follow for the new `PRIOR_BLOCKING` token — read the digest file content (or `(none)` if the flag is absent) once, pass into both render call sites.
- Fixer briefs (`plugins/mill/templates/fixer-batch-brief.md`, `fixer-holistic-brief.md`) already document their full token list in a leading HTML comment (see `fixer-batch-brief.md:4-19`) — add `<PRIOR_BLOCKING>` there, and a new section (e.g. after "## Inputs", before "## Before reading any finding") presenting the digest with instruction not to reintroduce those problems.
- `code-review`'s fixer flow, unlike discussion-review's, writes no structured `## Fixed` / `## Pushed Back` report — the fixer just commits code and emits the success/stuck JSON. The prior-blocking digest is therefore sourced purely from the review files' `### [BLOCKING...]` headings (which findings were *presented* as BLOCKING), not from a fix-outcome record — this is sufficient and consistent with how the existing NIT digest already works (also sourced from headings only, not from a fix-outcome record).
- `mill-plan/SKILL.md`'s current `done_gate` guidance is at lines 206-208 (verify-command section). `mill-config.yaml` template's `done_gate` comment is at line 122. `_done_gate.py` and the "Pre-done gate" step in `mill-go/SKILL.md` (~line 1324-1336) already run whatever `done_gate` string is configured — no changes needed there; this task only changes what mill-plan *authors* into that string.
- Per-language lint commands already documented in build skills: `golang-build` → `golangci-lint run` (SKILL.md, "Build Commands" + "Tool Installation" sections, including the `$GOPATH/bin` fallback detection pattern); `python-build` → `ruff check .`; `csharp-build` defines no lint command today (only a formatter note, explicitly absent) — the done_gate default is conditional on the language skill defining one, so C# is unaffected.
- `_review_common.RECOGNIZED_CLASSES = ("design", "scope", "decision", "consistency")` (scripts/_review_common.py:309) and `DEFAULT_BLOCKING_CLASSES` (scripts/_review_common.py:2390-2396) are explicitly NOT touched by this task (see "no-new-reviewer-class" Decision).
