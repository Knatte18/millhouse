## Problem

`plugins/mill/skills/mill-plan/SKILL.md` is meant to be a **self-contained** doc: a fresh Opus session with zero conversation history reads it and autonomously turns `discussion.md` into an approved implementation plan, with no operator interaction except at designed halt points. Seven GitHub issues (#839, #832, #831, #827, #826, #821, #815), filed against real mill-plan runs across three different repos (millhouse, loomyard), each found a place where the doc's literal instructions are unsatisfiable, misleading, or silently wrong — forcing the executing agent to guess, fail once, or (in #815's case) miss a real regression entirely. All seven are fixed in this task; none require behavior changes to shared scripts (`_paths.py`, `_status.py`, `_phase_wait.py`, `_plan_validate.py`) — every fix is text/logic inside `mill-plan/SKILL.md` itself, using helpers that already exist and already do the right thing.

**Why now:** these are all recently-filed (2026-08-11/12), real-usage-triggered bugs, not speculative — each has a concrete repro from an actual run.

## Scope

**In:**
- `plugins/mill/skills/mill-plan/SKILL.md` — Entry section (hub_root binding), Entry-gate wait section, Phase: Plan (new authoring guardrail), Phase: Plan Review (Step 1.5 fix table, Agent-mode dispatch `--agent-output` documentation, Step 6 halt message, new Entry `blocked` row).
- No script changes. `_paths.resolve_main_worktree_root`, `_status.append_phase`'s `blocked_reason` auto-clear, and `_phase_wait.matches_wait_trigger`'s regex parameter all already exist and already behave correctly — the bugs are exclusively in how (or whether) `mill-plan/SKILL.md` calls them.

**Out:**
- `_paths.py`'s `resolve_hub_path` docstring/behavior — confirmed to already do the right thing for its actual use (anchoring `_mill/` paths to the task worktree); only the inline comment in mill-plan's own "Path Setup" section that mislabels it "the hub root" needs correcting, to avoid two different "hub root" labels existing side by side once `hub_root` is introduced as a distinct, correctly-bound variable.
- `--recompute-baseline` / `mill-merge-in` — the wiki task body mentioned "`--revise` implies `--recompute-baseline`" but the actual GitHub issue #832 body never mentions this; `--recompute-baseline` exists only in the unrelated `mill-merge-in` skill. Treated as a stale wiki transcription, not pursued.
- A new mechanical `_plan_validate.py` check for #815's existing-test-impact guardrail — rejected in favor of a planner-authoring principle (see Decisions), since "this card intentionally changes an exported symbol's contract" is a judgment call, not a greppable pattern.
- Strengthening the plan-review reviewer's own prompt/template (`plugins/mill/templates/`) for #815 — the issue shows the reviewer template already *can* catch this (it flagged the omission as a NIT, just too late in the pipeline); mill-plan's own authoring guardrail is the primary fix, and reviewer-template changes are a separate concern outside this task's named scope.
- mill-start/SKILL.md's own copy of the identical Entry step-2 `<hub_root>` ordering issue (same pattern, same bug shape) — out of scope; this task is named for mill-plan only. Worth a follow-up issue but not fixed here.

## Decisions

### Entry: bind `hub_root` explicitly (#839, #826)

- Decision: Entry step 1 binds `hub_root = _paths.resolve_main_worktree_root(git_root)` explicitly, alongside `git_root`/`wiki_path`, named exactly like steps 1/3 already name their resolvers (`resolve_git_root`, `resolve_wiki_path`, `slug_from_branch`). Step 2's `load_config` call is updated to reference the now-bound `hub_root`. Path Setup's `worktree_root = _paths.resolve_hub_path()` line drops the "(the hub root; ...)" phrase from its inline comment — replaced with wording that says what it actually is: the task worktree root, used to anchor `_mill/` paths (unchanged behavior, comment-only fix).
- Rationale: both issues independently converge on `_paths.resolve_main_worktree_root(git_root) -> Path` as the correct, already-existing, already-tested helper (`_paths.py:233`, uses `pygit2` to resolve the git common dir and correctly collapses to the main worktree root from any child worktree). No script change needed. Fixing the stray "hub root" label on `resolve_hub_path()`'s result prevents the exact naming collision issue #839 warned about ("note the naming collision that makes this easy to get wrong: `resolve_hub_path()` returns the worktree, not the hub") from being reintroduced now that a *second*, correctly-named `hub_root` exists in the same file.
- Rejected: renaming/fixing `_paths.py`'s `resolve_hub_path` itself (unrequested by either issue, ripples into every skill that calls it — mill-start, mill-go — well beyond this task's scope); leaving the ordering issue as doc-only prose clarification without actually reordering (doesn't fix the unsatisfiable-as-written problem #839 reports).

### Max-rounds block: add a `blocked` re-entry row (#832)

- Decision: Entry step 4's phase table gets a new `blocked` row. On re-entry, read `blocked_reason` via `_status.read_full`. If it starts with `"max-rounds exhausted"`: call `_status.append_phase(status_path, f"plan-review-r{N+1}", ts)` (this auto-clears `blocked_reason` per `_status.append_phase`'s existing transition-away-from-blocked behavior), commit+push, and fall through into the Plan Review loop with a fresh round budget. Any other `blocked_reason` value (`"non-progress round {N}"`, `"plan-validate non-progress"`) stays a hard stop exactly as today — surface the reason, require manual `status.md` intervention. Separately, reword step 6's halt message from `"...{M} BLOCKINGs remain."` to `"...the last round's {M} BLOCKING finding(s) were addressed but not yet re-reviewed."`, since step 4d's fixer pass runs on those exact findings *before* the round-cap check fires.
- Rationale: matches the issue's own suggested fix ("add a `blocked` row to Entry step 4 routing back into Phase: Plan Review"). Distinguishing max-rounds (resource exhaustion — safe to retry once an operator explicitly re-invokes `/mill-plan`) from non-progress (stuck disagreement — genuinely needs a human, per mill-plan's existing Principles: "non-progress... user intervention is required") preserves the existing halt semantics for the case that's supposed to stay hard-stopped, while actually fixing the case that was reported as a pure dead end. The message reword directly addresses the issue's repro: an operator saw "3 BLOCKINGs remain" when all three had, in fact, just been fixed and committed.
- Rejected: requiring manual `_status.append_phase` surgery for every `blocked` case (documents around the bug instead of fixing it — status quo the issue is complaining about, which the file's own Board Discipline section separately says is banned: "Hand-editing the status.md yaml block is banned"); routing re-entry through `--revise` instead (conflates two different verbs — `--revise` is specifically for reopening an *already-approved* plan, not resuming a stalled, never-approved review round).

### Document `--agent-output` for finalize (#831)

- Decision: add the same sentence pattern mill-start already uses (`mill-start/SKILL.md:241` and `:297`) to mill-plan's Phase: Plan Review step 2 (Agent-mode dispatch, ~line 363) and Step 4.5's ERROR-retry re-dispatch (~line 458): state that the finalize invocation threads `--round <round>` unchanged and also passes `--agent-output <output_path>` (the prepare envelope's `output_path` field, read verbatim), and that `millpy-review-plan.py --stage finalize` exits 1 with `"ERROR: --agent-output required for finalize stage"` when omitted.
- Rationale: verified directly against `millpy-review-plan.py:266-267` — the flag is genuinely required today, and mill-plan/SKILL.md currently has zero mentions of `agent-output` anywhere (grepped the full file). This is a real, current gap, not something already fixed by a prior commit. mill-start already solved the identical problem at its own two call sites with a self-contained sentence; matching that precedent keeps the fix local.
- Rejected: adding the requirement once to the shared `mill-go-base/SKILL.md` "Agent-mode dispatch" section instead — larger blast radius (three skills read that section); mill-start's existing precedent shows the narrower, per-skill fix is the established pattern here.

### Step 1.5 fix table: add missing rows, resolve `verify-full-suite` contradiction (#827)

- Decision: add four rows to the Step 1.5 fix table:
  - `verify-malformed-cwd` — re-fix the `{cwd, command}` mapping per the validator error (bad `cwd` value or missing `command`).
  - `verify-mixed-cwd` — make every batch's `verify:` mapping resolve to the same `cwd` (all `hub` or all `git_root`) within one plan.
  - `depends-on-batch-mismatch` — sync a per-batch file's `depends-on:` with the overview's Batch Index entry for that batch.
  - `verify-full-suite` — require `--only <every affected test file>` (or a `-k` pattern); bare/unfiltered `run-all.py` is never permitted, full stop.
  Also **remove** the "Verify command scope" section's existing carve-out ("A batch that legitimately touches a cross-cutting helper... MAY use the unbounded `run-all.py` — but state the justification in `## Batch Tests`"), since it now directly contradicts the validator's unconditional rejection (`_plan_validate.py:2271`, no allowlist/skip-check exists for this check, unlike `wiki-config-mutation`).
- Rationale: grounded via direct grep of `_plan_validate.py` for every check-name literal it emits, cross-referenced against the ~20 rows already in the SKILL.md table — these 4 are confirmed emitted (`:1071`, `:2242`, `:2305`, `:2173`/`:2237`) and confirmed absent from the table. The prose/validator contradiction is real: the check's condition (`"run-all.py" in command and "-k " not in command and "--only " not in command`) fires unconditionally with no way to satisfy it via justification text, so a planner following the old prose produces a plan the validator can never mechanically pass, exhausting the two-pass cap on an "unfixable" error that the fix table has no row for at all — compounding #827's core complaint.
- Rejected: adding a `wiki-config-mutation`-style `skip_checks` escape hatch for `verify-full-suite` to preserve the original prose's intent — requires new plumbing (a justification test, wiring `--skip-check` through both Agent-mode and subprocess/psmux dispatch) for a case the validator's own author apparently decided not to allow; simpler to make the prose match the code.

### Widen the entry-gate wait trigger (#821)

- Decision: change `matches_wait_trigger(phase, {"discussing"}, [])` to `matches_wait_trigger(phase, {"discussing"}, [r"^discussion-fix-r\d+$"])`. Rewrite the justification paragraph (current SKILL.md lines 79-81) to drop the now-disproven claim that `discussion-fix-r{N}` "is never itself pushed as a standalone, externally observable phase."
- Rationale: issue #821 has a concrete repro — commit `ab1786d6` pushed `phase: discussion-fix-r1` standalone while mill-start was mid-loop. This is explained by mill-start's own convergence-gate logic (`mill-start/SKILL.md` Phase: Discussion Review step 4b, not-converged branch): when `round < max_review_rounds` and the convergence gate hasn't fired, mill-start appends+commits+pushes `discussion-fix-r{N}` and continues to the next round *without* the `discussed` phase following in the same commit — directly contradicting mill-plan's stated assumption. `_phase_wait.matches_wait_trigger`'s third parameter already supports fully-anchored regex patterns, and mill-go's own copy of this exact wait pattern already uses it for mill-plan's phases (`mill-go-base/SKILL.md:172`: `{"discussed", "discussing", "planning"}, [r"^plan-review-r\d+$", r"^plan-fix-r\d+$"]`) — direct precedent, same mechanism, same file family.
- Rejected: widening the trigger without correcting the justification paragraph — leaves a demonstrably false claim in a doc that's supposed to be authoritative for a cold-start agent, risking reintroduction of the narrow matcher by a future editor who trusts the (wrong) prose over the (fixed) code.

### New authoring guardrail: existing-test-impact check for contract changes (#815)

- Decision: add a new principle to mill-plan/SKILL.md's Phase: Plan, next to the existing "Card `Context:` is an allowlist" / "`Requirements:` must use stable identifiers" principles (~line 551-560): when a card's `Requirements:` states that it changes an exported function's, method's, or class's existing behavior/contract (not just adding new code), the planner must grep the codebase for existing callers and tests of that symbol before finalizing the plan, and add any found to that card's `Context:` (read-only) or `Edits:` (if the test itself needs updating to match the new contract).
- Rationale: issue #815's repro is a genuine miss across the *entire* existing pipeline — 5 discussion-review rounds, 5 plan-review rounds, and a holistic code review all failed to catch that hardening `Fabric.ResetHard` against dirty checkouts would break an existing, unlisted integration test, because no card's `Edits:` or the overview's `All Files Touched` ever named the test file. The holistic reviewer *did* eventually flag the omission — but only as a post-hoc NIT, after the plan was already through review. "Intentionally changes an exported symbol's contract" is a judgment call about the card's own stated design intent — something only the planning agent (Opus, already reading the full `Requirements:` prose) can reliably make; a mechanical validator check can't distinguish an intentional contract change from an incidental edit to the same function.
- Rejected: a new `_plan_validate.py` mechanical check (can't judge intent, only greppable patterns — would need a fragile heuristic like "any Requirements: line containing a negation+behavior-change keyword," prone to false positives/negatives the same way the existing `context-completeness` prohibition-detection already is); relying on the reviewer template/prompt instead (issue shows this path already exists and already failed once — too late in the pipeline to prevent the wasted implementer round the issue describes); doing nothing (leaves the exact gap #815 reports).
