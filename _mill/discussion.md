## Problem

Three independent CLI bugs, triaged into one task because they share the `millpy-implement.py` / `_done_gate.py` surface but have no code dependency on each other. Each was filed as its own GitHub issue after being hit in a real mill-go run:

1. **#1032 — Windows baseline teardown leaves a stray `.scratch/` dir.** `millpy-implement.py --stage baseline` tears down its scratch worktree via `_worktree.remove_safe`. That function already retries-with-backoff (`dotnet build-server shutdown` + up to 3 attempts) when the `git worktree remove` + `rmtree` fallback hits a Windows "directory not empty" error (WinError 145) — added for a prior, already-fixed incident. The issue reports a *different* Windows lock error, WinError 32 ("the process cannot access the file because it is being used by another process"), which is not covered by that retry path and fails immediately, leaving the scratch dir orphaned on disk (`git worktree list` no longer tracks it, but the directory remains). The stage itself still exits 0 (non-blocking by design), so this is a disk-hygiene bug, not a correctness bug.
2. **#1020 — `_done_gate.run_gate`'s captured `reason` is tail-truncated blindly.** Both `_done_gate.run_preflight` and `_done_gate.run_gate` truncate failed-gate output to the last 2000 characters (`out[-2000:]`) with no regard for where the actual failure text sits. For a `go test ./...`-style gate, packages print in alphabetical order, so an early-failing package's `--- FAIL:`/`FAIL` lines are pushed out of the tail by later passing-package `ok` noise, leaving `reason` with only `ok` lines and a bare `FAIL` — useless both in the operator-facing halt message and in the brief handed to `mill-done-gate-fixer` (both read this same `reason` field, per `mill-go-base/handoff.md`).
3. **#1012 — `millpy-implement.py --stage finalize` silently ignores `--start-sha`.** The CLI accepts `--start-sha` "for CLI-shape parity with millpy-fix.py" but the finalize branch always reads `start_sha` from `status.md` instead, per an explicit in-source comment. `mill-go-base/SKILL.md`'s Agent-mode dispatch pattern documents threading `--start-sha` into "every finalize call for fix and implementer CLIs" — and `millpy-fix.py`'s finalize branch *does* honor it (`start_sha=args.start_sha`). An operator who manually corrected a batch's `start_sha` (after resetting `status.md` to `pending` and re-running `--stage prepare` non-`--resume-incomplete`, which re-captured HEAD as a wrong new `start_sha`) and passed `--start-sha <original-sha>` to `--stage finalize` found it had zero effect — finalize's completeness recount used the wrong (re-minted) SHA and reported a false `stuck_type: logic, reason: "success reported but no content commit"`. Fixed only by hand-editing `status.md` via `_status.set_batch_field`.

**Why now:** all three were hit live during real mill-go/mill-implement runs (not synthesized), each cost an operator manual recovery time, and none has any interaction with the others — bundling them keeps three small, independent fixes in one review pass instead of three near-empty tasks.

## Scope

**In:**
- `_worktree.py`: extend `remove_safe`'s existing WinError-145 retry-with-backoff path to also cover WinError 32 (sharing violation).
- `_done_gate.py`: replace blind tail-truncation in `run_preflight` and `run_gate` with the same failure-line-prioritizing truncation already used by `_implementer_common._run_verify_gate` (reuse `_extract_failure_signatures`, don't reinvent it).
- `millpy-implement.py`: `--stage finalize` honors an explicitly-passed `--start-sha`, falling back to `status.md`'s stored value when the flag is absent/empty — matching `millpy-fix.py`'s existing behavior.
- Unit test updates/additions for all three (existing tests currently assert the old, buggy behavior in two places — see Testing).

**Out:**
- `--session-id` and `--round` at `--stage finalize` stay ignored by `millpy-implement.py` — issue #1012 only reports `--start-sha`, and there is no reported bug or reproduction for the other two flags. Do not touch their handling or their "ignored" help text.
- No change to `--stage prepare`'s re-mint/reuse logic (the `_prepare_reuse_entry` self-resolve-remint machinery in `millpy-implement.py`). The deeper question of whether prepare should detect and reuse an already-committed-but-`state:pending` batch is a separate, much larger behavioral change with its own edge cases (documented at length in `mill-go-base/SKILL.md`'s Resume section) — out of scope for this task, which fixes the reported symptom (the correction flag being ignored) not the trigger that made a correction necessary in the first place.
- No change to the Windows dotnet-build-server-shutdown cleanup already present in `_done_gate.run_gate` on success.
- No change to `run_preflight`'s or `run_gate`'s non-Windows behavior, subprocess invocation shape, or `"skipped"`/`"blocked"`/`"ok"` result contract — only how `reason` is derived from the captured output.
- No change to `millpy-implement --stage baseline`'s non-blocking teardown-failure handling (still logged and swallowed) — only to whether that failure actually happens on a WinError-32 race.

## Decisions

### winerror-32-retry

- Decision: Add a `_is_sharing_violation_error(exc)` helper mirroring the existing `_is_dir_not_empty_error(exc)` (winerror-attribute check first, falling back to a lowercase substring match on `str(exc)` for non-Windows/test doubles: `"being used by another process"`). Combine both into `_is_retryable_lock_error(exc) = _is_dir_not_empty_error(exc) or _is_sharing_violation_error(exc)`. Restructure `remove_safe`'s rmtree-fallback block (both the initial `try` and the retry loop's per-attempt `try`) to catch `OSError` once (not `PermissionError` and `OSError` as two separate clauses) and branch on `_is_retryable_lock_error`: retryable → existing 3-attempt backoff+shutdown loop (unchanged mechanics, just now also triggered by WinError 32); not retryable → preserve the exact existing behavior split (a `PermissionError` instance still becomes `WorktreeLockedError`; any other non-matching `OSError` still re-raises raw).
- Rationale: `PermissionError` is a subclass of `OSError`, and Python's `except PermissionError as exc: raise WorktreeLockedError(...)` clause currently runs *before* `except OSError` ever gets a chance — so a WinError-32 `PermissionError` (this is how CPython surfaces `ERROR_SHARING_VIOLATION`) short-circuits past the retry loop entirely, even mid-retry-sequence. The WinError-145 retry loop already exists and already does exactly what issue #1032's own root-cause analysis asks for (shut down a lingering dotnet build-server node, then retry) — WinError 32 is the same underlying race (a `dotnet test`/`build` subprocess's file handle not yet released when teardown runs) on a different file, so reusing the identical retry mechanism is the minimal fix. `#846/#859/#929/#928/#918/#909` (cited in the existing WinError-145 comment) already establish that this class of race self-clears within the existing backoff window.
- Rejected: A longer initial delay before the first teardown attempt (doesn't address the case where the lock outlives the delay, and slows every teardown, not just the rare locked one). A broader "retry any `PermissionError`" without signature-matching (would also retry genuinely permanent permission failures, e.g. real ACL issues, wasting ~2s before failing anyway) — the existing test suite has a case asserting an unidentified `PermissionError` fails immediately (`test-worktree.py` "remove_safe raises WorktreeLockedError when shutil.rmtree raises PermissionError (long-path fallback)"), and narrowing to a matched signature preserves that test unchanged.

### done-gate-reason-prioritizes-failures

- Decision: In `_done_gate.py`, import and reuse `_implementer_common._extract_failure_signatures` (scans for lines starting with the fixed prefix tuple `--- FAIL:`, `FAIL\t`, `FAILED `, `--- FAIL `, `FAIL -- `) and mirror `_run_verify_gate`'s existing truncation-enrichment shape: when combined stripped output exceeds 2000 chars, build `reason` as an `"[... N earlier chars omitted; earlier failures:\n<up to 20 matched lines>\n...]\n"` marker (only appended when at least one match exists in the omitted prefix) followed by the last-2000-char tail — instead of the current bare `out[-2000:]`. Apply identically to both `run_preflight` and `run_gate`, since their docstrings already promise both call sites treat output shaping identically.
- Rationale: This exact problem (a failure signature buried by later passing-package noise before a fixed tail-truncation) was already solved for verify-gate output in `_implementer_common._run_verify_gate` — `_done_gate.py` is a separate, smaller module that duplicated the truncation logic without duplicating the fix. Reusing `_extract_failure_signatures` rather than writing a second failure-marker regex/prefix set avoids the two modules drifting on what counts as a "failure line" (that prefix tuple already covers Go per-test/package-summary, pytest, and mill's own run-all.py shapes).
- Rejected: A configurable/regex-based reason-extraction scheme (issue only asks for a fix to the truncation-loses-signal problem, not a general extensibility feature; YAGNI). Truncating from the head or middle instead of the tail (issue's own "at minimum" fallback) — rejected because the enriched-tail approach already ships elsewhere in this codebase and keeping both the recent tail (often has the final error/exit summary) and the earlier failure lines is strictly more informative than either truncation direction alone.

### finalize-honors-start-sha

- Decision: In `millpy-implement.py`'s `--stage finalize` branch, resolve `start_sha` as `args.start_sha if args.start_sha else batch_status.get("start_sha")` (CLI flag wins when non-empty, `status.md` remains the fallback) — the same precedence `millpy-fix.py`'s finalize branch already uses. Update the `--start-sha` argparse help text and the two in-source comments (currently: "ignored by implement; status.md is authoritative") to state the flag is now honored when passed, falling back to `status.md` otherwise. Leave `--session-id` and `--round` fully unchanged (still ignored, still documented as ignored) — see Scope/Out.
- Rationale: This is the one place in this task with a genuine open design call — the issue's own "Suggested fix" offered two options (honor the flag, or just document that it's ignored). Honoring it is the more defensible choice: (a) it makes `millpy-implement.py` consistent with `millpy-fix.py`'s already-shipped dispatch contract for the same documented `mill-go-base/SKILL.md` line-357 threading rule ("for fix and implementer CLIs, pass ... `--start-sha`"), closing a real CLI-family asymmetry rather than papering over it in docs — note `millpy-fix.py` itself has no status.md-fallback mechanism to copy (it passes `start_sha=args.start_sha` unconditionally, with no per-batch status.md record of its own); the CLI-flag-wins-else-status.md fallback is a new pattern specific to `millpy-implement.py`, justified below on its own merits, not a copy of an existing `millpy-fix.py` mechanism. (b) it is safe by construction in the normal (non-manual-correction) path — `mill-go-base/SKILL.md`'s Agent-mode dispatch pattern already threads `--start-sha` from the *same* prepare envelope that just wrote that value into `status.md` moments earlier in the same dispatch chain, so honoring the flag is a no-op whenever prepare and finalize are the ordinary consecutive pair; the resume-preserving paths (`--resume-incomplete`, prepare-reuse, warm-`SendMessage`) all keep the envelope's `start_sha` equal to what's already in `status.md`, so no path is documented to legitimately diverge except the exact manual-correction scenario #1012 reports; (c) it requires no change to the trickier prepare-side re-mint logic, which is explicitly out of scope. The status.md fallback itself is needed because, unlike `millpy-fix.py`, `millpy-implement.py`'s normal and resume-path dispatches (per `mill-go-base/SKILL.md` step 5.5's warm-`SendMessage` recovery, which bypasses prepare entirely) can reach `--stage finalize` with no `--start-sha` flag at all — status.md must remain authoritative in that case.
- Rejected: Doc-only fix (leaves the reported bug reproducible — an operator's explicit correction would still silently do nothing) — noted as the rejected alternative to the autonomous decision below.
