## Problem

Four related bugs in `millpy-implement.py`/`millpy-fix.py`'s finalize/prepare machinery were reported from two real mill-go runs (issues #954, #916, #956, #955). Together they cause the stuck-escalation machinery to misfire — flagging batches as stuck for reasons that have nothing to do with the implementer's actual work (its own bookkeeping writes, a missing baseline forward), silently corrupting session bookkeeping on legitimate self-resolve retries, and leaving a background baseline pre-flight failure undiagnosable after the fact. None of these are behavioral regressions the implementer caused — they are gaps in the orchestration/finalize layer that surface as false `stuck_type` classifications or silent state corruption, both of which cost operator time chasing phantom failures.

This task is deliberately sequenced *after* two other bug clusters (mill-go-execution-and-bookkeeping-bugs' PATH bug, merged at `def97c8c`; millpy-implement/bg Windows teardown/liveness fixes, merged at `1c61b831`) because both touch the same finalize verify-replay/baseline-dispatch code paths this task edits — landing on top of both avoids racing them.

## Scope

**In:**
- `_implementer_common.py`: fix `_in_scope_dirty_stuck`/`_run_verify_gates` ordering so finalize's own uncommitted `verify_baseline_failures` write to `status.md` never trips its own dirty-tree gate (#954). Requires adding `git_name`/`git_email` parameters to `_run_verify_gates` and threading them through `finalize_from_output`/`_forward_output`, since the commit-after-write idiom needs git identity that this module does not currently have.
- `millpy-implement.py` / `millpy-fix.py`: pass the already-locally-resolved `git_name`/`git_email` (both files already compute these at startup for their own `git_commit` calls) into the new `finalize_from_output` parameters at both call sites (#954).
- `millpy-fix.py`: forward `batch_verify_baseline`/`module_verify_baseline`/`batch_name` into `finalize_from_output` for both `--scope batch` and `--scope holistic` (#916). Also derive `module_wide_verify_cmd`/`module_wide_cwd_override` from `00-overview.md`'s frontmatter (mirroring `millpy-implement.py:662`) and forward them too — `module_verify_baseline` alone is inert without a `module_wide_verify_cmd` to gate.
- `millpy-implement.py`: narrow the `_prepare_reuse_entry` session/start_sha reuse heuristic so a self-resolve-after-stuck re-fire always mints fresh `session_id`/`start_sha`, while a genuine transient-dispatch-failure re-fire still reuses them (#956). The fresh-mint branch additionally records a **batch-scoped** status field (not a global phase-timeline append — see below) marking that it already reacted to the most recent self-resolve event, so a *subsequent* re-fire (e.g. a transient retry of the just-fresh-minted session) does not keep re-detecting the same self-resolve marker and re-minting indefinitely.
- `millpy-bg.py`: add a heartbeat write to the worker log so a hard-killed background worker leaves a last-known-alive timestamp in the log (#955).

**Out:**
- `millpy-fix.py`'s missing `task_dir`/`parent_branch` wiring (which disables the in-scope dirty-tree gate entirely for fixer dispatches) — a related gap found while reading `finalize_from_output`'s call site, but not named by any of the four sourced issues. Flagged as a follow-up candidate, not fixed here.
- Any change to the `_in_scope_dirty_stuck` `_mill/briefs/` exclusion (already fixed under #885) — unaffected by this task.
- Any change to the transient-retry / `incomplete` / infrastructure stuck-escalation paths in `mill-go-base/SKILL.md` — this task only fixes the false-positive-producing code millpy-implement.py/millpy-fix.py call, not the orchestrator's escalation policy itself.
- Adding new CLI flags (e.g. an explicit `--resume` distinct from `--resume-incomplete`) — the #956 fix uses an existing signal (the phase timeline) instead of a new flag surface.

## Decisions

### 954-commit-baseline-write-before-dirty-check

- Decision: In `_run_verify_gates`'s corroboration-waiver branch (`_implementer_common.py:1180-1189`), after `_status.set_batch_field(status_path, batch_name, "verify_baseline_failures", expanded)` succeeds, immediately `git add`+commit `status_path` on the task branch using `_subprocess_util.git_commit(project_root, message, name=git_name, email=git_email)` — the same commit helper the existing idiom at `millpy-implement.py:857` uses. This runs before `_in_scope_dirty_stuck` is reached later in the same `finalize_from_output` call (line 1975), so the write is never observed as dirt.
  - **New plumbing required:** `git_commit`'s `name`/`email` kwargs are mandatory (`_subprocess_util.py:219-225`), and `_implementer_common.py` currently has no git-identity parameter anywhere. Add `git_name: str | None = None` and `git_email: str | None = None` parameters to `_run_verify_gates` and thread them through `finalize_from_output`/`_forward_output` (defaulting to `None`, matching this module's existing backward-compatible-default convention for every other optional parameter). When either is `None`, skip the commit (safe no-op, same fallback posture as `_in_scope_dirty_stuck`'s own required-inputs-absent behavior) rather than crashing. Both `millpy-implement.py` (already resolves `git_name`/`git_email` at lines ~564-571 for its own `git_commit` call) and `millpy-fix.py` (same pattern at ~301-308) pass their already-resolved values into the new `finalize_from_output` parameters at their respective `--stage finalize` call sites.
  - **All four `_run_verify_gates` call sites, not just one:** `_forward_output` calls `_run_verify_gates` four times — `_implementer_common.py:1865` (explicit-JSON-success path) and three more at lines 2091, 2201, and 2311 (the no-JSON-inference success branches) — all four forwarding an identical parameter set (`status_path`, `start_sha`, `batch_verify_baseline`, etc.) and therefore all four equally reachable through the corroboration-waiver branch #954 fixes. `git_name`/`git_email` must be threaded from `_forward_output`'s own parameters into every one of the four calls, not just the first — an implementation that only wires the explicit-JSON-success call site leaves the three no-JSON-inference paths exposed to the identical false-positive #954 already reports.
- Rationale: The root cause is a write-then-check-without-commit race entirely internal to one `finalize_from_output` call, not a scope or exclusion problem — `status.md` legitimately needs to reflect the expanded baseline set for later batches, so excluding it from the dirty check (rather than committing it) would silently mask genuinely dirty `status.md` states caused by something else. The codebase already has a working precedent for the commit-with-explicit-identity pattern at `millpy-implement.py:857`; the new parameters just make that pattern reachable from a module that doesn't otherwise resolve git identity.
- Rejected: Blanket-excluding `status.md` from `_in_scope_dirty_stuck`'s scope (loses real-dirt detection for other causes of a dirty `status.md`). Reordering the dirty-check before the corroboration write (the corroboration write's whole purpose is to persist the expanded baseline for correctness *before* finalize returns; deferring it past the dirty-check would either lose the persist on a dirty-tree abort or require duplicating the write, more invasive than a commit-after-write). Resolving `git config --global user.name`/`user.email` freshly inside `_implementer_common.py` itself instead of accepting it as a parameter (duplicates logic both call sites already have, and both already fail fast with a clear error message before reaching finalize when identity is unset — re-resolving inside the shared module would either duplicate that check or silently diverge from it).

### 916-forward-verify-baselines-both-scopes

- Decision: In `millpy-fix.py`'s single `--stage finalize` branch (lines 415-457, shared by `--scope batch` and `--scope holistic`), read and forward `batch_verify_baseline` and `batch_name` for both scopes, and `module_verify_baseline` for both scopes. For `--scope batch`, read `verify_baseline_failures` from the batch's status entry the same way `millpy-implement.py:728` does. For `--scope holistic`, union (concatenate + dedupe) the per-batch `verify_baseline_failures` for every batch contributing to the holistic verify command (per the issue's own fix suggestion), keyed by the same `batch_verifies` list already computed by `_plan_dag.iter_batch_verifies` at line 436.
  - **`module_verify_baseline` needs `module_wide_verify_cmd` to not be inert:** `_run_verify_gates` short-circuits the module-wide gate entirely whenever `module_wide_verify_cmd is None` (`_implementer_common.py:1194-1196`), before `module_verify_baseline` is ever consulted — and `millpy-fix.py` currently has no derivation of `module_wide_verify_cmd`/`module_wide_cwd_override` anywhere in the file. Add that derivation to the `--stage finalize` branch, reading `00-overview.md`'s frontmatter via `_plan_dag.parse_verify_field` exactly as `millpy-implement.py:660-664` already does, and forward both `module_wide_verify_cmd` and `module_wide_cwd_override` alongside `module_verify_baseline` into `finalize_from_output`.
- Rationale: Issue #916 names holistic scope specifically (that was the reproduced failure), but the finalize branch is one shared code path for both scopes — fixing only holistic would leave batch-scope fixer dispatches carrying the identical latent bug, undetected until someone hits it. Since the fix touches the same call site regardless, extending it to both scopes is not scope creep, it's fixing the actual shared bug. Forwarding `module_verify_baseline` without also deriving `module_wide_verify_cmd` would satisfy the issue's literal parameter name but leave the module-wide gate exactly as disabled as before (`None` short-circuit) — the derivation is not optional for the fix to have any real effect.
- Rejected: Fixing holistic scope only, exactly matching the issue title — leaves a known-identical bug in the batch-scope path deliberately unfixed in code that a reader/reviewer will immediately notice is inconsistent. Forwarding `module_verify_baseline` alone without deriving `module_wide_verify_cmd` — technically matches the issue's named parameter but is inert by construction, so it would look fixed without being fixed. Leaving module-wide gating explicitly disabled for fixer finalizes and only fixing `batch_verify_baseline` — rejected because the derivation mirrors an already-existing four-line pattern in `millpy-implement.py`, so the cost of doing it properly is low relative to leaving a known-inert parameter in the code.

### 956-fresh-session-after-self-resolve

- Decision: Narrow the `_prepare_reuse_entry` gate (`millpy-implement.py:764-775`) with an additional condition: reuse only when the most recent entry in `status.md`'s `## Timeline` (read via `_status.read_full(status_path)["timeline"]`, taking the last row's phase-token) is *not* one of the self-resolve markers (`self-resolved-verify-logic`, `self-resolved-dead-parent`), OR this batch has already fresh-reminted in response to that specific self-resolve occurrence (see compounding-retry fix below). When neither exception applies, fall through to the fresh-mint branch (new `session_id`, current-HEAD `start_sha`) even though `state == "running"`.
  - **Compounding-retry fix — batch-scoped marker, not a phase-timeline append.** An earlier version of this decision proposed marking "already fresh-reminted" by calling `_status.append_phase(status_path, "session-fresh-mint", timestamp)`. Rejected on review: `append_phase` (`_status.py:429-460`) atomically overwrites the task-level `phase:` YAML field *and* appends the timeline row — it is not a timeline-only operation. `"session-fresh-mint"` is not in `mill-go-base/SKILL.md`'s phase-gate table or its widened mid-execution matcher (`SKILL.md:107-158`), so an interruption right after that commit would leave `phase: session-fresh-mint` on disk and misroute the next crash-recovery resume to the table's `any other -> surface + halt` row — out of this task's scope to fix (`## Scope`'s "Out:" list already excludes touching `mill-go-base/SKILL.md`'s escalation paths). Corrected fix: record the marker as a **batch-scoped field** instead, via `_status.set_batch_fields(status_path, batch_name, {"self_resolve_remint_at": <the self-resolve timeline row's own timestamp>})` — `set_batch_fields` only rewrites the `## Batches` block (confirmed by its existing calls in the fresh-mint branch itself, `millpy-implement.py:827-831`, which already set `state`/`start_sha`/`implementer_session` without touching `phase:`), so it cannot collide with the phase-gate table. The reuse-gate's self-resolve check then compares the timeline's most-recent self-resolve-marker row's own timestamp against this batch field: a mismatch (or field absent) means "not yet reacted to" → fresh-mint and record the timestamp; a match means "already reacted to this occurrence" → ordinary reuse applies. This also correctly handles a batch that gets stuck and self-resolved more than once over its lifetime, not just once.
  - **Required schema change:** `set_batch_field`/`set_batch_fields` (`_status.py:947-1010`) validate every key against a closed allow-list, `_BATCH_ALLOWED_KEYS` (`_status.py:512-521`: `state`, `implementer_session`, `commit_sha`, `start_sha`, `review_round`, `review_file`, `blocked_reason`, `verify_baseline_failures`), raising `ValueError` on any key outside it ("Unknown keys raise ValueError so typos fail loudly," `_status.py:957`). `self_resolve_remint_at` is not in that set today. This is real, additional plumbing #956 must include — add `"self_resolve_remint_at"` to `_BATCH_ALLOWED_KEYS` — not something the existing `set_batch_fields` call in the fresh-mint branch absorbs for free; only the *commit* is free (the write itself needs the schema extension first, or the fresh-mint branch's existing `set_batch_fields` call at lines 827-831 would raise `ValueError` the moment the new key is added to the `fields` dict passed to it).
- Rationale: Per `mill-go-base/SKILL.md:905,924-925`, self-resolve-after-stuck (`verify`/`logic` first occurrence) only appends a `self-resolved-verify-logic` phase entry and commits a plan edit — it never changes the batch's `state` field away from `"running"`, and `implementer_session` stays set. That makes a self-resolved re-fire structurally indistinguishable from a genuine transient-dispatch-failure re-fire to the current `state == "running"` heuristic, even though SKILL.md documents self-resolve re-fire as "fresh" (`"Then re-fire the implementer fresh for this batch"`, line 925). The phase timeline already carries the exact signal needed to detect a self-resolve (read-only — no collision risk), and a per-batch status field bounds the fresh-mint's effect to exactly one re-mint per self-resolve occurrence without ever touching the task-level `phase:` field the orchestrator's crash-recovery table depends on.
- Rejected: Removing the `_prepare_reuse_entry` heuristic outright (it exists specifically to prevent a second "mill-go: start batch" commit and session_id churn on legitimate transient-retry re-dispatch — see the code comment citing #625/#635/#643; removing it reintroduces that regression). Adding a new explicit `--resume`-style flag distinct from `--resume-incomplete` (adds CLI surface and a new decision point to `mill-go-base/SKILL.md`'s already-complex stuck-escalation branching, when the existing phase timeline already disambiguates the two cases without any new API). Using `_status.append_phase` for the "already reminted" marker (round-1 proposal — collides with the task-level `phase:` field and the orchestrator's crash-recovery phase-gate table; see compounding-retry fix above). Extending `mill-go-base/SKILL.md`'s phase-gate widened set to recognize a new phase token instead of using a batch-scoped field (touches the orchestrator's escalation-routing file, which `## Scope`'s "Out:" list explicitly excludes from this task).

### 956-timeline-reader-already-exists

- Decision: No new reader is needed. `_status.py` already exposes `read_full(status_path) -> {"yaml": dict, "timeline": list[str]}` (`_status.py:746-788`, part of the module's documented Public API), returning timeline rows as raw strings in file order (last element = most recent). The #956 gate reads the most-recent row via `_status.read_full(status_path)["timeline"][-1]` and extracts its phase-token with `row.split(None, 1)[0]` — the exact parsing pattern `_status.phase_entry_timestamp` (`_status.py:818-870`) already uses internally (it also demonstrates stripping quotes from the timestamp field via `.strip("'\"")` on `parts[1]`, needed when the gate compares the self-resolve row's own timestamp for the compounding-retry fix above). This correction replaces an earlier version of this discussion, which incorrectly claimed no such reader existed and proposed adding a new `_status.read_phases` helper.
- Rationale: The earlier premise ("consumed nowhere currently — no reader exists") was factually wrong, caught on review — `read_full` and the parsing pattern it enables are already established, working code. Proposing a redundant new helper would have been unnecessary work for mill-plan to schedule and unnecessary surface area for the codebase.
- Rejected: Adding a new `_status.read_phases` helper (the original, now-corrected proposal — redundant given `read_full` already returns everything needed). Parsing the `## Timeline` text block ad hoc inline inside `millpy-implement.py` instead of going through `_status.read_full` — every other status.md structured-section read in this codebase goes through `_status.py`, and duplicating parsing logic outside it breaks that convention for no benefit.

### 955-heartbeat-for-diagnosability

- Decision: In `millpy-bg.py`'s `_worker_main` (worker fast-path, lines 34-89), start a lightweight background thread before calling `subprocess.run(cmd, ...)` that appends a `[mill-bg] HEARTBEAT <ISO-8601 UTC timestamp>` line to the log file at a fixed interval (e.g. every 30s) for as long as the inner subprocess runs, and stop/join the thread in the existing `finally` block before the `[mill-bg] EXIT` write.
- Rationale: The observed failure mode (log has only the `WORKER PID=... START` line, no `WORKER ERROR`, no `EXIT`) means the worker process was killed hard enough that neither the `except Exception` nor the `finally` block ever ran — confirmed by the module's own docstring, which already documents this as unrecoverable in-process ("does NOT survive a hard process kill"). A heartbeat can't catch the kill itself, but it narrows the diagnostic window: the last heartbeat timestamp before the gap tells the operator roughly when the process died, rather than leaving total silence.
- Rejected: No code change, documenting the limitation only (the issue explicitly asks for "enough in its log... to diagnose the failure without re-running" — a pure doc note doesn't satisfy that). Wrapping in a supervisor/watchdog process instead of a heartbeat thread (much larger surface change — new process, new IPC — for a diagnostic improvement that a heartbeat achieves more cheaply).

### 954-916-956-out-of-scope-dirty-gate-gap

- Decision: Do not add `task_dir`/`parent_branch` wiring to `millpy-fix.py`'s finalize call in this task, even though their absence disables `_in_scope_dirty_stuck` entirely for both fixer scopes.
- Rationale: Not named by any of the four sourced issues (#954/#916/#956/#955); expanding scope to an adjacent-but-unrequested gate risks scope creep and delays landing the four confirmed fixes. Recorded here so it isn't silently lost.
- Rejected: Fixing it now since the code is adjacent — rejected per YAGNI/scope discipline; this task fixes what was reported, not everything found nearby.

This is why #956's compounding-retry fix must use `_status.set_batch_fields` (which only rewrites `## Batches`, confirmed by its existing fresh-mint-branch usage) rather than `_status.append_phase`, for a marker that has no reason to exist in the orchestrator's phase vocabulary.

- Git identity for #954's commit-after-write: both `millpy-implement.py` (lines ~564-571) and `millpy-fix.py` (lines ~301-308) resolve `git_name`/`git_email` via `git config --global --get user.name`/`user.email` near the top of `main()`, before slug resolution, and both already fail fast with a clear stderr message if either is unset. `_subprocess_util.git_commit(cwd, message, *, name, email)` (lines 219-234) is the existing helper that issues a commit with explicit `-c user.name=`/`-c user.email=` overrides — both call sites already use it for their own housekeeping commits (`millpy-implement.py:857`), so `_implementer_common.py` just needs `git_name`/`git_email` accepted as new optional parameters and forwarded to a new `git_commit` call inside the corroboration-waiver branch.
- `_forward_output` (`_implementer_common.py:1768` onward) calls `_run_verify_gates` from **four** distinct call sites: line 1865 (the explicit-JSON `status: success` path) and lines 2091, 2201, 2311 (three no-JSON-inference success branches — different ways `_forward_output` infers success when the sub-agent's output didn't contain a parseable JSON status line). All four pass the same argument shape (`status_path`, `start_sha`, `batch_verify_baseline`, etc.), so the corroboration-waiver branch (and therefore #954's fix) is reachable from any of the four. `git_name`/`git_email` must be forwarded to all four, not only the first.
- `_status.py`: `_BATCH_STATES` includes `"blocked"` as a distinct state from `"running"` (line 522-528) — self-resolve does not use `"blocked"`, so state alone can't disambiguate #956; the phase timeline (`append_phase`, line 429; consumed nowhere currently — no reader exists) is the available signal instead.
- `millpy-bg.py`: worker fast-path is stdlib-only (no mill imports, by design — see module comment at line 28) and lives in the same file as the launcher path (which does import mill modules). Any heartbeat implementation must stay within that stdlib-only constraint for the worker path.
- `_bg.py`'s `check_bg_status`/`_probe_liveness` (the consumer side, used by mill-go's Step 0.5 polling and by mill-start's own discussion-review background polling) needs no change for #955 — a heartbeat line doesn't affect its resolution order, since heartbeats never match `_EXIT_RE`/`_EXIT_CODE_RE` and `_has_valid_json_result` already only looks at `{`-prefixed lines.
