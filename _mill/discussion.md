## Problem

`mill-go-base` (the shared orchestration machinery loaded by `/mill-go` and `/mill-go2`) has seven independently-reported robustness gaps, each surfaced during a real, live self-hosted or cross-repo mill-go run and triaged into GitHub issues #1031, #1013, #1005, #1001, #997, #995, #990.
None are theoretical — each has an observed incident writeup in its source issue.
They span wasted wall-clock (serialized waits with no data dependency), missing recovery documentation (an externally-fixed blocked batch has no resume path), a stale-cache correctness bug (crash-recovery freshness check misindexes phase-timeline occurrences), a latent duplicate-dispatch corruption risk (incomplete-recovery could in principle cold-dispatch while the original implementer is still alive), a doc-completeness gap that already caused one manual recovery (NIT-fix dispatch instructions omit an explicit capture+finalize reminder), a context-overflow risk (a documented liveness probe can dump a full JSONL transcript), and a race condition (a concurrent `mill-cleanup` can delete the task worktree out from under a still-running Handoff phase).

Fix each independently — they touch different, mostly non-overlapping sections of `plugins/mill/skills/mill-go-base/SKILL.md`, `holistic-review.md`, `handoff.md`, `resume.md`, and `plugins/mill/scripts/_status.py`.

## Scope

**In:**

- #1031 — overlap the entry-gate wait for `phase: planned` with the step-0.5 baseline pre-flight dispatch.
- #1013 — a documented, helper-backed resume procedure for a `blocked` batch that was fixed externally.
- #1005 — fix the holistic crash-recovery freshness check's positional phase-occurrence indexing.
- #1001 — close the residual liveness-probe gap in the `incomplete`-recovery `--resume-incomplete` cold-fallback path.
- #997 — inline the capture+finalize reminder into both the holistic and per-batch APPROVE-branch NIT-fix dispatch instructions.
- #995 — add an explicit "status-only, never read the output" warning at every `TaskOutput` liveness-probe call site.
- #990 — guard Handoff step 6 (`mill-self-report`) against a concurrent `mill-cleanup` having already deleted the task worktree.

**Out:**

- No broader rewrite of the `## Agent-mode dispatch` pattern — each fix is a targeted, local change.
- No new lock mechanism to prevent `mill-cleanup` from ever racing a live Handoff (rejected for #990 — see Decisions; the existence-check-and-skip guard is sufficient and far lower blast radius).
- No general auto-resume-from-blocked automation for #1013 — the operator's out-of-band fix must still be explicitly re-armed, never silently assumed.
- #1005 needs no CLI-internals changes to `millpy-review-discussion.py` / `millpy-review-code.py` / `millpy-implement.py` — its fix is a `_status.py` helper change plus one call-site edit. (`millpy-implement.py` DOES still gain the new `--module-wide-only` flag, but that's #1031's Decision below, not #1005's — this bullet scopes only the #1005 fix.)
- `mill-go2`'s own `## Dispatch overrides` are untouched; since it loads this same `mill-go-base` skill, all seven fixes apply to it automatically without any mill-go2-specific edit.
- No change to `pipeline.entry_wait` / `pipeline.entry_wait_timeout_minutes` semantics for #1031 — the fix only changes when the baseline job is *launched*, not the wait's own timeout/give-up behavior.

## Decisions

### 1031-parallel-entry-baseline

- Decision: When the Entry phase gate's `discussed`/`discussing`/`planning`/`plan-review-r{N}`/`plan-fix-r{N}`/`discussion-fix-r{N}`/`discussion-gap-fix-r{N}` row is hit and `entry_wait` is `True` (the "Entry-gate wait for upstream mill-plan" branch, `plugins/mill/skills/mill-go-base/SKILL.md` ~line 160-201), immediately BEFORE arming the `Monitor` wait, do a one-shot, non-blocking check: does `<plan_dir>/00-overview.md` already exist on disk with `approved: true` in its frontmatter, AND does `status.md`'s top yaml block have no existing `baseline_preflight_log:` field? If both hold, launch "0.5. Baseline pre-flight"'s `millpy-bg` job, but with a new `--module-wide-only` flag added to `millpy-implement.py --stage baseline` for this early call specifically (`millpy-implement.py --stage baseline --module-wide-only`, ~SKILL.md line 548-578) — the speculative launch computes and caches ONLY the module-wide substage, skipping the per-batch substage entirely. This is required, not optional: at speculative-launch time (before mill-go's own `## Prepare` has run `_status.init_batches`), `## Batches` does not exist in `status.md` yet, so `_status.set_batch_field` (called per batch by `_run_baseline_stage`'s per-batch loop, `millpy-implement.py` line 454) raises `ValueError: Batch {name!r} not present in ## Batches` for every batch — caught by that loop's own per-batch `except Exception` (line 455-456) and recorded as `errored`, silently discarding the (potentially slow) verify-replay work the early launch just paid for with zero caching benefit. The module-wide substage has no such dependency (it never touches `## Batches`) and is genuinely safe to compute this early. Launch it fire-and-forget, and IMMEDIATELY persist its `log-path` into a new `baseline_preflight_log:` field in `status.md`'s top yaml block (a new small helper alongside `set_module_verify_baseline`, e.g. `_status.set_baseline_preflight_log(status_path, log_path)`) — committed on the task branch the same way every other Builder-owned status.md mutation is. Do not poll it yet — continue straight into the `Monitor` wait as today.
  **Restart/orphan reconciliation (closes the race a restarted wait would otherwise hit):** because `millpy-bg` dispatches via a genuinely detached OS process (`_subprocess_util.popen_detached`, outside the interrupted session's own lifecycle) and the builder lock has documented stale-self-lock reclaim on a `/mill-go` restart (SKILL.md line 207), a session restart must not launch a second speculative job while an earlier one may still be running and both would race an unlocked read-modify-write on the same `status.md` row. Persisting the log path in `status.md` (not only in a Builder variable) makes this discoverable across a restart: the one-shot check above reads the persisted field FIRST — if `baseline_preflight_log:` is already set, do not launch a second job; instead check that log's `_bg.check_bg_status` result: `"running"` → do nothing further here (the existing job is still in flight; step 0.5 will find and poll it when reached), `"exit"` → leave the field as-is (step 0.5 will consume the cached JSON and clear the field itself), `"dead"` → clear the field and launch a fresh speculative job (mirrors step 0.5's own existing `"dead"` handling: log the reason, don't halt, and don't leave a stale pointer behind). Once the wait resolves (`phase: planned` reached) and execution later reaches "0.5. Baseline pre-flight" for real (inside the Execute loop, batch 1 — by which point `## Prepare` has already run and `## Batches` exists), it always reads `baseline_preflight_log:` first (whether set by this session or an earlier, restarted one): if present and `[mill-bg] EXIT` already appears in that log, extract the cached module-wide-only JSON summary immediately (no re-launch of the module-wide substage) and clear the field, THEN run a second, ordinary (non-`--module-wide-only`) `--stage baseline` call for the per-batch substage only — now safe, since `## Batches` exists — exactly as the un-early-launched path already does today (the module-wide half of that call is itself a free no-op per its own existing `"cached"` short-circuit, so this is not double work); if present but still running, poll that same log exactly as documented today (not a fresh launch), then proceed to the per-batch call the same way; if absent (overview wasn't on disk yet at entry-gate time, or this is a genuinely fresh mill-plan run with no restart involved), fall back to launching the full (both-substage) job as today, unchanged.
- Rationale: `--stage baseline`'s handler is explicitly idempotent — it checks `module_verify_baseline`/per-batch caches in status.md and no-ops on a re-invocation (SKILL.md line 569, 571-573) — so a speculative early launch is safe to simply consume later, never re-run. Confirmed via `mill-plan/SKILL.md` line 623-628: the plan overview's `approved: true` frontmatter is written and committed well BEFORE `_status.append_phase(status_path, "planned", ...)` fires (line 628) — so for the entire duration of mill-go's entry-gate wait, the approved overview is already present on disk. `--stage baseline` is invoked with no `batch_name` argument (task-scoped, not batch-scoped) and reads the plan directory itself; it does not need anything from `status.md`'s `phase:` field, `order`, or any Builder-held DAG variable that isn't already computable from the already-approved plan files. Gating the early launch on "overview exists with `approved: true`" (rather than launching unconditionally at every entry-gate wait) avoids racing a plan that's still under active revision (`approved: false` mid `plan-review`/`plan-fix` round) or dispatching against nonexistent batch files.
- Rejected: (a) always launching speculatively regardless of plan-file existence — could dispatch against a plan mid-revision or before any batch files exist, adding failure modes with no benefit since the common case (overview already approved and stable for the whole wait) is what actually saves wall-clock. (b) leaving it sequential — defeats the issue's whole purpose; the observed incident measured ~13 minutes of dead time that could have overlapped a multi-minute wait. (c) accepting the restart/orphan race as-is with only a Builder-variable memory of the launch — rejected on review: the builder lock's own documented stale-self-lock reclaim means a restart is a first-class, expected recovery path here, not a rare edge case, and `set_module_verify_baseline`/the new `baseline_preflight_log:` field have no independent file-locking of their own, so an undetected second concurrent launch risks a lost-update race on `status.md`; persisting the log path is cheap and closes this without adding real complexity.

### 1013-blocked-resume

- Decision: Add `_status.resume_batch(status_path: Path, batch_name: str, *, timestamp: str, preserve_start_sha: bool) -> None` to `plugins/mill/scripts/_status.py`. It: (1) sets the named batch's `state` to `pending` via the existing `set_batch_field` mechanics; (2) clears that batch's `blocked_reason` field (set to empty/absent, mirroring `_status.py`'s existing blocked_reason-clearing pattern in `append_phase`, ~line 478-489); (3) when `preserve_start_sha` is `False`, also clears the batch's `commit_sha`/`start_sha` fields so a fresh capture happens on re-dispatch; when `True`, leaves them untouched; (4) calls `append_phase(status_path, "implementing", timestamp)` at the task level (this also auto-clears any top-level `blocked_reason:` row per `append_phase`'s existing behavior, ~line 440-443, 478-489). Also update the Entry phase gate's `blocked` row itself (`SKILL.md` line 111-119: `blocked_reason = status["yaml"].get("blocked_reason")` → "surface `blocked_reason` from status.md and halt") so the halt message doesn't surface empty/`None` for the common case: when the top-level `blocked_reason` is absent, fall back to scanning `_status.read_batches(status_path)` for the entry whose `state == "blocked"` and surface THAT entry's `blocked_reason` (plus the batch name) in the halt message instead, before falling through to the existing behavior unchanged when a top-level reason IS present (the `set_blocked`-based task-halt case, e.g. discussion-review halts).
  Document a new explicit subsection under that same `blocked` row titled "Resume after external fix," instructing: (a) call `_status.read_batches(status_path)` and find the entry whose `state == "blocked"` (note: the task-level top-yaml `blocked_reason:` field is populated only by `_status.set_blocked` call sites, e.g. discussion-review halts — every batch-level blocking call site in SKILL.md sets the batch's own `blocked_reason` via `set_batch_field` and appends `phase: blocked` WITHOUT ever calling `set_blocked`, so the real reason for a batch-triggered block lives only in `## Batches`, not the top-level yaml — the resume doc must read the per-batch field, not assume the top-level one is populated — this is also exactly why the halt-message fallback above is needed); (b) decide `preserve_start_sha` by checking whether the batch's `commit_sha` field is already set or any per-card commits exist on the branch (partial progress → preserve; nothing committed yet → don't); (c) call `resume_batch`, commit (`git -C <worktree> add <status_path> && git -C <worktree> commit -m "<VARIANT_LABEL>: resume {batch_name} after external fix"`), push; (d) re-run `/mill-go`, which will now route through the existing "Mid-execution phase-gate widening" → `## Resume` (`resume.md`) path unchanged, since `phase: implementing` with a `pending` batch and no non-terminal batch entries falls through to the normal dispatch flow for that batch.
- Rationale: matches the issue's own suggested fix directly — a named helper plus documented decision points (the two judgment calls: which batch, and start_sha preservation) rather than leaving the exact hand-rolled sequence to reinvention each time, which the issue reports already caused a *second*, separate bug (the start_sha companion report) from an ad-hoc recovery.
- Rejected: (a) manual-steps-only documentation with no helper — rejected because the issue explicitly names this as the failure mode to avoid (improvised `_status.set_batch_field` calls). (b) fully automatic detection-and-resume with no operator step — rejected: only the operator knows whether the external fix genuinely landed; auto-resuming from `blocked` on process restart alone would silently retry a batch that's still broken.

### 1005-latest-occurrence

- Decision: Add an optional `latest: bool = False` keyword-only parameter to `_status.phase_entry_timestamp` (`plugins/mill/scripts/_status.py` line 820-872). When `True`, ignore `occurrence` entirely and return the timestamp of the LAST matching timeline row (still `None` if there are zero matches) instead of the `occurrence`-th one. Update the holistic crash-recovery call site — `plugins/mill/skills/mill-go-base/holistic-review.md` line 51, currently `_status.phase_entry_timestamp(status_path, "holistic-reviewing", occurrence=H)` — to `_status.phase_entry_timestamp(status_path, "holistic-reviewing", latest=True)`.
- Rationale: confirmed via `_status.py`'s current signature (line 820-822, `occurrence: int = 1`) that no latest-occurrence mode exists today. Confirmed the bug is genuinely scoped to the holistic call site only: the per-batch mirror at `SKILL.md` line 776 uses `f"reviewing-{batch_name}-r{N}"` — a phase string that already embeds the round number, so it is unique per round and `occurrence=1` is always structurally correct there. `"holistic-reviewing"` (holistic-review.md line 51) is the one call site that reuses the SAME literal phase string across every round H, relying purely on positional occurrence-indexing to distinguish rounds — exactly what breaks when an operator manually re-appends the phase without incrementing the round counter. Centralizing "latest" in the shared helper (rather than recomputing an occurrence count at the call site) means any future round-invariant-phase-string call site gets the same protection for free.
- Rejected: recomputing occurrence dynamically at the call site (count existing `"holistic-reviewing"` timeline rows, pass that as `occurrence`) — this just reimplements "latest" by hand at one call site instead of centralizing it in the helper it belongs in, and does nothing for a future call site with the same round-invariant-string shape.

### 1001-liveness-before-cold-redispatch

- Decision: The current `step 5.5` "`incomplete` recovery" warm-`SendMessage` flow (`SKILL.md` line 382-412) already gates the notification-arrival path with a `TaskOutput` liveness probe: any notification that is non-clean-terminal (status not `completed`, OR `completed` with no valid JSON) triggers the probe before being treated as terminal, and "still running" takes no action and waits unbounded for the next notification. This already closes the exact scenario #1001 observed for the *first* warm-resume reply. The residual gap is structural, not behavioral: none of the three documented triggers for "2. `--resume-incomplete` fallback (cold re-dispatch)" (no `agentId` retained; `SendMessage` errors because the agent already terminated; "the warm-resumed agent again stops without emitting JSON") includes an explicit statement that the third trigger is reachable ONLY after the probe has already confirmed not-running for that notification — an implementer reading this file in isolation could reasonably read "stops without emitting JSON" as a bare textual condition, independent of the probe, and code a fallback that skips the liveness check. Close this by: (a) rewording the fallback's trigger list to state explicitly that the third trigger fires only once the per-notification liveness probe above has already confirmed the agent is no longer running (removing the ambiguity, not adding new runtime logic); (b) adding one more explicit liveness re-check immediately at the top of the `--resume-incomplete` fallback's own numbered step, applying to the third trigger only (the other two triggers have nothing to re-check — no `agentId`, or a `SendMessage` error that already proves termination) — a defensive, belt-and-suspenders TOCTOU guard for the narrow window between the notification-time probe and the fallback actually firing.
- Rationale: the observed incident predates this liveness-probe text (it is plausible the probe was added by a later, unrelated fix for #587/#595-style staleness and happens to also cover most of #1001's scenario) — but the issue must be demonstrably closed against its own reproduction, not just argued closed by cross-referencing adjacent text. A cheap, narrowly-scoped re-check plus an explicit wording fix removes all residual doubt at minimal cost.
- Rejected: (a) trusting the existing probe as sufficient with no code/doc change — rejected because it leaves the ambiguity for a future editor and doesn't produce an auditable closure of the reported incident. (b) replacing warm-`SendMessage`+probe with a different mechanism (e.g., a `ListAgents` polling loop) — rejected as disproportionate; it also contradicts this file's own stated "Agent-mode properties: no log-polling or liveness check required" design principle for every other dispatch path.

### 997-inline-capture-finalize-reminder

- Decision: In both `plugins/mill/skills/mill-go-base/holistic-review.md` (the NIT-fix dispatch at line 167, followed by "After the NIT-fix completes successfully... compute `converged`" at line 169) and the per-batch mirror in `SKILL.md`'s Execute step 4 APPROVE branch (line 840-842, identical shape), inline the missing steps explicitly between the dispatch line and the "compute `converged`" line: state in-line "capture the notification to `<brief_path>.out.md` (step 4 of the Agent-mode dispatch pattern), then run `--stage finalize` (step 5), which appends the `nits-fixed-<scope>` marker Handoff's nit-enforcement gate requires — only THEN compute `converged`."
- Rationale: confirmed both call sites currently read only "Follow the Agent-mode dispatch pattern... After the NIT-fix completes successfully... compute `converged`," with no inline restatement of capture+finalize — exactly the gap the issue reports, which already caused one live manual recovery (a missing `nits-fixed-holistic` marker caught by Handoff's nit-enforcement gate, requiring an after-the-fact `.out.md` write and `--stage finalize` re-run).
- Rejected: leaving the generic one-line "Follow the Agent-mode dispatch pattern" cross-reference as sufficient — already proven insufficient by the live incident; a reader going straight from the dispatch notification to computing `converged` is exactly what happened.

### 995-taskoutput-write-only-warning

- Decision: At every `TaskOutput(task_id: <agentId>, block: false)` call site in `SKILL.md` — the implementer probe (step 3(b), line 303), the reviewer/fixer probe (step 3(c), line 325), and the `incomplete`-recovery probe (step 5.5, line 393) — add an explicit inline warning immediately adjacent to the call: "This call is for its status field only — the subagent's raw JSONL transcript in its return value must never be read, logged, or otherwise acted on." Leave the reviewer sub-case's existing `test -f <output_path>` short-circuit (line 326-330) unchanged and do not add an equivalent file-existence guard for the implementer/fixer sub-cases.
- Rationale: confirmed via `grep` that none of the three `TaskOutput` call sites in `SKILL.md` currently carries any such warning — matching the issue's report exactly (a probe on a mid-flight reviewer returned tens of KB of raw JSONL into the orchestrator's context). The reviewer-only `test -f` shortcut already reduces how often the reviewer sub-case even reaches `TaskOutput`, and line 330 documents WHY no equivalent exists for implementer/fixer (the `cheap-liveness-check-reviewer-only (#784)` Decision: fixer/implementer have no autonomously-written deliverable file available before their terminal notification, so there is nothing to `test -f` against) — extending the file-check to those sub-cases would contradict that already-recorded rationale. The issue's proposed fix offers two options ("state that the probe is called for its status field only... and/or prefer a cheaper liveness signal for implementer/fixer too") — the first is directly actionable and closes the actual reported harm (context overflow from reading the return value); the second is already ruled out by an existing, cited Decision.
- Rejected: extending the reviewer-only `test -f` shortcut to implementer/fixer — would contradict the already-recorded `#784` Decision's own rationale for why that shortcut is reviewer-only.

### 990-worktree-race-guard

- Decision: At the very top of `handoff.md` step 6 (`If pipeline.auto_report: true → invoke /mill-self-report --auto`, line 169-173), add a plain filesystem existence check on `worktree_root` (already a Builder-held variable from Path Setup) BEFORE invoking `/mill-self-report`. If it still exists, proceed exactly as today (unchanged). If it does NOT exist (a concurrent `mill-cleanup` swept it after step 5's `mill-finalize`/`mill-merge` flipped Home.md to `[done]` and created the archive tag, but before this session reached step 6), skip step 6 entirely and log one ASCII line noting the worktree was already cleaned up by a concurrent `mill-cleanup` run — do not attempt `/mill-self-report` at all.
- Rationale: the issue's own suggested fix (a) — "have mill-go's Handoff step 6 explicitly `cd` to a stable directory... before invoking mill-self-report" — conflicts with this repo's own, more fundamental "Worktree isolation" convention (`mill:conversation`: "MAY NOT run `cd <parent-path>` or any shell command that changes the process working directory to the parent" — a rule that binds every mill orchestrator session running from a task worktree, not just this self-hosting task's own driving session). `mill-self-report/SKILL.md` (line 36) resolves its own `<worktree-root>` via `git rev-parse --show-toplevel` from cwd, so it structurally requires cwd to be inside SOME git worktree — cd'ing to a non-repo "stable directory" like `$HOME` would just move the failure one step later inside self-report's own first command, and cd'ing to the hub/parent worktree is the one thing worktree isolation explicitly forbids. An existence-check-and-skip guard closes the exact reported harm (a non-obvious failure deep inside a downstream skill's first shell command) without ever attempting a forbidden cd, and correctly reflects reality: self-report has nothing meaningful left to inspect for a worktree that a concurrent cleanup has already confirmed-and-archived as done.
- Rejected: (a) the issue's literal suggested fix (a) (cd to a stable directory) — rejected per the worktree-isolation conflict above. (b) a new lock/guard preventing `mill-cleanup` from sweeping a worktree mid-Handoff (the issue's suggested fix (b)) — rejected as YAGNI for this task: heavier-weight (a new lock file plus a new `mill-cleanup`-side check with its own staleness/cleanup concerns), and the existence-check-and-skip guard fully closes the one reported incident at far lower cost; worth reconsidering only if a future incident shows the skip itself losing real self-report value often enough to matter.
