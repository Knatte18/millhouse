## Problem

C) ...` options with a separate trailing `Recommended: {A/B/C}` line — this is a structural mismatch with `mill:conversation`'s mandated format (numbered `1) Label — description` list, `(Recommended)` suffixed directly onto option 1's label), not merely "the same shape" as an earlier draft of this discussion overstated (caught by discussion-review round 3). See Decisions > max-rounds-prompt-format-conformance for whether/how this task also brings the prompt itself into conformance.
- `mill-go/SKILL.md` has several such prompts under `### Stuck escalation`, none preceded by a load — re-verified line-by-line against the enclosing stuck_type heading after an earlier draft of this discussion mis-attributed three of them (caught by discussion-review round 2):
  - `infrastructure` (line 490): `1) Re-fire fresh (Recommended)` / `2) Block`.

## Decisions

### mill-conversation-load-placement

- Decision: In `mill-plan/SKILL.md`, insert a new numbered step at the very start of `## Entry` (before the existing step 1), worded to parallel mill-start's Step 0: load `mill:conversation` via the Skill tool, unconditionally, immediately, before any other Entry step or phase, with a one-sentence rationale naming that this file's prompts (the Phase: Plan Review max-rounds escape) depend on the skill's numbered-options/no-`AskUserQuestion` convention. In `mill-go/SKILL.md`, insert a new **Step 0.5** immediately after the existing Step 0 (currently "Verify `CLAUDE_PLUGIN_ROOT`") — a separate step, not merged into Step 0's own paragraph — that loads `mill:conversation` unconditionally, with a rationale naming this file's stuck-escalation and rounds-exhausted prompts. A separate step (rather than folding the load into Step 0's text) keeps each step single-purpose and matches mill-go's existing convention of numbering closely-related-but-distinct Entry/dispatch actions with decimal sub-steps (e.g. "0.55", "0.5", "4.5" elsewhere in the file).
- Rationale: mill-start's own Step 0 already establishes the pattern and its justification word-for-word ("because prompts depend on [it] being active"); reusing that exact framing keeps the three orchestrator-tier skills (mill-start, mill-plan, mill-go) consistent and gives future skill authors one pattern to copy. Placing the load first (not lazily at each call site) means it protects prompts not yet written, which is the exact risk the source issue named. Mill-go's `Step 0.5` naming/placement was left ambiguous in an earlier draft of this discussion ("at/immediately after Step 0" in Scope vs. "extend/adjoin... keeping it first" in this Decision) — caught as a discussion-review round-3 NOTE and resolved explicitly here to a new decimal sub-step, not a merged paragraph, so mill-plan can write the exact edit without re-deciding.
- Rejected: Lazy-loading only immediately before each currently-known prompt call site — rejected because it requires enumerating every current AND future call site correctly, reproducing the exact maintenance burden the issue flags, and both mill-plan and mill-go have multiple scattered call sites (see Problem section) making a single lazy-load point impossible without picking one arbitrarily. Documenting-only (no load) — rejected because both files were independently verified in this discussion to have genuine numbered-options prompts today, not merely borderline cases; a documentation-only resolution would leave the `AskUserQuestion` ban unenforced in these files' context. Merging the load into Step 0's existing paragraph in mill-go — rejected in favor of a distinct `Step 0.5`, for the single-purpose-step reason above.

### max-rounds-prompt-format-conformance

- Decision: As part of this task, also reformat mill-plan's max-rounds-escape prompt (lines 246-254 today, inside "6. **Max-rounds escape**") from its current lettered `A) B) C)` + trailing `Recommended: {A/B/C}` shape into `mill:conversation`'s mandated numbered format: `1) Label — description` per option, with `(Recommended)` suffixed directly onto the recommended option's label, and the recommended option listed first (option `1)`). Preserve the prompt's existing content (the three choices — rethink/one-more-round/override — and the `{N}`/`{M}` computed values and the invoke-command text for the "one more review round" choice) verbatim in substance; only the presentation format changes. Update the corresponding "Wait for the user's choice. A → ... B → ... C → ..." follow-up sentence to reference the new numbers (`1 → ... 2 → ... 3 → ...`) instead of letters.
- Rationale: `mill:conversation`'s own text states the numbered-options rule "applies retroactively — when you touch an existing skill that uses prose prompts, convert them"; this task is already editing `mill-plan/SKILL.md` specifically to load `mill:conversation` into this exact prompt's context, so leaving the one prompt the skill governs in a non-conformant format directly undercuts the point of loading the skill at all — an executor with the skill newly active in context, reading a prompt that visibly contradicts what it just loaded, is a worse outcome than not having flagged the mismatch. This gap was caught by discussion-review round 3, which correctly identified the earlier draft's "same shape" claim as overstated (see Problem section correction).
- Rejected: Leaving the prompt's lettered format unchanged and only adding the skill load — rejected because it satisfies the letter of #748 (skill is loaded) while leaving the one prompt in this file visibly non-compliant with what was just loaded, which a future reader (or `mill-self-report`) would likely flag as a fresh gap. Deferring the reformat to a separate task — rejected as unnecessary process overhead; the content is unchanged, only the presentation shape, making this a same-edit, low-risk change alongside the Entry-step insertion already touching this file.

### push-wording-scope

- Decision: Fix all four found instances in the same task: Phase: Plan's commit step (line 116), Phase: Plan Review's step 4d's commit bullet (line 242), and Step 1.5's validator-fix commit in both its subprocess/psmux branch (line 167) and Agent-mode branch (line 176). Phase: Plan and 4d each get "Push." appended as a separate sentence immediately after the existing `git commit` instruction, matching 4a's/4b's exact wording pattern (not the "Commit+push." shorthand used by Handoff/4c). Step 1.5's two validator-fix branches each get the same treatment — append "Push." as a separate sentence after their respective commit instructions (subprocess-branch line 167: after "...`mill-plan: validator-fix pass for {slug}"`" and before "and re-runs the CLI."; Agent-mode-branch line 176: after "...`mill-plan: validator-fix pass for {slug}"`." and before "Then re-invoke the prepare stage..."). Additionally, while editing lines 116 and 242 specifically: both currently read `git -C <worktree> add ... && git commit -m "..."` — the `-C <worktree>` prefix is present on `add` but missing on `commit`, unlike every other commit-producing step in the file (4a/4b/4c/Handoff/167/176, all of which prefix `-C <worktree>` on both `add` and `commit`). Normalize both to `git -C <worktree> add ... && git -C <worktree> commit -m "..."` in the same edit that appends "Push."
- Rationale: Phase: Plan's commit step and step 4d's commit bullet are both single-purpose, single-commit steps structurally closest to 4a/4b's shape (a `git add ... && git commit -m "..."` followed by a bare "Push." sentence), so matching that exact pattern is the more natural fit than introducing the "Commit+push." shorthand seen in Handoff/4c. The validator-fix branches are also single-commit steps immediately followed by a re-run/re-invoke instruction, so the same "append a bare Push. sentence before the next instruction" shape applies cleanly there too. 4d and the two validator-fix branches were found during this discussion's own verification pass (a full `grep -n -i "push"` sweep of the file, including a discussion-review round-1 GAP that caught an initial mis-scoping of the validator-fix branches — see Problem section) — same file, same category of gap (missing push instruction on an otherwise-complete commit step), trivial additional edits; leaving any of them unfixed immediately next to the Phase: Plan fix would be an obvious remaining inconsistency on next read of the same file, and is exactly the kind of gap `mill-self-report` would likely re-file as a new issue afterward. The `-C <worktree>` omission on lines 116/242 was caught by discussion-review round 3: since the plan is already touching these exact two lines to append "Push.", normalizing the pre-existing `-C <worktree>` inconsistency in the same edit costs nothing extra and closes another gap a future reader would otherwise catch separately.
- Rejected: Scoping strictly to issue #747's literal text (Phase: Plan's commit step only) and filing the other three as separate issues — rejected as needless process overhead for one-line, same-file, same-root-cause fixes already fully specified by this discussion. Using the "Commit+push." shorthand instead of a separate "Push." sentence — rejected only for consistency with the nearest structural siblings (4a/4b); no functional difference either way. Leaving the `-C <worktree>` omission on lines 116/242 unfixed as a separate, out-of-scope inconsistency — rejected since the same lines are already being edited for the push fix; deferring would mean touching the same two lines twice across two tasks for no benefit.
