## Problem

Five independent, single-item bugs surfaced as GitHub feedback issues (#834, #833, #825, #818, #812) across four separate mill subsystems: worktree bootstrap, hub-path resolution, per-batch finalize, cleanliness drift detection, and discussion-review. Each is small in isolation, but two of them (#833, #834) share one root cause and are fixed together here; the other three are unrelated and fixed independently. None of these are feature requests — each is a correctness gap discovered live during real mill-go/mill-plan/mill-start sessions, where the failure mode was either a silent wrong-answer (worktree resolution, drift detection) or a false positive that blocked otherwise-correct work (finalize, discussion-review).

## Scope

**In:**
- `_paths.resolve_hub_path()` terminal-fallback fix (#833): when the cwd-walk and main-worktree-stub checks both fail to redirect, return the current `git_root` instead of `main_root`.
- `millpy-spawn.py` defensive `config.local.yaml` write (#834): after `copy_millhouse`, unconditionally verify the destination has `.millhouse/config.local.yaml`; self-heal if missing, covering both the `hub_relative_path == "."` case (currently never covered by the existing gated stub-write) and any `copy_millhouse` miss for the `!= "."` case.
- `_implementer_common._in_scope_dirty_stuck` batch-scoping fix (#825): scope the per-batch finalize dirty check to changes since the batch's own `start_sha`, not the whole task's parent-diff (`compute_terminal_dirt`'s current scope), so a prior approved batch's post-commit file drift no longer false-blocks the current batch.
- `_cleanliness._parent_diff_names` unresolvable-diff signal (#818): return `None` (distinct from `[]`) when `git diff --name-only <parent>...HEAD` fails, and propagate that distinction through `compute_terminal_dirt` and `revert_out_of_scope_drift` so callers escalate to stuck/blocked instead of silently reporting "no drift."
- `plugins/mill/templates/review-discussion.md` criterion addition (#812): an explicit Criteria bullet instructing the discussion reviewer to cross-check testing-plan claims about tooling/validator/prefix requirements (e.g. `PYTHONPATH=`) against CLAUDE.md and `_plan_validate.py`'s actual enforcement, flagging contradictions as `[BLOCKING:consistency]`.
- Unit test coverage for all five fixes in their existing test files (`test-paths.py`, `test-millpy-spawn.py`, `test-implementer-common.py`, `test-cleanliness.py`, `test-review-discussion-flow.py`).

**Out:**
- Forensic investigation into what process rewrites an already-committed `.out.md` post-commit (#825's underlying mystery) — the batch-scoping fix makes finalize robust regardless of cause; the cause itself is a separate, currently-unreproduced concern.
- Retroactively fixing any other discussion.md/plan file that may carry the same false `PYTHONPATH=` claim (#812) — no evidence any currently-active branch repeats it; the fix here is prospective (future discussion-review rounds catch it).
- Changing `_plan_validate.py`'s `_check_verify_not_isolated` validator logic itself — it is correct and matches CLAUDE.md's documented rule; #812's bug is in review coverage, not validator behavior.
- Any change to `_paths.py`'s cwd-walk or M2+sub-repo nested-hub logic beyond the single terminal-fallback line (#833) — those paths are unaffected and already handle their documented cases correctly.
- Escalation/severity redesign for the cleanliness gate beyond adding the "unknown" state (#818) — "unknown" is treated with the same blocking severity the gate already applies to genuine dirt; no new gate-strength taxonomy.

## Decisions

### hub-path-terminal-fallback (#833)

- Decision: In `_paths.resolve_hub_path()` (`plugins/mill/scripts/_paths.py:169-228`), change the terminal fallback at line 228 from `return main_root` to `return git_root` (the resolved git root passed in or of the current worktree).
- Rationale: When cwd is the main worktree itself, `git_root == main_root` already, so this is a no-op there — no regression. When cwd is a task worktree whose own `.millhouse/config.local.yaml` is missing (the exact scenario in #833), the walk starting at `actual_cwd` breaks immediately because `check == git_root_resolved` on the first iteration (a task worktree's `git_root` is its own root, not reachable-upward from the container's hub), so the only remaining signal is the main-worktree stub check at line 218-226 — which only redirects when that stub's `hub_relative_path != "."`. For this repo's own layout (`hub_relative_path: .`), that check never redirects, and the function silently returns the wrong worktree. Returning `git_root` instead makes `resolve_hub_path()` degrade to "the worktree I'm actually standing in," which is what every downstream caller (branch detection, `find_active_slug`) actually wants when no more specific hub info is discoverable.
- Rejected: (a) raising a hard error instead — would require passing `--slug` explicitly at every call site broken by this, disproportionate for what is a one-line fix; (b) leaving this alone and relying solely on the #834 spawn-write fix — leaves the fallback landmine live for any other future cause of a missing local config (hand-created worktrees, corrupted files, etc.).

### spawn-config-local-yaml-defensive-write (#834)

- Decision: In `millpy-spawn.py`, immediately after the `copy_millhouse` call (currently ending around line 216), add an unconditional check: if `dest_hub / ".millhouse" / "config.local.yaml"` does not exist, write it directly with `{"hub_relative_path": hub_subpath}` (the same `hub_subpath` value already computed at line 98, and the same content shape the existing gated block at lines 263-269 writes). This runs regardless of the `hub_subpath != "."` gate that the existing stub-write block is scoped to.
- Rationale: The existing stub-write block (line 263) only fires when `hub_subpath != "."`, so for this repo's own container-form layout (`hub_subpath == "."`), the destination's `config.local.yaml` depends entirely on `copy_millhouse` successfully copying it from the hub's own `.millhouse/config.local.yaml` — with no fallback if that copy doesn't happen (root cause of the underlying miss in #834's reported worktree is unconfirmed; `copy_millhouse` itself has no swallowed exceptions, so the precise mechanism wasn't pinned down from static reading alone). Adding an unconditional existence-check-and-self-heal closes the gap regardless of the exact historical cause, and is idempotent (a no-op whenever the file is already present, which is the overwhelmingly common case).
- Rejected: (a) only fixing the `hub_subpath == "."` case and leaving the `!= "."` block as-is — leaves no defense-in-depth for a `copy_millhouse` miss in the nested-hub case; (b) moving the write before `copy_millhouse` — `copy_millhouse`'s documented overwrite semantics ("Existing files in dst are overwritten") mean write-then-copy risks the hub's own (possibly stale or worktree-inappropriate) file silently clobbering a freshly-written correct one; write-after-copy-if-missing is simpler and matches intent (only step in when copy didn't produce the file).

### finalize-batch-scoped-dirty-check (#825)

- Decision: In `_implementer_common._in_scope_dirty_stuck` (`plugins/mill/scripts/_implementer_common.py:416-464`), replace the call to `_cleanliness.compute_terminal_dirt(project_root, task_dir, parent_branch)` (which scopes to the whole task's `task_dir` ∪ full parent-diff-owned paths) with a batch-scoped equivalent: compute dirty files via `git status --porcelain` intersected with paths touched since the current batch's own `start_sha` (already available and threaded through the calling scope at `_implementer_common.py:1758`, used for `_is_only_start_batch_commit` and `_batch_completeness_stuck` at the same call site) rather than the task-wide `parent_branch...HEAD` diff. `compute_terminal_dirt` itself is unchanged — it remains correct and is still the authoritative check used by mill-go's separate terminal (task-completion) cleanliness gate.
- Rationale: `compute_terminal_dirt`'s scope is deliberately task-wide ("terminal" = whole-task-complete check), which is correct for mill-go's end-of-task gate but wrong for a per-batch finalize check — a prior, already-approved batch's committed file (e.g. `_mill/briefs/implement-<batch>-r1.out.md`) falls within the task-wide parent-diff-owned set, so if it becomes dirty again post-commit for any reason unrelated to the current batch, the current batch's finalize incorrectly blames it. Scoping to `start_sha...HEAD` (or equivalently, dirty files whose last touch is within the current batch's own commit range) means only files the *current* batch actually could have touched are eligible to trip the gate.
- Rejected: (a) keeping task-wide scope but excluding `_mill/briefs/*.out.md` specifically — a narrow band-aid that doesn't generalize to any other file type hit by the same class of bug; (b) auto-reverting any dirt found before failing — risks silently discarding genuine uncommitted work that legitimately belongs to the current batch.

### cleanliness-unresolvable-parent-diff (#818)

- Decision: Change `_cleanliness._parent_diff_names` (`plugins/mill/scripts/_cleanliness.py:113-130`) to return `list[str] | None`: `None` when `git diff --name-only <parent>...HEAD` exits non-zero (parent ref unresolvable — e.g. exit 128 from a deleted branch), `[]` only when the command succeeds with genuinely no changed paths. Propagate this distinction through both callers — `compute_terminal_dirt` (`_cleanliness.py:157-187`) and `revert_out_of_scope_drift` (`_cleanliness.py:326` onward) — so that when the parent diff is unresolvable, both functions signal "unknown" rather than "clean" to their own callers (`_in_scope_dirty_stuck` in `_implementer_common.py`, and mill-go's terminal cleanliness gate), which then escalate to stuck/blocked with the same severity they already apply to genuine dirt.
- Rationale: The issue's core complaint is that "there is no distinction in the gate's return value between 'genuinely clean' and 'couldn't check' " — a silent `[]` on exit 128 makes real out-of-scope drift undetectable for the remainder of the task. Escalating "unknown" with the same severity as "dirty" is the smallest change that closes the undetectable-drift gap: it reuses existing stuck/blocked plumbing rather than introducing a new severity tier.
- Rejected: (a) keeping `[]` but only upgrading the stderr warning's visibility — doesn't fix the actual problem (drift still passes through undetected, just with a louder log line); (b) raising an exception immediately inside `_parent_diff_names` — too blunt without auditing every call site for legitimate tolerance of a missing parent ref elsewhere in the codebase; out of scope for this fix.

### discussion-review-tooling-claim-consistency-check (#812)

- Decision: Add an explicit bullet to the Criteria section of `plugins/mill/templates/review-discussion.md` (after the existing "Constraint coverage" bullet, alongside the existing four-class rubric where `consistency` is already defined as "the artefact contradicts itself, carries a superseded statement, or violates an established repo convention"): instruct the reviewer to verify any testing-plan claim about tooling, validator, or command-prefix requirements (naming `PYTHONPATH=` as the concrete example) against CLAUDE.md and the actual `_plan_validate.py` enforcement, and flag a contradiction as `[BLOCKING:consistency]`.
- Rationale: `_plan_validate.py`'s `_check_verify_not_isolated` (`plugins/mill/scripts/_plan_validate.py:1952-2004`) is correct and intentional — it requires the `PYTHONPATH=` prefix on every `verify:` command whenever any Python marker file exists anywhere in the project, regardless of whether the specific command invokes Python, matching CLAUDE.md's documented rule verbatim. The bug in #812 is that a discussion.md's Testing section asserted the opposite ("no PYTHONPATH= needed for grep-only verify commands") and this false claim passed three discussion-review rounds unchallenged. The `consistency` finding class already exists and already covers "violates an established repo convention" in principle, but the reviewer wasn't specifically prompted to fact-check tooling/validator claims against source — a concrete criterion closes that gap and generalizes to any future similarly-shaped false claim about tooling behavior, not just this one phrase.
- Rejected: (a) changing the validator itself — off-target, the validator is correct; (b) a narrow automated grep-based pre-check in `millpy-review-discussion.py`'s backend for this specific phrase — a heavy one-off linter that doesn't generalize the way a reviewer-prompt criterion does.

## Technical context

- `_paths.resolve_hub_path()` (`_paths.py:169-230`): cwd-walk primary strategy, main-worktree-stub fallback, terminal `return main_root` fallback (line 228, the one line changing for #833). Note the walk's loop-termination condition at line 212 (`if check == git_root_resolved or check == check.parent: break`) is why a task worktree's walk never reaches the container-level hub directory — worktree roots are independent git checkouts, not nested filesystem descendants of the hub for `git_root` purposes.
- `millpy-spawn.py`: `hub = resolve_hub_path()` at line 95 (subject to the same #833 resolution, but under normal invocation — spawn run from the hub — resolves correctly since `main_root` computation via git-common-dir is unaffected by the bug); `hub_subpath = cfg.get("hub_relative_path", ".")` at line 98; `_worktree.copy_millhouse(src=hub/".millhouse", dst=dest_hub/".millhouse", exclude={"wiki","active"})` at lines 212-216 (unconditional, copies all non-excluded, non-symlink entries via `shutil.copy2`/`copytree`); existing gated stub-write at lines 263-269 (`if hub_subpath != ".":`).
- `_worktree.copy_millhouse` (`_worktree.py:127-161`): no swallowed exceptions internally — any copy failure propagates to millpy-spawn.py's outer `except Exception` at line 282, which rolls back the *entire* worktree via the LIFO `_cleanup_stack`. This means the reported #834 symptom (a worktree that exists with `.millhouse/builder.lock` but no `config.local.yaml`) is not explained by a raised-and-swallowed exception inside `copy_millhouse` — the exact historical mechanism remains unconfirmed, which is why the fix is a defensive self-heal rather than a targeted root-cause patch.
- `_implementer_common._in_scope_dirty_stuck` (`_implementer_common.py:416-464`) is called from `_implementer_common.py:1758` inside the same function scope where `start_sha` is already available and used by `_is_only_start_batch_commit(project_root, start_sha)` (line 1723) and `_batch_completeness_stuck(project_root, start_sha, card_ids, ...)` (line 1743-1751) — the batch-scoping fix for #825 reuses this existing `start_sha`, no new parameter needs to be threaded in from further up the call stack beyond adding it to `_in_scope_dirty_stuck`'s own signature.
- `_cleanliness._parent_diff_names` (`_cleanliness.py:113-130`), `compute_terminal_dirt` (`_cleanliness.py:157-187`), `revert_out_of_scope_drift` (`_cleanliness.py:326` onward, returns `tuple[list[str], list[str]]`) all currently treat a nonzero `git diff` exit identically to a genuinely-empty diff — the #818 fix touches all three, changing `_parent_diff_names`'s return type and both downstream functions' handling of the new `None` case.
- `plugins/mill/templates/review-discussion.md`: Criteria section at lines 23-36; the four-class rubric (`design`/`scope`/`decision`/`consistency`) at lines 93-105, with `consistency` already defined broadly enough to cover #812's case in principle (lines 103-104).
- Existing unit test files confirmed present for all five areas: `test-paths.py`, `test-millpy-spawn.py`, `test-implementer-common.py`, `test-cleanliness.py`, `test-review-discussion-flow.py` (all under `plugins/mill/unit_tests/`).
