## Problem

Three independent pipeline-reliability gaps were found in production runs and consolidated into this task (originally GitHub issues #578, #579, #582 on the millhouse repo, now closed/folded):

1. **Discussion-review round-cap blocks the documented `--auto` extension round.** `mill-start --auto`'s non-progress-extension rule says: when gaps are still converging (disjoint titles) at the configured round cap, allow exactly one more round without operator intervention. But `millpy-review-discussion.py --stage prepare` independently rejects `round_n > effective_max` with `ReviewError("Round N exceeds max M for discussion review")`, and mill-start's `SKILL.md` never passes the already-existing `--max-rounds` override on that extension round. The documented behavior is unreachable through the CLI as currently wired.
2. **Cold wiki daemon after machine sleep/resume raises an uncaught exception during `millpy-implement.py --stage finalize`.** `_marker.slug_from_branch()` (called unconditionally near the top of `millpy-implement.py:main()`) calls `wiki.list_tasks_brief(wiki_path)`, which can raise `wiki.WikiStartupError` when the daemon's first contact after a long sleep needs more than the default startup timeout. Only `_marker.MarkerError` is caught at that call site, so the raw traceback surfaces and forces the operator to hand-wake the daemon (`_client.health_check()`) and re-run the identical command.
3. **A legitimate all-pushback `--nits-only` fixer pass is misclassified as stuck.** `_implementer_common.py`'s `finalize_from_output()` checks `HEAD == start_sha` (or "only the batch-start commit exists") and unconditionally demotes to `stuck_type: "logic"` *before* the `nits_only` marker-writing block ever runs. When a fixer correctly pushes back on every NIT per the `mill-receiving-review` decision tree — the correct outcome, zero commits expected — this still gets misreported as stuck, and the `nits-fixed-<scope>` timeline marker is never written. That blocks Handoff's nit-enforcement gate (`_nit_gate.compute_unfixed_nits`), which expects a `nits-fixed-<scope>` row for any approved scope that had NITs.

**Why now:** all three were hit live during recent `--auto`/`mill-go agent-dispatch` runs and required manual operator intervention to unblock (manually raising `rounds` in `config.local.yaml`, manually calling `health_check()`, manually appending the missing status marker). Each is a small, well-localized fix; none requires architectural change.

## Scope

**In:**
- `plugins/mill/skills/mill-start/SKILL.md`: thread a `--max-rounds` override into the discussion-review dispatch (both the Agent-mode dispatch pattern's `<args>` and the subprocess/psmux `millpy-bg` invocation) on the one non-progress-extension round only.
- `_marker.slug_from_branch()` (`plugins/mill/scripts/_marker.py`): catch `wiki.WikiStartupError` around the `wiki.list_tasks_brief(wiki_path)` call, call `wiki._client.health_check(wiki_path)` to force a daemon wake, and retry the call once. If the retry is still exhausted, re-raise the original `wiki.WikiStartupError` unwrapped (do not convert it to `MarkerError`).
- `millpy-implement.py`'s `main()`: add a sibling `except wiki.WikiStartupError` (alongside the existing `except _marker.MarkerError`) around the `slug_from_branch()` call, printing a clean "wiki daemon unreachable" message instead of letting a raw traceback surface on the rare case the retry above is exhausted.
- `_implementer_common.py`'s `finalize_from_output()`: when `nits_only=True` and the fixer self-reported `status == "success"`, skip the two `HEAD == start_sha` / "only batch-start commit" stuck:logic demotions and fall through to the existing completeness gate, dirty-tree gate, and the `nits_applied` / `nits-fixed-<scope>` marker block unchanged.
- Unit test coverage for all three fixes in their existing test files (see Testing).

**Out:**
- No change to the round-cap check itself for non-`--auto` discussion-review runs, or to `millpy-review-plan.py` / `millpy-review-code.py`'s round-cap logic — those already have working `--max-rounds` escape hatches via mill-go and are not part of the reported gaps.
- No change to `_ensure_daemon()`'s internal spawn timeout/polling (`SPAWN_TIMEOUT`) — the fix wraps the existing `health_check()` primitive at the call site rather than widening the daemon's own startup budget.
- No change to the fixer LLM's own behavior or prompts. The secondary note in #582 (fixer self-reported "worktree was clean" while a stray uncommitted blank-line edit remained) is a subagent self-report accuracy issue, not an orchestration bug — the existing in-scope dirty-tree gate (which still runs, unchanged, after the nits_only reordering) is the safety net that catches this case and correctly reports it as stuck, separately from the no-op-success path. No prompt or subagent behavior change is in scope here.
- No change to `_nit_gate.compute_unfixed_nits` itself — once the `nits-fixed-<scope>` marker is reliably written, the existing gate logic is correct as-is.
- No retry/backoff change for any wiki touch point other than `_marker.slug_from_branch()` (e.g. `_client` calls made directly by other scripts already have their own error handling and are out of scope).

## Decisions

### Round-cap extension is a SKILL.md-only fix, not a CLI change

- Decision: `millpy-review-discussion.py` already accepts `--max-rounds <N>` on `--stage prepare` (and `--stage full`), which overrides `cfg["roles"]["discussion-review"]["holistic"]["rounds"]` for that invocation only (`_review_discussion.py:prepare()`, line ~66). `--stage finalize` has no round-cap check at all (confirmed: `finalize()`'s signature carries no `max_rounds` parameter) — only `prepare()` validates `round_n > effective_max`. So the fix is entirely in `mill-start/SKILL.md`: when the `--auto` non-progress-extension rule fires for a round (`extension_used` transitions `True`, `round` becomes `max_review_rounds + 1`), the dispatch step for that round's prepare call must pass `--max-rounds <max_review_rounds + 1>`. All other rounds omit the flag and rely on the config default, unchanged.
- Rationale: matches the GitHub issue's suggested fix (a) and mirrors the precedent already used by `millpy-review-plan.py --max-rounds` (driven by mill-go's own round-cap escape hatch). Smallest possible diff — the CLI plumbing already exists; only the caller was missing the flag.
- Rejected: changing the CLI to auto-detect/permit `round == max+1` without an explicit override (issue's suggested fix (b)) — this hides the cap-bypass decision inside the script instead of making it an explicit, auditable instruction in the SKILL, and weakens the contract for every other (non-`--auto`) caller of `--stage prepare`.

### WikiStartupError retry lives in `_marker.slug_from_branch()`, not at each call site — and exhausted-retry failures must stay typed as `WikiStartupError`, never wrapped as `MarkerError`

- Decision: wrap the `wiki.list_tasks_brief(wiki_path)` call inside `_marker.slug_from_branch()` (`plugins/mill/scripts/_marker.py`) with a catch for `wiki.WikiStartupError`: on first catch, call `wiki._client.health_check(wiki_path)` to force-wake the daemon, then retry `list_tasks_brief()` once. **If the retry also raises `WikiStartupError`, let it propagate unwrapped — do NOT convert it to `MarkerError`.** Separately, `millpy-implement.py`'s `main()` gets a sibling `except wiki.WikiStartupError` clause (alongside its existing `except _marker.MarkerError`) so an exhausted retry still produces a clean message there instead of a raw traceback.
- Rationale: `slug_from_branch()` is the single chokepoint every mill script uses to validate cwd against the wiki (`millpy-implement.py`, `millpy-bg.py`, `millpy-review-*.py`, mill-start, mill-go, etc. — confirmed via grep). The reported failure (cold daemon after machine sleep) is generic to *any* first wiki contact after a long idle period, not specific to `millpy-implement.py --stage finalize` — that was simply the first script to hit it in practice. Fixing at the chokepoint closes the gap for every caller in one change instead of requiring the same try/except to be copy-pasted at N call sites (and inevitably missed at some of them). Critically, `wiki.WikiStartupError` is a subclass of `wiki.WikiError` (confirmed: `wiki/__init__.py:45,70`), and `millpy-bg.py:152` already has `except _wiki_mod.WikiError as exc:` ahead of its `except _marker.MarkerError as exc:` clause, printing a fitting "wiki unreachable" message. Letting the exhausted-retry failure stay a `WikiStartupError` means `millpy-bg.py` needs **no code change at all** — its existing `WikiError` handler already does the right thing. The earlier draft of this decision (round-1 discussion) wrapped the exhausted retry as `MarkerError`, which would have collapsed into `millpy-bg.py`'s *other* handler — the one that prints "cwd appears to be a non-task worktree... switch to the task-worktree terminal" — giving the operator a misleading diagnosis for what is actually a wiki/daemon problem. Keeping the original exception type flowing through is what makes the existing per-script handlers (which already discriminate `WikiError` from `MarkerError` correctly) work as designed.
- Rejected: fixing only the `millpy-implement.py:162` call site. Scoped exactly to the reported issue, but leaves every other script (e.g. `millpy-bg.py`'s own `slug_from_branch` call) exposed to the identical cold-start failure the next time it's hit elsewhere.
- Rejected: wrapping the exhausted-retry failure as `MarkerError` (the round-1 draft of this decision). Collapses a wiki-availability problem into the same exception type used for branch/slug mismatches, which — as described above — misroutes `millpy-bg.py`'s existing error handling to the wrong message. Keeping `WikiStartupError` unwrapped costs nothing (every caller either already handles `WikiError` correctly or, for `millpy-implement.py`, gets the new sibling `except` clause described above) and preserves the type information callers need to react appropriately.

### Nits-only no-op success: skip the no-content-commit gate only when `nits_only=True`

- Decision: in `_implementer_common.py`'s `finalize_from_output()`, the existing `if start_sha is not None:` block (current lines ~934-968) that demotes to `stuck_type: "logic"` on `HEAD == start_sha` or "only batch-start commit" must be skipped entirely when `nits_only` is `True`. Flow then continues to the existing completeness gate, the existing in-scope dirty-tree gate, and finally the existing `nits_only` marker block (`nits_applied = True` + `_status.append_phase(..., f"nits-fixed-{nits_scope}", ...)`) — all unchanged.
- Rationale: a `--nits-only` pass that legitimately pushes back on every finding is expected to produce zero commits; that is success, not a logic bug. The two gates below the skip point (completeness, dirty-tree) are unaffected by this change and continue to catch real problems — e.g. the dirty-tree gate still demotes to stuck if a fixer leaves uncommitted residue, which is exactly the secondary failure mode noted in #582.
- Rejected: relaxing the `HEAD == start_sha` check globally (i.e. for `nits_only=False` too) — a normal batch/holistic fixer with BLOCKING findings must always produce a commit; that gate's existing behavior for `nits_only=False` is correct and untouched.
