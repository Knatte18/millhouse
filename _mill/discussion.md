## Problem

Five gaps were self-discovered via live dry-runs of the mill pipeline (GitHub issues #753, #755, #757, #758, #759) and bundled into this one task. Each is a narrow, mechanical fix to an existing `SKILL.md` file or a small Python helper — no new features, no architecture change. They fall into three clusters:

- **mill-plan self-validate doc bugs** (#759, #753) — the Phase: Plan self-run of `_plan_validate.run(...)` (mirrors the CLI-driven Step 1.5 gate but has no CLI to source flags from) is missing an import line for a helper it calls, and has no escape hatch for the one validator check (`wiki-config-mutation`) whose CLI-driven twin already supports a documented `--skip-check` override.
- **mill-go behavior gaps** (#757, #758) — the Entry-step phase gate's table doesn't recognize batch-scoped `phase:` values (`approved-*`, `reviewing-*-rN`, `fixing-*-rN`, `holistic-reviewing`) as mid-execution/resumable, so a resumable task can wrongly hit "any other → surface + halt"; and the `verify`/`logic` stuck-escalation self-resolve step (rewritten same-day as the issue, but *after* it was filed) only *conditionally* threads the failure reason into the plan card before re-firing, leaving the exact silent-no-op failure mode the issue reported still reachable.
- **Undocumented harness contracts** (#755) — no in-repo doc records the confirmed differences between `Agent`'s single combined-result notification and `Monitor`'s per-line-event-then-separate-terminal-notification shape, forcing empirical re-discovery each time a plan reaches for a new harness tool.

**Why now:** all five were caught by directly operating the pipeline (dry-runs, live incident writeups referenced in each issue) — they are concrete, reproduced gaps, not speculative cleanup.

## Scope

**In:**
- `plugins/mill/skills/mill-plan/SKILL.md` — add the missing import to the Phase: Plan self-validate prose (#759); add a conditional `wiki-config-mutation` skip-check override to that same self-validate call, mirroring Step 1.5's fix-table condition (#753).
- `plugins/mill/skills/mill-go/SKILL.md` — widen the Entry step 5 phase-gate table so batch-scoped phase values route to Resume (#757); make the `verify`/`logic` self-resolve step's plan-card failure-reason annotation mandatory instead of conditional (#758).
- A new reference doc recording confirmed harness tool contracts (`Agent` vs `Monitor` notification/return shape), with pointers from `cli/SKILL.md`, `mill-go/SKILL.md`'s "## Agent-mode dispatch" section, `mill-go/SKILL.md`'s "### Entry-gate wait for upstream mill-plan" section, and `mill-plan/SKILL.md`'s "### Entry-gate wait for upstream mill-start" section (#755).
- Unit test coverage for #757's phase-gate widening, extending the existing `test-phase-wait.py`. #758 is a SKILL.md prose change interpreted by the orchestrating LLM at runtime with no Python function backing the annotation logic — it has no test deliverable (see `## Testing`).

**Out:**
- No change to `_plan_validate.run`'s signature (rejected alternative for #759/#753 — see Decisions).
- No new CLI flags on `millpy-implement.py` (rejected alternative for #758).
- No change to `## Batches`-vs-`phase` precedence in the Entry gate beyond the regex widening (rejected alternative for #757).
- No general harness-contract *testing* infrastructure — #755 is documentation only; no new code path exercises `Monitor` or `Agent` differently as a result of this task.
- No splitting of this task into five separate tasks — all five are addressed within this one discussion/plan.

## Decisions

### 759-missing-import

- Decision: Add an explicit `from _review_common import _load_root_from_overview` line directly into the Phase: Plan self-validate prose in `mill-plan/SKILL.md` (the paragraph currently at the line documenting `_plan_validate.run(plan_dir, project_root, root=_load_root_from_overview(...), ...)`). The file has two live conventions for documenting helper calls — bare `signature:` lines (e.g. lines 19-22) and fenced Python snippets with an explicit `import` line (e.g. the `quote_scalar` example at lines 149-150: ```from _yaml_writer import quote_scalar```). Use the **fenced-Python-snippet-with-import** form, not a `signature:` line — a `signature:` line documents a call's shape, it does not itself import anything, so it cannot carry the missing import statement this fix needs to add. The existing paragraph's explanatory prose (the sentence describing what the self-run call mirrors and why `skip_checks=frozenset()` is passed explicitly) is preserved unchanged; a new fenced ```python``` snippet — mirroring the `quote_scalar` example's shape (import line, then the call) — is inserted immediately adjacent to that paragraph, not used to replace or restructure it.
- Rationale: `_load_root_from_overview` is a real, already-tested helper (`_review_common.py:1030`, imported the same way by `millpy-review-plan.py:117`) — the fix is purely documentary. Reusing the exact same import statement keeps the self-run's prose consistent with the CLI-driven twin it's explicitly designed to mirror.
- Rejected: Changing `_plan_validate.run`'s signature to accept `overview_path: Path` and resolve root internally — touches every call site (`millpy-review-plan.py`, `_review_plan.py`, `_review_code.py`, `_plan_validate.py` itself) for a problem that is purely a missing doc line, not a design flaw in the helper split.

### 753-skip-check-override

- Decision: Extend the Phase: Plan self-validate call's `skip_checks=frozenset()` argument to be conditional: when the same two-condition test from Step 1.5's fix table holds (a: a bootstrap-justification card is present in the plan explaining why the `mill-config.yaml` change is safe mid-flight; or b: the modified keys are provably unused per grep), pass `skip_checks=frozenset({"wiki-config-mutation"})` instead, and document the justification in the validator-fix/plan commit message — exactly mirroring Step 1.5's `--skip-check wiki-config-mutation` CLI flag and its fix-table row.
- Rationale: `_plan_validate.run` already accepts `skip_checks` as a parameter (the self-validate call already passes it, just hardcoded to empty) — no signature change needed, only conditional logic in the SKILL.md prose describing when to populate it.
- Rejected: Routing the self-validate call through the `millpy-review-plan.py --stage prepare` CLI instead of calling `_plan_validate.run` directly, to inherit `--skip-check` uniformly — the doc explicitly states "There is no 'or invoke the standalone CLI' fallback for this self-run — call `_plan_validate.run` directly," and changing that would be a bigger architectural shift than the issue calls for.

### 757-phase-gate-widening

- Decision: Reuse `_phase_wait.matches_wait_trigger(phase, exact, regex_patterns)` (`plugins/mill/scripts/_phase_wait.py:113`, already used for the `discussed`/`discussing`/`planning`/`plan-review-r\d+`/`plan-fix-r\d+` widening) for the Entry step 5 phase-gate table's mid-execution detection, matching `phase` against: `matches_wait_trigger(phase, {"implementing", "reviewing", "fixing"}, [r"^approved-.*$", r"^reviewing-.*-r\d+$", r"^fixing-.*-r\d+$", r"^holistic-reviewing$"])`. The four widened values do **not** all route to the same destination, though — confirmed by reading `### Resume` (mill-go/SKILL.md ~lines 607-656) and the Holistic Code Review crash-recovery scan (~lines 701-710):
  - `reviewing-{batch_name}-rN` / `fixing-{batch_name}-rN` → route to `### Resume` exactly as the existing `implementing`/`reviewing`/`fixing` row does. `### Resume` step 1 locates "the single entry whose `state` is non-terminal: `running`, `reviewing`, or `fixing`" — for these two phase values, that batch's `state` genuinely is `reviewing`/`fixing`, so Resume's existing batch-matching logic works unchanged.
  - `approved-{batch_name}` → this phase fires *between* batches (the just-finished batch is `state: approved`, per line 451/533; every other batch is either already `approved` or still `state: pending` from `_status.init_batches`, `_status.py:957`) — no batch entry is `running`/`reviewing`/`fixing`, so `### Resume`'s step 1 has nothing to match. Route this value to `## Execute — sequential loop` instead, continuing from the next batch in `order` whose `state` is `pending` — this is the same continuation the normal in-flow path already takes at line 451 ("continue to the next batch"), not a new mechanism.
  - `holistic-reviewing` → fires *after all* batches are `approved`, entirely outside the per-batch `## Batches` state machine. Route this value directly to `## Holistic code review`; its own step 1 crash-recovery scan (lines 701-710) already handles resuming a specific round — do not route through `### Resume` at all.
- Rationale: `matches_wait_trigger` is a pure, already-tested (`test-phase-wait.py`) predicate purpose-built for exactly this "exact set + regex-widened" phase-matching pattern, and the SKILL.md file already establishes the precedent of using it for another row in the same table. Reusing it for the *match* keeps the two widened rows consistent; routing each matched value to the destination that can actually resolve it (rather than uniformly to `### Resume`) is necessary because `### Resume`'s own batch-locating step only handles the three states it names — it cannot resolve a phase value that occurs between batches or after all batches, and blindly routing there would just trade one halt-on-a-resumable-task bug for a Resume step that finds no matching entry.
- Rejected: Consulting `## Batches`' per-batch `state` field directly instead of `phase` for this decision — `state` is more granular and arguably more "authoritative" for what Resume itself does (Resume already reads it, per `## Resume` step 1), but changing the *gate's* trigger condition to depend on parsing the `## Batches` section (rather than the single `phase:` YAML field it already reads) is a bigger textual/parsing change than the regex widening, for no added benefit — the gate only needs to know "is this task machine-resumable, and which of the three destinations handles it," not to re-derive that from `state` when `phase` already discriminates it via the regex above.

### 758-mandatory-reason-annotation

- Decision: In the `verify`/`logic` (first occurrence) branch of mill-go's `### Stuck escalation` section, remove the conditional hedge ("edit the plan file(s) **if** the failure traces to an ambiguous or incorrect card") and make annotating the batch file with the stuck JSON's `reason` text **mandatory** on every self-resolve pass, regardless of whether the orchestrator judges the card itself to be ambiguous or incorrect. The existing `_status.append_phase(status_path, "self-resolved-verify-logic", ...)` + commit + re-fire-fresh mechanism is otherwise unchanged.
  - **Annotation target/format:** if the stuck reason names a specific card (e.g. a test-verify failure traceable to one card's Requirements:), append the reason text to that card's `Requirements:` field. When the reason is not card-attributable — confirmed in `_implementer_common.py` that several `logic` reasons are whole-batch conditions with no single-card target (`"success reported but no content commit"`, `f"untracked files outside scope: {violations}"`, `"inferred success but working tree dirty -- implementer likely skipped git-commit on modified files"`) — add or append to a `## Prior failure` section placed **immediately after the batch file's frontmatter, before any other section** (i.e. before the existing `## Rename mechanic` and `## Batch Scope` sections in `plan-batch.md`, not merely "before `## Cards`"), one bullet per self-resolve occurrence, each stating the round and the verbatim `reason` text. The implementer reads the full batch file via its own Read call before starting cards (the brief passes `<BATCH_FILE>` as a path token, not inline-substituted text), so a batch-level section is read unconditionally on the next dispatch, same as any card.
  - Rationale (annotation target): mirrors the existing `review-code-batch.md` template's `## Prior non-blocking items` section — a precedent already in this codebase for carrying batch-level context forward across rounds without attaching it to one specific card.
- Rationale: The 2026-08-01 20:01 rewrite (commit `6cbd6dc6`) already replaced the old three-option interactive escalation with a self-resolve-then-refire step — but its "if it traces to an ambiguous/incorrect card" wording leaves exactly the failure mode #758 reported reachable: a freshly-introduced code defect (the reported `go vet` copylocks error) is not a "card" problem, so an orchestrator following the current wording literally could judge no plan edit is needed and re-fire fresh with zero information about the prior failure — reproducing the silent no-op. Making the annotation unconditional closes this without inventing a new CLI-flag/token mechanism; the plan-card-edit channel already exists and already gets read by every implementer dispatch.
- Rejected: A new `--failure-reason` CLI flag on `millpy-implement.py`, threaded through `_render.render`'s token dict into a new `implementer-brief.md` token (parallel to how `START_SHA` is conditionally populated). This would work but adds a second, redundant channel for the same information (plan-card body vs. a brief token) when the existing plan-card-edit channel already reaches the implementer — every batch dispatch already renders the card body into the brief. Fixing the *conditional* wording is a strictly smaller change that reuses the mechanism the same-day rewrite already introduced.
- Note: this issue is *not* treated as already-resolved by the prior rewrite (the third, "close with no change" option was considered and rejected) — the rewrite narrowed the bug but didn't close it, per the reasoning above.

### 755-harness-contracts-doc

- Decision: Create a new standalone reference file, `plugins/mill/docs/harness-tool-contracts.md`, recording the confirmed contract shapes for `Agent` (single combined-result `<task-notification>` carrying the subagent's final message, `agentId` as the addressable handle for `SendMessage`/`TaskOutput`) and `Monitor` (one `<event>`-tagged notification per stdout line, followed by a separate terminal `<status>completed</status>` notification with no `<event>` tag) discovered during the `phase-wait-gate` task (per #755's incident writeup). Add a one-line pointer to this file from all four locations that already carry inline copies of this contract content: `plugins/mill/skills/cli/SKILL.md` (the one existing Monitor note, "Monitor runs bash, not PowerShell"); `mill-go/SKILL.md`'s "## Agent-mode dispatch" section (documents `Agent`'s contract inline, scattered across several paragraphs); `mill-go/SKILL.md`'s "### Entry-gate wait for upstream mill-plan" section (~lines 130-181, carries the Monitor two-notification-shape prose verbatim); and `mill-plan/SKILL.md`'s "### Entry-gate wait for upstream mill-start" section (~lines 42-91, carries a near-verbatim duplicate of the same Monitor two-notification-shape prose). None of the four inline copies are replaced or deleted — each is load-bearing for its own skill's logic — the new doc only consolidates and cross-references them.
- Rationale: `cli/SKILL.md`'s own frontmatter scopes it to "shell command guidelines" — folding harness-tool-return-shape reference material (which isn't a shell command at all for `Agent`) into that file conflates two different kinds of documentation. A standalone doc under `plugins/mill/` (alongside `templates/`, matching the existing `plugins/mill/templates/review-output.schema.md` precedent for small reference docs that aren't skills) is easy to extend as more tools get spiked (e.g. `Bash run_in_background`'s shape, mentioned as a future candidate in #755) without repeatedly resizing an unrelated skill file.
- Rejected: Folding it into `cli/SKILL.md` directly — simpler (no new file), but the issue's own ask was for "a shared reference," and `cli/SKILL.md`'s scope is specifically shell-command guidelines, not harness-API return-shape documentation.

## Technical context

- **`_review_common._load_root_from_overview(overview_path: Path) -> str | None`** (`plugins/mill/scripts/_review_common.py:1030`) — reads the `root:` field from an overview file's fenced-yaml block. Already imported this way by `millpy-review-plan.py:117`.
- **`_plan_validate.run(plan_dir, project_root, root=..., git_root=..., wiki_root=..., skip_checks=frozenset(), parent_branch=..., max_cards_per_batch=..., max_batch_context_tokens=...)`** — the validator entry point both the CLI-driven Step 1.5 gate and the Phase: Plan self-run call directly. `skip_checks` is a `frozenset[str]` of check names to bypass; already a parameter, no signature change needed for #753.
- **`_phase_wait.matches_wait_trigger(phase: str, exact: set[str], regex_patterns: list[str]) -> bool`** (`plugins/mill/scripts/_phase_wait.py:113`) — pure predicate, no I/O; `phase in exact or any(re.fullmatch(p, phase) for p in regex_patterns)`. Already covered by `test-phase-wait.py`; the #757 fix's new regex patterns (`^approved-.*$`, `^reviewing-.*-r\d+$`, `^fixing-.*-r\d+$`, `^holistic-reviewing$`) should get their own test cases in the same file.
- **`mill-go/SKILL.md` Entry step 5 phase-gate table** (currently around line 80-87) is a markdown table interpreted directly by the orchestrating LLM — there is no Python function backing the table lookup itself (unlike the wait-trigger widening, which does call `_phase_wait.matches_wait_trigger` from the "Entry-gate wait for upstream mill-plan" subsection immediately below the table). The #757 fix adds a second call site for the same helper, for the `implementing`/`reviewing`/`fixing` resume row.
- **`mill-go/SKILL.md` `### Stuck escalation` `verify`/`logic` branch** (currently around line 596) — the exact prose to edit: "self-resolve once: investigate the failure using the same judgment an implementer/fixer already applies when picking 'edit plan and retry' — read the verify/review output that produced this stuck signal, edit the plan file(s) **if** the failure traces to an ambiguous or incorrect card." Drop the conditional; the `_status.append_phase(status_path, "self-resolved-verify-logic", ...)` commit step immediately after is unchanged.
- **`plugins/mill/skills/mill-go/SKILL.md` "## Agent-mode dispatch"** (starting ~line 205) already documents `Agent`'s `agentId`/notification contract inline, in prose scattered across steps 3-6 — this is load-bearing for mill-go's own logic and must NOT be deleted or replaced; the new `harness-tool-contracts.md` doc consolidates/cross-references it, it doesn't own it.
- **`plugins/mill/skills/cli/SKILL.md`** currently has exactly one Monitor-related line (bash-vs-PowerShell). This is the file to add the pointer to the new doc from.
- No `CONSTRAINTS.md` exists at the hub root — nothing to fold in from it.
