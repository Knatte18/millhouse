# Discussion: Merge-in conflict handling: silent marker-verification gaps, mill-config.yaml chicken-and-egg crash, and undocumented dirty-worktree squash failure

status: discussing

## Problem

Four related robustness gaps were found in mill's merge-conflict handling (`mill-merge-in` / `mill-merge`), all discovered as live incidents during real task merges:

- **#713** — the conflict-resolution sub-agent (`millpy-merge-in-subagent.py --mode conflicts`) can self-report `{"status":"success"}` while literal `<<<<<<<`/`=======`/`>>>>>>>` conflict markers are still staged in a file it claimed to have resolved. The orchestrator caught this only because it happened to run a manual `git diff --cached --check` sanity check that isn't part of the documented flow.
- **#718** — the same sub-agent can resolve a conflict by keeping both sides ("union") when the correct resolution is a semantic reconciliation — specifically the "moved on one side, unrelated edit on the other" shape, where keeping both produces a duplicated, self-contradictory result (e.g. a roadmap item lives in two mutually-exclusive sections at once). It self-reports success with no signal that the resolution is questionable.
- **#706** — when the conflicted file is `mill-config.yaml` itself, `_config.load_config`'s repo-layer YAML parse (`_config.py:239`) crashes with a raw, unhandled `yaml.scanner.ScannerError` instead of a usable error — a chicken-and-egg problem, since the merge-in tooling needs to load config to even dispatch the conflict-resolution sub-agent, but the config file is the thing that's broken.
- **#705** — `mill-merge` SKILL.md's Step 5 ("Direct squash") has no documented handling for `git -C <parent-path> merge --squash` failing up front because the parent worktree has uncommitted local changes that would be overwritten. The skill gives no guidance, risking either lost work (force-discard) or a silently wrong squash if an operator improvises.

**Why now:** all four were caught and manually worked around during live tasks (see issues #713, #706, #705, #718 for full incident writeups); each is a real gap that will recur on the next task that hits the same shape.

## Scope

**In:**
- `_config.load_config` (`plugins/mill/scripts/_config.py`): catch a YAML parse failure on the repo-layer `mill-config.yaml` read (line 239) AND the cache-lag template-augmentation read (line 229), fall back to template-only config for the affected source, warn to stderr, never crash.
- `_review_common.load_config`'s missing-source strictness check: regression-test only — already correctly treats "repo-layer file exists but failed to parse" as "source found" (no spurious `ReviewError`); no production edit expected.
- `millpy-merge-in-subagent.py` (`--mode conflicts`): add a conflict-marker verification gate before any `{"status":"success"}` is allowed to reach the caller, in both the `full`-stage direct path and the Agent-mode `finalize`-stage path.
- `plugins/mill/templates/merge-in-conflict-brief.md`: add explicit instruction covering the moved-vs-unrelated-edit shape (#718), and extend the existing `discarded` self-report field's surfacing convention to also cover ambiguous "kept both sides" resolutions.
- `plugins/mill/skills/mill-merge/SKILL.md` Step 5 ("Direct squash"): document a pre-squash dirty-parent-worktree check with an explicit halt-and-ask policy.
- `plugins/mill/skills/mill-merge-in/SKILL.md` Step 3's "Real code conflicts" row: reword the `discarded`-field operator guidance to cover both the genuine-drop case and the new kept-both case (see Decisions/merge-in-semantic-duplication).
- Unit test coverage for the above (extending `test-config.py` for the config fixes, `test-millpy-merge-in-subagent.py` for the conflicts-mode marker gate), plus an integration-test extension (`test-merge.py`) for the dirty-parent-worktree preflight.

**Out:**
- A structural/heuristic detector for semantic content duplication across a whole file (rejected for #718 — see Decisions).
- Auto-stash + diff-verify automation for the dirty-parent-worktree case (rejected for #705 — see Decisions).
- Any change to `mill-merge-in`'s verify-fix mode (`--mode verify-fix`) — none of the four issues touch it.
- Any change to the PR-path / branch-protection fallback logic in `mill-merge` Step 5 — orthogonal to the dirty-worktree pre-check.
- Any change to how `_review_common.load_config`'s stale-`review:`-key warning works — unrelated to the YAML-crash fix.
- Re-litigating the "combine both edits when sides are disjoint" instruction already in `merge-in-conflict-brief.md` step 3 — it stays; #718's fix is an additional instruction, not a replacement.

## Decisions

### config-yaml-crash-fallback (#706)

- Decision: in `_config.load_config` (`plugins/mill/scripts/_config.py`), wrap **both** unguarded `yaml.safe_load` calls over git-tracked files in a `try/except yaml.YAMLError`: (1) the repo-layer `mill-config.yaml` read at line 239 (`repo_cfg = yaml.safe_load(mill_cfg_path.read_text(...))`), and (2) the cache-lag template-augmentation loop's read at line 229 (`_cand_cfg = yaml.safe_load(_candidate.read_text(...))` over `worktree_root|hub_root / plugins/mill/templates/mill-config.yaml`) — in the self-hosted millhouse repo this source-tree template path is itself git-tracked and can carry merge-conflict markers exactly like the repo-layer file, so it is equally exposed to the same crash shape. On failure in either case: print a stderr warning naming the path and the parse error, skip that source's contribution to the merge (treat it as absent — `repo_cfg = {}` for case 1, skip the `deep_merge` into `template_cfg` for case 2), and continue. Do not crash. For case 2 specifically: the existing loop iterates `worktree_root`'s candidate first, then `hub_root`'s, `break`-ing on the first candidate that `.exists()` and differs from the resolved template. A `yaml.YAMLError` on a candidate must NOT `break` the loop — it must be treated exactly like `.exists()` being false for that candidate (skip it, warn, fall through to try the next candidate in the tuple). Only a candidate that exists, differs, AND parses successfully breaks the loop. This matters concretely for this task's own trigger shape: a task worktree mid-merge-conflict has markers in its own copy of the source-tree template while the hub's copy (on a clean branch) parses fine — falling through lets that hub copy still augment the config instead of silently abandoning cache-lag augmentation entirely just because the first candidate tried happened to be broken.
- Rationale: a global fix in `_config.load_config` benefits every mill script that loads config, not just merge-in, and keeps the merge-in sub-agent dispatch functional even when the very file it needs to resolve is unparseable — which is the actual chicken-and-egg problem #706 describes. Falling back to template defaults (rather than halting) means `millpy-merge-in-subagent.py` can still resolve model/reviewer selection well enough to dispatch the conflict-resolution sub-agent that will fix `mill-config.yaml` itself. Correction from round-1 review: the original wording claimed the repo-layer file was "the only git-tracked config source that can carry merge-conflict markers" — that's wrong for this self-hosted repo, where `plugins/mill/templates/mill-config.yaml` is also git-tracked and mergeable; both parse sites need the same guard.
- Rejected: fixing only inside `millpy-merge-in-subagent.py`'s call site — narrower, leaves every other caller of `_config.load_config` exposed to the same crash from any other cause of a corrupted `mill-config.yaml` (not just a merge conflict, e.g. a hand-edit typo). Also rejected: halting with an actionable error instead of falling back — this just moves the crash to a slightly nicer message without actually letting merge-in proceed to fix the root cause.
- Follow-on: no production change needed. `_review_common.load_config`'s missing-source strictness check (`_review_common.py:2001-2007`) already keys off `resolve_repo_config_path(hub_root, worktree_root) is None` (path existence) — never parse success — so a present-but-unparseable repo-layer file already cannot trigger a spurious `ReviewError`, before or after this fix. This item is regression-test-only (see Testing): add a test asserting the existing behavior holds once the parse guard above is in place, rather than changing `_review_common.py`.

### merge-in-marker-verification (#713)

- Decision: after the conflict-resolution sub-agent's output is captured, and only when the sub-agent's own self-reported status is `"success"`, run `git -C <project_root> diff --cached --check -- <file1> <file2> ...` (scoped to exactly the files passed via `--files`). Grep the command's output for the substring `"conflict marker"`. If present, override the envelope before it reaches the caller: emit `{"status":"stuck","stuck_type":"logic","reason":"residual conflict markers found in staged files: <matched files/lines>"}` instead of the sub-agent's claimed success. If the file no longer exists on disk (a valid `git rm` resolution for a modify/delete conflict), the check naturally has nothing to report for it — no special-casing needed.
  - **Two call sites, two different seams** (verified against `_implementer_common.py`): the `full`-stage direct-call path in `_run_conflicts` already has the sub-agent's raw output text in a local variable (`output`, from `_implementer_claude.run(...)`) before calling `_forward_output(output, project_root)` — the gate slots in there directly, reading `output` to extract the self-reported status (e.g. via `_extract_status_json`, currently private in `_implementer_common.py` — either import it as-is or promote it to a public name) before deciding whether to call `_forward_output` normally or print the overriding stuck JSON itself. The Agent-mode `--stage finalize` path in `main()` has no equivalent local variable: `finalize_from_output` internally reads `--agent-output`, `html.unescape`s it, and calls `_forward_output`, which prints its own JSON and returns only an int — there is nothing to intercept after that call returns. For `args.mode == "conflicts"` at `--stage finalize`, `main()` must itself read and `html.unescape` `args.agent_output` first (mirroring exactly what `finalize_from_output` does internally), run the same self-reported-status extraction and marker gate against that text, and only then either call `finalize_from_output(Path(args.agent_output), project_root)` unchanged (gate passed / status wasn't success) or print the overriding stuck JSON directly and return 0 (gate failed) — bypassing `finalize_from_output` for that one outcome. No change to `_implementer_common.py`'s shared helpers themselves; both callers (implementer, fixer) keep today's behavior. This new pre-read MUST reuse or exactly replicate `finalize_from_output`'s existing `is_file()` guard (`_implementer_common.py` lines ~1296-1307: check `Path(args.agent_output).is_file()` first; on failure, print the same actionable stderr message and `return 1`) before ever calling `read_text`/`html.unescape`/extracting status — otherwise a missing `--agent-output` file would crash with a raw, unhandled `FileNotFoundError` in the new gate code, silently reintroducing the exact crash class commit `8eb2cb05` already fixed generically inside `finalize_from_output`, but only for the conflicts-mode finalize path (since the gate-fail branch never reaches that existing guard). The new finalize-stage gate code also needs its own `args.files`-falsy guard (print an actionable error, e.g. matching the existing "`--files` is required for conflicts mode" message at `_run_conflicts` line 337-339, and `return 1`) before scoping `git diff --cached --check -- <args.files>` — that existing check lives only inside `_run_conflicts`, which the finalize early-exit branch (lines 279-316) never reaches, so an omitted `--files` at `--stage finalize --mode conflicts` would otherwise crash with an unguarded `TypeError` iterating `None`, the same unguarded-crash class as the `--agent-output` case just above.
- Rationale: `git diff --cached --check` is git's own conflict-marker detector — it is the exact command the operator used manually to catch the real #713 incident, so reusing it (rather than a custom regex) inherits git's own handling of marker formats (e.g. `<<<<<<< HEAD` with a branch-name suffix) for free. Filtering the check's output for "conflict marker" specifically (rather than treating any nonzero exit as a failure) avoids false-positive blocking on `--check`'s unrelated whitespace-error warnings. Reusing the existing `stuck_type: logic` classification means this plugs directly into `mill-merge-in` SKILL.md's already-documented `{"status":"stuck"}` handling (roll back to checkpoint, preserve it, report to caller) — no new stuck-type plumbing needed anywhere in the stuck-escalation machinery.
- Rejected: a custom `<<<<<<<`/`>>>>>>>` line-start regex — works, but reinvents what git's `--check` already does correctly, including edge cases like marker-length variants. Also rejected: a new `stuck_type` (e.g. `"unverified"`) — the existing `logic` type already means "the sub-agent's work isn't trustworthy," which is exactly this case; a new type would need new handling wired into every consumer of `stuck_type` for no behavioral difference.

### merge-in-semantic-duplication (#718)

- Decision: add an explicit instruction to `plugins/mill/templates/merge-in-conflict-brief.md`'s "Instructions" section, alongside the existing step 3 ("combine both edits" for disjoint changes): before keeping content from either side inside a conflict hunk, search the rest of the file (outside the hunk) for that same content. If it already exists elsewhere, this signals the content was *moved* rather than independently duplicated — do not re-add it in the hunk; keep only the other side's unrelated edit. Additionally, extend the sub-agent's report schema so that a resolution which kept content from both sides of a hunk (not just outright-discarded content) is surfaced the same way the existing `discarded` field already is — i.e. a `"kept both sides of a conflict"` description populates the same `discarded` list field, reusing `mill-merge-in` SKILL.md's existing read of that field. That SKILL.md row's operator-facing wording must also change: today it says to "verify nothing load-bearing was lost," which is accurate for a genuine drop but wrong for a kept-both entry (nothing was lost — the risk is duplication/self-contradiction, not loss). Generalize the wording to cover both: for each `discarded` entry, either confirm nothing load-bearing was lost (drop case) or check for duplication/self-contradiction (kept-both case), based on the entry's own description.
- Rationale: #718 is a semantic-correctness problem (is this specific hunk a move-vs-add, or a genuine independent duplication?) — the kind of judgment a structural post-check would need heavy heuristics to approximate and would still produce false positives/negatives on. The template already has step 3's "combine both edits" instruction for the general disjoint-change case; #718's shape is the one place that general rule goes wrong, so a targeted addition (check-the-rest-of-the-file first) closes exactly that gap without touching the rule for cases where it's already correct. Reusing the `discarded` field's existing surfacing convention (rather than inventing a new report field) means `mill-merge-in` SKILL.md's step 3 conflict-handling row needs no new branch — it already reads this field and puts the operator in the loop before `git merge --continue` runs.
- Rejected: a structural post-check scanning the resolved file for near-duplicate content blocks — fragile, prone to false positives on legitimately repeated phrases/structures, and out of proportion to a single reported incident (YAGNI).

### dirty-parent-worktree-preflight (#705)

- Decision: in `plugins/mill/skills/mill-merge/SKILL.md` Step 5 ("Direct squash"), immediately before `git -C <parent-path> merge --squash "$CHILD_BRANCH"`, add `git -C <parent-path> status --porcelain`. If non-empty, halt the skill and report to the operator, with wording that covers both the scenario the check is primarily meant to catch (an independent uncommitted edit in the parent worktree) and the scenario a Step-5 retry can also produce: "the parent worktree is not clean — either (a) this is independent uncommitted work in the parent worktree: commit or stash it, then re-run `/mill-merge`; or (b) this is a partially-applied squash left over from a Step 5 that failed after `merge --squash`/`reset`/`checkout` already staged changes but before `commit` landed: run `git -C <parent-path> commit` to complete it, or `git -C <parent-path> reset --hard` to discard it, then re-run." This check applies only in `worktree` mode (a separate `-C <parent-path>` target exists); it is skipped entirely in `mode == 'inplace'`, since in-place mode has no separate parent worktree to inspect — Step 5 already omits the `-C <parent-path>` flag in that mode.
- Rationale: `mill-merge` can run as part of an unattended chain (`mill-go` → `mill-finalize` → `mill-merge`, direct-merge path), so an automated auto-stash-and-verify recovery risks silently interacting with a human's own uncommitted work in the parent worktree with no one watching — exactly the scenario the reporter flagged as risky if "a less careful operator" mis-resolves it. Halting is the simplest safe default: it never touches the parent's uncommitted state, and the operator (who put that state there) is the right party to decide whether to commit or stash it. The two-scenario wording (round-2 review gap) is needed because Step 5 is documented as re-runnable after a partial failure — a retry landing mid-squash (staged but not yet committed) would otherwise see the same "dirty parent" signal as an independent edit and get told to "commit or stash your own work," which is misleading when the dirty state is mill-merge's own half-applied squash. Rather than building state-detection logic to tell the two cases apart automatically (e.g. inspecting whether the staged diff matches what a squash of `$CHILD_BRANCH` would produce), the halt message names both possibilities and lets the operator — who knows which situation they're in — pick the right recovery. This keeps the fix as simple as the original halt-and-ask design while closing the gap the reviewer found.
- Rejected: auto-stash with a labeled message, squash, then diff-verify before dropping the stash — matches the issue's alternative "expected" behavior and is more automated, but adds meaningfully more logic (stash/diff/conditional-drop with a "never drop unconditionally" invariant to get right) for a case that, per the incident writeup, is rare enough that a clean halt-and-retry is an acceptable cost.

## Q&A log
