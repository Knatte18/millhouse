## Problem

A second live-dry-run session (same shape as the already-done `mill-pipeline-skill-doc-gaps` task) surfaced seven documentation/logic gaps across mill-go's Execute/dispatch surface, mill-plan's entry table, and mill-merge's entry gate.
All seven were filed as GitHub issues (#781-#787) and have already been consolidated into this wiki task (each issue closed with a "Consolidated into wiki task" pointer comment).
None of the seven blocks a currently-running task — each was worked around in-session — but each represents a real gap between what the SKILL.md text says and what the orchestrator needs to do when it actually happens again.

Why now: these are exactly the kind of gaps that only surface under real dispatch load (stalls, closed-PR re-entry, plan revision after upstream merges), and the fixes are cheap relative to the operator time lost improvising a workaround each time they recur.

## Scope

**In:**
- `mill-go/SKILL.md` "## Agent-mode dispatch" step 4: widen the classification branches so a stall/watchdog `status: failed` notification (neither an (a) API-error marker nor a stopped/interrupted signal by (b)/(c)'s literal wording) has a defined home, for both the implementer (b) and reviewer/fixer (c) sub-cases.
- `plugins/mill/docs/harness-tool-contracts.md`: document that Agent-tool `<task-notification>`s carry a `<status>` tag (confirmed live during this discussion), correcting the current text that implies message-text is the only available signal on that path.
- `implementer-brief.md`: a lightweight heartbeat-nudge instruction for long, silent verify commands (issue #787), to reduce (not eliminate) the recovery cost of a legitimate stall.
- `mill-go/SKILL.md` step 4(c): replace the mandatory `TaskOutput` liveness probe with a cheap `test -f <output_path>` check for the reviewer sub-case specifically, falling back to `TaskOutput` when the file's absence is ambiguous or for the fixer sub-case (which has no equivalent file).
- `mill-go/SKILL.md`: add the missing `signature:` lines for `_treeguard.check_and_restore` / `_status.append_recovery_log`, and make the `if result["triggered"]:` guard explicit at all 12 tree-guard checkpoint call sites.
- `mill-plan/SKILL.md`: a new `--revise` re-entry mode for an already-approved plan, including how it interacts with the on-disk review-round budget.
- `mill-merge/SKILL.md` Entry Step 4: a `status_path`-absent fallback to `cfg.git.base_branch` so the documented closed-PR re-entry path (Step 5's wiki fallback) is actually reachable.
- `mill-go/SKILL.md` (or `_implementer_common.py`, whichever is the natural site): a one-line observability note when the implementer's no-JSON inference (`"inferred": true`) path fires successfully, so a recurring trailing-JSON omission becomes visible rather than silent.

**Out:**
- The Claude Code harness's own 600s stream-watchdog constant — confirmed (see Technical context) to be outside mill's config surface entirely; not something this task can tune.
- Building orchestrator-side retry/re-prompt machinery to force the implementer to emit its trailing JSON — investigation found no prior art and a 1/8 observed failure rate does not justify it; the existing finalize-side commit-count recount is the accepted safety net (see Decisions, `implementer-status-line-omission`).
- A cheap liveness-check alternative to `TaskOutput` for the implementer (b) and fixer (c) sub-cases — investigation confirmed neither has an autonomously-written deliverable file available before its terminal notification arrives, so no equivalent to the reviewer's `output_path` check exists for them.
- Any change to `_parent_branch.py`'s or `_treeguard.py`'s actual Python implementation — both already behave correctly; every fix in scope is a `SKILL.md` documentation/logic fix, not a script bug fix.
- Restructuring verify commands into smaller per-package implementer turns (issue #787's third, heavier option) — disproportionate to this task.

## Decisions

### widen-step4-stall-classification (#785)

- Decision: widen (c)'s trigger from "stopped or interrupted notification for a reviewer or fixer dispatch" to "any non-clean terminal notification for a reviewer or fixer dispatch that is not an (a) API-error marker," where the concrete test is: **the `<task-notification>`'s `<status>` tag is present and its value is not `completed`** (observed values include `completed`, `failed`; a stall/watchdog kill surfaces as `<status>failed</status>` with the stall reason in `<summary>`), AND the message doesn't contain (a)'s literal marker text.
  Apply the identical wording widening, and the same concrete `<status>` test, to (b)'s "Stopped/interrupted notification" implementer sub-case, so an implementer-side stall (already observed in #787, and recovered correctly there only because the orchestrator improvised) has the same defined home.
  Companion doc fix: `plugins/mill/docs/harness-tool-contracts.md`'s Agent-tool section currently states only that "the notification payload carries the subagent's final message text," with no mention of a `<status>` tag — that's inaccurate for the Agent-tool path specifically (the doc's only `<status>` mention is scoped to the separate Monitor-tool contract).
  Update that section to state plainly that Agent-tool `<task-notification>`s also carry a `<status>` tag, with `completed` for clean success and other values (`failed`, `stopped`, `interrupted`) for everything else, alongside the existing message-text-based signals.
- Rationale: the existing five-value `stuck_type` taxonomy (`transient`, `verify`, `logic`, `infrastructure`, `incomplete`) is already exhaustive for *outcomes*; the gap is purely in notification-*classification* routing (which of a/b/c a stall notification lands in), not a missing outcome type.
  The original discussion draft cited the issue's literal `<status>failed</status>` example without confirming the notification actually carries a structured `<status>` field at all — `harness-tool-contracts.md` as written implies message-text is the only signal for the Agent-tool path, which would make "non-clean" untestable without fragile text-pattern matching.
  This is now confirmed: live task-notifications received during this very discussion/review session (for Agent-tool-dispatched work) carried literal `<status>completed</status>` tags, so the field exists on this path and a structured `!= "completed"` check is the correct, reliable signal — not a message-text heuristic.
  Widening (c) — and (b)'s mirrored sub-case — to test this field closes the gap with no new machinery: the probe-then-retry path already handles a dead agent correctly (confirmed by the #785 incident's own manual recovery, and by #787's implementer-side recovery).
- Rejected: a new explicit fourth branch just for stall/watchdog — unnecessary complexity, since (c)'s existing recovery logic already applies cleanly once the notification reaches it; leaving step 4 unchanged — the reported gap forces every orchestrator to improvise the same judgment call each time; keying on message-text patterns instead of the `<status>` tag — less reliable, and unnecessary now that the structured field is confirmed present.

### heartbeat-nudge-for-long-verify (#787)

- Decision: add a short instruction to `implementer-brief.md`'s verify-command guidance: when a batch's `verify:` command runs multiple sequential sub-invocations (e.g. several `go test` / `go test -tags integration` calls), emit a brief progress line (e.g. `Running: go test ./builderengine/...`) before each sub-invocation, rather than staying silent until all verify output returns at once.
- Rationale: the 600s stream watchdog that killed the #787 implementer mid-verify is a Claude Code harness constant, confirmed (via full-file grep of `mill-go/SKILL.md` and the nearby `llm.*_timeout` config keys in `mill-config.yaml`, which turned out to gate only `subprocess`/`psmux`-mode LLM-provider calls, not Agent-tool background dispatch) to be outside any config mill exposes.
  The only lever available from mill's side is what the dispatched agent itself outputs during a long silent phase.
  A cheap heartbeat line addresses the root cause (harness reads "no output for 600s" as stalled) directly, complementing rather than replacing the reactive recovery from `widen-step4-stall-classification` above, and materially reduces the ~10-minute/~1.5M-token cost of a full second implementer dispatch observed in the #787 incident.
- Rejected: relying solely on reactive recovery — cheaper to write, but leaves the full redo cost in place every time a legitimately slow, silent verify run trips the watchdog; restructuring verify into smaller per-package turns — a much larger change disproportionate to the actual problem (a missing print statement).

### cheap-liveness-check-reviewer-only (#784)

- Decision: in step 4(c), before calling `TaskOutput`, add a `test -f <output_path>` check for the reviewer sub-case, using `output_path` already extracted from the prepare envelope in step 2 (per step 6's existing convention: "For the three review CLIs, `<path>` is the `output_path` field read verbatim from step 2's prepare envelope").
  If the file exists, treat the reviewer as no-longer-running and proceed straight to the existing post-probe branching (skip `TaskOutput` entirely).
  If the file does not exist, the result is ambiguous (could be still-running or dead-before-writing) — fall back to `TaskOutput` exactly as today.
  Leave the fixer sub-case of (c), and the implementer's mirrored probe in (b), using `TaskOutput` unchanged.
- Rationale: investigation confirmed the reviewer CLI is the only one of the three dispatch kinds funneling through steps 4(b)/4(c) that autonomously writes its own deliverable file (the review report) while still running — that is the review-CLI contract itself.
  Fixer and implementer dispatches have no such file: per step 6's existing convention, "implementer, fixer, and merge-in CLIs ... carry no `output_path` field" and their `<brief_path>.out.md` is written by the *orchestrator*, after the terminal notification already arrives — so checking for its existence cannot distinguish "still running" from "dead" for those two.
  Scoping the fix to reviewer-only avoids inventing a check that doesn't actually work for fixer/implementer, and matches the issue's own literal suggested fix.
- Rejected: building an equivalent cheap check for fixer/implementer (e.g. a live commit-count probe mirroring finalize's own recount) — technically possible but meaningfully more machinery, and not what #784 reported; can be revisited separately if fixer/implementer's `TaskOutput` cost is later shown to be a comparable problem.

### treeguard-signature-and-guard (#783)

- Decision: add one `signature:` line for each of `_treeguard.check_and_restore` and `_status.append_recovery_log` at the first tree-guard occurrence in the file (the per-batch review loop's per-round checkpoint, currently line 638), with a note that all 11 other tree-guard checkpoints in the file share this signature.
  Separately — and independently of where the signature text lives — rewrite all 12 call sites' prose to show the guard explicitly, e.g.:
  `result = _treeguard.check_and_restore(worktree_root, "_mill", git_root=git_root)` then `if result["triggered"]: _status.append_recovery_log(status_path, result["timestamp"], result["restored_paths"])`,
  instead of the current unguarded "on trigger, call `_status.append_recovery_log(...)`" prose.
  The confirmed real signatures: `_treeguard.check_and_restore(worktree: Path, tracked_root: str = "_mill", *, git_root: Path | None = None) -> dict` returning `{"triggered": bool, "restored_paths": list[str], "timestamp": str | None}`; `_status.append_recovery_log(status_path: Path, timestamp: str, restored_paths: list[str]) -> None`.
- Rationale: the crash is caused by the missing guard, not the missing signature — every one of the 12 call sites independently needs the guard spelled out in its own snippet, because each is a copy-pasteable unit an orchestrator follows in isolation without cross-referencing another part of the file.
  The signature, by contrast, is genuinely one fact worth stating once with a forward reference, per the file's own "Helper signatures are documented inline" principle — repeating the identical one-liner 12 times adds no information, only maintenance surface if the signature ever changes.
- Rejected: repeating the full signature at all 12 sites — literal compliance with the Principles wording, but pure duplication for a value that never varies by call site; adding the signature without touching the 12 snippets' guard — would satisfy the Principles rule but leave the actual `TypeError` crash unfixed, which is the entire point of #783.

### mill-plan-revise-reentry (#786)

- Decision: add a new "**Entry step 0.5 — Parse arguments**" section to `mill-plan/SKILL.md`'s Entry, inserted immediately after the existing "Step 0: Load `mill:conversation`" and before Entry step 1, following the token-walk-with-unknown-token-halt convention already used by `mill-setup/SKILL.md`'s own "Phase 0 — Parse arguments" section.
  Name it "step 0.5," not "Phase 0": mill-plan's Entry already reserves "Step 0" for loading `mill:conversation` and uses unnumbered `### Phase: ...` headings exclusively for the later named phases under `## Phases` (`Phase: Plan`, `Phase: Plan Review`, etc.) — reusing "Phase 0" here would collide with both conventions in the same file.
  The fractional "0.5" numbering matches this plugin's own established precedent for an inserted sub-step (e.g. `mill-merge/SKILL.md`'s "1.5. Path Setup").
  Position it before step 1 rather than folding it into Step 0 itself, since Step 0 is specifically the `mill:conversation` load and mixing argument-parsing into it would blur two distinct responsibilities; position it before (not after) path resolution since parsing `$ARGUMENTS` doesn't depend on any resolved path.
  Recognize a `--revise` flag, valid only when **both** `phase: planned` (checked via `_status.read_full(status_path)["yaml"].get("phase")`) **and** the overview frontmatter's `approved:` is currently `true`; on any other token, halt with a usage hint per the existing convention.
  The `phase: planned` guard is required, not optional: `approved:` is confirmed to stay `true` for the entire duration of mill-go's run (Prepare through Handoff — mill-go never resets it), so `approved: true` alone cannot distinguish "freshly approved, mill-go hasn't started" from "mill-go is mid-execution or already `done`."
  `phase: planned` is the narrow, correct window — it is the exact phase mill-plan's own Handoff leaves behind, and mill-go's Entry-step Prepare immediately overwrites it to `implementing` the moment execution actually starts (confirmed: `mill-go/SKILL.md` line ~192, `_status.append_phase(status_path, "implementing", ...)`), so `phase: planned` can only be true in the intended pre-execution window.
  On any other phase (`implementing`, `reviewing-*`, `holistic-reviewing`, `done`, etc.) with `--revise` passed: halt with an explicit message naming the current phase and stating that revising a plan mill-go has already started or finished executing is unsupported — do not silently force-flip `phase: planning` onto a task with committed/approved batches.
  When `--revise` fires: (1) flip `approved: false` in `plan/00-overview.md` via the same direct-Edit convention the file already uses elsewhere for this field (no `_status.py` involvement, since `approved:` intentionally lives outside `status.md`); (2) call `_status.append_phase(status_path, "planning", timestamp)`; (3) commit both mutations together on the task branch; (4) fall through into the existing row-45 re-entry path (`phase: planning`, overview exists, `approved: false` → Phase: Plan Review, do NOT rewrite plan files) unmodified.
  Give the revision pass its own round-numbering namespace via a **subdirectory**, not a filename convention: `RE_SIMPLE`/`RE_BATCH` in `_review_common.py` are fixed-shape regexes (`^\d{8}-\d{6}-(discussion|code|plan)-review-r(\d+)\.md$`, no room for a distinguishing prefix), so a filename-only scheme either collides with the original pass's numbering or never matches at all — a distinct subdirectory is the only form that actually works, since the same regexes still match normally once scoped to a different `reviews_dir`.
  This requires a new `--reviews-subdir <name>` flag threaded through **three** `reviews_dir = resolve_path(cfg["paths"]["reviews_dir"], slug)` call sites, not two: `_review_plan.py`'s `prepare()` (line ~369) and `run()` (line ~696), **and** `millpy-review-plan.py`'s own `--stage finalize` handler (line ~223), which independently resolves `reviews_dir` before calling `_review_plan.finalize(..., reviews_dir=reviews_dir, ...)` — `finalize()` takes `reviews_dir` as a caller-supplied parameter and never re-resolves it itself, and the prepare envelope carries no `reviews_dir` field for finalize to inherit, so prepare and finalize are independent resolutions that must both receive the override or the round file gets discovered under the subdir but written to the original directory.
  The subdirectory name is computed at Entry step 0.5, not hardcoded to `revise-1`: scan `<reviews_dir>/` for existing `revise-<N>` subdirectories, take the max `N` found (or `0` if none exist), and use `revise-<N+1>` for this invocation — the same max-plus-one pattern `discover_round` already applies to round files, applied one level up at the subdirectory level.
  This supports any number of `--revise` passes on the same task over time, each getting its own full round budget and its own fully preserved audit trail — a second `--revise` (e.g. after the first revision was re-approved and mill-go later needs another correction) resolves to `revise-2`, never colliding with or overwriting `revise-1`.
  Resolves to that computed `<reviews_dir>/revise-<N+1>/` at all three plumbing sites — mirroring the existing `--reviewer` flag's "override for this invocation only, nothing written back to config" contract.
  mill-plan's `--revise` entry passes this flag on every prepare/finalize call for the revision pass.
  `--revise`'s scope is strictly re-review, not content authorship: it re-enters the Plan Review loop to re-examine the existing plan files against current source, which is what organically catches drift from merged upstream changes — the issue's own motivating case.
  It carries no operator-authored change-reason token or free-text input channel; if the operator wants a specific content change beyond what re-review would naturally re-flag (e.g. deliberately adding new scope), they edit the plan files directly via `Edit` before invoking `--revise`, exactly as any other manual plan intervention already works in this file — `--revise` only handles the re-entry and round-bookkeeping mechanics, consistent with mill-plan's autonomous design ("mill-plan never pauses mid-phase to ask the user").
- Rationale: `--revise` matches existing plugin precedent exactly (mill-setup already token-walks `$ARGUMENTS` this way) and reuses the Plan Review loop's *review-execution* logic unmodified once the two flags are flipped — only round-number *discovery and reporting* needs a new hook, because neither `_review_plan.py` nor `millpy-review-plan.py`'s own finalize handler has an existing parameter for redirecting `reviews_dir` per-invocation (confirmed: all three call sites read it straight from `cfg["paths"]["reviews_dir"]` with no override).
  The round-budget problem is real and was flagged explicitly by the issue: `discover_round` (in `_review_common.py`) has no concept of "revision pass" versus "original pass," it purely scans `reviews_dir` and returns `max(found) + 1` — so without a distinct namespace, a revision pass silently inherits however many rounds the original pass already consumed against the same `roles.plan-review.holistic.rounds` cap, and could hit the cap prematurely through no fault of the revision itself.
  A distinct namespace gives the revision pass its full configured budget and keeps the original pass's audit trail completely undisturbed — no files moved, nothing renamed.
- Rejected: an entry-table row keyed on an on-disk sentinel file instead of a CLI flag — no established convention for that kind of signal anywhere in this codebase, and it would need new state-storage machinery a flag doesn't; continuing round-numbering as today (silent budget shrink) — simplest, but directly contradicts the issue's explicit concern and could strand a revision pass mid-review with no rounds left; archiving/moving old round files to reset numbering — resets the count correctly but relocates the original pass's history, which a fresh namespace avoids doing; a fixed `revise-1` literal with no repeat-revision handling — collides with itself on a second `--revise`, silently overwriting the first revision's audit trail; adding an operator-authored free-text reason token threaded into the re-dispatched review brief — heavier machinery than the issue's own motivating case (drift from merged prerequisites) requires, and inconsistent with mill-plan's autonomous, no-mid-phase-prompt design; direct plan-file `Edit` before `--revise` already covers the operator-directed-content case without new input plumbing.

### mill-merge-status-absent-fallback (#782)

- Decision: in `mill-merge/SKILL.md` Entry Step 4, add a check for `status_path.exists()` before calling `_parent_branch.resolve(status_path, interactive=False, expected_slug=slug)`.
  When `status_path` does not exist at all, skip the `resolve()` call entirely and set `parent_branch = cfg.git.base_branch` directly (already loaded in Entry Step 1, with its own documented fallback to `"main"` when absent).
  When `status_path` exists, call `resolve()` exactly as today, including its existing `ParentBranchError` handling for the "file exists but no `parent:` row" case, which is unaffected by this change.
  No reordering of Entry Step 4 relative to Step 5.
- Rationale: investigation confirmed nothing between Entry Steps 1-3/1.5 and Step 5's phase gate consumes Step 4's resolved parent-branch value — every consumer (`## Steps` Step 1's merge-lock, Step 5's branch-protection fallback, Step 9's notify call) runs downstream of Step 5's phase gate regardless of where Step 4 sits, so reordering buys nothing on its own.
  What actually causes the crash is that `_read_parent_from_status` (in `_parent_branch.py`) treats "file missing" identically to "file present but no `parent:` row," so `resolve()` raises `ParentBranchError` in non-interactive mode either way — reordering Step 4 to run after Step 5 would only relocate the same crash to fire slightly later, still inside the status.md-absent case Step 5 is specifically designed to route around via its wiki fallback.
  The existence check is the minimal, surgical fix: it targets exactly the one case (`status_path` absent entirely) that Step 5's own documentation already calls out as reachable ("the `closed` route can be reached from a `pr-pending` re-entry where `_mill/status.md` is typically absent"), and `cfg.git.base_branch` is not merely a fallback approximation here — since this scenario is only reachable via `require_pr_to_base: true`, `base_branch` **is** the actual parent branch for that flow.
- Rejected: reordering Step 4 to run after Step 5 (with or without the fallback) — confirmed unnecessary once the existence-check fallback exists, and touches significantly more of the file's control flow for no additional correctness benefit.

### implementer-status-line-omission (#781)

- Decision: no further changes to `implementer-brief.md`'s trailing-JSON instruction itself.
  Add exactly one new, self-contained mechanism instead: a new `_status.append_inferred_success_log(status_path, batch_name, round, timestamp)` helper, modeled directly on the existing `_status.append_recovery_log`'s convention (lazily create a `## Inferred-success log` section in `status.md` on first use, append-only on every subsequent call — mirroring `## Tracked-file recovery log`'s own established pattern).
  Call it at **two** sites, both standalone commits made at the exact point each finalize envelope is examined, neither piggybacked on any other call, neither touching the `phase:` field: (1) step 4(b)'s Clean mid-work stop `status: success` sub-case (`mill-go/SKILL.md` line ~273), immediately when that first finalize envelope has `inferred: true`, before "proceed normally to step 7"; and (2) step 6.5's "After recovery" bullet 3 (line ~342, "`status: success` (or inferred success) means the batch finished — proceed normally"), immediately when the post-recovery finalize envelope has `inferred: true`, before proceeding normally.
  Both sites are needed: an implementer that goes `incomplete` on its first turn (no JSON, partial commits) and then completes cleanly on the resumed turn without emitting JSON produces an `inferred: true` envelope only step 6.5 sees — step 4(b)'s call alone would silently miss that occurrence, undermining the whole point of the note (visibility into every occurrence of the protocol violation, not just first-turn ones).
  When `inferred` is absent or `false` (the implementer reported the JSON line normally), this new call is skipped entirely — the existing success path is otherwise unchanged.
  This is genuinely new machinery, not an addition alongside an existing status-append call: step 4's own classification block (lines 199-357) makes no `_status.append_phase`/commit calls anywhere today, confirmed by grep; every existing append/commit site sits in structurally separate sections finalize's outcome routes to afterward, and which one of those runs next varies (e.g. the `approved-{batch_name}` append at line ~630 fires only when per-batch code review is disabled, so it cannot be relied on as the anchor).
- Rationale: investigation found the brief already states the trailing-JSON requirement four times across ~60 lines, each bolded, including a dedicated anti-truncation paragraph (telling the implementer to emit the JSON early *and* duplicate it at the end) that already anticipates the general failure shape — there is limited remaining headroom for prompt-side reinforcement alone to close the observed gap, especially since the #781 incident explicitly had no turn-budget pressure, the one scenario the existing mitigation targets.
  Separately, the finalize-side commit-count recount (`_implementer_common.py`'s no-JSON inference path) is confirmed to already work correctly and generally — it recovered the #781 incident transparently (all 7 declared cards matched commits, correctly inferred `status: success`) and applies symmetrically across the success/incomplete/stuck outcomes, not as a narrow special case.
  Given a 1/8 observed failure rate and a safety net that already produces the correct outcome, the actionable gap is visibility, not correctness: nothing currently distinguishes "the protocol was followed" from "the protocol was violated but the outcome happened to be fine," which matters if the omission rate ever climbs.
- Rejected: building orchestrator-side retry/re-prompt machinery that detects a missing JSON line and re-prompts the same implementer session before falling back to the recount — investigation found no prior art for this pattern anywhere in the codebase, and a 1/8-observed rate with an already-correct fallback does not justify the added complexity; making no change at all — would leave a real (if low-frequency) protocol violation completely untracked, with no way to notice if it becomes systemic.

## Technical context

- `mill-go/SKILL.md`'s "## Agent-mode dispatch" step 4 (lines ~242-293) is the single site for all classification-branch and liveness-probe changes (#785, #784).
  Step 4(b) (implementer, lines 258-267) and step 4(c) (reviewer/fixer, lines 283-293) are separate, explicitly-mirrored code paths — a fix to one's wording/logic does not automatically apply to the other; both must be edited.
- Step 4's "Deliberately no ack predicate" note (lines 252-257) is adjacent to (a) but is not a fourth classification branch — do not disturb it while widening (c).
- The 12 tree-guard checkpoint call sites (#783) span two sections: the per-batch "### 3. Code Review loop" (lines 638, 675, 710, 775, 780) and "## Holistic code review" (lines 1026, 1038, 1079, 1088, 1093, 1126, 1133) — five pre/post pairs plus two combined-form occurrences (lines 638, 1026).
  All 12 must be updated identically; there is no shared helper section they all delegate to (each is inlined at its own call site by design, per the file's existing "Do not add this checkpoint inside the shared '## Agent-mode dispatch' section itself" notes).
- `_treeguard.check_and_restore`'s actual signature and return shape (confirmed by reading `plugins/mill/scripts/_treeguard.py` directly): `check_and_restore(worktree: Path, tracked_root: str = "_mill", *, git_root: Path | None = None) -> dict`, returning `{"triggered": bool, "restored_paths": list[str], "timestamp": str | None}` — `timestamp` is `None` whenever `triggered` is `False`, which is exactly what makes the current unguarded `_status.append_recovery_log(status_path, result["timestamp"], ...)` call crash with `TypeError: quote_scalar requires str, got 'NoneType'`.
- `_status.append_recovery_log`'s actual signature (confirmed by reading `plugins/mill/scripts/_status.py`): `append_recovery_log(status_path: Path, timestamp: str, restored_paths: list[str]) -> None`.
- `mill-plan/SKILL.md`'s Entry section (lines 39-48) has zero argument-parsing today — no `$ARGUMENTS` handling anywhere in the file.
  `--revise` needs a new Entry step 0.5 section; the precedent in this plugin is `mill-setup/SKILL.md`'s "### Phase 0 — Parse arguments" (lines 99-116, `--from-url`/`--branch`), which token-walks `$ARGUMENTS` left-to-right with an explicit "unknown token" halt.
  `git-pr/SKILL.md` (line 38/45-48) is not an equivalent precedent — it only strips/ignores one specific flag (`--skip-task-branch-guard`) via a substring case-match and takes the first remaining token positionally, with no unknown-token halt at all — so mill-setup, not git-pr, is the model to follow for `--revise`'s parsing behavior.
- `approved:` lives in `plan/00-overview.md`'s frontmatter, not `status.md`, and is intentionally outside `_status.py`'s management (`mill-plan/SKILL.md`'s own "## Board discipline" section states this explicitly).
  Every existing write site uses "direct Edit," not a helper function — `--revise` should follow the same convention rather than introducing a new `_status`-style setter for a single field.
- Round-number discovery for plan review is `discover_round(reviews_dir, review_type, scope) -> int` in `plugins/mill/scripts/_review_common.py` (lines ~496-541): lists `reviews_dir`, regex-matches filenames (`RE_SIMPLE` for holistic, `RE_BATCH` for per-batch) filtered by `review_type`/`scope`, returns `max(found) + 1` or `1` if none found.
