## Decisions

### 1084-entry-table-row

- Decision: Add a row to mill-plan/SKILL.md's Entry step-4 table, between the `phase: discussed, no plan_dir` row and the `phase: planning/plan-review-*/plan-fix-*` re-entry row: `phase: discussed` with `plan_dir/00-overview.md` existing on disk → treat identically to the re-entry row (enter Phase: Plan Review; do NOT rewrite plan files).
- Rationale: the only way `plan_dir` exists while `phase` is still `discussed` is that Phase: Plan's file writes landed but its own commit (which bundles the plan files with the `phase: planning` status write, per "Update `_mill/status.md`" → "Commit on the task branch") never completed — an interrupted run, or a deliberate draft-now/finalize-later split (the issue's own repro). Resuming into Plan Review is safe either way: Plan Review re-validates the DAG and re-runs `_plan_validate` (Step 1.5) before ever dispatching a reviewer, so a genuinely broken/partial `plan_dir` is still caught. This matches the issue's own "Expected" text.
- Rejected: halting with a message naming the condition (the issue's other suggested remedy) — the validator gate makes resuming strictly safer with no extra information lost, so a halt would only add an unnecessary operator round-trip.

### 1083-allow-missing-refs

- Decision: Add an opt-in `allow_missing_refs: bool = False` keyword to `_review_common.resolve_ref_paths`, applied only at `Context:`-only call sites — never `Edits:`/`Creates:`/`Deletes:`, which name files the batch is expected to produce or touch and must keep hard-failing. When `True`, a `Context:` ref that is not on disk, not in `creates_union`/`deletes_union`, and not confirmed git-ignored is skipped with a stderr warning (`[resolve_ref_paths] warning: skipping missing Context: ref '<raw>' (not on disk, allow_missing_refs)`) instead of raising `ReviewError`. Add a matching `--allow-missing-refs` CLI flag to `millpy-review-plan.py` (next to the existing `--skip-check`), threaded through `_review_plan.prepare()`'s new `allow_missing_refs` parameter into every `context_reads`/`all_context_reads` call site: `_review_one_batch` (batch scope, `--stage full`/subprocess), `prepare()`'s batch-scope branch, `prepare()`'s holistic-scope branch (used by agent-mode `--stage prepare`, this hub's configured dispatch mode), and `run()`'s own holistic branch (`--stage full`). All four call sites must accept the flag for parity across dispatch modes, even though this hub's `dispatch: agent` config only exercises `prepare()`/`finalize()` today.
- Rationale: mirrors the exact shape the issue asks for ("the shape `soft_fail_gitignored` already uses"); restricting to `Context:` keeps the check meaningful for a batch's own edit targets.
- Rejected: a blanket bypass of the whole bulking step — would also suppress genuine typo-path hard-fails, which the issue does not ask to lose.
- Rejected: extending `soft_fail_gitignored` itself to also cover non-gitignored missing paths — would silently change what existing `soft_fail_gitignored=True` callers mean today; a distinctly-named flag keeps "gitignored artifact" and "not-yet-merged predecessor file" separately auditable in warning text.

### 1076-batch-sizing-split-by-file-union

- Decision: Add one sentence to mill-plan/SKILL.md's "Batch sizing" section, right after the existing ">80% shared Context: → merge" sentence: when a batch's cards collectively cite several large pre-existing files whose combined `Context:`/`Edits:`/`Creates:` byte total exceeds `pipeline.max_batch_context_tokens` even though no single file does, split by which file each card edits rather than by feature/mechanism, so each resulting batch's own file-union stays under cap even when the underlying mechanisms are tightly coupled. Add the matching remedy to the `batch-oversized` fix-table row in Phase: Plan Review Step 1.5, before its existing "Halt" sentence: when the overage comes from the combined size of several large pre-existing files (not any single one) and the `context-completeness` signature-inlining escape hatch doesn't apply to any of them, split by edited-file union size rather than by feature.
- Rationale: names the exact working remedy the issue discovered, in both places a planner encounters batch-sizing guidance — proactively (Batch sizing) and reactively (the fix-table row once the check has already fired).
- Rejected: editing only the fix-table row — the proactive section is what should prevent needing the reactive split in the first place; the issue's own repro shows the remedy was only found after the check fired.

### 1063-discussion-sha-nested-path

- Decision: At all three call sites in mill-plan/SKILL.md — Phase: Plan's initial `discussion_sha` capture, Phase: Plan's pre-commit drift check, and Phase: Plan Review's discussion drift guard — replace the hardcoded `git -C <git_root> rev-parse HEAD:_mill/discussion.md` with `git -C <worktree_root> rev-parse HEAD:./<cfg['paths']['discussion_file']>`: run `-C` against the hub root (`worktree_root`, already bound at Entry step 1) instead of `git_root`, prefix the path with `./` so git resolves it relative to the `-C` cwd instead of the repository top level, and read the path from `cfg['paths']['discussion_file']` instead of the literal string (matching the file's own existing, currently-dead "or the config-derived relative path... if it differs" parenthetical).
- Rationale: matches the issue's own "Expected" text verbatim ("run the command with `-C <hub_root>` and a `:./`-prefixed path"); this form is correct in both the flat layout (this repo, `worktree_root == git_root`) and a nested layout (NORCE Models, `worktree_root` a subdirectory of `git_root`) with no branching logic needed.
- Rejected: manually computing `<hub-relative-to-git-root> + cfg['paths']['discussion_file']` and keeping `-C git_root` — strictly more code for the same result git's own `-C`+`./` resolution already gives.

### 1056-cross-batch-build-break-check

- Decision: Add a new `_plan_validate` check, `cross-batch-build-break`, gated on the overview's **existing** top-level `verify:` frontmatter field (`plugins/mill/templates/plan-overview.md` already documents it as an OPTIONAL "whole-module compile/vet/smoke command" run at each batch boundary — no new field). The check runs only when that field is non-null. When active: (a) collect every card's `Requirements:` text plan-wide; (b) pattern-match a fixed set of rename/removal phrasings — `rename <backtick symbol> to <backtick symbol>`, `remove <backtick symbol>`, `delete <backtick symbol>` — into a list of `(batch_number, old_symbol)` pairs; (c) for each pair, grep the worktree (excluding the renaming batch's own `Edits:`/`Creates:` targets, and every batch at or before it in dependency order) for the literal `old_symbol`; (d) if a hit lands in a batch that depends-on-follows or is unordered relative to the renaming batch, and that later batch's own `Requirements:` doesn't already list the same symbol update, emit a finding naming both batches, the symbol, and the hit file:line. Fix-table remedy: add the missing `depends-on` edge, or add a `### Decision:` acknowledged-degrade subsection under Shared Decisions (mirroring the plan's existing acknowledged-degrade convention, e.g. `windows-status-line-is-an-unbranched-accepted-degrade`) when the sequencing is intentional.
- Rationale: the issue's own suggested shapes (symbol-diffing, or a Shared-Decision-style acknowledgment) map directly onto the acknowledged-degrade convention plans already use, so the remedy needs no new mechanism, only a new detection. Gating on the existing `verify:` field (rather than a new one) needs no template change and no new frontmatter surface — the field's own documented purpose ("catches cross-package regressions from shared-helper edits at the introducing batch") already signals exactly the whole-module build sensitivity this check cares about.
- Rejected: a new `verify_module:` field duplicating `verify:` — this was this discussion's first draft, corrected after discussion-review round 1 (see Q&A log) flagged that `plan-overview.md` already has a top-level `verify:` field with the identical purpose (a whole-module compile/vet/smoke command run at each batch boundary); a second field holding essentially the same command would be pure duplication with no rejected-alternative justification.
- Rejected: making the check unconditional — a plan with `verify: null` has no real "does it build at every batch boundary" question, and a purely textual rename/removal grep would false-positive with no way to tell "breaks the build" from "just changes wording"; gating on `verify:` being set keeps it precise.
- Rejected: actually running the `verify:` command after simulating each batch's DAG-ordered state during plan review — far too expensive for a review-time static check (would require materializing every intermediate batch state in a scratch worktree); `mill-go`'s own runtime verify gate already exists for the runtime case, this is a planning-time review addition, not a replacement for it.
- Rejected: widening the phrasing set beyond the three fixed patterns now — scope creep; the three cover the reported incident (`reedengine.Engine.HeaderText -> StatusLineText`) and can be extended later on a real false-negative report, per YAGNI.

### 1054-finalize-advances-round

- Decision: Two changes. (a) In `_agent_dispatch.write_brief`, before its existing unconditional `output_path_for(brief_path).unlink(missing_ok=True)`, check whether that `.out.md` already exists and print a stderr warning (`[write_brief] warning: overwriting existing unfinalized output '<path>' -- if this round's finalize already ran, its result is about to be lost`) before unlinking — a warning, not a refusal, because a transient-retry re-dispatch (the function's own documented, legitimate reuse case) must keep proceeding unattended. (b) Add a paragraph to mill-plan/SKILL.md's Phase: Plan Review step 2, immediately before the "If `agent` (Claude provider only): follow the Agent-mode dispatch pattern..." branch line (not before step 2's opening "Waiting is never a decision point" / dispatch-mode-resolution text, which precedes the Agent-mode-vs-subprocess split by several paragraphs), stating plainly that `--stage finalize` is what writes the review file into `reviews_dir` and is therefore what makes the next `--stage prepare`'s round-discovery advance past this round — reading the reviewer's `.out.md` directly is not equivalent to calling finalize, and skipping finalize silently re-issues the same round number next time while deleting the just-produced `.out.md`.
- Rationale: (a) is the mechanical warning the issue's "Suggested fix" names first; (b) is the doc statement the issue asks to see in mill-plan's own text, not only in `mill-go-base/SKILL.md`.
- Rejected: making `write_brief` refuse outright when a stale `.out.md` exists — would break the existing legitimate transient-retry re-dispatch path (same round, same `.out.md` path, by design); there is no existing signal that distinguishes that from "orchestrator forgot to finalize" without inventing new state this task doesn't need.

### 1045-numbered-round-recorded-append

- Decision: Rename the "**Unconditional round-recorded append.**" paragraph heading in mill-plan/SKILL.md's Phase: Plan Review to "**Step 3.6: Unconditional round-recorded append (no round consumed).**", matching the file's existing `1.5.`/`3.5.` numbering convention for a same-round side-step between two main numbered steps. No change to the paragraph's own wording or logic — the existing text (already unconditional and decoupled from the 4a/4b/4c/4d branch) is correct; only its structural signposting needed to change.
- Rationale: this is the issue's first suggested remedy exactly; a numbered step reads as a mandatory action in sequence, not as background explanation for 4a/4b/4c's own appends — the original mis-scan failure mode.
- Rejected: the issue's second suggested remedy (adding cross-reference text inside each of 4a/4b/4c/4d) — redundant once the step has its own number: 4a/4b/4c/4d already immediately follow "Step 3.6" in document order, the same way "Step 1.5" needs no restatement from steps 2/3.

### 1086-discussion-immutability-and-descope-path

- Decision: Two changes. (a) Add a "**Post-Handoff immutability.**" paragraph to mill-start/SKILL.md's Phase: Handoff: once this phase's `_status.append_phase(status_path, "discussed", ...)` commits, `discussion_path` must not be edited again by mill-start, in this session or a later one — `phase: discussed` is mill-plan's entry-gate signal, and a mill-start that keeps mutating discussion.md after raising it races mill-plan and makes the gate meaningless; a correction discovered after Handoff is reported to the operator as a note for the next task/gap, not edited in directly. (b) Add one sentence to mill-plan/SKILL.md's two discussion-drift-guard `BLOCKED:` halt messages (the pre-commit drift check and the Phase: Plan Review discussion drift guard — the initial `discussion_sha` capture itself is not a halt site): if the drift is a pure scope narrowing (dropping something the plan hasn't started yet) rather than a new requirement, `/mill-descope-batch` may be the cheaper fix instead of discarding the plan.
- Rationale: (a) closes "problem 1" (the race is not detectable by waiting longer, so it must be prevented at the source); (b) answers "problem 2"'s ask for "at minimum, a documented operator-sanctioned patch path" by pointing at the one skill already shaped for exactly the reported incident (a pure scope removal mapping onto one not-yet-started batch).
- Rejected: building a narrowing-vs-change classifier into the drift guard itself (the issue's own heavier option) — speculative machinery for a one-off incident; the existing manual `/mill-descope-batch` skill gives the same two-minute-patch outcome without new automatic-classification logic this task has no second incident to validate against.
- Rejected: letting mill-plan silently proceed past drift when it "looks like" a narrowing — that judgment call is exactly what let the original incident pass two review rounds undetected; a hard halt with a cheaper documented recovery path is safer than a heuristic auto-continue.
