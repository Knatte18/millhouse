## Problem

Four related-but-distinct bugs, bundled from closed GitHub issues #730, #737, #729, and #728, all in mill's wiki/worktree/config-resolution layer:

1. **#730** — no mill skill or the wiki daemon's `health_check` fetches/fast-forwards the local `.wiki` clone against `origin` before reading it. A task pushed to the wiki from another machine is silently invisible on a second machine until a manual `git fetch` + `git merge --ff-only` inside the wiki clone.
2. **#737** — `health_check()` only confirms the daemon process is reachable; it never verifies the wiki directory is actually a valid git repo. A session ran an entire `mill-go` pipeline against a `.git`-less wiki, with every daemon-restart's `.gitignore` chore-commit silently logged as a warning, only surfacing when `set_phase` at Handoff raised `WikiPushError`.
3. **#729** — `mill-resume` Phase 1 only checks for `.millhouse/config.local.yaml` and a `.wiki` junction at cwd; if either is missing it unconditionally tells the user to run `mill-setup`, which is the wrong remedy for a task worktree that already exists on disk (e.g. hand-created via `git worktree add` at a non-canonical path) with `_mill/` state already committed on the branch.
4. **#728** — `millpy-implement.py`, `millpy-fix.py`, `millpy-abandon.py`, and `millpy-merge-in-subagent.py` each call `_review_common.load_config(git_root, mill_dir)` with the outer git-repo root instead of the resolved hub root, silently missing the hub's own `mill-config.yaml` whenever the hub lives in a subdirectory of the git repo (blocked mill-go's implement/fix dispatch entirely for a hub-in-subdirectory repo).

**Why now:** all four surfaced from real cross-machine / non-standard-layout usage (a loomyard resume on a fresh machine, a NORCE-DrillingAndWells hub-in-subdirectory repo) and were independently reported and closed as issues; this task bundles them because they all live in the same "mill assumes a clean, canonical, single-machine setup" blind spot.

## Scope

**In:**

- `wiki/_client.py`'s `health_check()`: return semantics updated so a missing/invalid git repo is a hard failure; a fetch/network failure is a soft warning (health_check still reports OK). On hard failure, log the underlying reason (not just a bare `False`) — see health-check-error-surfacing.
- `plugins/mill/skills/mill-resume/SKILL.md`: add an explicit `_client.health_check(wiki_path)` call (Phase 1, before Phase 2's `list_tasks_brief` candidate-listing query) — mill-resume today never calls `health_check` anywhere, so the wiki-health-check-scope fix would not otherwise reach the literal #730 repro path (a fresh-machine mill-resume listing).
- `plugins/mill/skills/mill-go/SKILL.md`: update the two `health_check()`-failure halt blocks (lines ~206-216, ~594-604) to surface the actual daemon-reported failure reason instead of only the fixed generic string, and to stop implying "re-run mill-setup" is the fix for every failure cause — see health-check-error-surfacing.
- `plugins/mill/skills/mill-resume/SKILL.md`: Phase 1's halt condition itself changes to branch on `_mill/status.md` presence at cwd before halting (see mill-resume-detection-point below), plus a new phase (inserted after Phase 1, not renumbering existing phases) that detects an already-existing, off-canonical, under-scaffolded task worktree (when mill-resume — or, per its own doc, "any mill skill" — is invoked from inside such a worktree) and repairs it: safety check for uncommitted changes, user confirmation, collision check against the canonical path, `git worktree move` to the canonical `<container>/wts/<slug>` path, then Phase 7/8's copy-`.millhouse`/create-`.wiki`-junction steps.
- `millpy-implement.py`, `millpy-fix.py`, `millpy-abandon.py`, `millpy-merge-in-subagent.py`: fix the `load_config(...)` call to pass the already-resolved hub-rooted variable, matching `millpy-review-code.py`'s existing correct pattern. For `millpy-merge-in-subagent.py`, this also requires fixing `project_root = Path.cwd()` to resolve via `_paths.resolve_hub_path()` (cwd is not hub-rooted there today).
- `millpy-validate-plan.py`: fix `project_root = Path.cwd()` itself to `_paths.resolve_hub_path()` — the same root-computation bug as `millpy-merge-in-subagent.py`, and correcting it also fixes `mill_dir` (which derives from `project_root`) plus the two other cwd-rooted consumers of `project_root`: `find_active_slug(project_root, wiki_root, cfg)` (whose first parameter is named `hub_root` in `_review_common.py:306`) and `_plan_validate.run(plan_dir, project_root, ...)` (defined at `_plan_validate.py:2001`, threads `project_root` down to `_check_verify_not_isolated`, whose docstring at `_plan_validate.py:1455` states `project_root` "also doubles as the hub_root"). Not one of the 4 originally-named files, but the same root cause, already diagnosed.
- `millpy-merge-in-subagent.py` additionally needs its `cfg` reloaded after the script's own second, more-precise root resolution (`_paths.resolve_active_hub()` at line ~357) corrects `project_root`/`mill_dir` — see merge-in-subagent-cfg-reload.
- Regression tests: extend the existing per-script unit test files (`test-millpy-implement.py`, `test-millpy-fix.py`, `test-abandon.py`, `test-merge-in-subagent.py`, `test-millpy-validate-plan.py`) with a hub-in-subdirectory config-resolution fixture; new/extended daemon unit test for health_check's git-validity + staleness-fetch behavior; new integration test for mill-resume's relocate+scaffold flow.

**Out:**

The one genuine swallow site is `_ensure_gitignore`'s startup chore-commit, and it stays non-fatal (see Decisions).

## Decisions

### wiki-health-check-scope

- Decision: implement both the git-repo-validity check and the fetch+ff-merge staleness fix server-side, inside the daemon's `_handle_health` (`wiki/_server.py`), reusing `wiki/_sync.py:pull()` (already implements `git pull --ff-only`). No client-side git access, no new op.
- Rationale: `health_check()` is already the one chokepoint called before every batch/review dispatch in mill-go; fixing it there requires zero call-site changes there. Correction from discussion review round 4: mill-resume does **not** already call `health_check()` anywhere today (verified via grep — zero references in `mill-resume/SKILL.md`) — Phase 2's candidate listing uses `list_tasks_brief` directly, a different op that never reaches `_handle_health`. This means the fix, as scoped so far, would not by itself reach the literal #730 repro path (a fresh-machine mill-resume listing) — see mill-resume-health-check-callsite for the added scope that closes this. The daemon already owns the wiki lock and all git mutation goes through `_sync.py` — doing this client-side would bypass that lock discipline.
- Rejected: client-side git access in `_client.health_check()` (lock-safety risk); a new dedicated op (adds call-site fanout for no benefit — every existing caller already calls `health_check()` for exactly this purpose).

### mill-resume-health-check-callsite

- Decision: add an explicit `_client.health_check(wiki_path)` call to `mill-resume/SKILL.md` — in Phase 1, before Phase 2's `list_tasks_brief` candidate-listing query — so the wiki-health-check-scope fix (fetch+ff-merge staleness, git-validity check) actually runs before mill-resume reads the wiki for resume candidates.
- Rationale: #730's own reproduction is specifically a mill-resume Phase 2 listing on a fresh machine; without this call site, the entire wiki-health-check-scope fix would exist in the codebase but never execute in the one scenario the issue describes (caught in discussion review round 4 — the original rationale incorrectly assumed mill-resume already called `health_check`).
- Rejected: relying on some other skill's `health_check()` call to have already run earlier in the session (mill-resume is explicitly the entry point for a fresh machine that has never run any other mill skill in this container yet — there is no earlier call to rely on).

### health-check-error-surfacing

- Decision: `wiki/_client.py:health_check() -> bool` keeps its bare bool return signature, but on a hard failure (see health-check-failure-semantics), it logs the underlying reason (the git-validity or `WikiPushError` message) to stderr before returning `False`, instead of returning only the bool with no detail. `mill-go/SKILL.md`'s two `health_check()`-failure halt blocks (currently at both the per-batch dispatch chokepoint and the equivalent Handoff-time check) keep their existing generic `"[mill-go] wiki daemon health check failed"` print, but their halt message changes: stop unconditionally implying `"re-run mill-setup if mill-config.yaml is missing"` is the fix for every failure cause — append guidance to also inspect the printed reason (git-validity/divergence failures need a different remedy than a genuinely missing hub config).
- Rationale: verified both `mill-go/SKILL.md` call sites print only the fixed generic string then the fixed `"HALT: no config source reachable -- re-run mill-setup..."` message regardless of cause — accurate for "no config source reachable" but actively misleading for a diverged or missing-`.git` wiki, which `mill-setup` does not fix (caught in discussion review round 4). Changing `health_check()`'s return type to something richer than `bool` would ripple into every existing caller for a benefit only two call sites need; logging the reason at the point of detection plus a less presumptive halt message closes the gap with a minimal-footprint change.
- Rejected: changing `health_check()`'s signature to return a reason string or raise a typed exception (larger ripple than needed — every caller across the codebase would need updating for a need only mill-go's two halt sites have); leaving the halt message unchanged (reproduces the exact misdirection this gap identifies).

### health-check-failure-semantics

- Decision: a missing/invalid `.git` directory is a hard failure (`health_check()` returns `False` / surfaces a clear error) per issue #737's explicit ask. A fetch/pull failure due to network unreachability is a soft warning only — `health_check()` still reports healthy, since most mill work doesn't require wiki connectivity and offline use shouldn't be blocked by a transient network blip.
- Rationale: distinguishes "this is fundamentally broken and needs user action" (missing repo) from "this is transient and shouldn't block work" (no network).
- Rejected: hard-fail on both conditions (too strict, blocks all mill work when offline); soft-warn on both (reproduces exactly the "false assurance" problem #737 complains about for the missing-repo case).

### health-check-fetch-cadence

- Decision: debounce the fetch+ff-merge with an in-daemon-memory TTL (e.g. 60s) rather than fetching on every single `health_check()` call.
- Rationale: `health_check()` is called before every batch/review dispatch in a mill-go session — fetching on every call adds a network round-trip to every dispatch even when calls are seconds apart. A TTL still catches staleness within a session and always fetches fresh on daemon (re)spawn.
- Rejected: fetch unconditionally on every call (simplest, but unnecessarily chatty over the network for long mill-go sessions).

### gitignore-swallow-left-nonfatal

- Decision: `_ensure_gitignore`'s startup chore-commit (`wiki/_server.py`, called once per daemon `on_start`) stays best-effort/non-fatal, logged via `self._log.warning` as today. The git-repo-validity signal now lives in `health_check`/`OP_HEALTH` (see wiki-health-check-scope), which is where callers actually check for it.
- Rationale: failing daemon startup entirely over a cosmetic `.gitignore` commit is disproportionate; the actual problem (missing `.git`) is now caught at the point callers gate on it. Verified all real data-mutation wrappers already raise `WikiPushError` correctly — this was the one narrow genuine gap, not a systemic swallowing problem.
- Rejected: making `_ensure_gitignore` raise/propagate, which would fail daemon startup for a non-critical file write.

### mill-resume-detection-point

- Decision: Phase 1's own halt condition changes — before halting on missing `.millhouse/config.local.yaml` or `.wiki`, first check whether `_mill/status.md` exists at cwd. If it does (cwd is a genuine task worktree, just under-scaffolded), branch into a new repair phase inserted immediately after Phase 1 instead of halting. Phase 1 still halts unconditionally to the `mill-setup` remedy only when `_mill/status.md` is also absent — the genuine "this isn't a task worktree at all" case, where `mill-setup` remains the correct remedy.
- Rationale: matches issue #729's literal reproduction (user `cd`s into the hand-created, non-canonical worktree and runs a mill skill there). The original "insert after Phase 1, don't touch Phase 1" framing was self-contradictory — Phase 1's unconditional halt would prevent the new phase from ever being reached in exactly the scenario it targets (caught in discussion review round 1). Proactively scanning `git worktree list` from the hub for orphans would also help but expands scope to a case not actually reported.
- Rejected: leaving Phase 1's halt condition untouched and routing the new phase through a separate entry point (adds an unnecessary second invocation path for what is conceptually one setup-verification step); hub-side proactive enumeration via `git worktree list` (real capability, but not what was reported — flagged as future work, not blocking this task).

### mill-resume-relocate-then-scaffold

- Decision: on detection, first check whether the canonical `<container>/wts/<slug>` path already exists (stale entry, or another worktree occupying that slot). If it does, halt with a clear message identifying what occupies the canonical path and let the user resolve manually — do not auto-remove or auto-replace it. If the canonical path is free, relocate the worktree there via `git worktree move <old-path> <canonical-path>` (native git, atomic, updates the worktree's administrative files), then run the equivalent of Phase 7 (copy `.millhouse/`, excluding `scratch/`/`children/`, from the parent/hub) and Phase 8 (create the `.wiki` junction).
- Rationale: issue #729 explicitly calls out that downstream lookups (`resolve_container_path`, used by mill-cleanup, mill-merge, wiki-by-slug resolution) assume the canonical path — leaving the worktree in place would just move the fragility elsewhere. `git worktree move` is the correct git primitive; no existing mill helper does this today (confirmed: no `worktree move`/`worktree_move` helper anywhere in `plugins/mill/scripts/`). The collision case is plausible precisely because the reported scenario already has a worktree living somewhere non-canonical (caught in discussion review round 1) — halting matches the same "don't silently mutate state mill didn't create/expect" philosophy as mill-resume-confirmation-gate; auto-removal is a destructive action against unknown state.
- Rejected: scaffold in place without relocating (simpler, but reproduces the exact fragility the issue is trying to eliminate); auto-removing/replacing whatever occupies the canonical path on collision (destructive, could discard another task's worktree or genuine user work).

### mill-resume-confirmation-gate

- Decision: require explicit user confirmation before the relocate+scaffold repair runs, after a safety pre-check that the worktree has no uncommitted changes (`git status --porcelain`); halt with a clear message if dirty.
- Rationale: this is a novel, off-happy-path repair operating on a worktree the user created by hand outside any mill skill — more can be wrong than mill expects (uncommitted changes, mid-rebase, detached state). `git worktree move` mutating a worktree with uncommitted work is exactly the kind of hard-to-reverse action that warrants a confirm step.
- Rejected: fully automatic with no confirmation (matches the rest of mill-resume's largely-unattended phases, but this phase handles state mill didn't create and can't fully vouch for).

### mill-resume-cwd-after-move

- Decision: since mill-resume's repair phase is reached "from inside" the off-canonical worktree (per the reactive-detection framing), and `git worktree move` then relocates that same directory out from under the running session, every operation from that point on (the Phase 7/8-equivalent scaffold steps, and Phase 10's final report) must reference the new canonical path via absolute paths — never relying on relative-path or implicit-shell-cwd resolution. The phase's final report must explicitly surface the new canonical path so the operator knows where the worktree now lives, and note that any follow-on skill invocation (e.g. `mill-go`) should be started from a shell explicitly pointed at the new canonical path rather than assuming the current session's shell cwd followed the rename.
- Rationale: `git worktree move` is a directory rename on disk; whether a shell's tracked cwd string follows a renamed directory is platform-dependent and not something a skill can force from within a running session (caught in discussion review round 3). This repo's own CLAUDE.md already establishes the general principle ("Scripts always resolve real paths via `_paths.py`", never rely on implicit cwd) — this decision applies that same discipline to the one place mill-resume's own execution model creates a genuine cwd-validity risk.
- Rejected: doing nothing (a stale/relocated cwd could silently break follow-on relative-path commands in the same session); attempting to programmatically force the session's shell cwd to follow the move (no such capability exists for a skill to invoke against its own running harness session — absolute-path discipline plus explicit reporting is what's actually available).

### wiki-pull-failure-classification

- Decision: `pull()`'s docstring (`wiki/_sync.py:156-169`) documents that it raises `WikiPushError` for two distinct causes — "`git pull --ff-only` failed" (network/timeout) and "non-fast-forward state" (local wiki has diverged from `origin`) — as the same exception type. `_handle_health` must distinguish them by inspecting the exception message: if it contains "fast-forward" (case-insensitive — git's own stderr for a failed `--ff-only` says "Not possible to fast-forward, aborting."), classify as a **hard failure** (same bucket as the missing-`.git` case in health-check-failure-semantics) — a diverged local wiki needs manual resolution, not silent continuation. Any other `WikiPushError` from `pull()` (verified: `_run()`'s timeout path raises a message containing "timed out"/"remote may be unreachable"; other network failures surface git's own connection-error stderr text) is the existing **soft warning** case.
- Rationale: without this split, a diverged/non-fast-forwardable local wiki — a real, non-transient problem — would fall into whichever bucket health-check-failure-semantics' binary split happened to catch by accident, and neither documented case (missing-repo hard-fail, network-timeout soft-warn) actually names it (caught in discussion review round 3). Continuing to report "healthy" for a diverged wiki would reproduce the exact false-assurance problem #737 complains about, just from a different root cause. Message-content inspection is the only available signal without changing `pull()`'s exception contract, which is out of scope for this task.
- Rejected: leaving all `pull()` failures soft (masks a real, actionable divergence problem); hard-failing on every `pull()` failure including plain network timeouts (too strict — reproduces the rejected "hard-fail on both" option from health-check-failure-semantics for the same reason: blocks offline mill work over a transient network blip).

### mill-resume-phase-placement

- Decision: insert the new repair logic as its own phase directly after Phase 1 (documented as "Phase 1b" or similar clearly-scoped label), without renumbering the file's existing phases or filling the pre-existing Phase-2→Phase-4 numbering gap.
- Rationale: the numbering gap is a pre-existing, unrelated cosmetic issue (confirmed: `mill-resume/SKILL.md` has no "Phase 3" anywhere, phases run 1, 2, 4, 5...); renumbering the whole file is unrelated churn for this task.
- Rejected: renumbering every phase from 3 onward while inserting the new phase (correct hygiene, but out of scope — YAGNI for this task).

### load-config-fix-mechanics

- Decision: for `millpy-implement.py` (line ~236), `millpy-fix.py` (line ~297), and `millpy-abandon.py` (line ~42), swap the `load_config(git_root, mill_dir)` call to use the already-locally-computed hub-rooted variable (`project_root` in the first two, `hub_dir` in the third) — a mechanical one-line fix per site, matching `millpy-review-code.py`'s existing correct pattern (`project_root = _paths.resolve_hub_path(); ...; load_config(project_root, mill_dir)`). For `millpy-merge-in-subagent.py`, fix the root cause: `project_root = Path.cwd()` (line ~337) is not hub-rooted at all — change it to `_paths.resolve_hub_path()`. This alone is not sufficient: the `load_config` call itself (line ~345) passes `git_root` (`_paths.resolve_git_root()`, line ~341) as arg1, not `project_root` — `project_root` only feeds `mill_dir` (arg2) today. Both changes are required: fix `project_root`'s definition, AND swap the call to `_review_common.load_config(project_root, mill_dir)` (replacing `git_root`) — fixing only the definition would leave arg1 as the outer git-repo root, the exact #728 bug pattern, unfixed for this file.
- Rationale: 3 of the 4 sites need only a call-site argument swap since the correct variable already exists in scope; the 4th needs both its root-computation fixed AND its call-site argument swapped (`load_config(git_root, mill_dir)` -> `load_config(project_root, mill_dir)`, verified — `project_root` is not currently passed to `load_config` at all in this file, only `mill_dir` derives from it) — conflating them into one blanket "swap the argument" instruction would silently under-fix `millpy-merge-in-subagent.py` (caught in discussion review round 2).
- Rejected: a structural refactor centralizing root-resolution in `_review_common.py` (bigger diff, not needed to close these 4 bugs, and risks touching call sites that are already correct).

### load-config-validate-plan-included

- Decision: also fix `millpy-validate-plan.py`, where `load_config(resolve_hub_path(), mill_dir)` (line ~44) passes the correct hub root as arg 1 but `mill_dir = Path.cwd() / ".millhouse"` (line ~39) is cwd-based rather than hub-rooted — the inverse mismatch of the other 4 sites, same underlying bug class. The actual fix is upstream of `mill_dir`: `project_root = Path.cwd()` (line ~38) is itself the wrong root — change it to `project_root = _paths.resolve_hub_path()`, then derive `mill_dir = project_root / ".millhouse"` from the corrected value. Fixing `project_root` this way also fixes its two other consumers in the same file, both the identical cwd-vs-hub-root bug: `find_active_slug(project_root, wiki_root, cfg)` (whose first parameter is named `hub_root` in `_review_common.py:306`) and `_plan_validate.run(plan_dir, project_root, ...)` (defined at `_plan_validate.py:2001`, threads `project_root` down to `_check_verify_not_isolated`, whose docstring at `_plan_validate.py:1455` states `project_root` "also doubles as the hub_root").
- Rationale: discovered while investigating #728, already fully diagnosed. Fixing only `mill_dir` in isolation (the original, narrower framing of this decision) would have left two more identically-broken consumers of the same mis-rooted `project_root` variable untouched in the same file — caught in discussion review round 1. Leaving known, already-understood sibling instances of the exact bug unfixed after finding them would be an oversight, not scope discipline.
- Rejected: fixing only `mill_dir` and leaving `project_root`'s other two consumers cwd-rooted (incomplete — same bug class, same file, same fix); filing it as a separate follow-up issue instead of fixing now (unnecessary process overhead for a fix already fully understood).

### merge-in-subagent-cfg-reload

- Decision: in `millpy-merge-in-subagent.py`, `cfg` (loaded once at line ~345, via the bootstrap-rooted `load_config(project_root, mill_dir)` per load-config-fix-mechanics) must be reloaded after the script's own later, more-precise resolution: `project_root = _paths.resolve_active_hub(container_path, slug, cfg=cfg, git_root=git_root, ...)` at line ~357, which derives a corrected `mill_dir` at line ~360. `resolve_hub_path()` (the bootstrap resolver, a cwd-walk with no slug/cfg dependency) and `resolve_active_hub()` (the final resolver, slug- and cfg-aware, reading `hub_relative_path` which may itself come from a hub-level `mill-config.yaml` the bootstrap load never saw) are **not** guaranteed to agree in a hub-in-subdirectory container layout — that potential disagreement is exactly the class of bug #728 is about. All downstream consumers of `cfg` in this file (the verify-cwd computation, conflict handling, finalize dispatch) must use the reloaded value, not the bootstrap one.
- Rationale: `resolve_active_hub`'s own docstring documents a two-tier resolution — cfg's `hub_relative_path` first, then an override from the resolved worktree's own `.millhouse/config.local.yaml` — meaning the corrected `mill_dir` at line 360 can legitimately point at a different, more-specific `mill-config.yaml` than the bootstrap load found. Using the stale bootstrap `cfg` for everything downstream would silently reproduce a narrower version of #728 even after the call-site argument fix, inside the very function whose job is to resolve this correctly (caught in discussion review round 4).
- Rejected: assuming the two resolvers always agree for this script's invocation context and skipping the reload (unverifiable in general — the whole point of `resolve_active_hub`'s two-tier logic is to handle the case where they don't); reloading `cfg` unconditionally on every invocation regardless of whether the paths actually differ (unnecessary I/O when they match, but simpler and safer than trying to detect agreement first — implementation may choose to compare paths and skip the reload only when `project_root` is unchanged after line 360, as a minor optimization, not as a correctness requirement).

## Technical context

- **Wiki daemon health check:** `wiki/_client.py:585 health_check()` → dispatches `OP_HEALTH` → `wiki/_server.py:295 _handle_health()`, which today unconditionally returns `{FIELD_OK: True}` (no git-validity or staleness logic at all — this is the entire fix surface for #730/#737-part-1).
- **Existing fetch/pull helper:** `wiki/_sync.py:156 pull(wiki_path)` already implements `git pull --ff-only` and raises `WikiPushError` on failure — reuse this rather than writing new git-invocation logic. Its docstring documents `WikiPushError` covers two distinct causes (ff-pull failure/network, and non-fast-forward/diverged state) as one exception type — see wiki-pull-failure-classification for how `_handle_health` must distinguish them via message-content inspection. `wiki/_sync.py:180 commit_push()` is the general commit+push helper (already raises `WikiPushError` correctly at every failure stage, confirmed for the swallowing question above).
- **Existing git-validity check to reuse:** `wiki/_sync.py:commit_push()` (lines ~206-225) already runs `git rev-parse --git-dir` and raises `WikiPushError` with a "not a git repository" message — this is the exact validity check `_handle_health` needs (see wiki-health-check-scope). Factor/extract it rather than re-implementing an equivalent check inline in `_handle_health`, to avoid two inconsistent validity checks in the same module.
