## Problem

Three related bugs (GitHub #686, #689, #698, all consolidated into this task) share one root cause: mill's review/verify machinery treats a plan's batch DAG as if the file layout and implementation state were static, when in reality batches can move files, delete files, and be at different stages of completion relative to each other.

- **#686** — `millpy-review-code.py`'s holistic *prepare* stage hard-ERRORs (`ReviewError` in `resolve_ref_paths`) when a batch card's `Context:` ref points at a path that a *later* batch relocates via `Moves:`. The path was valid when the plan was written and when the referencing batch ran, but by the time holistic review runs, the file has moved away.
- **#689** — `millpy-fix.py`'s holistic *finalize* verify-replay (`_plan_dag.iter_batch_verifies`, joined via `_resolve_holistic_verify`) replays every batch's `verify:` command in DAG order against the *final* tree, with no notion that a later "revert" batch legitimately deleted an earlier batch's build target. This produces a false-positive `stuck_type: verify` that blocks handoff even though the authoritative final-state checks pass.
- **#698** — `mill-merge-in`'s Step 4 calls the same `iter_batch_verifies()` with no phase/implementation gate. If merge-in runs before any batch has been implemented (e.g. an operator-directed sync during the PLAN phase), it replays verify commands against packages/paths that don't exist *yet*, dispatches a vacuous verify-fix sub-agent, and risks a stuck→rollback of an otherwise-good merge.

All three were filed with a documented manual workaround (retarget the stale `Context:` refs; rewrite batch `verify:` commands to the final-state command; run only the verifies whose targets exist) — the point of this task is to make the pipeline handle these cases automatically.

## Scope

**In:**
- `_review_code.py`'s holistic prepare: stop discarding the `sources` half of `compute_moves_union()`'s return value; merge it into `deletes_union` before calling `resolve_ref_paths`, per that helper's own docstring contract.
- `_plan_dag.iter_batch_verifies()`: skip (not fail) a batch's `verify:` command when a strictly-later batch (in topo order) declares — via its own `Deletes:` or `Moves:` — the exact path(s) referenced in that command's tokens.
- `_plan_dag.iter_batch_verifies()`: add an optional `status_path` parameter; when given, filter out any batch whose `_status.read_batches()` state is not `"approved"`.
- Wire the new `status_path` parameter through both existing callers: `millpy-fix.py` (holistic prepare + finalize) and `mill-merge-in` Step 4.
- Visible, counted skip reporting for both new skip reasons, mirroring the existing "allowlisted as known-broken" skip pattern in `mill-merge-in`'s report line, plus an equivalent stderr note from `millpy-fix.py`.
- Unit test coverage for all of the above in `test-review-code-flow.py`, `test-plan-dag.py`, and `test-millpy-fix.py`.

**Out:**
- No new plan-authoring schema fields (e.g. no `verify-superseded-by:` or `verify-target:` frontmatter key). The fix reuses the existing `Deletes:`/`Moves:` bullets that plans already author for other purposes.
- No filesystem-existence heuristic for verify-target detection (rejected — see Decision 2 below; a command that creates its own output path before using it, e.g. `mkdir -p out && go build -o out/app ./cmd/app`, would be falsely flagged as referencing a missing path).
- No `mill-plan`-time validation/warning for revert-style plans (option (c) from #689) — this task is a runtime fix, not an authoring-time lint. A future task may add the lint; not needed once the runtime skip is correct.
- No change to per-batch verify during live `mill-go` dispatch (`millpy-implement.py` / per-batch `parse_verify_field` calls) — `iter_batch_verifies` is only ever used for cross-batch *replay* (holistic prepare/finalize, merge-in), never for a single batch's own live verify, so nothing there needs to change.
- No change to `_review_plan.py`'s two `compute_moves_union()` call sites (lines 354, 668) — those already correctly keep both halves (`moves_sources_union` used directly, not discarded); only `_review_code.py`'s holistic prepare has the bug.
- No handling of flag=value path tokens (e.g. `--dir=foo/bar`) in the verify-command tokenizer — out of scope; see Technical context for the exact tokenization rule and its known limitation.
- No per-target splitting of a multi-target `verify:` command (e.g. `go build ./tools/x ./tools/y`) — suppression is all-or-nothing on the whole command when any one referenced target matches a later removal; see Decision 2.
- No coordinate-space resolution between a `verify: {cwd: ...}` mapping form's resolved cwd and the plan `root:` that `Deletes:`/`Moves:` tokens are authored relative to — matching stays purely lexical on raw strings; see Decision 2.

## Decisions

### 1. `_review_code.py` — stop discarding `compute_moves_union()`'s sources half

- Decision: In `_collect_source_files` (or equivalent) in `plugins/mill/scripts/_review_code.py` around line 279, change `_, moves_targets_union = compute_moves_union(plan_dir)` to capture both halves, and pass `deletes_union | moves_sources_union` (not bare `deletes_union`) into the `resolve_ref_paths(...)` call at line ~280-283.
- Rationale: `compute_moves_union()`'s own docstring (`_review_common.py:714-736`) states "the source set mirrors the semantics of `compute_deletes_union`" — i.e. sources are files that disappear from their old location once the moving batch runs, the exact same "path legitimately no longer exists at the location a `Context:` ref names" situation `deletes_union` already exists to suppress in `resolve_ref_paths`. (The docstring's next sentence is actually about the *targets* half and `creates_union`, not sources — it does not itself instruct callers to feed sources into `deletes_union`; that step is this decision's own inference from the stated semantic equivalence, not a quoted instruction.) `_review_plan.py` already treats `moves_sources_union` as live, used data at both of its call sites (lines 354 and 668, feeding it into its own ref-suppression logic, consistent with the same semantic equivalence). `_review_code.py`'s holistic prepare is the one place in the codebase that discards the tuple's first element with `_,`.
- Rejected: A new third suppression kwarg on `resolve_ref_paths` (adds API surface for something that already fits the existing `deletes_union` semantics exactly); resolving sources via `resolve_existing_paths` and appending unconditionally to `source_files` (wrong semantics — a moved-away source should be *suppressed*, i.e. not hard-fail, not necessarily *included* in the reviewer's file list, since it no longer exists at its old path by the time holistic review runs).

### 2. Cross-batch verify-target detection uses plan metadata, not disk state

- Decision: A batch's `verify:` command is considered to reference a "removed-later" target when: (a) the command is tokenized with `shlex.split(command)`; (b) a token is a *path candidate* iff it does not start with `-` (excludes flags), contains `/`, and does not contain any of `*`, `?`, or the literal substring `...` (excludes shell globs and Go's `./...` wildcard); (c) each path-candidate token is normalized (strip one leading `./`, strip any trailing `/`); (d) the normalized token exact-matches a normalized entry in the *per-batch* `Deletes:` or `Moves:`-source set of some batch that is strictly later than the verifying batch in `topo_order()`. Suppression is **existential and all-or-nothing**: if *any* path-candidate token matches, the entire triple (the whole joined command) is dropped — a multi-target command like `go build ./tools/x ./tools/y` is fully suppressed even if only `tools/x` was reverted and `tools/y` is still a perfectly valid target. This is an accepted limitation, not a bug to fix here: the same class of carve-out as the flag=value and directory-containment limitations below — splitting a single `verify:` command into independently-suppressible per-target sub-checks is out of scope (it would require understanding the command's own argument grammar per build tool, which this task deliberately does not attempt).
- Directory-containment is explicitly out of scope: exact-match only — `go build ./tools/x/` is suppressed by a later `Deletes: tools/x/` (both normalize to `tools/x`), but `go build ./tools/x/cmd/app` is **not** suppressed by that same `Deletes: tools/x/` even though the directory it lives under was removed. A plan author relying on directory-level removal to suppress a file-level verify reference must declare the file path itself under `Deletes:`/`Moves:`, or accept that the verify still runs (and, per Decision 5, is visibly reported as "ran", not silently treated as obsolete). This is the same class of limitation as the already-scoped-out flag=value case (Scope, Out) and is not addressed by this task.
- Coordinate-space assumption: matching is purely lexical, string-to-string, on the *raw* tokens as authored — no path resolution against `cwd:`/`root:` happens before comparing. This assumes verify-command path tokens and `Deletes:`/`Moves:` tokens are authored in the same coordinate space (both relative to the plan's `root:`, the common case). When a batch's `verify:` uses the `{cwd: hub|git_root, command: ...}` mapping form (`parse_verify_field`) with a `cwd` that differs from the plan `root:`'s implied base, a token that is lexically a genuine match in on-disk terms may fail to string-match here — the verify is **not** suppressed and still runs, i.e. this degrades to "#689/#698 unfixed for that specific config," never to a false suppression. Resolving both sides to a common absolute-path space before comparing is out of scope for this task; plans that mix `verify: {cwd: ...}` batches with cross-batch revert patterns may not get the suppression benefit and must fall back to the existing manual workaround (rewrite the stale batch's `verify:` command directly, as both #689's and #698's authors already did).
- Composition with Decision 4's `status_path` filter: when `status_path` is provided, a later batch's `Deletes:`/`Moves:` declaration counts as a "removal" for this check **only if that later batch's own state is `"approved"`**. A `pending`/`running`/`reviewing`/`fixing`/`blocked` later batch has not actually executed its declared removal yet, so its target still exists and must not suppress an earlier (already-approved) batch's still-valid verify. This is what keeps the mid-`mill-go` merge-in case correct: batches 1-3 approved, batch 4 (`depends-on: [1,2,3]`) still `pending` with `Deletes: tools/x/` in its frontmatter — since batch 4 hasn't run, `tools/x/` still exists on disk, and batches 1-3's verify referencing it must still run, not be suppressed. When `status_path` is `None` (not provided), this check is skipped and every strictly-later batch's declared removal counts regardless of state, matching this decision's original unconditional wording — `status_path` is the only thing that ever narrows which later-batch declarations count.
- Rationale: Matches against plan-declared removals (author intent) rather than live disk existence, avoiding a real false-positive: a verify command that creates its own output path before consuming it (`mkdir -p out && go build -o out/app ./cmd/app`) would see `out/app` as "missing" under a naive existence check before the `mkdir` runs, and get wrongly skipped even though the verify is perfectly valid. Getting there requires **one genuinely new per-batch parser**, not pure reuse (correcting an earlier, inaccurate version of this rationale): `_review_common.py` has a standalone per-batch `parse_moves(batch_path) -> list[tuple[str, str]]` (line 551) that Decision 2 reuses directly for the Moves-source half, but it has **no** standalone per-batch Deletes parser — `compute_deletes_union()` (line 666) inlines its Deletes-parsing logic rather than delegating to a named function, and the only existing per-batch Deletes parser, `_parse_deletes_only` (`_plan_validate.py:220`), lives in the wrong module for this purpose (see Rejected). Decision 2 therefore adds a new public `parse_deletes(batch_path) -> set[str]` function to `_review_common.py`, mirroring `parse_moves`'s existing shape and signature convention, and refactors `compute_deletes_union()` to call it internally (deleting the duplicate inline logic — a net simplification, not just an addition). `_plan_dag.py` then imports both `parse_deletes` and `parse_moves` from `_review_common`. This is "new" only in the sense of a newly-named, newly-tested unit — the Deletes-line parsing behavior itself is a mechanical extraction of already-exercised inline logic, not a new algorithm.
- Rejected: Blind filesystem-existence check on tokenized args (the false-positive above); a new plan-schema field requiring authors to hand-declare which batch supersedes which (adds authoring burden and a new validation surface for a case the existing `Deletes:`/`Moves:` bullets already describe); directory-containment matching (adds a second matching mode — prefix as well as exact — for a case neither #689 nor #698 actually hit, and risks over-suppressing a verify whose file target merely shares a path prefix with an unrelated deleted directory); reusing `_plan_validate._parse_deletes_only` cross-module from `_plan_dag.py` instead of adding `parse_deletes` to `_review_common.py` — rejected because it would require `_plan_dag.py` to import from `_plan_validate.py`, but `_plan_validate.py` already imports `_plan_dag` (`import _plan_dag`; `from _plan_dag import PlanDAGError, extract_batch_index, resolve_deps_as_names`), so the reverse import would create a circular dependency. Importing from `_review_common.py` instead is safe: `_review_common.py` has zero dependency on `_plan_dag.py` or `_plan_validate.py`, so `_plan_dag.py` gaining a one-directional dependency on `_review_common.py` introduces no cycle — this mirrors the exact dependency shape `_plan_validate.py` already has today (it depends on both `_plan_dag` and `_review_common`; `_plan_dag` gaining a dependency on `_review_common` only, not on `_plan_validate`, keeps the graph acyclic).
- Note: "strictly later in topo order" is essential — it must not suppress a batch's own legitimately-broken verify just because that same batch also deletes something, and must not suppress an *earlier* batch's verify based on something declared even earlier (nonsensical — nothing has been removed yet from that batch's point of view).

### 3. The filter lives inside `_plan_dag.iter_batch_verifies()` itself

- Decision: Decision 2's filtering logic is applied unconditionally inside `_plan_dag.iter_batch_verifies()` (`plugins/mill/scripts/_plan_dag.py:359`), not as an opt-in wrapper. Every existing caller gets the corrected behavior automatically with no call-site changes beyond Decision 4's new kwarg.
- Rationale: `iter_batch_verifies()`'s own docstring already frames its contract from the caller's perspective as "replay exactly the checks that ran during implementation." A verify against a target a later batch legitimately reverted was never really part of that surviving contract — no current or plausible future caller wants the unfiltered, technically-incorrect list. Both current callers (`millpy-fix.py` holistic prepare/finalize, `mill-merge-in` Step 4) need this fix; a wrapper would just be a second name for "the function everyone should actually call."
- Rejected: A separate wrapper function (`iter_batch_verifies_filtered` or similar) that callers opt into — pure indirection with no caller that would ever want the old behavior.

### 4. `#698` gate: per-batch state filter via a new `status_path` kwarg

- Decision: Add `status_path: Path | None = None` as a keyword-only parameter to `iter_batch_verifies(plan_dir, hub_root, git_root, *, status_path=None)`. When provided, call `_status.read_batches(status_path)` once, build a `{name: state}` lookup, and skip any batch whose state is not `"approved"` (this naturally covers "no `## Batches` section yet" — `read_batches` returns `[]`, so every batch is filtered out — and the partial-completion case where merge-in runs mid-`mill-go`). When `status_path` is `None` (not passed), behavior is unchanged from today (no state filtering) — this preserves the parameter as strictly additive.
- Rationale: `_status.read_batches()` / the `state` field (`pending`, `running`, `reviewing`, `fixing`, `approved`, `blocked` — `_status.py:540-547`) is the existing, precise source of truth for per-batch implementation progress, already read elsewhere in `millpy-fix.py`'s per-batch dispatch. It degrades correctly to "skip everything" pre-`mill-go` without a separate phase check, and handles partial-run merge-in more precisely than a single coarse phase gate could (a phase gate can only say "building has started," not "batch 3 specifically is done").
- Rejected: A coarse top-level `phase:` gate (skip entirely if `phase` < `"building"`) — too coarse for the partial-completion case, and redundant once the per-batch filter exists; doing both (belt-and-suspenders) — unnecessary complexity, the per-batch filter is a strict superset of what the phase gate would catch.
- Call-site wiring: `mill-merge-in` Step 4 passes `status_path` (the actual fix for #698 — resolved the same way Step 4 already resolves `hub_root`/`git_root`, i.e. `status_path = _paths.resolve_task_path(hub_root, "_mill/status.md")`). `millpy-fix.py`'s two `iter_batch_verifies(...)` call sites (holistic prepare-time verify_cmd derivation and holistic finalize, both already have `status_path` in scope as a local variable) also pass it — this is a no-op in practice, since `mill-go`'s own linear DAG execution guarantees every batch is already `"approved"` by the time holistic fix runs, but keeps the contract consistent rather than leaving one caller silently relying on an invariant the function itself doesn't enforce.
- Malformed `## Batches` section: `_status.read_batches()` raises `ValueError` on a corrupt fenced-yaml block (missing/unterminated fence — see `_find_batches_block` in `_status.py`), whereas `iter_batch_verifies()` today only catches `PlanDAGError` (from a malformed plan overview/batch index) and degrades to `[]`. When `status_path` is provided, wrap the `read_batches()` call in the same catch-and-degrade shape: catch `ValueError` there too and treat it identically to the existing `PlanDAGError` path — return `[]` (skip verify replay entirely) rather than letting the exception propagate out of the finalize/merge-in verify step. This keeps `iter_batch_verifies()`'s existing documented contract ("if malformed, returns `[]` and the caller falls back to nothing-to-verify") uniform across every kind of malformed input, plan-side or status-side, rather than having plan corruption degrade gracefully while status corruption crashes the caller.

### 5. Skip visibility: extend the existing `skipped` counter pattern

- Decision: Both new skip reasons (Decision 2's "target removed by a later batch" and Decision 4's "batch not yet approved") must be visibly logged and counted, using the same shape as `mill-merge-in` Step 4's existing "allowlisted as known-broken" skip (`plugins/mill/skills/mill-merge-in/SKILL.md` Step 4). `iter_batch_verifies()` itself doesn't print (it's a pure data function returning triples) — so each *skip reason* becomes visible in the return path: batches filtered out by Decision 2/4 are simply absent from the returned list (same contract as today's `verify: null` skip), and the two callers are responsible for surfacing *why* triples are missing.
  - `mill-merge-in` Step 4: extend the existing `skipped` counter to also count "not yet approved" and "target removed" batches, distinguished in the final report line (e.g. `Verify: <ran> batch tests ran, <N> skipped (allowlisted), <M> skipped (batch not approved), <K> skipped (target removed by later batch).` — only emit the clauses whose count is nonzero, mirroring the existing conditional-clause pattern). Because `iter_batch_verifies()` returns only the surviving triples (Decision 5's opening paragraph — it is a pure data function, not a reason-coded one), Step 4 must attribute each *dropped* batch's specific reason itself, using the same diff-and-reclassify mechanism as the `millpy-fix.py` bullet below: independently compute the full set of batches with a non-null `verify:` (via `extract_batch_index()` + `topo_order()` + `parse_verify_field()` per batch, i.e. what `iter_batch_verifies()` would have returned with no filtering at all), diff it against the triples `iter_batch_verifies()` actually returned, and for each missing batch re-check Decision 4's condition (state via `_status.read_batches(status_path)` is not `"approved"`) first, falling back to Decision 2's condition (a later-and-approved batch's `Deletes:`/`Moves:` matches one of its command's path tokens) when the state check doesn't explain the drop — the two checks apply to different roles for the same missing batch and both must be tried: Decision 4's check asks "is *this* batch itself approved" (if not, that alone explains its absence), while Decision 2's check asks "did some strictly-later, *approved* batch declare removing a path *this* batch's command references" (this can explain the absence of an approved batch whose own state passes Decision 4 cleanly). A batch can only be missing for one of the two reasons — check Decision 4's condition first purely because it is cheaper (one state lookup vs. a token scan), not because one decision structurally precedes the other in `iter_batch_verifies()`'s own filtering.
  - `millpy-fix.py` holistic prepare/finalize: print an equivalent `[millpy-fix] skipped <batch_name>: <reason>` line to stderr for each batch `iter_batch_verifies()` silently dropped, so the fixer session's own log carries the same auditability merge-in's report line has. (Compute this by diffing "which batches from `extract_batch_index()`/`topo_order()` had a non-null `verify:` in their own frontmatter" against "which batch names came back from `iter_batch_verifies()`" — the difference is exactly the skipped set, tagged with the specific reason from re-checking Decision 2/4's conditions.)
- Rationale: matches this project's existing convention (the allowlist skip already does this) and general good practice — a verify that silently never ran must never look identical to a verify that ran and passed.
- Rejected: Silent skip with no counter/log change — indistinguishable from "verified" in the report, which is exactly the kind of gap this task exists to close.
