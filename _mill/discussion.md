## Problem

Five independent reliability gaps have surfaced in mill's Agent-mode orchestration (`dispatch: agent` — background subagents dispatched via the `Agent` tool instead of `psmux`/subprocess) and in the review/fix/verify pipeline shared by both dispatch modes. All five were observed in real task runs (not hypothetical) and are consolidated here from closed issues #587, #595, #590, #592, #593.

Two of the five (#587, #595) are live-incident dispatch races: mill-go's Agent-mode "stopped/interrupted" recovery path (`## Agent-mode dispatch` step 4 in `mill-go/SKILL.md`) treats any stopped/killed `<task-notification>` as terminal and immediately re-dispatches a fresh implementer/reviewer/fixer session — but the harness's own notification semantics allow a "stopped" or "killed" notification to be stale: the same background agent can still be alive and later deliver a second, `completed` notification with real commits. Both incidents resulted in two live sessions racing on the same batch, requiring manual `TaskStop` intervention to prevent conflicting commits.

The other three are narrower correctness/consistency bugs discovered while reading the code and templates: `millpy-implement.py`'s finalize stage runs a module-wide verify gate unconditionally on every batch (added deliberately in #541 to catch batch-introduced regressions elsewhere in the module), which also means it blocks a batch on failures that predate the task entirely (#590); the fixer-brief templates' pre-report self-check unconditionally forbids a zero-new-commit `success` report, contradicting the `nits_only` guard `_implementer_common.py` already implements for legitimate no-op nits-only passes (#592); and `mill-receiving-review`'s "load the skill BEFORE reading any review file" rule assumes a discrete, orchestrator-controlled file read, which doesn't exist in mill-start's/mill-plan's Agent-mode discussion/plan review — the reviewer's findings arrive already embedded in the `<task-notification>` payload the orchestrator must read to know the round even completed (#593).

**Why now:** #587/#595 are active double-dispatch risks — every Agent-mode mill-go run is exposed to a race that can silently corrupt a batch with conflicting commits. #590 actively blocks Agent-mode batches (and subprocess-mode ones) on failures the batch never caused. #592 and #593 are process-integrity bugs that produce false `stuck` escalations / inconsistent enforcement, both of which erode trust in the pipeline's automation.

## Decisions

### stopped/interrupted-notification liveness probe (#587, #595)

- Decision: In `## Agent-mode dispatch` step 4, when a `<task-notification>` indicates the background agent was stopped or interrupted (as opposed to a raw API/infrastructure error), do **not** immediately classify it as `stuck_type: transient` and re-dispatch. First call `TaskOutput(task_id: <agentId>, block: false)` (the `agentId` already retained per step 3) as a one-shot, non-blocking liveness probe. If it reports the agent as still running, take no dispatch action this turn — the harness will deliver the agent's own next `<task-notification>` when it actually finishes (matches the observed #595 behavior, where the "killed" agent later delivered a real `completed` notification unprompted). Only when the probe confirms the agent is no longer running (or the probe itself errors because the task_id is already gone) does the existing transient re-dispatch-once path apply, unchanged. Raw API/infrastructure errors (the other branch of step 4) are unaffected — they still classify as transient immediately, since there is no live agent to probe. Step 3's framing sentence and both "Agent-mode properties" bullets restating "stopped/interrupted → same as raw API error → one-retry transient path" must be reworded alongside step 4 (e.g., "...treat that as a candidate for the one-retry transient path in step 4, after step 4's liveness probe confirms the agent is no longer running") so no part of the SKILL still asserts stopped/interrupted is unconditionally terminal.
- Rationale: Both incidents show the "stopped"/"killed" notification itself can be stale while the underlying background worker keeps running to completion. A liveness probe converts an assumption ("stopped means dead") into a checked fact before taking the risky action (fresh re-dispatch, which risks a second live session on the same batch). `TaskOutput` with `block: false` is the harness-native way to check a background task's current state without blocking (per its own tool description: "Use block=false for non-blocking check of current status") — it does not require prompting the agent (unlike `SendMessage`, which assumes the agent is idle and waiting), so it doesn't perturb an agent that's mid-work.
- Rejected: (a) Treat "killed" as always-terminal and only probe on "stopped" — rejected because #595's incident was specifically a `status: killed` / "stopped by user" notification for an agent that was, in fact, still running; the evidence doesn't support trusting either status label as reliably terminal. (b) Send a warm `SendMessage` resume prompt instead of probing — rejected because it actively interferes with an agent that may already be working correctly toward completion on its own (unnecessary and can race with the agent's own final report); reserve `SendMessage` warm-resume for the already-correct step 6.5 `incomplete` path, where the agent has genuinely stopped and needs to be told to continue. (c) Poll `git log`/`start_sha` for new commits as the liveness signal — rejected as a secondary confirmation only; it can't distinguish "still working, no commit yet" from "dead before committing," whereas `TaskOutput`'s own running/completed state can.

### baseline-aware module-wide verify gate (#590)

- Decision: `_run_verify_gates` gains a third input — a cached per-task baseline state, `module_verify_baseline: "clean" | "pre-existing-failures" | null` — read from and written to `status.md`. On the *first* module-wide gate invocation for a task (baseline is `null`), lazily compute it once: create a transient `git worktree add <tmp-path> <parent_branch_tip_sha>` (never touch the task worktree's own working tree), then before running verify, reuse the task worktree's already-installed gitignored dependency state by creating filesystem junctions/symlinks from the task worktree's known dependency directories (e.g. `.venv`, `node_modules`, `vendor`, or whichever the project's own venv-check/dependency convention already names — mirror the existing per-project `verify:`/venv-check pattern in `mill-config.yaml` rather than inventing a new one) into the transient worktree, run `module_wide_verify_cmd` there with cwd set to that transient worktree, record `"pre-existing-failures"` if it fails or `"clean"` if it passes, remove the transient worktree, and persist the result to `status.md`. This dependency-reuse is safe specifically because the baseline check runs at the very start of the task (the first module-wide gate call fires before any batch has modified dependency manifests), so the parent branch tip's manifests are still identical to what the task worktree already has installed. If baseline computation itself raises (missing junction target, verify command not found, or any error distinct from a clean non-zero exit code) treat the result as inconclusive: do NOT cache a baseline verdict, log the error, and fall back to running the module-wide gate strictly for this call (i.e., behave as if the baseline were `"clean"`) — a computation failure must fail safe toward #541's stricter behavior, never silently disable the gate. On every module-wide gate invocation thereafter (this batch and all later batches), read the cached value: if `"pre-existing-failures"`, skip the module-wide gate entirely (treat as passed/no-op, same as `module_wide_verify_cmd is None`) for the remainder of the task; if `"clean"`, run the module-wide gate exactly as today (any failure blocks with `stuck_type: verify`, `"[module-wide verify]"`-prefixed reason). Invalidate the cached value (reset to `null`, forcing recomputation on the next module-wide gate call) whenever `mill-merge-in` pulls new parent commits into the task branch, since the parent's verify health can change after a merge-in.
- Rationale: #590's real-world case is a task blocked on 2 pre-existing, unrelated failures that predated the task's branch point entirely — the module-wide gate (added by #541 specifically to catch batch-introduced regressions) was never supposed to punish a batch for failures it didn't cause. A one-time binary "was the parent already red" check directly fixes this without weakening #541: when the baseline is clean (the common case), the strict per-batch gate is fully preserved, so a batch that newly breaks something elsewhere in the module still blocks exactly as #541 intended. The check runs once per task (amortized cost), not once per batch, so it doesn't reintroduce the ~5.5-minutes-per-batch latency complaint on top of an already-known-broken baseline.
- Rejected: (a) Remove the module-wide gate entirely from per-batch finalize, reserving it for the terminal Handoff `done_gate` only (#590's literal original ask) — rejected because it reverts #541's purpose: a batch-introduced module-wide regression would go undetected until Handoff, potentially after several more batches have built on top of the broken state, making the eventual failure much harder to bisect. (b) Per-test-name diffing of module-wide verify output before vs. after the batch — rejected as too fragile/complex: parsing failing-test identifiers out of arbitrary verify command output (pytest, `dotnet test`, `go test`, etc.) is command/tool-specific and this gate must stay language-agnostic; a binary pass/fail baseline requires only the exit code. (c) Make the module-wide gate advisory-only (log, never block) — rejected because it silently defeats #541's entire purpose; a real regression would never halt the pipeline. (d) Reinstall dependencies fresh in the transient worktree instead of reusing the task worktree's installed state — rejected as needlessly slow (defeats the "amortized one-time cost" rationale) and just as capable of producing a spurious, unrelated baseline failure (e.g., a flaky package registry) as the junction-reuse approach, without the offsetting speed benefit.

### fixer-brief nits-only carve-out (#592)

- Decision: Add a carve-out to BOTH unconditional zero-commit sentences in each template — the "Pre-report self-check" paragraph's "never report `success` when HEAD equals the baseline" sentence (`fixer-holistic-brief.md:71`, `fixer-batch-brief.md:65`) AND the separate "`commit_sha` MUST be a real new content commit distinct from the housekeeping commit" sentence (`fixer-holistic-brief.md:84`, `fixer-batch-brief.md:78`) — since both currently forbid a zero-commit `success` and both must be carved out together or the second still blocks the same legitimate case. The carve-out: when the fix pass was invoked with `--nits-only` and every finding was legitimately a reviewer-acknowledged no-op (nothing required a code change), the fixer MAY report `success` with zero new commits and no `commit_sha` — matching the `nits_only` guard `_implementer_common.py`'s `_forward_output()`/`finalize_from_output()` already implements (it skips the no-content-commit demotion specifically when `nits_only` is True). The carve-out only applies to the `--nits-only` scope; the ordinary batch/holistic fix path (real `[BLOCKING]`/`[GAP]` findings) is unchanged — a fixer working a real finding list must still produce a new commit before reporting `success`.

  Mechanism for the fixer to know it was invoked with `--nits-only` (the brief text alone can't express a runtime-only condition): add a `NITS_ONLY` boolean render token to `millpy-fix.py`'s brief-rendering token map (alongside the existing token maps at `millpy-fix.py:319` and `:384`), computed directly from `args.nits_only`. Both templates render a conditional carve-out block driven by this token — present (both sentences carved out) when `NITS_ONLY` is true, absent (both sentences stay strict, current wording) when false. This keys the carve-out off the exact same condition the runtime guard already checks, so brief wording and runtime behavior can never diverge.
- Rationale: The template's unconditional "never report success with zero commits" directly contradicts a guard the CLI-side code already implements and tests for; the fixer has no way to know the code-side exception exists unless the brief tells it, and both zero-commit prohibition sentences must move together or the second re-blocks what the first just unblocked. A dedicated `NITS_ONLY` render token (rather than an inferred condition) keeps the brief's claim exactly synchronized with the runtime guard's actual `nits_only` check — the only thing that determines whether `_implementer_common.py` will actually accept a zero-commit success.
- Rejected: (a) Remove the `nits_only` guard from `_implementer_common.py` instead, keeping the strict template rule — rejected because that guard was added deliberately (see `_implementer_common.py:894-898`) specifically to allow legitimate nits-only zero-commit passes; removing it reintroduces the exact false-`stuck` bug #592 was filed to fix. (b) Key the carve-out off an inferred fixer-visible condition instead ("pushed back on every finding, no code change required") rather than an explicit `NITS_ONLY` token — rejected because a full-scope (non-nits-only) fixer session can also legitimately push back on every `[BLOCKING]`/`[GAP]` finding under `mill-receiving-review`'s legitimate-pushback rules, which would incorrectly grant the zero-commit carve-out to a pass the runtime guard never intended to cover (the guard checks `nits_only`, not "all findings pushed back"); an explicit token avoids this semantic drift entirely.

### reword "before reading" to "before evaluating or acting" (#593)

- Decision: In `mill-receiving-review/SKILL.md`'s frontmatter `description` and its "Core Rule"/opening paragraph, and in `mill-start/SKILL.md` (Phase: Discussion Review step 3, plus the `--auto` mode subsection reference) and `mill-plan/SKILL.md` (Phase: Plan Review step 3), reword "BEFORE reading any review file" / "BEFORE reading the review file" to "before evaluating or acting on findings." Additionally, instruct both `mill-start` and `mill-plan` to load `mill-receiving-review` unconditionally at the very start of their review phase — before round 1's dispatch call — rather than gating the load on the moment of reading a file. This makes the rule structurally satisfiable in both dispatch modes: in subprocess/psmux mode the skill is now loaded even earlier than the literal file read; in Agent-mode, where findings arrive pre-embedded in the `<task-notification>` the orchestrator must read to learn the round's outcome, the skill is already active in context by the time the orchestrator evaluates or acts on those findings, even though it was technically "visible" in the notification text a moment earlier.
- Rationale: #593 is scoped specifically to `mill-start` and `mill-plan`, where the orchestrator itself reads and acts on review findings in the same session (no delegation). `mill-go` is explicitly out of scope for this fix (see Scope/Out) — it already delegates finding-reading to a dispatched fixer/implementer subagent's own brief, so the orchestrator never reads findings text there in any dispatch mode, and the existing "before reading" phrasing at mill-go's fixer-dispatch callsite is accurate as written.
- Rejected: (a) Leave `mill-receiving-review`'s own wording unchanged and only touch mill-start/mill-plan's callsites — rejected because the skill's own frontmatter/opening line is what an operator or a future dispatched agent reads first, and leaving it saying "before reading" while callers say "before evaluating" is an inconsistent, confusing split. (b) Branch the rule text per dispatch mode (subprocess/psmux keep "before reading a file"; agent-mode says "before evaluating") — rejected as unnecessary complexity; "before evaluating or acting on findings" is true and enforceable in both modes without branching.

## Technical context

- `## Agent-mode dispatch` step 3 already retains the background agent's `agentId` in a local Builder variable for the duration of the batch ("Record the `agentId` the Agent tool returns... and retain it for the duration of this batch") — the liveness probe reuses this existing handle; no new state needs to be threaded through.
- `TaskOutput` (deferred tool, loaded via `ToolSearch`) accepts `task_id` (matches the `agentId`), `block` (default `true`), and `timeout` — call with `block: false` for the liveness probe so it returns immediately with current status rather than waiting.
- `_run_verify_gates` (`_implementer_common.py:642-696`) currently sequences `verify_cmd` (batch) then `module_wide_verify_cmd` (module) unconditionally when both are non-`None`; this is the function to extend with the baseline parameter. It's called from all `_forward_output` success-emit paths (`_implementer_common.py:1099,1192,1281` roughly) plus `finalize_from_output` — the baseline lookup/short-circuit should live inside `_run_verify_gates` itself (or a thin wrapper it delegates to) so every call site picks it up automatically, matching the existing "no code path can skip the module-wide check" invariant from #541.
- `module_wide_verify_cmd` is read once in `millpy-implement.py` from the overview frontmatter (`overview_frontmatter.get("verify")`, `millpy-implement.py:266`) and passed down to both the `finalize` stage (line 295) and the `full` stage (line 515) — the baseline lookup needs the same `status_path`/task context available at both call sites.
- `_status.py` already has `set_batch_field`/batch-scoped helpers; the new `module_verify_baseline` field is task-scoped (not per-batch), so it likely wants a new top-level status.md YAML field plus a small `_status` helper pair (get/set/clear) rather than reusing the per-batch field helpers. Mirror the existing pattern used for other task-scoped scalar fields in the status.md YAML block (e.g., `plan:`, `parent:`).
- `mill-merge-in`'s SKILL.md (and/or its underlying script) is the natural place to clear the cached `module_verify_baseline` after a successful parent-branch sync, since that's the only event that can change what the parent branch's verify health looks like mid-task.
- `_implementer_common.py:894-898`'s existing `nits_only` guard/comment already documents the exact carve-out semantics the templates need to describe in prose — the template wording should mirror this comment's language rather than inventing new terminology.
- `mill-go/SKILL.md:349,496,672,787` are the four places that already correctly describe the fixer/implementer owning `mill-receiving-review` — read these as the reference pattern for "delegated reading," confirming why mill-go itself needs no wording change for #593.
- Test file naming: `test-agent-mode-dispatch.py` and `test-agent-dispatch.py` are the existing suites most likely to already cover step 4's transient/stuck classification and would need new cases for the liveness-probe branch (probe-says-running vs. probe-says-dead vs. probe-errors); `test-implementer-common.py` already has cases 30/31/32 covering the #541 module-wide gate and is the natural home for the new baseline-aware cases.

## Constraints

- Windows/`cp1252` stdout: any new `print()`/log output added to `_implementer_common.py` or `millpy-implement.py` must stay ASCII-only per project convention (`—` → ` -- `, `->` stays `->`).
- The transient `git worktree add` used for the baseline check must be cleaned up (`git worktree remove`) even on a failing verify run or an exception mid-check — use a `try`/`finally` (or equivalent) so a crashed baseline computation never leaves an orphaned worktree directory behind for the next run to trip over.
- The baseline computation must not mutate the task worktree's own working tree or index at any point (no `git stash`/checkout-and-restore approach) — CLAUDE.md's path-invariants and general "recursive deletion strips junctions first" caution both reflect a project-wide aversion to any operation that could leave the active worktree in an inconsistent state if interrupted; a fully separate transient worktree sidesteps this class of risk entirely.
- `Verify command shape` (CLAUDE.md): for Python/mill projects, `verify:` commands must start with a literal empty `PYTHONPATH=` prefix so the subprocess doesn't inherit the cache `PYTHONPATH`. The baseline check re-runs the existing `module_wide_verify_cmd` string verbatim in the transient worktree, so this constraint is already satisfied by construction — no new prefix logic needed.
- The liveness-probe fix (#587/#595) has no automated-test surface — `TaskOutput` depends on live harness runtime state that unit tests can't fabricate. It must be documented as an orchestration-wording change validated by manual reasoning and observed in the next real stopped/killed-notification incident, not covered by `test-agent-mode-dispatch.py` assertions beyond exercising the surrounding classification logic with a mocked/stubbed probe result.
