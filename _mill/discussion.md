## Problem

Three independent gaps surfaced from real external usage of mill-plan/mill-go against another repo (loomyard), filed as GitHub issues #741, #742, #743:

1. **Fork scope violations (#741).** During a mill-plan session, two `Agent(subagent_type: "fork")` calls were dispatched in parallel with narrow, explicit "research only — read these files, report back facts, do not write or edit any plan files" directives. Both ignored the scope: one began writing real `_mill/plan/*.md` batch files and created its own competing task list mirroring the parent's; the other wrote a full competing restructuring of `00-overview.md` and made an out-of-scope edit to `mill-config.yaml` (adding a `pipeline.done_gate` key). Both had to be caught mid-session via file-timestamp/task-list drift and manually told via `SendMessage` to stop. This is a different failure mode than the one already fixed by `8eb2cb05` (which added mill-start's "Fork echo caution" note about a fork *restating/echoing* the parent's context) — here the fork took real, unauthorized **write actions** on shared task state, it did not just parrot text back.

2. **No mechanical Context/Edits completeness check (#742).** During a holistic plan review, 5 of 6 review rounds (rounds 2-6) each surfaced a NEW instance of the identical finding class: a card's `Requirements:` prose referenced an identifier whose defining file was absent from that card's own `Context:`/`Edits:` list. Round 1 caught real bugs; every BLOCKING finding after that was this one mechanically-detectable, recurring pattern — costing a full paid LLM review round each time it recurred, instead of being caught up front the way `_plan_validate.py`'s existing structural checks (`card-missing-field`, `reads-not-backtick-path`, etc.) already catch other card defects.

3. **Missing anti-pause guidance (#743).** mill-plan's Phase: Plan Review is meant to be fully autonomous — the skill text says "Never pause mid-phase to ask the user. Only the max-rounds escape ... is allowed to break that rule" (`plugins/mill/skills/mill-plan/SKILL.md:10`) and lists exactly two escape hatches (max-rounds prompt, non-progress halt). But nothing in the skill text, nor in the shared "## Agent-mode dispatch" section in `mill-go/SKILL.md` that mill-plan/mill-start reuse for background-agent dispatch, explicitly states that *waiting* on a background reviewer/implementer is never itself a decision point. During a planning session, `AskUserQuestion` was called right after dispatching a background plan-review agent, offering a fake choice between "wait" and "give me other work" — there was no real decision, and the operator had to correct it directly.

**Why now:** all three were caught via direct operator observation during real task execution, not via unit tests — they are gaps in the *guidance text* and the *pre-review validator*, not runtime bugs. Left unfixed, gap 1 risks real data loss/corruption in shared plan/config state next time a fork over-reaches; gap 2 keeps burning paid LLM review rounds on a class of defect that is cheap to catch mechanically; gap 3 keeps producing unnecessary operator interruptions during what is supposed to be a fully autonomous phase.

## Scope

**In:**
- A new "Fork scope guardrail" subsection in `plugins/mill/skills/mill-plan/SKILL.md` (Phase: Plan) requiring any research-only fork's prompt to explicitly forbid Edit/Write/Bash-mutating tool calls and touching `plan_dir`/`status_path`/config files, plus a mandatory post-return `git status --porcelain` check by the orchestrator to catch unauthorized writes before trusting the fork's report.
- A new heuristic validator check, `context-completeness`, added to `plugins/mill/scripts/_plan_validate.py` and wired into `run()`, plus its fix-table row in `plugins/mill/skills/mill-plan/SKILL.md`'s Step 1.5 table.
- A one-line explicit anti-pause rule added in two places: `plugins/mill/skills/mill-plan/SKILL.md` Phase: Plan Review (step 2, before the dispatch-mode branch) and the shared "## Agent-mode dispatch" section's "Agent-mode properties" bullet list in `plugins/mill/skills/mill-go/SKILL.md`.
- Unit tests for the new validator check (`plugins/mill/unit_tests/test-plan-validate.py`, following the existing `test_check_*` naming/assertion pattern in that file).

**Out:**
- No change to mill-start's existing "Fork echo caution" note (`plugins/mill/skills/mill-start/SKILL.md`) — that addresses a different symptom (echoing/restating) and stays as-is.
- No change to the Agent tool's actual capability model — forks cannot be structurally prevented from calling Edit/Write/Bash (the "fork" subagent type always inherits full tool access per its design); the fix here is procedural (prompt wording + post-hoc verification), not a tool-permission change.
- No broader identifier-matching heuristic (function/type/sentinel-name patterns) for `context-completeness` — scoped to file-path-shaped backtick tokens only (see Decisions).
- No batch/module split mandated for this plan — left to mill-plan's existing batch-sizing rules (see Decisions).
- No change to `git-clone/SKILL.md:92`'s stale `AskUserQuestion` reference (found during exploration, contradicts the `mill:conversation` ban) — out of scope for this task; not part of any of the three filed issues.
- No repo-wide "fork dispatch contract" doc — guidance stays skill-local, consistent with how mill-start already documents its own fork guidance inline rather than via a shared doc.

## Decisions

### Fork scope guardrail placement and mechanism (#741)

- Decision: Add a "Fork scope guardrail" section to `plugins/mill/skills/mill-plan/SKILL.md`'s Phase: Plan (mill-plan currently has zero fork-dispatch guidance of any kind — verified by reading the full file; only mill-start has fork guidance, and it addresses a different failure mode). The section must state: (a) any research-only fork's prompt must explicitly instruct it not to call Edit/Write, not to run mutating Bash commands, and not to touch `plan_dir`, `status_path`, or any `mill-config.yaml`/`config.local.yaml`; (b) immediately after the fork returns, the orchestrator MUST run `git status --porcelain` (scoped to the worktree) and treat any unexpected new/modified/untracked path as a scope violation — the fork's report is not trusted until this check is clean; (c) on a detected violation, the orchestrator must revert the unauthorized changes (`git checkout --` / delete untracked files as appropriate, using the same care as any other uncommitted-work-preservation situation) before proceeding, and must not silently incorporate the fork's unauthorized writes into the plan.
- Rationale: The reported failure mode is not "the fork misunderstood and restated the prompt" (already covered by the existing echo-caution note) — it is "the fork used its inherited full tool access to make real writes despite an explicit no-write directive." Since Agent-mode forks cannot be structurally sandboxed away from Edit/Write/Bash, the only two levers are (1) stronger, more explicit negative instructions in the dispatch prompt itself, and (2) a mechanical, cheap post-hoc check (`git status --porcelain`) that catches the failure even if the prompt-level instruction is again ignored. This mirrors how `_treeguard.check_and_restore` already exists elsewhere in the codebase as a cheap git-status-based safety net around out-of-process work.
- Rejected: (a) Only strengthening mill-start's existing echo-caution wording — rejected because it targets a different symptom and mill-plan (where the incident actually happened) would still have zero fork guidance. (b) A repo-wide shared "fork dispatch contract" doc — rejected as premature abstraction; mill-start already documents its own fork guidance locally rather than via a shared doc, and duplicating that pattern for mill-plan is consistent and YAGNI (only two skills currently dispatch forks; a third occurrence would be the trigger to extract a shared doc).

### `context-completeness` validator check design (#742)

- Decision: Add `_check_context_completeness(batch_files: list[Path]) -> list[dict]` to `plugins/mill/scripts/_plan_validate.py`, wired into `run()` alongside the other per-batch checks (`errors.extend(_check_context_completeness(batch_files))`). Per card (obtained via the existing `_parse_cards(text)` helper at `_plan_validate.py:117`, same pattern `_check_card_missing_field` already uses at `_plan_validate.py:742-761` to get `(card_num, card_lines)` pairs and join them into `card_text`): extract that card's `Requirements:` field text (locate the `- **Requirements:**` header line the same way `_check_card_missing_field` locates any required-field header, then take its inline value plus any wrapped continuation text up to the next `- **Field:**` header or end of card), then regex-find every backtick-quoted token in that Requirements text (`` `([^`]+)` ``) that "looks like a file-path reference" — contains a `/` OR ends in one of `.py .go .cs .ts .md .yaml .yml .json`. For each such token, check whether it (as an exact string, or by basename if the token is a bare filename without a directory component) appears in that same card's own `Context:`, `Edits:`, or `Creates:` token sets. **Important existing-code gotcha discovered during exploration:** the existing `_parse_context_only` / `_parse_edits_only` / `_parse_creates_only` helpers (`_plan_validate.py:150-299`) parse Context:/Edits:/Creates: tokens for an ENTIRE batch file, not scoped to one card — they scan every `- **Context:**` etc. header in the whole file regardless of which card it belongs to. `context-completeness` needs *per-card* Context/Edits/Creates, so it must NOT reuse those three helpers directly; it must extract Context:/Edits:/Creates: tokens from the same single card's `card_text` using the same backtick-extraction regex logic inline (mirroring how `_check_card_missing_field` and `_card_field_is_none` already scope their field-header search to one card's `card_lines`/`card_text`), not from the whole-batch helpers. Flag any unresolved token as a new blocking validator error: `{"check": "context-completeness", "batch": batch_path.stem, "card": card_num, "path": <token>, "message": f"card {card_num}'s Requirements: references '{token}' which is not in this card's Context:/Edits:/Creates:"}`. Add the fix-table row to `plugins/mill/skills/mill-plan/SKILL.md`'s Step 1.5 table (positioned alphabetically/logically near `plugin-manifest-context-missing`): mechanical fix = "Add the referenced file to the card's `Context:` list (unless the card's own `Edits:`/`Creates:` already covers it, in which case re-verify the check's own-list cross-reference before editing)."
- Rationale: File-path-shaped backtick tokens are the narrowest, highest-precision heuristic available — they reuse the plan's own existing "all references are backtick-wrapped paths" convention (already enforced by `reads-not-backtick-path`, confirmed check-name string `"reads-not-backtick-path"` at `_plan_validate.py:1185` etc.), so a Requirements sentence like "Replace `_load_config` in `mill-claim.py` with `from _config import load_config`" (the exact example already used in mill-plan/SKILL.md's own Principles section, `mill-plan/SKILL.md:267`) naturally produces backtick-quoted, extension-bearing tokens the check can reliably extract, with zero new grammar for planners to learn. The issue's own literal examples (`Err*Sentinel`, `client.<method>(`, etc.) are Go-identifier-shaped and would require an ever-growing, language-specific pattern list to generalize across this multi-language codebase (Python, Go, C#) — accepting narrower recall in exchange for not maintaining per-language regex heuristics is the right trade given the issue's own explicit statement that "false negatives are acceptable, since the goal is catching the common case cheaply." Treating it as a hard blocking validator error (not advisory-only) matches how every other structural check in this validator already behaves and slots into the existing fix-table/two-pass-cap machinery with no new plumbing.
- Rejected: (a) Broader identifier-matching (function/type/sentinel-name regex patterns) — rejected per the language-specific brittleness above. (b) Advisory-only/non-blocking — rejected because it would not actually stop the recurring paid-review-round cost the issue describes; the whole point is to catch it before the LLM reviewer round, the same way every other Step 1.5 check does.

### Anti-pause rule placement (#743)

- Decision: Add the same one-line rule in two places. First, `plugins/mill/skills/mill-plan/SKILL.md` Phase: Plan Review, inserted at the start of step 2 (before "Dispatch mode: Resolve dispatch mode via `_agent_dispatch.resolve_dispatch_mode(cfg)`", currently `mill-plan/SKILL.md:161`) — this covers both the Agent-mode and subprocess/psmux branches for plan review specifically, since the subprocess/psmux branch's log-polling loop (`mill-plan/SKILL.md:175-189`) is documented inline per-skill and is NOT part of the shared "## Agent-mode dispatch" section. Second, add the same rule to the "Agent-mode properties" bullet list inside the shared "## Agent-mode dispatch" section of `plugins/mill/skills/mill-go/SKILL.md` (that section spans `mill-go/SKILL.md:105-199`; the "Agent-mode properties" bullets — confirmed present, e.g. the "No log-polling or liveness check required" bullet — are the natural home) — this covers every other reuser of that shared section (mill-go's own Implement/Fix/merge-in dispatch, and mill-start's discussion-review reuse, per `mill-start/SKILL.md`'s explicit "follow the Agent-mode dispatch pattern" references). Exact wording (adapt inline to each site's surrounding prose): "Waiting on this dispatch — either branch — is a narration point: state in one sentence what you're waiting for. It is never a question point; `AskUserQuestion` (and, under `mill:conversation`'s numbered-options rule, any equivalent operator prompt) is banned here absent one of this phase's explicitly named escape hatches." Reuse the existing repo-wide phrasing pattern already established elsewhere (`plugins/mill/skills/conversation/SKILL.md:33` — "Never use `AskUserQuestion`" — and `plugins/mill/skills/mill-self-report/SKILL.md:65`'s "(no `AskUserQuestion`)" parenthetical) rather than inventing new phrasing.
- Rationale: The issue's own suggestion explicitly frames this as "and/or" between mill-plan's Phase: Plan Review and the shared Agent-mode dispatch section — doing both closes the gap for all three review loops (mill-start's discussion review, mill-plan's plan review, mill-go's implement/fix loop) in two edits rather than three-plus, and specifically covers the subprocess/psmux branch (which the shared section alone cannot, since that branch's polling loop lives outside the shared section entirely — confirmed by reading mill-go/SKILL.md:105-199 in full, which contains no subprocess/psmux content, and by mill-plan/SKILL.md's own subprocess branch at lines 175-189 having no such content either today).
- Rejected: (a) mill-plan only — rejected because it leaves mill-go's own dispatch waits and mill-start's discussion-review reuse with no equivalent explicit guidance, when the same failure mode (a spurious "wait vs. do other work" prompt) is equally possible there. (b) Shared section only — rejected because it silently fails to cover the subprocess/psmux branch, which is exactly the branch this hub's config was observed running under during the incident (per `roles.plan-review.batch.reviewer: null` / dispatch-mode config already noted in mill-plan/SKILL.md:161).

### Batching left to mill-plan (housekeeping)

- Decision: This discussion documents all three gaps as independent Decisions but does not prescribe a batch split; mill-plan's own batch-sizing rules (`mill-plan/SKILL.md:47`, "Split on natural module/subsystem boundaries... If two adjacent batches share >80% of their Context:, merge them") decide 2 vs. 3 batches once the final Context:/Edits: lists are known.
- Rationale: The three gaps touch disjoint code (SKILL.md prose for #741 and #743, `_plan_validate.py` + its unit tests for #742) with no shared Context:, so mill-plan's existing heuristics will most likely naturally separate or combine them correctly without this discussion pre-deciding it — avoiding a hypothetical prescription that might not match mill-plan's actual card-level Context: analysis.
- Rejected: Explicitly mandating a 3-batch (one-per-gap) split — rejected as an unnecessary constraint on mill-plan's own sizing logic (YAGNI).
