## Problem

mill-go's batch-verify, finalize, and baseline machinery has accumulated seven independent reliability bugs/gaps, each caught live during real mill-go runs across three different downstream repos (loomyard, millhouse itself, and NORCE.Models). None of them are hypothetical — every one has a filed GitHub issue with a concrete reproduction from an actual run. They cluster into five subsystems:

1. **mill-plan's verify-command authoring** misses failure modes it should catch and folds in failure modes it shouldn't: batches that add `//go:build` tags to previously-untagged files don't get an untagged compile check, so a Tier-1 build break introduced by re-tiering can go undetected for several batches (#642); and batches' `--only` verify lists can accidentally include test files unrelated to the batch's own cards, causing a pre-existing `main`-level failure to falsely block a fully-correct batch (#638).
2. **mill-go's finalize completeness recount** is a bare "commits since start_sha vs. cards in batch" comparison with no way to know when a batch brief legitimately sanctioned combining multiple cards into one commit — it misclassifies a genuinely complete batch as `stuck_type: incomplete`, and because `--resume-incomplete`'s re-dispatch makes no new commit (there's nothing left to do), the same misclassification repeats forever (#660).
3. **`pipeline.done_gate`** has no pre-implementation baseline pre-flight, so a self-capturing regression/snapshot test suite used as the done_gate silently captures its "baseline" from the task's own just-finished implementation at Handoff — reporting success while providing zero actual regression protection (#650).
4. **mill-go SKILL.md's extended-timeout guidance** (600000ms/10min for Bash-tool calls that replay a batch's `verify:` command) is scoped only to `millpy-fix.py --stage finalize`, but `millpy-implement.py --stage finalize` runs the exact same regression-guard verify replay and hits the same default 2-minute Bash-tool timeout (#639, #624) — a pure documentation gap.
5. **`_verify_baseline.compute_baseline`'s transient-worktree checkout** can hit a Windows `WinError 3` (path not found / MAX_PATH) on repos with deeply-nested test fixtures, because `.scratch/verify-baseline-<uuid4().hex>/` adds ~50+ characters of path prefix on top of an already-long fixture path (#629). This is a real gap, but investigation during discussion turned up a wrinkle: a prior fix (commit `698b5a10`, landed 2026-07-09) already added `core.longpaths=true` to the `git worktree add` call, two days *before* #629 was filed — yet the failure still occurred. It is not established from static analysis alone whether the WinError 3 originates in git's checkout itself (longpaths insufficient at this nesting depth) or in the verify command's own test-fixture writes during execution inside the deep transient path. No Windows machine is available in this dev environment to confirm either way (see Decisions → `windows-long-path-mitigation`).

**Why now:** all seven were auto-filed by `/mill-self-report` (or manually) during real task work over 2026-07-09 through 2026-07-15 — this is accumulated operational debt in the pipeline's own reliability, not a feature request. Left unfixed, several of these actively cause wasted implementer/reviewer cycles (false `stuck_type: verify`/`incomplete` escalations) or silent loss of regression protection (`done_gate` capturing from the wrong commit).

## Scope

**In:**
- mill-go / `_implementer_common.py`: a new finalize-time gate diffs each batch's commits for newly-added Go build tags on previously-untagged files and runs an untagged compile check over the affected package(s) before accepting success (#642).
- mill-plan / `_plan_validate.py`: a new deterministic validator (`_check_verify_unrelated_test_files`) drops candidate verify test files from a batch's `verify:` command when they're both untouched by the batch's cards and byte-identical to `main` (#638).
- mill-go / `_implementer_common.py`: the implementer's success envelope gains a self-reported `cards_done` field (integer card numbers, extracted batch-file card IDs as the comparison set — not a bare count); the finalize completeness gate compares against it instead of raw commit count; `--resume-incomplete` re-dispatch gets an idempotent-confirmation short-circuit as a backstop (#660).
- mill-go: an opt-in Prepare-phase `done_gate` baseline pre-flight, config-gated, mirroring the existing "0.5 Baseline pre-flight" module-wide-verify pattern (#650).
- mill-go SKILL.md: generalize the existing extended-timeout note (Agent-mode dispatch step 6) to cover any finalize-stage CLI call that replays a `verify:` command, not just `millpy-fix.py` (#639, #624). Documentation-only.
- `_verify_baseline.py`: shorten the transient-worktree directory name (`verify-baseline-<uuid4().hex>` → a shorter collision-resistant form) to reclaim Windows path budget (#629).

**Out:**
- Generalizing the #642 build-tag-retiering detection beyond Go (no pytest-marker / C#-trait equivalent) — explicitly deferred until a concrete non-Go instance is observed.
- Extending the module-wide verify-baseline (clean/pre-existing-failures) machinery down to per-batch verify commands (the heavier alternative fix considered for #638) — the lighter plan-time list-validation fix was chosen instead; this is documented as a rejected alternative, not built.
- Any `\\?\`-extended-length-path-prefix change to the `git worktree add` invocation for #629 — cannot be validated without a Windows machine; explicitly rejected as too risky to land unverified. The existing non-blocking degrade (baseline computation fails → `result: "error"` → task proceeds with strict per-batch gating) remains the terminal safety net and is not being changed.
- Heuristic auto-detection of "self-capturing" done_gate commands for #650 — the fix is an explicit opt-in config flag, not automatic detection.
- Any change to `pipeline.done_gate`'s existing Handoff-time invocation itself (step 0, "Pre-done gate" in mill-go SKILL.md) — it still runs at Handoff exactly as today; the new pre-flight is an *additional*, earlier, opt-in step.

## Decisions

### go-build-tag-retiering-check (#642)

- Decision: **not** authored by mill-plan at plan-write time — at plan-write time no diff exists yet, only card prose, so there is nothing mechanical to detect. Instead, this is a new automatic **finalize-time gate**, parallel to the existing verify/module-wide-verify/completeness/dirty gates in `_implementer_common.py`'s success-path pipeline (see Technical context). On a batch's explicit-success path, after the existing verify gate passes, finalize diffs `start_sha..HEAD` for newly-added `//go:build <tag>` lines in previously-untagged `.go` files. If any are found, finalize runs a plain untagged compile check (`go build ./<pkg>/...` or `go vet ./<pkg>/...`) over the affected package(s) before accepting the batch as complete. A failure demotes the result to `stuck_type: verify` with a reason naming the retiered package(s) — identical in shape to the existing verify-gate failure path, so it flows through the same `_reclassify_verify_failure` partial-batch logic already in place.
- Rationale: the batch that introduces the re-tiering is the one whose diff is available to inspect — by construction, this gate can only run after the commits exist, so finalize-time is not a compromise, it's the only point in the pipeline where "which files gained a build tag" is actually knowable. Catching the compile break in the introducing batch's own finalize call (rather than incidentally, several batches later) avoids a discovered-scope fix commit downstream. This mirrors the resolution chosen for #638's implementation locus (see `batch-verify-list-validation` below): prefer a deterministic, unit-testable gate over mill-plan skill-authoring judgment wherever a mechanical check is possible.
- Rejected: (a) mill-plan authoring the check at plan-write time — physically unsatisfiable; no diff exists before implementation. (b) a task-level module-wide verify entry that always runs both tagged and untagged builds on every batch — broader than needed; only batches that actually retier files need the extra check, and the finalize-time diff scopes it precisely. (c) doc-only reviewer guidance — relies on manual vigilance for a mechanically detectable pattern.
- Scope note: Go-only for now. `//go:build` is a Go-specific mechanism; no other language's equivalent (pytest markers, C# `[Trait]` categories) has produced a concrete failure yet. Generalizing now would be designing for a hypothetical. The finalize-time diff check (newly-added build-tag lines → untagged compile check over affected packages) is documented as a pattern a future language-specific extension can follow, implemented as its own gate rather than generalized prematurely.

### batch-verify-list-validation (#638)

- Decision: at plan-write time, mill-plan's existing self-review loop (`mill-review-plan`) runs a **new deterministic validator function** — `_check_verify_unrelated_test_files` — added to `plugins/mill/scripts/_plan_validate.py` alongside its existing `_check_verify_*` family (`_check_verify_not_isolated`, `_check_verify_full_suite`, `_check_verify_malformed_cwd`, `_check_verify_mixed_cwd`; see `_plan_validate.py:1218` onward). For each candidate test file in a batch's `verify:` command: if it is NOT in the batch's own "Files Touched" list AND its content is byte-identical to `main` (`git diff main -- <file>` is empty), the validator flags it; mill-plan drops the flagged files from the batch's verify command before the plan is committed.
- Rationale: directly targets the root cause described in the issue's reproduction hint (an unrelated file that is byte-identical to `main` and not touched by the batch's own cards has no business gating that batch). Naming the concrete module resolves the code-vs-skill ambiguity: `_plan_validate.py` already runs deterministic, unit-testable checks against batch files as part of the same self-review loop this decision hooks into (see CLAUDE.md's `_plan_validate.py` verify-not-isolated convention), so this is an additive check in an established pattern, not a new mechanism. Lower implementation cost than extending the module-wide baseline machinery to per-batch granularity, and doesn't risk under-including legitimately-related tests the way a strict exact-match-only heuristic would.
- Rejected: (a) exact-match-only verify lists (verify = Files Touched, no keyword/path matching at all) — simpler, but would under-include a test file that legitimately exercises a touched module without being named after it. (b) Extending the existing module-wide verify-baseline (clean/pre-existing-failures) machinery down to per-batch verify commands — more robust in principle (catches ANY pre-existing failure regardless of how it entered the list, not just ones the plan-time heuristic already knew to check), but a materially bigger mechanism change (baseline computation is currently task-scoped and module-wide only); deferred as a heavier follow-up if plan-time validation proves insufficient in practice. (c) leaving the implementation locus as "mill-review-plan, the natural place" skill-prose only — makes the check impossible to unit test, which the Testing section below requires.

### completeness-recount-cards-done (#660)

- Decision: two complementary changes. (a) The implementer's success JSON envelope gains a self-reported `cards_done` field: a list of integer card numbers the implementer addressed in this commit set. The **declared card-ID set** the gate compares against is extracted from the batch file itself, reusing the same heading regex `millpy-implement.py` already uses to compute `card_count` (`r"(?m)^###\s+Card\s+\d+\s*:"`, line 368) — extended to capture the numeric group (`^###\s+Card\s+(\d+)\s*:`) so the result is the literal `set[int]` of card numbers actually declared in the batch file, not an assumed contiguous `1..card_count` range. This distinction matters: the #660 repro's own batch had cards numbered "Card 7" and "Card 8" (task-global numbering, not batch-local 1-indexing), so a range assumption would have been wrong. This `card_ids: set[int]` is threaded into `_batch_completeness_stuck` alongside `card_count` (both derived from the same batch-file parse; `card_count` can become `len(card_ids)` rather than a separately-computed value). The gate's new rule: stuck iff `card_ids - set(cards_done)` is non-empty (some declared card was never reported done); no discrepancy → gate passes regardless of raw commit count. (b) As a backstop, `--resume-incomplete`'s re-dispatch short-circuits directly to `status: success` when the fresh implementer session makes zero new content commits AND its envelope explicitly confirms (e.g. an `already_complete: true` field, itself populated by the same `cards_done` self-report matching all declared `card_ids`) that every card's requirements are already satisfied by the existing commit(s).
- Rationale: the raw commit-count heuristic was always a proxy for "did the implementer finish all the cards" — it has no way to represent the batch brief's own explicit permission to combine cards into one commit. Self-reporting `cards_done` replaces the proxy with the actual signal the gate wants. The resume backstop closes the specific infinite-loop failure mode from the issue (identical verdict repeats forever because no new commit is possible) as defense-in-depth, in case `cards_done` self-reporting has its own edge cases (e.g. a batch resumed after a mill-go version upgrade where the original session predates the new field).
- Rejected: (a) loosening the heuristic to "at least one content commit exists" — simplest, but weakens the gate's ability to catch a genuinely partial batch (implementer does card 1 of 2, stops — one content commit would now pass even though card 2 is unaddressed). (b) resume-backstop only, without `cards_done` — fixes the infinite loop but leaves the *initial* misfire on every legitimately-combined-commit batch unfixed; every such batch would always burn one wasted resume round-trip before the backstop rescues it.
- Note for mill-plan / implementer-brief template: this decision requires a template change to `implementer-brief.md` (or wherever the success-envelope schema is documented) so implementers know to populate `cards_done`. mill-plan itself is not otherwise involved in this fix — it's implementer-brief + `_implementer_common.py`.

### done-gate-baseline-preflight (#650)

- Decision: add a new, explicitly opt-in Prepare-phase step to mill-go — a `done_gate` baseline pre-flight, gated by a new config key (e.g. `pipeline.done_gate_baseline_preflight: true`, default `false`/absent). When set, this runs the `pipeline.done_gate` command **once, directly in the task's real worktree (not a transient one)**, from `git_root` — identical cwd to the Handoff-time invocation — positioned immediately after "0. Wiki health-check" and before "0.5 Baseline pre-flight" in mill-go SKILL.md's Prepare flow, i.e. strictly before batch 1's implementer is ever dispatched. Because this point in the flow is, by construction, before any batch has made a commit, the working tree is already at the pre-implementation state — no detached-HEAD checkout or throwaway worktree is needed (unlike `compute_baseline`'s transient-worktree pattern for `module_wide_verify_cmd`, which exists specifically to test the *parent* branch's state without touching the task's own tree; done_gate's self-capturing baseline needs the opposite — it must write into the real tree so the identical Handoff-time invocation finds it there later). mill does not parse, move, or persist whatever snapshot/baseline artifacts the project's own test framework writes as a side effect — they're left exactly where that framework put them; the framework's own "does a baseline already exist" internal logic is what makes the Handoff-time run compare instead of re-capture.
- Rationale: mirrors an established, already-working pattern in the same file (mill-go SKILL.md's "0.5 Baseline pre-flight") for *when* to run, while diverging deliberately on *where* to run, since the self-capturing-baseline problem needs the artifacts to persist in the real tree rather than a torn-down transient one. Explicit opt-in avoids forcing every task through an extra done_gate invocation when the repo's done_gate isn't self-capturing (the common case) — running a project's full done_gate command an extra time at Prepare has a real time cost that shouldn't be paid by tasks that don't need it.
- Persistence confirmed safe without new mill-side plumbing, provided the captured artifacts land in a gitignored path (true for the motivating repro: NORCE.Models' regression suite already wrote to `.scratch/regression-baseline/`, gitignored per this repo's own CLAUDE.md "Numerical Regression Testing" convention). Verified against `_cleanliness.py`: `compute_new_dirt`/`revert_out_of_scope_drift` (the per-batch cleanliness gate) call `_pygit2_util.status_porcelain(..., include_untracked=False)` — tracked-file diffs only — and `compute_scope_violations` (the Handoff terminal scope-violations gate) reads `git status --porcelain` output, which never includes gitignored paths by default. A gitignored baseline directory is therefore invisible to both gates through every intervening batch; no new persistence location or restore step is required. Caveat carried forward for implementation: if a project's self-capturing done_gate writes baseline artifacts to a *tracked* (non-gitignored) location, those files would surface as new tracked-file dirt in a later batch's cleanliness gate and could false-positive block it — this decision assumes/requires the artifacts are gitignored, and the implementer should verify that precondition for the specific `done_gate` command being configured, not assume it universally.
- Rejected: (a) doc-only guidance — doesn't actually prevent the original failure (silent capture from the wrong commit); the issue's own recovery required manual detached-HEAD surgery, which is exactly the kind of error-prone manual step automation should remove. (b) heuristic auto-detection of "self-capturing" done_gate commands (e.g. "did new files appear after a first run") — no reliable signal exists; a heuristic here is more likely to misfire (false positive on an unrelated gate that happens to write a log file) than to help. (c) running the preflight in a transient worktree mirroring `compute_baseline` exactly — would require the same self-capturing baseline files to somehow be copied back into the real tree afterward, an extra mechanism the real-worktree approach makes unnecessary.
- The Handoff-time "Pre-done gate" invocation (step 0 in mill-go SKILL.md's Handoff section) is unchanged — it still runs exactly as today. The new step is additive and earlier.

### finalize-timeout-guidance-generalization (#639, #624)

- Decision: rewrite mill-go SKILL.md's Agent-mode dispatch step 6 timeout note to state the rule generically — any `--stage finalize` call for a CLI whose finalize stage replays a batch's `verify:` command as a regression guard gets the extended 600000ms (10-minute) Bash-tool timeout. Explicitly name the current instances (`millpy-fix.py --stage finalize`, `millpy-implement.py --stage finalize`) so the rule is concrete, not just abstract, and keep the existing carve-out ("review-CLI finalize calls don't run verify commands and aren't affected") verbatim.
- Rationale: closes both #639 and #624 in one text edit, and prevents the identical doc gap from recurring if a third finalize-stage CLI is ever added that also replays verify. Pure documentation change — no code, no tests beyond confirming the SKILL.md wording is unambiguous.
- Rejected: narrow fix (add `millpy-implement.py --stage finalize` to the existing sentence without generalizing the rule) — same effort to write, but leaves the underlying pattern (finalize-stage CLIs default to needing the extended timeout unless they're review-only) implicit rather than stated, which is exactly how this gap was missed the first time.

### windows-long-path-mitigation (#629)

- Decision: shorten the transient-worktree directory name in `_verify_baseline.compute_baseline` from `verify-baseline-<uuid4().hex>` (32 hex chars) to a shorter collision-resistant form (e.g. 12 hex chars — still ~2^48 combinations, effectively collision-free for a short-lived per-invocation scratch directory) to reclaim path budget. Do not modify the `git worktree add` invocation to use a `\\?\`-extended-length-prefixed target path.
- Rationale: reclaiming ~20 characters of path budget is a pure string-length change, verifiable via existing unit tests on any platform (assert the directory-name pattern/length), and carries no platform-specific behavioral risk. It may or may not be sufficient to resolve #629's specific fixture path on its own — that's unknown without a Windows repro — but it strictly reduces the chance of hitting the limit and has zero downside. A `\\?\`-prefix change to the `git worktree add` target is a genuine git-invocation behavior change that cannot be validated in this dev environment (no Windows machine); landing it unverified risks a worse regression (broken worktree creation for every Windows user) than the narrow issue it targets.
- Rejected: (a) the `\\?\`-prefix approach — real regression risk, unverifiable here. (b) doc-only ("avoid self-capturing test frameworks with deeply-nested fixtures on Windows") — doesn't reduce the actual chance of hitting the limit for repos that already have such fixtures and can't restructure them. (c) splitting #629 out of this task's scope entirely — the shortened-directory-name mitigation is low-risk and low-cost enough to include; full scope-out is unnecessarily conservative given a safe partial fix exists.
- Open uncertainty carried into implementation: it remains unconfirmed whether the WinError 3 in #629 originates in `git worktree add`'s own checkout (where `core.longpaths=true`, already present since commit `698b5a10`, evidently wasn't sufficient) or in the verify command's own test-fixture writes during execution inside the transient worktree (i.e., the self-capturing-snapshot pattern from #650, but tripping a path-length limit rather than a wrong-baseline problem). The implementer should note this ambiguity in the batch's PR/commit message rather than asserting the mitigation "fixes" #629 — it reduces the odds, it does not guarantee resolution. The existing non-blocking degrade (baseline computation fails → `result: "error"` printed → task proceeds with strict per-batch gating, per `_run_baseline_stage`'s docstring contract) is unchanged and remains the terminal safety net regardless.

## Technical context

- **mill-plan verify-command authoring / validation** lives in the mill-plan skill/scripts — batch `verify:` fields are frontmatter on each batch file, parsed by `_plan_dag.parse_verify_field`/`_plan_dag._read_batch_frontmatter` (see `plugins/mill/scripts/millpy-implement.py:324-335` for how the overview's module-wide `verify:` is read the same way). `plugins/mill/scripts/_plan_validate.py` already has an established `_check_verify_*` family (`_check_verify_not_isolated` at line 1218, `_check_verify_full_suite` at 1305, `_check_verify_malformed_cwd` at 1375, `_check_verify_mixed_cwd` at 1440, all wired into `run()` at line 1663) — `batch-verify-list-validation`'s new `_check_verify_unrelated_test_files` check is added to this same family and file.
- **Go build-tag re-tiering gate** (`go-build-tag-retiering-check`, #642) is new code in `plugins/mill/scripts/_implementer_common.py`'s finalize success-path pipeline (same region as the other gates below — see `_forward_output`/`finalize_from_output`'s explicit-success branch around line 995 onward) — it needs a `git diff --unified=0 <start_sha>..HEAD -- '*.go'` (or equivalent) scan for added `//go:build` lines in files that had none on the parent side, then a `go build`/`go vet` subprocess call scoped to the affected package(s) on a verify-gate failure/pass.
- **Completeness/resume machinery** is in `plugins/mill/scripts/_implementer_common.py`:
  - `_content_commit_count` (line 37) — counts content commits since `start_sha`, excluding the "mill-go: start batch" housekeeping commit.
  - `_batch_completeness_stuck` (line 172) — the heuristic gate itself. Only fires when `verify_cmd is None or ignore_verify` (a passing verify command is currently treated as conclusive on the explicit-success path — this is WHY #660's batch, which apparently had no `verify:` command configured, hit the heuristic at all; a batch with a verify command wouldn't reach this gate today). `card_ids: set[int]` (superseding the bare `card_count` int) and `cards_done` should be threaded through this function's signature.
  - `card_count` is currently computed in `millpy-implement.py` at line 368 via `re.findall(r"(?m)^###\s+Card\s+\d+\s*:", _batch_text)` — extend the pattern to `r"(?m)^###\s+Card\s+(\d+)\s*:"` and use the captured groups to build `card_ids` instead of (or alongside) `len(...)`.
  - Call sites at lines 1083, 1223, 1315, 1407 — four distinct call sites (explicit-success path, and three no-JSON-inference fallback paths with `ignore_verify=True`) all need the `card_ids`/`cards_done` plumbing.
  - `--resume-incomplete` handling lives in `millpy-implement.py` (lines 426-461) — reads `start_sha`/`implementer_session` from `status.md` rather than re-capturing, specifically so the completeness recount isn't corrupted by a fresh `start_sha`. The idempotent-confirmation short-circuit described in `completeness-recount-cards-done` should hook in around where `finalize_from_output`/`_forward_output` process the resumed session's output (same `_implementer_common.py` module).
- **`module_verify_baseline` machinery** (`plugins/mill/scripts/_verify_baseline.py`) is the existing pattern both `done-gate-baseline-preflight` and `windows-long-path-mitigation` build on/interact with:
  - `compute_baseline` (line 70) creates a transient worktree at `<project_root>/.scratch/verify-baseline-<uuid4().hex>/` via `git worktree add ... -c core.longpaths=true` (long-path flag already present, added in commit `698b5a10`), reuses gitignored dependency dirs via junctions, and runs `module_wide_verify_cmd` there with a flakiness-guard retry and a control-run corroboration step before caching `"pre-existing-failures"`.
  - Invoked from `millpy-implement.py`'s `_run_baseline_stage` (line 78) at mill-go's Prepare "0.5 Baseline pre-flight" step, and cached via `_status.get_module_verify_baseline`/`set_module_verify_baseline`.
  - `_run_baseline_stage` never raises to its caller — every failure path prints a JSON line and returns 0, leaving the baseline field unset (fail-safe: next `_run_verify_gates` call runs the gate strictly). This existing contract is what makes #629's mitigation "safe to attempt, safe to fail" — no behavior change needed for the fail-safe itself.
- **mill-go SKILL.md** (`plugins/mill/skills/mill-go/SKILL.md`) is 833 lines. Relevant sections: line 157 (the existing timeout-guidance sentence to generalize, in the Agent-mode dispatch documentation), and lines 771-798 (the "0. Pre-done gate" Handoff step, which the new opt-in Prepare-phase pre-flight in `done-gate-baseline-preflight` mirrors but does not replace).
- **`pipeline.done_gate`** config resolution: `(cfg.get("pipeline") or {}).get("done_gate")`, deep-merged from `<hub_root>/mill-config.yaml` and `.millhouse/config.local.yaml` via `_config.load_config`. The new `pipeline.done_gate_baseline_preflight` key should follow the same deep-merge convention and be documented in both `mill-config.yaml` (hub) and the plugin's config template, per this repo's CLAUDE.md note "`mill-config.yaml` hub file and plugin template must stay in sync."

## Constraints

- No CONSTRAINTS.md exists at the hub root — none carried forward beyond what's stated inline above.
- The dev environment for this task is Linux; #629's fix cannot be validated end-to-end on Windows. The scope for #629 is deliberately narrowed to a change that is verifiable cross-platform (see `windows-long-path-mitigation`).
- Per CLAUDE.md: `print()`/`_log()` output must stay ASCII-only (no em dashes, no arrow glyphs) in any new script output.
- Per CLAUDE.md: Ad-hoc `dotnet build`/`dotnet test` invocations (relevant to `done-gate-baseline-preflight`'s testing, since the motivating #650 repro used a dotnet regression-test project as `done_gate`) must pass `--nologo -clp:ErrorsOnly` and must never be piped through `grep`/`tail` in the gating invocation itself, to avoid masking dotnet's exit code.

## Testing

- **`go-build-tag-retiering-check`**: unit test in `_implementer_common.py`'s test suite — given a synthetic batch commit range that adds `//go:build` to a previously-untagged fixture file (tempfile git repo, consistent with `unit_tests/` conventions — no real LLM), assert the new finalize gate detects the added tag and invokes the untagged compile check for the affected package; assert it stays silent when no build tag was added. TDD candidate.
- **`batch-verify-list-validation`**: unit test for `_check_verify_unrelated_test_files` in `_plan_validate.py`'s test suite — given a candidate verify file list and a fake `main` ref, assert files that are (a) not in Files-Touched and (b) byte-identical to `main` are flagged/dropped, while files that fail either condition are kept. Use the existing in-memory/tempfile git fixture pattern already used by the other `_check_verify_*` tests. TDD candidate.
- **`completeness-recount-cards-done`**: unit tests in `test-millpy-implement.py`-style coverage for `_implementer_common.py`:
  - The card-ID extraction regex change: given a batch file with non-contiguous card numbers (e.g. "Card 7" and "Card 8" only, mirroring the #660 repro), assert `card_ids == {7, 8}`, not `{1, 2}`.
  - `_batch_completeness_stuck` (or its renamed/extended successor) returns no-stuck when `cards_done` covers all of `card_ids` even with fewer commits than `len(card_ids)`.
  - Still returns stuck/incomplete when `cards_done` is missing entries from `card_ids`.
  - The `--resume-incomplete` short-circuit: a resumed session with zero new commits and `already_complete: true` yields `status: success`, not a repeated `incomplete` verdict. ## Q&A log

- **Q:** How should mill-go catch Tier-1 compile breaks when a batch adds Go build tags to previously-untagged files (#642)? **A:** [auto-pick] Add an untagged build/vet check over the affected package(s), run automatically at the introducing batch's own finalize stage (not authored by mill-plan at plan-write time, since no diff exists then — see Decisions → `go-build-tag-retiering-check`, resolved during discussion review round 1 after this design gap was flagged). **Why:** the introducing batch's finalize call is the first point where the compile-break-causing diff actually exists; catching it there avoids a downstream discovered-scope fix commit.
- **Q:** Should the #642 fix generalize beyond Go build tags to other languages' re-tiering mechanisms? **A:** [auto-pick] Go-only for now; document the pattern for future extension. **Why:** no concrete non-Go instance has been observed — generalizing now would be designing for a hypothetical (YAGNI).
- **Q:** How should mill-plan avoid folding unrelated pre-existing-failing tests into a batch's verify list (#638)? **A:** [auto-pick] Validate candidate verify test files against `main` at plan-write time; drop files that are both untouched by the batch's cards and byte-identical to `main`. **Why:** directly targets the issue's own reproduction hint at lower implementation cost than extending the module-wide baseline machinery to batch-level granularity.
- **Q:** How should finalize's completeness gate account for brief-sanctioned combined commits without looping forever on resume (#660)? **A:** [auto-pick] Self-reported `cards_done` in the implementer's success envelope as the primary completeness signal, plus an idempotent-confirmation short-circuit on `--resume-incomplete` as a backstop. **Why:** replaces a heuristic proxy (commit count) with the actual signal the gate wants, while still closing the specific infinite-loop failure mode as defense-in-depth.
- **Q:** How should `done_gate` get a pre-implementation baseline for self-capturing snapshot suites (#650)? **A:** [auto-pick] New opt-in Prepare-phase pre-flight step, config-gated, mirroring the existing module-wide-verify baseline pre-flight. **Why:** reuses an established working pattern; explicit opt-in avoids forcing an extra done_gate run on tasks whose done_gate isn't self-capturing.
- **Q:** Should the extended-timeout SKILL.md guidance (#639, #624) be generalized or just extended to name `millpy-implement.py` specifically? **A:** [auto-pick] Generalize the rule to any finalize-stage CLI that replays a verify command, while still naming the current concrete instances. **Why:** same edit cost as the narrow fix, but prevents the identical doc gap recurring for a future finalize-stage CLI.
- **Q:** How should the Windows long-path WinError 3 in baseline computation be mitigated (#629), given it can't be reproduced or validated from this Linux dev environment? **A:** [auto-pick] Shorten the transient-worktree directory name only; explicitly reject an unverifiable `\\?\`-extended-length-prefix change to the git invocation. **Why:** a pure string-length change is verifiable cross-platform and has zero regression risk, unlike a git-invocation behavior change that can't be tested here; the existing non-blocking degrade remains the safety net either way.
