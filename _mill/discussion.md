## Problem

This task bundles seven GitHub-issue-sourced defects (#904, #900, #899, #880, #879, #863, #862) that all surfaced while running `mill-merge` / `mill-merge-in` — the skills that sync a task's parent branch and squash-merge a completed task back to its parent. They fall into three clusters: (1) the push-failure/rollback/lock-hygiene path around `mill-merge` Step 5 and Step 8 can race, leak state, or reset the wrong ref; (2) `_parent_branch.check_liveness` misclassifies a live, local-only (never-pushed) parent branch as dead; (3) three independent nested-hub-layout bugs (`hub_root != git_root`) — config-override resolution, verify-replay cwd, and codeguide path resolution — silently diverge or fail depending on which entry point or cwd happens to be in play. None of these are one coherent feature; each is a narrow, independently-fixable correctness bug discovered in production use (mostly on the `NORCE-DrillingAndWells/Models` nested-hub repo and this repo's own dogfooding).

**Why now:** all seven were filed against real runs (2026-08-14 through 2026-08-20) and are open correctness/reliability gaps in a skill every task in this repo depends on (mill-merge/mill-merge-in run at the end of every task).

## Decisions

### push-failure-classification (#904, #862)

- Decision: In `mill-merge/SKILL.md` Step 5's "On push failure" handling, add a third branch after the existing branch-protection-substring check: when the output matches none of the branch-protection substrings AND contains `! [rejected]` together with either `(fetch first)` or `(non-fast-forward)` (git's own literal rejection markers for a plain non-fast-forward push), run `git -C <parent-path> fetch origin <parent_branch>` + `git -C <parent-path> rebase origin/<parent_branch>` to replay the local squash commit, then retry `git -C <parent-path> push` once. On a real conflict during the rebase, abort the rebase (`git -C <parent-path> rebase --abort`) and fall through to the existing Step 1–5 rollback with a message naming the conflicting files. On a second push failure after a clean rebase, also fall through to rollback. Any push failure matching neither the branch-protection substrings nor this rejection-marker pair (e.g. auth or network failures) falls through to the existing Step 1–5 rollback unchanged — this new branch is not an unconditional fallback.
- Rationale: the existing pre-squash `merge --ff-only` guard (already in code, commit `6474a96a`) narrows the race window but cannot close it — `origin/<parent_branch>` can still advance between the ff-only check and the final push (squash+commit happen in between). #904 reproduced exactly this. #862 independently asked for the identical fetch+rebase+retry fix for the same Step 5 push-failure path. User's standing guidance (prior feedback on git races): fix races via rebase+retry, don't halt-and-ask.
- Rejected: leaving the ff-only pre-check as the sole mitigation (does not close the race); a second ff-only re-check immediately before push with no retry (still fails the push and rolls back on legitimate remote advancement, wasting the local squash work for no reason since the fix is trivial).
- Note — already fixed, no action needed: #862's *rollback-target* complaint (`git -C <parent-path> reset --hard mill-checkpoint-<name>` resetting the parent to an unrelated child-branch SHA) was already fixed by commit `6474a96a` (2026-08-13) — the `## Rollback (Steps 1-5 only)` section now resets to `origin/<parent_branch>`, with an explanatory "Why" paragraph already in place. Verify this is still true and, if so, do not re-touch that section beyond what the new rebase-retry branch needs.

### merge-lock-early-release (#863)

- Decision: Keep Step 8's literal heading number unchanged (`### 8. Release merge lock` stays where it is in the document) — do not renumber the Steps section. Change only the *documented execution order*: state explicitly, in the "Teardown sequence" intro paragraph and again at the end of Step 5's direct-squash success path, that Step 8 executes immediately after Step 5's squash+push succeeds (including after the new rebase-retry path above resolves), before Steps 5.5 (cache-helper preflight), 6 (archive tag), 7 (Home.md flip) run. Update the "Failure handling after the squash landed on parent" note (currently under Step 7) to no longer say "release all locks" since the lock is already released by that point. The `merged` PR-state route's existing step list ("run Step 4 ..., then Step 5.5 ..., then Step 6 ..., Step 7 ..., Step 8 (release lock -- no-op if never acquired), Step 9") needs no change: that route already skips Steps 1/2 (lock acquisition), so Step 8 is already documented there as a no-op, unaffected by moving its *execution point* earlier on the direct-squash path.
- Rationale: the file already tolerates steps executing out of strict textual/numeric order based on routing — the `merged` PR-state route already runs 4, 5.5, 6, 7, 8, 9 while skipping 1/2/3/5 entirely, so documenting Step 8 as running earlier relative to 5.5/6/7 on the direct-squash path is consistent with the file's existing convention of numbered-step identity decoupled from strict execution order. Renumbering the whole Steps section — and every cross-reference to Step 5.5/6/7/8/9 across the Entry, PR-state-gate, and Rollback sections — is unnecessary churn for a purely cosmetic reordering and materially raises the risk of a missed cross-reference.
- Rejected: renumbering the entire Steps section to reflect the new execution order (large, invasive, no functional benefit over stable numbered anchors with an explicit reordering note).
- Rationale: `mill-merge`'s steps are Claude-agent instructions, not code with real try/finally — if the orchestrating session is interrupted (crash, disconnect, context exhaustion) between Step 5's push and Step 8, the lock leaks regardless of how carefully Step 8's own instructions are written. Releasing the lock as soon as the locked resource (the parent worktree) is no longer being touched eliminates the exposure window structurally rather than relying on every downstream step to remember to release it. This matches the actual reported scenario (push had already landed on origin; lock never got released).
- Rejected: keeping release at Step 8 and adding more explicit "release lock" reminders to intermediate steps (still leaves a real gap if the session dies mid-step); a self-heal check at lock-acquisition time that treats a lock as stale immediately when its recorded branch's commit is already on `origin/<parent_branch>` (useful defense-in-depth, but adds parsing complexity for a case the early-release fix already prevents — can be added later if leaks recur).

### dead-parent-liveness-widen (#879)

- Decision: Widen `_parent_branch.check_liveness(branch, git_root)` to return `True` when *either* `git ls-remote --exit-code origin <branch>` succeeds *or* a local branch ref exists (`git rev-parse --verify --quiet refs/heads/<branch>` against `git_root`, exit 0). Keep the function's existing single-bool return type and both call sites (`mill-merge/SKILL.md` Entry Step 4, `mill-merge-in/SKILL.md` Entry step 2) unchanged — they already branch on a single `alive` bool and already handle the "resolve_dead_parent" flow correctly when `alive` is `False`.
- Rationale: the existing docstring warning ("local remote-tracking refs... deliberately not used, because mill-cleanup's remote-branch deletion never prunes them") is about stale `origin/<branch>` *remote-tracking* refs cached locally — a different, unrelated signal from the local branch ref itself (`refs/heads/<branch>`). Checking the local branch ref directly does not reintroduce the staleness problem that warning describes, since `mill-cleanup` deletes the actual local branch (not just its remote-tracking counterpart) when a task is torn down. The issue itself notes the downstream `MERGE_REF` fallback in `mill-merge-in` Steps 1/3 already treats a local-only parent correctly — only the liveness gate disagreed with it.
- Rejected: introducing a three-state classification (`alive-remote` / `alive-local-only` / `dead`) threaded through both skills — no caller currently needs to distinguish those two "alive" cases, and no caller does anything different for them; this would be scope beyond what the bug requires.

### config-local-yaml-caller-alignment (#900)

- Decision: Add a new optional keyword-only parameter `git_root: Path | None = None` to `_review_common.load_config(hub_root, mill_dir, *, git_root=None)`. When `git_root` is provided, pass it (not `mill_dir.parent`) as the delegate `_core_load_config`'s (i.e. `_config.load_config`'s) second positional argument for the merge-order stub-layer resolution. The function's existing stale-`review:`-key peek (`local_path = mill_dir / "config.local.yaml"`, unchanged) continues to always read from `mill_dir` regardless of `git_root` — that peek needs the hub's own file, not a git-root stub, so it is untouched by this change. When `git_root` is omitted (the default), preserve today's exact behavior (`worktree_root = mill_dir.parent`) byte-for-byte for every existing call site. Only `millpy-review-plan.py`'s call site — the one #900 actually reported — is updated to pass `git_root=git_root` explicitly, aligning it with `mill-plan`/`mill-merge`'s convention for exactly the case #900 reported. Confirmed by source read: `_review_common.load_config` has ~9 other call sites (`millpy-abandon.py` x2, `millpy-implement.py` x2, `millpy-merge-in-subagent.py` x2, `millpy-fix.py` x2, `millpy-review-summary.py` x1), all passing the same hub-anchored `mill_dir = project_root / ".millhouse"` pattern this decision does NOT change — none of those were reported by #900 and none are touched by this task; auditing them for nested-layout correctness is a separate, unfiled concern.
  Additionally, in `_config.load_config` (the shared delegate, not the wrapper), after loading the stub layer (layer 3, `worktree_root / ".millhouse" / "config.local.yaml"`), if that stub dict has any top-level key other than `hub_relative_path`, print a `[config] warning: ...` line to stderr naming the file and the unexpected keys — mirroring the existing stale-`review:`-key warning precedent already in this module's style. This warning applies to every caller of `_config.load_config` (including the ~9 unchanged `_review_common.load_config` call sites), since it only inspects the file that already exists at whatever `worktree_root` each caller already resolves — it does not depend on the `git_root` parameter added above.
- Rationale: confirmed via source read that `_config.load_config(hub_root, worktree_root)`'s layer-3 stub path is `worktree_root / ".millhouse" / "config.local.yaml"` — when callers disagree on what `worktree_root` means (hub root vs. git root), they silently read different files for the "local override" layer in a nested-hub layout, where the two only diverge when hub_root != git_root. Confirmed by direct source read: `mill-plan/SKILL.md` Entry step 2 literally calls `_config.load_config(hub_root=worktree_root, worktree_root=git_root)` (its local `worktree_root` variable is bound to the hub value and passed as the function's `hub_root` arg; `git_root` is passed as the function's `worktree_root` arg), and `mill-merge/SKILL.md` Step 1 calls `_config.load_config(_paths.resolve_hub_path(), git_root)` — the same positional pattern. That's 2 confirmed callers using this convention (not "3 of 4" as originally claimed here — `mill-start/SKILL.md` Entry step 2 documents the same `_config.load_config(hub_root: Path, worktree_root: Path) -> dict` signature but its SKILL.md text shows no concrete literal call at that step, only the signature comment, so it is not counted as confirmed either way). `_review_common.py`'s wrapper instead collapses both stub and real layers onto the hub itself for every one of its ~9 call sites, so a git-root stub is invisible to all of them today — but `mill_dir` is also independently used inside the wrapper for the stale-`review:`-key peek (`local_path = mill_dir / "config.local.yaml"`), so blindly reassigning the wrapper's existing second positional argument to mean `git_root` would break that peek (it would read a nonexistent `git_root/config.local.yaml`) and would silently change behavior for the ~8 other call sites never reported by #900. An additive, opt-in `git_root` parameter fixes exactly the reported call site without disturbing `mill_dir`'s existing role or any unaudited caller's behavior.
- Rejected: reassigning the wrapper's existing second positional argument's meaning globally (breaks the stale-key peek and silently changes ~8 unaudited call sites); auditing and fixing all ~9 call sites for nested-layout correctness in this task (out of scope — #900 only reported the `millpy-review-plan.py` divergence); docstring-only clarification with no behavior change (leaves the actual inconsistency live); aligning the one caller without the stub-misuse warning (loses cheap, immediate detection of the exact misuse pattern — a real-key stub file — that surfaced this bug in the first place).

### merge-in-verify-cwd-default (#899)

- Decision: In `mill-merge-in/SKILL.md` Step 4 (Verify)'s cwd-resolution bullet, change "hub_root when cwd is None (the string-form default)" to "git_root when cwd is None (the string-form default)".
- Rationale: confirmed via `_implementer_common._run_verify_gate`'s docstring and its two call sites in `_run_verify_gates` (`plugins/mill/scripts/_implementer_common.py` ~L1043, ~L1072) that mill-go's own live batch-dispatch always passes `git_root=git_root`, and `_run_verify_gate` resolves a plain-string verify command's cwd to `git_root` whenever `git_root` is not `None` (only falling back to `project_root`/hub when `git_root` itself is `None`, which live dispatch never does). So the plain-string `verify:` form's *actual* originally-exercised cwd is git_root, not hub_root, in every real mill-go run. `mill-merge-in`'s replay must match that to avoid exactly the reported symptom (`MSBUILD : error MSB1009: Project file does not exist` when replayed from hub_root against a git_root-relative command).
- Rejected: leaving the hub_root default and requiring plan authors to always use the explicit `{cwd: ..., command: ...}` mapping form for nested-hub plans — this pushes a correctness fix onto plan-authoring discipline instead of fixing the actual default to match live-dispatch behavior, and does nothing for plans already written with the plain-string form.

### codeguide-cwd-pinning (#880)

- Decision: In `mill-merge-in/SKILL.md` Step 5, before invoking the `codeguide-update` skill, run `cd <hub_root>` (`hub_root = _paths.resolve_hub_path()`) via the Bash tool, then invoke the Skill tool exactly as documented (`"$CHK..HEAD"` as its argument), then `cd <worktree>` via the Bash tool immediately after to restore cwd for any subsequent steps.
- Rationale: confirmed via source read of `codeguide/scripts/resolve.py` — `_inline_walk`/`resolve()` only walks from cwd *upward* to the git toplevel (`_walk_levels`); it has no mechanism to find a `_codeguide/` directory that lives in a descendant directory below cwd (i.e., the hub, nested under git_root). Running from git_root in a nested-hub layout can therefore never find a codeguide anchored at hub_root. Also confirmed via source read of `plugins/codeguide/skills/codeguide-update/SKILL.md`: its Step 1 (`resolve.py --json`) and Step 2 (`resolve_scope.py $ARGUMENTS`) both take no cwd/root argument at all — `resolve.py`'s CLI has no `--cwd` flag and `resolve()` defaults to `os.getcwd()` when none is passed — so the only lever available to a caller is the actual ambient shell cwd at invocation time. Since the Bash tool's cwd persists across tool calls within a session (per this harness's documented behavior) and a Skill invocation executes its own Bash calls in that same persisted cwd, an explicit `cd <hub_root>` immediately before the Skill-tool call is both necessary and sufficient: `resolve.py`'s upward walk then starts at hub_root and finds `hub_root/_codeguide/config.yaml` immediately, matching the issue's own confirmed repro ("re-running from the hub root resolves correctly"). `resolve_scope.py`'s git operations are unaffected by cwd being hub_root instead of git_root, since git commands auto-discover the repository toplevel regardless of which subdirectory they run from, and the helper emits absolute paths. This `cd` is intra-worktree (hub_root is a subdirectory of the current worktree, not a different worktree), so it does not conflict with the cross-worktree `cd`-to-parent prohibition. `resolve.py` is a shared, widely-depended-on resolver used by other (flat-layout) call sites; changing its core upward-only walk algorithm risks unintended behavior changes elsewhere, so pinning cwd at the one call site that has this specific nested-hub requirement is the minimal, contained fix — and matches the issue's own second suggested fix.
- Rejected: changing `resolve.py`'s `_inline_walk`/`resolve()` to also search descendant directories under cwd — larger blast radius across every codeguide call site for a fix only one nested-hub call site needs.

## Q&A log

- **Q:** How should Step 5's push failure be classified when it's a plain non-fast-forward rejection (neither branch-protection nor already-up-to-date)? **A:** [auto-pick] Add a third branch: fetch + rebase the parent's local squash commit onto the new `origin/<parent_branch>` tip and retry the push once; fall through to existing rollback on a real conflict or a second failure. **Why:** closes the #904/#862 race instead of narrowing it; matches standing guidance to fix git races via rebase+retry rather than halting.
- **Q:** Where should the merge lock be released to prevent the #863 stale-lock leak? **A:** [auto-pick] Move release to immediately after Step 5's squash+push succeeds, before Steps 5.5/6/7. **Why:** those later steps don't touch the parent worktree; releasing early eliminates the crash/interrupt exposure window structurally, since SKILL.md instructions can't guarantee true try/finally semantics.
- **Q:** How should `check_liveness` stop misclassifying a local-only parent branch as dead (#879)? **A:** [auto-pick] Widen it to return `True` when either the origin ref exists or a local `refs/heads/<branch>` ref exists. **Why:** minimal, doesn't disturb the existing alive/dead-boolean call sites, and doesn't conflict with the function's existing (unrelated) warning about stale remote-tracking refs.
- **Q:** How should the two divergent `_config.load_config` call conventions be reconciled (#900)? **A:** [auto-pick] Align `_review_common.py`'s wrapper to pass `git_root` (matching the 3-of-4-entry-points-already-do-this convention), plus add a stderr warning when a stub file carries unexpected keys. **Why:** fixes the actual divergence, not just its documentation; the warning gives cheap early detection of the exact misuse pattern that surfaced the bug.
- **Q:** What should `mill-merge-in` Step 4's verify cwd default be when a batch's `verify:` field is a plain string (#899)? **A:** [auto-pick] Change the `cwd is None` resolution from `hub_root` to `git_root`. **Why:** confirmed via `_run_verify_gate`/`_run_verify_gates` source that mill-go's own live batch dispatch always resolves the plain-string form to `git_root`, not `hub_root` — merge-in's replay must match what was actually exercised originally.
- **Q:** How should `mill-merge-in` Step 5 find a nested-hub codeguide when running from git_root (#880)? **A:** [auto-pick] Pin the `codeguide-update` invocation's cwd/root explicitly to `hub_root` at the Step 5 call site, rather than modifying `resolve.py`'s shared upward-only walk algorithm. **Why:** minimal, contained blast radius — `resolve.py` is depended on by other flat-layout call sites that shouldn't change behavior.
