## Problem

Two unrelated production bugs, both filed against mill-go by the same reporter, bundled into one task because both are small, self-contained fixes in the same script family (`plugins/mill/scripts/millpy-implement.py` / `_implementer_common.py` / `_verify_baseline.py`) and both were confirmed against real mill-go runs.

**Bug A — baseline-stage timeout / cold-build cost (issues #897, #875, #894).** `millpy-implement.py --stage baseline`'s per-batch substage (`_run_baseline_stage`) replays every batch's `verify:` command (each command run twice, as a flakiness guard) plus the module-wide command (up to three times) against one shared transient checkout of the parent branch. On a task with several slow `verify:` commands (full `dotnet test`/`dotnet build` suites), this has twice exceeded even the SKILL.md-recommended 600000ms (10-minute) Bash-tool timeout, killing the call with zero JSON output and forcing the operator to improvise a `run_in_background` + poll workaround. Root cause of the wasted cost (not just the raw suite runtime): `.venv`/`node_modules`/`vendor` dependency dirs get junctioned into the transient checkout for reuse, but there is no equivalent for `.NET`'s `bin`/`obj` build output — the transient checkout starts stone cold, and because no single build runs up front, the cold-compile cost lands inside the first of several doubled verify commands instead of being paid once, deliberately, before any of them.

**Bug B — finalize dirty-tree false positive (issue #885).** `_implementer_common._in_scope_dirty_stuck` treats any tracked-and-modified file inside `git diff --name-only start_sha` ∩ `git status --porcelain` as an in-scope dirty file, and reports `stuck_type: logic` even when the implementer's actual card work is complete and correctly committed. This misfires when a blocked-then-resumed batch's `_mill/briefs/implement-<batch>-r1.md`/`.out.md` files end up tracked and are then rewritten by the fresh dispatch (confirmed in code: `millpy-implement.py`'s prepare stage hardcodes `round_n=1` — see `millpy-implement.py:865` `"ROUND": "1"` and `millpy-implement.py:901` `emit_prepare(..., 1, ...)` — for every implementer dispatch, so a resumed batch's brief/output filenames always collide with whatever the same batch's round-1 attempt already wrote). The gate exists to catch genuinely-uncommitted implementer content, not to police Builder-owned bookkeeping files, so it should not be scoped to include `_mill/briefs/` at all.

## Scope

**In:**
- `_verify_baseline.py` / `millpy-implement.py`'s `_run_baseline_stage` Case B (shared-checkout) path: add an optional, config-driven build-once step that runs before any verify command executes against the shared checkout.
- New `mill-config.yaml` key: `pipeline.baseline_prepare_cmd` (optional string, per-project; documented in `plugins/mill/templates/mill-config.yaml`).
- `mill-go-base/SKILL.md` "0.5. Baseline pre-flight" (and "0.6. Per-batch baseline recapture") dispatch mechanism: switch from a foreground capped-timeout Bash call to the `millpy-bg.py` background-dispatch + poll pattern already used for discussion-review/code-review dispatch elsewhere in this file.
- `_implementer_common._in_scope_dirty_stuck` (`_implementer_common.py:417`): exclude `_mill/briefs/` paths from the dirty-tree gate's `owned_paths`/`dirt` scope.
- Unit test coverage extending `plugins/mill/unit_tests/test-verify-baseline.py` / `test-millpy-implement.py` (build-once step) and `test-implementer-common.py` (dirty-tree gate exclusion), following each file's existing tempfile+real-git fixture conventions.

**Out:**
- Redesigning implementer round numbering (the hardcoded `round_n=1`) to increment across blocked→resumed attempts. The dirty-tree fix (excluding `_mill/briefs/` from the gate's scope) makes this unnecessary — see `dirty-tree-fix-approach` Decision below.
- Auto-detecting build ecosystem (`*.sln`/`*.csproj` sniffing) to choose a build command automatically — the fix is explicit config, not inference.
- Any change to the doubled-verify-command flakiness guard in `compute_batch_baselines`/`_run_module_wide_verify_algorithm` — issue #894 explicitly states "The doubling itself is a deliberate flakiness guard and is not what this issue asks to change."
- `_run_baseline_stage`'s Case A (module-wide-only, no per-batch computation) standalone path (`_run_module_wide_standalone` / `compute_baseline`) — the cold-build waste this task targets is specifically the *shared-checkout, multiple-commands* case; Case A already only pays the cold-build cost once naturally (subsequent runs in the same transient checkout are incremental).
- Any change to `mill-go`'s per-batch or holistic code-review round loops, or to `millpy-fix.py` — Bug B is scoped to the implementer's own finalize dirty-tree gate only.
- Two other foreground 600000ms-capped Bash calls in `mill-go-base/SKILL.md` that share the identical Bash-tool-timeout risk this task fixes for baseline pre-flight: the finalize-stage verify replay for `millpy-fix.py`/`millpy-implement.py --stage finalize` (SKILL.md line ~374) and "0.55. Done-gate baseline pre-flight"'s `run_preflight` `done_gate` command (SKILL.md line ~526). Both are deliberately left untouched here — converting them to the same background+poll pattern is a same-shape follow-up, not bundled into this task, since neither was named in the sourcing issues (#897/#875/#894/#885) and each has its own call-site details (e.g. `--stage finalize`'s envelope/notification contract) worth scoping independently rather than folding in unreviewed.

## Decisions

### baseline-prepare-cmd-config

- Decision: add a new optional `pipeline.baseline_prepare_cmd` key to the consuming project's own `mill-config.yaml` (not millhouse's own hub config — the affected repos are external projects using mill, e.g. a .NET solution). When set (non-null, non-empty string), `_run_baseline_stage`'s Case B path runs it once per distinct cwd fragment (mirroring the existing per-fragment `_link_dependency_dirs` loop) against the shared transient checkout, immediately after dependency-dir linking and before any module-wide or per-batch verify command executes.
- Rationale: mirrors the existing `_DEPENDENCY_DIR_CANDIDATES` philosophy — an explicit, listed mechanism rather than ecosystem sniffing — and generalizes beyond `.NET` (any ecosystem whose verify commands pay a cold-build tax up front can opt in). Config lives per-consuming-project because build commands vary (`dotnet build`, `dotnet build -c Release`, a custom prepare script, etc.) and this repo (millhouse) is not itself the repo paying this cost.
- Rejected: auto-detecting `.NET` via `*.sln`/`*.csproj` presence and hardcoding `dotnet build` — fragile (doesn't generalize, guesses configuration/target framework), and diverges from the explicit-list convention already established for dependency dirs.

### baseline-prepare-cmd-failure-handling

- Decision: a `baseline_prepare_cmd` failure (non-zero exit) is non-fatal — log the failure to stderr (ASCII-only, matching this repo's `print()`/`_log()` convention) and proceed to run the verify commands anyway.
- Rationale: preserves the existing fail-safe direction of the whole baseline mechanism (a computation failure leaves the field unset -> next `_run_verify_gates` call runs the gate strictly, never silently disabling it). A real build break will also surface naturally as a verify-command failure signature, which is correct baseline data, not something to suppress by aborting early.
- Rejected: treating a prepare-cmd failure as fatal to the whole shared-checkout computation (mark every batch needing computation as errored) — over-broad; the existing per-batch/module-wide try/except structure already isolates failures at the right granularity, and a prepare-cmd failure doesn't mean the verify commands themselves can't still run (some may still pass against stale-but-present build output, some may fail — both are legitimate signal).

### baseline-prepare-cmd-scope

- Decision: the build-once step applies only to `_run_baseline_stage`'s Case B (shared-checkout, at least one batch needs computation) path — not Case A's standalone `compute_baseline`/`_run_module_wide_standalone` path.
- Rationale: Case A only runs the module-wide command against its own single transient checkout; the cold-build cost is paid once on the first of up to three runs regardless (subsequent runs against the same checkout are incremental), so there is no doubled/multiplied cost to eliminate there. The waste #894 identifies is specific to Case B's N-commands-times-2(-or-3)-doubled pattern sharing one checkout.
- Rejected: applying the prepare-cmd step universally (both cases) for symmetry — adds a config-driven subprocess call to a path where it has no measurable benefit, and complicates `_run_module_wide_standalone`'s signature/behavior for no reason.

### baseline-dispatch-background

- Decision: switch "0.5. Baseline pre-flight" and "0.6. Per-batch baseline recapture (self-hosting only)" in `mill-go-base/SKILL.md` from a foreground Bash-tool call (currently documented with a 600000ms/10-minute timeout) to the `millpy-bg.py` background-dispatch-and-poll pattern: `millpy-bg.py --slug baseline-preflight -- "$MILL_PYTHON" millpy-implement.py --stage baseline`, then poll `cat <log-path>` for `[mill-bg] EXIT` (with the same liveness-check-via-`_bg.check_bg_status` branch already used for discussion review: `"running"` -> keep polling, `"exit"` -> proceed, `"dead"` -> surface a clear message and halt), then `grep '^{' <log-path>` to extract the two JSON summary lines.
- Precedent (corrected): `millpy-bg.py` does NOT appear anywhere in `mill-go-base/SKILL.md` today — grep-confirmed zero occurrences. `mill-go-base/SKILL.md`'s own "### 3. Code Review loop" dispatches reviewers through the "## Agent-mode dispatch" Task-tool/subagent-notification pattern instead (no log-polling, per that file's own "Agent-mode properties" text). The pattern this decision borrows from exists in two places, not `mill-go-base/SKILL.md`: `mill-start/SKILL.md`'s "Subprocess/psmux branch" for discussion-review (its fallback path when dispatch mode is not `agent`), and more extensively `mill-plan/SKILL.md`, which uses the identical `millpy-bg.py --slug ... -- ...` / poll `[mill-bg] EXIT` / `grep '^{' <log-path>` pattern at multiple call sites (plan-review dispatch, the plan-validator-fix re-run) — including a `pwd`/cwd-guard step ("Before invoking `millpy-bg`: verify `pwd` in the Bash terminal matches the task worktree...") at every one of those call sites. That cwd guard must be replicated for the baseline pre-flight dispatch too — `millpy-bg` itself rejects a non-task-worktree cwd with a parent-worktree error, so omitting the guard just means the operator hits that raw rejection instead of the SKILL.md text pre-empting it with a clear instruction.
- Rationale: `--stage baseline` is a plain, synchronous Python CLI computation, not an LLM subagent — the Agent-mode Task-tool dispatch pattern exists to spawn and track a background *Claude subagent* (via `agentId` + `<task-notification>`), which is the wrong tool for backgrounding a deterministic subprocess call. `millpy-bg.py` is purpose-built for exactly this: backgrounding an arbitrary shell command and polling its log file for completion, which is precisely what `mill-start/SKILL.md` already does for discussion-review's own CLI dispatch (`millpy-review-discussion.py`) in its subprocess/psmux branch. Reusing that same mechanism removes the Bash-tool timeout ceiling categorically instead of raising a number that a large-enough plan can still exceed, and matches what issue #875's reporter had to improvise by hand.
- Rejected: raising the documented timeout number (e.g. to 20 minutes) — cheaper edit, but does not fix the underlying problem for a plan with enough slow batches, and issue #897's own numbers show even 10 minutes with real suites was insufficient. Also rejected: leaving the foreground call in place and just documenting `run_in_background` as a manual fallback in prose — reintroduces exactly the operator-improvisation risk issue #875 reports, since the SKILL.md text is easy to skip under time pressure and the background+poll pattern is already mechanically available. Also rejected: routing `--stage baseline` through the Agent-mode Task-tool dispatch pattern used for code review — that pattern's `agentId`/`<task-notification>` machinery is designed around spawning a Claude subagent to do LLM work, not around backgrounding a deterministic CLI call; forcing a non-LLM computation through it would be a structural mismatch with no benefit over `millpy-bg.py`.

### dirty-tree-fix-approach

- Decision: `_in_scope_dirty_stuck` (`_implementer_common.py:417`) excludes any path under `_mill/briefs/` from both `owned_paths` (the `git diff --name-only start_sha` set) and the final `dirt` intersection with `git status --porcelain`, before deciding whether to return a stuck/logic dict.
- Rationale: the gate's purpose is to catch implementer content the agent forgot to commit — `_mill/briefs/*.md` (rendered prompt) and `*.out.md` (captured transcript) are Builder-owned orchestration bookkeeping that the Builder already stages and commits itself at well-established points (batch-approve, holistic-approve, handoff — see `mill-go-base/SKILL.md`'s and `holistic-review.md`'s existing `git -C <worktree> add <status_path> ... _mill/briefs/` commit lines). Excluding them from this gate is correct regardless of the exact mechanism that leaves them dirty at finalize time (a resumed-after-blocked batch reusing the same round-1 filenames is the confirmed reproduction, but the fix does not depend on that mechanism — any future scenario that dirties a brief/output file without dirtying implementer source content is handled the same way).
- Rejected: incrementing the implementer's hardcoded `round_n` (`millpy-implement.py:865`,`:901`) across blocked→resumed attempts so brief filenames never collide — a materially bigger change (round is currently a bare literal `1` for every implementer prepare call, with no per-batch attempt counter in `status.md` to build on; the `ROUND` template token and brief-naming convention are read by `resume.md`'s crash-recovery matching too, so incrementing it needs to stay consistent everywhere that convention is assumed). It also treats the symptom (filename collision) rather than the design flaw (the gate scoping in files it was never meant to police), so it would need re-solving again for any other Builder-owned file that could someday land in the diff range.

## Technical context

- `_run_baseline_stage` (`plugins/mill/scripts/millpy-implement.py:216-452`): Case A (nothing per-batch needs computing) at line ~307 calls `_run_module_wide_standalone` and returns — untouched by this task. Case B (at least one batch needs computing) at line ~324 onward: resolves `parent_branch` once, computes `cwd_fragments` (line ~349, at most two: `None`/`git_root`-form and the hub-relative fragment), then does the one-time shared setup (line ~357-389): `_verify_baseline._checkout_parent_branch` followed by a loop calling `_verify_baseline._link_dependency_dirs(project_root, target)` per fragment. **This is the insertion point** for the new build-once step — immediately after the `_link_dependency_dirs` loop, before the `try` block at line ~391 that runs the module-wide command and every batch's command.
- `_verify_baseline._DEPENDENCY_DIR_CANDIDATES` (`_verify_baseline.py:64`) is the existing fixed-list convention to mirror in spirit (explicit, not inferred) — the new `baseline_prepare_cmd` is a single optional string, not a list, since it's one build command per project rather than a set of directories to probe.
- Config loading: `millpy-implement.py` already loads `cfg` via `_review_common.load_config(project_root, mill_dir)` near the top of `main()` (~line 523) — `_run_baseline_stage` currently does not receive `cfg` as a parameter; it will need `baseline_prepare_cmd = (cfg.get("pipeline") or {}).get("baseline_prepare_cmd")` threaded in from the `--stage baseline` call site (~line 645) alongside the existing `module_wide_verify_cmd`/`module_wide_cwd_override`/`plan_base` arguments.
- `millpy-bg.py`'s existing dispatch pattern — used today in `mill-start/SKILL.md`'s "Phase: Discussion Review" step 2 subprocess/psmux branch (wrapping `millpy-review-discussion.py`) and, more extensively, throughout `mill-plan/SKILL.md` (plan-review dispatch, plan-validator-fix re-run) — NOT anything in `mill-go-base/SKILL.md`, which has zero `millpy-bg` occurrences and dispatches code review through the separate Agent-mode Task-tool pattern instead — is the pattern to copy: `millpy-bg.py --slug <slug> -- <command>` returns immediately with `pid=<N> log=<abs-path>`; poll `cat <log-path>` for `[mill-bg] EXIT`, with a parallel liveness check via `_bg.check_bg_status(Path('<log-path>'))` branching `"running"`/`"exit"`/`"dead"`. `--stage baseline` already prints its two JSON summary lines to stdout, which `millpy-bg.py` captures into the log file the same way discussion-review's CLI output is captured today — no output-shape change needed on the `--stage baseline` side. Every `mill-plan/SKILL.md` call site pairs the `millpy-bg` invocation with a `pwd`/cwd-guard step ("Before invoking `millpy-bg`: verify `pwd` in the Bash terminal matches the task worktree...") — this guard must be copied into the baseline pre-flight edit too, not just the invocation-and-poll mechanics.
- `_in_scope_dirty_stuck` (`_implementer_common.py:417-478`): `owned_paths` is built from `git diff --name-only start_sha` (line ~463); `dirt` is `git status --porcelain` lines whose path (`line[3:]`) is in `owned_paths` (line ~465). The exclusion belongs in this filter — either drop `_mill/briefs/`-prefixed entries from `owned_paths` before building `dirt`, or filter them out of `dirt` directly; either is equivalent here since `dirt` is the only thing consumed downstream.
- Confirmed root cause detail (not required for the fix itself, kept for context): `millpy-implement.py:865` (`"ROUND": "1"`) and `:901` (`emit_prepare(..., 1, ...)`) hardcode round 1 for every implementer `--stage prepare` call — there is no per-batch attempt/round counter in `_status.py`'s batch schema (confirmed via `_status.py` grep) to build on if a future task decides to revisit the round-increment alternative.
- Existing test fixtures to extend: `plugins/mill/unit_tests/test-implementer-common.py` around its "Case 57" fixture (~line 3316 onward) already builds a tempdir git repo, a task branch, a dirty in-scope tracked file, and calls `_forward_output` with `task_dir`/`start_sha` — the new test should reuse this fixture shape but dirty a `_mill/briefs/implement-<batch>-r1.md` file instead (or in addition) and assert the gate does NOT fire, while a companion case keeps a dirty non-briefs in-scope file to prove the exclusion is scoped correctly (not a blanket disable of the gate).
- `plugins/mill/unit_tests/test-verify-baseline.py` is the home for `_run_baseline_stage`/`compute_batch_baselines`-level coverage of the new build-once step — assert it is invoked exactly once per distinct `cwd_fragments` entry, before any verify command's subprocess call (order can be asserted via a shared call-order list in a mocked/faked `_subprocess_util.run` or `_run_verify_in`, following whatever mocking convention that file already uses for `compute_baseline`/`compute_batch_baselines` tests).
