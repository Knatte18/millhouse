## Problem

Five independent reliability gaps have surfaced in mill's Agent-mode orchestration (`dispatch: agent` — background subagents dispatched via the `Agent` tool instead of `psmux`/subprocess) and in the review/fix/verify pipeline shared by both dispatch modes. All five were observed in real task runs (not hypothetical) and are consolidated here from closed issues #587, #595, #590, #592, #593.

Two of the five (#587, #595) are live-incident dispatch races: mill-go's Agent-mode "stopped/interrupted" recovery path (`## Agent-mode dispatch` step 4 in `mill-go/SKILL.md`) treats any stopped/killed `<task-notification>` as terminal and immediately re-dispatches a fresh implementer/reviewer/fixer session — but the harness's own notification semantics allow a "stopped" or "killed" notification to be stale: the same background agent can still be alive and later deliver a second, `completed` notification with real commits. Both incidents resulted in two live sessions racing on the same batch, requiring manual `TaskStop` intervention to prevent conflicting commits.

The other three are narrower correctness/consistency bugs discovered while reading the code and templates: `millpy-implement.py`'s finalize stage runs a module-wide verify gate unconditionally on every batch (added deliberately in #541 to catch batch-introduced regressions elsewhere in the module), which also means it blocks a batch on failures that predate the task entirely (#590); the fixer-brief templates' pre-report self-check unconditionally forbids a zero-new-commit `success` report, contradicting the `nits_only` guard `_implementer_common.py` already implements for legitimate no-op nits-only passes (#592); and `mill-receiving-review`'s "load the skill BEFORE reading any review file" rule assumes a discrete, orchestrator-controlled file read, which doesn't exist in mill-start's/mill-plan's Agent-mode discussion/plan review — the reviewer's findings arrive already embedded in the `<task-notification>` payload the orchestrator must read to know the round even completed (#593).

**Why now:** #587/#595 are active double-dispatch risks — every Agent-mode mill-go run is exposed to a race that can silently corrupt a batch with conflicting commits. #590 actively blocks Agent-mode batches (and subprocess-mode ones) on failures the batch never caused. #592 and #593 are process-integrity bugs that produce false `stuck` escalations / inconsistent enforcement, both of which erode trust in the pipeline's automation.

## Decisions

### stopped/interrupted-notification liveness probe (#587, #595)

- Decision: In `## Agent-mode dispatch` step 4, when a `<task-notification>` indicates the background agent was stopped or interrupted (as opposed to a raw API/infrastructure error), do **not** immediately classify it as `stuck_type: transient` and re-dispatch. First call `TaskOutput(task_id: <agentId>, block: false)` (the `agentId` already retained per step 3) as a one-shot, non-blocking liveness probe. If it reports the agent as still running, take no dispatch action this turn — the harness will deliver the agent's own next `<task-notification>` when it actually finishes (matches the observed #595 behavior, where the "killed" agent later delivered a real `completed` notification unprompted). Only when the probe confirms the agent is no longer running (or the probe itself errors because the task_id is already gone) does the existing transient re-dispatch-once path apply, unchanged. Raw API/infrastructure errors (the other branch of step 4) are unaffected — they still classify as transient immediately, since there is no live agent to probe.

  **Implementer scope carve-out:** the probe applies to reviewer and fixer dispatches only, not the implementer. `mill-go/SKILL.md:129`'s existing "Clean mid-work stop (implementer only)" path already routes an implementer's non-error non-JSON notification (which is exactly what a stopped/interrupted implementer notification typically looks like) straight to `--stage finalize` / the `incomplete` recovery machinery (step 6.5) rather than the transient retry path — and that finalize call is itself already the correct "is this actually done or partial" check, making a liveness probe redundant for the implementer specifically. The implementer's stopped/interrupted notification decision tree is therefore: non-error non-JSON (clean mid-work stop) → existing finalize/`incomplete` routing (`:129`, step 6.5), unchanged; raw API/infrastructure error → existing transient retry, unchanged. Only a reviewer or fixer stopped/interrupted notification (which has no finalize-stage equivalent to disambiguate partial-vs-dead) reaches the new liveness probe. Step 3's framing sentence and both "Agent-mode properties" bullets restating "stopped/interrupted → same as raw API error → one-retry transient path" must be reworded alongside step 4 (e.g., "...treat that as a candidate for the one-retry transient path in step 4, after step 4's liveness probe confirms the agent is no longer running") so no part of the SKILL still asserts stopped/interrupted is unconditionally terminal.
- Rationale: Both incidents show the "stopped"/"killed" notification itself can be stale while the underlying background worker keeps running to completion. A liveness probe converts an assumption ("stopped means dead") into a checked fact before taking the risky action (fresh re-dispatch, which risks a second live session on the same batch). `TaskOutput` with `block: false` is the harness-native way to check a background task's current state without blocking (per its own tool description: "Use block=false for non-blocking check of current status") — it does not require prompting the agent (unlike `SendMessage`, which assumes the agent is idle and waiting), so it doesn't perturb an agent that's mid-work.
- Rejected: (a) Treat "killed" as always-terminal and only probe on "stopped" — rejected because #595's incident was specifically a `status: killed` / "stopped by user" notification for an agent that was, in fact, still running; the evidence doesn't support trusting either status label as reliably terminal. (b) Send a warm `SendMessage` resume prompt instead of probing — rejected because it actively interferes with an agent that may already be working correctly toward completion on its own (unnecessary and can race with the agent's own final report); reserve `SendMessage` warm-resume for the already-correct step 6.5 `incomplete` path, where the agent has genuinely stopped and needs to be told to continue. (c) Poll `git log`/`start_sha` for new commits as the liveness signal — rejected as a secondary confirmation only; it can't distinguish "still working, no commit yet" from "dead before committing," whereas `TaskOutput`'s own running/completed state can.
- Bounded wait after a "running" probe: unlike the subprocess/psmux poll-loop's explicit ~3600s max-wait (`mill-go/SKILL.md:161`, which bounds an orchestrator-driven polling loop), the liveness probe in agent-mode is a single one-shot `TaskOutput(block: false)` check, not a loop — when it reports "running," the orchestrator takes no further action and returns control, waiting for the harness's own asynchronous `<task-notification>` delivery (the same wait every other Agent-mode dispatch already relies on per "Agent-mode properties": "No log-polling or liveness check required: the orchestrator waits for the `<task-notification>`"). This wait is unbounded by design, matching the existing accepted contract for every other Agent-mode dispatch in the file (implement, review, fix) — none of which have a max-wait guard today, since the harness, not the orchestrator, owns detecting and reporting a truly-dead background worker. Introducing a bounded re-check specifically for this one probe would be inconsistent with that established contract and is out of scope for this task; a systemic agent-mode watchdog (if ever needed) is a separate concern from the stopped/interrupted race this task fixes.

### baseline-aware module-wide verify gate (#590)

- Decision: `_run_verify_gates` gains a third input — a cached per-task baseline state, `module_verify_baseline: "clean" | "pre-existing-failures" | null` — read from and written to `status.md`. The computation is exposed as a new named CLI stage, `millpy-implement.py --stage baseline`, which resolves `status_path`, reads the cached value, does nothing if already non-`null`, and otherwise runs the computation described below and persists the result — this is the concrete, reusable invocation surface both callers below share (rather than each caller re-implementing the computation inline). Compute it **eagerly, once, before the task's first batch implementer is ever dispatched** — insert a new pre-flight step in `mill-go/SKILL.md` immediately before "1. Implement" fires for the task's first batch, invoking `millpy-implement.py --stage baseline` (idempotent no-op on a resumed/restarted mill-go run, since the stage itself checks for a non-`null` cached value) — rather than lazily on the first module-wide gate call inside finalize. This ordering is the load-bearing correctness requirement: it guarantees the computation runs before any implementer session has touched dependency manifests (`pyproject.toml`/`requirements*`/`package.json`/etc.), so the task worktree's currently-installed dependency state is still guaranteed identical to what the parent branch tip needs. (Triggering lazily inside finalize, by contrast, would run for the first time at batch 1's own finalize — *after* batch 1's implementer has already run and possibly touched a manifest — which is the wrong side of that boundary.) The computation itself: create a transient `git worktree add <tmp-path> <parent_branch_tip_sha>` (never touch the task worktree's own working tree), then reuse the task worktree's already-installed gitignored dependency state by creating filesystem junctions/symlinks into the transient worktree from a fixed candidate list of directory names — `.venv`, `venv`, `node_modules`, `vendor` — probed for existence at the task worktree's top level: junction whichever of these actually exist there, skip the rest. (There is no existing `mill-config.yaml` venv/dependency-dir convention to mirror — confirmed absent from both the hub config and the template schema, and `verify:` itself lives in the plan overview frontmatter, not `mill-config.yaml` — so this fixed probe-list is the mechanism, not a reference to a pre-existing convention. `mill-config.yaml`'s schema is not extended for this.) run `module_wide_verify_cmd` there with cwd set to that transient worktree. A pass records `"clean"` immediately. A failure is NOT trusted on the first occurrence — caching `"pre-existing-failures"` disables #541's regression gate for the rest of the task, which is the unsafe direction (a false `"clean"` merely costs one over-strict gate later; a false `"pre-existing-failures"` silently removes the regression gate entirely), so a first failing run re-runs `module_wide_verify_cmd` once more in the same transient worktree before caching anything: only a second consecutive failure caches `"pre-existing-failures"`; if the re-run passes, treat the first failure as a spurious/transient fluke (flaky test, stale absolute path in a relocated venv, a flaky package registry) and cache `"clean"` instead, falling safe toward #541's stricter behavior. Remove the transient worktree and persist the result to `status.md`. If baseline computation itself raises (missing junction target, verify command not found, or any error distinct from a clean non-zero exit code) treat the result as inconclusive the same way: do NOT cache a baseline verdict, log the error, and fall back to running the module-wide gate strictly for this call (i.e., behave as if the baseline were `"clean"`) — a computation failure must fail safe toward #541's stricter behavior, never silently disable the gate. Before `git worktree remove`, in the same `try`/`finally`, strip the reused-dependency junctions from the transient worktree via `_junction.strip_all_in_worktree(transient_worktree_path, {})` — `junctions_cfg` is vestigial (per its own docstring: "retained for backward compatibility; it is no longer read"), the function scans the transient worktree tree itself and strips any junction/symlink it finds regardless of a declared config, so it auto-detects the `.venv`/`node_modules`/`vendor` junctions just created with no config dict needed — per CLAUDE.md's hard constraint that recursive deletion must strip junctions first: `git worktree remove` (or any recursive delete) on a directory containing an un-stripped junction to the task worktree's real dependency directories would delete those real directories through the junction. Every batch's module-wide gate invocation (starting with batch 1's own finalize, since the baseline is already cached by the time any batch reaches finalize) reads this cached value: if `"pre-existing-failures"`, skip the module-wide gate entirely (treat as passed/no-op, same as `module_wide_verify_cmd is None`) for the remainder of the task; if `"clean"`, run the module-wide gate exactly as today (any failure blocks with `stuck_type: verify`, `"[module-wide verify]"`-prefixed reason). Whenever `mill-merge-in` pulls new parent commits into the task branch, it must recompute the baseline eagerly at its own clean post-sync boundary — immediately after the sync completes and before control returns to any further batch work — by resetting `module_verify_baseline` to `null` and then immediately invoking `millpy-merge-in-subagent.py`'s own call to the same `millpy-implement.py --stage baseline` computation described above (not merely resetting to `null` and leaving recomputation to whichever batch's finalize happens to run next). This mirrors the batch-1 pre-flight rule exactly: the parent's dependency manifests just changed as of the merge-in, and recomputing eagerly at that boundary — rather than lazily inside a later batch's finalize, after that batch's implementer may have already touched manifests again — keeps the baseline computation on the correct side of the "no implementer has touched manifests since this snapshot" invariant established for batch 1. `mill-merge-in/SKILL.md` gains the instruction to call this recompute step after a successful sync; `millpy-merge-in-subagent.py` gains the actual subprocess call to `millpy-implement.py --stage baseline` (reset-then-recompute, not just reset).
- Rationale: #590's real-world case is a task blocked on 2 pre-existing, unrelated failures that predated the task's branch point entirely — the module-wide gate (added by #541 specifically to catch batch-introduced regressions) was never supposed to punish a batch for failures it didn't cause. A one-time binary "was the parent already red" check directly fixes this without weakening #541: when the baseline is clean (the common case), the strict per-batch gate is fully preserved, so a batch that newly breaks something elsewhere in the module still blocks exactly as #541 intended. The check runs once per task (amortized cost), not once per batch, so it doesn't reintroduce the ~5.5-minutes-per-batch latency complaint on top of an already-known-broken baseline.
- Rejected: (a) Remove the module-wide gate entirely from per-batch finalize, reserving it for the terminal Handoff `done_gate` only (#590's literal original ask) — rejected because it reverts #541's purpose: a batch-introduced module-wide regression would go undetected until Handoff, potentially after several more batches have built on top of the broken state, making the eventual failure much harder to bisect. (b) Per-test-name diffing of module-wide verify output before vs. after the batch — rejected as too fragile/complex: parsing failing-test identifiers out of arbitrary verify command output (pytest, `dotnet test`, `go test`, etc.) is command/tool-specific and this gate must stay language-agnostic; a binary pass/fail baseline requires only the exit code. (c) Make the module-wide gate advisory-only (log, never block) — rejected because it silently defeats #541's entire purpose; a real regression would never halt the pipeline. (d) Reinstall dependencies fresh in the transient worktree instead of reusing the task worktree's installed state — rejected as needlessly slow (defeats the "amortized one-time cost" rationale) and just as capable of producing a spurious, unrelated baseline failure (e.g., a flaky package registry) as the junction-reuse approach, without the offsetting speed benefit.

### fixer-brief nits-only carve-out (#592)

- Decision: Add a carve-out to BOTH unconditional zero-commit sentences in each template — the "Pre-report self-check" paragraph's "never report `success` when HEAD equals the baseline" sentence (`fixer-holistic-brief.md:71`, `fixer-batch-brief.md:65`) AND the separate "`commit_sha` MUST be a real new content commit distinct from the housekeeping commit" sentence (`fixer-holistic-brief.md:84`, `fixer-batch-brief.md:78`) — since both currently forbid a zero-commit `success` and both must be carved out together or the second still blocks the same legitimate case. The carve-out: when the fix pass was invoked with `--nits-only` and every finding was legitimately a reviewer-acknowledged no-op (nothing required a code change), the fixer MAY report `success` with zero new commits and no `commit_sha` — matching the `nits_only` guard `_implementer_common.py`'s `_forward_output()`/`finalize_from_output()` already implements (it skips the no-content-commit demotion specifically when `nits_only` is True). The carve-out only applies to the `--nits-only` scope; the ordinary batch/holistic fix path (real `[BLOCKING]`/`[GAP]` findings) is unchanged — a fixer working a real finding list must still produce a new commit before reporting `success`.

  Mechanism for the fixer to know it was invoked with `--nits-only` (the brief text alone can't express a runtime-only condition): `_render.render(template_path, values: dict[str, str])` (`_render.py:56`) only does flat `<TOKEN>` string substitution — it has no conditional/`if`-block grammar, so a boolean token cannot itself include or exclude prose inside the template. Instead, add a `NITS_ONLY_CARVEOUT` string render token to `millpy-fix.py`'s brief-rendering token map (alongside the existing token maps at `millpy-fix.py:319` and `:384`), whose *value* is computed in `millpy-fix.py` from `args.nits_only`: the full carve-out sentence text when `nits_only` is true, or an empty string when false. Restructure both templates' two strict sentences (`fixer-holistic-brief.md:71,84`, `fixer-batch-brief.md:65,78`) so the hardcoded "never report success..." / "MUST be a real new content commit..." prose ends with `<NITS_ONLY_CARVEOUT>` placed directly where the sentence's own terminal punctuation goes (e.g., "...no new commit was made<NITS_ONLY_CARVEOUT>" with no literal period after the token in the template source). The token's *value*, computed in `millpy-fix.py`, carries the entire trailing clause including leading punctuation/conjunction and the terminal period in both cases — `", unless every finding was a legitimate --nits-only no-op requiring no code change."` when `nits_only` is true, or just `"."` when false — so neither branch ever produces a dangling "unless ." or a missing terminal period; the template source itself never hardcodes sentence-ending punctuation after the token. This keys the carve-out off the exact same condition the runtime guard already checks, computed once in Python rather than requiring template-engine conditionals, so brief wording and runtime behavior can never diverge.
- Rationale: The template's unconditional "never report success with zero commits" directly contradicts a guard the CLI-side code already implements and tests for; the fixer has no way to know the code-side exception exists unless the brief tells it, and both zero-commit prohibition sentences must move together or the second re-blocks what the first just unblocked. A dedicated `NITS_ONLY` render token (rather than an inferred condition) keeps the brief's claim exactly synchronized with the runtime guard's actual `nits_only` check — the only thing that determines whether `_implementer_common.py` will actually accept a zero-commit success.
- Rejected: (a) Remove the `nits_only` guard from `_implementer_common.py` instead, keeping the strict template rule — rejected because that guard was added deliberately (see `_implementer_common.py:894-898`) specifically to allow legitimate nits-only zero-commit passes; removing it reintroduces the exact false-`stuck` bug #592 was filed to fix. (b) Key the carve-out off an inferred fixer-visible condition instead ("pushed back on every finding, no code change required") rather than an explicit `NITS_ONLY` token — rejected because a full-scope (non-nits-only) fixer session can also legitimately push back on every `[BLOCKING]`/`[GAP]` finding under `mill-receiving-review`'s legitimate-pushback rules, which would incorrectly grant the zero-commit carve-out to a pass the runtime guard never intended to cover (the guard checks `nits_only`, not "all findings pushed back"); an explicit token avoids this semantic drift entirely.

### reword "before reading" to "before evaluating or acting" (#593)

- Decision: In `mill-receiving-review/SKILL.md`'s frontmatter `description` and its "Core Rule"/opening paragraph, and in `mill-start/SKILL.md` (Phase: Discussion Review step 3, plus the `--auto` mode subsection reference) and `mill-plan/SKILL.md` (Phase: Plan Review step 3), reword "BEFORE reading any review file" / "BEFORE reading the review file" to "before evaluating or acting on findings." Additionally, instruct both `mill-start` and `mill-plan` to load `mill-receiving-review` unconditionally at the very start of their review phase — before round 1's dispatch call — rather than gating the load on the moment of reading a file. This makes the rule structurally satisfiable in both dispatch modes: in subprocess/psmux mode the skill is now loaded even earlier than the literal file read; in Agent-mode, where findings arrive pre-embedded in the `<task-notification>` the orchestrator must read to learn the round's outcome, the skill is already active in context by the time the orchestrator evaluates or acts on those findings, even though it was technically "visible" in the notification text a moment earlier.
- Rationale: #593 is scoped specifically to `mill-start` and `mill-plan`, where the orchestrator itself reads and acts on review findings in the same session (no delegation). `mill-go` is explicitly out of scope for this fix (see Scope/Out) — it already delegates finding-reading to a dispatched fixer/implementer subagent's own brief, so the orchestrator never reads findings text there in any dispatch mode, and the existing "before reading" phrasing at mill-go's fixer-dispatch callsite is accurate as written.
- Rejected: (a) Leave `mill-receiving-review`'s own wording unchanged and only touch mill-start/mill-plan's callsites — rejected because the skill's own frontmatter/opening line is what an operator or a future dispatched agent reads first, and leaving it saying "before reading" while callers say "before evaluating" is an inconsistent, confusing split. (b) Branch the rule text per dispatch mode (subprocess/psmux keep "before reading a file"; agent-mode says "before evaluating") — rejected as unnecessary complexity; "before evaluating or acting on findings" is true and enforceable in both modes without branching.

## Technical context

- `## Agent-mode dispatch` step 3 already retains the background agent's `agentId` in a local Builder variable for the duration of the batch ("Record the `agentId` the Agent tool returns... and retain it for the duration of this batch") — the liveness probe reuses this existing handle; no new state needs to be threaded through.
- `TaskOutput` (deferred tool, loaded via `ToolSearch`) accepts `task_id` (matches the `agentId`), `block` (default `true`), and `timeout` — call with `block: false` for the liveness probe so it returns immediately with current status rather than waiting.
- `_run_verify_gates` (`_implementer_common.py:642-696`) currently sequences `verify_cmd` (batch) then `module_wide_verify_cmd` (module) unconditionally when both are non-`None`; this is the function to extend with the baseline parameter. It's called from all `_forward_output` success-emit paths (`_implementer_common.py:1099,1192,1281` roughly) plus `finalize_from_output` — the baseline lookup/short-circuit should live inside `_run_verify_gates` itself (or a thin wrapper it delegates to) so every call site picks it up automatically, matching the existing "no code path can skip the module-wide check" invariant from #541.
- `module_wide_verify_cmd` is read once in `millpy-implement.py` from the overview frontmatter (`overview_frontmatter.get("verify")`, `millpy-implement.py:266`) and passed down to both the `finalize` stage (line 295) and the `full` stage (line 515) — the baseline lookup needs the same `status_path`/task context available at both call sites.
- `_status.py` already has `set_batch_field`/batch-scoped helpers; the new `module_verify_baseline` field is task-scoped (not per-batch), so it likely wants a new top-level status.md YAML field plus a small `_status` helper pair (get/set/clear) rather than reusing the per-batch field helpers. Mirror the existing pattern used for other task-scoped scalar fields in the status.md YAML block (e.g., `plan:`, `parent:`).
- `mill-merge-in/SKILL.md` (prose instruction to recompute after sync) and `millpy-merge-in-subagent.py` (the actual subprocess call to `millpy-implement.py --stage baseline`) both need the edit — the SKILL.md documents when to call it, the script performs the call — since that's the only event that can change what the parent branch's verify health looks like mid-task.
- `_implementer_common.py:894-898`'s existing `nits_only` guard/comment already documents the exact carve-out semantics the templates need to describe in prose — the template wording should mirror this comment's language rather than inventing new terminology.
- `mill-go/SKILL.md:349,496,672,787` are the four places that already correctly describe the fixer/implementer owning `mill-receiving-review` — read these as the reference pattern for "delegated reading," confirming why mill-go itself needs no wording change for #593.
- Test file naming: `test-agent-mode-dispatch.py` and `test-agent-dispatch.py` are the existing suites most likely to already cover step 4's transient/stuck classification and would need new cases for the liveness-probe branch (probe-says-running vs. probe-says-dead vs. probe-errors); `test-implementer-common.py` already has cases 30/31/32 covering the #541 module-wide gate and is the natural home for the new baseline-aware cases.

## Constraints

## Q&A log

- **Q:** How should mill-go react to a stopped/killed `<task-notification>` before deciding whether to re-dispatch fresh? 1) Probe liveness via `TaskOutput(block: false)` on the retained `agentId` before treating it as terminal; only re-dispatch once the probe confirms the agent is no longer running (Recommended). 2) Treat `killed` as always-terminal (skip probe, re-dispatch immediately) but probe only on `stopped`. 3) Send a warm `SendMessage` resume prompt immediately instead of a passive probe. **A:** [auto-pick] Option 1. **Why:** Both #587 and #595 are real incidents of a `killed`/`stopped by user` notification being stale for an agent that kept running to completion unprompted — trusting either status label as reliably terminal (option 2) contradicts the observed evidence, and actively resuming (option 3) risks interfering with an agent that's already correctly working toward its own completion; `TaskOutput`'s non-blocking status check is the harness-native way to distinguish "still running" from "actually dead" without perturbing the agent.
- **Q:** How should the module-wide verify gate (added by #541 to catch batch-introduced regressions) stop blocking batches on pre-existing, task-unrelated failures? 1) Cache a one-time binary "was the parent branch's own module-wide verify already red" baseline per task; skip the gate for the whole task when the baseline is broken, keep it strict when clean (Recommended). 2) Remove the module-wide gate from per-batch finalize entirely, run it only once at Handoff's `done_gate`. 3) Make the module-wide gate advisory-only (log, never block). **A:** [auto-pick] Option 1. **Why:** Option 2 fully reverts #541's original purpose — a batch-introduced module-wide regression would go undetected until Handoff, after several more batches may have built on the broken state. Option 3 silently defeats #541 the same way. Option 1 is the only choice that fixes #590's actual complaint (don't block on failures the task didn't cause) while fully preserving #541's regression-catching value in the common case (clean baseline).
- **Q:** Should the baseline check diff individual failing-test names (before vs. after) or just compare pass/fail as a whole? 1) Coarse binary pass/fail comparison via exit code only (Recommended). 2) Parse and diff individual failing-test identifiers from verify command output. **A:** [auto-pick] Option 1. **Why:** mill's `verify:` commands are project/language-agnostic (pytest, `dotnet test`, `go test`, etc. — see `mill-config.yaml`'s per-project `verify:` field); per-test-name diffing requires parsing tool-specific output formats, which would make this gate fragile and non-generic. A binary "was the parent already red" signal requires only the process exit code and directly matches the observed real-world case (2 known pre-existing failures made the whole gate red).
- **Q:** Where should the fixer-brief nits-only carve-out be sourced from — new prose, or mirrored from existing code? 1) Mirror the exact semantics already documented in `_implementer_common.py:894-898`'s `nits_only` guard comment (Recommended). 2) Write independent carve-out language without cross-referencing the code comment. **A:** [auto-pick] Option 1. **Why:** The runtime guard is already correct and tested; the template's only job is to stop contradicting it.
