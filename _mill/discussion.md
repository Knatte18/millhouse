## Problem

Two reliability bugs surfaced during real `/mill-go` runs in **agent-dispatch mode** (`llm.claude.dispatch: agent`), both filed as GitHub issues:

- **#574 — implementer stops mid-batch and finalize falsely infers success.** A batch with 3 cards committed only Card 15, then the background implementer agent stopped with `status: completed`. The notification payload was a mid-work narration ("Card 15 committed and pushed. Now Card 16: move cli.go ... via git mv"), not the required `{"status":"success",...}` JSON line. The mill-go "Clean mid-work stop" path wrote `.out.md` and ran `--stage finalize`. Because Cards 16–17 were pure `git mv` moves, the one committed card's `verify:` passed — and finalize's completeness gate (`_batch_completeness_stuck`) is deliberately skipped whenever `verify_cmd` is present ("a passing verify is conclusive evidence of batch completeness"). So finalize emitted **inferred success on a 1/3-done batch.** The human orchestrator improvised a recovery — resume the same warm session via SendMessage to finish Cards 16–17 — which worked but is undocumented and not the happy path. A literal reading of the flow risks either false-success (as above) or a transient-retry-fresh that re-does the already-committed Card 15.

- **#575 — fixer self-reports success with no commit.** During a holistic fix round on the `haiku` fix role, the fixer applied source edits but **left them uncommitted** and returned `{"status":"success","commit_sha":"<X>",...}` where `commit_sha == start_sha` (the prepare-stage HEAD — i.e. no new commit was made). It also skipped a new test that a BLOCKING finding explicitly required. The finalize gate in `_forward_output` correctly caught the no-commit case (`stuck_type: logic`, "success reported but no content commit (HEAD == start_sha)"), so the safety net held — but the fixer **self-reporting success while having made no commit** wastes a fix round and produces a confusing report. The fixer briefs (`fixer-batch-brief.md`, `fixer-holistic-brief.md`) lack the pre-report self-check and the "commit_sha must be a real new commit" guard that the implementer brief already carries.

**Why now:** both bugs were hit in production agent-dispatch runs (2026-06-29) on real downstream repos. Agent-dispatch is the mode being stabilized, and these are the two open reliability gaps blocking confidence in unattended runs.

## Scope

**In:**

- Add a distinct **`stuck_type: incomplete`** classification, emitted by finalize on the **no-JSON inference paths** when the implementer made a partial batch (content-commit count `<` card count), **even when `verify:` passes**. This is the deterministic signal that a clean stop left the batch unfinished.
- Make the existing partial-batch detections emit `incomplete` consistently: `_reclassify_verify_failure`'s "0 < content < card_count" branch and `_batch_completeness_stuck` change their `stuck_type` from `transient` to `incomplete`. The `incomplete` dict carries `commits_made` and `session_id`.
- Run the commit-count completeness check on the **no-JSON inference paths regardless of `verify_cmd`** (a new helper or a `force` flag), because on those paths there is no success claim to trust and a passing verify does not prove completeness (a partial batch of `git mv` moves passes).
- Have `_forward_output` recognize an implementer-emitted `status: incomplete` JSON and normalize it to the stuck `incomplete` envelope (so a best-effort partial-progress report from the agent routes the same way as finalize-detected incompleteness). The normalization MUST compute and attach `commits_made` via `_content_commit_count(project_root, start_sha)` — the implementer's partial-progress JSON carries `cards_done`/`cards_remaining` but not `commits_made`, and subprocess routing keys on `commits_made` (see the `normalized-incomplete-commits-made` decision).
- **mill-go SKILL routing:** document a first-class **warm-session resume** recovery for `stuck_type: incomplete` in agent mode — `SendMessage` the still-warm implementer agent (keyed on the **agent ID the Agent tool returns at dispatch**, see the `warm-resume-mechanism` decision) to finish the remaining cards and emit the JSON report, then re-run finalize on the resumed output. In subprocess/psmux mode (and the agent-mode fallback when the warm agent is gone), `incomplete` does **not** reuse the skip-to-cleanliness branch — it re-dispatches the implementer once via a new **start_sha-preserving resume path** (see the `start-sha-preserving-resume` and `subprocess-incomplete-resume` decisions).
- **New `millpy-implement.py` resume path that preserves `start_sha`.** Today prepare/full unconditionally captures `start_sha = HEAD` (`millpy-implement.py` line 289) and overwrites status.md's `start_sha`/`implementer_session` (line 300); there is no `--resume` flag. Add a resume mode (e.g. `--resume-incomplete`) whose prepare reads the **existing** `start_sha` from status.md instead of capturing HEAD, does NOT overwrite it, re-renders the brief with the resume-after-incomplete directive, and dispatches. This is what lets finalize (which already reads `start_sha` from status.md, line 258) recount content commits against the **original** batch start so a finished batch counts all its cards.
- Update the **implementer brief** with two additions: (a) a best-effort instruction that when forced to stop before the batch is complete, emit `{"status":"incomplete","cards_done":N,"cards_remaining":M,"session_id":"<SESSION_ID>"}` as the partial-progress signal (finalize detection remains authoritative); (b) a **resume-after-incomplete** instruction — when re-dispatched on a batch that already has commits since `start_sha` (i.e. a prior pass committed some cards), first run `git -C <PROJECT_ROOT> log <start_sha>..HEAD --oneline`, identify cards already committed by their `Commit:` message, and implement only the remaining cards (do not re-edit or re-commit completed cards). This mirrors the existing "On review resume" section's resume discipline.
- Update **both fixer briefs** (`fixer-batch-brief.md`, `fixer-holistic-brief.md`) with: (a) a mandatory pre-report self-check that the current HEAD differs from the fix-round housekeeping commit before reporting success; (b) the "`commit_sha` MUST be a real new content commit distinct from the start commit; otherwise report `stuck`" guard mirroring the implementer brief; (c) a line requiring that when a finding mandates a NEW test, the fixer must add it and confirm it runs.
- Unit tests for the new `incomplete` classification and the `status: incomplete` parse normalization.

**Out:**

- **No change to the fixer default model** (`haiku`). #575 suggests haiku "is too weak," but model choice is a separate config decision; the brief fix plus the existing finalize safety net are sufficient. Bumping the default fixer model would raise cost for every fix and is out of scope.
- **No change to the explicit-success-JSON completeness GATE** (`_batch_completeness_stuck` at line ~939 in `_forward_output`). When the implementer emits a real `status: success` JSON and verify passes, trusting that verify stays the design — changing it would falsely flag legitimately-complete combined-commit batches. Only the **no-JSON inference paths** get the verify-ignoring completeness check. (This is separate from the `_reclassify_verify_failure` rename, which fires on verify *failure* and does reach the success path — see `reclassify-rename-all-callers`.)
- **Subprocess/psmux dispatch mechanics change only as required by the `incomplete` route:** a new start_sha-preserving resume path is added to `millpy-implement.py` (see `start-sha-preserving-resume`) and the `incomplete` routing is added to mill-go. No other subprocess/psmux behavior changes. `incomplete` deliberately does **not** fall through to the `commits_made > 0` "skip to cleanliness gate" branch, and the warm-`SendMessage` recovery remains agent-mode-specific.
- No new config keys, no change to `pipeline.autonomous_mode` semantics.
- Not attempting to fully solve "fixer skips a required new test that doesn't exist to fail verify" — the brief line is a mitigation, not a mechanical guarantee (a test that was never written cannot be detected by running verify).

## Decisions

### incomplete-stuck-type

- Decision: Introduce `stuck_type: incomplete` as a first-class classification distinct from `transient`, `verify`, and `logic`. It means: the batch is provably partial (fewer content commits than cards) on a path where no trustworthy success report exists, and the correct recovery is to **finish the remaining work in the existing session**, not retry from scratch and not accept it as done.
- Rationale: `transient` routes to "retry fresh" (which re-does committed cards) or "skip to cleanliness gate" (which accepts a partial batch as complete). Neither matches the actual situation. A dedicated type lets the orchestrator route deterministically to warm-session resume.
- Rejected: Reusing `transient` + `commits_made` (the issue's status quo) — ambiguous routing, conflates network blips with partial batches. Relying only on an implementer-emitted partial JSON (#574 suggestion 3) — unreliable, since the agent stops precisely because it ran out of budget to report.

### completeness-check-on-no-json-path-ignores-verify

- Decision: On the no-JSON inference paths, run the content-commit-vs-card-count check **even when `verify_cmd` is set**, and emit `incomplete` when `count < card_count`. Implement via a dedicated helper (e.g. `_incomplete_batch_stuck`) or a `force=True` flag on `_batch_completeness_stuck` that bypasses the `verify_cmd is not None → return None` short-circuit.
- Rationale: #574 proves a passing verify is **not** conclusive of completeness — a partial batch whose unfinished cards are file moves passes the committed card's tests. The "verify is conclusive" short-circuit is only safe on the explicit-success path where the agent affirmatively claimed completion.
- Rejected: Removing the `verify_cmd` short-circuit everywhere — would falsely flag legitimately-complete batches (combined commits) that emit a proper success JSON. Keep that short-circuit on the explicit-success path.

### reclassify-rename-all-callers

- Decision: `_reclassify_verify_failure`'s `0 < content < card_count` branch is renamed `transient` -> `incomplete` for **all** callers — both the explicit-`status: success` path (`_implementer_common.py` ~line 883) and the three no-JSON inference paths (~lines 1040, 1128, 1212). Do NOT gate the rename to inference-path callers only.
- Rationale: The helper fires only when `verify` has already FAILED. A partial batch (`0 < content < card_count`) that fails verify is `incomplete` regardless of which path detected it — the success-path caller means "agent claimed success but verify failed AND the batch is partial," which is precisely the resume-the-session case. Gating the rename would create two different verdicts for the identical underlying state (partial + verify-failed) depending on whether a success JSON happened to be emitted, which is incoherent.
- Rejected: A `force`/`caller` flag to keep the success-path branch emitting `transient` (splits one concept across two verdicts; complicates the helper for no behavioral benefit). Note this is distinct from the `_batch_completeness_stuck` verify short-circuit, which DOES stay caller-specific (disabled on the explicit-success path, forced on inference paths) — that gate fires on verify *pass*, where the success claim is trustworthy.
- **`commit_sha` attachment:** the four post-reclassify guards `if gate_result.get("stuck_type") in ("verify", "transient"): ... commit_sha` (`_implementer_common.py` lines 888, 1047, 1131, 1215) MUST add `"incomplete"` to the membership tuple — `in ("verify", "transient", "incomplete")`. An `incomplete` envelope needs `commit_sha` (the current HEAD) so the orchestrator and the resumed/`--resume`d session can correlate the partial state; without the rename to the guard tuple, reclassified `incomplete` dicts would silently drop `commit_sha`. The same applies anywhere `incomplete` is emitted by `_batch_completeness_stuck` (it already sets `commits_made`; ensure `commit_sha` is attached by the caller on the same paths that attach it for `transient` today).

### incomplete-carries-commit-sha

- Decision: `stuck_type: incomplete` envelopes carry `commit_sha` (current HEAD), `commits_made`, and `session_id`. Every code path that attaches `commit_sha` for a `transient` result must also attach it for `incomplete` — concretely, the four `in ("verify", "transient")` membership checks following `_reclassify_verify_failure` add `"incomplete"`.
- Rationale: The orchestrator's resume/`--resume` recovery and the Stuck-escalation `commits_made > 0` accounting both benefit from knowing the partial HEAD; dropping `commit_sha` on `incomplete` would be an inconsistent, lossy envelope versus the `transient` it replaces.
- Rejected: Dropping `commit_sha` on `incomplete` (lossy; breaks parity with the `transient` envelope it supersedes).

### false-positive-incomplete-is-safe

- Decision: Accept that the no-JSON `incomplete` detection can false-positive (a genuinely-complete batch that used combined commits AND lost its JSON to truncation will show `count < card_count`). The recovery — resume the warm session asking it to "finish any REMAINING cards, then emit the JSON" — is self-correcting: a complete batch's resumed session confirms completion and emits success in one cheap round.
- Rationale: Correctness dominates cost here. A false `incomplete` costs one short resume round; a false `success` (the #574 bug) ships an unfinished batch. The asymmetry favors over-detecting incompleteness.
- Rejected: Trying to perfectly distinguish truncated-but-complete from genuinely-incomplete from commit/tree state alone — impossible given combined commits are allowed, which is the root of the ambiguity.
- Caveat (recount on resume): the self-correcting property holds ONLY if the resume preserves the original `start_sha`. The completeness recount after a resume MUST measure against the original batch `start_sha`, not a re-captured HEAD — otherwise a finished batch under-counts its cards and re-loops `incomplete`. This is guaranteed by the `start-sha-preserving-resume` decision.

### warm-session-resume-recovery

- Decision: In agent mode, `stuck_type: incomplete` routes to a documented **warm-session resume**: the orchestrator retains the Agent runtime ID returned when it dispatched the implementer, and on `incomplete` issues `SendMessage(to: <agent_id>, "Finish any remaining cards in this batch, run verify, then emit the required JSON report as your final line.")`, captures the resulting notification to `.out.md`, and re-runs `--stage finalize`. The warm-`SendMessage` path is inherently start_sha-safe: it does NOT go through `millpy-implement.py` prepare, so status.md's original `start_sha` is left untouched and the post-resume finalize counts against it correctly. If the agent cannot be resumed (no retained ID, or the resume itself stops without JSON again), fall back to the new **start_sha-preserving resume path** (`--resume-incomplete`, see `start-sha-preserving-resume`) — NOT today's running-state re-fire, which would re-capture `start_sha`. The committed cards are preserved by two mechanisms: (a) those cards are already in HEAD, so their `Edits`/`Creates` are already in their target state; (b) the re-dispatch brief instructs the implementer to first run `git log <start_sha>..HEAD --oneline`, identify cards already committed (by their `Commit:` message), and implement **only the remaining cards**. A truly fresh start with a new `start_sha` (which would re-do committed cards AND cause a false re-incomplete count) is never used for `incomplete`.
- Rationale: This is exactly the recovery the human orchestrator improvised in #574, and it worked. Making it first-class removes the improvisation. Resuming preserves the committed cards (no re-doing Card 15) and drives the session to a definitive JSON report.
- Rejected: Fresh re-dispatch as the primary path (re-does committed cards, risks a second completeness loop). Auto-accepting partial work via the cleanliness gate (ships an unfinished batch).

### warm-resume-mechanism

- Decision: The warm-resume `SendMessage` is a **harness/orchestrator-runtime capability, not a Python function in `plugins/mill/scripts/`.** When mill-go dispatches an implementer via the **Agent tool** in agent mode, the tool returns an **`agentId`** (a runtime handle) along with an explicit instruction to use `SendMessage(to: <agentId>, ...)` to continue that agent with its conversation context intact. mill-go must **capture and retain that `agentId`** when it makes the Agent-tool call (today's `## Agent-mode dispatch` step 3 treats dispatch as fire-and-forget and discards it), and on `stuck_type: incomplete` call `SendMessage(to: <agentId>, ...)`. The mill-go SKILL `## Agent-mode dispatch` section must be amended to (a) record the returned `agentId` at dispatch, (b) define the `incomplete` -> `SendMessage` resume step, and (c) define the fresh-re-dispatch fallback when no `agentId` is retained or the resumed agent again stops without JSON.
- Rationale: A read-only reviewer grepping `scripts/` will not find `SendMessage` (the only in-repo match is an unrelated Win32 call in `_winenv.py`) and may flag the mechanism as nonexistent. It exists, but at the harness layer: the orchestrator running this very task received `agentId: <id>` from its own Agent-tool dispatch with the documented `SendMessage(to: <id>)` continuation contract. The design depends on the SKILL retaining that handle; it is not a codebase API to be written, but a documented orchestrator workflow.
- Rejected: Treating warm-resume as a new Python helper to implement (it is a harness tool, not library code). Relying on the mill-internal `session_id`/`implementer_session` UUID as the resume handle (that is the brief's report-correlation id, NOT the Agent-tool runtime handle; `SendMessage` keys on the `agentId`, not the brief `session_id`).

### subprocess-incomplete-resume

- Decision: In subprocess/psmux dispatch, `stuck_type: incomplete` re-dispatches the implementer **once** via the new start_sha-preserving resume path (`--resume-incomplete`, see `start-sha-preserving-resume`), and only escalates if the resume still yields `incomplete`. It must NOT route into the `commits_made > 0` "skip to cleanliness gate" branch, and it must NOT use today's running-state re-fire (which re-captures `start_sha`). Under `pipeline.autonomous_mode: true` the same one-auto-resume applies; a still-`incomplete` second result blocks the batch (`blocked_reason: "incomplete after resume"`).
- Rationale: The existing `commits_made > 0` autonomous auto-pick is "skip to cleanliness gate ... as if the implementer had reported success" (mill-go SKILL ~line 411-412). For a provably-partial batch that auto-accepts unfinished work — the exact #574 false-success `incomplete` was introduced to prevent. `incomplete` must finish the work (resume), not accept it. The resume must preserve `start_sha` or the completeness recount loops (see `start-sha-preserving-resume`).
- Rejected: Reusing the `commits_made > 0` handling verbatim (auto-ships partial batches in autonomous mode). Reusing today's running-state re-fire (re-captures `start_sha`, causing a false re-incomplete loop). Blocking immediately without a resume attempt (wastes the recoverable partial state).

### start-sha-preserving-resume

- Decision: Add a resume path to `millpy-implement.py` (e.g. a `--resume-incomplete` flag or a dedicated `--stage resume-prepare`) that preserves the **original** `start_sha`. Today the prepare/full path always runs `start_sha = git rev-parse HEAD` (line 289) and `_status.set_batch_fields(..., {"start_sha": start_sha, "implementer_session": ...})` (line 300), overwriting status.md. The resume path instead **reads** `start_sha` from the batch's status.md entry, does NOT capture HEAD, does NOT overwrite `start_sha`, re-renders the brief with the resume-after-incomplete directive (passing the original `start_sha` so the implementer can `git log <start_sha>..HEAD`), and dispatches. `implementer_session` may be refreshed (the fallback is a new agent/session); only `start_sha` must be preserved.
- Rationale: finalize already reads `start_sha` from status.md (line 258), so completeness counting is correct **iff** the resume did not overwrite `start_sha`. Re-capturing HEAD (which now contains the already-committed cards) makes `_content_commit_count` see only the newly-added cards, so a genuinely-complete 3-card batch counts 2 < 3 and re-emits `incomplete` forever (or blocks as "incomplete after resume"). Preserving the original `start_sha` is the load-bearing requirement that makes both the recount and the "skip committed cards" logic correct.
- Scope reconciliation: this IS a change to subprocess/psmux dispatch mechanics — it is moved from "Out" into "In" as a necessary part of the `incomplete` route. The agent-mode warm-`SendMessage` path needs no such change (it bypasses prepare); only the fallback re-dispatch and the subprocess/psmux route use it.
- Rejected: Threading the original `start_sha` via the (currently ignored) `--start-sha` arg without a resume path (prepare still overwrites status.md). Reusing today's running-state re-fire (re-captures `start_sha`). Counting completeness against a re-captured `start_sha` (the false re-incomplete loop).

### normalized-incomplete-commits-made

- Decision: When `_forward_output` parses an implementer-emitted `{"status":"incomplete", "cards_done":N, "cards_remaining":M, ...}`, it normalizes to the stuck envelope `{"status":"stuck","stuck_type":"incomplete","commits_made":<count>,"session_id":<id>, ...}`, computing `commits_made` via `_content_commit_count(project_root, start_sha)`. The implementer's partial-progress JSON does not carry `commits_made`.
- Rationale: Subprocess routing and the Stuck-escalation `commits_made` logic key on that field; a normalized envelope missing it would mis-route. Computing it from git is authoritative and matches how finalize-detected `incomplete` already populates it.
- Rejected: Trusting `cards_done` as a commits proxy (cards != commits; combined commits exist). Omitting `commits_made` (breaks subprocess routing parity).

### fixer-brief-commit-guard

- Decision: Add to both fixer briefs a mandatory pre-report self-check — confirm `git -C <PROJECT_ROOT> rev-parse HEAD` differs from the fix-round housekeeping commit (whose message starts with `mill-go: fixing` or `mill-go: holistic fix`) before reporting success — plus the implementer brief's "`commit_sha` MUST be a real new content commit; otherwise report `stuck`" guard, and a requirement that a finding mandating a NEW test be satisfied by actually adding and running that test.
- Rationale: The implementer brief already carries this guard and the implementer side does not exhibit #575. Porting the same discipline to the fixer briefs prevents the false-success self-report at the source, upstream of the finalize safety net that currently has to catch it.
- Rejected: Relying solely on the finalize gate (works, but wastes a round and confuses the report). Bumping the fixer model off haiku (separate cost decision; out of scope).

## Constraints

- `stuck_type: incomplete` is **mostly additive** — the `transient` emitters that stay unchanged are the API-error/network markers and the LLM-layer synthetic-stuck path; the `verify`, `logic`, and `infrastructure` routings are unchanged. The **two partial-batch detections are intentionally reclassified** from `transient` to `incomplete`: `_batch_completeness_stuck` (`content < card_count`) and `_reclassify_verify_failure`'s `0 < content < card_count` branch. The existing tests that assert the old `transient` verdict for these two (e.g. `test-implementer-common.py` case 27a, "fewer commits than cards -> stuck/transient") **MUST be updated to assert `incomplete`** — this is an expected, in-scope test change, not a regression. No other `transient`-emitting test may change verdict.
- The explicit-`status: success` finalize path is unchanged **when verify passes**: its completeness gate stays disabled while `verify_cmd` is set (verify is conclusive of completeness only when the agent affirmatively claimed success), so legitimate combined-commit batches are never falsely flagged. The **one** behavioral change reaching the explicit-success path is via the shared `_reclassify_verify_failure` helper (invoked at `_implementer_common.py` ~line 883 on the `status == "success"` path): when verify FAILS on a partial batch (`0 < content < card_count`) its emitted type becomes `incomplete` instead of `transient`. This rename applies to **all callers** of the helper (the success path and the three inference paths) — see the `reclassify-rename-all-callers` decision — because a success-claim on a partial batch that also fails verify is exactly an `incomplete` situation. The no-JSON inference paths additionally gain the verify-ignoring completeness check.
- Reason strings ASCII-only.
