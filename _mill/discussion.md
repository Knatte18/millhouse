## Problem

Five independent, single-item bugs surfaced as GitHub feedback issues (#834, #833, #825, #818, #812) across four separate mill subsystems: worktree bootstrap, hub-path resolution, per-batch finalize, cleanliness drift detection, and discussion-review. Each is small in isolation, but two of them (#833, #834) share one root cause and are fixed together here; the other three are unrelated and fixed independently. None of these are feature requests — each is a correctness gap discovered live during real mill-go/mill-plan/mill-start sessions, where the failure mode was either a silent wrong-answer (worktree resolution, drift detection) or a false positive that blocked otherwise-correct work (finalize, discussion-review).

## Scope

**In:**
- `_paths.resolve_hub_path()` terminal-fallback fix (#833): when the cwd-walk and main-worktree-stub checks both fail to redirect, return the current `git_root` instead of `main_root`.
- `millpy-spawn.py` defensive `config.local.yaml` write (#834): after `copy_millhouse`, unconditionally verify the destination has `.millhouse/config.local.yaml`; self-heal if missing, covering both the `hub_relative_path == "."` case (currently never covered by the existing gated stub-write) and any `copy_millhouse` miss for the `!= "."` case.
- `_implementer_common._in_scope_dirty_stuck` batch-scoping fix (#825): scope the per-batch finalize dirty check's owned-paths set to `git diff --name-only <start_sha>` (working-tree diff, catches uncommitted dirt too) instead of the whole task's parent-diff/task_dir-blanket scope (`compute_terminal_dirt`'s current, unchanged scope), so a prior approved batch's post-commit file drift no longer false-blocks the current batch.
- `_cleanliness._parent_diff_names` unresolvable-diff signal (#818): return `None` (distinct from `[]`) when `git diff --name-only <parent>...HEAD` fails, and propagate that distinction through `compute_terminal_dirt` and `revert_out_of_scope_drift`'s return shapes, PLUS update both production consumers of the binary branch — `plugins/mill/skills/mill-go-base/handoff.md`'s Terminal cleanliness gate and `SKILL.md` step 2b — to add an explicit `is None` branch that escalates to stuck/blocked instead of silently reporting "no drift."
- `plugins/mill/templates/review-discussion.md` criterion addition (#812): an explicit Criteria bullet instructing the discussion reviewer to cross-check testing-plan claims about tooling/validator/prefix requirements (e.g. `PYTHONPATH=`) against CLAUDE.md and `_plan_validate.py`'s actual enforcement, flagging contradictions as `[BLOCKING:consistency]`.
- Unit test coverage for all five fixes in their existing test files (`test-paths.py`, `test-millpy-spawn.py`, `test-implementer-common.py`, `test-cleanliness.py`, `test-review-discussion-flow.py`).

**Out:**
- Forensic investigation into what process rewrites an already-committed `.out.md` post-commit (#825's underlying mystery) — the batch-scoping fix makes finalize robust regardless of cause; the cause itself is a separate, currently-unreproduced concern.
- Retroactively fixing any other discussion.md/plan file that may carry the same false `PYTHONPATH=` claim (#812) — no evidence any currently-active branch repeats it; the fix here is prospective (future discussion-review rounds catch it).
- Changing `_plan_validate.py`'s `_check_verify_not_isolated` validator logic itself — it is correct and matches CLAUDE.md's documented rule; #812's bug is in review coverage, not validator behavior.
- Any change to `_paths.py`'s cwd-walk or M2+sub-repo nested-hub logic beyond the single terminal-fallback line (#833) — those paths are unaffected and already handle their documented cases correctly.
- Escalation/severity redesign for the cleanliness gate beyond adding the "unknown" state (#818) — "unknown" is treated with the same blocking severity the gate already applies to genuine dirt; no new gate-strength taxonomy.

## Decisions

### hub-path-terminal-fallback (#833)

- Decision: In `_paths.resolve_hub_path()` (`plugins/mill/scripts/_paths.py:169-228`), change the terminal fallback at line 228 from `return main_root` to `return git_root` (the resolved git root passed in or of the current worktree).
- Rationale: When cwd is the main worktree itself, `git_root == main_root` already, so this is a no-op there — no regression. When cwd is a task worktree whose own `.millhouse/config.local.yaml` is missing (the exact scenario in #833), the walk starting at `actual_cwd` breaks immediately because `check == git_root_resolved` on the first iteration (a task worktree's `git_root` is its own root, not reachable-upward from the container's hub), so the only remaining signal is the main-worktree stub check at line 218-226 — which only redirects when that stub's `hub_relative_path != "."`. For this repo's own layout (`hub_relative_path: .`), that check never redirects, and the function silently returns the wrong worktree. Returning `git_root` instead makes `resolve_hub_path()` degrade to "the worktree I'm actually standing in," which is what every downstream caller (branch detection, `find_active_slug`) actually wants when no more specific hub info is discoverable.
- Rejected: (a) raising a hard error instead — would require passing `--slug` explicitly at every call site broken by this, disproportionate for what is a one-line fix; (b) leaving this alone and relying solely on the #834 spawn-write fix — leaves the fallback landmine live for any other future cause of a missing local config (hand-created worktrees, corrupted files, etc.).

### spawn-config-local-yaml-defensive-write (#834)

- Decision: In `millpy-spawn.py`, immediately after the `copy_millhouse` call (currently ending around line 216), add an unconditional check: if `dest_hub / ".millhouse" / "config.local.yaml"` does not exist, write it directly with `{"hub_relative_path": hub_subpath}` (the same `hub_subpath` value already computed at line 98, and the same content shape the existing gated block at lines 263-269 writes). This runs regardless of the `hub_subpath != "."` gate that the existing stub-write block is scoped to.
- Rationale: The existing stub-write block (line 263) only fires when `hub_subpath != "."`, so for this repo's own container-form layout (`hub_subpath == "."`), the destination's `config.local.yaml` depends entirely on `copy_millhouse` successfully copying it from the hub's own `.millhouse/config.local.yaml` — with no fallback if that copy doesn't happen (root cause of the underlying miss in #834's reported worktree is unconfirmed; `copy_millhouse` itself has no swallowed exceptions, so the precise mechanism wasn't pinned down from static reading alone). Adding an unconditional existence-check-and-self-heal closes the gap regardless of the exact historical cause, and is idempotent (a no-op whenever the file is already present, which is the overwhelmingly common case).
- Rejected: (a) only fixing the `hub_subpath == "."` case and leaving the `!= "."` block as-is — leaves no defense-in-depth for a `copy_millhouse` miss in the nested-hub case; (b) moving the write before `copy_millhouse` — `copy_millhouse`'s documented overwrite semantics ("Existing files in dst are overwritten") mean write-then-copy risks the hub's own (possibly stale or worktree-inappropriate) file silently clobbering a freshly-written correct one; write-after-copy-if-missing is simpler and matches intent (only step in when copy didn't produce the file).

### finalize-batch-scoped-dirty-check (#825)

- Decision: In `_implementer_common._in_scope_dirty_stuck` (`plugins/mill/scripts/_implementer_common.py:416-464`), replace the call to `_cleanliness.compute_terminal_dirt(project_root, task_dir, parent_branch)` (which scopes to the whole task's `task_dir` ∪ full parent-diff-owned paths) with a batch-scoped equivalent. The function's signature gains a new `start_sha: str | None` parameter, threaded in from the call site (`_implementer_common.py:1758`, where `start_sha` is already in scope and used by `_is_only_start_batch_commit`/`_batch_completeness_stuck`). The owned-paths set for the per-batch check is computed as `git diff --name-only <start_sha>` (a working-tree-relative diff — **not** a commit-range log/rev-list — so it captures both files changed by commits since `start_sha` AND files with uncommitted local changes since `start_sha`). Current dirt is still obtained via `git status --porcelain` (unchanged from today), intersected against this batch-scoped owned-paths set instead of the task-wide parent-diff set. `task_dir`'s blanket subtree inclusion is deliberately **dropped** for this per-batch check — retaining it would still catch any dirty file anywhere under `_mill/` (including a prior batch's re-dirtied `.out.md`), defeating the fix's purpose. `compute_terminal_dirt` itself is unchanged — it keeps its task-wide `task_dir`-blanket-inclusion behavior and remains the authoritative check used by mill-go's separate terminal (task-completion) cleanliness gate.
  `start_sha` is genuinely nullable at this call site (`_batch_completeness_stuck`'s own docstring, case 3, already special-cases `start_sha is None` as "gate has nothing to check against" — e.g. a docs-only batch with zero cards). The batch-scoped gate extends its existing "gate is a no-op when required inputs are absent" guard (currently `if task_dir is None or parent_branch is None: return None`) to also cover `start_sha is None`, disabling the gate rather than attempting a `git diff` against a missing ref.
  This function's own `git diff --name-only <start_sha>` call keeps the function's existing, already-documented error tolerance: any subprocess failure is caught and treated as a no-op (per its current docstring — "Any exception ... is caught and treated as a no-op -- the authoritative mill-go 2b cleanliness gate still runs afterward"). This is a deliberately weaker tolerance than #818's `None`-vs-`[]` "unknown must escalate" rule, because `_in_scope_dirty_stuck` was never, and remains not, the authoritative gate — `compute_terminal_dirt`/`revert_out_of_scope_drift` (hardened by #818) and their handoff.md/SKILL.md-step-2b consumers are. #818's `is None`-propagation obligation therefore does **not** extend to this function: after this fix, `_in_scope_dirty_stuck` no longer calls `_parent_diff_names` or anything derived from it (its owned-paths source is the new, distinct `start_sha`-based `git diff`, not `<parent_branch>...HEAD`), so #818's consumer list should be read as covering `compute_terminal_dirt`, `revert_out_of_scope_drift`, `handoff.md`, and `SKILL.md` step 2b only — not this function, whose earlier-round wording ("whatever underlying `_parent_diff_names`-derived call remains in its dependency chain") is now stale and superseded by this paragraph.
- Rationale: `compute_terminal_dirt`'s scope is deliberately task-wide ("terminal" = whole-task-complete check), which is correct for mill-go's end-of-task gate but wrong for a per-batch finalize check — a prior, already-approved batch's committed file (e.g. `_mill/briefs/implement-<batch>-r1.out.md`) falls within the task-wide parent-diff-owned set (and within the task_dir blanket-inclusion), so if it becomes dirty again post-commit for any reason unrelated to the current batch, the current batch's finalize incorrectly blames it. A pure commit-range mechanism (`git log`/`git rev-list start_sha..HEAD`) was considered and rejected mid-discussion-review: `_is_only_start_batch_commit` (`_implementer_common.py:18-35`) confirms that shape is commit-diff only, which would silently stop flagging the everyday "implementer forgot to commit" case the gate exists for. `git diff --name-only <start_sha>` avoids this — it diffs against the current working tree, so an uncommitted change since `start_sha` still appears in the owned-paths set and still trips the gate when `git status --porcelain` shows it dirty. Extending the disable-guard to `start_sha is None` reuses the exact pattern the function already applies to `task_dir`/`parent_branch`, rather than inventing new null-handling semantics.
- Rejected: (a) keeping task-wide scope but excluding `_mill/briefs/*.out.md` specifically — a narrow band-aid that doesn't generalize to any other file type hit by the same class of bug; (b) auto-reverting any dirt found before failing — risks silently discarding genuine uncommitted work that legitimately belongs to the current batch; (c) a pure `start_sha..HEAD` commit-range diff (`git log`/`git rev-list`) as the owned-paths source — would miss never-committed dirt, caught in discussion-review round 1 (see Q&A log); (d) giving the new `start_sha`-based `git diff` call the same strict `None`-on-failure/escalate treatment as #818's functions — rejected in discussion-review round 2 because this function is explicitly non-authoritative (the terminal gate always re-checks), so matching #818's stricter contract here would be inconsistent with its own documented no-op-on-error design, not an improvement.

### cleanliness-unresolvable-parent-diff (#818)

- Decision: Change `_cleanliness._parent_diff_names` (`plugins/mill/scripts/_cleanliness.py:113-130`) to return `list[str] | None`: `None` when `git diff --name-only <parent>...HEAD` exits non-zero (parent ref unresolvable — e.g. exit 128 from a deleted branch), `[]` only when the command succeeds with genuinely no changed paths. Propagate this distinction through both callers:
  - `compute_terminal_dirt` (`_cleanliness.py:157-187`) returns `list[str] | None` — `None` when the parent diff was unresolvable, matching `_parent_diff_names`'s own sentinel one level up.
  - `revert_out_of_scope_drift` (`_cleanliness.py:326` onward) changes its `remaining_in_scope_lines` tuple element from `list[str]` to `list[str] | None` — the return type becomes `tuple[list[str], list[str] | None]` (`reverted_paths` stays a plain list; nothing can be reverted when the owned-path set itself is unknown, so that element is never `None`).
  Every production consumer of these two return values must add an explicit third branch for `None`, distinct from the existing empty/non-empty branches, escalating exactly as if genuine dirt were found. Note `_implementer_common._in_scope_dirty_stuck` is explicitly **not** one of these consumers after the #825 fix above — its owned-paths source becomes a distinct `start_sha`-based `git diff` call, not `_parent_diff_names` or anything derived from it, and its own error tolerance is governed entirely by the #825 Decision, not this one. The consumers actually requiring the new branch are:
  - `plugins/mill/skills/mill-go-base/handoff.md`'s "Terminal cleanliness gate" has **two** `compute_terminal_dirt` call sites needing the fix, not one: the initial check (line 50: `in_scope_dirt = _cleanliness.compute_terminal_dirt(worktree_root, task_dir, parent_branch)`) AND the post-self-resolve-commit re-check (line 55: "Re-run `_cleanliness.compute_terminal_dirt(worktree_root, task_dir, parent_branch)`", currently branched only on "If it is STILL non-empty..."). Both are the same binary non-empty/empty truthiness pattern; both need a third `in_scope_dirt is None` branch that halts/escalates rather than falling through to the "proceed" path (since `None` is falsy exactly like `[]` in a plain truthiness check, an explicit `is None` check is required at both sites, not an `if not in_scope_dirt:` shortcut).
  - `plugins/mill/skills/mill-go-base/SKILL.md` step 2b (around line 646-662: `reverted_paths, remaining_in_scope_lines = _cleanliness.revert_out_of_scope_drift(...)`, then `in_scope_dirt = remaining_in_scope_lines`) — same binary-branch risk, same required third `is None` branch. The same step's `signature:` doc-comment at line 653 (`` `signature: _cleanliness.revert_out_of_scope_drift(...) -> tuple[list[str], list[str]]` ``) must be updated to `tuple[list[str], list[str] | None]` alongside the branch logic — confirmed `test-skill-helper-drift.py` validates only that referenced function names resolve, not signature text, so this doc-comment would otherwise silently go stale with no test catching it.
- Rationale: The issue's core complaint is that "there is no distinction in the gate's return value between 'genuinely clean' and 'couldn't check' " — a silent `[]` on exit 128 makes real out-of-scope drift undetectable for the remainder of the task. Escalating "unknown" with the same severity as "dirty" is the smallest change that closes the undetectable-drift gap: it reuses existing stuck/blocked plumbing rather than introducing a new severity tier. Discussion-review round 1 caught that the initial version of this decision named only `_in_scope_dirty_stuck` and a vague "mill-go's terminal cleanliness gate" as consumers, without citing the two actual markdown-pseudocode call sites (`handoff.md`, `SKILL.md` step 2b) that perform the real binary branch in production — both are now named explicitly, and both must gain an explicit `is None` branch (not a truthiness check) since `None` and `[]` are both falsy in Python. Discussion-review round 2 caught two follow-on gaps: (i) after #825 rewrites `_in_scope_dirty_stuck`'s owned-paths source, that function no longer derives from `_parent_diff_names` at all, so it was wrongly left hedged as a consumer here — now explicitly excluded and pointed at #825's own Decision instead; (ii) `SKILL.md`'s `signature:` doc-comment for `revert_out_of_scope_drift` would go stale silently (no test checks signature text) unless its update is named explicitly in scope, which it now is.
- Rejected: (a) keeping `[]` but only upgrading the stderr warning's visibility — doesn't fix the actual problem (drift still passes through undetected, just with a louder log line); (b) raising an exception immediately inside `_parent_diff_names` — too blunt without auditing every call site for legitimate tolerance of a missing parent ref elsewhere in the codebase; out of scope for this fix; (c) leaving the two markdown-driven call sites (`handoff.md`, `SKILL.md` step 2b) unmentioned and letting the plan writer discover them independently — caught in discussion-review round 1 as a real risk of the `None` sentinel silently collapsing back into "clean" via ordinary falsy-check idiom at the actual production gate (see Q&A log); (d) leaving `_in_scope_dirty_stuck` listed as a consumer needing the `is None` branch — caught in discussion-review round 2 as stale once #825 supersedes that function's owned-paths source entirely; (e) leaving the `SKILL.md` `signature:` doc-comment unmentioned — caught in discussion-review round 2 as a silent-drift risk with no test coverage.

### discussion-review-tooling-claim-consistency-check (#812)

- Decision: Add an explicit bullet to the Criteria section of `plugins/mill/templates/review-discussion.md` (after the existing "Constraint coverage" bullet, alongside the existing four-class rubric where `consistency` is already defined as "the artefact contradicts itself, carries a superseded statement, or violates an established repo convention"): instruct the reviewer to verify any testing-plan claim about tooling, validator, or command-prefix requirements (naming `PYTHONPATH=` as the concrete example) against CLAUDE.md and the actual `_plan_validate.py` enforcement, and flag a contradiction as `[BLOCKING:consistency]`.
- Rationale: `_plan_validate.py`'s `_check_verify_not_isolated` (`plugins/mill/scripts/_plan_validate.py:1952-2004`) is correct and intentional — it requires the `PYTHONPATH=` prefix on every `verify:` command whenever any Python marker file exists anywhere in the project, regardless of whether the specific command invokes Python, matching CLAUDE.md's documented rule verbatim. The bug in #812 is that a discussion.md's Testing section asserted the opposite ("no PYTHONPATH= needed for grep-only verify commands") and this false claim passed three discussion-review rounds unchallenged. The `consistency` finding class already exists and already covers "violates an established repo convention" in principle, but the reviewer wasn't specifically prompted to fact-check tooling/validator claims against source — a concrete criterion closes that gap and generalizes to any future similarly-shaped false claim about tooling behavior, not just this one phrase.
- Rejected: (a) changing the validator itself — off-target, the validator is correct; (b) a narrow automated grep-based pre-check in `millpy-review-discussion.py`'s backend for this specific phrase — a heavy one-off linter that doesn't generalize the way a reviewer-prompt criterion does.

## Technical context

Note the walk's loop-termination condition at line 212 (`if check == git_root_resolved or check == check.parent: break`) is why a task worktree's walk never reaches the container-level hub directory — worktree roots are independent git checkouts, not nested filesystem descendants of the hub for `git_root` purposes.
- `millpy-spawn.py`: `hub = resolve_hub_path()` at line 95 (subject to the same #833 resolution, but under normal invocation — spawn run from the hub — resolves correctly since `main_root` computation via git-common-dir is unaffected by the bug); `hub_subpath = cfg.get("hub_relative_path", ".")` at line 98; `_worktree.copy_millhouse(src=hub/".millhouse", dst=dest_hub/".millhouse", exclude={"wiki","active"})` at lines 212-216 (unconditional, copies all non-excluded, non-symlink entries via `shutil.copy2`/`copytree`); existing gated stub-write at lines 263-269 (`if hub_subpath != ".":`).

## Q&A log

- **Q:** Fix #833 and #834 together or independently? **A:** [auto-pick] Fix both — robustify the fallback (#833) AND make the spawn-time write defensive (#834). **Why:** same root symptom; fixing only the write leaves the fallback silently wrong for any other cause of a missing file.
