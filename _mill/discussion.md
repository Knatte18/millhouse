## Problem

Four independent, file-and-line-level bugs in mill's own dispatch/report/tag machinery, all self-discovered while running mill-go/mill-merge against this repo in other task sessions this week (sources: GitHub issues #746, #740, #745, #744, all now closed and folded into this task). Each is small and self-contained, but all four erode trust in mill's own automation feedback loops — a silently-stale archive tag, a review-round override that doesn't actually override, a test helper that looks like it seeds state but doesn't, and a commit SHA that can't always be trusted downstream. Fixing them now (all together, since they were surfaced in the same triage pass) prevents each from causing a confusing, hard-to-diagnose failure the next time someone hits it during a live mill-go/mill-merge run.

## Scope

**In:**
- `_archive_tag.create_or_resolve` (`plugins/mill/scripts/_archive_tag.py`): surface push failures via a `push_failed` flag (and `push_error` when applicable) on every push it attempts (`created`, `force_update`, and both `moved_aside` pushes), instead of silently discarding the subprocess result.
- mill-merge Step 6 (`plugins/mill/skills/mill-merge/SKILL.md`, "### 6. Archive tag"): read the new `push_failed` field and print a clear warning to the operator when set; do not halt.
- `_review_plan.py::run()` (`plugins/mill/scripts/_review_plan.py`): fix the holistic-disablement gate (currently `elif holistic_name is None or cfg["roles"]["plan-review"]["holistic"]["rounds"] == 0:`) to read the already-computed `holistic_max_rounds` variable instead of the raw config value, mirroring `_review_discussion.py::run()`'s equivalent check (`max_rounds_cfg == 0`).
- `_test_registry.write_to` (`plugins/mill/unit_tests/_test_registry.py`): redirect it to write `.millhouse/agents.local.yaml` (the layer `_reviewers.load()` actually merges) instead of `wiki_root/agents.yaml`; update its parameter from `wiki_root: Path` to the hub/mill directory it should write under.
- Consolidate `_test_helpers.write_local_overlay` (the duplicate workaround two prior implementer batches independently wrote) into/onto the redirected `_test_registry.write_to`, or otherwise remove the now-redundant helper — exact mechanics left to mill-plan, see Decisions.
- `implementer-brief.md`, `fixer-batch-brief.md`, `fixer-holistic-brief.md`, `merge-in-verify-brief.md` (`plugins/mill/templates/`): tighten the `<last-HEAD-sha>` JSON-report contract wording to explicitly require the full 40-char SHA via `git rev-parse HEAD` (never `git rev-parse --short HEAD` / `git log --oneline`).
- `_implementer_common.py::_forward_output`'s success-path `commit_sha` override (~line 1648, `plugins/mill/scripts/_implementer_common.py`): close the one gap found during investigation — the override only fires `if result.returncode == 0`; add a length/format check (accepting either a 40-char SHA-1 or a 64-char SHA-256 hex string, not hardcoded to 40 — this repo's git objects are SHA-1 today, but the check should not assume that forever) so a bad self-reported value can never silently reach `status.md` when the corrective `git rev-parse HEAD` call itself fails.
- New/updated unit tests for all four fixes (see Testing).

**Out:**
- The `reviewer_override`-specific rounds gate in `_review_plan.py::run()` (a few lines above the fixed gate) — its current behavior of checking the *raw* config `rounds` value even when an override name is given is intentional and already documented (the "null-bypass Decision" in its docstring). Not touched.
- The analogous batch-rounds gate in the same function (`cfg["roles"]["plan-review"]["batch"]["rounds"] == 0`) — not verified as buggy, not mentioned in the source issue. If it turns out to have the same bug, that's a separate follow-up.
- Any cleanup of the 11 existing test call sites that already call `_test_registry.write_to(wiki_root)` for tests that don't actually need a resolvable named reviewer (e.g. tests using the `"test_stub"` reviewer, which bypasses registry lookup entirely). They remain harmless no-ops after the redirect and are not touched.
- A full forensic reproduction of the exact historical #744 incident. Investigation during discussion found the finalize-side correction already existed (added 2026-06-06, before the incident) and covers the normal success path; the fix scope is the brief-wording tightening plus the one concrete gap found, not an open-ended re-investigation.
- Any other latent bugs elsewhere in the mill pipeline not covered by these four issues.

## Decisions

### push_failed reporting shape

- Decision: `create_or_resolve` gains a `push_failed: bool` key (plus `push_error: str | None`, populated from the failed push's stderr, when `push_failed` is true) on its returned dict, on **every** action including `noop` — `noop` attempts no push and always returns `push_failed: False, push_error: None`, so the key is never absent and mill-merge can do an unconditional `result["push_failed"]` read exactly like its existing `result["action"]`/`result["tag"]` reads. For `created` and `force_update` (single push each), `push_failed`/`push_error` reflect that one push's outcome directly. For `moved_aside` (two independent pushes: the moved-aside-tag push, then the primary-tag push), `push_failed` is the OR of both pushes' outcomes, and `push_error` is a combined string that labels which push(es) failed (e.g. `"moved-aside tag push failed: <stderr>"` and/or `"primary tag push failed: <stderr>"`, joined if both fail) so the operator warning can name the specific tag(s) needing reconciliation. The underlying `git push` calls stay `check=False` (best-effort, as today) — only the returncode inspection and reporting change.
- Rationale: issue #746 specifically named the force-with-lease push, but a plain push (e.g. for a brand-new tag) can also fail for reasons worth surfacing (remote already has an unexpected tag by that name). One consistent, always-present field is simpler for `mill-merge` to check than a key that's sometimes absent (`noop`) or ambiguous when two pushes happen (`moved_aside`).
- Rejected: retry-after-fetch (adds retry-loop complexity to a low-level git helper; the caller can decide to retry if it wants); making push failure fatal/raising (too aggressive — local git state is still correct, only the remote is stale, and mill-merge should be able to complete teardown regardless); omitting `push_failed` on `noop` and requiring callers to use `.get("push_failed", False)` (inconsistent shape, easy to forget); tracking `moved_aside`'s two pushes under separate keys (breaks the uniform single-pair shape the other three actions use).

### mill-merge Step 6 reaction to push_failed

- Decision: mill-merge Step 6 prints a clear warning (`[mill-merge] WARNING: archive tag push failed -- reconcile <tag> with remote manually`, or similar) when `result["push_failed"]` is true, but does not halt Step 6 or block subsequent steps (Home.md flip, lock release, notify).
- Rationale: matches the issue's own suggested remediation ("surface push failure ... so the operator knows to reconcile manually instead of silently leaving remote stale"); a stale archive tag is a housekeeping issue, not a correctness issue for the merged branch itself.
- Rejected: halting mill-merge at Step 6 — over-blocks a mostly-successful merge on a tag-push race that's recoverable after the fact.

### holistic-rounds gate reads the effective override

- Decision: in `_review_plan.py::run()`, change `elif holistic_name is None or cfg["roles"]["plan-review"]["holistic"]["rounds"] == 0:` to `elif holistic_name is None or holistic_max_rounds == 0:`, where `holistic_max_rounds` is the variable already computed a few lines earlier (`max_rounds if max_rounds is not None else cfg["roles"]["plan-review"]["holistic"]["rounds"]`). No other gate in the function changes.
- Rationale: mirrors `_review_discussion.py::run()`'s equivalent check (`max_rounds_cfg = max_rounds if max_rounds is not None else cfg[...]["rounds"]; if max_rounds_cfg == 0: ...`), which already gets this right. The `reviewer_override`-specific gate a few lines above is deliberately left alone — its docstring documents that a `reviewer_override` should still respect a raw `rounds: 0` config even though it bypasses the `holistic_name is None` disablement; that is a distinct, already-intentional design decision, not the bug being fixed here.
- Rejected: also changing the `reviewer_override` gate to use `holistic_max_rounds` — reverses currently-documented, deliberate behavior and is out of scope for this bug; fixing the sibling `batch`-rounds gate in the same pass — unverified, not part of the reported bug, would expand scope without a confirmed repro.

### test_registry redirected to the local-overlay layer

- Decision: `_test_registry.write_to` writes `.millhouse/agents.local.yaml` under the hub/mill directory it's given (parameter renamed from `wiki_root: Path` to reflect the new target), instead of `wiki_root/agents.yaml`. `make_minimal_registry` (the dict-building half) is unchanged. Since `_test_helpers.write_local_overlay` already does exactly this (added independently by two prior implementer batches as a workaround), mill-plan should decide the exact consolidation mechanics — e.g. have `write_to` become the canonical implementation and either remove `write_local_overlay` or make it a thin alias, whichever produces the smaller diff across the ~2 files that currently call `write_local_overlay` directly.
- Rationale: `_reviewers.load()` only falls back to the legacy wiki `agents.yaml` when both the plugin template and `.millhouse/agents.local.yaml` are empty — never true in this repo (populated plugin template) — so `write_to`'s current target is dead for its stated purpose (seeding a resolvable named `reviewer_override` spec for tests). This is exactly the issue's stated fix direction.
- Rejected: an optional `layer: "wiki" | "local"` parameter defaulting to `"wiki"` — preserves the broken default and adds a footgun; leaving `write_to` alone and just promoting `write_local_overlay` as the "real" helper — perpetuates two helpers doing the same job under different names, which is the duplication the issue flagged in the first place.

### commit_sha: brief wording + one finalize gap, not a re-investigation

- Decision: (a) tighten the `<last-HEAD-sha>` placeholder wording in all four brief templates that use it (`implementer-brief.md`, `fixer-batch-brief.md`, `fixer-holistic-brief.md`, `merge-in-verify-brief.md`) to explicitly instruct `git rev-parse HEAD` for the full 40-char SHA, calling out that `--short` / `git log --oneline` must not be used. (b) In `_implementer_common.py::_forward_output`'s success-path override (~line 1648), the `parsed["commit_sha"] = result.stdout.strip()` correction currently only fires `if result.returncode == 0`; add a check so that if the corrective `git rev-parse HEAD` call itself fails, or the resulting value is not a well-formed 40-char (SHA-1) or 64-char (SHA-256) hex SHA, the report is not silently passed through — surface it as a `stuck_type: logic` (or similar existing classification) instead of `status: success` with a bad SHA.
- Rationale: investigation during discussion found that `_forward_output`'s success path already overwrites the agent's self-reported `commit_sha` with a freshly computed, correct `git rev-parse HEAD` result — this code was added 2026-06-06, before the #744 incident (2026-07-29), and applies uniformly to both subprocess and Agent-mode dispatch (both route through `--stage finalize` -> `finalize_from_output` -> `_forward_output`). So the normal success path should already be immune to a truncated agent self-report by the time `status.md` is written. The one concrete gap found is the unguarded `if result.returncode == 0:` — if that git call fails, whatever the agent self-reported (potentially abbreviated) passes through untouched. Tightening the brief wording is cheap defense-in-depth regardless of root cause.
- Rejected: skipping the finalize-side fix and only tightening brief wording — leaves the one confirmed gap unaddressed; an open-ended deeper audit to reproduce the exact historical incident before deciding anything — the code-level investigation already done here is sufficient to act on; further forensics have a low expected payoff relative to just closing the identified gap.

## Technical context

- **`_archive_tag.py`** (`plugins/mill/scripts/_archive_tag.py`): `create_or_resolve(worktree, slug, child_branch) -> dict` has four `_subprocess_util.run([..., "push", ...], check=False)` call sites (lines ~65-68 `created`, ~105-108 `force_update`, ~154-161 both `moved_aside` pushes). All four currently discard the `CompletedProcess` result entirely. Its only caller is `mill-merge/SKILL.md` "### 6. Archive tag", which today only reads `result["action"]`, `result["tag"]`, `result["moved_aside_to"]`. `plugins/mill/unit_tests/test-archive-tag-conflict.py` already exists and covers `create_or_resolve`'s created/noop/force_update/moved_aside branches (including the `-01`/`-02` suffix logic) via a `git init`-only fixture with **no remote configured** — so today's tests never exercise the push calls at all (each `check=False` push there presumably no-ops or fails silently against the absent remote, untested either way).
- **`_review_plan.py`** (`plugins/mill/scripts/_review_plan.py`): the bug is at the `elif` inside `run()` around line 730 (holistic reviewer resolution, step 3). `holistic_max_rounds` is computed at line 676, printed for diagnostics at line 682, and already correctly used later (line 852, 859) for the round-cap check inside the holistic dispatch block itself — only the *disablement* gate at line 730 misses it. Compare against `_review_discussion.py::run()` lines 251-252 (`max_rounds_cfg` computed and checked) for the reference pattern; `_review_discussion.py::prepare()` lines 79-85 (`effective_max`) shows the same pattern used a second place in that sibling module.
- **`_test_registry.py`** (`plugins/mill/unit_tests/_test_registry.py`): `write_to(wiki_root: Path, **overrides) -> Path` writes `wiki_root / "agents.yaml"`. `_reviewers.load(hub_dir)` (`plugins/mill/scripts/_reviewers.py` line 132) reads the plugin template (`resolve_plugin_template_path("mill-agents.yaml")`) and `hub_dir / ".millhouse" / "agents.local.yaml"`, only falling back to `wiki_path / "agents.yaml"` when *both* are empty (line 163's `if not template_registry and not local_registry:`). `_test_helpers.write_local_overlay(mill_dir, **entries) -> None` (`plugins/mill/unit_tests/_test_helpers.py` line 305) already writes `mill_dir / "agents.local.yaml"` and is used by `test-reviewers.py`'s `reviewer_override` tests and referenced in `test-review-discussion-flow.py`'s comments. 11 call sites total call `_test_registry.write_to(wiki_root)`: `test-agent-mode-dispatch.py` (x1), `test-review-code-flow.py` (x7), `test-review-plan-flow.py` (x2), `test-review-discussion-flow.py` (x1) — spot-checked `test-review-code-flow.py`'s usage and confirmed it uses the `"test_stub"` reviewer, which bypasses registry lookup, so the redirect is harmless there; all other sites likewise use `"test_stub"` or a real-template-resolvable reviewer name.
- **`_implementer_common.py`** (`plugins/mill/scripts/_implementer_common.py`): `finalize_from_output()` (line 1275) reads the agent's captured output text and delegates to `_forward_output()` (line 1410), which extracts the last JSON object via `_extract_status_json`. Both dispatch modes reach this same function: subprocess/psmux via `millpy-implement.py --stage finalize` directly, and Agent-mode via the same `--stage finalize` CLI call documented in `mill-go/SKILL.md`'s "## Agent-mode dispatch" step 6 (both write the captured notification text to `<brief_path>.out.md` first).

## Testing

- **`_archive_tag.py`**: extend the existing `plugins/mill/unit_tests/test-archive-tag-conflict.py` (do not create a new `test-archive-tag.py` — this file already covers created/noop/force_update/moved_aside via a `git init`-only fixture, and a second file would duplicate its `_init_repo`/`_make_commit`-style helpers) with push-outcome coverage: add a local bare "remote" repo to the fixture (tempfile-based, no network) and cover (a) `created`/`noop`/`force_update` with a push that succeeds → `push_failed: false, push_error: None`; (b) `force_update`/`moved_aside` with a push that's rejected by pre-manipulating the bare remote's ref to simulate a stale-lease conflict → `push_failed: true` and a populated `push_error`; (c) `moved_aside` specifically with only one of its two pushes rejected → `push_failed: true` with `push_error` naming which tag failed. Stays in `unit_tests/`, alongside `test-archive-tag-conflict.py`: the bare "remote" is a second local tempdir repo with no network involved, the same "no real git/LLM" spirit the existing file's `git init`-only fixture already operates under (that file already does real local git operations; only a real network remote or a real LLM call would require `integration_tests/`).
- **`_review_plan.py`**: add a case to `test-review-plan-flow.py` (which already has extensive `reviewer_override`/rounds-related cases, e.g. tests 31a-32d) asserting that with `roles.plan-review.holistic.rounds: 0` in config and `run(..., max_rounds=1)` (no `reviewer_override`), the holistic reviewer *is* resolved and dispatched (mirrors whatever pattern `_review_discussion.py`'s equivalent test uses, if one exists — check `test-review-discussion-flow.py` for a same-shaped case to mirror the assertion style).
- **`_test_registry.py`**: a round-trip test — call the redirected `write_to(mill_dir, ...)`, then `_reviewers.load(mill_dir)`, and assert the seeded entry resolves. Update/consolidate any test currently exercising `_test_helpers.write_local_overlay` per the Decisions section's consolidation call.
- **`_implementer_common.py`**: a `finalize_from_output`/`_forward_output` test that constructs a fake agent-output text containing an abbreviated `commit_sha` (e.g. `"commit_sha":"2469b6f0"`) in an otherwise-valid success JSON, and asserts the finalized envelope's `commit_sha` is the full-length value matching the fixture repo's actual hash algorithm (40-char SHA-1 for a normal `git init` fixture) — and a second case that forces the `git rev-parse HEAD` call to fail (unwritable/missing repo) and asserts the result is NOT a silent `status: success` passthrough with the bad (short) SHA. The validator itself should be covered directly (not just through the git-repo fixture): assert it accepts both a 40-char hex string and a 64-char hex string, and rejects anything else (wrong length, non-hex characters, empty string).
