## Problem

During a `/mill-start` discussion-review loop (GitHub issue #726, Windows 11, nested-hub worktree layout), every tracked file under `_mill/` — `discussion.md`, `status.md`, `briefs/`, `reviews/` — was deleted from the working tree by something outside the orchestrator's own edits. It surfaced only when an unrelated `Edit` on `discussion.md` failed with "File does not exist"; `git status` showed working-tree deletions across the whole tree. Recovery was trivial (`git checkout HEAD -- _mill/`) because everything was committed, but the loss was **silent** until an unrelated operation happened to trip over it.

`mill-start/SKILL.md`'s existing "Status safeguard" (Phase: Discussion Review) already anticipates this failure class — it checks `git status --short -- _mill/status.md` before every `_status.append_phase` call and restores on detected deletion — but its scope is exactly one file. The observed incident hit `discussion.md`, `reviews/`, and `briefs/` too, none of which the existing safeguard checks. `mill-plan` and `mill-go` run structurally identical review loops (Plan Review; Code Review / Holistic Review) and have **no equivalent safeguard at all**, not even a status.md-only one.

**Why now:** the existing status.md-only safeguard is itself evidence this bug class is known and recurring; it was a targeted patch for one prior incident, not a fix for the class. This task widens the fix to the whole `_mill/` tree and to all three skills that run review loops.

## Scope

**In:**
- A new reusable Python helper, `_treeguard.py`, exposing `check_and_restore(worktree: Path, tracked_root: str = "_mill", *, record: bool = True) -> dict`, that detects any working-tree or staged deletion anywhere under a tracked subtree and restores exactly the deleted paths in one shot.
- Wiring `check_and_restore` into all three review loops: mill-start's Discussion Review (replacing the existing status.md-only safeguard), mill-plan's Plan Review, and mill-go's Code Review and Holistic Review loops.
- Orchestrator-level bracketing of the Agent-mode dispatch window: a `check_and_restore` call immediately before each Agent-mode `--stage prepare` dispatch and again right after `--stage finalize` returns, for every review loop, in addition to the existing per-`_status.append_phase` checkpoint pattern.
- A non-blocking audit record on detection: when a deletion is found and restored, append a short line (timestamp + restored paths) to the task's own history via a new `_status.py` function, `append_recovery_log(status_path, timestamp, restored_paths)`, which lazily creates a `## Tracked-file recovery log` section on first use (mirroring `_write_batches`'s existing lazy-insert-if-absent pattern for `## Batches`) and appends one line per incident thereafter.
- A unit test (`plugins/mill/unit_tests/test-treeguard.py`) covering detection and restore using a tempfile git fixture.

**Out:**
- Identifying the actual root cause of the deletion. Exploration during this discussion ruled out every plausible in-repo mechanism (see Technical context) — the reviewer sub-agent has no Bash/Edit-delete capability under its tool grant (`Read, Grep, Glob, Write` only), no recursive-delete or cross-tree tempdir/tempfile logic sits on the discussion/plan/code-review code paths (the one real delete call on this path, `_agent_dispatch.write_brief`'s same-round `.out.md` unlink, only ever targets a single untracked file from the same round — see Technical context), and mill-cleanup's whole-worktree removal (`_safe_rmtree.py`/`_worktree.remove_safe`) is architecturally distinct from a `_mill/`-scoped subtree loss. The deleter remains unidentified; this task is detect-and-recover only, matching the conclusion #726 itself reached.
- Any change to `worktree_snapshot_guard` (`_review_common.py`) itself or its subprocess/psmux `run()` bracketing — that mechanism already works correctly for subprocess/psmux mode and is left as-is. The new orchestrator-level check is additive, for the Agent-mode gap specifically, not a replacement. This means the subprocess/psmux path keeps its existing hard-block-on-overstep behavior (no auto-restore) for the exact same class of `_mill/` deletion the new Agent-mode checkpoints auto-restore-and-record — an intentional, accepted asymmetry; see Decisions: "Subprocess/psmux path keeps its existing block-on-overstep behavior".
- Preventing or blocking on detected deletions **at the new orchestrator-level checkpoints** specifically. Recovery there is always a clean `git checkout HEAD --` of exactly the deleted paths because that content is committed before a review round starts; this task does not add a manual-acknowledgement gate to those checkpoints. (This does not apply to `worktree_snapshot_guard`'s existing subprocess/psmux behavior — see the bullet above.)
- Any change to mill-merge, mill-merge-in, or any non-review-loop phase. Only the three review loops (discussion/plan/code+holistic) are in scope.
- Recovering round-fresh, not-yet-committed `_mill/briefs/`/`_mill/reviews/` artifacts (the specific files written during the current round, before that round's own end-of-round commit lands). This is an accepted residual risk, not a mitigated case — see Decisions: "Uncommitted round-fresh artifacts are an accepted residual risk".

## Decisions

### Reusable helper over duplicated Bash

- Decision: Implement the widened safeguard as `_treeguard.py::check_and_restore(worktree: Path, tracked_root: str = "_mill", *, record: bool = True) -> dict`. Signature returns a dict with at least `{"triggered": bool, "restored_paths": list[str], "timestamp": str | None}` — `triggered=False` and empty `restored_paths` when nothing was found.
- Rationale: A single Python helper is unit-testable in isolation, called identically from all three SKILL.md docs, and avoids tripling near-identical Bash prose across mill-start/mill-plan/mill-go. Matches the project's existing pattern of pushing logic into `_*.py` helpers (`_status.py`, `_cleanliness.py`) rather than duplicating shell across skills.
- Rejected: Inlined `git status --short` Bash prose repeated per-skill (today's status.md-only pattern) — works but can't be unit-tested and drifts across the three copies over time.

### Detection query and restore granularity

- Decision: `check_and_restore` runs `git -C <worktree> status --porcelain -- <tracked_root>` once (a single query scoped to the whole subtree, not per-file). Any line whose status code is ` D` (working-tree deleted) or `D ` (staged deleted) anywhere under `tracked_root` is collected into a pathspec list, and exactly those paths — never the whole subtree — are restored in one shot: `git -C <worktree> checkout HEAD -- <deleted-path-1> <deleted-path-2> ...`.
- Rationale: Scoping the checkout to exactly the paths reported as deleted (rather than blanket-reverting the whole `tracked_root` to HEAD) means the restore only ever touches paths that are actually missing. Any OTHER tracked file under `_mill/` that has a legitimate, currently-uncommitted modification (not a deletion — e.g. a just-appended, not-yet-committed `status.md` phase row from `_status.append_phase`) is left completely untouched, because it never appears in the ` D`/`D ` pathspec list in the first place. This is still a single detection query and a single restore command — the targeting is precise, not the complexity. (Revised from an earlier whole-subtree-checkout design after review round 2 flagged that a blanket `git checkout HEAD -- _mill/` would also revert legitimate uncommitted diffs elsewhere in the tree, not just restore deletions — see "Closing the Agent-mode bracketing gap" below for the concrete scenario.) **Residual risk, accepted (see below): round-fresh, not-yet-committed artifacts are outside what this restore can recover — see "Uncommitted round-fresh artifacts are an accepted residual risk" below.**
- Rejected: Blanket `git checkout HEAD -- <tracked_root>` reverting the whole subtree regardless of which specific paths were deleted — simpler to write, but reverts every other uncommitted tracked change in the subtree along with the actual deletions, which is unsafe whenever a round has an uncommitted `_status.append_phase` write in flight (confirmed real for mill-go's per-batch Code Review loop, which appends `reviewing-{batch_name}-r{N}` before its Agent-mode dispatch with no intervening commit).
- Rejected: Per-file checks replicated for status.md/discussion.md/briefs/reviews/ individually — this is exactly the pattern being widened away from; it doesn't scale to new files added under `_mill/` later (e.g. a future subdirectory) the way a single subtree-scoped detection query does. (The restore itself is now per-path per the decision above — only the *detection query* stays subtree-scoped.)

### Uncommitted round-fresh artifacts are an accepted residual risk

- Decision: `check_and_restore` cannot detect or recover the loss of round-fresh `_mill/briefs/*.md`, `_mill/briefs/*.out.md`, or `_mill/reviews/*.md` files written during the *current* round, before that round's own end-of-round commit. This is an accepted residual risk for this task, not a defect to mitigate here.
- Rationale: `_agent_dispatch.write_brief` and `_review_common.write_review_file` never commit — every review loop (mill-start's Discussion Review, mill-plan's Plan Review, mill-go's Code/Holistic Review) intentionally batches the brief write, the reviewer's `.out.md` write, and the review-file write into a single end-of-round commit (e.g. mill-start step 4b/5's "single git commit covering exactly four pathspecs"). Until that commit lands, those specific files are untracked, so a deletion of exactly those files leaves no trace in `git status --porcelain` (an untracked file that disappears simply stops appearing — there is no `D` line to detect) and `git checkout HEAD --` has nothing to restore them from. Closing this fully would mean making every brief/review-file write commit immediately instead of batching at round-end — a change to the commit-cadence architecture that mill-go, mill-plan, and mill-start all rely on for their round-audit-trail and crash-recovery conventions (e.g. mill-go's freshness check in the Code Review loop's crash-recovery step, which compares a review file's mtime against a specific `_status.append_phase` timestamp) — a change with blast radius well beyond this task's scope of detecting and recovering already-committed `_mill/` content.
- Rejected: Making `write_brief`/`write_review_file` commit immediately on write — would close the gap but destabilizes the batched-commit-per-round pattern that multiple other decisions across mill-start/mill-plan/mill-go (crash recovery, round audit trail, "one commit per round" conventions) depend on; out of scope for a task whose problem statement is specifically about restoring already-committed tracked content.

### Wiring point: all three review loops, not just mill-start

- Decision: Wire `check_and_restore(worktree, "_mill")` into mill-start's Discussion Review (replacing the existing status.md-only safeguard), mill-plan's Plan Review, and mill-go's Code Review and Holistic Review loops — same call, same helper, same trigger points (before each `_status.append_phase` call in each loop).
- Rationale: mill-plan and mill-go run structurally identical review-loop architecture (prepare → dispatch reviewer → finalize → append_phase, looped up to `max_review_rounds`) and are equally exposed to whatever caused the original incident, whether environmental (a background process, an OS-level sweep, antivirus, sync-client interference) or a concurrent second mill session on the same worktree. Protecting only mill-start would leave two structurally identical, equally-exposed loops unprotected for no principled reason.
- Rejected: mill-start only (matches issue #726's literal title) — narrower than the actual exposure; the issue's title names mill-start because that's where the incident was observed, not because the mechanism is mill-start-specific.
- Rejected: mill-start now + separate follow-up task for mill-plan/mill-go — unnecessary process overhead when the fix is the same three-line wiring change in three files; no reason to split it across tasks.

### Closing the Agent-mode bracketing gap

- Decision: In addition to the per-`_status.append_phase` checkpoint (which catches drift at fixed points but does nothing to bracket the review-agent's actual execution window), add an orchestrator-level `check_and_restore` call immediately before each Agent-mode `--stage prepare` dispatch and immediately after the corresponding `--stage finalize` call returns, for every review loop (discussion, plan, code, holistic). This applies only to the `dispatch == agent` path; the `subprocess`/`psmux` path already gets end-to-end coverage from `worktree_snapshot_guard` wrapping the CLI's `run()` in one process.
- **Ordering note (resolves review round 2's GAP):** mill-go's per-batch Code Review loop calls `_status.append_phase(status_path, f"reviewing-{batch_name}-r{N}", ...)` *before* firing the Agent-mode `--stage prepare` dispatch, with no commit in between (`mill-go/SKILL.md:357` onward) — so the pre-prepare `check_and_restore` call runs while that round's `status.md` phase-append is still uncommitted. This is safe only because `check_and_restore` restores exactly the paths reported as deleted (per "Detection query and restore granularity" above), not the whole subtree: `status.md`'s legitimate uncommitted modification shows as ` M` in `git status --porcelain`, never as ` D`/`D `, so it is never included in the restore pathspec and is left untouched regardless of when the checkpoint runs relative to that round's `append_phase` call. A blanket whole-subtree restore would not have had this property, which is exactly what review round 2 caught.
- Rationale: `worktree_snapshot_guard` (`_review_common.py:127-215`) already detects and raises on exactly this class of git-state overstep, but it's wired into `_review_discussion.py`'s `run()` function, which is only invoked by the CLI's `--stage full` path (subprocess/psmux). Under Agent-mode dispatch — the default for the Claude provider, and what mill-start's own SKILL.md documents as the primary path — `--stage prepare` and `--stage finalize` are two separate CLI process invocations, with the actual review agent executing out-of-process (via the harness's Agent tool) in between. No single Python function call can bracket that window, because prepare and finalize don't share process state and the agent's execution happens entirely outside both. The orchestrator (the Claude Code session itself) is the one party present continuously across prepare → Agent dispatch → finalize, so it's the only place a before/after check can actually span the whole window.
- Rejected: Leaving `worktree_snapshot_guard` subprocess-only and relying solely on the per-`append_phase` checkpoint — this still leaves gaps: a deletion that happens and gets silently overwritten by some later legitimate commit before the next append_phase checkpoint would not be caught retroactively (though it would still be caught by the next round's pre-prepare snapshot under the chosen design, since that snapshot runs before any such overwrite could occur in the same round).
- Rejected: Extending `worktree_snapshot_guard` itself to persist a snapshot file in `--stage prepare` for `--stage finalize` to diff against — technically workable, but pushes state across two process boundaries via a side-channel file, adding a new persistence concern (where does the snapshot live, cleanup, staleness) for no benefit over the orchestrator just calling the same `check_and_restore` helper twice, which requires no new state at all.

### Detection behavior: record, don't block

- Decision: When `check_and_restore` triggers a restore, append a short audit line — timestamp plus the list of restored paths — to a small, append-only record. Use a new `## Tracked-file recovery log` section in `status.md` (parallel to the existing phase-timeline convention: append-only, one line per incident, never edited in place). Do not block the task.
- Rationale: The entire premise of this task is that the deletion was silent — recoverable, but invisible until an unrelated failure surfaced it. Restoring silently (today's status.md-only behavior) preserves that exact silence for the wider tracked-file case. Blocking on every detection would be disproportionate: recovery is always a clean, lossless `git checkout HEAD --` because everything is committed beforehand, so forcing an operator to manually acknowledge each occurrence adds friction without adding safety. A visible, non-blocking record gives operators (and future debugging of the still-unidentified root cause) a timeline of when and how often this happens, without interrupting the pipeline.
- Rejected: Silent restore (today's behavior) — defeats the purpose of this task.
- Rejected: Block on every detection (`_status.set_blocked`) — disproportionate given lossless, deterministic recovery; would turn a self-healing safeguard into a manual-intervention chokepoint for an event that, per the original incident, causes no actual harm once caught.

### Recovery-log section: lazy creation via a new `_status.py` helper

- Decision: The `## Tracked-file recovery log` section is not added to `status-discussing.md` (or any other status template) at spawn time. Instead, a new `_status.py` function, `append_recovery_log(status_path: Path, timestamp: str, restored_paths: list[str]) -> None`, creates the section lazily on its first call (inserting the heading if absent) and appends a new line on every subsequent call — mirroring `_write_batches`'s existing lazy-insert-or-replace pattern for `## Batches` (`_find_batches_block` returns `None` when the heading is absent; `_write_batches` inserts it), except append-only rather than replace-whole-section, matching the append-only `## Timeline` convention instead.
- Rationale: Every existing status.md section has a dedicated owner in `_status.py` (`append_phase` owns `## Timeline`; `init_batches`/`set_batch_field` own `## Batches`) that creates or mutates its section without requiring the template to pre-declare it. Adding the recovery-log heading to every task's status.md at spawn time, whether or not the bug this task addresses ever occurs for that task, would put an empty, likely-never-used section in every task's status.md — noise for the common case. Lazy creation on first actual trigger matches the existing precedent and keeps the common case (no detected deletion, ever) template-clean.
- Rejected: Adding `## Tracked-file recovery log` to `status-discussing.md` (and any other spawn-time status template) unconditionally — creates an empty section in every task regardless of whether the bug this task addresses ever manifests; inconsistent with how `## Batches` (a section that also doesn't apply to every task phase) is already handled.

### Subprocess/psmux path keeps its existing block-on-overstep behavior

- Decision: `worktree_snapshot_guard` (`_review_common.py:127-215`, wrapping subprocess/psmux's `run()` in `_review_discussion.py:215`, `_review_plan.py:643`, `_review_code.py:622`) keeps its current behavior unchanged: it raises `ReviewerOverstepError` and hard-stops (no auto-restore; per its own docstring, "the operator resets manually after investigating") on any working-tree deletion it observes — including exactly the class of `_mill/` tracked-file deletion this task's new checkpoints auto-restore-and-record elsewhere. This is an intentional, accepted asymmetry between the subprocess/psmux path and the new Agent-mode checkpoints, not an oversight.
- Rationale: `worktree_snapshot_guard` is not scoped to `_mill/` — its `expected_paths` filter only allowlists the reviews_dir; any OTHER unexpected git-state change anywhere in the repo (a non-fast-forward HEAD move, new dirt anywhere, arbitrary removed files) also raises. It is a general reviewer-overstep detector for the whole subprocess/psmux review invocation, not a narrow `_mill/`-deletion safeguard. Weakening its raise-and-block behavior to auto-restore-and-continue, in order to be consistent with the new narrower `_mill/`-scoped checkpoints, would also soften its response to a reviewer (potentially running with broader tool access than the Agent-mode reviewers' `Read, Grep, Glob, Write`-only grant, depending on which LLM backend `subprocess`/`psmux` mode is configured to use) committing arbitrary changes or resetting HEAD — a more serious, integrity-relevant overstep where silent auto-recovery is the wrong default. Consistency with the new narrower safeguard is not worth trading away a broader safety property for a mechanism this task did not set out to change.
- Rejected: Harmonizing `worktree_snapshot_guard` to auto-restore-and-record like the new checkpoints — would make the subprocess/psmux path consistent with Agent-mode, but at the cost of silently auto-recovering from a class of overstep (arbitrary git-state mutation, not just `_mill/` deletion) where blocking is the safer, currently-correct default; out of scope per this task's own Scope (Out) exclusion of `worktree_snapshot_guard` changes.
- Rejected: Narrowing `worktree_snapshot_guard`'s scope so `_mill/`-only deletions specifically get the new auto-restore treatment while everything else it catches still hard-blocks — technically possible but adds conditional branching to a mechanism this task explicitly left unchanged, for a benefit (consistency) that doesn't offset the added complexity in a function neither incident nor this task's exploration found reason to touch.

## Testing

- **TDD candidate:** `_treeguard.check_and_restore` is the core unit to build test-first.
- **Fixture:** a tempfile-based local git repo (matching `plugins/mill/unit_tests/`'s existing in-memory/tempfile convention — no real git worktree or LLM needed). Initialize a repo, create and commit a `_mill/` tree with a few files (e.g. `status.md`, `discussion.md`, `briefs/x.md`, `reviews/y.md`), then exercise scenarios:
  - **No deletion:** `check_and_restore` on a clean tree returns `triggered=False`, `restored_paths=[]`, makes no git calls beyond the status check, and leaves the tree untouched.
  - **Single file deleted:** delete one tracked file on disk (not via git), call `check_and_restore`, assert the file is restored, `triggered=True`, `restored_paths` reflects what was found.
  - **Multiple files deleted across subdirectories:** delete e.g. `status.md` and a file under `briefs/` simultaneously, assert both are restored by the single `git checkout HEAD -- <path1> <path2>` call (both paths named explicitly, not the whole subtree).
  - **Staged deletion (`git rm` without commit):** assert this is also detected and restored, per the `D ` status-code case in the Decisions section.
  - **Untracked file present alongside a real deletion:** an untracked file under `_mill/` (e.g. a `.scratch`-style leftover, if such a case is reachable) must not itself trigger a restore or be touched — only tracked-deletion status codes (` D`/`D `) trigger the restore path; confirm `check_and_restore` does not mis-trigger on `??` (untracked) porcelain lines.
  - **Legitimate uncommitted modification alongside a real deletion (regression case for review round 2's GAP):** modify one tracked file in place (e.g. append a line to `status.md`, matching an in-flight `_status.append_phase` write) without committing, and separately delete a different tracked file on disk. Call `check_and_restore` and assert: the deleted file is restored; the modified-but-not-deleted file's uncommitted change is left completely intact (not reverted to HEAD) — proving the restore targets exactly the `D`-flagged paths and never touches ` M` (modified) paths.
- **Record shape:** assert the returned dict's `restored_paths` and `timestamp` fields are populated correctly when `record=True`, and that no audit-record side effect occurs when `record=False` (useful for a caller that wants detection without the status.md-append side effect, though every current call site in this task uses `record=True`). `timestamp` reflects the wall-clock time of the check itself and is always populated when `triggered=True`, independent of `record` — `record` only gates whether the status.md audit-append side effect happens, not whether the returned dict carries a timestamp.
- **Integration-level (manual/SKILL-level, not a new automated test):** after wiring, a full mill-start/mill-plan/mill-go dry run through at least one review round should be manually confirmed to still work end-to-end (the new check adds a git status call and, on the non-triggering path, a no-op — should be invisible to normal operation). No new integration test is required beyond this since `integration_tests/` already exercises the review loops end-to-end and would surface a wiring mistake.
- **Deliberately not covered:** all fixtures above commit the `_mill/` tree before exercising deletion, matching `check_and_restore`'s actual guarantee. The round-fresh-uncommitted-artifact case (see Decisions: "Uncommitted round-fresh artifacts are an accepted residual risk") is intentionally not exercised by any test here — there is nothing for `check_and_restore` to detect or restore in that case, so a test would only demonstrate the accepted gap, not the helper's behavior.

## Q&A log

- **Q:** Should the widened safeguard be a reusable Python helper or inlined Bash prose repeated per-skill? **A:** [auto-pick] New helper module `_treeguard.py` with `check_and_restore(worktree, tracked_root="_mill", *, record=True) -> dict`. **Why:** required for the unit test to mean anything; avoids tripling near-identical Bash prose across three SKILL.md docs.
- **Q:** Which skills should adopt the widened safeguard? **A:** [auto-pick] All three — mill-start, mill-plan, mill-go. **Why:** identical review-loop architecture, identical exposure to the bug class; no principled reason to protect one and not the others.
- **Q:** When a deletion is detected, what scope gets restored? **A:** [auto-pick, revised in round 2 — see below] One `git status --porcelain -- _mill/` check; the detection query is subtree-scoped, but the restore itself only checks out the exact paths reported as deleted (never a blanket whole-subtree checkout). **Why:** everything under `_mill/` is always committed before a review round, so restoring already-committed deleted content is safe; scoping the restore to exactly the deleted paths (rather than the whole subtree) additionally avoids clobbering any other tracked file's legitimate uncommitted modification — see the round 2 GAP entry below for why this revision was necessary.
- **Q:** Should this task also close the Agent-mode gap in `worktree_snapshot_guard` (which only wraps subprocess/psmux's `run()`, not the split prepare/finalize Agent-mode path)? **A:** [auto-pick] Yes — call `check_and_restore` at the orchestrator level immediately before Agent-mode's `--stage prepare` and immediately after `--stage finalize` returns, for every review loop. **Why:** the orchestrator is the only party present across the whole prepare → Agent-dispatch → finalize window, since prepare and finalize are separate CLI processes with the actual reviewer running out-of-process between them — no Python-level function call can bracket that span.
- **Q:** Should detection be silent, recorded, or blocking? **A:** [auto-pick] Restore and record — append a timestamp + restored-paths line to a new append-only `## Tracked-file recovery log` section in status.md; do not block. **Why:** the issue's whole premise is that silent recovery is the problem; blocking every occurrence is disproportionate given recovery is always clean and lossless.
- **Q:** What test coverage should this get? **A:** [auto-pick] Unit test `test-treeguard.py` using a tempfile git fixture covering no-deletion, single-file, multi-file, and staged-deletion cases. **Why:** matches the project's existing tempfile/in-memory unit-test convention; no real git worktree or LLM needed to exercise this helper.
- **Q:** [Review r1 GAP] Round-fresh brief/`.out.md`/review-file writes are uncommitted until end-of-round — since `git checkout HEAD --` can't restore what was never committed, and an untracked file's deletion leaves no `git status --porcelain` trace, is this an accepted residual risk or does it require mitigation (e.g. committing those writes immediately)? **A:** Accepted residual risk — documented in Decisions ("Uncommitted round-fresh artifacts are an accepted residual risk") and Scope (Out). **Why:** closing it fully means changing the batched end-of-round commit cadence that mill-start/mill-plan/mill-go's crash-recovery and round-audit-trail conventions depend on — that blast radius is well outside this task's scope of restoring already-committed `_mill/` content.
- **Q:** [Review r2 GAP] mill-go's per-batch Code Review loop appends `reviewing-{batch_name}-r{N}` to status.md with no commit before that round's Agent-mode `--stage prepare` dispatch — a whole-subtree `git checkout HEAD -- _mill/` at the pre-prepare checkpoint would silently discard that uncommitted, not-yet-committed phase row (which `_status.phase_entry_timestamp` reads for crash-recovery freshness checks). Require an immediate commit before every bracketing checkpoint, make the restore diff-aware, or accept this as a second residual risk? **A:** Made the restore diff-aware — revised "Detection query and restore granularity" so `check_and_restore` restores exactly the paths reported as deleted (` D`/`D ` status codes), never a blanket whole-subtree checkout. **Why:** a legitimate uncommitted modification (like the fresh `append_phase` row) shows as ` M`, not ` D`, so it's structurally excluded from the restore pathspec regardless of when the checkpoint runs relative to that write — this closes the gap without requiring a commit-cadence change (which round 1's GAP already ruled out as too invasive) and without accepting a second residual risk, since the fix is a strict improvement over the round-1 design with no added complexity.
