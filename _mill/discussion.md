## Problem

A piecewise run of `plugins/mill/unit_tests/` (forced after the default parallel `run-all.py` invocation silently stalled with zero output) surfaced three independent, pre-existing breakages — none caused by the unrelated markdown-only task that triggered the sweep. All three were re-reproduced live during this discussion, with the exact failure point traced in each case via `PYTHONFAULTHANDLER=1` + `SIGABRT` stack dumps and direct source reading. None of them are flaky — every failure is deterministic given the current code.

The three GH issues bundled into this task (#779, #778, #777) turn out to cover **four** distinct broken test-code sites, because #779 bundles two files with unrelated causes:

1. **`test-claude-sub.py` hangs** (part of #779) — scenario `S5` ("keep-alive true, error mid-call when wrapper owns session", `test-claude-sub.py:258`) never mocks `_wait_for_idle_stable`. The real `millpy-claude-sub.py:_wait_for_idle_stable` (`millpy-claude-sub.py:142`) runs for real against a mocked-but-static `capture_pane` return value, looping on real `time.sleep`/`time.monotonic` for up to ~5.25 minutes (`PROCESSING_WAIT_TIMEOUT_S = 15`s Phase-1 + up to `RESPONSE_POLL_TIMEOUT_S["bulk"] = 300`s Phase-2 bulk-mode default, `millpy-claude-sub.py:29,33`) before it would resolve on its own — indistinguishable from an indefinite hang under any bounded test timeout.
2. **`test-millpy-claim.py` hangs** (the other file in #779) — `_make_stub_map()` (`test-millpy-claim.py:79`) never stubs the `wiki` package that `millpy-claim.py` imports via `from wiki import _client as wiki` (`millpy-claim.py:46`). Every scenario's `mod.main()` call reaches the real `wiki._client.list_tasks_brief()` → `_dispatch()` → `_ensure_daemon()` (`wiki/_client.py:656`), which tries to spawn/reach a real background wiki daemon and polls for up to `SPAWN_TIMEOUT` seconds — again reading as an indefinite hang.
3. **`test-millpy-spawn.py`: 9/16 ERROR on `/fake/wiki/tasks.json`** (#778) — same root shape as #2: the 9 failing tests' stub maps register a module literally named `"_wiki"`, but `millpy-spawn.py` also imports `from wiki import _client as wiki` (`millpy-spawn.py:51`), so the `"_wiki"` stub never intercepts it. The real `wiki._client` code runs against the fake `/fake/wiki` path returned by the (correctly) mocked `_paths.resolve_wiki_path`, producing `[Errno 2] No such file or directory: '/fake/wiki/tasks.json'`. The 7 passing tests in the same file simply don't exercise a `wiki._client`-reaching path. **A correct, already-working fix pattern already exists elsewhere in this same file** (`test-millpy-spawn.py:1301-1339`, in a test not among the 9 failing ones): it injects `sys.modules["wiki._client"] = <mock>` directly and additionally sets `mod.wiki = <mock>` right after `exec_module` as a belt-and-suspenders safety net.
4. **Stuck/success envelope bug in 3 files** (#777: `test-agent-mode-dispatch.py`, `test-bg-json-contract.py`, `test-millpy-merge-in-subagent.py`) — commit `6d92c82d` (2026-07-29, "Self-discovered mill pipeline bugs: … truncated commit_sha in implementer reports") added strict `_is_valid_commit_sha` validation (`_implementer_common.py:386-391`, requiring exactly 40 or 64 lowercase hex chars) to `_forward_output`'s final commit_sha-correction step, as a genuine fix for issue #744 (agents self-reporting untrusted/truncated commit SHAs). This changed the corrective `else` branch (`_implementer_common.py:1800-1808`) from a harmless passthrough (`print(json.dumps(parsed))`, preserving whatever status was already there) into an unconditional hard override to `{"status": "stuck", "stuck_type": "logic", ...}`. Two things follow from this one commit:
   - All three affected test files use placeholder fake commit SHAs in their mocked `git rev-parse HEAD` output that are not valid 40/64-char lowercase hex (`"abc1234"`, `"abc"`, `"xyz"`, `"sha_123"`, `"sha_456"`) — these now fail `_is_valid_commit_sha` and get demoted to `stuck/logic`, which is what the 5+ failing assertions across the three files observe.
   - Independent of the test fixtures, the `else` branch is reached not only on a genuine "self-reported success but corrective SHA came back invalid" case, but also as the generic passthrough for **any** other already-classified non-success status (e.g. an incoming `{"status": "stuck", "stuck_type": "transient", ...}` or `{"status": "stuck", "stuck_type": "verify", ...}` envelope) that falls through the `status == "success"` and `status == "incomplete"` branches above it. If the corrective `git rev-parse HEAD` call ever fails or returns something non-hex in that passthrough case in real production (not just in tests), a correctly-classified `stuck/transient` or `stuck/verify` report is silently corrupted into `stuck/logic` — which would misroute mill-go's retry-vs-halt recovery logic. This is a real latent defect introduced by `6d92c82d`, not only a test-fixture staleness issue.

## Scope

**In:**
- `test-claude-sub.py` S5: add the missing `_wait_for_idle_stable` mock.
- `test-millpy-claim.py`: add a correct `wiki._client` stub (following the proven pattern in `test-millpy-spawn.py`) to every scenario that currently has none.
- `test-millpy-spawn.py`: fix the 9 failing scenarios' stub maps to inject `sys.modules["wiki._client"]` (and `mod.wiki`) instead of the ineffective `"_wiki"` entry, matching the already-working pattern in the same file.
- `_implementer_common.py`: narrow the `_forward_output` corrective `else` branch (`_implementer_common.py:1790-1809`) so the "invalid corrective SHA → demote to stuck/logic" behavior only fires on the actual `status == "success"` self-report path; a passthrough of an already-classified non-success envelope (e.g. `stuck/transient`, `stuck/verify`) must never be routed through commit-SHA validation/correction at all.
- `test-agent-mode-dispatch.py`, `test-bg-json-contract.py`, `test-millpy-merge-in-subagent.py`: update fake commit-SHA constants used in mocked `git rev-parse HEAD` output to well-formed 40-char lowercase hex strings, so these tests exercise the intended code paths under the (correct) stricter validation.
- Verify by running the **full** suite via plain `run-all.py` (default parallel mode, no `--only`/`--sequential`) and confirming zero failures/errors/hangs — this is the real regression check, since the original discovery was that a single hang silently stalls the entire parallel batch.

**Out:**
- Adding a per-subprocess timeout to `run-all.py`'s `_run_one` (`run-all.py:24-36`, which currently calls `subprocess.run(...)` with no `timeout=`). This is a real, separate robustness gap — a future hang in any test would again silently stall the whole parallel batch — but it's not one of the three reported breakages. Flagged here as a candidate follow-up task, not part of this task's scope.
- Any change to `millpy-claude-sub.py`, `wiki/_client.py`, or `millpy-spawn.py`/`millpy-claim.py` production logic. All of #779 and #778 are pure test-fixture bugs; production code is correct as-is.
- Any change to the `_is_valid_commit_sha` validation itself or to the #744 postmortem fix's intent — it stays exactly as strict as commit `6d92c82d` made it. Only the passthrough branch's scope of applicability narrows.
- Any other file in `plugins/mill/unit_tests/` not named above; this sweep found exactly these four broken sites.

## Decisions

### test-claude-sub.py S5 fix

- Decision: add `mock.patch.object(mod, "_wait_for_idle_stable", return_value=False)` to S5's `with` block (`test-claude-sub.py:284-295`).
- Rationale: `False` drives `main()` into the real `RuntimeError(f"response-poll timeout: ...")` path (`millpy-claude-sub.py:351-355`), which is caught, calls `_psmux.kill_session` (mocked, since `session_owned_by_us=True`), and returns `1` — matching S5's existing, unmodified assertions (`assert m_kill.call_count > 0`, `assert ret == 1`) exactly. No other line in S5 needs to change.
- Rejected: mocking `return_value=True` and rewriting S5's assertions for a success path — contradicts the scenario's own name and stated intent ("error mid-call"), and would require reworking assertions that are actually correct as written.

### wiki stub fix (test-millpy-claim.py and test-millpy-spawn.py)

- Decision: follow the pattern already proven to work in `test-millpy-spawn.py:1301-1339` — inject `sys.modules["wiki._client"] = <mock>` directly (saving/restoring the prior value in the same try/finally as the rest of the stub map), and additionally set `mod.wiki = <mock>` immediately after `spec.loader.exec_module(mod)` as a belt-and-suspenders safety net for the module-level `from wiki import _client as wiki` binding.
- Rationale: `from wiki import _client as wiki` resolves through `sys.modules["wiki._client"]` when present — a stub named `"_wiki"` (as used by the 9 failing `test-millpy-spawn.py` scenarios and entirely absent in `test-millpy-claim.py`) never intercepts it. This exact fix is already working elsewhere in `test-millpy-spawn.py`, so it's mechanical, low-risk, and introduces no new pattern into the suite.
- Rejected: patching `wiki._client.list_tasks_brief` (or other individual functions) via string-target `unittest.mock.patch` after import — more indirection, no precedent in this file, higher risk of not matching how `main()` actually references the name at call time.

### _forward_output stuck-passthrough fix

- Decision: fix both the test fixtures and the production code. (a) Update the fake SHA constants in the three affected test files to well-formed 40-char lowercase hex strings. (b) In `_implementer_common.py`, gate the commit-SHA-correction block (`_implementer_common.py:1790-1809`) so it only executes when `parsed.get("status") == "success"` at that point — anything else (a passthrough `stuck/*` envelope that reached this point without matching the `"success"` or `"incomplete"` branches above) should print unchanged, exactly as it did before commit `6d92c82d`.
- Rationale: the passthrough corruption (any non-success status silently becoming `stuck/logic` if the corrective `git rev-parse HEAD` call fails validation) is a real latent bug independent of the tests — the tests merely expose it via implausible fake SHAs. Fixing only the fixtures would leave production code able to corrupt a legitimate `stuck/transient`/`stuck/verify` report into `stuck/logic` any time the corrective rev-parse call in that branch fails for real, which would misroute mill-go's retry-vs-halt logic downstream.
- Rejected: test-fixture-only fix — faster, but leaves the described production defect in place.

## Technical context

- `plugins/mill/unit_tests/run-all.py` — the sequential/parallel test runner. `_run_one` (`run-all.py:24-36`) spawns each `test-*.py` as a `subprocess.run(..., capture_output=True)` with **no timeout**, which is why one hanging file silently stalls the entire default parallel run (`ThreadPoolExecutor` workers all block on `as_completed`, no per-test output until the batch finishes or is killed).
- `millpy-claude-sub.py` (`plugins/mill/scripts/millpy-claude-sub.py`) — `main()` (`:227`) unconditionally calls `_wait_for_idle_stable(session_name, poll_timeout_s)` at Step 11 (`:351`) after building/sending the claude launch command or reuse keystrokes, regardless of which of the two session-acquisition branches (reuse vs. create) was taken. Every `main()`-driving scenario in `test-claude-sub.py` therefore needs a `_wait_for_idle_stable` mock unless it errors out earlier (S2, S3, S8 legitimately bail before Step 11).
- `wiki/_client.py` — `_ensure_daemon` (`:620-662`) is the real wiki-daemon connection/spawn logic; it reads/writes a `.wiki-daemon.json` state file under the resolved wiki path and, on a cold start, calls `_spawn_server` then polls up to `SPAWN_TIMEOUT` seconds via `time.sleep(0.1)` (`:656`). Any test that reaches this function without a `wiki._client` stub will exercise this real polling loop against whatever fake path `_paths.resolve_wiki_path` was mocked to return.
- `_implementer_common.py:_forward_output` (`:1559-1809+`) is the single shared envelope-classification/emission helper used by `millpy-implement.py`, `millpy-fix.py`, and `millpy-merge-in-subagent.py` (via `finalize_from_output`/direct call) — this is the "shared envelope-classification path" issue #777's own hypothesis pointed at, confirmed correct by this investigation. `_is_valid_commit_sha`/`_COMMIT_SHA_RE` live at `_implementer_common.py:386-391`.
- `_attach_commit_sha` (`_implementer_common.py:394+`) is an existing, separate helper used elsewhere in this file (e.g. `_go_build_tag_retiering_stuck`'s result, `_completeness_result`) to stamp a commit SHA onto a stuck dict without the strict-validation/demotion behavior. It is **not** used by the passthrough fix in scope here — per the Decision below, the non-success passthrough branch prints `parsed` unchanged (no commit_sha touch at all, matching pre-`6d92c82d` behavior); this bullet is retained only as codebase context in case a later task wants a stuck envelope to carry a validated commit_sha.

## Constraints

- The fix to `_implementer_common.py` must preserve the `6d92c82d`/#744 behavior on the actual success path exactly as-is: an agent-self-reported `commit_sha` on a `status: success` envelope must still be replaced by a freshly-validated `git rev-parse HEAD` value, and must still demote to `stuck/logic` if that corrective value fails `_is_valid_commit_sha`. Only the non-success passthrough case changes.
- Do not touch `millpy-claude-sub.py`, `wiki/_client.py`, `millpy-spawn.py`, or `millpy-claim.py` production code — all four fixes in scope are test-side (three fixture/mocking bugs) plus the one narrowly-scoped `_implementer_common.py` passthrough-gating change.
- Every fix must be verified against the **specific previously-failing test(s)** it targets AND against a full `run-all.py` run (default parallel mode) with zero failures/errors/hangs, per this repo's `mill-unit-test-suite-breakage`-flavored acceptance bar described in Scope above.
