## Batch Scope

Fixes GitHub #689 and #698 at their shared root: `_plan_dag.iter_batch_verifies()` (line 359) replays every batch's `verify:` command in DAG order with no notion that a later batch might have reverted an earlier batch's target, and no notion of which batches have actually been implemented yet. This batch adds both filters directly inside `iter_batch_verifies()` so every caller gets the corrected behavior automatically (no wrapper, no call-site duplication — see the overview's "`iter_batch_verifies()` is the single choke point" Shared Decision). Card 3 adds the metadata-driven target-removal filter (Decision 2/3); Card 4 adds the `status_path`-gated approved-batch filter (Decision 4) and composes it with Card 3's filter exactly as specified below. Depends on batch `review-common-parse-deletes` for the new `parse_deletes()` import. External interface the next batch (`verify-replay-callers-wiring`) consumes: `iter_batch_verifies(plan_dir, hub_root, git_root, *, status_path: Path | None = None)` — the new keyword-only parameter, strictly additive (omitting it reproduces today's behavior byte-for-byte per the overview's "`status_path` kwarg is strictly additive" Shared Decision).

## Cards

### Card 3: Metadata-driven target-removal suppression in `iter_batch_verifies()`

- **Context:**
  - `plugins/mill/scripts/_review_common.py`
  - `_mill/discussion.md`
- **Edits:**
  - `plugins/mill/scripts/_plan_dag.py`
  - `plugins/mill/unit_tests/test-plan-dag.py`
- **Creates:** none
- **Deletes:** none
- **Moves:** none
- **Requirements:** In `plugins/mill/scripts/_plan_dag.py`, add `from _review_common import parse_deletes, parse_moves` to the module's imports. Inside `iter_batch_verifies(plan_dir, hub_root, git_root)` (line 359), after `order = topo_order(batches)` and `file_by_name = {...}` are computed (lines 401-405), build a per-batch removal map: for every batch `name` in `batches` (not just those in `order` — use the same `file_by_name` lookup), compute `removed_by_batch[name] = {normalize(t) for t in parse_deletes(plan_dir / file_ref)} | {normalize(src) for src, _dst in parse_moves(plan_dir / file_ref)}` where `file_ref = file_by_name.get(name)` (skip a batch with no `file_ref`, mirroring the existing `if not file_ref: continue` guard in the main loop) and `normalize(token)` strips one leading `"./"` prefix and any trailing `"/"` from `token`. Then, in the main `for name in order:` loop that builds the `commands` list (lines 408-415), before appending `(name, command, cwd)`, determine whether `command` references a "removed-later" target: tokenize `command` with `shlex.split(command)` (add `import shlex` to the module's imports); a token is a *path candidate* iff it does not start with `"-"`, contains `"/"`, and does not contain `"*"`, `"?"`, or the literal substring `"..."`; for each path-candidate token, normalize it the same way as above and check whether it exact-matches any entry in `removed_by_batch[later_name]` for any `later_name` that appears strictly after `name` in `order` (i.e. at a higher index). If **any** path-candidate token matches **any** strictly-later batch's removal set, skip this `(name, command, cwd)` entirely — do not append it to `commands` — this is existential and all-or-nothing over the whole command, not per-token. A batch's own removal declarations, and any earlier batch's, must NOT affect its own suppression (only strictly-later removals count — this also means a batch never suppresses itself even if it deletes a path its own `verify:` references). This card intentionally does NOT yet consult batch approval state — every batch counts as a valid "remover" regardless of implementation status; Card 4 narrows that. Update the function's docstring to describe the new suppression semantics (a target-removed-later batch's verify is silently dropped from the returned list, same contract shape as the existing `verify: null` skip) and to note the known limitations: exact-match only (no directory-containment — `Deletes: tools/x/` does not suppress a verify referencing `tools/x/cmd/app`), all-or-nothing per command (a multi-target command is fully suppressed if any one target matches), purely lexical matching with no `cwd`/`root` coordinate resolution (a verify authored in a different coordinate space than the `Deletes:`/`Moves:` tokens may fail to match and will simply keep running, never be falsely suppressed), and `shlex.split`'s default `posix=True` tokenization treating backslash as an escape character regardless of host OS (a verify command containing a Windows-style backslash path may have its tokens corrupted before the path-candidate check runs, so such a command will not be reliably suppressed even when its target is genuinely removed later). See `_mill/discussion.md` Decision 2 for the full rationale and worked examples (`#689`'s exact fixture: batches 1-3 `verify: go build ./tools/x/`, batch 4 `Deletes: tools/x/` and `verify: go build ./...` — batches 1-3 must be silently absent from the returned list, batch 4 present).
- **Commit:** `feat(plan-dag): suppress iter_batch_verifies() entries whose target a later batch declares removed`

### Card 4: `status_path`-gated approved-batch filter, composed with Card 3

- **Context:**
  - `plugins/mill/scripts/_status.py`
- **Edits:**
  - `plugins/mill/scripts/_plan_dag.py`
  - `plugins/mill/unit_tests/test-plan-dag.py`
- **Creates:** none
- **Deletes:** none
- **Moves:** none
- **Requirements:** In `plugins/mill/scripts/_plan_dag.py`, add `import _status` to the module's imports. Change `iter_batch_verifies`'s signature to `iter_batch_verifies(plan_dir, hub_root, git_root, *, status_path=None)`. When `status_path` is not `None`: call `states = {}` then try `for b in _status.read_batches(status_path): states[b.get("name")] = b.get("state")`, wrapped so that a `ValueError` raised by `_status.read_batches` (malformed `## Batches` fenced-yaml block — see `_status._find_batches_block`'s documented `ValueError` cases) is caught and degrades to returning `[]` from `iter_batch_verifies` immediately, mirroring the function's existing `PlanDAGError`-degrades-to-`[]` behavior for a malformed plan overview (do not let `ValueError` propagate to the caller). When `status_path` is `None` (the default, omitted): skip all of the following state-filter logic entirely — no `_status` call is made, and the function's behavior is byte-for-byte identical to before this card (this is the "strictly additive" contract from the overview's Shared Decision). When `status_path` is provided and `read_batches` succeeds: (1) exclude a batch `name` from the returned `commands` list entirely when `states.get(name) != "approved"` (covers a `status.md` with no `## Batches` section at all — `read_batches` returns `[]`, `states` stays empty, every batch's lookup is `None`, every batch is excluded — this is the #698 fix); (2) narrow Card 3's removal-map construction so that `removed_by_batch[name]` only contributes to suppression when `states.get(name) == "approved"` — concretely, when checking whether a path-candidate token matches a strictly-later batch's removal set, skip any `later_name` whose `states.get(later_name) != "approved"` (that later batch has not actually executed its declared removal yet, so its target still exists — do not suppress on its account). This composition is exactly the discussion-review-round-1 gap fix: with batches 1-3 `approved` (`verify: go build ./tools/x/`) and batch 4 `pending` with `Deletes: tools/x/`, batches 1-3's verifies must still be returned (not suppressed, since the only declarer of `tools/x/`'s removal is not yet approved) while batch 4's own triple is excluded (not approved). If batch 4's state were `approved` instead, batches 1-3 would then be suppressed. See `_mill/discussion.md` Decision 2's "Composition with Decision 4's `status_path` filter" paragraph and Decision 4 in full for the rationale, plus the malformed-`## Batches` NOTE.
- **Commit:** `feat(plan-dag): add status_path kwarg to iter_batch_verifies for approved-batch gating`
