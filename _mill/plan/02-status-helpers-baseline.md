### Card 4: `--module-wide-only` flag for `--stage baseline`

- **Context:** none
- **Edits:**
  - `plugins/mill/scripts/millpy-implement.py`
  - `plugins/mill/unit_tests/test-millpy-implement.py`
- **Creates:** none
- **Deletes:** none
- **Moves:** none
- **Requirements:** Add a `--module-wide-only` boolean CLI flag (argparse `action="store_true"`, default `False`) to `millpy-implement.py`'s `--stage baseline` argument handling, and thread it into `_run_baseline_stage` as a new `module_wide_only: bool` parameter.
  Inside `_run_baseline_stage`, when `module_wide_only` is `True`, the fix must bypass the ENTIRE per-batch computation path — not just the final per-batch loop body. Specifically: skip the call to `_enumerate_batch_verify_triples(plan_base, project_root, git_root)` and the `status_by_name`-lookup loop that follows it (the block that currently populates `batches_needing_computation`/`cached_batches` at lines 295-305) entirely, and instead bind `batches_needing_computation = []` and `cached_batches = []` directly. This is required, not optional: `batches_needing_computation` is populated by reading every batch FILE's own `verify:` frontmatter directly off disk (`_enumerate_batch_verify_triples`), completely independent of whether `## Batches` exists in `status.md` — so on a genuine speculative early launch (this plan alone has 6 batches with non-null `verify:`), that list is non-empty regardless of `## Batches`'s existence, which forces the existing `if not batches_needing_computation:` branch check (Case A) to evaluate `False` and fall through to Case B (parent-branch resolution, a full shared checkout via `_verify_baseline._checkout_parent_branch`, and `_link_dependency_dirs` per distinct cwd fragment) even though no per-batch command is ever actually going to run. Binding both lists to `[]` directly (bypassing enumeration rather than computing it and discarding the result) makes the existing `if not batches_needing_computation:` check naturally take Case A — the existing, already-correct "nothing per-batch needs computing" path, which runs the module-wide substage standalone with no shared checkout at all. Do not attempt to reach Case A by any other route (e.g. letting enumeration run and then clearing the list afterward) — that would still pay the enumeration cost for no benefit and risks a future edit re-introducing the Case B fallthrough if the branch condition is ever refactored to check something other than list emptiness.
  The module-wide substage (the `if module_wide_needs_computation:` block, which calls `_verify_baseline._run_module_wide_verify_algorithm` and `_status.set_module_verify_baseline`, reached via Case A's `_run_module_wide_standalone` path) must still run exactly as it does today, completely unaffected by this flag.
  The existing per-batch JSON summary line (currently printed with shape `{"stage": "baseline", "substage": "per_batch", "computed": [...], "cached": [...], "errored": {...}}`) must still print exactly once when `--module-wide-only` is set, with `"computed": [], "cached": [], "errored": {}` — all three lists/dicts empty, which falls out naturally from `batches_needing_computation`/`cached_batches` both being bound to `[]` and Case A's existing print logic requiring no further change. This is a distinct, empty-but-present line, not an omitted one.
  Add `test_baseline_stage_module_wide_only_skips_per_batch_loop` to `plugins/mill/unit_tests/test-millpy-implement.py` — NOT `test-verify-baseline.py`, which has no CLI-invocation fixture convention at all (its existing `_case_*` functions call `_verify_baseline.compute_baseline`/`compute_batch_baselines` directly with a mocked `_subprocess_util.run`, no config/worktree/status.md fixture, no `--stage` argument of any kind). `test-millpy-implement.py` is the file with the matching, already-established convention: it loads `millpy-implement.py` via `importlib.util.spec_from_file_location` (see its module-level `_spec`/`_IMPLEMENT_PATH` setup) and already has multiple existing tests that call `self._run_main(["--stage", "baseline"])` against tempdir config/worktree/status.md fixtures with `_verify_baseline.compute_baseline` mocked out (e.g. `test_baseline_stage_cwd_hub_derives_relative_fragment_for_compute_baseline`, `test_baseline_stage_cwd_git_root_passes_none_relative_fragment`) — read those existing tests first and match their fixture-building helpers exactly. The new test invokes `self._run_main(["--stage", "baseline", "--module-wide-only"])` against a fixture plan directory containing at least one batch file with a non-null `verify:` command, and a fixture `status.md` that has NO `## Batches` section at all (simulating the pre-`## Prepare` scenario) and asserts: (a) the call completes without raising; (b) the printed per-batch JSON line has `computed: []`, `cached: []`, `errored: {}`; (c) `_verify_baseline._checkout_parent_branch` (referenced through the same `millpy_implement.` module-attribute mocking pattern the existing tests in this file already use for `compute_baseline`) is never invoked — this is the assertion that specifically catches the Case-B-fallthrough bug this fix closes, distinguishing "the loop body didn't run" from "the expensive shared-checkout setup didn't run either"; (d) when the fixture's config declares a module-wide verify command, the module-wide substage's own result is still written to `status.md`'s `module_verify_baseline:` field (confirming the module-wide half is genuinely unaffected by the flag).
